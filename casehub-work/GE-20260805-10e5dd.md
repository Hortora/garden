### Symptom

Queue entries displayed after escalation show `viewName: null` even though the entry is in a valid view with a known name.

### Context

`CaseQueueService.escalate(entryId, tenancyId, targetViewId)` moves a queue entry from one view to another. During the move, it sets `viewId` to the target but sets `viewName` to `null`:

```java
// CaseQueueService.escalate() — line 87-88
entry.setViewId(targetViewId);
entry.setViewName(null);        // ← undocumented: viewName is NOT resolved
```

The previous view's name IS preserved in `previousViewName`, but the new view's name is not populated. This is not documented in the API — the method signature takes `targetViewId` (UUID) and there is no mechanism to pass or resolve the view name.

### Root cause

The `escalate()` method only receives a `UUID targetViewId`. It does not inject or call `SubjectViewStore` to resolve the view name. The `viewName` field is set to `null` as a side effect.

### Fix

Callers that display queue entries must resolve `viewName` from the cached `SubjectViewStore` view ID → name mapping when `entry.getViewName()` returns `null`:

```java
String resolvedViewName = entry.getViewName() != null
    ? entry.getViewName()
    : viewNameMapping.getOrDefault(entry.getViewId(), null);
```

Build `viewNameMapping` at `@PostConstruct` from `SubjectViewStore.findByTenancy()`:

```java
Map<UUID, String> viewNameMapping = new HashMap<>();
for (SubjectViewSpec view : viewStore.findByTenancy(tenancyId)) {
    viewNameMapping.put(view.id(), view.name());
}
```

### Why this is non-obvious

The `CaseQueueEntry` model has both `viewId` and `viewName` fields. A developer reading the model would expect `viewName` to always be populated when `viewId` is set. The `escalate()` method's Javadoc does not mention that it nulls `viewName`. The behaviour is only discoverable by reading the implementation source.
