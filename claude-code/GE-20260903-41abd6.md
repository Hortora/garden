### Symptom

`cannot find symbol` compile errors after moving Java source files between Maven modules using `ide_move_file`. The IDE reports success for each move — `affectedFiles` lists the consuming files as updated — but the build fails with missing symbol errors for types that were just moved.

### Context

Extracting types from a monolithic module into a new API module while keeping the same Java package name. Example: moving 10 types from `blocks/src/main/java/io/casehub/blocks/summarisation/` to `summarisation-api/src/main/java/io/casehub/blocks/summarisation/`. The package stays `io.casehub.blocks.summarisation` — only the Maven artifact changes.

Test files in subpackages (e.g., `io.casehub.blocks.summarisation.examples.logistics`) had `import io.casehub.blocks.summarisation.*` to access the types.

### What was tried

Used `ide_move_file` for each of the 10 files. Each move returned `success: true` with `affectedFiles` listing the consuming test files. Expected the IDE to handle reference updates correctly since the package name was unchanged.

### Root cause

`ide_move_file` treats a cross-module move as the type "leaving" the source module's copy of the package. It removes `import io.casehub.blocks.summarisation.*` from consuming files in the source module — as if the wildcard no longer covers those types. But the package name is identical; the types are still in `io.casehub.blocks.summarisation`, just in a different Maven artifact. The wildcard import is still valid (the source module depends on the API module via `<dependency>`).

The IDE's import cleanup logic doesn't account for Maven module boundaries when evaluating whether a wildcard import is still needed — it only sees that the source file moved out of the module's source tree.

### Fix

After a batch of cross-module same-package moves, check the git diff for incorrectly removed imports:

```bash
git diff --cached -- "*.java" | grep "^-import"
```

Restore any removed imports that reference the unchanged package. Use `ide_replace_text_in_file` to re-add them:

```
ide_replace_text_in_file(
    file="path/to/Test.java",
    searchText="import org.junit.jupiter.api.BeforeEach;",
    replaceText="import io.casehub.blocks.summarisation.*;\nimport org.junit.jupiter.api.BeforeEach;"
)
```

### Why this is non-obvious

The IDE reports success for each move operation. The `affectedFiles` response lists consuming files, suggesting they were correctly updated. There is no warning about removed imports. The compile failure is the only signal — and the error messages (`cannot find symbol`) point at the consuming files, not at the move operation that caused the problem.

The natural assumption — "IDE refactoring handles imports automatically" — is specifically wrong for this scenario. The existing garden entry GE-20260511-ce1c9d recommends "Use IDE refactor (Move Class) when available — it handles both cases automatically." This is true for package changes but false for cross-module same-package moves via MCP.

### Alternatives considered

- Moving files with bash (cp + rm) — avoids the IDE import removal but doesn't update any references at all; worse overall
- Moving one file at a time and checking imports after each — catches the problem early but extremely tedious for batch extractions
- Post-move `ide_optimize_imports` — doesn't help because the imports were correctly removed from the IDE's perspective; optimize would not re-add them
