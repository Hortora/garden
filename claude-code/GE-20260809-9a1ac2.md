## Symptom

`ide_structural_search_replace` with pattern `new Foo<$T$>($args$)` matches callers using explicit type parameters (`new Foo<String>(...)`) but silently skips callers using diamond inference (`new Foo<>(...)`). No error — the replacement count just misses the diamond-inferred sites.

## Context

When updating constructor call sites across a codebase (e.g. adding a new field to a record), both `new Foo<>("a", "b")` and `new Foo<String>("a", "b")` exist. A single SSR pattern cannot match both forms.

## Root cause

IntelliJ's structural search treats `<$T$>` as requiring an explicit type argument. Diamond `<>` has no type argument in the AST — it's inferred by the compiler. The SSR engine doesn't unify these.

## Fix

Run two separate SSR passes:

1. First pass for explicit generics: pattern `new Foo<$T$>($a$, $b$)` → replacement `new Foo<$T$>($a$, $b$, null)`
2. Second pass for diamond: use `ide_replace_text_in_file` with literal text `new Foo<>(` → `new Foo<>(newArg, ` as a text-level replacement

Alternatively, use `grep` to find all remaining callers after the SSR pass and fix them with targeted `ide_replace_text_in_file` calls.

### Why this is non-obvious

SSR is presented as AST-aware — you'd expect it to handle all syntactic variants of the same semantic construct. The silent skip (no error, partial match count) makes it hard to detect missed sites until compilation fails.
