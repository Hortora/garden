## IntelliJ MCP ide_replace_text_in_file replaces ALL occurrences — structural code patterns produce silent duplication

### Symptom
After using `ide_replace_text_in_file` to append code after a function's closing pattern, the appended code appears multiple times in the file — once after every function that shares the same closing pattern. The tool reports `replacements: 3` but the caller expected exactly 1.

### Context
TypeScript (and Java) files commonly have multiple functions with identical structural endings — e.g., `return { model: newModel, violations: validateConstraints(newModel) };\n}` appeared in three functions (`addNode`, `removeNode`, `replaceNode`). Appending new functions after this pattern duplicated the new code three times.

### What was tried (didn't work)
- Using the closing pattern of the last function as the search text — the pattern was not unique across the file
- Trusting the `replacements: 1` expectation without checking the actual count in the response

### Root cause
`ide_replace_text_in_file` is a global find-and-replace — it replaces every occurrence of `searchText` in the file. There is no `maxReplacements` or `firstOnly` parameter. The tool always reports the actual replacement count in the response (`replacements: N`), but this requires the caller to check the count and react to unexpected values.

### Fix
Two strategies:

**1. Use unique anchoring text** — include enough surrounding context to make the match unique. Instead of matching a generic closing pattern, include the function name or a unique preceding line:

```typescript
// Bad — matches all three functions
searchText: "  return { model: newModel, violations: validateConstraints(newModel) };\n}"

// Good — matches only replaceNode
searchText: "  if (newNode.id !== nodeId) {\n    throw new Error(`Replacement node ID"
```

**2. Check the replacement count** — the response always includes `replacements: N`. If `N > 1` when you expected 1, the file has been corrupted and needs immediate cleanup. Read the file to assess the damage before proceeding.

### Why this is non-obvious
The tool name (`replace_text_in_file`) and description ("Find and replace text") suggest a single-target operation — most text editors default to "replace next" not "replace all." The structural similarity of code (many functions ending with the same return pattern, or many methods with identical signatures) creates non-unique matches that aren't apparent until the replacement count reveals the problem. The damage (duplicated code blocks interleaved between existing functions) is particularly hard to clean up because the duplicates are valid syntax — the file may even compile.
