## Symptom

Calling `ide_edit_member` with `member: "ClassName"` (matching the class
name) to edit a constructor replaces the **entire class declaration and
body** with just the provided content. The file is reduced to the package
statement, imports, and the constructor code — all fields, methods, inner
classes, and other members are destroyed.

The tool reports success: `"Replaced class 'ClassName' entirely"` — the
word "entirely" in the success message confirms the destructive behavior.

## Context

Editing a constructor in a Java class using the IntelliJ MCP structural
editing tools. The constructor shares its name with the class (as all
constructors do in Java), so `member: "SC2CbrRetentionObserver"` matches
both the constructor AND the class declaration.

## Root cause

`ide_edit_member` resolves the `member` parameter against all named
elements in the class. When the member name matches the class name itself,
it matches the class declaration rather than the constructor. The `content`
parameter then replaces the entire class declaration — from modifiers
through closing brace — with the provided text.

The tool's own documentation hints at this: "To edit a class/interface
declaration itself, set member to the class name." This is the intended
behavior for class-level edits, but it creates a trap when the intent is
to edit a constructor.

## Fix

Never use `ide_edit_member` to edit constructors. Use
`ide_replace_text_in_file` with a targeted search/replace instead:

```
ide_replace_text_in_file(
    file: "path/to/MyClass.java",
    searchText: "<old constructor signature and body>",
    replaceText: "<new constructor signature and body>")
```

If the file was already destroyed, recover immediately with:
```bash
git checkout -- path/to/MyClass.java
```

## Why this is non-obvious

The constructor's name IS the class name in Java — there is no way to
disambiguate via the `member` parameter alone. A developer would naturally
pass `member: "ClassName"` expecting to match the constructor, not realising
this matches the class declaration instead. The success message
("Replaced class 'ClassName' entirely") only makes sense in retrospect.

### Alternatives considered

- **Use `parameterCount` to disambiguate** — the tool supports this for
  overloaded methods, but it doesn't help when the match is class-vs-constructor
  (both share the name). Untested whether `parameterCount` forces constructor
  resolution over class resolution.
- **Use `line` parameter** — passing the constructor's line number might
  disambiguate, but this was not tested after the destructive incident.
