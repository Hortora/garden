### Symptom
`ide_replace_text_in_file` returns `{"success": true, "replacements": 2}` but the file on disk
still contains the original text. A subsequent `ide_build_project` shows 0 warnings (IntelliJ's
VFS has the replaced content), but `git commit` captures the un-replaced file from disk.

### Context
File was created via `ide_create_file` in the same session. `ide_replace_text_in_file` was called
to fix deprecated method calls. The IntelliJ VFS held the correct content (build passed with 0
warnings) but the filesystem file was never updated.

### What was tried (didn't work)
- Trusted the tool's success response and committed — the deprecated code shipped
- Used `ide_build_project` for verification — passed because IntelliJ reads from VFS, not disk

### Root cause
`ide_replace_text_in_file` modifies IntelliJ's Document model (VFS) but may not flush to disk
before the caller reads/commits the file via non-IntelliJ tools (git, cat, Read). This is the
same VFS→filesystem desync class as GE-20260717-886249 (ide_create_file) but affects replace
operations.

### Fix
After `ide_replace_text_in_file`, verify with a filesystem-level read (`Read` tool or `cat`) that
the change persisted. If not, use the `Edit` tool with `replace_all: true` as a reliable fallback
that writes directly to disk.

### Why this is non-obvious
The tool returns an explicit success response with replacement count. IntelliJ's own build
system confirms the change. Both indicators say "done" — but the file on disk is unchanged.
The failure is only visible when a non-IntelliJ tool (git) reads the file.
