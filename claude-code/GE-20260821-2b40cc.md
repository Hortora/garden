## IntelliJ MCP ide_refactor_rename completes silently on timeout — operations succeed despite error response

### Stack
IntelliJ MCP (intellij-index plugin), TypeScript monorepo

### Symptom
`ide_refactor_rename` returns a timeout error via MCP, leading the caller to assume the rename failed and retry or fall back to a different approach. But the file has already been renamed and all references across the project updated successfully.

### Context
Renaming symbols across a TypeScript monorepo with Yarn workspaces. Five parallel `ide_refactor_rename` calls were issued to rename type aliases, interfaces, and field names. Three of the five returned timeout errors. All five completed successfully — files were renamed, imports updated, and string references changed across 40+ files.

### What was tried (didn't work)
1. **Retrying the rename** — fails with "File not found" because the source file was already renamed by the "failed" operation
2. **Assuming failure and using text replacement instead** — produces duplicate changes since the rename already applied

### Root cause
IntelliJ's refactoring engine runs asynchronously within the IDE. The MCP plugin has a response timeout that fires before IntelliJ finishes processing the refactoring across all project files. The IDE continues processing after the timeout — the rename completes successfully in the background. The MCP layer reports a timeout error but the IDE state is already mutated.

### Fix
After a timeout error from `ide_refactor_rename`, verify the current state before retrying:

```bash
# Check if the source file still exists
ls path/to/original-file.ts

# If missing — the rename completed. Check the target:
ls path/to/renamed-file.ts
```

If the source file is gone and the target exists, the rename succeeded despite the timeout. Proceed with the next operation.

For batch renames, issue them sequentially rather than in parallel — each rename modifies shared state (import paths) that subsequent renames need to read correctly. Parallel renames can also compound the timeout issue as IntelliJ processes multiple refactorings concurrently.

### Why this is non-obvious
Timeout errors universally signal "operation did not complete." The natural response is to retry or fall back. But IntelliJ's MCP integration has a fire-and-forget characteristic for long-running refactorings — the operation is committed to the IDE's undo stack before the MCP response is sent. The timeout is on the response channel, not on the operation itself.

### Alternatives considered
- **Increasing MCP timeout** — not configurable from the caller side; the timeout is set by the MCP plugin
- **Using `ide_replace_text_in_file` instead** — works for simple renames but doesn't update imports or handle cross-file references semantically
- **Syncing files after timeout** — `ide_sync_files` helps IntelliJ see external changes but doesn't help diagnose whether a timed-out rename completed
