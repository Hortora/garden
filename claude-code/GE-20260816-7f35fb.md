## Context

The `design-review` skill's `review.py` script accepts a `--type` argument for selecting the review dimension. The skill documentation describes "spec review" and "decision review" as review phases, which suggests `--type spec` should work.

## Symptom

```
review.py: error: argument --type: invalid choice: 'spec' (choose from 'coherence', 'structure', 'robustness', 'conformance', 'readiness', 'crosscutting', 'decision')
```

## Root cause

`--type` selects a review *dimension* (what aspect to examine), not a review *lifecycle point* (what kind of document is being reviewed). Spec reviews are multi-dimension — they run coherence + structure + robustness in parallel, then cross-cutting. The lifecycle point determines which dimensions run; the `--type` flag is for single-dimension overrides.

## Fix

For spec reviews, launch three separate `review.py` instances — one per dimension — with `--type coherence`, `--type structure`, `--type robustness`. The design-review skill handles this orchestration automatically when invoked without `--type`.

For decision reviews, use `--type decision` (this IS a valid type).

## Why this is non-obvious

The skill documentation uses "spec review" and "post-spec review" terminology that suggests a `--type spec` flag should exist. The actual architecture separates lifecycle detection (handled by the skill) from dimension selection (handled by `--type`).
