### Symptom

After using `ide_replace_text_in_file` to rename a class (e.g. `A2ATaskState.` → `A2ATaskStateMapper.`), compilation fails because a *different* class in another package with the same simple name was also renamed.

### Context

Searching for `A2ATaskState.` also matches `io.casehub.a2a.model.A2ATaskState.` — a Layer 0 protocol enum in a completely different package. The replace changes all occurrences, breaking references to the unrelated class.

### Root cause

`ide_replace_text_in_file` performs plain text replacement, not semantic symbol replacement. Short class names appear as substrings of fully-qualified names in other packages.

### Fix

Use fully-qualified search text when the simple name exists in multiple packages: search for `runtime.api.A2ATaskState` instead of `A2ATaskState`. Alternatively, after a broad replace, immediately check for and revert cross-package hits with a targeted reverse replace (e.g. `io.casehub.a2a.model.A2ATaskStateMapper` back to `io.casehub.a2a.model.A2ATaskState`).

### Why this is non-obvious

`ide_refactor_rename` is the correct tool for semantic renames, but it can fail on cross-project references or doc files. When falling back to text replacement, the cross-package collision is silent — the tool reports success and the error only surfaces at compile time.
