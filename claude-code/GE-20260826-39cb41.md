## IntelliJ MCP ide_replace_text_in_file silently targets wrong project when project_path points to a different clone

### Symptom
Changes made via `ide_replace_text_in_file` report success with the correct replacement count, but the changes don't appear in the expected project directory. `grep` on the working project's file shows zero matches for the new content.

### Context
Multiple IntelliJ projects are open — e.g., a slot clone at `/path/slots/148/pages` and the working project at `/path/pages`. Both contain the same file paths relative to their roots. The `project_path` parameter was set to the slot clone path (from a previous `ide_index_status` call that listed available projects), but the working directory is the non-slot project.

### What was tried (didn't work)
- Assuming the tool's `success: true` and `replacements: 1` meant the working file was modified
- Running tests immediately after the replacement — tests ran against the unmodified working project and passed (old code), giving false confidence that the replacement worked

### Root cause
`project_path` is a routing parameter, not a validation parameter. The tool routes the operation to whichever IntelliJ project matches the path — it does not verify that the path corresponds to the caller's working directory. When two clones of the same repo are open (e.g., a slot and the main checkout), the relative file path resolves in both projects, and the operation silently targets whichever `project_path` was specified.

### Fix
Always verify the IntelliJ project path matches the working project path before any MCP operation:

```bash
# Working project path (from session context)
PROJECT=/Users/me/project

# Check which IntelliJ projects are open
ide_index_status  # lists available project paths

# Use the path that matches your working project — NOT a slot or worktree clone
ide_replace_text_in_file(file="src/file.ts", project_path="/Users/me/project", ...)
```

After any replacement, verify on disk:
```bash
grep "expected text" /Users/me/project/src/file.ts
```

### Why this is non-obvious
The tool reports success because the operation DID succeed — in the wrong project. The replacement count is correct. No error or warning is emitted. The only signal is that the working directory's file is unchanged, which requires an explicit disk check to detect. Tests running against the working project pass because they see the original code, reinforcing the false belief that the replacement worked.
