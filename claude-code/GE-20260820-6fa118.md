### Symptom

`ide_find_class("ScenarioExecutor")` returns empty results despite the class
existing in a commit on `main`. The repo is open in IntelliJ. `git show
8ed27ee7:backend/scenario-runtime/src/.../ScenarioExecutor.java` works fine.

### Context

A multi-repo slot has a pages repo checked out on branch
`issue-408-scenario-engine`. The `ScenarioExecutor` class was added to `main`
in commit `8ed27ee7`. The feature branch diverged one commit before that.
IntelliJ is open on the repo but shows the working tree of the checked-out
branch — the `scenario-runtime/` directory does not exist on disk.

### Root cause

IntelliJ indexes the filesystem working tree, not git refs. A class that
exists on `main` but not on the checked-out branch has no file on disk, so
it's absent from the IDE index. All `ide_find_*` tools operate on the index,
not on git history.

### Fix

Use `ide_import_modules` with the absolute path to a directory tree that HAS
the code on disk — e.g. a slot copy that's been rebased onto the commit
containing the class:

```
ide_import_modules(
  paths=["/Users/dev/slots/112/pages/backend/scenario-runtime"],
  project_path="/Users/dev/casehub/pages"
)
```

This imports the slot's module into the existing IntelliJ project, making its
classes visible for cross-project navigation. The same module combination is
cached — subsequent calls reuse the workspace.

### Alternatives considered

- **Checkout main in the IDE project** — works but disturbs uncommitted
  changes on the active branch and loses the branch context.
- **Open the slot repo as a separate IntelliJ project** — works but loses
  cross-project code intelligence with the main repo's other modules.
- **Use `git show` to read files** — works for reading but doesn't enable
  IntelliJ navigation, refactoring, or diagnostics.

### Why this is non-obvious

The mental model is "the repo has this class on main → IntelliJ should see
it." But IntelliJ's index is branch-scoped via the filesystem, not
git-scoped. `git show` sees it; `ide_find_class` doesn't. The fix —
importing from a completely different directory tree on a different branch —
is counterintuitive until you understand that IntelliJ indexes files, not
commits.

### Why this fix

`ide_import_modules` is the only approach that gives both: (a) the missing
classes visible in the index, and (b) cross-project code intelligence with
the existing project's modules. Any other approach sacrifices one of these.
