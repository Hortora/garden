### Symptom

`ide_find_references` returns `{"error":"project_not_found"}` with hint "Path exists but has no .idea directory" when called with a submodule `project_path` (e.g. `/path/to/neocortex/memory`), even though that submodule IS indexed as part of a parent workspace.

`ide_edit_member`, `ide_file_structure`, and `ide_replace_text_in_file` work fine with the same submodule path.

### Context

A multi-repo Maven workspace is open in IntelliJ (e.g. engine workspace including neocortex, eidos, and blocks modules). The workspace was created via `ide_open_workspace` with a parent directory scan. Individual submodules appear in the project list with `"workspace": "engine"` but do not have their own `.idea` directory.

### Root cause

IntelliJ MCP tools resolve `project_path` differently depending on operation scope:

- **Cross-module navigation** tools (`ide_find_references`, `ide_find_class`, `ide_find_symbol`) need to search across the entire workspace index. They require the **parent workspace** project_path (the root that owns the `.idea` directory).

- **Per-file operation** tools (`ide_edit_member`, `ide_file_structure`, `ide_replace_text_in_file`, `ide_replace_member`, `ide_insert_member`) operate on a single file within a known module. They accept the **submodule** project_path because the file path is resolved relative to the submodule root.

The error message ("has no .idea directory") is technically correct but misleading — it implies the project isn't open, when the real issue is that the tool needs the parent workspace path to access the cross-module index.

### Fix

Use the parent workspace `project_path` for cross-module navigation:
```
ide_find_references(project_path="/path/to/engine", symbol="com.example.MyClass")
```

Use the submodule `project_path` for per-file operations:
```
ide_edit_member(project_path="/path/to/neocortex/memory", file="src/main/java/...", ...)
```

### Why this is non-obvious

The `project_path` parameter documentation says "Required when multiple projects are open. For workspace projects, use the sub-project path." This guidance is correct for per-file tools but wrong for cross-module tools. A developer following the documentation consistently will get silent failures on navigation while edits work fine — the asymmetry is not documented anywhere.
