## IntelliJ MCP ide_insert_member renders HTML entities in Java string literals

**ID:** GE-20261114-8bb169
**Stack:** IntelliJ MCP Plugin
**Symptom:** Java method containing HTML entity references (e.g. `"&amp;"` in a string literal) compiles and runs but does nothing — the replacement strings are identical to the originals. No compiler error, no runtime error, no test failure.
**Context:** Using `ide_insert_member` or `ide_edit_member` to write Java code that manipulates HTML entities — e.g. an `escapeHtml()` method that replaces `&` with `&amp;`, `<` with `&lt;`, `>` with `&gt;`.

### What was tried (didn't work)
- Wrote the method via `ide_insert_member` with correct entity references in the content parameter — the tool rendered them before writing to disk
- Wrote test assertions checking for the escaped output — the test assertions were equally mangled, so tests passed with a green bar
- Compiled and ran the full test suite — all tests passed because both production code and assertions were transformed identically

### Root cause
The IntelliJ MCP `ide_insert_member` tool interprets the `content` parameter as HTML-like markup before writing it to the Java source file. HTML entity references in the content are rendered to their character equivalents:
- `&amp;` → `&`
- `&lt;` → `<`
- `&gt;` → `>`

This transforms `text.replace("&", "&amp;")` into `text.replace("&", "&")` — a no-op. The Java source file contains syntactically valid code that does nothing.

### Fix
Use `ide_replace_text_in_file` instead of `ide_insert_member` for any code containing HTML entity references. `ide_replace_text_in_file` performs literal text substitution without interpreting entities.

For code already written via `ide_insert_member`, verify with raw byte inspection:
```bash
python3 -c "
with open('path/to/File.java', 'rb') as f:
    lines = f.readlines()
for i in range(start, end):
    print(f'{i+1}: {lines[i]}')"
```

The `repr()` output will show whether entity references survived (`b'..."&amp;"...'`) or were rendered (`b'..."&"...'`).

### Alternatives considered
- Reading the file back after insertion to verify — adds overhead to every edit, and the Read tool also renders entities in its display, making visual inspection unreliable
- Using the Edit tool instead of IntelliJ MCP — blocked by project hooks requiring IntelliJ-first editing for Java source files

### Why this is non-obvious
The corruption is invisible at every normal inspection point. The Java source looks correct when viewed in an editor (which also renders entities). The compiler accepts it (valid Java). Tests pass because test assertions go through the same tool and are corrupted in the same way. Only reading raw bytes — `repr()` or `xxd` — reveals that the file contains `"&"` where it should contain `"&amp;"`.

This is a particularly dangerous class of bug: the verification mechanism (tests) is corrupted by the same vector as the production code, creating a closed loop where everything appears correct.

### Why this fix
`ide_replace_text_in_file` is documented as performing literal text replacement — "Passed through as-is (no escape processing)". This makes it safe for any content, including HTML entities. The tradeoff is that `ide_replace_text_in_file` requires knowing the exact text to replace, while `ide_insert_member` works structurally by member name. For HTML-entity-containing code, the literal safety outweighs the structural convenience.
