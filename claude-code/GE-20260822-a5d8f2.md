### Symptom

After running `ide_structural_search_replace` to extend a Java record constructor from 13 to 17 parameters, one file that used the fully-qualified class name `new io.quarkmind.domain.GameState(...)` compiled with "cannot find symbol: class GameState" — the replacement stripped the package prefix.

### Context

71 constructor call sites matched the SSR pattern `new GameState($a$, ..., $m$)`. Most used the short class name with an import. One file used the fully-qualified name `new io.quarkmind.domain.GameState(...)` — no import statement. The SSR pattern matches both forms but the replacement always outputs the short name.

### Root cause

IntelliJ's SSR operates on the AST, not text. The pattern `new GameState(...)` matches the constructor call node regardless of how the class was referenced in source. But the replacement template uses the short name from the pattern, discarding the original FQN qualification.

### Fix

After any SSR replacement that touches constructor calls, check for files that now reference an unimported class:

1. Compile and check for "cannot find symbol" errors
2. For each error, add the missing import via `ide_replace_text_in_file`

Alternatively, before running SSR, find FQN constructor calls:
```bash
grep -rn "new io\.quarkmind\.domain\.GameState(" src/
```
And convert them to short-name + import before running SSR.

### Why this is non-obvious

SSR is documented as AST-aware, which suggests it would preserve the reference form. The silent FQN-to-short-name conversion is not flagged as a warning and only manifests as a compilation error — easy to miss if not compiling immediately after.

### Alternatives considered

- Using `ide_replace_text_in_file` per-file: works but requires one call per file (71 calls vs 1 SSR call)
- Writing a Python script for bulk text replacement: blocked by IntelliJ-first editing hooks
