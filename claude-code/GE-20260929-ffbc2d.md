### Symptom

`ide_move_file` returns `success: true` and reports affected files, but the destination file does not exist at the expected location. The source file IS deleted. Git status shows the source as deleted, but no new file appears in the target project.

### Context

A multi-repo workspace is open via `ide_open_workspace` with two Maven projects (e.g. `blocks` and `neocortex`). Attempting to move a Java file from one project to another using an absolute destination path:

```
ide_move_file(
  file="src/main/java/io/casehub/blocks/agentic/social/MoodTick.java",
  destination="/Users/dev/neocortex/cognition-api/src/main/java/io/casehub/neocortex/cognition/mood",
  project_path="/Users/dev/blocks"
)
```

Returns success but warns "destination is outside every source root." The file path in `affectedFiles` shows the absolute path without the leading `/`, suggesting it was treated as relative to the source project root.

### Root cause

`ide_move_file` resolves the `destination` parameter relative to the source project root, even when an absolute path is provided. In a workspace context, there is no mechanism to target a directory in a different project module. The file gets deleted from source but the destination path resolves incorrectly.

### Fix

Do not use `ide_move_file` for cross-project transfers in workspaces. Instead:

1. Read the source file content
2. Create the file in the target project (via `ide_create_file` or Write tool) with updated package declaration
3. Delete the source file after the target compiles
4. Use `ide_move_file` only for within-project moves (where it correctly updates packages and references)

For bulk cross-repo migrations, use a workspace-local Python script that reads source files, transforms package declarations, and writes to the target location.

### Why this is non-obvious

The tool returns `success: true` with no error. The affected-files list shows the destination path (without leading `/`), which looks correct at a glance. Only checking the filesystem reveals the file wasn't actually placed where expected. A developer would naturally assume that a workspace with both repos open supports cross-module file moves.
