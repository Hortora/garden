### Context

When extending a Java record with new fields, every constructor call site must be updated. For records with many callers (e.g. domain value objects used across the entire codebase), this is a significant mechanical burden.

### Technique

Use `ide_structural_search_replace` with one SSR variable per existing constructor argument, then append the new default values in the replacement:

**Search pattern:**
```
new GameState($a$, $b$, $c$, $d$, $e$, $f$, $g$, $h$, $i$, $j$, $k$, $l$, $m$)
```

**Replace pattern:**
```
new GameState($a$, $b$, $c$, $d$, $e$, $f$, $g$, $h$, $i$, $j$, $k$, $l$, $m$, PlayerEconomyStats.EMPTY, PlayerEconomyStats.EMPTY, Set.of(), Set.of())
```

This replaced 71 call sites across 33 files in a single AST-aware operation.

### Why this is non-obvious

The natural approach is per-file text replacement (`ide_replace_text_in_file`) or a Python script. SSR is typically thought of for pattern-based code search, not bulk constructor argument extension. The key insight is that each constructor argument maps to a separate `$variable$` in the SSR pattern, allowing exact arity matching.

### Caveats

- SSR strips fully-qualified class names from matched call sites — see GE-20260822-a5d8f2
- After SSR, all affected files need import statements added for any new types used in the appended arguments
- If some call sites have different arities (overloaded constructors), use separate SSR patterns per arity
