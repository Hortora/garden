### Symptom

Multiple independent S-scale issues need implementation. Sequential work is slow — each takes 15-30 minutes, and they don't depend on each other.

### Context

When a backlog has 3+ independent issues (different files, different subsystems), dispatching them as parallel agents with worktree isolation lets all three run simultaneously. Each agent gets its own copy of the repo, implements with TDD, and commits to an auto-generated branch. The parent session then cherry-picks the results to main one at a time.

### The technique

1. **Dispatch N agents** in a single response, each with `isolation: "worktree"`:
   - Each agent prompt includes: project type, Maven command, test conventions, specific files to modify, TDD discipline, commit message format
   - Explicitly instruct agents NOT to use IntelliJ MCP (worktrees aren't IDE-visible)
   
2. **Monitor completion** — agents run in background, notifications arrive on completion

3. **Review each agent's worktree**:
   ```bash
   git -C .claude/worktrees/agent-<id> log --oneline -3  # check commits
   git -C .claude/worktrees/agent-<id> diff HEAD~1..HEAD  # review changes
   ```

4. **Cherry-pick to main** in dependency order:
   ```bash
   git cherry-pick <sha> --no-edit
   ```
   If agents fixed the same pre-existing issue (e.g. constructor arity breaks), the first cherry-pick includes the fix; subsequent agents' duplicate fixes are skipped.

5. **Clean up worktrees**:
   ```bash
   git worktree remove .claude/worktrees/agent-<id>
   ```

### Caveats

- **No IntelliJ MCP in worktrees** — agents must use Read/Edit/Bash (see GE-20260803-032978)
- **Overlapping fixes** — if multiple agents independently fix the same pre-existing break (e.g. a SNAPSHOT constructor change), cherry-picking the second agent's fix may conflict. Manual reconciliation needed.
- **Cross-repo work can't be isolated** — if an agent needs to modify a dependency repo (e.g. rename an SPI), that repo isn't worktree-isolated. Schedule cross-repo work after all worktree agents complete.
- **Maven port conflicts** — Quarkus tests use random ports by default (`test-port=0`), so concurrent test runs don't conflict. But CPU load from 3+ concurrent Maven builds may slow all agents.

### Why this is non-obvious

The natural approach is sequential: create branch, implement, test, merge, repeat. Parallel dispatch requires upfront analysis of file independence, explicit IntelliJ-avoidance in prompts, and a cherry-pick merge strategy that handles overlapping fixes. The technique yields ~3x wall-clock speedup for 3 independent S-scale issues (verified: 3 agents completed in ~15 minutes total vs ~45 minutes sequential estimate).

### Alternatives considered

- **Sequential work-start/work-end cycles** — clean but slow for independent work
- **Parallel agents without worktree isolation** — agents would conflict on shared working directory
- **work-slot with cloned repos** — heavier setup, designed for multi-repo families rather than single-repo parallelism
