## Symptom

`ide_insert_member` reports success when adding a constructor to a record in a dependency jar (e.g. `engine-api`'s `TaskNode.CompoundTask`). IntelliJ diagnostics show no errors — the new constructor is visible to PSI analysis. But `mvn compile` fails with "actual and formal argument lists differ in length" because the jar on disk is unchanged.

## Context

Occurs when trying to add backward-compatible secondary constructors to upstream dependency types (e.g. a record gained a new field and you want a 2-arg constructor matching the old signature). The IntelliJ MCP tools operate on the PSI model which can load and modify decompiled jar sources in memory, but these modifications are not written to disk.

## What was tried (didn't work)

1. Used `ide_insert_member` to add secondary constructors to `TaskNode.CompoundTask` and `DecompositionMethod` (both in engine-api jar)
2. Verified with `ide_diagnostics` — no errors (PSI model was updated)
3. Ran `mvn compile` — compilation failed because the jar was unchanged

## Root cause

IntelliJ's PSI model treats decompiled jar sources as editable in-memory documents. `ide_insert_member` modifies this in-memory representation successfully, and `ide_diagnostics` validates against it. But Maven compiles against the actual jar file on disk (`~/.m2/repository/...`), which was never modified. The two views diverge silently.

## Fix

Do not use `ide_insert_member`, `ide_edit_member`, or `ide_replace_member` on types that come from dependency jars. Instead, update all callers in your project source to match the new API. Use `ide_structural_search_replace` or `ide_replace_text_in_file` for bulk caller updates.

To identify whether a file is from a jar: check if `find <project-root> -name "ClassName.java"` returns nothing — if the file doesn't exist on disk, it's a dependency type.

### Why this is non-obvious

The MCP tools give no indication that the target file is a jar-sourced decompilation vs. a project source file. Success is reported, diagnostics pass, and the change appears to work — until Maven runs against the real jar.
