## IntelliJ MCP ide_import_modules with duplicate Maven artifactIds — edits silently route to first-registered module

### Symptom

`ide_insert_member` or `ide_replace_member` succeeds (returns `{"success": true}`) but `git diff` in the target repo shows nothing. Running `git diff` on the OTHER repo with the same module reveals the changes went there instead. No error, no warning — the edit silently landed in the wrong repository.

### Context

A multi-repo slot setup where the same Maven module exists in two locations:
- Main repo: `/Users/dev/casehub/pages/backend/push` (on `main` branch)
- Slot repo: `/Users/dev/casehub/slots/112/pages/backend/push` (on `issue-408` branch)

Both directories contain `casehub-pages-push` with the same `artifactId` in `pom.xml`. The main repo's module was already in the IntelliJ workspace. The slot's module was imported via `ide_import_modules`.

### What was tried (didn't work)

1. Used `ide_import_modules` to import the slot's push module into the existing workspace — import succeeded, module appeared in the project list
2. Used `ide_insert_member` with `project_path` pointing to the slot's module path — call returned success with correct line numbers
3. Verified with `ide_diagnostics` on the slot's module — showed no compilation errors (because the source file hadn't actually changed)

### Root cause

When two modules with the same Maven `artifactId` exist in one IntelliJ workspace, `ide_insert_member` and `ide_replace_member` resolve the relative `file` parameter against the FIRST-registered module, not the one specified by `project_path`. The `project_path` parameter selects the correct project context for type resolution, but the file write goes to whichever module IntelliJ's VFS resolves first for that relative path.

The import creates a valid module reference (it appears in `available_projects`), and `project_path` correctly routes type-checking and diagnostics. But the file-write operation uses a different resolution path that doesn't honour the project_path override.

### Fix

Create a `git diff` patch from the wrong repo and apply it to the right one:

```bash
# 1. Create patch from the repo that received the edits
git -C /path/to/main/repo diff -- backend/push/ > /tmp/changes.patch

# 2. Apply to the target repo
git -C /path/to/slot/repo apply /tmp/changes.patch

# 3. Restore the wrong repo to clean state
git -C /path/to/main/repo checkout -- backend/push/
```

For future edits on the slot's module, either:
- Continue using the patch approach after each edit batch
- Only import modules that DON'T exist in the original workspace (e.g. a new `scenario-client` module unique to the slot)
- Use the main workspace's modules directly if working on `main` branch

### Alternatives considered

- Editing files directly with the Write/Edit tools — blocked by the `intellij-first.sh` hook which enforces IntelliJ-only editing for Java/Kotlin files
- Opening the slot as a completely separate IntelliJ project — loses cross-project code intelligence with the main workspace's other modules
- Removing the main repo's module before importing the slot's — risks breaking other workspace references

### Why this is non-obvious

The entire operation appears to succeed. `ide_import_modules` returns success. `ide_insert_member` returns `{"success": true}` with plausible line numbers. `ide_diagnostics` shows no errors. The only way to discover the problem is to run `git diff` in both repositories — which you'd only do if you suspected the edits went to the wrong place. The symptom (empty `git status` in the target repo) could easily be misattributed to IntelliJ not flushing to disk.

### Why this fix

The patch approach preserves the IntelliJ-first workflow (edits are still made via IDE tools, maintaining reference tracking and import optimisation) while working around the file-routing bug. It's also recoverable — the wrong repo's changes are never committed, just patched across.
