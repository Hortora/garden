### Symptom

After using `ide_edit_member` with `member=ClassName` to replace an entire class body with new code that uses new types (e.g., `CopyOnWriteArrayList`, `ReentrantReadWriteLock`, `Map`), Maven compilation fails with "cannot find symbol" for every new type referenced in the replacement.

### Context

Occurs when rewriting a Java class via IntelliJ MCP structural editing. The `reformat=true` flag (default) triggers IntelliJ's "Optimize Imports" action after the edit. The natural assumption is that this handles import management end-to-end.

### What was tried (didn't work)

1. `ide_edit_member` with `reformat=true` — imports not added
2. `ide_reformat_code` with `optimizeImports=true` after the edit — only removes unused imports, does not add missing ones
3. `ide_optimize_imports` directly — same remove-only behaviour
4. `ide_sync_files` followed by `ide_reformat_code` — still remove-only

### Root cause

`ide_edit_member` replaces the range from the class declaration's first modifier/annotation through the closing brace. Import statements are above this range and are never touched by the replacement. The `reformat=true` flag triggers IntelliJ's "Optimize Imports" which is a cleanup action — it removes imports that are no longer referenced but never adds imports for newly referenced types. This is consistent with IntelliJ's UI behaviour (Optimize Imports ≠ Auto Import), but surprising in the MCP context where the replacement is the only edit path.

### Fix

After `ide_edit_member` class replacement, use `ide_replace_text_in_file` to replace the import block with the correct set of imports:

```
ide_replace_text_in_file({
  file: "src/main/java/.../MyClass.java",
  searchText: "import java.util.ArrayList;\nimport java.util.List;",
  replaceText: "import java.util.List;\nimport java.util.Map;\nimport java.util.concurrent.CopyOnWriteArrayList;\nimport java.util.concurrent.locks.ReadWriteLock;"
})
```

### Why this is non-obvious

`reformat=true` with "import optimization" strongly implies imports will be handled. The actual behaviour — remove-only — contradicts the reasonable expectation that a structural edit tool producing valid Java would manage its own imports. The same gap applies to `ide_reformat_code` with `optimizeImports=true` and standalone `ide_optimize_imports`. None of the three import-related operations add missing imports.
