### Context
`casehub-eidos-api` added a `styleVocabulary` (String) field to the `AgentDescriptor` record at position 11 (between `dispositionVocabulary` and `axisVocabularies`). `casehub-ops-api`'s `AgentNodeSpec.toDescriptor()` and `withAgentId()` methods pass positional arguments to the `AgentDescriptor` constructor.

### What happens
The `casehub-ops-api` module fails compilation with `constructor AgentDescriptor in record cannot be applied to given types; reason: actual and formal argument lists differ in length`. The error shows the full type signature (22 parameters) but not the field names — all 11 String parameters before `Map<DispositionAxis, String>` look identical in the error message.

~40 test call sites across `app/src/test` and `deployment/src/test` also use the `AgentNodeSpec` constructor and need the new `styleVocabulary` null argument inserted at the correct position.

### Symptom
Compilation failure in `AgentNodeSpec.java:61` — "actual and formal argument lists differ in length". The error lists 22 required parameters; the call passes 21.

### Root cause
Cross-repo record field addition without propagating to consuming modules. Java records use positional constructors — adding a field anywhere except the end requires updating every call site's argument order.

### Fix
Add `styleVocabulary` (null for ops purposes) at position 11 in `AgentNodeSpec.toDescriptor()`:
```java
return new AgentDescriptor(
    agentId, name, version, provider, modelFamily, modelVersion,
    weightsFingerprint, domainVocabulary, slotVocabulary,
    dispositionVocabulary, styleVocabulary, // ← new field at position 11
    axisVocabularies, slot, capabilities,
    disposition, jurisdiction, dataHandlingPolicy, tenancyId, briefing,
    List.of(), List.of(), List.of());
```

Also add `String styleVocabulary` to the `AgentNodeSpec` record fields and update `withAgentId()`.

**Workaround to unblock the app module while test callers are pending:**
```bash
mvn install -pl api -Dmaven.test.skip=true
```

Use `javap -p -cp <jar-path> io.casehub.eidos.api.AgentDescriptor` to discover which field was added and where — the compiler error shows types but not field names.

### Why this is non-obvious
The compiler error lists 22 type parameters (11 Strings, then Map, then more Strings, then Lists). All the String fields are visually identical in the error. Determining which String was added requires decompiling the jar with `javap` to see field names. The field `styleVocabulary` is new but sits among 10 other String vocabulary/identity fields — easy to insert the null at the wrong position.

### Alternatives considered
- Builder pattern for AgentDescriptor — would prevent positional drift but is an eidos API change
- Checking the eidos source directly — the cloned source in casehub/all/eidos was stale (18 fields vs 22 in the installed jar)
