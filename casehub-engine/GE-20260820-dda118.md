### Symptom
A compound with ALL completion semantics transitions to COMPLETED when all children reach terminal status — even if one or more children are FAULTED or CANCELLED. The parent should fault, not complete, when required children failed.

### Context
`DefaultCasePlanModel.evaluateCompletion()` correctly counts FAULTED and CANCELLED as terminal statuses. Under ALL semantics, it returns `true` when `totalTerminal == totalCount`. `CompoundCompletionEvaluator.evaluate()` then unconditionally calls `tryDefinitionTransition(parentId, ..., TaskStatus.COMPLETED)`. The gap: "all children are terminal" ≠ "all children succeeded."

### Root cause
`CompoundCompletionEvaluator` has no fault-awareness. It treats `evaluateCompletion() == true` as "ready to complete" without checking the character of the terminal statuses. Under ALL semantics, a FAULTED child means the compound's goal was not fully achieved — it should propagate the fault upward.

### Fix
After `evaluateCompletion()` returns true, check `plan.hasAnyFaultedParticipant(parentId)`. If true AND completion semantics is ALL, transition to FAULTED instead of COMPLETED:

```java
TaskStatus targetStatus = TaskStatus.COMPLETED;
if (def instanceof PlanItemDefinition.Compound c
    && c.completion() instanceof CompletionSemantics.All
    && plan.hasAnyFaultedParticipant(parentId)) {
  targetStatus = TaskStatus.FAULTED;
}
plan.tryDefinitionTransition(parentId, plan.getDefinitionStatus(parentId), targetStatus);
```

MOfN and FirstWins semantics are unaffected — they complete based on threshold/first-success regardless of individual faults.

### Why this is non-obvious
`evaluateCompletion()` returning `true` looks like it means "ready to complete" — and it does mean "completion criteria are met" in the terminal-count sense. The distinction between "all terminal" and "all successful" is hidden inside the boolean return value. The bug is silent: no error, no exception, the compound just completes when it shouldn't.
