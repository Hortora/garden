## Symptom
Design spec proposed creating a new `RoutingSignalProvider` interface in `engine-api` for composable routing signals. The design review discovered this interface already exists at `io.casehub.api.spi.routing.RoutingSignalProvider` with `RoutingSignalAssembler` composition — used by blocks-layer strategies for signal enrichment.

## Root Cause
The existing SPI was a supplementary enrichment mechanism (blocks strategies consume it for candidate scoring enrichment). The new design needed it as the primary Layer 3 scoring system. Same concept, different scope.

## Fix
Evolved the existing SPI in place: `CandidateSignal` from a score-only record to a sealed interface (Score/Exclude/Escalate), `signal()` renamed to `evaluate()`, and `NamedStrategy` extension added. `RoutingSignalAssembler` updated for sealed pattern matching. Zero new interfaces — pure SPI evolution.

## Key Insight
Before proposing any new SPI in the routing package, run `ide_find_class("RoutingSignal")` — the existing infrastructure may already provide the foundation. The eidos API similarly has `DispositionSignalStore` (not `BehavioralSignalStore`) for personality signals, and `DispositionEvolution` with `DefaultDispositionEvolution` already implementing all 4 JPAF decision rules.
