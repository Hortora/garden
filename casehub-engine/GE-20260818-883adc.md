### Symptom

Two YAML bindings both fire on the same context change. One produces the correct outcome (escalation to head of compliance), the other produces a failure state (investigation stalled). The faster-completing worker wins — outcome is non-deterministic.

### Context

Building gate rejection routing for AML investigations. After post-rejection-triage writes its result to context, two bindings became eligible simultaneously:

1. `rejection-escalation` — creates a head-of-compliance WorkItem (correct path)
2. `rejection-stall-detection` — marks investigation as stalled (failure path)

Both check `.postRejectionTriage != null and .rejectionEscalation == null`. The stall binding was intended for second-cycle detection but lacked guards excluding cases where escalation should fire.

### What was tried (didn't work)

Relying on YAML ordering — assumed bindings listed first in the YAML would be dispatched first and their output committed before later bindings evaluated. This is NOT how ChoreographyStrategy works. All eligible bindings are dispatched concurrently.

### Root cause

The engine's `CaseContextChangedEventHandler` evaluates ALL binding conditions on each context change and dispatches ALL eligible bindings simultaneously. There is no priority ordering or sequential evaluation. If two bindings have overlapping conditions and produce conflicting outcomes, both workers execute concurrently and the faster-completing one has its output committed first.

The stall-detection worker was a simple stub returning `{investigationStalled: true}` immediately (sub-millisecond). The escalation worker called `WorkItemService.create()` (database write, ~50ms). Stall always won the race.

### Fix

Add mutually exclusive guards to prevent both bindings from being eligible simultaneously. For each triage decision that has a resolution path (SAR_WARRANTED, FALSE_POSITIVE, INCONCLUSIVE), exclude it from the stall detection condition:

```yaml
- name: rejection-stall-detection
  when: >-
    .actionGateRejected != null and
    .rejectionReview != null and
    .postRejectionTriage != null and
    .rejectionEscalation == null and
    .investigationStalled != true and
    .postRejectionTriage.decision != "SAR_WARRANTED" and
    .postRejectionTriage.decision != "FALSE_POSITIVE" and
    .postRejectionTriage.decision != "INCONCLUSIVE"
```

The general principle: when two bindings could be eligible simultaneously and produce conflicting outcomes, one must carry explicit negation guards for the other's conditions.

### Why this is non-obvious

The natural assumption is that YAML ordering provides implicit priority — bindings listed first fire first. This is how most rule engines work (Drools salience, Rete priority). CasePlanModel ChoreographyStrategy does not provide this guarantee. All eligible bindings fire concurrently with no ordering.

### Alternatives considered

- **Binding priority attribute** — the engine doesn't support priority on bindings
- **Sequential evaluation** — would require engine changes to add a `sequential: true` flag
- **Removing the stall binding** — works but loses the safety net for future decision types
