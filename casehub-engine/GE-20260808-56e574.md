### Symptom

After calling `CasePlanModel.replaceCompound()`, completed PlanItems appear
missing when looked up by binding name. `getPlanItemByBindingName("cap-a")`
returns `Optional.empty()` even though the PlanItem exists and was explicitly
preserved during compound replacement.

### Context

`DefaultCasePlanModel` has two binding-name lookup methods with different
semantics:

- `getPlanItemByBindingName(bindingName)` — returns `Optional.empty()` for
  non-active items (COMPLETED, FAULTED, REJECTED, etc.). Checks
  `item.getStatus().isActive()` before returning.
- `findPlanItemByBindingName(bindingName)` — returns any item regardless of
  status. Wraps `latestByBinding.get()` directly.

The method naming does not signal the filtering difference.

### Root cause

`getPlanItemByBindingName()` at line 122-126 of `DefaultCasePlanModel`:

```java
public Optional<PlanItem> getPlanItemByBindingName(String bindingName) {
    PlanItem item = latestByBinding.get(bindingName);
    if (item == null) return Optional.empty();
    return item.getStatus().isActive() ? Optional.of(item) : Optional.empty();
}
```

The `isActive()` check silently drops terminal items. `findPlanItemByBindingName`
(line 135) has no such filter.

### Fix

Use `findPlanItemByBindingName()` when you need to check whether ANY PlanItem
exists for a binding, regardless of its lifecycle status. Reserve
`getPlanItemByBindingName()` for dispatch contexts where only active items matter.

### Why this is non-obvious

The method name `getPlanItemByBindingName` gives no hint that it filters by
status. A developer reasonably expects it to return whatever PlanItem is
associated with the binding name. The `find` prefix on
`findPlanItemByBindingName` doesn't conventionally signal "unfiltered" in Java.
