### Symptom

When a PlannedAction gate is rejected, the case enters a dead state — no completion path is reachable. The natural assumption is that routing after rejection requires engine-level changes (a new event type, SPI, or handler).

### Context

Implementing gate rejection routing for AML investigations: when the MLRO rejects a SAR filing gate or a compliance officer rejects an investigation clearance gate, the case should route to re-investigation or escalation rather than stalling.

### What was tried

Initially explored engine-level approaches: new gate rejection events, SPI hooks for rejection handlers, programmatic binding manipulation. All would require engine changes and cross-repo coordination.

### Fix

Use the existing engine mechanism: `ActionGateRejectedHandler` already writes `actionGateRejected` to context and fires `CaseContextChangedEvent`. Add YAML bindings conditioned on this field — no engine changes needed.

The rejection routing flow is entirely expressed in YAML:

```yaml
# 1. Senior analyst reviews the rejection
- name: rejection-review
  when: ".actionGateRejected != null and .rejectionReview == null"
  capability: rejection-review

# 2. Re-triage with extended input
- name: post-rejection-triage
  when: ".actionGateRejected != null and .rejectionReview != null and .postRejectionTriage == null"
  capability: post-rejection-triage

# 3. Escalation when re-triage confirms the rejected decision
- name: rejection-escalation
  when: ".postRejectionTriage != null and .rejectionEscalation == null and ..."
  capability: rejection-escalation
```

Key design decisions:
- **ChoreographyStrategy, not supervised compound** — the rejection flow is linear (one eligible binding at a time), so LLM supervisor selection adds latency with no decisional value
- **`.actionGateRejected == null` guard on original sar-drafting binding** — explicit mutual exclusion between normal and rejection flows
- **Separate capabilities for rejection workers** — output projections are capability-level in the YAML DSL, so rejection-review needs its own capability (writes to `.rejectionReview`) rather than reusing senior-analyst-review (writes to `.seniorAnalystReview`)

### Why this is non-obvious

The natural approach to "handle gate rejection" is to look for an engine extension point — a rejection event SPI, a callback hook, or a programmatic handler. The YAML-binding approach works because the engine's existing internal handler already does the context write and context-change event that YAML bindings need. This means rejection routing is a pure application-layer concern — no engine changes, no cross-repo PRs, no version coupling.
