### Symptom

Looking up a compound by its goal name (e.g., `definitions.get("research-topic")`)
returns null after `registerDefinition()`, even though the compound was built with
`Compound.builder("research-topic")`.

### Context

`PlanItemDefinition.Compound.builder(name)` stores `name` on the builder but
initialises `id` to `UUID.randomUUID().toString()` (line 65 of
`PlanItemDefinition.java`). The `name` parameter is only used for the
compound's `name()` field — the `id()` field gets a random UUID.

### Root cause

Builder constructor:
```java
private Builder(String name) {
    this.name = Objects.requireNonNull(name, "name required");
}
```

Field declaration:
```java
private String id = UUID.randomUUID().toString();
```

The `name` and `id` are independent fields. Without calling `.id(goalName)`,
the compound is registered under a random UUID in `CasePlanModel.definitions`.

### Fix

Explicitly set the id when you need predictable compound lookup:

```java
PlanItemDefinition.Compound.builder(goal.name())
    .id(goal.name())   // ← required for predictable lookup
    .completion(CompletionSemantics.all())
    .build();
```

### Why this is non-obvious

Most builder patterns default the `id` to the `name` when no explicit id is
given. The random UUID default is counter-intuitive for a plan definition type
where the name is the natural identifier.
