### Convention
When adding a new SPI that needs a classification/execution context record, check whether a record with the desired name already exists for another SPI. If it does, create a separate type with a qualified name rather than modifying the existing record.

### Example
`ClassificationContext` already exists for `ActionRiskClassifier` (6 fields: workerId, caseId, tenancyId, caseDefinitionName, capabilityName, bindingName). The new `FailureClassifier` SPI needs different fields (adds attemptCount, maxRerouteAttempts; drops caseDefinitionName).

Wrong: modify `ClassificationContext` to carry all fields — breaks the existing `ActionRiskClassifier` contract.
Right: create `FailureClassificationContext` with the fields `FailureClassifier` needs.

### Why this convention
The record IS the SPI contract. Adding fields breaks existing implementations that construct the record. Removing fields breaks existing implementations that read them. Even in a pre-release platform, modifying an SPI parameter record has cascading test failures across all consumer modules.

### Alternative
A single `ClassificationContext` with optional/nullable fields for both SPIs — rejected because it conflates two unrelated contexts and makes both SPIs harder to understand.
