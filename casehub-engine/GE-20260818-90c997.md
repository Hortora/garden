### Symptom

After a PlannedAction gate is rejected (e.g., MLRO rejects SAR_FILING), the worker output is NOT committed to case context (documented in investigation-triage-design.md). However, the engine separately writes rejection metadata to the case context — this is not documented in any AML spec or engine documentation.

### Context

Building gate rejection routing for AML investigations. The natural assumption was that gate rejection is a dead end — the engine marks the worker as faulted, output is discarded, and no context change occurs. Designing rejection routing seemed to require engine changes.

### Root cause

`ActionGateRejectedHandler` (casehub-engine) does five things on gate rejection:
1. Clears `PendingActionGate` from the case instance
2. **Writes `actionGateRejected: {actionType, workerId, rejectedBy, resolution}` to the case context** via `instance.getCaseContext().set()`
3. Marks the worker as faulted via `workerStatusListener.onWorkerCompleted(gate.workerId(), WorkResult.faulted(...))`
4. Records `RoutingOutcome.GATE_REJECTED`
5. **Fires `CaseContextChangedEvent`** — this triggers YAML binding re-evaluation

The combination of steps 2 and 5 means YAML bindings conditioned on `.actionGateRejected` will fire after a gate rejection without any engine modifications.

### Fix

No fix needed — this is a feature, not a bug. Use it by adding YAML bindings conditioned on `.actionGateRejected`:

```yaml
- name: rejection-review
  on: { contextChange: {} }
  when: >-
    .actionGateRejected != null and
    .rejectionReview == null
  capability: rejection-review
```

The `actionGateRejected` context field contains:
- `actionType`: e.g., `"sar.filing"` or `"investigation.clearance"`
- `workerId`: which worker's output was rejected
- `rejectedBy`: who rejected the gate
- `resolution`: the rejection rationale

### Why this is non-obvious

The investigation-triage-design.md explicitly states "the triage result is NOT committed to context" for gate rejections, which reads as "nothing is written to context." The fact that the engine separately writes rejection metadata is only visible in the decompiled `ActionGateRejectedHandler` bytecode. No spec, design doc, or engine documentation mentions this behavior.
