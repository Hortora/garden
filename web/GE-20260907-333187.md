### Symptom
ReactFlow's `edgeTypes` prop requires explicit registration of every edge type string used by edges. Edge types not in the map (e.g. `org-delegates-to`, `case-flow`) silently fall back to ReactFlow's built-in default BezierEdge — not the `default` key in the provided edgeTypes map.

### Context
Graph diagrams with many domain-specific edge types registered via a stencil registry at runtime. Each edge type provides CSS styling (color, dash pattern) but should share the same rendering component. Registering every possible edge type in the static `edgeTypes` map is fragile and requires coordination between the stencil registry and the ReactFlow config.

### Root cause
ReactFlow resolves edge components by looking up `edgeTypes[edge.type]`. If the key doesn't exist, it uses its internal default renderer, ignoring any `default` key in the user-provided edgeTypes. The edge's `type` field IS used as a CSS class on the rendered SVG group, so it must be preserved for styling.

### Fix
Wrap the edgeTypes object in a JavaScript Proxy that intercepts property access and returns the appropriate component for any edge type string:

```typescript
const smartEdgeTypes: EdgeTypes = new Proxy(
  { default: SmartBezierEdge } as EdgeTypes,
  {
    get(target, prop) {
      if (prop === 'default' || prop === 'smart') return SmartBezierEdge;
      if (typeof prop === 'string') return AutoBezierEdge;
      return Reflect.get(target, prop);
    },
  }
);
```

ReactFlow calls `edgeTypes[edgeType]` which triggers the Proxy's `get` trap. The Proxy returns the desired component for any string key without needing explicit registration. Non-string accesses (Symbols, internal React checks) pass through to `Reflect.get`.

### Why this is non-obvious
The ReactFlow documentation shows edgeTypes as a static object with explicit keys. There's no mention of using Proxy for dynamic dispatch. The fallback behaviour (ignoring the `default` key for unknown types) is not documented and only discoverable by inspecting ReactFlow's source code.
