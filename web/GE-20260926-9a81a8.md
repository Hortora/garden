### Symptom

`hostPanel("component-name", { getRowDetail: fn, getRowKey: fn })` is called.
The component declares `@property({ type: Object }) getRowDetail?` — so it should work.
At runtime, `this.getRowDetail` is `undefined`. No error, no warning.

### Context

When a Lit component is hosted via `hostPanel()` in pages-ui, the pages-runtime
calls `component.configure(panelProps)` before `connectedCallback()`. The
`panelProps` object contains all properties passed in the DSL — functions,
objects, arrays, everything.

### What was tried (didn't work)

Assumed `@property` declarations would automatically receive values from
`configure()`. Spent time debugging the hostPanel runtime — which was
delivering the properties correctly.

### Root cause

`configure()` is an explicit method override. Only properties that the
component's `configure()` implementation specifically assigns are wired.
Properties not in the method body are silently dropped — `panelProps`
arrives with them, but they're never read.

The `@property` decorator only handles attribute/property reflection for
DOM usage — it has nothing to do with `configure()`.

### Fix

Every property that hostPanel consumers need must be explicitly handled
in `configure()`:

```typescript
override configure(props: Record<string, unknown>): void {
  // Each property must be explicitly assigned
  if (props.getRowDetail !== undefined)
    this.getRowDetail = props.getRowDetail as (...) => ...;
  if (props.getRowKey !== undefined)
    this.getRowKey = props.getRowKey as (...) => ...;
  super.configure(props);
}
```

### Why this is non-obvious

The `@property` decorator creates the impression that properties are
automatically available. In normal Lit usage (DOM, attribute binding),
they are. But `configure()` is a custom integration point — it's not
part of Lit's property system. The silent failure (no error, property
just stays undefined) makes debugging particularly time-consuming.
