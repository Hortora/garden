### Symptom

Tests for **success paths** pass, but tests for **error paths** fail with
assertions seeing empty results — even though the error handling code is correct.
The same handler works at runtime.

### Context

A synchronous DOM event handler (e.g. `addEventListener('pages-event', onEvent)`)
calls an `async` function and chains `.then()/.catch()` to process results:

```typescript
// Broken pattern
async function executeCommand(cmd: CommandPayload): Promise<void> {
  switch (cmd.action) {
    case 'click': click(cmd.target!); return;     // sync — but wrapped in Promise
    case 'wait': return waitFor(cmd.target!, ...); // genuinely async
    default: throw new Error(`Unknown: ${cmd.action}`); // sync throw — becomes rejected Promise
  }
}

function onEvent(e: Event): void {
  const cmd = parseCommand(e);
  executeCommand(cmd)
    .then(() => sendResult(conn, cmd.id, true, null))
    .catch((err) => sendResult(conn, cmd.id, false, err.message));
}
```

Test code runs synchronously after `dispatchEvent()`:

```typescript
fireCommand(eventTarget, { id: 'cmd-1', action: 'click', target: ... });
expect(conn.sent).toHaveLength(1); // PASSES — but only by luck (microtask scheduling)

fireCommand(eventTarget, { id: 'cmd-2', action: 'unknown', target: ... });
expect(conn.sent).toHaveLength(1); // FAILS — conn.sent is empty
```

### Root cause

The `async` keyword wraps **every** return path in a Promise — including
synchronous returns and synchronous throws. `return;` becomes a resolved
Promise; `throw new Error()` becomes a rejected Promise. Both settle on
the **next microtask**, not synchronously.

`dispatchEvent()` is synchronous — the handler runs inline. But `.then()`
and `.catch()` callbacks are always microtasks. The test assertion runs
before the microtask queue is flushed.

Success paths may appear to work due to microtask scheduling timing in
specific test environments, making the bug intermittent and
environment-dependent.

### Fix

Use a non-async function that returns `void | Promise<void>`. Only the
genuinely async path (`waitFor`) returns a Promise:

```typescript
function executeCommand(cmd: CommandPayload): void | Promise<void> {
  switch (cmd.action) {
    case 'click': click(cmd.target!); return;      // returns void — sync
    case 'wait': return waitFor(cmd.target!, ...);  // returns Promise — async
    default: throw new Error(`Unknown: ${cmd.action}`); // sync throw
  }
}

function onEvent(e: Event): void {
  const cmd = parseCommand(e);
  try {
    const result = executeCommand(cmd);
    if (result) { // Promise — async path
      result
        .then(() => sendResult(conn, cmd.id, true, null))
        .catch((err) => sendResult(conn, cmd.id, false, err.message));
    } else { // void — sync path
      sendResult(conn, cmd.id, true, null);
    }
  } catch (err) { // sync throw
    sendResult(conn, cmd.id, false, (err as Error).message);
  }
}
```

Sync actions dispatch results immediately via try/catch. Async actions
use `.then()/.catch()`. Tests get synchronous verification for the common
case.

### Why this is non-obvious

The `async` keyword is invisible in its effect on synchronous code paths.
A function that does only synchronous work looks and behaves identically
to a non-async version — except that every return and throw is silently
wrapped in a Promise. The symptom (success tests pass, error tests fail)
misdirects toward the error handling logic rather than the `async` keyword.

### Alternatives considered

- Making tests async and awaiting microtask flush (`await new Promise(r => setTimeout(r, 0))`) — works but adds fragile timing dependencies to every test and obscures the real issue
- Using `vi.useFakeTimers()` to control microtask scheduling — overcomplicates tests for a handler that should be synchronous in the first place
