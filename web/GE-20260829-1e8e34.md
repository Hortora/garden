## Server-extracted targets for client-side readiness probing

### Symptom

Designing a script/automation catalog served from a backend, with a
"readiness" indicator per script showing whether the script can run
at the current browser state. The natural design puts `ready: boolean`
on the server's descriptor response.

### Context

The server parses scenario YAML files and builds a catalog of
`ScriptDescriptor` records. Each script's first step targets specific
DOM elements (e.g., ARIA targets like `{role: button, name: Submit}`).
The UI wants to show green/amber/red indicators in the library browser.

### What developers normally try

Put `ready: boolean` directly on the `ScriptDescriptor` returned by
the REST API. The server attempts to determine readiness when the
descriptor is requested.

### Root cause

The server doesn't have access to the browser's DOM. It cannot run
`findByRole()` or any DOM query. Readiness is inherently a client-side
concern — only the browser knows what elements are currently rendered.

### Fix

Split the probe into two parts across the server/client boundary:

1. **Server extracts probe targets at parse time** — when building the
   `ScriptDescriptor`, the server parses the first step's commands and
   extracts ARIA targets into a `firstStepTargets: List<AriaTarget>`
   field on the descriptor.

2. **Client runs the actual DOM check** — the library browser UI
   receives the targets and runs `findByRole()` against the live DOM
   for each target. Green = all found, Red = any missing, Amber = no
   targets to check (e.g., first step is `navigate` or `call`).

```java
// Server side — extract at parse time
public record ScriptDescriptor(
    String name,
    // ...
    List<AriaTarget> firstStepTargets  // extracted from first step's commands
) {}
```

```typescript
// Client side — probe the live DOM
function probeReadiness(targets: AriaTarget[]): 'ready' | 'unknown' | 'not-ready' {
    if (targets.length === 0) return 'unknown';
    for (const target of targets) {
        if (!findByRole(document.body, target.role, target.name)) return 'not-ready';
    }
    return 'ready';
}
```

### Why this is non-obvious

The `ready: boolean` design feels clean — the server has the data,
the client displays it. The boundary violation is invisible until you
try to implement the server-side check and realise the server has no
DOM. Caught during design review, not implementation — if it had
reached implementation, the rework would have been significant
(changing the descriptor type, adding client-side probe logic,
re-wiring the library browser).

### Alternatives considered

- **WebSocket probe from server to browser** — server asks the browser
  to check DOM state. Over-engineered for a catalog display — adds
  round-trip latency and connection management for a simple indicator.
- **Declarative `requires` metadata** — script declares preconditions
  like "requires page /dashboard". More expressive but adds authoring
  burden and a new contract. The ARIA targets already encode what the
  first step needs.
