### Symptom
A dropdown menu appended to an overlay container renders visually and passes unit tests (via `dispatchEvent`), but real user clicks pass through it without triggering any handlers.

### Context
Common pattern in windowing/workspace UIs: an overlay container positioned `absolute; inset: 0` with `pointer-events: none` to let clicks pass through to content underneath. Interactive elements (floating frames, drag handles) inside it have explicit `pointer-events: auto`. But dynamically created elements (dropdowns, menus, tooltips) appended to the overlay container inherit `pointer-events: none` and silently swallow all click attempts.

### What was tried (didn't work)
- Testing with `element.dispatchEvent(new MouseEvent('click', { bubbles: true }))` — handlers fire correctly because `dispatchEvent` bypasses CSS pointer-events entirely
- Debugging click handlers, event propagation, and stopPropagation — all correct; the events simply never reach JavaScript

### Root cause
CSS `pointer-events: none` is inherited by all child elements. `dispatchEvent()` is a JavaScript API that directly invokes event listeners — it does not go through the browser's hit-testing pipeline and therefore ignores CSS `pointer-events`. This creates a testing trap: programmatic events work, real user interaction doesn't.

### Fix
Explicitly set `pointer-events: auto` on any interactive element appended to a `pointer-events: none` container:

```typescript
dropdown.style.cssText = "position:absolute;pointer-events:auto;...";
container.appendChild(dropdown);  // container has pointer-events:none
```

### Why this is non-obvious
1. The CSS inheritance of `pointer-events` is silent — no visual indicator that clicks are being absorbed
2. `dispatchEvent` bypassing pointer-events makes test suites unreliable for detecting this — all unit tests pass while the feature is completely broken for users
3. The overlay pattern (`pointer-events:none` with selective `auto` children) is well-established, but the trap appears when new children are added dynamically after initial setup

### Alternatives considered
- Setting `pointer-events: auto` on the overlay container itself — breaks the pass-through behavior for the entire overlay
- Using Playwright's `{ force: true }` click — works around it in tests but doesn't fix the actual bug
