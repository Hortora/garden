### Symptom
Clicking different rows in a list backed by pages-table always shows the
detail for the first item. No error, no warning — the wrong data appears
silently.

### Context
Any component that listens for the `row-activate` CustomEvent from
`pages-table` and uses `detail.index` to look up the source entity.

### What was tried (didn't work)
Assumed `detail.index` existed (the natural property name for "which row
was clicked"). Used `detail?.index ?? 0` — the nullish coalescing hid
the fact that `index` is always `undefined`, silently falling back to 0.

### Root cause
`pages-table` dispatches `row-activate` with `{ row, key }` in the
detail — where `row` is the TypedRow and `key` is the result of
`getRowKey(row)`. There is no `index` property. No TypeScript type
export exists for the event detail, so the compiler cannot catch the
mistake.

### Fix
Use `detail.key` to identify the entity instead of `detail.index`:

```typescript
private _onRowActivate = (e: Event): void => {
  const detail = (e as CustomEvent).detail;
  const key = detail?.key as string | undefined;
  const entity = key
    ? this._entities.find(ent => reader.id(ent) === key)
    : this._entities[0];
  // ...
};
```

### Why this is non-obvious
`index` is the standard property name for "which item in a list" across
most UI frameworks. The event is `composed: true, bubbles: true` so it
crosses shadow DOM — but its detail shape is only discoverable by grepping
the compiled `pages-data-table.js` source. No type definition, no
documentation, no runtime error when accessing the wrong property.

### Why this fix
Using `key` (the row's identity) is more robust than index anyway —
it survives sorting, filtering, and pagination without mapping visual
position back to data position.
