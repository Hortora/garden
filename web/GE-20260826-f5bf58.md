## Symptom

A wrapper component accepts ReactiveControllers as properties from a host component. Data arrives via the controllers, but the wrapper never re-renders — it displays stale initial state.

## Context

Lit's `ReactiveController` protocol binds the controller to a specific `ReactiveControllerHost` via `host.addController(this)` in the constructor. When data changes, controllers call `this._host.requestUpdate()` on that original host — not on whatever component is currently reading the controller's state.

If component A creates `new MyController(A)` and passes it to component B as a property, the controller calls `A.requestUpdate()` when data changes. Component B never re-renders because `requestUpdate()` was never called on B.

## Fix

The receiving component must create the controllers itself, binding itself as the host:

```typescript
// WRONG — controller updates host A, not this component
@property({ attribute: false }) controller?: MyController;

// RIGHT — this component is the controller host
private _controller?: MyController;

override updated(changed: Map<string, unknown>) {
  if (changed.has('pushController')) {
    this._controller = new MyController(this, this.pushController);
  }
}
```

For convenience wrappers that compose sub-components (workbenches), accept a transport-agnostic data source (e.g. `PushController`) from the host and create domain-specific controllers internally. The transport source only needs `applyOp()` — it doesn't call `requestUpdate()` on data changes directly; registered handlers do that through the domain controllers.

## Why this is non-obvious

The pattern of passing controllers as properties looks natural — controllers are objects, properties carry objects. The binding is implicit (happens in the constructor via `addController`) and the symptom is silent (no error, just stale data). The design review that caught this required tracing the `requestUpdate()` call chain through three layers of indirection.
