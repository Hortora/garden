### Symptom
Importing a package that registers custom elements (via `customElements.define()` in module-level code or static initializers) results in the custom elements not being registered at runtime. The elements render as empty `HTMLUnknownElement` instances. No error is thrown — the registration is silently removed.

### Context
Occurs in webpack 5 production builds when importing a package solely for its side effects (custom element registration). The importing module doesn't reference any exports from the package, so webpack's tree-shaking eliminates the entire import as dead code. Common with Lit-based web component libraries and any package that registers custom elements at import time.

### What was tried (didn't work)
- Adding the import statement (`import '@my/component-lib'`) — tree-shaken away because nothing is used
- Importing and re-exporting a type (`export type { MyComponent }`) — type-only exports don't prevent tree-shaking
- Using `import()` dynamic import — still tree-shaken if the result is unused

### Root cause
webpack 5's tree-shaking respects the `sideEffects` field in `package.json`. When a package declares `"sideEffects": false` (or webpack infers it), imports that don't use any exported bindings are eliminated. Custom element registration happens as a side effect of importing the module, but webpack cannot detect that `customElements.define()` is a meaningful side effect — it treats the entire import as dead code.

### Fix
Add a `sideEffects` rule to the consuming project's webpack config to mark the package's distribution files as having side effects:

```javascript
// webpack.config.js
module.exports = {
  module: {
    rules: [
      {
        test: /node_modules\/@my\/component-lib\/dist/,
        sideEffects: true,
      },
    ],
  },
};
```

Alternatively, if you control the component library, set `"sideEffects": true` (or list specific files) in its `package.json`:

```json
{
  "sideEffects": ["dist/**/*.js"]
}
```

### Why this is non-obvious
The import statement is present in the source code and appears correct. No build warning is emitted. The failure is completely silent — elements simply don't register. Debugging requires knowing that webpack treats side-effect-only imports as dead code, which is counterintuitive when the import's entire purpose is its side effect. The fix location (webpack config rule, not the import statement) is also non-obvious.
