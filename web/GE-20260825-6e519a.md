### Symptom
When a container subtree needs to change (split, collapse, workspace mode transition), the naive approach — unmount the entire root container tree and remount — causes cascading side effects: sibling containers lose ephemeral DOM state (scroll positions, selections, chart highlights), and serialize/recreate cycles introduce state divergence (split brain).

### Context
A recursive container tree where each container has entries, and each entry can hold either content or a child container. Layout strategies (tabbed, accordion, split, free) each manage their own DOM. Structural operations (split a pane, collapse a split, transfer to workspace) need to swap child containers at specific nodes in the tree.

### What was tried (didn't work)
**Full-tree unmount/remount:** `root.unmount(); /* mutate tree */; root.mount(el);` — tears down all DOM and rebuilds it. Simple but loses all ephemeral state in sibling subtrees.

**replaceChild:** `container.replaceChild(oldKey, newEntry)` — uses remove/add decomposition which triggers cascade collapse on 2-entry splits (see GE-20260825-6f8a9e).

**Serialize/recreate:** Capture container state to JSON, create entirely new container instances from the snapshot. Guarantees fresh state — but diverges from the original (split brain). Any imperfection in the getState/restoreState round-trip becomes a bug.

### Root cause
The remove/add and full-tree approaches both stem from the assumption that changing a subtree requires destroying and recreating containers. But entry properties (`childContainer`, `component`) are mutable — the entry object is shared between the container's entry array and the strategy's internal array. Mutating the entry is visible to both.

### Fix — the refreshEntry pattern

Add `refreshEntry(key: string)` to the strategy interface and the container:

```typescript
// Container delegates to strategy
refreshEntry(key: string): void {
  const entry = entries.find(e => e.key === key);
  if (!entry) return;
  currentOrganiser.refreshEntry(key);
}
```

Each strategy re-renders just that entry's content slot:

```typescript
// Tabbed strategy — only re-renders if this is the active tab
refreshEntry(key: string): void {
  const entry = currentEntries.find(e => e.key === key);
  if (!entry || key !== activeKey || !contentEl) return;
  if (entry.contentElement?.parentElement) entry.contentElement.remove();
  entry.contentDispose?.();
  entry.contentElement = undefined;
  entry.contentDispose = undefined;
  contentEl.appendChild(ensureContent(entry));
}
```

**Usage pattern for surgical replant:**

```typescript
// 1. Unmount old child (if it was mounted)
oldChild.unmount();

// 2. Mutate the entry in place
entry.childContainer = newSplitContainer;

// 3. Re-render just that slot
parentContainer.refreshEntry(entry.key);
```

No remove/add cycle. No cascade collapse. No position changes. No full-tree teardown. Siblings are completely untouched.

### Why this is non-obvious
The intuitive approach for swapping a subtree is to use `replaceChild` or full-tree remount — both are the "standard" solutions in component frameworks. Mutating entry properties in place feels unsafe ("what if the strategy doesn't see the change?"), but because the strategy's `currentEntries` holds references to the same Entry objects (shallow array copy, not deep), the mutation is immediately visible. The `refreshEntry` call then tells the strategy "this entry changed, re-render its slot" — a targeted notification instead of a destructive rebuild.

**Critical implementation detail:** `Container.refreshEntry` must NOT clear `entry.contentElement` before delegating to the strategy. The strategy needs the old reference to find and remove the DOM element from its layout. If the container clears it first, the strategy can't locate the old element, leaving stale DOM in place.
