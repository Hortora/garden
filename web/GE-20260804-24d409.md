### Symptom
Custom element renders child content but has no styles, no event handling,
no reactive properties, and no shadow DOM. The UI looks "close enough" to
pass visual inspection — layout is roughly correct because slotted children
still appear as regular HTML.

### Context
A Lit component registers as `@customElement('blocks-split-workbench')` but
the consuming template uses `<split-workbench>`. The browser treats
`<split-workbench>` as an unknown HTMLElement — it never upgrades. No
console error, no warning. The import succeeds (the class is loaded and
registered under its declared tag name), but the template references a
different tag that nobody registered.

### What didn't work
- Visual testing — the layout appeared functional because child elements
  rendered as regular HTML (no shadow DOM boundary to hide them)
- The bug survived across 3+ implementation sessions (#103-#105) without
  detection because the mock data populated the child elements correctly

### Root cause
Custom element registration is tag-name exact. `customElements.define('blocks-foo', Foo)`
only upgrades `<blocks-foo>` elements. `<foo>` is a completely separate,
unknown element — the browser does not connect them. There is no fuzzy
matching, no warning, and no runtime error.

### Fix
Match the tag name in the template exactly to the `@customElement()` decorator
value. When consuming a component library that uses a vendor prefix (e.g.
`blocks-`), always use the prefixed tag in templates:

```html
<!-- Wrong — never upgrades -->
<split-workbench></split-workbench>

<!-- Correct -->
<blocks-split-workbench></blocks-split-workbench>
```

Verify tag names by checking `@customElement('...')` in the component source
or `customElements.get('tag-name')` in the browser console.

### Why this is non-obvious
The failure is completely silent. The browser renders unknown custom elements
as inline/block elements that display their children — so the content appears.
There is no console error, no TypeScript error (Lit templates are tagged
template literals, not type-checked against the custom element registry), and
no build error. The visual output is degraded but functional-looking.

### Alternatives considered
- TypeScript strict custom element type checking: not supported by Lit's html
  tagged template literals — tag names are strings, not types
- ESLint rules for custom element registration: exist but not enforced in
  this project; would catch the mismatch at lint time
