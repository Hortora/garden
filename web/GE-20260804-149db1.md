## Quarkus Quinoa dev mode serves stale frontend

### Symptom

After running `yarn build` manually in the webui directory, the browser still shows the old frontend code. Hard refresh, cache-busting query parameters, and new browser tabs all serve the stale version.

### Context

Quarkus Quinoa copies the frontend build output from `src/main/webui/dist/` to `target/quinoa/build/` during Quarkus startup. The Quarkus HTTP server serves static files from `target/quinoa/build/`, not from `dist/` directly.

### Root cause

Manual `yarn build` updates `dist/app.js` but Quinoa only re-copies to `target/quinoa/build/` when:
1. Quarkus starts up (initial copy)
2. A Java source file change triggers hot-reload (Quinoa re-runs the build as part of the reload cycle)

Without a Java file change, the hot-reload cycle doesn't fire and Quinoa serves the stale copy.

### Fix

Touch any Java file to trigger the Quarkus hot-reload cycle, which forces Quinoa to re-copy:

```bash
touch src/main/java/some/ExistingFile.java
```

Or restart `quarkus:dev` entirely for a clean rebuild.

The browser may also cache the old JS aggressively — use a cache-busting query parameter:
```
http://localhost:8080/?_=timestamp#route
```

### Why this is non-obvious

The mental model is "yarn build updates the frontend, Quarkus serves the updated files." In reality there is an intermediate copy step that only fires on Java changes. The `yarn build` succeeds, the `dist/` directory has the new code, but the served files are from a different directory. No error or warning indicates the served version is stale.
