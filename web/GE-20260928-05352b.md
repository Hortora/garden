### Symptom
Test assertions on `TemplateResult.values[N].strings` crash with "Cannot read properties of undefined (reading 'join')" or "Cannot read properties of undefined (reading '0')" when the template contains `.map()` calls inside `html` tagged template literals.

Tests that check only top-level template strings pass — but any assertion that traverses into `values` to find content rendered by `.map()` silently misses the mapped content or crashes.

### Context
When testing lit `html` tagged template output without DOM rendering (e.g. in vitest with jsdom), the natural approach is to inspect `TemplateResult.strings` and `TemplateResult.values` directly. This works for simple templates but breaks when the template contains `.map()`.

### What was tried (didn't work)
Navigating the `TemplateResult` structure assuming values are either primitives or nested `TemplateResult` objects:

```typescript
const values = (result as { values: unknown[] }).values;
const inner = values[0] as { strings: readonly string[] };
inner.strings.join(''); // crashes — inner is an Array, not a TemplateResult
```

### Root cause
Lit's `html` tagged template literal processes `.map()` results as `Array<TemplateResult>` entries in the `values` array. The template engine handles array flattening at render time (when stamping to DOM), but the raw `TemplateResult` data structure preserves the array nesting.

For example, `html\`<ul>${items.map(i => html\`<li>${i}</li>\`)}</ul>\`` produces a `TemplateResult` where `values[0]` is `Array<TemplateResult>`, not a single `TemplateResult`.

### Fix
A recursive `collectText` helper that handles all value types:

```typescript
import { nothing } from 'lit';

function collectText(result: unknown): string {
  if (result === nothing || result == null) return '';
  if (typeof result === 'string' || typeof result === 'number' || typeof result === 'boolean') {
    return String(result);
  }
  if (Array.isArray(result)) return result.map(collectText).join('');
  const r = result as { strings?: readonly string[]; values?: unknown[] };
  if (!r.strings) return '';
  let text = '';
  for (let i = 0; i < r.strings.length; i++) {
    text += r.strings[i];
    if (r.values && i < r.values.length) {
      text += collectText(r.values[i]);
    }
  }
  return text;
}
```

Usage in tests:

```typescript
const text = collectText(renderMyComponent(data));
expect(text).toContain('expected-css-class');
expect(text).toContain('expected-content');
```

This flattens the entire template tree — including `.map()`-produced arrays, `nothing` sentinels, and nested `TemplateResult` objects — into a single string suitable for `toContain()` assertions.

### Why this is non-obvious
The `TemplateResult` type doesn't document its internal structure for testing purposes — it's designed for DOM stamping, not inspection. The natural testing approach is to render to a real DOM via jsdom and query elements, but that requires custom element registration, is slower, and pulls in more infrastructure. Direct `TemplateResult` inspection is faster and sufficient for many test scenarios, but only works with the array-aware recursive traversal.

### Alternatives considered
- **DOM rendering with jsdom:** Works but requires registering custom elements, waiting for updates, and querying the DOM. Much heavier for simple "does the template contain X" assertions.
- **Snapshot testing:** Captures the full template output but is brittle to whitespace and attribute ordering changes.
