# Coordinated-mode flag to suppress document-internal undo/notification under external coordination

### Symptom
When adding an external coordinator (_applyEdit) over a document model (PageDocument) that has its own internal undo stack and onChange notification, every mutation fires both the coordinator's sync pipeline AND the document's internal notification — causing double editor writes, double change emissions, and dual undo stacks recording the same operation.

### Context
Rich editor architectures where a shell/coordinator wraps a document model. The document model was designed for standalone use (internal undo, internal onChange notification). The shell adds its own undo stack (YAML string snapshots) and view sync pipeline (_syncViews). Both mechanisms coexist during migration — you can't remove the internal one without breaking standalone consumers.

### What developers usually try
1. Remove the document's internal notification — breaks standalone consumers and tests
2. Add the coordinator first, then suppress notification — creates a window where both fire during the transition
3. Use a flag that callers set/unset around each mutation — error-prone, easy to forget

### Root cause
The document model's _notify() and _pushUndo() fire synchronously inside every mutation method. When an external coordinator wraps these mutations, both the coordinator's post-mutation sync and the document's internal sync execute.

### Fix
Add a construction-time `_coordinated` flag to the document model. When set, `_pushUndo()` and `_notify()` become no-ops. The flag is set via a factory method (`parseCoordinated()`), ensuring it's never forgotten at a call site.

The critical ordering: enable coordinated mode BEFORE adding the coordinator. This eliminates the double-fire window entirely — the document's internal mechanisms are already suppressed when the first coordinated mutation arrives.

```typescript
static parseCoordinated(yaml: string): PageDocument {
  const doc = PageDocument.parse(yaml);
  doc._coordinated = true;
  return doc;
}

private _notify(): void {
  if (this._coordinated) return;
  if (this._inTransaction) return;
  for (const l of this._listeners) l(this.toString());
}
```

Transaction methods (beginTransaction/commitTransaction/abortTransaction) also guard their direct stack manipulation with `if (!this._coordinated)`, preserving atomicity (rollback still works) while suppressing undo recording.

### Why this is non-obvious
The natural instinct is to add the coordinator and remove the old sync path. But removal breaks standalone consumers, and the two-step migration (add coordinator, then remove old path) creates a double-fire window that causes subtle bugs — cursor jumps, duplicate change events, undo stack corruption. The flag-at-construction pattern eliminates both problems.

### Why this fix
A runtime toggle (set/unset per mutation) is fragile — every call site must remember to set the flag. A construction-time factory makes coordination a property of the document instance, not a per-call discipline.

### Alternatives considered
- **Remove internal undo/notification entirely** — breaks standalone PageDocument consumers and 105 existing tests. Rejected.
- **Wrapper/proxy pattern** — intercept _notify calls via a subclass or proxy. More complex, harder to reason about, and the transaction method guards still need explicit changes. Rejected.
- **Event-based coordination** — document emits events, coordinator listens. Doesn't solve the double-fire problem — the coordinator's _syncViews and the document's onChange both fire.
