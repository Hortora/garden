## ReactFlow is wrong for force-directed graph rendering — use D3 SVG directly

### Symptom
Existing graph infrastructure wraps ReactFlow in a Lit component for directed diagrams. The natural approach for a force-directed graph is to reuse this infrastructure with a pluggable layout function. It compiles and renders but the interaction model is fundamentally wrong.

### Context
`pages-graph-canvas` wraps ReactFlow with ELK layout — designed for static, directed diagrams (case definitions, workflows, DAG plans). Node positions are computed once by ELK, then rendered by ReactFlow. This works because positions are stable.

Force-directed simulation is a different paradigm: positions evolve continuously as the simulation ticks, drag feeds back into physics, and the graph converges over time.

### What was tried (didn't work)
Making ReactFlow's layout pluggable — swapping ELK for D3 force as a `layoutFn`. The positions could be pre-computed (run simulation to convergence), but:
- Drag-to-rebalance doesn't exist in ReactFlow — dragging just repositions the node statically
- React reconciliation runs on every position update during simulation ticks — unnecessary overhead
- The ReactFlow node component bridge (Lit → React via `createStencilNodeComponent`) adds complexity with no benefit

### Root cause
ReactFlow is designed for node-based UIs with fixed positions. It expects stable coordinates and uses React's virtual DOM for updates. Force-directed simulation needs direct SVG DOM manipulation — D3 updates element attributes directly without any framework overhead.

### Fix
Use D3 modules (`d3-force`, `d3-selection`, `d3-zoom`, `d3-drag`) directly in a Lit component. The component owns the SVG element via Lit's `render()`, then D3 takes ownership of the `<g>` container for node/edge rendering. The simulation's `tick` callback updates SVG attributes directly.

Share the graph data model (`GraphModel` from `graph-core`) for platform consistency, but render with D3's own SVG pipeline.

### Why this is non-obvious
The existing graph infrastructure (`graph-core` + `graph-renderer` + `pages-graph-canvas`) is well-designed and works for its use case. The natural assumption is that adding a new layout algorithm to the same pipeline is simpler than building a parallel rendering path. The paradigm mismatch between static-position rendering (ReactFlow) and continuous-simulation rendering (D3 force) only becomes apparent when you trace through the interaction model.

### Alternatives considered
- **Pre-compute force positions, render in ReactFlow** — works for static display but loses drag-to-rebalance, which is the primary interaction affordance of a force-directed graph
- **Pluggable layout in GraphCanvas** — small API change to pages, but doesn't fix the ReactFlow interaction model mismatch
