### Symptom

After adding `role` and `aria-label` via `this.setAttribute()` in `connectedCallback()`, dynamic ARIA state attributes (`aria-busy`, `aria-disabled`, `aria-expanded`) don't update when the component's internal state changes.

A screen reader sees the initial state but never learns when loading starts/stops, when a picker opens/closes, or when a control becomes disabled.

### Context

Lit web components with `@state()` private reactive properties that drive UI state (e.g. `_loading`, `_showPicker`, `disabled`). The `@state()` decorator triggers re-renders but does NOT reflect values to DOM attributes.

### What was tried (didn't work)

Setting `aria-busy` once in `connectedCallback()` alongside `role` and `aria-label`. The attribute stayed at its initial value regardless of `_loading` changes — Lit re-renders the shadow DOM template but never touches host attributes unless explicitly told to.

### Root cause

Lit's `@state()` decorator is explicitly designed to NOT reflect to DOM attributes (it's private reactive state). Only `@property({ reflect: true })` reflects. Since ARIA state attributes live on the host element (not in the shadow DOM template), they need manual `setAttribute()` calls that track the state changes.

### Fix

Set dynamic ARIA attributes in `render()` (called on every state change) or `willUpdate()`:

```typescript
// In render() — for loading state
override render() {
  this.setAttribute('aria-busy', String(this._loading));
  // ... template
}

// In willUpdate() — for property-driven state like disabled
override willUpdate(changed: Map<PropertyKey, unknown>): void {
  if (changed.has('disabled')) {
    this.setAttribute('aria-disabled', String(this.disabled));
  }
}
```

Static attributes (`role`, `aria-label`, `aria-live`) stay in `connectedCallback()` — they don't change. Dynamic state attributes go in `render()` or `willUpdate()`.

### Why this is non-obvious

The `connectedCallback` pattern feels complete — "I set all the ARIA attributes, done." The trap is that `@state() _loading = false` looks like it should be observable, and `role` + `aria-label` work fine from `connectedCallback`, so there's no signal that `aria-busy` needs different treatment. The failure is silent: no console warning, no test failure, no build error — just an invisible screen reader gap.

### Alternatives considered

- `@property({ reflect: true, attribute: 'aria-busy' })` — works but pollutes the public API with ARIA implementation details. Internal loading state should stay `@state()`.
- Lit reactive controller for ARIA — adds indirection for what's a one-line `setAttribute` call.
