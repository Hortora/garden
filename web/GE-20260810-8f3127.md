## Symptom

A parent component manages selection state via `@state` (e.g. `bulkSelected: string[]`). A child component (`grove-entry-table`) is conditionally rendered only in one view mode. After selecting entries, switching to another mode (which unmounts the child), then switching back:

- The parent's bulk action bar shows "3 selected"
- The child table's checkboxes are all unchecked
- The UI is inconsistent — stale parent state paired with fresh child state

No error, no warning. The bulk action bar is technically correct (the parent array has 3 items) but the user sees no visual indication of which entries are selected.

## Context

This occurs when:
1. A parent Lit component uses `@state` to track child-derived state (e.g. selection from a child event)
2. The child is conditionally rendered (`${this.mode === 'list' ? html\`<child>\` : html\`<other>\`}`)
3. The child maintains its own internal state (e.g. a `Set<string>` of selected IDs)
4. Switching modes unmounts the child (Lit removes it from DOM) but the parent's `@state` properties persist

## Root cause

Lit's `@state` decorator creates reactive properties on the component instance. When a child is conditionally removed from the template, Lit calls `disconnectedCallback` on the child and garbage-collects it. But the parent instance stays alive — its `@state` properties are never cleared by child lifecycle events.

The child's internal `selected` Set is rebuilt empty on next render (fresh instance). The parent's `bulkSelected` array still holds the old values from the previous child instance's events.

## Fix

Clear parent state that couples to child internal state whenever the view mode changes away from the mode that renders that child:

```typescript
// In the parent's mode-switch handler:
<button @click=${() => {
  this.mode = 'detail';
  this.bulkSelected = [];  // clear state coupled to the list-mode child
}}>Detail</button>
```

Apply this in every code path that transitions away from the child's render mode — button clicks, programmatic navigation, entry selection that switches modes.

## Why this is non-obvious

Developers expect unmounting a child to "clean up" related state. In React, lifting state to a parent with conditional children has the same issue, but React's ecosystem has patterns like `useEffect` cleanup. In Lit, `@state` is a simple reactive property with no lifecycle hooks tied to child presence — there's nothing that fires when "the child this state was derived from" disappears.

The bug is invisible in testing unless you specifically test the round-trip: select → switch away → switch back. Single-direction tests (select → verify) pass fine.

### Alternatives considered

- Persisting selection in the child and restoring on reconnect — adds complexity to the child for a parent concern
- Using a shared store/context — overkill for view-local selection state
- Clearing in `switchToList()` — only covers one direction; the fix must cover all paths into detail mode
