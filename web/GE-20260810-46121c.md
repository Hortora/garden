### Symptom

`npm ci` completes with exit code 0 and reports "added N packages" — but `node_modules/@scope/package` entries are dangling symlinks pointing to non-existent directories. The build appears to succeed until esbuild (or any bundler) tries to resolve imports from those packages and fails with "Could not resolve".

### Context

A Quarkus project using Quinoa for frontend builds. The `package.json` used Yarn-style `resolutions` with `portal:` links to local directories. A CI migration switched from checking out a sibling repo (creating the symlink targets) to Maven WebJar extraction (different path). The `package-lock.json` was not regenerated — it still had `link: true` entries pointing to the old sibling paths.

### Root cause

`npm ci` reads `package-lock.json` strictly. For entries with `"link": true`, it creates symlinks in `node_modules/` pointing to the `resolved` path — without checking whether the target directory exists. The command exits 0 regardless. The dangling symlinks only cause failures when a bundler (esbuild, webpack) or Node.js runtime tries to follow them.

Additionally, npm ignores the `resolutions` field in `package.json` entirely — that's a Yarn-only feature. So even though `resolutions` pointed to the correct `.casehub-packages/` paths, npm never read them.

### What was tried (didn't work)

1. Switching `dependencies` from `"*"` to `"file:.casehub-packages/..."` — npm then tried to resolve the packages' transitive `@casehubio/*` dependencies from the npm registry (404)
2. Using npm `overrides` instead of Yarn `resolutions` — same transitive resolution problem
3. Setting `quarkus.quinoa.package-manager-command=yarn` — Quinoa prepends `npm` to the command, resulting in `npm yarn install`
4. Adding esbuild aliases for all casehub packages — broke on subpath imports (`@scope/pkg/subpath`) and transitive deps

### Fix

Ensure the `package-lock.json` link targets match the actual location where packages are extracted. Two approaches:

**Approach 1 — Make the link targets exist on CI:**
Restore the CI checkout step that places the sibling repo at the path the lock file expects. This is the path of least resistance when the lock file was generated against a sibling directory layout.

**Approach 2 — Regenerate the lock file:**
Delete `package-lock.json`, run `npm install` with packages at their new location, commit the new lock file. Only works if npm can resolve all transitive dependencies (fails when packages have internal `@scope/*` deps not on the npm registry).

### Why this is non-obvious

`npm ci` exiting 0 is the misleading signal. In most CI systems, a green install step means packages are ready. The failure only surfaces later in the build step when the bundler follows the symlinks. With 16 real packages installed alongside 6 dangling links, the "added 16 packages" output looks normal. The 12-day CI outage in DraftHouse was caused by this — nobody noticed because `npm ci` never reported an error.

### Why this fix

Approach 1 (restore checkout) was chosen because the lock file was generated against a Yarn workspace layout with sibling repos. Regenerating the lock file (Approach 2) was impossible because the packages' internal dependencies used `@casehubio/*` scoped names not published to npm — npm install 404'd on transitive resolution.

### Alternatives considered

- **Switch to Yarn entirely** — Yarn supports `resolutions` with `portal:` natively, but Quinoa (Quarkus frontend plugin) only auto-detects Yarn from `yarn.lock` presence, and its `package-manager-command` property is appended to `npm`, not a replacement. Would require disabling Quinoa's package manager and managing Yarn externally.
- **esbuild aliases for all packages** — works for direct imports but breaks on subpath imports (`@scope/pkg/input`) and doesn't resolve transitive dependencies that the aliased packages need.
