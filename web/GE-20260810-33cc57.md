### Symptom

Setting `quarkus.quinoa.package-manager-command=yarn` or `quarkus.quinoa.package-manager-command.install=yarn install` results in Quinoa running `npm yarn` or `npm yarn install` — the npm CLI receives "yarn" as an unknown subcommand and fails.

### Context

A project needs Yarn for its `resolutions` / `portal:` dependency resolution (npm ignores the `resolutions` field). Quinoa handles frontend builds in Quarkus and has a `package-manager-command` config property that appears to support switching package managers.

### Root cause

When `quarkus.quinoa.package-manager-install=true`, Quinoa downloads and installs its own Node.js + npm. The `package-manager-command` property values are passed as **arguments to the installed npm binary**, not as replacement commands. The install command is always: `node <quinoa-npm-path>/npm-cli.js <command-value>`.

Quinoa auto-detects the package manager from lock files (`package-lock.json` → npm, `yarn.lock` → yarn), but when `package-manager-install=true`, it only installs npm — yarn detection has no effect on the install step.

### Fix

Do not use `package-manager-command` to switch package managers. Instead:

1. Disable Quinoa's install: set `quarkus.quinoa.package-manager-install=false`
2. Ensure node/yarn are available in the environment (CI runners have node; use `corepack enable` for yarn)
3. Run `yarn install` as a separate CI step before the Maven build

Or: keep Quinoa's npm install but ensure the CI environment makes packages available through paths that npm can resolve (checkout sibling repos, use `file:` deps).

### Why this is non-obvious

The property name `package-manager-command` strongly implies it controls which package manager runs. The Quinoa documentation doesn't clarify that it's appended to npm rather than replacing the command. The only way to discover this is from the runtime log output showing `npm yarn install`.
