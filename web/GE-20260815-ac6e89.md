## Content preserved across layout toggle via detach/reattach — not destroy/recreate

### Stack
TypeScript, DOM APIs, Lit web components

### Symptom
Toggling between layout modes (tab view ↔ accordion view ↔ free-layout) caused nested component state loss — scroll positions reset, nested workspace frames disappeared, event listeners broke. Every toggle was a full destroy/recreate cycle.

### Context
A floating frame system where each frame can display its content in different arrangements (tabs showing one panel at a time, accordion showing all panels stacked, free-layout with positioned rectangles). Toggling between arrangements requires changing the DOM structure — tab strips, accordion headers, and positioned containers are fundamentally different DOM trees.

### What was tried (didn't work)
1. **Hide/show with display:none** — CSS-only approach, but the layout containers (tab strip vs accordion headers) are structurally different, not just visually different. Hiding one and showing another leaves orphaned DOM and stale event listeners.
2. **Destroy and recreate content** — the obvious approach. Works for simple content but loses nested component state (nested workspace frames, scroll positions, form inputs). For content containing web components with internal state, recreation means state loss.
3. **Move content between containers** — tried to use the same container element and swap the wrapper. But the wrapper IS the layout — you can't change a tab panel into an accordion section by CSS alone.

### Fix
Cache content elements on the data model (Entry objects), not in the DOM. The layout organiser borrows content elements — it never owns them.

```typescript
interface Entry {
  readonly key: string;
  readonly label: string;
  contentElement?: HTMLElement;    // cached after first render
  contentDispose?: () => void;
}

interface Organiser {
  mount(container: HTMLElement, entries: Entry[], factory: ContentFactory): void;
  unmount(): void;  // detaches content elements, tears down organiser DOM
}
```

Toggle lifecycle:
```
1. currentOrganiser.unmount()
   → detaches content elements from slots (removeChild, not dispose)
   → tears down organiser-specific DOM (tab strip, accordion headers)
   → content elements remain cached on Entry objects

2. newOrganiser = createOrganiser(newType)

3. newOrganiser.mount(container, entries, factory)
   → creates new organiser DOM
   → reattaches cached content elements into new slots (appendChild)
   → content elements that don't exist yet are created via factory
```

The key rules:
- `unmount()` only touches organiser-owned DOM (tab strip, accordion headers, resize handles). It detaches content via `removeChild` but never calls `dispose`.
- `mount()` checks `entry.contentElement` — if present, reattaches it; if absent, calls the factory to create it.
- Content elements are created once (lazily, on first mount) and reused across all subsequent organiser toggles.

### Why this is non-obvious
The default instinct is destroy/recreate because the DOM structures are genuinely different. The insight is separating ownership: the organiser owns the layout DOM (tab strip, accordion headers), the Entry owns the content element. These are independent lifecycles. The organiser is ephemeral (created/destroyed on toggle); the content is persistent (survives across toggles).

This is the same principle as React's reconciliation or Lit's template caching — but applied at the layout level rather than the component level.

### Alternatives considered
- **Destroy/recreate** — simpler but loses all nested state; was the approach that caused 24 hours of lifecycle bugs
- **CSS-only toggle** — impossible when the layout containers are structurally different
- **Shadow DOM encapsulation** — would preserve content but adds unnecessary complexity; standard `appendChild` reparenting already works for HTML elements and Lit components
