### Symptom

Gallery page loads, bundle script executes, `window.casehubPages` global is available
with `loadSite` function — but custom elements never render. Shadow root is null.
`customElements.get('pages-action-catalog')` returns `undefined` despite the component
class being in the bundle. No console errors.

### Context

A monorepo gallery app uses webpack to bundle a Lit web component library. The library's
`package.json` has `"sideEffects": ["dist/*.js"]`. The webpack alias was changed to point
to source (`src/controller/standalone.ts`) instead of the pre-built dist file. The source
file has bare side-effect imports:

```typescript
import './scenario-controller.js';
import './step-catalog.js';
```

Each imported module calls `customElements.define()` at module scope.

### What was tried (didn't work)

1. Verified the bundle contained the component class — `grep -c "customElements"` showed 0
2. Checked if the component was registered — `customElements.get()` returned undefined
3. Rebuilt the dist bundle with esbuild — same result (esbuild also honours `sideEffects`)
4. Tried different ports thinking the dev server was stale

### Root cause

`"sideEffects": ["dist/*.js"]` tells webpack that only files matching `dist/*.js` have
side effects. When the webpack alias pointed to source files (`src/controller/standalone.ts`),
those source files didn't match the `dist/*.js` glob. Webpack treated all bare side-effect
imports as tree-shakeable and eliminated them — including the `customElements.define()` calls.

The bundle was 1MB but contained zero component registrations. The library object loaded
fine because its named exports were used, but the side-effect imports that register custom
elements were silently removed.

### Fix

Add source files that register custom elements to the `sideEffects` array:

```json
{
  "sideEffects": [
    "dist/*.js",
    "src/controller/standalone.ts",
    "src/controller/step-catalog.ts",
    "src/controller/scenario-controller.ts"
  ]
}
```

### Why this is non-obvious

The bundle is large (1MB) and the library global loads correctly — `typeof window.casehubPages`
returns `"object"`. Named exports work. The failure is entirely silent: no error, no warning,
components simply don't upgrade from HTMLElement. The `sideEffects` field is rarely inspected
during debugging because it's in the library's package.json, not the consuming app's config.

### Why this fix

The alternative — setting `"sideEffects": true` — disables tree-shaking for the entire package.
The targeted approach preserves tree-shaking for genuinely side-effect-free modules while
correctly marking the files that register custom elements.
