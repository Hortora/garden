### Symptom
A DnD handler needs edge-zone detection (is the pointer near a frame edge?) and split geometry computation (where do the two halves go after a split?). The temptation is to reimplement this geometry inline in the DnD handler.

### Context
An existing `frame-boundaries.ts` module already has pure functions for edge detection and split geometry, originally written for snap-zone and resize features. The DnD handler needs the same calculations for edge-split drops.

### Fix
Import and compose the existing pure functions directly in the DnD state machine's pointermove handler:

```typescript
import { detectEdgeZone, type EdgeZone } from "../frame-boundaries.js";

function detectTarget(clientX: number, clientY: number): {
  frameKey: string | null;
  edge: EdgeZone | null;
} {
  // ... hit-test against entry positions
  const edge = detectEdgeZone(
    { x, y },
    { x: position.x, y: position.y, width: size.width, height: size.height },
    EDGE_THRESHOLD,
  );
  return { frameKey: key, edge };
}
```

On drop, the `splitGeometry()` function computes both the resized target and new frame positions in one call:

```typescript
import { splitGeometry } from "../frame-boundaries.js";

const geo = splitGeometry(edge, targetRect);
// geo.target = resized existing frame
// geo.newFrame = position/size for the new frame
```

### Why this is non-obvious
DnD handlers are imperative state machines — developers tend to write self-contained logic rather than reaching for existing pure functions. The pure functions were written for different features (snap zones, resize) but their signatures are generic enough to compose directly. No adapters needed — the geometry types align naturally.
