### Symptom

Lip sync works on the first message but silently fails on every subsequent message. The avatar mouth doesn't move despite viseme data being present in the WebSocket segment messages. No errors in console.

### Context

A WebSocket-based avatar speech pipeline where:
- Server sends `segment` JSON (text, visemes, cues) followed by binary audio frames
- Client stores segments in `_pendingSegments` map keyed by `turnSeq:index`
- On new turn (different `turnSeq`), `_resetTurnState()` clears `_pendingSegments`
- Audio handler looks up the segment to attach viseme data for TalkingHead's `speakAudio`

### Root cause

Order-of-operations bug in `_handleSegment`:

```javascript
_handleSegment(msg) {
    const key = `${msg.turnSeq}:${msg.index}`;
    this._pendingSegments.set(key, { ... });  // ← STORES segment
    if (msg.turnSeq !== this._activeTurnSeq) {
        this._resetTurnState();     // ← CLEARS _pendingSegments (including what was just stored!)
        this._activeTurnSeq = msg.turnSeq;
    }
}
```

The segment is stored **before** the new-turn check. When the second message arrives with a new `turnSeq`, `_resetTurnState()` immediately wipes the segment that was just stored. When the audio frame arrives, `_pendingSegments.get(key)` returns `undefined`, so `r.words` is never set, and TalkingHead gets no viseme data.

### Why first message works

The first message's `turnSeq` matches `_activeTurnSeq` (both initial value), so `_resetTurnState()` is never called — `_pendingSegments` retains the data.

### Fix

Move the new-turn check **before** storing the segment:

```javascript
_handleSegment(msg) {
    if (msg.turnSeq !== this._activeTurnSeq) {
        this._resetTurnState();
        this._activeTurnSeq = msg.turnSeq;
    }
    const key = `${msg.turnSeq}:${msg.index}`;
    this._pendingSegments.set(key, { ... });
}
```

### Why this is non-obvious

The symptom (second message fails) suggests a server-side issue — different TTS path, state accumulation, or streaming vs non-streaming mismatch. The actual bug is a 3-line ordering issue in the client. Server-side investigation confirmed the pipeline is stateless per call, redirecting to the client where the store-then-clear pattern is easy to overlook.
