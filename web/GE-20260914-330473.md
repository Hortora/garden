## Symptom

LSP server process starts and appears in IntelliJ's Language Servers panel (running state), but IntelliJ log shows ZERO `textDocument/didOpen` or `textDocument/completion` entries. Server is idle — receiving nothing after the `initialize` handshake.

## Context

Building an LSP server with `vscode-languageserver` (Node.js) consumed by an IntelliJ plugin via LSP4IJ. The server returns `textDocumentSync: TextDocumentSyncKind.Full` (value `1`) in its `initialize` response — a bare number, which is valid per the LSP specification.

## What was tried (didn't work)

- Verified the server responds correctly to `initialize` via direct stdio testing — response is valid JSON-RPC with correct capabilities
- Verified `textDocument/didOpen` → `textDocument/completion` flow works end-to-end via stdio
- Multiple iterations of plugin changes (custom language types, CompletionContributors) — all failed
- Server process runs, LSP4IJ starts it, but no document events flow

## Root cause

The LSP specification defines `textDocumentSync` as `TextDocumentSyncOptions | TextDocumentSyncKind` — both the object form and the number form are valid. However, LSP4IJ may only parse the object form. Without `openClose: true` in the response, LSP4IJ doesn't know the server supports `didOpen`/`didClose` notifications and doesn't send them.

## Fix

Return the `TextDocumentSyncOptions` object form instead of the bare `TextDocumentSyncKind` number:

```typescript
// Before — number form (may not work with LSP4IJ)
connection.onInitialize(() => ({
  capabilities: {
    textDocumentSync: TextDocumentSyncKind.Full,  // value: 1
  },
}));

// After — object form (explicit openClose)
connection.onInitialize(() => ({
  capabilities: {
    textDocumentSync: {
      openClose: true,
      change: TextDocumentSyncKind.Full,
    },
  },
}));
```

### Why this is non-obvious

The LSP specification explicitly defines `textDocumentSync` as a union type accepting both forms. Every `vscode-languageserver` example and tutorial uses the number form. `vscode-languageclient` handles both. The server passes all protocol-level tests with the number form. The failure is silent — no error, no warning, just zero document events.

### Alternatives considered

- Debugging LSP4IJ source to confirm the parsing behavior — would be definitive but requires building LSP4IJ from source
- Filing an LSP4IJ bug for number-form support — correct long-term fix if confirmed
