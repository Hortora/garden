### Symptom
`setAttribute('aria-expanded', 'true')` on a `<div role="group">` succeeds silently, but a subsequent `getAttribute('aria-expanded')` returns the original value (`'false'`), not `'true'`. Other operations on the same element (e.g. `dispatchEvent`) work correctly — the element reference is valid.

### Context
Occurs in jsdom-based test environments (vitest with jsdom environment) when setting ARIA state attributes on non-form elements — divs, spans, or custom elements with explicit `role` attributes. Form elements (`<input>`, `<select>`) and their native boolean attributes (`disabled`, `checked`) are not affected.

Discovered in ARIA command executor tests where `expand()` and `collapse()` functions both call `setAttribute` then `dispatchEvent`. The click handler fires (proving the element was found), but the attribute assertion fails.

### Root cause
jsdom's attribute reflection for ARIA attributes on generic elements does not behave identically to browser engines. The setAttribute call may be intercepted by jsdom's ARIA attribute handling layer without updating the underlying attribute store that getAttribute reads from. This is specific to `aria-*` attributes on elements where jsdom does not model the full ARIA reflection spec.

### Fix
Separate concerns in tests. Test event dispatch (the executor's responsibility) independently from attribute mutation:

```typescript
// Don't: assert both click and attribute in one test
it('expand sets aria-expanded and dispatches click', async () => {
  expand({ role: 'group', name: 'Details' });
  expect(handler).toHaveBeenCalledOnce();
  // This fails in jsdom:
  expect(el.getAttribute('aria-expanded')).toBe('true');
});

// Do: test event dispatch only — attribute mutation is the executor's
// internal concern, verified by the executor's own unit tests or
// browser-based tests (Playwright)
it('expand dispatches click', async () => {
  expand({ role: 'group', name: 'Details' });
  expect(handler).toHaveBeenCalledOnce();
});
```

For end-to-end attribute verification, use Playwright (real browser) instead of jsdom.

### Why this is non-obvious
The setAttribute call doesn't throw. The element reference is correct (proven by the click handler firing). The test reads as logically sound — set an attribute, then read it back. The failure is silent and specific to ARIA attributes on non-form elements in jsdom.
