### Symptom

After calling `doc.setIn(['newKey'], [{ uuid: 'test' }])` to add a new
top-level key to a YAML Document, `doc.getIn(['newKey'])` returns a value
that `isSeq()` does not recognise. Code that reads back with
`const seq = doc.getIn(['newKey']); if (!isSeq(seq)) return [];` silently
returns empty — the data was written but can't be read back through the
standard seq/map check pattern.

### Context

When building a typed facade over `parseDocument()` from the `yaml` library
for a visual YAML editor. The pattern is: write with `setIn`, read back
with `getIn` + `isSeq`/`isMap` type guards.

### What was tried (didn't work)

Using `doc.setIn(['newKey'], [entry])` where `entry` is a plain JS object.
The documentation says `setIn` accepts "any value" and converts internally.
This works for modifying existing keys but fails when creating new top-level
keys — the internal conversion doesn't produce a YAMLSeq that `isSeq()`
recognises.

### Root cause

`Document.setIn()` with a plain JS array at a new path creates an internal
representation that doesn't pass the `isSeq()` type guard from the yaml
library's `identity` module. The array is stored but not wrapped as a
proper `YAMLSeq` node.

### Fix

Always use `doc.createNode()` to wrap plain JS values before passing to
`setIn()` when creating new keys:

```typescript
// Wrong — isSeq() will fail on read-back
doc.setIn(['datasets'], [{ uuid: 'test' }]);

// Right — creates a proper YAMLSeq
doc.setIn(['datasets'], doc.createNode([{ uuid: 'test' }]));
```

For appending to an existing sequence, use `seq.add(doc.createNode(entry))`
directly on the YAMLSeq node rather than `doc.addIn()`:

```typescript
const seq = doc.getIn(['datasets']);
if (isSeq(seq)) {
  (seq as YAMLSeq).add(doc.createNode(entry));
}
```

### Why this is non-obvious

The `setIn` documentation says it accepts "any value" and the method works
correctly when modifying existing keys — only creating new top-level keys
exposes the bug. There's no error, no warning — the write succeeds and the
data is present in `toString()`, but the type guard pattern silently drops
it on read-back.
