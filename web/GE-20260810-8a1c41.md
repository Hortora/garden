## npm `file:` protocol installs devDependencies of linked packages — cascading 404s for private-registry deps

### Symptom
`npm install` fails with 404 errors for packages you never declared as dependencies — e.g. `@private-scope/tsconfig@0.0.0` from the public npm registry.

### Context
When `package.json` has `"@private/pkg": "file:.local-packages/pkg"` as a dependency, npm copies the package AND resolves all of its dependencies — including devDependencies. If the linked package has private-registry devDependencies (e.g. `@private/tsconfig: workspace:*`), npm tries to resolve them from the public registry and fails with 404.

### What was tried (didn't work)
- `npm install --force` — still fails on 404
- `npm install --install-links=false` — still resolves devDeps
- `link:` protocol — `EUNSUPPORTEDPROTOCOL` error on npm 11.17.0

### Root cause
npm's `file:` protocol treats linked packages as if they were being fully installed — it resolves their complete dependency tree including devDependencies. The `--force` flag doesn't override 404 resolution failures.

### Fix
Move private-registry packages to `optionalDependencies` instead of `dependencies`:

```json
{
  "dependencies": {
    "lit": "^3.3.3"
  },
  "optionalDependencies": {
    "@private/pkg": "file:.local-packages/pkg"
  }
}
```

npm treats 404 failures for optional dependencies as non-fatal warnings. The packages still install when present, and build tools (vite, esbuild) resolve imports through their own alias systems regardless of npm resolution status.

### Why this is non-obvious
The `file:` protocol looks like a simple local reference — you'd expect it to just symlink or copy, not recursively resolve the package's own dependency tree including devDependencies. The `--force` flag's name suggests it should override failures, but it doesn't help with 404 resolution errors.
