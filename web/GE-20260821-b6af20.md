## Async initial-state fetch races with synchronous push wire events

### Symptom
A component shows stale or corrupted state despite receiving correct real-time push wire events. The initial REST fetch completes and overwrites data that was already updated by a push wire event, causing the UI to regress to an older state. No error — the component appears to work, then briefly shows correct data, then snaps back to the stale fetch result.

### Context
Common in components that combine REST for initial state loading with WebSocket/push wire for real-time updates. The pattern:
1. `connectedCallback` → `listen(['topic'])` + `fetch('/api/state')`
2. Push wire event fires → updates component state
3. REST fetch resolves → overwrites component state with older data

The race window is small (typically <100ms) but reliable when the server broadcasts state changes during the same period the client is fetching.

### Root cause
The REST fetch is a Promise that resolves asynchronously. Push wire events fire synchronously via DOM event dispatch. When both happen during component initialization, the push event updates state first (correct, newer data), then the fetch resolves and blindly assigns its (older) response to the same state property.

### Fix
Guard the state assignment in the REST fetch callback. Two approaches:

**Approach 1 — Skip if already populated (simplest):**
```typescript
private async _fetchInitialState(): Promise<void> {
  const resp = await fetch(`${this.restBase}/api/state`);
  if (resp.ok) {
    const data = await resp.json();
    // Only apply if no push event has updated state yet
    if (!this._state.scenario) {
      this._state = data;
    }
  }
}
```

**Approach 2 — Validate response shape (defensive):**
```typescript
if (resp.ok) {
  const data: unknown = await resp.json();
  // Guard against non-object responses (e.g. outline array hitting state)
  if (typeof data === 'object' && data !== null && !Array.isArray(data)) {
    this._state = data as State;
  }
}
```

Both approaches make the push wire event authoritative — the REST fetch is a fallback for when no push event arrives during initialization.

### Why this is non-obvious
Both the REST response and push wire event contain valid data. The component renders correctly either way — the bug only manifests as a brief visual regression that's easy to miss during development. In tests, the race is deterministic (mocked fetch resolves on the next microtask) but the symptom (state regression) looks like a rendering bug, not a timing issue. The developer investigates the push wire handler or Lit's reactive update cycle rather than the fetch callback ordering.

### Alternatives considered
- Making the fetch `await` complete before registering the push listener — prevents the race but creates a gap where push events are missed
- Using a monotonic version counter — more robust but over-engineered for most cases
- Debouncing state updates — masks the race but adds latency to legitimate updates
