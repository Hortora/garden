### Symptom

`accordion-strategy.ts` `detachEntry` silently failed to remove the accordion section element from the DOM. Tests passed because the DOM cleanup was skipped without error.

### Context

During a large refactor (engine-to-Container migration), a `detachEntry` method was added to the accordion strategy. The method used `hostElement?.querySelector(...)` to find and remove the section element. The variable `hostElement` was never declared in this scope — the correct variable was `containerEl`.

### What was tried (didn't work)

The bug was not caught by:
- Unit tests — the `?.` operator returned `undefined`, so `undefined?.remove()` was also a no-op. No error thrown.
- Code review — `hostElement` looked like a plausible variable name.

### Root cause

JavaScript's optional chaining operator (`?.`) is designed to short-circuit when the left-hand side is `null` or `undefined`. When `hostElement` is an undeclared variable accessed via `?.`, TypeScript's type system flags it as an error (`Cannot find name`), but only under strict type checking. In a less strict configuration or when suppressed by `as any`, this becomes a silent no-op at runtime.

### Fix

Use the correct variable name. More broadly: when using optional chaining on a variable, verify the variable is **declared in scope**, not just that null safety is handled. The `?.` operator protects against null/undefined values but silently masks undeclared variables.

```typescript
// Bug — hostElement is not declared in this scope
hostElement?.querySelector(`[data-accordion-section="${key}"]`)?.remove();

// Fix — containerEl is the correct closure variable
containerEl?.querySelector(`[data-accordion-section="${key}"]`)?.remove();
```

### Why this is non-obvious

Optional chaining creates a false sense of safety. A developer reading `hostElement?.querySelector(...)` assumes the `?.` handles the case where `hostElement` might be null — which is correct defensive coding. The actual bug is that `hostElement` doesn't exist at all, and the `?.` makes this indistinguishable from the intended null-guard case. Only `tsc --strict` catches this, and only if the file is being type-checked.

### Alternatives considered

- ESLint `no-undef` rule — doesn't apply to TypeScript files (deferred to tsc)
- Removing optional chaining — would cause runtime crashes for legitimate null cases
