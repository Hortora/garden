### Symptom

Custom key bindings registered via `keymap.of([{ key: 'Enter', run: handler }])` are silently ignored. The default handler runs instead. No error, no warning in the console. The binding function exists and is callable — it just never fires.

### Context

In a Yarn workspace monorepo, package A (`pages-code-editor`) creates CodeMirror extensions importing `keymap` from `@codemirror/view`. Package B (`pages-builder`) also imports from `@codemirror/view`. If Yarn resolves these to different physical copies (even the same version), the `keymap.of()` call in package A produces an extension object whose prototype chain doesn't match what package B's `Configuration.resolve()` expects.

### What was tried (didn't work)

- Placing the custom keymap before `defaultKeymap` in the extensions array — correct ordering, but still ignored
- Using a separate `keymap.of()` call vs spreading bindings into the same `keymap.of()` — no difference
- Clearing Vite cache and restarting dev server — no effect (the duplicate is in node_modules resolution, not Vite cache)

### Root cause

CodeMirror's `Configuration.resolve()` (in `@codemirror/state`) uses `instanceof` checks to identify extension types. When two copies of `@codemirror/state` are loaded (even the same version from different paths), `instanceof` fails across the boundary. The extension is classified as "unrecognized" and silently dropped.

The error message `"Unrecognized extension value in extension set ([object Object]). This sometimes happens because multiple instances of @codemirror/state are loaded, breaking instanceof checks."` only appears when `Configuration.resolve` encounters the mismatch — but in many cases the extension is nested deep enough that the error surfaces as a generic unhandled rejection, not near the code that created the extension.

### Fix

Create the extension using the SAME `@codemirror/view` import that the consuming editor uses. In a monorepo, this means building the extension inline in the consuming package rather than importing a pre-built extension from another package:

```typescript
// WRONG: importing extension from another package (may use different @codemirror/state)
import { createSchemaCompletion } from '@other/package';

// RIGHT: build the extension in the consuming package using its own imports
import { autocompletion } from '@codemirror/autocomplete';
import { keymap } from '@codemirror/view';
const ext = autocompletion({ override: [mySource] });
const keys = keymap.of([{ key: 'Enter', run: myHandler }]);
```

Alternatively, ensure all packages resolve to the exact same physical copy via Yarn `resolutions` or `nohoist` configuration.

### Why this is non-obvious

The failure is completely silent in most cases — no console error, no exception. The editor works fine, it just ignores the custom bindings. A developer would naturally suspect ordering, precedence, or the binding configuration — not a module resolution issue. The `instanceof` failure is an implementation detail of CodeMirror's extension system that isn't documented as a monorepo concern.

### Alternatives considered

- Using `Prec.highest()` to force precedence — doesn't help because the extension is unrecognized, not low-priority
- Re-exporting `keymap` from the editor package — adds coupling and is fragile across version bumps
