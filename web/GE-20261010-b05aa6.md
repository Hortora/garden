### Symptom
Line-highlight code that checks for ProseMirror `hardbreak` nodes to detect visual line breaks produces incorrect results — highlights stop short or split visual lines that are actually continuous.

### Context
When building visual line detection for a Milkdown-based markdown editor, `doc.nodesBetween()` finds `hardbreak` nodes at positions where the markdown source had newlines within a paragraph. The natural assumption is that these correspond to `<br>` elements causing visual line breaks.

### What was tried (didn't work)
Added explicit hardbreak detection to the `coordsAtPos` walk — when a hardbreak node was encountered, the walk stopped, treating it as a line boundary. This caused highlights to end mid-line (e.g., highlighting "items are complete" but not "and integration testing" on the same visual line).

### Root cause
Milkdown renders hardbreak nodes as `<span data-type="hardbreak" contenteditable="false"> </span>` — an inline span containing a space. NOT as `<br>`. The text flows continuously with no visual line break. `coordsAtPos` correctly reports the same Y coordinate before and after the hardbreak because there IS no visual break.

`doc.textBetween()` inserts `\n` at hardbreak positions, making the text LOOK like it has line breaks, but this is a document-model artifact, not a rendering reality.

### Fix
Do not check for hardbreak nodes when detecting visual line boundaries. Use `coordsAtPos` Y-coordinate comparison only — it accurately reflects the actual rendered layout regardless of document-model node types.

```typescript
// WRONG — hardbreaks don't cause visual breaks in Milkdown
if (r.nodeAfter?.type.name === 'hardbreak') break;

// RIGHT — just check coordinates
const c = this.view.coordsAtPos(p);
if (Math.abs(c.top - selCoords.top) > threshold) break;
```

### Why this is non-obvious
The ProseMirror documentation describes hardbreak as "a hard line break" and its default spec maps to `<br>`. Milkdown overrides this with a custom node view that renders as an inline span. The `\n` in `textBetween` output reinforces the false belief that a visual break exists.
