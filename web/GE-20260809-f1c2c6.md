## Lit updated() with @state() triggers double render — D3 setup must wait for second cycle

### Symptom
Setting `graphData` on a Lit component triggers `updated()`, which sets `this._model` (a `@state()` property). Code in the same `updated()` call tries to find the SVG element that `_model` controls via conditional rendering — but the SVG doesn't exist yet. `this.shadowRoot.querySelector('svg')` returns `null`.

### Context
A component renders an SVG only when `_model` is set: `${this._model ? html\`<svg>...\` : html\`<div>No data</div>\`}`. The `updated()` callback sets `_model` from the incoming `graphData` property, then tries to run D3 setup on the SVG.

### What was tried (didn't work)
- `this.updateComplete.then(() => ...)` inside `updated()` — resolves for the current cycle before the `@state()` change takes effect
- `this.requestUpdate()` + `this.updateComplete.then(...)` — same problem, and Lit warns about scheduling updates during updates

### Root cause
Setting a `@state()` property inside `updated()` schedules a second render cycle. The current `updated()` invocation runs during the first cycle, before the DOM from the second cycle exists. `updateComplete` resolves for the current cycle, not the pending one.

### Fix
Separate the data update from the DOM-dependent setup. In `updated()`:
1. Set `_model` (triggers second render)
2. Check if the DOM element exists (`this.shadowRoot?.querySelector('svg')`)
3. Only run D3 setup when the element is present — which happens on the second `updated()` call

```typescript
override updated(changed: Map<PropertyKey, unknown>): void {
  if (changed.has('graphData') && this.graphData) {
    this._model = this.graphData;  // triggers re-render
  }
  // Runs on SECOND updated() when SVG is in DOM
  if (this._model && !this._sim) {
    const svg = this.shadowRoot?.querySelector('svg');
    if (svg) this._buildGraph();
  }
}
```

In tests, await two update cycles: `await el.updateComplete; await el.updateComplete;`

### Why this is non-obvious
The Lit documentation shows `updated()` as the place to do post-render work. But it doesn't make clear that setting `@state()` inside `updated()` creates a second cycle that the current `updated()` invocation can't see. The fix (checking for DOM presence and relying on the second call) feels like a workaround but is actually the correct Lit pattern for this situation.
