# Zod v4 internal ._zod.def field names differ from v3 ._def — undocumented mapping required

### Symptom

Code accessing Zod internals for schema introspection breaks silently after
v3→v4 migration. Fields return `undefined` instead of expected values. A naive
`._def` → `._zod.def` text replacement compiles but produces wrong results at
runtime.

### Context

Library code that introspects Zod schemas — LSP completion engines,
schema-to-JSON-Schema converters, hover providers — accesses `._def.typeName`,
`._def.shape`, `._def.type`, `._def.values`, etc. The v4 migration guide says
`._def` moved to `._zod.def` but states "the structure of all internal defs is
subject to change" without enumerating what changed.

### Root cause

v4 moved internals from `._def` to `._zod.def` AND renamed several fields.
Additionally, two schema types lost their distinct type discriminators and now
share type tags with other schemas.

### Fix

Complete field mapping (verified against Zod 4.6.5 source):

**Renamed fields:**

| v3 | v4 | Notes |
|---|---|---|
| `._def.typeName` = `"ZodString"` | `._zod.def.type` = `"string"` | Field renamed + values are lowercase without `Zod` prefix |
| `._def.type` (ZodArray element) | `._zod.def.element` | Renamed to avoid collision with type discriminator |
| `._def.values` (ZodEnum) | `._zod.def.entries` | Renamed |
| `._def.value` (ZodLiteral, singular) | `._zod.def.values` (array) | Renamed + now array of values |
| `._def.values` (ZodNativeEnum) | `._zod.def.entries` | Renamed |
| `._def.optionsMap` (ZodDiscriminatedUnion) | Removed | Iterate `._zod.def.options` instead |

**Unchanged fields** (same name under `._zod.def`):

`shape`, `innerType`, `getter`, `options`, `left`, `right`, `valueType`, `checks`

**Merged type discriminators:**

| v3 | v4 `._zod.def.type` | How to distinguish |
|---|---|---|
| `"ZodDiscriminatedUnion"` | `"union"` | Check `._zod.def.discriminator` field presence |
| `"ZodNativeEnum"` | `"enum"` | Check if `._zod.def.entries` is an array (ZodEnum) or object (ZodNativeEnum) |

### Why this is non-obvious

The migration guide explicitly says the internal structure "won't be
comprehensively documented." The field mapping can only be derived from reading
the v4 source code (`packages/zod/src/v4/classic/schemas.ts`). A pure
`._def` → `._zod.def` text replacement silently produces wrong results because
5 fields were renamed and 2 type discriminators were merged.

### Alternatives considered

- Use v4 public APIs (`.toJSONSchema()`, `z.registry`, `.meta()`) instead of internals — these serve different purposes (serialization, registration, annotation) and cannot replace structural schema traversal needed for LSP completion engines
- Use a compatibility shim that maps both v3 and v4 internals — adds complexity for a one-time migration; not worth maintaining
