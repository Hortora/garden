### The problem

You need both a graph (nodes and edges for rendering) and a path map (YAML positions for property editing). The SDK produces accurate graphs but doesn't expose YAML positions. The YAML library gives you CST positions but doesn't understand the domain's graph structure.

### The technique

Walk the same YAML twice — once via the SDK for graph construction, once via the YAML library's CST for path tracking. Both walks must agree on node identity.

```
SWF YAML string
  ├─→ SDK: parse → buildFlatGraph() → GraphModel (nodes, edges, types)
  └─→ YAML: parseDocument() → walk CST → yamlPaths Map<nodeId, path[]>
```

The SDK walk produces the graph; the YAML walk produces edit targets. Both use the same ID scheme (path-based for SWF), so they can be correlated after completion.

### The integrity assertion

After both walks, assert they agree:

```typescript
const taskNodes = sdkNodes.filter(n => !SYNTHETIC_TYPES.has(n.type));

let degraded: { reason: string } | undefined;
if (yamlPaths.size !== taskNodes.length) {
  degraded = { reason: `yamlPaths/model mismatch: ${yamlPaths.size} paths for ${taskNodes.length} task nodes` };
} else {
  for (const node of taskNodes) {
    if (!yamlPaths.has(node.id)) {
      degraded = { reason: `No YAML path for task node '${node.id}'` };
      break;
    }
  }
}

return { model, yamlPaths, degraded };
```

### Degraded mode — not an error

When the assertion fails, the adapter returns a valid graph with a `degraded` flag — not an exception. The graph renders normally (layout and stencils don't need YAML paths). Only property editing is disabled, with a warning banner explaining why.

This matters because:
- SDK upgrades may change ID generation — the mismatch surfaces immediately on first render
- The user sees their workflow visualised even when editing is unavailable
- Silent YAML corruption (editing with wrong paths) is prevented without losing the entire feature

### When to use this

Any time you're building a domain adapter that:
1. Uses a third-party SDK for graph/model construction
2. Needs CST-preserving edits (format, comments, whitespace retained)
3. Can't trust the SDK to maintain a stable internal path format across versions

The dual walk decouples rendering quality (SDK's job) from edit safety (your job), with the integrity assertion as the canary.

### Why this is non-obvious

The natural approach is either (a) use only the SDK and derive paths from its output, coupling to SDK internals, or (b) build the entire graph yourself from the YAML CST, duplicating the SDK's graph construction logic. The dual walk avoids both: the SDK handles what it's good at (graph construction), the YAML library handles what it's good at (CST access), and the integrity assertion catches divergence before it causes harm.

### Alternatives considered

- **SDK-only with path derivation** — couples to SDK internal ID format; breaks silently on SDK upgrades without the integrity assertion catching it
- **Full custom graph construction** — duplicates the SDK's graph logic (hundreds of lines for SWF); the SDK handles edge cases (fork branches, nested containers) that are easy to get wrong
- **Throw on mismatch** — prevents rendering entirely when paths diverge; too aggressive for what may be a minor SDK update that doesn't affect the graph structure
