### Symptom
Consumer apps with static HTML pages (login, register, landing pages) cannot use Lit web components from a shared library without setting up a build pipeline. The library ships tree-shakeable ESM exports that require esbuild/webpack to bundle — static HTML has no bundler.

### Context
A web component library (`@casehubio/pages-ui-components`) provides `<pages-button>`, `<pages-input>`, `<pages-select>`, etc. as Lit 3 components with `--pages-*` design token styling. Bundled apps import via ESM (`import '@casehubio/pages-ui-components'`) and esbuild handles registration. But static HTML pages (auth flows, landing pages) served by Quarkus need the same components without a build step.

### What was tried (didn't work)
- Inline `<script>` imports of the ESM source — fails because Lit and decorator dependencies aren't resolved
- Separate entry points per consumer app — works but duplicates the problem across every repo

### Root cause
Tree-shakeable ESM exports are designed for bundlers. The `customElements.define()` calls and Lit dependency resolution only work inside a module graph that a bundler traverses. Static HTML has no module graph.

### Fix
Ship two consumption paths from the same package:

**1. Pre-generated CSS theme files** — The design token library (`pages-ui-tokens`) generates theme CSS at runtime via JavaScript. Add a build step that writes the generated CSS to static files:
```
dist/themes/casehub-dark.css
dist/themes/casehub-light.css
```
Content is exactly what `generateCSS(tokens, name)` already produces — persisted to a file instead of only living in JS memory.

**2. Pre-bundled self-registering ESM** — The component library adds a build step that outputs a single bundled JS file with Lit included:
```
dist/bundle.js  (or components.js)
```
One esbuild call with `bundle: true, format: 'esm'` on the package index.

These files land in `dist/` and are included in the Maven SNAPSHOT artifact via the existing `pack-all.sh` script. Every Quarkus consumer gets them automatically at known paths.

**Static HTML consumption:**
```html
<link rel="stylesheet" href="/pages/tokens/casehub-dark.css">
<script type="module" src="/pages/ui/components.js"></script>

<pages-input label="Username" placeholder="Your name"></pages-input>
<pages-button label="Sign in" variant="primary"></pages-button>
```

**Bundled app consumption (unchanged):**
```typescript
import '@casehubio/pages-ui-components';
import { applyTheme } from '@casehubio/pages-ui-tokens';
```

Same components, same tokens, two consumption paths. The `sideEffects` field in `package.json` ensures esbuild doesn't tree-shake `customElements.define()` calls for bundled consumers.

### Why this is non-obvious
Most Lit component library guides only document the ESM path. The assumption is that consumers always have a bundler. In a multi-repo platform where some pages are server-rendered static HTML (auth flows, error pages) and others are bundled SPAs, this creates a gap. The technique of shipping both paths from a single package build — and using the Maven SNAPSHOT WebJar pattern to deliver the static assets — bridges the gap without requiring each consumer to maintain its own build configuration for static pages.
