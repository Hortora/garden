### Symptom

A `package.json` with both `dependencies` (using `"*"` version) and `resolutions` (using `portal:` links to local directories) works with Yarn but fails silently with npm. npm resolves the `"*"` versions from the npm registry instead of following the `resolutions` redirects — if the packages aren't on npmjs.org, `npm install` 404s.

### Context

Cross-repo frontend dependency management where packages are extracted from a Maven WebJar to a local `.casehub-packages/` directory. Yarn's `resolutions` with `portal:` links redirect resolution to these local paths. The project's CI switched from Yarn to npm (via Quinoa's built-in npm) without updating the dependency resolution mechanism.

### What's undocumented

npm's documentation doesn't explicitly state that it ignores the `resolutions` field. The field is silently skipped — no warning, no error, no deprecation notice. npm has `overrides` as its equivalent feature, but `overrides` uses different semantics:

1. `overrides` doesn't support the `portal:` protocol
2. `overrides` with `file:` paths triggers full transitive dependency resolution (npm tries to install the package's own dependencies from the registry)
3. Yarn `portal:` creates symlinks without resolving transitive deps; npm `file:` copies and resolves

There is no npm equivalent of Yarn's `portal:` + `resolutions` combination that creates local symlinks without triggering transitive resolution.

### Why this is non-obvious

The `resolutions` field sits in `package.json` alongside `dependencies` and `devDependencies` — it looks like a standard npm feature. Many developers assume package.json fields are universal across package managers. The silent ignore (no warning) means the misconfiguration is only discoverable when resolution fails for a different reason (404 on registry, wrong version installed).
