### Symptom

Custom elements exist in source, `sideEffects` is correctly declared in the package's `package.json`, but `customElements.get('pages-input')` returns `undefined` at runtime. Elements created via `document.createElement()` have no shadow DOM — they're in the DOM as empty tags with zero height.

No console errors. No webpack warnings. The build succeeds silently.

### Context

A monorepo where webpack aliases map package sub-paths to absolute filesystem paths:

```javascript
// webpack.config.js
resolve: {
  alias: {
    "@casehubio/pages-ui-components/input": path.resolve(__dirname, "../packages/pages-ui-components/dist/input"),
  }
}
```

The package correctly declares its side-effectful files:

```json
// pages-ui-components/package.json
{
  "sideEffects": [
    "./dist/input/index.js",
    "./dist/select/index.js"
  ]
}
```

Side-effect imports in the entry point or other modules:

```typescript
import "@casehubio/pages-ui-components/input";  // registers pages-input
```

### What was tried (didn't work)

1. Verified `sideEffects` field was correctly declared — it was
2. Checked that dist files existed and contained `customElements.define()` — they did
3. Added explicit side-effect imports in the webpack entry point — still tree-shaken
4. Pointed aliases to source `.ts` files instead of dist — failed due to `rootDir` constraints

### Root cause

When webpack resolves an import through a `resolve.alias`, it maps directly to the absolute filesystem path. It does NOT traverse up the directory tree to find a `package.json` with a `sideEffects` field. Without finding `sideEffects`, webpack's production-mode tree shaking treats the module as side-effect-free and eliminates bare imports (`import "..."`) that don't export used values.

This is distinct from `import type` erasure (GE-20260629-ebdb0a) — there, TypeScript removes the import before webpack sees it. Here, webpack sees the import but decides it's safe to remove because the `sideEffects` declaration is invisible through the alias.

### Fix

Add a webpack module rule that explicitly marks the alias-resolved paths as side-effectful:

```javascript
module: {
  rules: [
    {
      test: /pages-ui-components[\\/]dist[\\/]/,
      sideEffects: true,
    },
  ],
}
```

This tells webpack to preserve all imports from matching paths regardless of what it can (or can't) find in package.json.

### Why this is non-obvious

The `sideEffects` field is correctly declared. The webpack documentation describes `sideEffects` as the mechanism for controlling tree shaking. There is no documentation stating that aliases bypass this lookup. The symptom — elements in the DOM with no shadow roots, no errors — gives no indication that tree shaking is the cause. The debugging path naturally leads to checking element registration, import order, and bundle contents before suspecting the alias/sideEffects interaction.

### Alternatives considered

- Pointing aliases to source `.ts` files: fails with `rootDir` constraint errors when the alias crosses workspace package boundaries
- Removing aliases entirely and relying on node_modules resolution: works but loses the monorepo development workflow (edits require rebuild before they're visible)
