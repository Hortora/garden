## Symptom

A ts-morph code generator walking TypeScript types to emit Zod schemas produces `z.unknown()` or `z.array(z.unknown())` for a type that has many declared properties. The type name resolves correctly and `getProperties()` returns the right count — but the generated output is wrong.

## Context

TypeScript types generated from JSON Schema (e.g. via `json-schema-to-typescript`) use an intersection pattern:

```typescript
export type Binding = {
  name?: string;
  on: Trigger;
  capability?: string;
  // ... many declared properties
  [k: string]: unknown | undefined;
} & Binding1;

export type Binding1 = {
  [k: string]: unknown | undefined;
};
```

The `& Binding1` is an artifact of JSON Schema's `allOf` — it adds a second index signature member. The intersection of `{ declared props + index sig }` and `{ index sig only }` creates a type that ts-morph categorizes differently than a plain object.

## What was tried (didn't work)

- Checking `type.isObject()` — returns false for intersection types, so the object branch in the generator is never reached
- Increasing the depth limit — the type isn't hitting the depth limit, it's falling through to the `z.unknown()` default
- Checking `type.getText()` — shows the full intersection text, but pattern matching on text is fragile

## Root cause

`type.isIntersection()` returns true for these types, not `type.isObject()`. The generator's type walk checks `isUnion()` then `isObject()` — intersection types fall through both and hit the default `z.unknown()` return.

The fix requires an explicit `isIntersection()` branch that:
1. Calls `type.getProperties()` to get the flattened property set
2. Filters out index signatures and `__@` internal symbols
3. Generates `z.object({...})` from the remaining properties

## Fix

Add an intersection handler before the object handler in the type walker:

```typescript
if (type.isIntersection()) {
  const intersectionTypes = type.getIntersectionTypes();
  const objectTypes = intersectionTypes.filter(t => t.isObject());
  if (objectTypes.length > 0) {
    const allProps = new Map<string, MorphSymbol>();
    for (const prop of type.getProperties()) {
      allProps.set(prop.getName(), prop);
    }
    const nonIndexProps = [...allProps.values()].filter(
      p => !isIndexSignature(p) && !p.getName().startsWith('__@'),
    );
    if (nonIndexProps.length === 0) return 'z.object({})';
    const fields = nonIndexProps
      .map(p => propToZodField(p, depth + 1, visited))
      .filter(Boolean);
    // ... emit z.object({...})
  }
}
```

The key insight: `type.getProperties()` on an intersection type returns the merged/flattened property set from all intersection members. You just need to reach it via the `isIntersection()` branch.

## Why this is non-obvious

The intersection is invisible in the source type declaration — `Binding` looks like a normal object type with properties. Only the `& Binding1` at the end (where `Binding1` is just `{ [k: string]: unknown }`) creates the intersection. Since `Binding1` adds no new declared properties, the developer expects ts-morph to see `Binding` as a plain object. The misdirection is that `type.getText()` shows the properties, `type.getSymbol()` resolves correctly, and `type.getProperties()` returns the right count — but the type categorization (`isObject() === false`) silently routes to the wrong code path.

### Alternatives considered

- Pattern matching on `type.getText()` for intersection syntax — fragile, breaks on complex types
- Using `type.getApparentType()` — doesn't unwrap intersections to objects
