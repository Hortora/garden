## Symptom

ts-morph `getType().getProperties()` returns an empty array for an interface
imported from a workspace package, even though the interface name and symbol
resolve correctly (`getText()` shows the right name, `getSymbol()` shows the
right symbol).

## Context

A ts-morph Project reads a registry file that imports types from sibling
workspace packages (`import type { FooProps } from '@scope/package'`). Each
package declares `"types": "dist/index.d.ts"` in package.json. The types
are correctly exported in the source `.ts` files but the `dist/` directory
contains an older build that predates the type declarations.

## What was tried (didn't work)

- Adding source files via `addSourceFilesAtPaths()` — files are added to
  the project but module resolution still follows `types` field to dist
- Rebuilding individual packages — fails due to transitive dependency
  resolution in a monorepo (packages depend on other packages that also
  need building)
- Running the full topological `yarn build` — works but is slow and
  unnecessary for a generator that only needs type information

## Root cause

TypeScript module resolution (used by ts-morph) resolves `@scope/package`
through `node_modules` → `package.json` → `types` field → `dist/index.d.ts`.
When `dist/` is stale, the `.d.ts` file has the old interface (or no interface
at all), so ts-morph sees the type name but 0 properties.

`addSourceFilesAtPaths()` adds files to the ts-morph Project but does not
override module resolution — imports still resolve through package.json.

## Fix

Use TypeScript `paths` in the ts-morph project's tsconfig to override
module resolution and point directly at source files:

```json
{
  "compilerOptions": {
    "paths": {
      "@scope/package-*": ["../../components/*/src/index.ts"],
      "@scope/core": ["../core/src/index.ts"]
    }
  }
}
```

The `*` wildcard in paths captures a segment and substitutes it in the
target, so `@scope/package-foo` → `components/foo/src/index.ts`.

**Important:** Use a separate `tsconfig.generator.json` for the code
generator — the paths break `tsc` builds because resolved source files
fall outside `rootDir`.

## Why this is non-obvious

The type name resolves correctly — `getText()` shows `SlaIndicatorProps`,
`getSymbol()` shows the right symbol. Only `getProperties()` returns
empty. This makes the problem look like a ts-morph bug rather than a
module resolution issue. The misdirection costs significant debugging
time because the obvious diagnostic ("is the type found?") says yes.
