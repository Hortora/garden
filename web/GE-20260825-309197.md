### Symptom

A 220-line drag-and-drop state machine (`dragState`, `crossFramePreview`, `edgeSplitPreview`, `handleCrossFrameDragMove`, `showEdgeSplitOverlay`) built inside a 1355-line god closure resists extraction. It reads/writes ~8 closure variables (`frames` map, callback arrays, `containerEl`, `getContainerElement`) and dispatches to ~4 closure functions (`splitFrame`, `handleEmptyLeaf`, cross-frame tab move, external callbacks).

### Context

TypeScript closure-based modules (factory functions returning object literals) are common for encapsulating mutable state. Multi-phase interactions (drag-and-drop, resize, selection, workspace transitions) naturally accumulate state variables and helper functions inside the closure. Without an interface boundary, the interaction logic becomes inseparable from the host module.

In this case, `group-organiser-backend.ts` grew to 1355 lines with DnD state, visual preview management, hit-testing, and structural operations all sharing closure scope. Tree traversal helpers (~130 lines) and frame rendering (~110 lines of duplicates) extracted cleanly because they had no mutable state dependencies. The DnD code could not extract because it read/wrote shared mutable state across multiple closure functions.

### What was tried (didn't work)

Attempted to design a `DndCoordinator` interface post-hoc. The coordinator would need:
- `DndContext`: readonly frame map access, container element lookup, container-to-DOM resolution
- `DndCallbacks`: `onCrossFrameDrop(fromFrame, tabKey, toFrame, insertIdx)`, `onEdgeSplit(fromFrame, tabKey, targetFrame, zone, targetLeaf)`, `onTabDragOut(fromFrame, tabKey, position)`, cleanup hooks

This mirrors the closure's shape rather than modelling the concern. The `onTabDragEnd` handler alone reads three state variables, dispatches to two structural operations, fires two external callback arrays, and handles three branches (cross-frame drop, edge split, cancellation).

### Root cause

Three concerns were mixed into one closure scope without interface boundaries:

1. **Visual state** — preview elements, overlay elements, drag ghost tracking
2. **Hit-testing** — iterating frames, measuring tab strip positions, detecting edge zones
3. **Structural operations** — `splitFrame`, `handleEmptyLeaf`, cross-frame entry transfer

Because all three read/wrote the same closure variables, they became inseparable.

### Fix

Design multi-phase interaction state machines as standalone coordinators from the start:

```typescript
// Coordinator owns visual state and hit-testing
interface DndCoordinator {
  startDrag(sourceFrame: string, tabKey: string, ghost: HTMLElement): void;
  moveDrag(x: number, y: number): void;
  endDrag(): DragEndResult;
  cancelDrag(): void;
}

// Result is a discriminated union — caller handles structural operations
type DragEndResult =
  | { type: 'cross-frame'; fromFrame: string; tabKey: string;
      targetFrame: string; insertIndex: number }
  | { type: 'edge-split'; fromFrame: string; tabKey: string;
      targetFrame: string; zone: EdgeZone; targetLeaf?: Container }
  | { type: 'drag-out'; fromFrame: string; tabKey: string;
      position: { x: number; y: number } }
  | { type: 'cancelled' };

// Context is a typed read-only interface — not the closure's internals
interface DndContext {
  readonly frames: ReadonlyMap<string, FrameState>;
  getContainerElement(state: FrameState, container: Container): HTMLElement | null;
}

function createDndCoordinator(ctx: DndContext): DndCoordinator {
  // All visual state lives here — dragState, previews, overlays
  // Hit-testing reads ctx.frames (read-only)
  // endDrag() returns a result — never calls structural operations directly
}
```

The coordinator owns visual state and hit-testing. The caller (backend) owns structural operations and dispatches based on the result type. The boundary is the `DragEndResult` discriminated union — it describes what happened without knowing what to do about it.

### Why this is non-obvious

The closure pattern feels natural during initial development — state variables are right there, accessible without ceremony. The coupling only becomes visible when you try to extract. By then, the interaction logic is woven through multiple functions that share mutable state, and the extraction cost exceeds the original implementation cost.

The non-obvious insight: **the interface boundary must exist before the state machine grows**, not after. The cost of designing a coordinator interface upfront is ~30 minutes. The cost of extracting a coupled state machine after the fact is hours — or it gets deferred indefinitely.

### Applicability

This pattern applies to any multi-phase interaction in closure-based TypeScript modules:
- **Drag-and-drop** — preview management, hit-testing, drop resolution
- **Resize** — handle tracking, constraint enforcement, commit
- **Selection** — lasso state, shift-click accumulation, selection resolution
- **Workspace transitions** — mode tracking, mount transfer, state preservation
