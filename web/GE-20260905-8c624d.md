### Symptom

`Error: Denied ID /path/to/blocks-ui/node_modules/@xyflow/react/dist/style.css?raw` when running vitest tests for any component that imports `@casehubio/graph-renderer`.

### Context

In a multi-slot development setup, projects are cloned into slot directories (e.g. `slots/175/blocks-ui`). Portal resolutions in `.casehub-packages/` point to pages packages. The vitest config resolves `@casehubio/graph-renderer` to `.casehub-packages/packages/graph-renderer/dist`. Inside that dist, there's a `?raw` CSS import from `@xyflow/react`.

### What was tried (didn't work)

Setting vitest aliases to resolve `@casehubio/graph-renderer` to `dist/` — the same pattern used by `casehub-diagram`'s working vitest config. Same error. Running the casehub-diagram tests in the same slot confirmed they also fail identically — this is a pre-existing environment issue, not specific to the new component.

### Root cause

Vite's `server.fs.allow` security restricts filesystem access. The `?raw` CSS import resolves to a `node_modules/` path outside the slot's project root. The dist/ alias resolves the JavaScript correctly but the CSS raw import inside the compiled JS still references the absolute path to `@xyflow/react/dist/style.css`, which crosses the slot boundary.

### Fix

None known — pre-existing environment limitation. Tests that don't transitively import `graph-renderer` (e.g. toolbar-only tests) work fine. Component-level DOM tests that import the full diagram component (which imports `graph-renderer` → `@xyflow/react` CSS) fail.

Workaround: structure tests to test subcomponents (toolbar, individual panels) that don't import the graph-renderer chain. Full component integration tests must run in the primary (non-slot) clone or via the Vite dev server showcase.

### Why this is non-obvious

The vitest alias config looks correct — it's identical to `casehub-diagram`'s working config in the primary clone. The error message says "Denied ID" which doesn't explain the cross-slot filesystem boundary cause. The same tests pass in the primary blocks-ui clone (non-slot) because the paths don't cross boundaries. The failure only surfaces in slot-based development, making it intermittent across developer setups.

### Alternatives considered

- Adding `server.fs.allow` paths in vitest config — would work but requires knowledge of the concrete slot path, which varies per developer
- Mocking the CSS import — fragile, breaks if the import path changes
- Using happy-dom instead of jsdom — same Vite security restriction applies
