### Symptom
Consumer package test fails with `(0, deregisterGrammar) is not a function` at runtime. The import statement compiles without error. TypeScript type checking passes.

### Context
Monorepo with `workspace:*` dependencies. Package A (`graph-core`) exports `deregisterGrammar` from source. Package B (`graph-renderer`) imports it. A's `dist/` was built before the export was added. Vitest resolves the import to A's `dist/index.js`, not the source.

### What was tried (didn't work)
- Checking the source — export clearly present in `index.ts` and `grammar.ts`
- Checking the import path — correct, matches barrel export
- Running `yarn why` — dependency correctly resolved

### Root cause
`workspace:*` resolves to the package's `main`/`types` fields in `package.json`, which point to `dist/`. TypeScript type checking uses `dist/index.d.ts` (which may also be stale, but in this case was rebuilt). Vitest runtime uses `dist/index.js`, which was stale — the function existed in source but not in the compiled output.

### Fix
Rebuild the dependency package before running consumer tests:
```bash
yarn workspace @casehubio/graph-core run build
yarn workspace @casehubio/graph-renderer run test
```

For CI: ensure `build:packages` runs all packages in dependency order before `yarn test`.

### Why this is non-obvious
The import compiles. TypeScript doesn't error. The function name appears in autocomplete. Only at runtime does the resolution fail — because the JS dist is stale while the `.d.ts` may or may not be. The error message `(0, foo) is not a function` gives no hint that a stale build is the cause.

### Alternatives considered
- TypeScript project references with `--build` mode — handles incremental rebuilds but requires `composite: true` in every tsconfig, which not all monorepos use
- Vitest `deps.inline` — can force source resolution but breaks for packages with build-time transforms
