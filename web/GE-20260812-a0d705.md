### Symptom
Build or test fails with `Failed to resolve import "some-package" from "../../sibling/src/module.ts"` even though you never import from that module. The import error references a package you don't use and a module you don't import directly.

### Context
Project A imports `{ createFoo }` from `@scope/library`. The library's `index.ts` barrel also re-exports `{ createBar }` from `./bar-module.js`. `bar-module.ts` imports `some-package` which is not installed in Project A. Project A never uses `createBar`.

### Root cause
Vite's import-analysis plugin resolves ALL imports in ALL re-exported modules when processing a barrel file — even modules whose exports are not used by the consumer. Tree-shaking happens later (at bundle time), but import analysis runs first and fails on the unresolvable import.

Dynamic imports (`await import("some-package")`) are also caught by the analysis, despite being lazy.

### Fix
Import directly from the specific module file instead of the barrel:

```typescript
// Instead of:
import { createFoo } from '@scope/library';

// Use:
import { createFoo } from '@scope/library/foo-module.js';
```

This bypasses the barrel entirely. Vite only analyzes the imported module and its actual dependencies.

### Why this is non-obvious
The developer imports only `createFoo` and never touches `createBar` or its dependency. The error message references a module and package they've never heard of. The connection between "barrel re-exports an unused sibling module" and "your build fails on that sibling's transitive dependency" requires understanding Vite's import analysis ordering.
