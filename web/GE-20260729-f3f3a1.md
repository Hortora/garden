### Symptom
`NotSupportedError: This name has already been registered in the registry` at
module load time. No tests run. The error names no element — just the registry
violation.

### Context
A consuming app (chat-app) imports `@casehubio/blocks-ui-core` (which registers
`commitment-state-pill` via its barrel) and also imports
`@casehubio/blocks-ui-commitment-viz` (which re-exports the same component with
`@customElement('commitment-state-pill')`). TypeScript compiles with no errors
because both exports resolve to the same type. The failure is runtime-only — the
second `customElements.define()` call throws.

### Root cause
After blocks-ui#101 promoted `CommitmentStatePill` into `blocks-ui-core`, two
packages register the same custom element name. ES module deduplication does NOT
prevent this because the two `@customElement` decorators are in different physical
files (different module IDs). Vite's `resolve.dedupe` for `lit` ensures a single
Lit instance but cannot prevent two different modules from calling
`customElements.define()` with the same name.

### Fix
Import `CommitmentStatePill` from `@casehubio/blocks-ui-core` only (it's
registered as a side effect of the barrel import). Import
`@casehubio/blocks-ui-commitment-viz` only for components NOT promoted to core:
`CommitmentRangeBar`, `decorateCommitmentRanges`, `RangeDecoration`.

Use deep imports to avoid the commitment-viz barrel (which re-exports the pill):
```typescript
// Pill — from core (already registered via barrel)
import '@casehubio/blocks-ui-core';

// Range bar and decorator — from commitment-viz (deep imports, no barrel)
import '@casehubio/blocks-ui-commitment-viz/src/commitment-range-bar.js';
import { decorateCommitmentRanges } from '@casehubio/blocks-ui-commitment-viz/src/range-decorator.js';
```

### Why this is non-obvious
The barrel import compiles cleanly — TypeScript sees the same type from both
packages. The `@customElement` decorator runs at module load time with no
try/catch, so the failure is immediate and total (no tests execute). The error
message doesn't name the conflicting element, making diagnosis harder.

### Alternatives considered
- `resolve.dedupe: ['lit']` in vite config — prevents duplicate Lit instances
  but does not prevent two different modules from calling `customElements.define()`
- Wrapping `@customElement` in `if (!customElements.get('name'))` — requires
  modifying the component source (blocks-ui), not the consumer
