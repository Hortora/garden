# Zod v4 .default().optional() fires default for missing fields instead of returning undefined

### Symptom

Field alias resolution via `??` silently picks the default value instead of the
alias value. Tests pass in v3, fail in v4 with wrong values — no error, just
incorrect data.

### Context

When migrating from Zod v3 to v4. Schemas use `.default("X").optional()` with
a `??` fallback chain to resolve field aliases:

```typescript
const sortOrderSchema = z.enum(["ASCENDING", "DESCENDING"]).default("ASCENDING");

const sortColumnSchema = z.object({
  order: sortOrderSchema.optional(),
  sortOrder: sortOrderSchema.optional(),     // alias for order
}).transform((col) => ({
  column: col.column,
  order: col.order ?? col.sortOrder ?? "ASCENDING",
}));

// Input: { sortOrder: "DESCENDING" }
// v3 result: order = "DESCENDING" (correct)
// v4 result: order = "ASCENDING" (wrong — default fires for missing `order`)
```

### Root cause

In v3, `.optional()` wrapping `.default()` short-circuits — undefined input
returns `undefined`, and `??` falls through to the alias field.

In v4, `.default()` fires first — undefined input returns the default value
(`"ASCENDING"`), so `col.order` is `"ASCENDING"` (not `undefined`), and `??`
never reaches `col.sortOrder`.

### Fix

Remove `.default()` from schemas used in alias patterns. Apply defaults in the
`.transform()` step via `??` instead:

```typescript
// Before (v3 — worked, v4 — silently wrong)
const sortOrderSchema = z.enum(["ASCENDING", "DESCENDING"]).default("ASCENDING");

// After (works in both v3 and v4)
const sortOrderSchema = z.enum(["ASCENDING", "DESCENDING"]);
// The transform already has the fallback:
// order: col.order ?? col.sortOrder ?? "ASCENDING"
```

### Why this is non-obvious

The v4 migration guide doesn't flag this behavioral change explicitly. The
schema works correctly for non-alias cases — the bug only manifests when
`.default().optional()` is combined with `??`-based alias resolution in a
transform. The failure is silent (wrong value, no error), making it hard to
detect without specific test coverage for alias fields.

### Why this fix

Moving the default to the transform's `??` chain is the correct location
because the default should only apply after all alias candidates are exhausted.
Schema-level `.default()` fires per-field before the transform sees the values,
which is too early for cross-field alias resolution.

### Alternatives considered

- Reverse the chain to `.optional().default()` — not valid in v4 (`.optional()` on a `.default()` type is the only valid order)
- Use a single field name and drop the alias — breaks backward compatibility with existing YAML documents
