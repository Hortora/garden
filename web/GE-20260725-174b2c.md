### Symptom

Test throws `"Body is unusable: Body has already been read"` on the second call
to a mocked fetch function, even though the mock appears correctly configured.

### Context

When testing a source that triggers multiple fetches (e.g., a write that returns
204, which triggers a read-path refresh), the same mock function is called twice.

```typescript
// This creates ONE Response object and returns it for every call
const fetchFn = vi.fn().mockResolvedValue(
  new Response(JSON.stringify(data), { status: 200, headers: { "content-type": "application/json" } })
);
```

The first call reads the body successfully. The second call attempts to read the
same Response instance — `Response.body` is a ReadableStream that can only be
consumed once per the Fetch API spec.

### Root cause

`mockResolvedValue(value)` stores a single reference and returns it on every
invocation. Unlike primitive values, Response objects are stateful — reading the
body mutates the object (marks the stream as disturbed). The mock doesn't clone
the value per call.

### Fix

Create a fresh Response per invocation using `mockImplementation`:

```typescript
const fetchFn = vi.fn().mockImplementation(() =>
  Promise.resolve(new Response(JSON.stringify(data), {
    status: 200,
    headers: { "content-type": "application/json" },
  }))
);
```

Or use `mockResolvedValueOnce` for each expected call:

```typescript
const fetchFn = vi.fn()
  .mockResolvedValueOnce(new Response(JSON.stringify(data1), { status: 200 }))
  .mockResolvedValueOnce(new Response(JSON.stringify(data2), { status: 200 }));
```

### Why this is non-obvious

The error message ("Body is unusable") doesn't mention mocking or object reuse.
The natural debugging path is to check the Response construction, not the mock
delivery mechanism. `mockResolvedValue` works perfectly for primitives, strings,
and plain objects — the failure is specific to stateful objects like Response.
