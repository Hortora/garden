### Symptom

Custom tooltip styles set via `EditorView.theme()` with `& .cm-tooltip` have no
visible effect. `getComputedStyle()` on the tooltip element returns the base
theme's hardcoded values (e.g. light background `#f5f5f5`), even when CSS custom
properties resolve to different values at that element.

### Context

CodeMirror 6 uses generated class prefixes (`.ͼ1`, `.ͼ2`, `.ͼ3`) for its base,
light, and dark themes. Custom themes created with `EditorView.theme()` get their
own prefix (e.g. `.ͼw`). Both use two-class selectors (`.ͼw .cm-tooltip` vs
`.ͼ2 .cm-tooltip`) — identical specificity.

Inside a Lit shadow DOM, all these rules live in the same `adoptedStyleSheets`.
The base theme is injected AFTER the custom theme in the stylesheet order,
so it wins by cascade.

### What was tried (didn't work)

1. **EditorView.theme `& .cm-tooltip`** — generates `.ͼw .cm-tooltip`, same
   specificity as `.ͼ2 .cm-tooltip`, loses by cascade order.
2. **Lit `static styles`** — bare `.cm-tooltip` has LOWER specificity than
   the two-class base theme selector. Overridden completely.
3. **EditorView.theme `&.cm-editor .cm-tooltip`** — higher specificity but
   still overridden because the base theme's `!important`-free rule loads later.

### Root cause

CSS cascade order, not specificity. Both the custom theme and base theme
produce selectors with identical specificity. The base theme's stylesheet
is adopted later, so it wins. This is not a shadow DOM scoping issue — the
rules ARE reaching the tooltip — they're just being overridden.

### Fix

Use `!important` on the custom theme tooltip overrides:

```typescript
const pagesTheme = EditorView.theme({
  '& .cm-tooltip': {
    backgroundColor: 'var(--pages-neutral-2, #f5f5f5) !important',
    color: 'var(--pages-neutral-12, #1a1a1a) !important',
    border: '1px solid var(--pages-neutral-6, #d0d0d0) !important',
  },
  '& .cm-tooltip-autocomplete ul li[aria-selected]': {
    backgroundColor: 'var(--pages-accent-9, #3451b2) !important',
    color: 'white !important',
  },
});
```

The `!important` flag overrides the cascade order advantage. CSS custom
properties in the values handle light/dark mode adaptation automatically.

### Why this is non-obvious

The `&` prefix documentation implies scoped selector generation should
"just work" for tooltip overrides. The real issue only manifests in shadow
DOM where all CM6 stylesheets share the same adoptedStyleSheets scope.
In a regular document, injection order might differ.

### Alternatives considered

- Setting `{ dark: true }` on `EditorView.theme()` — only switches which
  base theme prefix is used (`.ͼ3` instead of `.ͼ2`), doesn't solve the
  cascade problem for custom values.
