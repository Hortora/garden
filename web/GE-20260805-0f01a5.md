### Symptom
`ReferenceError: document is not defined` when importing from a TypeScript package barrel (e.g. `@casehubio/blocks-ui-core`) in a vitest test file that does not configure `environment: 'jsdom'`.

The error points to a module the test never directly imports — the barrel's re-export chain pulls it in.

### Context
A monorepo package (`blocks-ui-core`) re-exports everything via `src/index.ts`. One transitive export — `SharedTimerController` — calls `document.createElement('div')` at module parse time (top-level statement, not inside a method). Any consumer importing anything from the barrel triggers evaluation of the entire module graph, including the browser-only module.

This surfaces when a non-UI package (e.g. `graph-stencil-case`) imports a pure-data utility (like `lookupStatus`) from the barrel. The test only needs the data function, but the barrel drags in the browser-dependent controller.

### What was tried (didn't work)
1. Importing the barrel normally — fails in non-JSDOM environments
2. Using package.json `exports` subpath — not configured in the monorepo

### Root cause
TypeScript barrel (`index.ts`) re-exports all modules. ES module evaluation is eager — `import { lookupStatus } from '@casehubio/blocks-ui-core'` evaluates every module in the re-export chain, including `SharedTimerController` which has a top-level `document.createElement()` call. There is no tree-shaking at import time in Node/vitest.

### Fix
Import from the specific subpath instead of the barrel:

```typescript
// Bad — pulls in entire module graph including browser-only modules
import { lookupStatus } from '@casehubio/blocks-ui-core';

// Good — only evaluates the status module and its dependencies
import { lookupStatus } from '@casehubio/blocks-ui-core/types/status.js';
```

Alternative: ensure the consuming package's `vitest.config.ts` sets `environment: 'jsdom'` — but this masks the real issue and adds unnecessary JSDOM overhead to pure-logic tests.

### Why this is non-obvious
The error message points to a file the test never imports (`shared-timer-controller.ts`). The import statement looks correct — `lookupStatus` is a pure function with no browser dependency. The connection between "I imported a data function" and "a timer controller tried to create a DOM element" requires understanding the barrel re-export evaluation chain.
