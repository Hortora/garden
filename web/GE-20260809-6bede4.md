### Symptom
Frame position resets to (0,0) after refresh despite save data being correct. Position persistence code reads `overlay.toJSON()` and checks `bounds.top != null` — this passes initially but fails silently after the user drags.

### Context
Dockview floating overlays use CSS `inset` property. On creation: `inset: 200px auto auto 300px` (top-left anchoring). After user drags the titlebar, Dockview switches to bottom-left anchoring: `inset: auto auto 50px 300px`. The `top` value becomes `auto`, not `0`.

### What was tried (didn't work)
- Reading `overlay.toJSON()` — returns `{bottom: 50, left: 300}` with `top` absent after drag
- Checking `bounds.top != null` — `undefined != null` is `false`, so the position update is silently skipped
- Guard with `bounds.top != null && bounds.left != null` — same failure, `undefined` is not `null`

### Root cause
`overlay.toJSON()` returns the raw CSS `inset` components. After a drag, Dockview uses bottom anchoring instead of top. The `top` property is literally absent from the returned object, not set to `0`.

### Fix
Read `overlay.element.getBoundingClientRect()` relative to the container instead of `toJSON()`. `getBoundingClientRect()` always returns absolute viewport coordinates regardless of CSS anchoring mode.

```typescript
const el = overlay.element;
const parentRect = container.getBoundingClientRect();
const rect = el.getBoundingClientRect();
const pos = { x: rect.left - parentRect.left, y: rect.top - parentRect.top };
```

### Why this is non-obvious
The CSS anchoring switch is invisible — the overlay looks the same visually. `toJSON()` returns a valid-looking object with `left` and `width` populated. The missing `top` only surfaces when you check the property, and `!= null` vs `=== undefined` behaves differently for absent properties vs explicit `null`.
