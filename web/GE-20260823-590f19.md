## Symptom

Adding a new component type (e.g. `event-timeline`) to the pages gallery YAML samples produces one of three silent failure modes depending on which registration point is missing.

## Context

The pages gallery renders YAML-defined samples through a pipeline: YAML parser → component desugar → displayer desugar → activation → DOM creation. Each stage has its own set of known component types.

## What was tried (didn't work)

1. Added `event-timeline` to `activation.ts` DATA_COMPONENT_TYPES only → component type parsed as `"unknown"` by the YAML desugar stage, never reached activation
2. Added to both `activation.ts` and `component-desugar.ts` DATA_COMPONENT_TYPES → component created but rendered as `data-table` because `displayer-desugar.ts` TYPE_MAP defaulted unknown types to `"data-table"`

## Root cause

Three independent type registries must all know about the component:

| File | Set/Map | Failure if missing |
|------|---------|-------------------|
| `packages/pages-ui/src/parser/component-desugar.ts` | `DATA_COMPONENT_TYPES` | Type becomes `"unknown"` — component container created but empty |
| `packages/pages-ui/src/parser/displayer-desugar.ts` | `TYPE_MAP` | Type falls through to `"data-table"` default — wrong component rendered |
| `packages/pages-runtime/src/activation.ts` | `DATA_COMPONENT_TYPES` | Component not created at all — container stays empty |

## Fix

Add the component type string to all three locations:

```typescript
// component-desugar.ts — DATA_COMPONENT_TYPES set
"badge", "countdown", "timeline", "graph", "event-timeline",

// displayer-desugar.ts — TYPE_MAP (uppercase key)
"EVENT-TIMELINE": "event-timeline",

// activation.ts — DATA_COMPONENT_TYPES set  
"event-timeline",
```

## Why this is non-obvious

Each missing registration produces a *different* failure mode with no error message. The component-desugar failure silently converts the type to "unknown". The displayer-desugar failure silently renders a data-table instead. Only the activation failure is somewhat visible (empty container). Debugging requires understanding the three-stage pipeline.

### Why this fix

The three registries exist because they serve different pipeline stages with different responsibilities. Unifying them would couple the parser, desugar, and activation layers. The correct fix is documenting the three-point registration requirement.

### Alternatives considered

- Unifying all three sets into a single shared registry — rejected because the three stages have different type vocabularies (desugar handles legacy uppercase names, activation handles tag name overrides)
