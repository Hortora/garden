### Symptom
Panel resize handle appears as a small corner grippy instead of a full-edge drag handle. Popovers, emoji pickers, tooltips, and context menus are clipped. No JavaScript events fire for persisting the new width.

### Context
Building resizable nav/member panels in a Lit web component workbench with shadow DOM. The panels need edge-dragging (grab the full vertical border between panels), width persistence to localStorage, and must not clip overlay content (popovers, emoji pickers, context menus).

### What was tried (didn't work)
CSS `resize: horizontal` on panel elements — the "native, zero-dependency" approach. Appears in every discussion of resizable elements as the simplest solution.

### Root cause
CSS `resize` has four fundamental issues in this context:

1. **Wrong interaction model** — places a small triangular grippy at the bottom-right corner of the element. Users expect to grab the full vertical edge between panels. No professional chat application (Slack, Discord, VS Code, Teams) uses CSS resize for panel sizing.

2. **No JavaScript callbacks** — CSS resize provides no events. Detecting when the user has finished resizing (to persist width to localStorage) requires wrapping with a `ResizeObserver`. The "zero-dependency" claim is misleading.

3. **Overflow constraint** — CSS resize only works when `overflow` is not `visible`. Setting `overflow: hidden` or `overflow: auto` clips emoji picker popovers, context menus, tooltips, and any other content that needs to overflow panel bounds.

4. **Shadow DOM inconsistency** — CSS resize behavior varies across browsers when applied inside shadow roots. Lit web components use shadow DOM by default.

### Fix
PointerEvent-based drag handles — a thin `<div>` (4px, `cursor: col-resize`) rendered between panels:

```typescript
private _onDragStart(panel: 'nav' | 'member', e: PointerEvent) {
  const target = e.currentTarget as HTMLElement;
  target.setPointerCapture(e.pointerId);
  const startX = e.clientX;
  const startWidth = panel === 'nav' ? this._navWidth : this._memberWidth;
  const minW = 180;
  const maxW = panel === 'nav' ? 360 : 300;

  const onMove = (me: PointerEvent) => {
    const delta = panel === 'nav' ? me.clientX - startX : startX - me.clientX;
    const newWidth = Math.max(minW, Math.min(maxW, startWidth + delta));
    if (panel === 'nav') this._navWidth = newWidth;
    else this._memberWidth = newWidth;
  };

  const onUp = () => {
    target.removeEventListener('pointermove', onMove);
    target.removeEventListener('pointerup', onUp);
    // persist to layout store
  };

  target.addEventListener('pointermove', onMove);
  target.addEventListener('pointerup', onUp);
}
```

CSS:
```css
.drag-handle {
  width: 4px;
  cursor: col-resize;
  background: transparent;
  flex-shrink: 0;
  transition: background 0.15s;
}
.drag-handle:hover { background: var(--pages-accent-7, #818cf8); }
.drag-handle:active { background: var(--pages-accent-9, #007bff); }
```

~30 lines of code. Full-edge dragging, fires events for persistence, no overflow constraints, works consistently in shadow DOM.

### Why this is non-obvious
CSS `resize` is the textbook "native" answer for resizable elements. Every discussion of resizable UI starts there. The four-way failure (interaction model, events, overflow, shadow DOM) only surfaces during actual implementation. Professional chat apps all use custom drag handles, but that pattern isn't documented as "because CSS resize fails" — it's just what they do.

### Alternatives considered
- **CSS resize with ResizeObserver wrapper** — fixes the events problem but corner grippy and overflow issues remain
- **Third-party resize libraries** (split.js, etc.) — heavy dependencies for ~30 lines of pointer capture code
