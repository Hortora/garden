### Symptom

esbuild alias maps `@scope/pkg` to a directory outside the project tree (e.g. a sibling repo). The aliased source files import standard dependencies like `lit`, `zod`, etc. esbuild fails with "Could not resolve 'lit'" pointing to the aliased source file — even though `lit` is installed in the consumer project's `node_modules`.

### Context

A Quarkus + Quinoa project aliases `@casehubio/blocks-ui-document-workbench` to a sibling `blocks-ui/` repo's source directory. The blocks-ui source files import from `lit` (installed in blocks-ui's own `node_modules` during local dev). On CI, blocks-ui is checked out but `npm install` is not run inside it — only the consumer project has `node_modules`.

### Root cause

esbuild resolves dependencies relative to the importing file's directory, walking up the directory tree looking for `node_modules/`. When the importing file is in a sibling repo (via alias), esbuild walks up THAT repo's directory tree — never reaching the consumer project's `node_modules/`. The consumer's `node_modules` is in a completely different subtree.

### Fix

Add `nodePaths` to the esbuild config pointing to the consumer project's `node_modules`:

```javascript
const options = {
  // ... other options
  nodePaths: [resolve(__dirname, "node_modules")],
  alias: {
    "@scope/external-pkg": resolve(__dirname, "../../sibling-repo/src"),
  },
};
```

`nodePaths` adds additional directories to the module resolution search path — esbuild checks these after the normal `node_modules` walk-up fails.

### Why this is non-obvious

esbuild's alias documentation describes it as replacing one package name with another path. It doesn't mention that the aliased directory's dependency resolution is isolated from the consumer — a developer expects that bundling external source into their project would naturally use their project's `node_modules`. The error message ("Could not resolve 'lit'") points to the external file but doesn't suggest `nodePaths` as a solution.
