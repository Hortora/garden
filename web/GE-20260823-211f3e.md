## Symptom

A subclass extending a Lit custom element from a SNAPSHOT WebJar package silently uses the parent's old `render()` method instead of the overridden version. The component renders PagesElement's loading skeleton instead of the subclass content. No error is thrown.

## Context

Cross-package inheritance: `BlocksTimeline extends PagesEventTimeline` where PagesEventTimeline comes from `@casehubio/pages-viz` resolved via a Yarn `portal:` to `.casehub-packages/packages/pages-viz`. The portal directory is populated by Maven dependency extraction from a SNAPSHOT JAR.

## What was tried (didn't work)

1. Checked for duplicate Lit installations — both resolve to the same `node_modules/lit`
2. Verified the source code has the override — it does
3. Checked `@customElement` decorator registration — both elements register correctly

## Root cause

The `.casehub-packages` portal directory contained the OLD built dist of PagesEventTimeline (without the `render()` override). After rebuilding pages-viz source, TWO steps are required to refresh the portal:

1. `mvn process-resources` — extracts the new SNAPSHOT JAR to `.casehub-packages/`
2. `yarn install` — re-links the Yarn portal to pick up the new files

Missing either step leaves the old dist in place. The Lit "Multiple versions loaded" warning appears but is misleading — the real issue is stale code, not version conflicts.

## Fix

After changing a pages package that blocks-ui consumes:

```bash
# In casehub-pages:
yarn build && mvn install

# In blocks-ui:
mvn -f npm-packages/pom.xml process-resources  # extract new SNAPSHOT
yarn install                                    # re-link portals
```

Both steps are mandatory. `yarn install` alone doesn't help because it re-links to the same stale directory. `mvn process-resources` alone doesn't help because Yarn caches the portal resolution.

## Why this is non-obvious

The class hierarchy appears correct (prototype chain is right, decorators are applied), but the dist code is stale. The Lit "Multiple versions" warning is a red herring — the issue is stale code, not version conflicts. No error is thrown; the parent's method simply runs instead of the child's override.
