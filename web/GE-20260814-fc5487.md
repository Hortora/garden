### Symptom
`npm install` fails with `E404 Not Found` for `@casehubio/*` packages on the public npm registry, even though all packages are available as local tarballs via `file:` dependencies.

### Context
CaseHub host apps (scaffold, devtown, clinical) consume blocks-ui and pages npm packages from Maven-unpacked tarballs in `.casehub-packages/tarballs/`. The `package.json` references them as `"@casehubio/blocks-ui-case-explorer": "file:.casehub-packages/tarballs/case-explorer.tgz"`.

### What was tried (didn't work)
1. Only listing direct dependencies — transitive deps (`@casehubio/pages-primitives`, `@casehubio/blocks-ui-core`, etc.) hit the public registry
2. Using `.npmrc` with `legacy-peer-deps=true` alone — fixes peer dep conflicts but not the registry lookups

### Root cause
The tarballs' internal `package.json` files declare dependencies on other `@casehubio/*` packages with `*` version ranges (from the yarn workspace). npm resolves `*` by querying the public registry — it doesn't know that the root `package.json`'s `file:` deps should satisfy these transitive requirements.

### Fix
Three things required:

1. **List ALL @casehubio packages** as direct `file:` deps in `package.json` — including transitives that aren't directly imported. Extract actual package names from tarballs (they don't always match tarball filenames: e.g. `diagram-core.tgz` is `@casehubio/diagram-core`, not `@casehubio/blocks-ui-diagram-core`).

2. **Add `overrides` section** to `package.json` with `"$@casehubio/package-name"` entries for every @casehubio package. This tells npm "use whatever version is specified for this package in our dependencies":
```json
"overrides": {
  "@casehubio/pages-primitives": "$@casehubio/pages-primitives",
  "@casehubio/blocks-ui-core": "$@casehubio/blocks-ui-core"
}
```

3. **Add `.npmrc`** with `legacy-peer-deps=true` for graph packages that peer-depend on react.

### Why this is non-obvious
The `file:` protocol in npm is well-documented for direct dependencies but its interaction with transitive `*` version ranges inside tarballs is not. The error manifests as a registry 404 for the transitive package — not as a local resolution failure — making it look like a registry/auth issue rather than a dependency resolution design problem.
