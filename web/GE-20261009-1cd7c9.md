### Problem
ProseMirror has no API for "which visual rendered line is the cursor on." Finding the start and end positions of a visual line requires coordinate-based detection.

### Solution 1 — Bidirectional coordsAtPos walk with line-height threshold (Recommended)
**Approach:** Walk positions in both directions from the cursor, using `coordsAtPos` to detect when the Y coordinate changes by more than 40% of line height.
**Pros:** Handles inline formatting (italic/code shift Y by 2-5px) correctly; adapts to any viewport width; simple implementation.
**Cons:** Walks one position at a time — O(n) in line length.

```typescript
const selCoords = this.view.coordsAtPos(sel);
const lineHeight = selCoords.bottom - selCoords.top;
const threshold = Math.max(lineHeight * 0.4, 8);

let startPos = sel;
for (let p = sel - 1; p >= blockStart; p--) {
  const c = this.view.coordsAtPos(p);
  if (Math.abs(c.top - selCoords.top) > threshold) break;
  startPos = p;
}

let endPos = sel;
for (let p = sel; p <= blockEnd; p++) {
  const c = this.view.coordsAtPos(p);
  if (Math.abs(c.top - selCoords.top) > threshold) break;
  endPos = p;
}
```

**Why 40% of line height:** Inline formatting (`<em>`, `<code>`) shifts baseline by 2-5px. With typical 19px line height, threshold is ~8px — inline shifts pass, line wraps stop. Fixed pixel thresholds (e.g., >5px) fail at certain font sizes.

### Solution 2 — getClientRects line bands + posAtCoords edges
**Approach:** Use `Range.getClientRects()` on the block element to get visual line bands, then `posAtCoords` to map band edges to positions.
**Pros:** Uses the browser's layout engine directly for line grouping.
**Cons:** `posAtCoords` at the right edge of a line band overshoots past the line wrap boundary — returns a position on the NEXT visual line. Unreliable for determining exact line end positions.

### Why this is non-obvious
`posAtCoords` at a wrap boundary snaps to the closest text position, which can be on the next line. The bidirectional walk avoids this by never querying edge positions — it walks outward from the cursor and stops when coordinates change.

The `coordsAtPos` walk was previously dismissed as unreliable due to inline formatting shifts. The key insight is using a relative threshold (% of line height) instead of a fixed pixel value — this correctly separates inline baseline shifts from actual line wraps.

### Alternatives considered
- `posAtCoords` at line band edges — overshoots at wrap boundaries (see Solution 2)
- Fixed pixel threshold (>5px) — fails when inline formatting shift equals the threshold
- Hardbreak node detection — Milkdown renders hardbreaks as inline spans, not `<br>` (see GE-20261010-b05aa6)
- `textBetween` split on `\n` — ProseMirror `\n` is a node boundary separator, not a visual line break
