### Problem
ProseMirror has no API for "which visual rendered line is the cursor on." The `coordsAtPos` API returns Y coordinates, but they are unreliable for visual line detection — inline code marks shift Y by several pixels, and the values change with scroll position. Walking positions and comparing Y values produces inconsistent results.

### Technique
Use the browser's `Range.getClientRects()` API on the block element, then `view.posAtCoords()` to map pixel boundaries back to ProseMirror positions:

```typescript
// 1. Find the block element in the DOM
const domPos = view.domAtPos(sel);
let blockEl = domPos.node;
while (blockEl && !blockEl.tagName?.match(/^(P|H[1-6]|LI|TD|TH)$/))
  blockEl = blockEl.parentNode;

// 2. Get all rects — one per inline fragment
const range = document.createRange();
range.selectNodeContents(blockEl);
const rects = Array.from(range.getClientRects());

// 3. Group by Y band into visual lines
const lines = [];
for (const r of rects) {
  const existing = lines.find(l => Math.abs(l.top - r.top) <= 5);
  if (existing) {
    existing.left = Math.min(existing.left, r.left);
    existing.right = Math.max(existing.right, r.right);
  } else {
    lines.push({ top: r.top, bottom: r.bottom, left: r.left, right: r.right });
  }
}

// 4. Find cursor's visual line
const cursorCoords = view.coordsAtPos(sel);
const cursorLine = lines.find(l => cursorMidY >= l.top - 2 && cursorMidY <= l.bottom + 2);

// 5. Map edges back to ProseMirror positions
const lineStart = view.posAtCoords({ left: cursorLine.left + 1, top: lineMidY });
const lineEnd = view.posAtCoords({ left: cursorLine.right - 1, top: lineMidY });
```

### Why this is non-obvious
The natural approach — walking positions with `coordsAtPos` and comparing Y values — is unreliable because:
- Inline marks (code, bold, italic) have slightly different rendered heights, shifting Y by 3-5px
- `coordsAtPos` returns the line box top, not the individual character position
- Results change with scroll position between runs

`getClientRects()` bypasses all of this by querying the browser's actual layout engine. Each rect corresponds to one inline fragment on one visual line. Grouping by Y band gives exact visual line boundaries that adapt to window width.

### Alternatives considered
- `coordsAtPos` walk with tolerance — unreliable across inline marks and scroll states
- `textBetween` split on `\n` — ProseMirror `\n` is a node boundary separator, not a visual line break
- `document.caretRangeFromPoint` — doesn't work reliably across shadow DOM boundaries
