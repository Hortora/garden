### Symptom

Changes to TypeScript source files in a workspace package are not picked up by the Vite dev server. The browser loads the old code. Full page reloads, cache clears, and Vite restarts don't help. HMR log shows the module URL points to `dist/` files.

### Context

In a Yarn workspace monorepo, package A (`pages-code-editor`) has in its `package.json`:
```json
{
  "exports": { ".": "./dist/index.js" },
  "main": "dist/index.js"
}
```

Package B (`pages-builder`) imports from `@scope/pages-code-editor`. Yarn creates a symlink in `node_modules/@scope/pages-code-editor` → `../../packages/pages-code-editor`. Vite follows the symlink, reads `package.json`, and resolves imports via the `exports` field — which points to `dist/`.

### What was tried (didn't work)

- `rm -rf node_modules/.vite` and restart Vite — cleared Vite's pre-bundle cache but `dist/` resolution is not a cache issue
- Full page reload with cache bypass (Cmd+Shift+R) — loads the same `dist/` module
- Checking if the package is in `.vite/deps/` pre-bundle cache — it wasn't; Vite loads it as a source file from `dist/`
- Fetching the raw `.ts` source from Vite's `/@fs/` URL — the source IS updated, but the running app uses the compiled `dist/` version

### Root cause

Vite resolves workspace package imports via the `exports` field in `package.json`, which points to compiled `dist/` files. The symlink lets Vite find the package, but it reads `package.json` to determine the entry point — just like Node would. The `.ts` source files exist alongside `dist/` but Vite never looks at them for the main entry resolution.

This is correct behavior by Vite — it follows the Node module resolution algorithm. But it's surprising in a dev context where you expect "source files are the truth."

### Fix

After editing source files in a workspace package, rebuild before the Vite dev server will pick up changes:

```bash
yarn workspace @scope/package-name run build
```

Then reload the Vite page. The dev server serves the newly compiled `dist/` files.

For packages that want true source-level HMR, change `package.json` to export source directly:
```json
{
  "exports": { ".": "./src/index.ts" },
  "main": "src/index.ts",
  "types": "src/index.ts"
}
```

This only works if all consumers can handle TypeScript imports (Vite can, webpack with ts-loader can, plain Node cannot).

### Why this is non-obvious

The developer sees updated source at `/@fs/.../src/file.ts` in Vite's module graph, which suggests HMR should work. The disconnect — that the *import resolution* uses `dist/` while the *file server* can see `src/` — is invisible in normal debugging. The browser's network tab shows the `dist/` URL, but only if you know to look for it. Performance entries (`performance.getEntriesByType('resource')`) reveal the actual loaded URLs.

### Alternatives considered

- Changing all workspace packages to export `src/*.ts` — works for Vite but breaks consumers that need compiled JS (e.g. webpack with restrictive rootDir)
- Using Vite's `optimizeDeps.exclude` — doesn't change how imports resolve, only affects pre-bundling
