## Schema composition for multi-format LSP — language layers via z.intersection()

### Symptom

Building an LSP that supports multiple YAML formats (pages, case, workflow, org) where a shared preprocessing layer (variables, modules, forEach, conditionals) applies to ALL formats. The natural approaches — extending each format schema or creating a new format registration — both have significant downsides.

### Context

An LSP with a schema registry where each format has a `documentSchema: z.ZodType`. A preprocessing language (like yaml-core) adds keys (`modules`, `imports`, `variables`, `forEach`, `when`) that are valid in ANY format.

### What was tried (didn't work)

1. **Extend each format schema** — add yaml-core keys as optional properties to each format's Zod schema. Wrong abstraction: treats language-level constructs as format-specific. Creates schema bloat and false promise if the runtime doesn't process them yet.

2. **New format registration** — create a `.composed.page.yaml` extension for yaml-core-enhanced documents. Fragments the format unnecessarily. Users must choose between two extensions for the same content.

### Root cause

Both approaches treat the preprocessing layer as a FORMAT concern. It's not — it's a LANGUAGE LAYER that sits below all formats. The preprocessing layer is orthogonal to what format the content describes.

### Fix

Define the preprocessing layer as a separate Zod schema and compose it with each format via `z.intersection()`:

```typescript
// Language layer schema (shared across all formats)
const yamlCoreDocumentSchema = z.object({
  variables: variablesSchema.optional(),
  modules: z.record(moduleDefinitionSchema).optional(),
  imports: z.array(importSchema).optional(),
});

const yamlCoreElementMixin = {
  forEach: forEachSchema.optional(),
  when: z.string().optional(),
};

// Each format composes — one line per format
// pages:
documentSchema: z.intersection(yamlCoreDocumentSchema, dashboardSchema),
// case:
documentSchema: z.intersection(yamlCoreDocumentSchema, caseSchema),
// workflow:
documentSchema: z.intersection(yamlCoreDocumentSchema, swfSchema),
```

The schema-navigation engine walks `ZodIntersection` natively (tries left, then right), so completions, diagnostics, and hover work automatically for both language-layer and format-specific keys.

### Why this is non-obvious

Developers building multi-format LSPs naturally reach for either extending each format (option 1) or creating new formats (option 2). The "false dichotomy" is only visible from first principles: asking "what IS this layer?" reveals it's not a format at all. The z.intersection() composition pattern falls out naturally once the abstraction is corrected — but the abstraction correction requires stepping back from the immediate options.

### Alternatives considered

- **z.object().merge()** — fails at compile time because format schemas are exported as widened `z.ZodType`, not `ZodObject`. See GE-20260914-fab341 for details.
- **Separate npm package for the language schema** — cleaner separation but adds a package for what's conceptually one line of composition per format.
