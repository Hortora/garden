## LSP4IJ requires explicit textEdit on CompletionItems — insertText alone inserts at column 0

**ID:** GE-20260914-22cde3
**Stack:** LSP4IJ 0.21.0, IntelliJ IDEA
**Symptom:** Completion selection inserts text at column 0 instead of the cursor position. No error message. YAML document structure breaks silently because indentation is lost.
**Context:** Custom LSP server returning `CompletionItem` with `insertText` but no `textEdit`. The LSP spec states that clients should compute a default replacement range when `textEdit` is absent. Particularly critical for YAML where indentation is structural.

### What was tried (didn't work)
- Returned `CompletionItem` with only `insertText` set (per LSP spec) — text inserted at column 0, not cursor position
- Verified completions appeared correctly in the completion popup — the issue is only on selection/insertion

### Root cause
LSP4IJ does not compute a default edit range from the cursor position when `textEdit` is absent on a `CompletionItem`. Unlike VS Code's LSP client (which infers a word-range replacement), LSP4IJ falls back to inserting at column 0 of the current line.

### Fix

Always return `textEdit` with an explicit `Range` on every `CompletionItem`. The range end is the cursor position; the range start is the beginning of any partially-typed word prefix.

```typescript
function getWordStart(textBefore: string): number {
  const match = textBefore.match(/([\w][\w-]*)$/);
  return match ? textBefore.length - match[0].length : textBefore.length;
}

// In completion handler:
const wordStart = getWordStart(textBefore);
return {
  label: c.label,
  kind: PROPERTY_KIND,
  textEdit: {
    range: {
      start: { line: position.line, character: wordStart },
      end: { line: position.line, character: position.character },
    },
    newText: completionText,
  },
};
```

When `textEdit` is present, omit `insertText` — the LSP spec says `textEdit` takes precedence, and sending both may confuse some clients.

### Alternatives considered
- Client-side fix in IntelliJ Kotlin plugin (intercept completion and compute insert offset) — rejected because it fights the LSP abstraction, requires per-client fixes, and leaves the server non-conformant

### Why this is non-obvious
The LSP specification explicitly states that when `textEdit` is not provided, the client should use a default edit range. A developer implementing an LSP server would reasonably expect `insertText` alone to work correctly. LSP4IJ's divergence from the spec is not documented — the only way to discover it is to observe the column-0 insertion behavior at runtime.
