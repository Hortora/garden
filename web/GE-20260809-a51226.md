## Relationship type registry follows status registry pattern — module-level Map, no deregistration

### The convention
When adding a new domain registry to blocks-ui-core, follow the established `registerStatus`/`lookupStatus` pattern:

- Module-level `Map<string, Descriptor>` with built-in entries pre-populated
- `register(key, descriptor)` to add or override entries
- `lookup(key)` returns the descriptor or a `FALLBACK` constant
- No `deregister()` function — registrations are permanent for the process lifetime
- Built-in entries are populated at module load time, not on first component connection
- Fallback descriptor is a named export (`FALLBACK_RELATIONSHIP`, `FALLBACK_DESCRIPTOR`)

### Known alternative
A per-component registry passed as a property (e.g. `edgeTypeConfig: Record<string, Descriptor>`). This avoids global state but forces every consumer to pass the same configuration. The module-level Map was chosen because relationship types (like status types) are platform-wide semantics, not per-component configuration.

### Why this convention
The status registry (`registerStatus`/`lookupStatus`) has been stable across 13 built-in domains. The pattern is well-tested, simple, and familiar to anyone who has worked with status badges. Introducing a different registry pattern for a structurally identical problem would create cognitive overhead with no benefit.
