### Symptom
`Container.replaceChild(oldKey, newEntry)` silently causes cascade collapse or disposal when used on a 2-entry split container. The container may be in a disposed state after the call, and the new entry is appended at the wrong position.

### Context
A UI framework uses a strategy pattern for container layouts (tabbed, split, accordion, free). Each strategy has `addEntry`/`removeEntry` methods. Split strategies check if entries drop to 1 and fire an `onCollapse` callback to promote the surviving child. `replaceChild` was intended for swapping a subtree in place (e.g., replacing a leaf container with a split container during a pane-level split operation).

### What was tried (didn't work)
Using `replaceChild` for surgical container tree surgery — replace one child container with another without unmounting/remounting the entire tree. The method existed on the Container interface but had zero callers in the codebase — it was never tested.

### Root cause
`replaceChild` decomposes into `removeEntry(oldKey)` then `addEntry(newChild)`:

```typescript
replaceChild(oldKey, newChild) {
  const idx = entries.findIndex(e => e.key === oldKey);
  entries[idx] = newChild;
  currentOrganiser.removeEntry(oldKey);  // ← triggers onCollapse!
  currentOrganiser.addEntry(newChild);   // ← runs on disposed organiser
}
```

**Bug 1 — Cascade collapse:** On a 2-entry split container, `removeEntry` reduces entries to 1, which fires `onCollapse`. The collapse handler promotes the surviving child upward, potentially disposing the container. Then `addEntry` runs on the disposed organiser — undefined behaviour.

**Bug 2 — Wrong position:** `addEntry` appends to the end of the strategy's internal `currentEntries` array. On a `[left, right]` split, replacing `left` produces `[right, newLeft]` — visually inverted.

### Fix
Don't use `replaceChild` for tree surgery. Instead, mutate the entry's properties in place and call `container.refreshEntry(key)`:

```typescript
// Surgical replant: mutate + refresh instead of replace
entry.childContainer = newSplitContainer;
parentContainer.refreshEntry(entry.key);
```

`refreshEntry` tells the strategy to re-render just that entry's content slot — no remove/add cycle, no collapse cascade, no position change. Each strategy disposes the old content element, runs the content factory, and replaces in the DOM.

### Why this is non-obvious
`replaceChild` looks correct — it's on the interface, it updates both the entries array and the organiser. The cascade is hidden: you'd need to know that `removeEntry` has a side effect (collapse check) that fires before `addEntry` can restore the entry count. The method had zero callers, so the bug was never surfaced by usage — only discovered during adversarial spec review.
