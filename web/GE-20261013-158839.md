### Symptom
`Error: root → Step 0 → parallel → Step 0 → block → Step 1: no step type identified. Keys: await` when running any coordination playbook that uses `signal:` or `await:` inside `concurrent:` branches.

### Context
The parser has a `preExtract` function that converts standalone `signal:` → `signal-fire` and `await: {signal: X}` → `await-signal` BEFORE the Walker sees them. The Walker treats `signal` and `await` as decorator keys, so if they reach the Walker as standalone steps, it finds no action key and throws.

The `concurrent:` pre-extraction converts named branches into `{parallel: [{step: name, block: branchSteps}]}` and passes `branchSteps` directly to the Walker — without running preExtract on them first.

### Root cause
Pre-extraction is a top-level-only pass. Nested steps inside concurrent branches bypass it entirely and hit the Walker raw. The Walker correctly rejects `await:` as "not a step type" because it IS a decorator key, not a step key.

### Fix
Pass `catalog` into `preExtract`. When catalog is available and `concurrent:` is encountered, resolve each branch's steps through the full `resolveStepArray` pipeline (which includes preExtract) recursively. The mutual recursion between `preExtract(rawSteps, catalog)` and `resolveStepArray(branchSteps, catalog)` terminates because branch arrays are always smaller than the parent.

When catalog is unavailable (standalone Walker use without the parser), fall through to the old non-recursive path.

### Why this is non-obvious
The pre-extraction architecture is invisible — there's no error that says "pre-extraction didn't run." The Walker's error message ("no step type identified. Keys: await") points to the Walker, not the parser. The fix requires understanding that signal/await processing happens in the parser's pre-extraction phase, not the Walker, and that concurrent branches skip it.
