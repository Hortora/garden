### Symptom

Test assertion fails after `await el.updateComplete` — the DOM doesn't reflect a `@state()` property change that was made inside `updated()`. The value is correct on the element but hasn't been rendered yet.

Lit emits a dev-mode warning: "Element scheduled an update after an update completed, causing a new update to be scheduled."

### Context

A LitElement component computes derived reactive state inside the `updated()` lifecycle hook — for example, incrementing an unread message count when new messages arrive while the user is scrolled up. The derived state is declared with `@state()` and rendered in the template.

### What was tried (didn't work)

- `await el.updateComplete` after setting the triggering property — resolves after the first render cycle, before the second render that reflects the `@state()` change
- Double `await el.updateComplete` — works but is fragile and obscures the real issue

### Root cause

Lit's `updated()` runs *after* the render completes. Setting a `@state()` property inside `updated()` marks the element dirty again, scheduling a new microtask update. The first `updateComplete` promise resolves at the end of the first cycle — before the second cycle starts. Tests that assert DOM state at that point see the pre-change DOM.

This is by design: Lit treats post-render state changes as a new update to avoid infinite render loops. The warning message confirms this.

### Fix

Move derived state computation from `updated()` to `willUpdate()`:

```typescript
// Before — broken in tests
override updated(changed: Map<string, unknown>) {
  if (changed.has('messages') && this.messages.length > this._prevMessageCount) {
    if (this._scrolledUp) {
      this._unreadCount += newCount;  // triggers second render
    }
  }
}

// After — single render cycle
override willUpdate(changed: Map<string, unknown>) {
  if (changed.has('messages') && this.messages.length > this._prevMessageCount) {
    if (this._scrolledUp) {
      this._unreadCount += newCount;  // applied before render
    }
  }
}
```

`willUpdate()` runs *before* `render()` in the same update cycle. State changes there are included in the current render — no second cycle, no race with `updateComplete`.

Keep DOM-dependent logic (scroll position checks, `requestAnimationFrame` calls) in `updated()` — only move pure state derivation to `willUpdate()`.

### Why this is non-obvious

The Lit docs describe `updated()` as the place for "work that requires the updated DOM" but don't prominently warn that setting reactive properties there causes a second cycle. The dev-mode warning appears in the console but doesn't explain the testing consequence. The fix (using `willUpdate()` for derived state) requires understanding the distinction between "needs DOM" and "needs changed-property info" — both are available in `willUpdate()`, but the DOM there reflects the *previous* render.
