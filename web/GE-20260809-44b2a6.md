### Symptom
Floating frames always appear at position (0,0) on page load despite correct saved positions. The save data has correct coordinates, `addPanel({floating: {x: 300, y: 200}})` is called with correct values, but the overlay renders at the top-left corner.

### Context
`DockviewComponent` is constructed in Lit's `firstUpdated()` callback. At this point, the container element exists in the DOM but the browser has NOT yet performed a layout pass. `getBoundingClientRect()` on the container returns `{width: 0, height: 0}`. Dockview's internal `ResizeObserver` hasn't fired yet. When `addPanel({floating: {x, y}})` is called, Dockview clamps the position to its known container dimensions — which are zero.

### What was tried (didn't work)
- Reading and re-applying overlay positions after save (the positions were already clamped)
- Event-driven position tracking via `onDidChangeEnd` (correct architecture but didn't fix the initial restore)
- Guards in `_syncFrameBoundsFromDockview` for zero values (the problem was in creation, not in reading)
- Removing `beforeunload` save to prevent corruption (the save was fine — the restore was the issue)

### Root cause
Dockview clamps floating group positions to the container's known dimensions. The container dimensions are zero when DockviewComponent is initialized in `firstUpdated` — the browser layout pass hasn't happened yet, and Dockview's ResizeObserver hasn't fired.

### Fix
Delay `_restoreLayout()` by two `requestAnimationFrame` calls to ensure the browser has performed a layout pass and Dockview's ResizeObserver has updated the internal container size.

```typescript
override firstUpdated() {
    this._container = this.shadowRoot!.querySelector('.dockview-container');
    this._initDockview();
    // Two rAFs: first for browser layout, second for ResizeObserver callback
    requestAnimationFrame(() => requestAnimationFrame(() => this._restoreLayout()));
}
```

### Why this is non-obvious
`firstUpdated` feels like the right lifecycle hook — the DOM exists, the element is connected. But Lit's rendering and the browser's layout pass are decoupled. The zero-dimension clamping is silent — no error, no warning, the frame just appears at (0,0). Debugging the save path (which is correct) instead of the restore path cost 2 days.

### Why this fix
A single `requestAnimationFrame` is insufficient — it fires before `ResizeObserver` callbacks. The double-rAF ensures: (1) browser layout pass completes, (2) ResizeObserver fires and updates Dockview's internal state, (3) `addPanel` receives non-zero container dimensions.
