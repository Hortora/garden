### What developers would normally do
Enable ECharts `aria.enabled` individually in each chart subclass's `buildOption()` method — 12 chart wrappers, 12 identical additions. Or add it via a shared utility function called from each subclass.

### The technique
Inject `aria: { enabled: true, decal: { show: false } }` into the ECharts option object in the abstract base class's `updated()` method, in the `apply` callback that runs just before `chart.setOption()`. One change point covers all chart subclasses.

```typescript
// PagesChartElement.ts — the abstract base
const apply = (option: Record<string, unknown>): void => {
  if (this._renderGen !== gen) return;
  option['backgroundColor'] = 'transparent';
  option['aria'] = { enabled: true, decal: { show: false } };
  chart.setOption(option, true);
};
```

The same `updated()` hook can set `role="img"` and `aria-label` on the host element from `props.title`, giving every chart wrapper a consistent ARIA presence without per-subclass code.

### Why this is non-obvious
The `apply` callback in `PagesChartElement.updated()` already mutates the option object (setting `backgroundColor`). It's the natural injection point, but the pattern isn't documented — ECharts' own docs describe `aria.enabled` as a per-chart option, not something you'd centralise in a base class. The key insight is that `option` is a mutable object passed by reference, so mutations in the base class's apply callback propagate to all subclasses without any override mechanism.
