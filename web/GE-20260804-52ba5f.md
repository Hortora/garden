## SSE addEventListener for named events silently ignores unnamed server events

### Symptom

Frontend uses `eventSource.addEventListener('agent:state', handler)` to listen for SSE events. The SSE connection succeeds, events arrive at the browser (visible in DevTools Network tab), but the handler never fires. The UI stays in its initial state (e.g. "starting...") indefinitely.

### Context

A Quarkus backend sends SSE events via `sse.newEvent(data)` (JAX-RS SseEventSink), which produces unnamed events — only a `data:` field, no `event:` field in the wire format:
```
data: {"topic":"agent:state","payload":{...}}

```

Three frontend views subscribed to these events. Two used `addEventListener('agent:state', ...)`, one used `onmessage`. Only the `onmessage` view received updates.

### Root cause

The EventSource API dispatches events differently based on whether the SSE message has an `event:` field:

- **With `event: agent:state`** → dispatches to `addEventListener('agent:state', handler)`
- **Without `event:` field** → dispatches to `onmessage` (the default "message" event type)

`addEventListener('agent:state', ...)` only fires for events explicitly named `agent:state` in the SSE stream. Unnamed events (data-only) are "message" events — `addEventListener` for a custom name silently ignores them.

### Fix

Use `onmessage` for unnamed SSE events:

```typescript
// Broken — handler never fires for unnamed events
eventSource.addEventListener('agent:state', () => handleUpdate());

// Working — fires for all unnamed events
eventSource.onmessage = () => handleUpdate();
```

If you need to distinguish event types within `onmessage`, parse the `topic` field from the JSON payload:

```typescript
eventSource.onmessage = (e) => {
  const data = JSON.parse(e.data);
  if (data.topic === 'agent:state') handleStateUpdate();
  if (data.topic === 'agent:eviction') handleEviction(data);
};
```

### Why this is non-obvious

The connection succeeds, events arrive, and DevTools shows data flowing. There is no error, no warning, and no indication that the handler is mismatched. The `addEventListener` API accepts any string as an event name — it doesn't validate against what the server sends. The mismatch between "I registered a listener" and "events are arriving" creates a debugging blind spot where the developer looks at the wrong layer (network, server, serialization) rather than the event dispatch mechanism.

### Alternatives considered

- Adding `event: agent:state` to the server-side SSE messages — works but requires changing the shared push infrastructure, which other consumers depend on
- Using `addEventListener('message', ...)` — equivalent to `onmessage` but more verbose
