### Symptom
A custom component type with `slots: { default: [child] }` renders its children
immediately, even when the activation callback (`onNode`) returns early intending
to defer rendering.

### Context
Creating a `deferred` wrapper component that stores children for later rendering
via a DOM event. The wrapper has `slots.default` containing the child to defer.
The activation callback sets up a one-shot event listener and returns — expecting
children to remain unrendered until the event fires.

### What was tried (didn't work)
Relying on the component being a non-layout type to prevent child rendering.
The assumption: since the type is not in `LAYOUT_TYPES`, `renderNode` would
skip slot processing. This is wrong.

### Root cause
`renderNode` (render.ts) recurses into children at line 104 whenever
`component.slots` exists. The gate is `LAZY_TYPES.has(component.type)` (line
107), NOT `isLayoutType()`. `LAYOUT_TYPES` only controls CSS application via
`applyLayoutCSS` (line 55).

The activation callback fires at line 89 (`onNode?.(el, component)`) — BEFORE
slot processing (lines 104-138). The callback's `return` statement exits the
callback function, not `renderNode`. After the callback returns, `renderNode`
continues to create slot containers and render children into them.

The `lazy-page` pattern (often cited as precedent) works only because
`lazy-page` components have `props` but no `slots`, so the slot-recursion
branch at line 104 is never entered.

### Fix
Add the new type to the `LAZY_TYPES` set in render.ts:

```typescript
const LAZY_TYPES = new Set([
  "tabs", "pills", "sidebar", "carousel", "stack", "tree", "menu", "tiles",
  "deferred"  // render-once-keep-forever semantics
]);
```

`wireInteractivity` is called with a `LazyConfig` but returns without action
for unrecognized types (no matching `case` in the switch). The activation
callback reads children from `component.slots.default` independently and
handles deferred rendering via a `pages-deferred-render` DOM event.

### Why this is non-obvious
The naming `LAYOUT_TYPES` vs `LAZY_TYPES` implies that layout types control
structural behavior (including child rendering). A developer reading the code
would reasonably assume that non-layout types skip the slot-rendering branch
entirely — they don't. `LAYOUT_TYPES` controls CSS; `LAZY_TYPES` controls
child recursion. These are independent concerns with misleading names.

### Alternatives considered
- Adding a separate `SKIP_CHILDREN_TYPES` set — rejected as redundant when
  `LAZY_TYPES` already gates the exact code path needed.
- Checking `component.type === "deferred"` inline in `renderNode` — rejected
  as less composable than the set-based approach.
