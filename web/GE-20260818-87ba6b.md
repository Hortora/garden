### Symptom

An `aria-check` build validation script reports 100% ARIA compliance, but some components have no host-level ARIA attributes. External consumers (parent ARIA trees, screen readers navigating the outer DOM, Playwright accessibility snapshots) see these components as unlabelled generic elements.

### Context

Web component monorepo with a CI script that validates ARIA by grepping each component's `.ts` source file for `role=` or `aria-` patterns. Components that set ARIA only on internal shadow DOM elements (e.g. `<div role="region">` inside the template) pass the grep check despite having no ARIA on the host element (`<my-component>` tag).

### What was tried (didn't work)

Trusting the `aria-check` script's "103/103 pass" result as proof of full ARIA coverage. The script found `role=` patterns inside Lit `html` template literals and counted them as ARIA-compliant, even though these attributes land on shadow DOM children — not the host element.

### Root cause

Source-level grep conflates two different ARIA contexts:

1. **Host-level ARIA** (`this.setAttribute('role', ...)` in `connectedCallback()`) — visible to the outer DOM tree, screen readers, and testing frameworks
2. **Internal ARIA** (`<div role="region">` in the shadow DOM template) — only visible within the shadow root

Both are valid and serve different purposes, but a grep for `role=` matches both indiscriminately. Components using only approach #2 pass validation but are invisible to anything querying the outer DOM.

### Fix

Validate host-level ARIA separately from internal ARIA:

```javascript
// Check for host-level ARIA (connectedCallback pattern)
const hasHostAria = /this\.setAttribute\s*\(\s*['"](?:role|aria-)/.test(source);

// Check for internal template ARIA (still valid, but different purpose)
const hasInternalAria = /(?:role|aria-)=/.test(source);

if (!hasHostAria && hasInternalAria) {
  warn(`${file} has internal ARIA but no host-level ARIA — external consumers won't see it`);
}
```

Alternatively, use axe-core or Playwright accessibility tree snapshots in CI — these test the rendered DOM, not the source, so they catch the distinction naturally.

### Why this is non-obvious

The grep approach is simple, fast, and works for the majority of components that set ARIA via `this.setAttribute()` in `connectedCallback()`. The false positive only appears for components that use template-level ARIA (a valid pattern for internal structure), and the result looks correct — "103/103 pass" gives no signal that 12 components have a different ARIA strategy that needs separate verification.
