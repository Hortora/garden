## Context

An IntelliJ-style dock layout (centre content + collapsible panels on left/right/bottom edges) is a common requirement for workbench applications. The natural approach is to build a `<dock-workbench>` Web Component that manages all the layout, state, and panel toggling internally.

## Technique

Instead of a monolithic component, Pages decomposes the dock workbench into three small, independently useful primitives plus a DSL builder:

1. **`exclusive` prop on `dockBar`** — clicking button B while A is active dispatches two synchronous events: hide-A, show-B. The dock bar buttons ARE the tabs — no separate tab bar inside the zone.

2. **`deferred` component type** — render-once-keep-forever semantics. Children don't render until first panel open (via `pages-deferred-render` event), then stay in DOM. Added to `LAZY_TYPES` set so `renderNode` skips children initially. ~15 lines of activation code.

3. **Component-level dock-toggle with cascading collapse** — hides the component element directly (not the slot), then cascades upward: all siblings hidden → hide slot → all slots hidden → hide parent. Zone collapse is emergent, not special-cased.

The `dockWorkbench(config)` builder then generates a tree of existing types (`rows`, `columns`, `split`, `dockBar`, `deferred`, `withId`). No new rendering path. The standard `renderComponent()` pipeline processes everything.

```typescript
const workbench = dockWorkbench({
  storageKey: 'my-app',
  centre: hostPanel('main-content'),
  left: [
    { key: 'nav', label: 'Nav', icon: 'menu', defaultOpen: true,
      content: hostPanel('nav-tree') },
  ],
  right: [
    { key: 'props', label: 'Properties', icon: 'settings',
      content: hostPanel('property-editor') },
  ],
});
```

State persistence falls out naturally — `LayoutState` already tracks `docks` (booleans) and `splits` (ratios). Zero new persistence code.

## Why this is non-obvious

The natural instinct is to build a `<dock-workbench>` component with its own shadow DOM, internal state, and custom rendering. The decomposition approach — no new Web Component, just a builder that generates a tree of existing primitives — is counterintuitive but produces better composability, no duplicated rendering logic, and immediate state persistence via existing infrastructure.
