## Symptom

After a `runTo` operation (which sets speed to 10x for fast-forwarding), subsequent steps execute at the fast speed even though the orchestrator sent a speed-reset control message. Spotlights are skipped and text fills instantly — the executor behaves as if still in fast mode.

## Context

The scenario engine uses a push-wire (WebSocket) protocol between the Java orchestrator and browser executor. Two message types control the executor:

- `executor-control` — point commands: pause, resume, step, speed
- `dispatch-sequence` — step payloads with commands to execute; carries `speed` and `paused` fields reflecting the orchestrator's state at dispatch time

The executor's `onDispatch` handler was setting `speed = detail.speed` on every incoming dispatch. During `runTo`, the orchestrator dispatches steps at speed=1000. Even after the orchestrator resets speed to 1.0 via a control message, the next dispatch-sequence arrives with `speed=1000` (captured at dispatch time) and overrides the reset.

## What was tried

- Sending speed-reset control messages before dispatching triggered steps — the dispatch still overrode the control
- Changing dispatch order (control before dispatch) — race condition persisted

## Root cause

The `onDispatch` handler treated every dispatch-sequence as authoritative for speed/paused state. But dispatch messages are queued with a delay (trigger delays in the YAML). By the time they arrive, the orchestrator's speed may have changed. The dispatch carries a stale snapshot.

## Fix

Only set `speed` and `paused` from the dispatch message when the session ID changes (new scenario start). Within the same session, speed is controlled exclusively by `executor-control` messages:

```typescript
function onDispatch(e: Event): void {
    const detail = (e as CustomEvent).detail as DispatchSequence;
    const isNewSession = sessionId !== detail.sessionId;
    sessionId = detail.sessionId;
    if (isNewSession) {
        paused = detail.paused;
        speed = detail.speed;
    }
    stepQueue.push(...detail.steps);
    void executeSequence();
}
```

### Why this is non-obvious

The dispatch-sequence message legitimately carries speed/paused for the initial dispatch (when the scenario starts). The bug only manifests when speed changes mid-scenario (runTo) and triggered steps arrive with stale speed values. Normal play/step workflows never change speed, so the bug is invisible in the common case.
