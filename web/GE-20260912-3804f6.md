### The technique

When building a visual editor for YAML documents (drag-and-drop builders,
property panels, outline trees), the standard approach is to build a typed
semantic model, edit it, and serialize back to YAML. This loses comments,
whitespace, and author formatting — every save reformats the file.

The CST-backed facade holds a **live `Document` object** (from `parseDocument()`)
as the single source of truth. Typed node classes (e.g. `PageNode`, `ComponentNode`)
hold CST paths into the document and delegate reads/writes directly to
`Document.getIn()` / `Document.setIn()` / `Document.deleteIn()`.

```typescript
class ComponentNode {
  constructor(private doc: Document, readonly path: readonly (string | number)[]) {}

  get type(): string {
    return String(this.doc.getIn([...this.path, 'type']) ?? '');
  }

  setProperty(key: string, value: unknown): void {
    this.doc.setIn([...this.path, 'properties', key], value);
  }
}
```

### Why use this over a semantic model

| Concern | Semantic model | CST facade |
|---------|---------------|------------|
| Comments | Lost on round-trip | Preserved |
| Whitespace/formatting | Reformatted | Preserved |
| Source of truth | Model + serialize | CST only |
| Divergence risk | Model ↔ YAML can drift | None — one truth |
| Bidirectional sync | Parse → update model → serialize | Both views read/write same CST |
| Structural operations | Clean API on model | Needs path manipulation |

### Bidirectional sync pattern

```
Visual edit → facade.setProperty() → Document mutation → onChange fires
  → code editor receives Document.toString() (diff-applied)

Text edit → code editor input → debounced re-parse via parseDocument()
  → facade holds new Document → tree re-renders from CST
```

### Undo/redo with string snapshots

Each facade mutation pushes `Document.toString()` onto a string stack.
Undo replaces the Document by re-parsing the snapshot. For typical
config YAML (5–50KB), `parseDocument()` completes in <1ms — string
snapshots are simpler and correct compared to operational transform.

### Extension to multiple document types

The facade pattern extends to any YAML document type — each gets its own
facade class (`CaseDocument`, `OrgDocument`, `PatternDocument`) providing
typed accessors while sharing the same CST mutation infrastructure. A
project graph aggregates facades across files for cross-reference
validation and rename refactoring.

### Why this is non-obvious

Most developers building visual editors for structured text reach for a
semantic model first — it's the pattern from every GUI framework tutorial.
The CST facade trades structural operation ergonomics (which are solvable
with path helpers) for format preservation (which is unsolvable after the
fact). The key insight is that the `yaml` library's `Document` API is
already a typed tree — wrapping it with domain accessors is thin, not a
second model.

### Why this fix

A semantic model requires maintaining parity between the model's type
system and the YAML schema, handling serialization edge cases, and losing
author formatting. The CST facade avoids all three by not having a second
representation — the YAML IS the model. The only cost is that structural
operations (move a component between containers) require path arithmetic,
which is a bounded problem.
