# Lazy resolve closures in property sources to survive document-instance swaps

### Symptom
After undo/redo or an editor flush that swaps the document instance, the property panel continues showing stale data — or worse, mutation closures (onChange) write to the old document, which is no longer the active model.

### Context
A property panel renders fields from a `source` object with `get data()` (reads current values) and `onChange(field, value)` (writes mutations). The source is created when the user selects a tree node. If undo/redo replaces the document instance, the captured node references inside the source point to the old document.

### What developers usually try
1. Re-create the property source after every undo/redo — works but requires explicit call sites everywhere the document changes
2. Store the document reference in the source — still captures one reference that goes stale
3. Subscribe to document changes and refresh — adds complexity and another notification path

### Root cause
Property source closures capture node references eagerly at selection time. These references are valid for in-place mutations but become stale when the document instance is swapped (undo, redo, editor flush all create a new PageDocument from a YAML string).

### Fix
Replace direct node captures with lazy `resolve()` functions that look up nodes from `this._document` at execution time:

```typescript
const resolve = () => this._findComponentAtPath(path);
const node = resolve();
if (!node) { this._propertySource = undefined; return; }

this._propertySource = {
  schema: addBlankEnumOptions(node.getSchema()),
  get data() { return resolve()?.getProperties() ?? {}; },
  onChange: (field, value) => {
    this._applyEdit('properties', () => {
      const n = resolve();
      if (!n) return;
      n.setProperty(String(field[0]), value);
    });
  },
};
```

Call `_resolvePropertySource()` from the view sync fan-out (`_syncViews`) so property sources are rebuilt on every mutation — not just on selection change.

### Why this is non-obvious
Eager capture works correctly for in-place mutations (the common case). The stale-reference bug only surfaces after undo/redo — a less-tested path. The symptom (property panel shows wrong data, mutations go to the wrong document) is confusing because the property panel "looks right" until you inspect the model.
