## `npx --prefix` sets module resolution path but does NOT change working directory

### Symptom
`npx --prefix /path/to/project vitest run` finds and runs vitest, but vitest uses default configuration instead of the project's `vitest.config.ts`. Test discovery scans from the wrong root directory.

### Context
Running `npx --prefix /path/to/webui vitest run` from a project root like `/project/`. The `--prefix` flag tells npx where to find `node_modules/.bin/vitest`, but vitest itself runs with `process.cwd()` still set to `/project/` — not `/path/to/webui/`.

### Root cause
`npx --prefix` only affects npm's module resolution — it sets the path where npx looks for binaries and packages. It does NOT change the working directory of the spawned process. Tools that resolve configuration files from `process.cwd()` (vitest, vite, eslint, etc.) will not find their config at the prefix path.

### Fix
Either use a wrapper script that changes directory first:

```bash
#!/bin/bash
cd /path/to/webui
node_modules/.bin/vitest run
```

Or pass the config path explicitly:

```bash
npx --prefix /path/to/webui vitest run --root /path/to/webui
```

Or use the local binary directly after `npm install`:

```bash
/path/to/webui/node_modules/.bin/vitest run
```

### Why this is non-obvious
`--prefix` sounds like it sets the project context — a developer would reasonably expect the tool to behave as if running from that directory. The npm docs describe `--prefix` as "the location to install global items" which doesn't clarify its effect on spawned process cwd.
