## EventConnection from pages-data doesn't expose eventTarget

### Symptom
A Lit component receives an `EventConnection` for push wire communication but cannot receive dispatched events. The connection's `listen()` succeeds, but no `pages-event` CustomEvents are ever received by the component. The component has no way to add an event listener for push wire events.

### Context
`createEventConnection()` accepts `PushSourceConfig.eventTarget` — a DOM `EventTarget` where incoming push wire events are dispatched as `CustomEvent('pages-event', { detail })`. This eventTarget is an internal implementation detail — the `EventConnection` interface exposes only `send()`, `listen()`, `unlisten()`, `close()`, `connected`, and `status`. No public accessor for the eventTarget.

Components that share a host page's existing EventConnection (embedded mode) cannot discover where events are dispatched. They must receive the eventTarget through a separate channel.

### Root cause
The `EventConnection` interface was designed for push wire subscription management (listen/unlisten), not for event consumption. Event consumption happens via DOM event listeners on the eventTarget, which is passed at creation time but not exposed on the interface.

### Fix
Accept `eventTarget` as a separate parameter alongside `connection`, matching the pattern established by `createScenarioHandler(connection, eventTarget)` in `pages-aria/src/server/scenario-handler.ts`.

For Lit components:
```typescript
@property({ attribute: false }) connection?: EventConnection;
@property({ attribute: false }) eventTarget?: EventTarget;
```

For remote/standalone mode (component creates its own connection), create a private `EventTarget` internally:
```typescript
private _ownEventTarget = new EventTarget();
this._ownConnection = createEventConnection(wsUrl, {
  config: { eventTarget: this._ownEventTarget },
});
```

### Why this is non-obvious
The `EventConnection` API looks complete — `listen()` appears to subscribe to topics and the connection handles everything. A developer expects that calling `listen(['topic'])` means they'll receive events through some callback or property on the connection. The silent gap between "subscribed" and "no events received" is the trap. The fix (pass eventTarget separately) requires knowing the internal architecture of `createEventConnection`.

### Alternatives considered
- Extending EventConnection interface to expose eventTarget — cleaner API but a breaking change to the sealed interface
- Listening on `document` for composed events — only works if the eventTarget is a DOM node in the document tree, not a standalone EventTarget
