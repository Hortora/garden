### Symptom

Frame positions don't persist across page refresh. After creating frames and dragging them to new positions, refreshing the page restores frames at their original creation positions, not where the user placed them.

### Context

The FloatingFrameEngine manages frame state (position, size, z-index, tabs). The DockviewBackend fires `onFrameMove`/`onFrameResize` callbacks when the user drags or resizes. But the engine's internal `frames` map is never updated — it retains the positions from `createFrame()` time.

### Root cause

The engine has no `updatePosition`/`updateSize` methods. The backend reports position changes via callbacks, but there's no path from those callbacks back into the engine's state. When `captureLayout()` is called for persistence, it returns the engine's stale internal positions.

### Fix

Maintain live position/size caches in the host component, populated from backend event callbacks. Prefer cached values over engine values when serializing:

```typescript
private _livePositions = new Map<string, { x: number; y: number }>();
private _liveSizes = new Map<string, { width: number; height: number }>();

// In _initEngine:
backend.onFrameMove((key, pos) => { this._livePositions.set(key, pos); this._scheduleSave(); });
backend.onFrameResize((key, size) => { this._liveSizes.set(key, size); this._scheduleSave(); });

// In _serializeLayout:
position: this._livePositions.get(f.key) ?? f.position,
size: this._liveSizes.get(f.key) ?? f.size,
```

Clean up caches on hideFrame/deleteFrame.

### Why this is non-obvious

The engine API appears complete — `captureLayout()` returns `FrameLayout[]` with position and size fields. The values look plausible (they're the creation-time positions). The bug only surfaces after drag + refresh, and the symptom is "wrong position" not "missing data".
