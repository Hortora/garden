## Symptom

A ts-morph code generator emits `z.object({}).optional()` for a property typed as `unknown?`, instead of the expected `z.unknown().optional()`. The generated Zod schema rejects valid data that should be accepted.

## Context

TypeScript interfaces with intentionally open-ended optional properties:

```typescript
export interface SwfDocumentYaml {
  document?: SwfDocumentInfo;
  input?: unknown;    // should generate z.unknown().optional()
  output?: unknown;   // should generate z.unknown().optional()
  use?: unknown;      // should generate z.unknown().optional()
}
```

The generator handles optional properties by calling `type.getNonNullableType()` to strip `undefined` before mapping the base type to Zod.

## Root cause

`getNonNullableType()` on `unknown` returns `{}` (the empty object type), not `unknown`. TypeScript defines `NonNullable<unknown>` as `{}` because `unknown` includes `null | undefined`, and stripping those leaves the empty object type.

When the generator calls `typeToZod(baseType)` on this `{}` result, it hits the object branch and emits `z.object({})` — completely losing the `unknown` semantics.

## Fix

Check for `unknown` before calling `getNonNullableType()`:

```typescript
const typeText = type.getText();
if (typeText === 'unknown' || typeText === 'unknown | undefined') {
  const suffix = prop.isOptional() ? '.optional()' : '';
  return `${safeName}: z.unknown()${suffix}`;
}

const isOptional = prop.isOptional();
const baseType = isOptional ? type.getNonNullableType() : type;
```

## Why this is non-obvious

`getNonNullableType()` is semantically correct — `NonNullable<unknown>` IS `{}` in TypeScript's type algebra. But in code generation, this transformation silently changes the Zod output from "accept anything" to "accept only empty objects". The generated code compiles and runs without error — the failure is only visible when valid data (e.g. a complex nested object) is rejected at parse time.
