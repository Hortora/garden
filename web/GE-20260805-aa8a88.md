### Symptom

Integrity check comparing yamlPaths count against GraphModel node count reports a mismatch — more nodes than paths. For a simple 4-step workflow: "yamlPaths/model mismatch: 4 paths for 8 task nodes". The graph renders correctly; the mismatch is in the correlation logic.

### Context

When building a domain adapter that uses `@openworkflowspec/sdk`'s `buildFlatGraph()` for graph construction and a separate YAML CST walk for path tracking. The integrity assertion after both walks compares node counts.

### Root cause

`buildFlatGraph(workflow, true)` generates structural container nodes that have no corresponding YAML task items:

- `root` (type=root) — the root graph container
- `root-entry-node` (type=start) — workflow start boundary
- `root-exit-node` (type=end) — workflow end boundary
- Container nodes for nested structures: `try` (type=try), `catch/do` (type=catch)
- Sub-graph boundaries: `entry`/`exit` nodes within try/for/fork blocks

These are graph-construction artefacts for layout and rendering. They don't correspond to `do:` array task items in the YAML and have no editable properties.

### Fix

Filter synthetic types before comparing against yamlPaths:

```typescript
const SYNTHETIC_TYPES = new Set(['start', 'end', 'entry', 'exit', 'root', 'try', 'catch']);

const taskSdkNodes = allSdkNodes.filter(n => !SYNTHETIC_TYPES.has(n.type));

if (yamlPaths.size !== taskSdkNodes.length) {
  // genuine mismatch — degrade gracefully
}
```

Run this assertion **before** type prefixing (e.g. before mapping `call` → `swf-call`), since `SYNTHETIC_TYPES` contains unprefixed SDK values.

### Why this is non-obvious

The SDK's `FlatGraph` type definition shows `nodes: FlatGraphNode[]` with no indication that some nodes are structural containers rather than task representations. The `GraphNodeType` enum includes `Root`, `Start`, `End`, `Entry`, `Exit`, `Try`, `Catch` alongside task types like `Call`, `Set`, `Switch` — they look like peers. Only empirical testing reveals which types have YAML counterparts and which are SDK-generated structural nodes.

### Why this fix

Filtering before comparison (rather than excluding from the graph entirely) preserves the structural nodes for layout — ELK uses them for proper graph hierarchy and boundary rendering. The integrity check only needs to validate task-node/path correlation; structural nodes are irrelevant to that concern.

### Alternatives considered

- Excluding synthetic nodes from the GraphModel entirely — breaks ELK layout which expects parent/boundary nodes for correct hierarchy rendering
- Including synthetic nodes in yamlPaths with dummy paths — masks real mismatches; defeats the purpose of the integrity check
