### Symptom
The first tab in a casehub-pages `tabs()` layout shows "No data" in its `dataTable`,
while subsequent tabs (using the same dataset) render data correctly. Clicking away
from the first tab and clicking back renders the data.

### Context
Any casehub-pages application using `tabs()` with data-bound components (`dataTable`,
`hostPanel`) on the first tab. Observed in scaffold console but applies to devtown
and clinical equally.

### What was tried (didn't work)
- Checked REST endpoint responses — data returned correctly
- Verified dataset configuration (`dataPath`, `refreshTime`) — all correct
- Suspected a timing issue with data fetching — REST sources fetch immediately on `connect()`
- Compared first tab columns (`col("caseId")`) vs Orchestration tab columns (`col("id")`) —
  both reference the same `"cases"` dataset

### Root cause
`renderInitialSlot()` in `packages/pages-component/src/renderer/interactive.ts` (line ~344)
makes the first tab visible via `applyOneVisible()` but **never dispatches a `pages-slot-change`
event**. The `swap()` function (line ~380), called on user clicks, DOES dispatch the event.

In `packages/pages-runtime/src/site.ts` (line ~497), the `pages-slot-change` listener
populates the `activeSlots` map and calls `computeCurrentPage()`. Without the event,
`activeSlots` is never populated for the first tab, so `computeCurrentPage()` returns
an empty string. Data bindings that depend on page context don't initialise.

### Fix
After `loadSite()`, explicitly navigate to the first tab when there's no URL hash:

```typescript
const site = await loadSite(container, app);
if (!location.hash) {
  site.navigate("Cases"); // or whatever your first tab label is
}
```

This triggers `swap()` → `pages-slot-change` → `activeSlots` populated → data bindings work.

### Why this is non-obvious
The symptom ("No data") points toward data fetching or dataset configuration. REST sources
DO fetch immediately on `connect()`, so the data is available — the problem is entirely in
the tab activation event lifecycle, two abstraction layers deeper. The fact that clicking
away and back fixes it is a strong clue, but only once you know about `pages-slot-change`.

### Why this fix
`site.navigate()` is the intended API for programmatic tab switching and correctly fires
all lifecycle events. The alternative — patching `renderInitialSlot()` in the framework —
would fix it at the source but requires a framework release. The app-level workaround is
immediate and safe.

### Alternatives considered
- **Framework fix** — modify `renderInitialSlot()` to dispatch `pages-slot-change`. Correct
  but requires a casehub-pages release and affects all consumers.
- **Default hash** — set `location.hash = "#/cases"` before `loadSite()`. Fragile — couples
  to the URL routing format and may conflict with pages' own URL management.
