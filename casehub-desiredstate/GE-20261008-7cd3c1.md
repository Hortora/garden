## Symptom

Drift exemption appears granted — `ExemptionStore.get(tenancyId, nodeId)` returns the exemption — but `ReconciliationLoop` still reconciles the device. The exemption is silently ignored. No error, no warning logged.

## Context

When granting drift exemptions programmatically (e.g. from a `TriggerDriftOverrideObserver` that watches trigger events and pre-emptively exempts devices), the `NodeId` used in `ExemptionStore.grant()` must exactly match the `NodeId` that `ReconciliationLoop.detectDrift()` uses to look up exemptions.

## What was tried (didn't work)

Using `NodeId.of(deviceId)` (bare device ID, e.g. `NodeId.of("light-1")`) to grant the exemption. The store accepts it, the exemption is persisted, but the reconciliation loop never finds it.

## Root cause

Three files establish a naming convention that must stay in sync:

1. **IoTEventSource** (line 51): emits capability-change drift as `NodeId.of(deviceId + "-config")` — this is the NodeId the ReconciliationLoop sees as DRIFTED
2. **IoTGoalCompiler** (line 58): creates config nodes with `NodeId.of(goal.deviceId() + "-config")` — this is the NodeId stored in the DesiredStateGraph
3. **ReconciliationLoop.detectDrift()**: looks up exemptions using the NodeId from the DesiredNode — which is the `-config` suffixed version

If you grant an exemption with bare `NodeId.of(deviceId)`, it never matches the lookup key. The ExemptionStore has the entry under key `light-1`, but the loop looks for `light-1-config`.

## Fix

Always use `NodeId.of(deviceId + "-config")` when granting exemptions for device capability drift:

```java
// Wrong — exemption exists but is never found
NodeId nodeId = NodeId.of(target.deviceId());
exemptionStore.grant(tenancyId, nodeId, exemption);

// Right — matches IoTEventSource and IoTGoalCompiler convention
NodeId nodeId = NodeId.of(target.deviceId() + "-config");
exemptionStore.grant(tenancyId, nodeId, exemption);
```

The `-config` suffix convention is established by `IoTEventSource` and `IoTGoalCompiler`. Any code that interacts with `ExemptionStore` for capability drift must match it.

Note: for physical device availability drift (device goes offline), `IoTEventSource` uses bare `NodeId.of(deviceId)` (line 48). The suffix depends on what kind of drift you're exempting.

### Alternatives considered

- Adding a helper method to IoTNodeTypes that constructs the correct NodeId for a given drift type — would centralise the convention but adds API surface for a simple string concatenation.

## Why this is non-obvious

- The symptom is actively misleading: the exemption IS in the store (you can verify with `ExemptionStore.get()`), so it looks like the reconciliation loop is ignoring exemptions entirely
- The naming convention is split across 3 files in 2 modules with no shared constant or documentation
- No error is thrown — `ExemptionStore.get()` with the wrong key simply returns `Optional.empty()`, and the loop treats "no exemption" as "reconcile"
- The `-config` suffix is an implementation detail of how `IoTGoalCompiler` creates two-node-type graphs (physical + config) for physical devices
