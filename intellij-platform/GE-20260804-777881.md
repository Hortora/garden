### Symptom
Java compilation fails with `illegal character: '\'` errors at column positions
where newlines should appear. Source files contain literal `\n` characters on a
single very long line instead of multi-line formatted code.

### Context
When `ide_replace_text_in_file` `replaceText` parameter contains `\n` escape
sequences, the tool writes the literal two-character sequence `\n` instead of
a newline. The tool description states "Passed through as-is (no escape
processing)" which is technically consistent — but misleading because sibling
tools `ide_insert_member` and `ide_edit_member` DO interpret `\n` as newlines
in their content parameters.

### What was tried
Used `ide_replace_text_in_file` for multi-line Java source replacements
(imports, constructors, method bodies) with `\n` in replaceText to separate
lines. Result: 8 source files corrupted with all replacement content on a
single line containing literal `\n` characters.

### Root cause
The tool's replaceText parameter performs no escape processing — `\n` is two
characters (backslash + n), not a newline. Unlike `ide_edit_member` which
processes content through a different pipeline that does interpret escapes.

### Fix
Use the Edit tool with `replace_all: true` for multi-line replacements on
Java source files. The `intellij-first` hook permits this as a
find-and-replace fallback. Alternatively, pass content with actual newlines
in the parameter value (most MCP clients support this).

### Alternatives considered
- Using `ide_edit_member`/`ide_replace_member` — these interpret `\n` correctly but have a separate bug: HTML-escaping angle brackets (`<` → `&lt;`, `>` → `&gt;`) which corrupts Java generics
- Writing a temp file and using `ide_replace_text_in_file` with file-read content — overcomplicated

### Why this is non-obvious
The inconsistency between sibling tools is the trap. `ide_edit_member` and
`ide_insert_member` DO interpret `\n` as newlines, so developers
naturally expect `ide_replace_text_in_file` to behave the same way. The
documentation says "no escape processing" but this is easy to miss when
you've been using the other tools successfully with `\n`.
