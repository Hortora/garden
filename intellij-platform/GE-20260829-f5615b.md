### Symptom

Renaming a Java record field named `confidence` on `ParsedEntity` via `ide_refactor_rename` modified 62 files — including markdown documentation, blog entries, design specs, and ADRs that happened to contain the word "confidence" in prose text.

The rename reported `changesCount: 62` and `success: true`. No warning that non-source files were modified. The damage was only discovered by checking `git diff --name-only`.

### Context

The `relatedRenamingStrategy` parameter defaults to `"all"`, which "automatically rename all related symbols." For record fields with common English names, IntelliJ's related-symbol detection extends to text matches in non-Java files indexed by the project.

### What was tried (didn't work)

Used `ide_refactor_rename` with just `file`, `line`, `column`, and `newName` — relying on the default behavior. The rename was too aggressive.

### Root cause

`relatedRenamingStrategy: "all"` (the default) triggers IntelliJ's full related-rename machinery, which includes text occurrences in comments, strings, and non-source files. For common words, this produces massive false-positive renames across the project.

### Fix

Use `relatedRenamingStrategy: "none"` when renaming symbols whose names are common English words:

```json
{
  "file": "src/main/java/.../ParsedEntity.java",
  "line": 11, "column": 22,
  "newName": "origin",
  "targetType": "symbol",
  "relatedRenamingStrategy": "none"
}
```

After an aggressive rename, immediately check the blast radius:
```bash
git diff --name-only
```

Restore non-source files:
```bash
git restore docs/
```

### Why this is non-obvious

Symbol rename is expected to be semantically scoped — renaming a Java record field should update Java references, not prose text in markdown files. The `relatedRenamingStrategy` parameter exists but defaults to the most aggressive option. The rename completes without any warning about non-source files being modified.

### Alternatives considered

- `relatedRenamingStrategy: "accessors_and_tests"` — renames getters/setters and test classes but still risks text matches in non-Java test resources
- `relatedRenamingStrategy: "ask"` — shows IDE dialog for interactive choice, but MCP sessions can't interact with IDE dialogs
- Using `ide_replace_text_in_file` instead — avoids the related-rename machinery entirely, but doesn't update references across the project
