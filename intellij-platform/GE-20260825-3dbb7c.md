### Symptom

After calling `ide_replace_member` to replace a method body, Java source contains literal `& lt;`, `& gt;`, and `- & gt;` instead of `<`, `>`, and `->`. The file compiles with errors like `> or ',' expected`, `not a statement`, `-> expected`.

### Context

Occurs when the `content` parameter of `ide_replace_member` contains angle brackets (Java generics like `Map<String, Object>`, `Set<String>`) or lambda arrows (`->`). The MCP tool parameter is transmitted as XML, and the XML serialization layer encodes these characters as HTML/XML entities. The tool then writes the encoded entities literally into the source file instead of decoding them.

### What was tried (didn't work)

- Passing generics and lambdas directly in the `content` parameter — produces corrupted source
- Using `&lt;` and `&gt;` XML entities explicitly in the content — the tool double-encodes them

### Root cause

The MCP tool's content parameter goes through XML serialization for transport. Angle brackets and arrow operators are encoded as XML entities (`&lt;`, `&gt;`). The tool writes the encoded form directly to the document instead of decoding the entities back to their original characters.

### Fix

Avoid `ide_replace_member` when the replacement body contains angle brackets or lambda arrows. Use `ide_replace_text_in_file` instead for targeted text substitution — it handles these characters correctly.

If `ide_replace_member` was already called and corrupted the source, fix the damage with `ide_replace_text_in_file`:

```
ide_replace_text_in_file(
  file: "path/to/File.java",
  searchText: "Map<\n    String, Object & gt;\n    rawOutput",
  replaceText: "Map<String, Object> rawOutput"
)
```

### Why this is non-obvious

The corruption is silent — the tool reports success. The error only surfaces at compile time, and the error messages (`> or ',' expected`) don't point to XML encoding as the cause. The multi-line splitting (generics broken across lines) makes the corrupted output hard to visually match to the original content.
