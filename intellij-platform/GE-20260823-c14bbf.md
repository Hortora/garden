## Symptom

Calling `ide_edit_member` with `class: "ProgressService"` and `member: "ProgressService"` to update a constructor replaces the **entire class declaration** — all fields, methods, and inner classes are destroyed. Only the content provided in the `content` parameter survives.

## Context

Java constructors share the name of their enclosing class. The IntelliJ MCP `ide_edit_member` tool resolves the target by matching `member` against all declarations in the class — both the class declaration itself and the constructor declaration share the same name.

When both `class` and `member` are set to the same value, the tool matches the class declaration first (it appears earlier in the candidate list) and replaces it entirely.

## Root cause

The `ide_edit_member` tool lists ambiguous candidates when the member name matches multiple declarations. The class declaration and the constructor are both named identically. Without explicit disambiguation, the tool defaults to the first match — the class declaration.

## What was tried (didn't work)

1. `ide_edit_member(class="ProgressService", member="ProgressService", content="public ProgressService(...) {...}")` — replaced the entire class
2. `ide_edit_member(class="ProgressService", member="ProgressService", line=43, content="...")` — still ambiguous; the tool's error message showed both candidates but the `line` parameter alone didn't resolve the ambiguity

## Fix

Use `parameterCount` to disambiguate the constructor from the class declaration:

```
ide_edit_member(
    class="ProgressService",
    member="ProgressService",
    parameterCount=8,    // <-- matches only the constructor
    content="public ProgressService(Param1 p1, ...) { ... }"
)
```

The class declaration has `parameterCount: null`; the constructor has the actual parameter count. This uniquely identifies the constructor.

**Recovery when the class is already destroyed:** `git restore <file>` to recover from the last committed state. The IDE tool writes directly to disk — there is no undo.

## Why this is non-obvious

The error message ("ambiguous_member") does list both candidates with their kinds (`class` vs `constructor`), but by the time you see it, the replacement has already happened if you didn't notice the ambiguity. A developer would naturally write `member="ClassName"` to target a constructor — the footgun is that it silently matches the class declaration first.

### Why this fix

`parameterCount` is the most reliable disambiguator because it is structurally different between a class (null) and a constructor (N). The `line` parameter should also work but the line numbers shift after edits, making it fragile across multiple tool calls in a session.

### Alternatives considered

- Using `line` parameter: works but fragile — line numbers change after prior edits in the same file
- Using a separate `target_kind` parameter: not supported by the current API
