### Symptom

`ide_edit_member` and `ide_insert_member` report success (`{"success": true}`)
but the file on disk is unchanged. Git commits then capture the old file content.
The change only exists in IntelliJ's in-memory document model.

### Context

When using IntelliJ MCP tools for structural code editing in an agentic workflow
(Claude Code → IntelliJ MCP → git commit), the agent calls `ide_edit_member` to
replace a class body or `ide_insert_member` to add a method. Both tools return
success and the IntelliJ index sees the change — `ide_diagnostics` reports no
errors, `ide_find_references` shows updated signatures.

However, the underlying file on the filesystem is never written. When the agent
subsequently runs `git add` and `git commit`, git reads the filesystem — capturing
the pre-edit file content. The commit silently contains the wrong code.

### What was tried (didn't work)

1. Trusting the `{"success": true}` response and committing — commits contained stale code
2. Running `ide_sync_files` after edits — syncs FROM disk TO IntelliJ (wrong direction)
3. Using `ide_build_project` after edits — builds from IntelliJ's in-memory model, reports success even though disk is stale

### Root cause

The IntelliJ MCP plugin's `ide_edit_member` and `ide_insert_member` modify the
PSI (Program Structure Interface) document model in memory but do not trigger a
file save (`FileDocumentManager.saveAllDocuments()`). The document model and the
filesystem are separate — IntelliJ lazily saves documents on focus loss, autosave
timer, or explicit save action. None of these trigger during headless MCP tool calls.

`ide_replace_text_in_file` uses a different code path — it writes through IntelliJ's
`Document` API which triggers an immediate VFS write. `ide_create_file` writes to the
VFS directly (the file doesn't exist yet, so there's no in-memory model to diverge from).

### Fix

Use `ide_replace_text_in_file` instead of `ide_edit_member` for modifications to
existing files. Use `ide_create_file` for new files. Both persist to disk immediately.

For `ide_replace_text_in_file`, provide the exact text to search for and its replacement:

```java
// Instead of:
ide_edit_member(file, class, member, newContent)  // ⚠️ in-memory only

// Use:
ide_replace_text_in_file(file, searchText=oldContent, replaceText=newContent)  // ✅ persists
```

For new methods/fields, use `ide_replace_text_in_file` to insert before a known
anchor point (e.g. `// --- Helpers ---` or a closing brace pattern).

### Why this is non-obvious

The tool explicitly returns `{"success": true, "message": "Replaced class 'AgentHealth' entirely"}`.
IntelliJ's own diagnostics and index reflect the change. There is zero indication that the
filesystem was not updated. The failure only surfaces when an external tool (git, cat, grep)
reads the file — by which point the agent has moved on and committed wrong code.

### Why this fix

`ide_replace_text_in_file` uses IntelliJ's Document write API which flushes to the VFS
synchronously. It requires knowing the exact text to replace (not just the member name),
which is slightly more verbose but guarantees the file on disk matches what IntelliJ sees.

### Alternatives considered

- **Calling `ide_sync_files` after every edit** — syncs the wrong direction (disk → IntelliJ, not IntelliJ → disk). Does not solve the problem.
- **Using the Edit tool directly** — blocked by project hooks that enforce IntelliJ-first editing on source files. Would work technically but violates the workflow.
- **Verifying file content after each edit** — adds overhead and doesn't fix the root cause; the verification step itself (reading from disk) would reveal the problem but the agent would need to redo the edit with a different tool anyway.
