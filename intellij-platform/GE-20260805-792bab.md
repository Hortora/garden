## Symptom

`ide_build_project` reports 0 errors and `success: true`. Running `mvn compile` on the same project fails with compile errors — constructor signature mismatch, wrong parameter count.

## Context

A SNAPSHOT dependency (`casehub-engine-api`) added a new record component (`violations` parameter on `AgentCandidate`). Maven resolved the updated SNAPSHOT from the remote repository. IntelliJ's internal dependency cache still held the previous SNAPSHOT version (6-param constructor vs 7-param).

## Root cause

IntelliJ and Maven resolve SNAPSHOT dependencies independently. IntelliJ caches resolved JARs in its own module library and does not re-resolve on every build — it uses its internal project sync schedule. Maven resolves from the remote repository based on `updatePolicy` in `settings.xml` (default: daily for SNAPSHOTs). After a remote SNAPSHOT is updated, Maven picks up the new version on next compile while IntelliJ continues using the cached version until the next project reimport or dependency refresh.

## Fix

Always verify compilation with `mvn compile` (or `mvn test-compile` for test sources) rather than trusting `ide_build_project` alone when working with SNAPSHOT dependencies. Treat `ide_build_project` as a fast feedback loop for syntax and obvious errors, not as a definitive compile check.

To force IntelliJ to re-resolve: `ide_reload_project` or manually reimport the Maven project.

## Why this is non-obvious

`ide_build_project` is the natural "does it compile?" check and it runs the full IntelliJ build pipeline. The expectation is that if IntelliJ says "0 errors", the code compiles. The divergence is silent — no warning that the cached JAR differs from what Maven would resolve. The symptom (compile error in Maven, green in IntelliJ) points toward a code bug, not a dependency resolution mismatch.
