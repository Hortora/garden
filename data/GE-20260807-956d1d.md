### Symptom
Need to map application-level long sequence numbers to Redis Stream entry IDs for an append/replay event store pattern.

### Context
Building a durable EventStore SPI implementation backed by Redis Streams. The SPI requires `append(topic, payload) → long seq` and `replay(topic, sinceSeq, limit) → List<StoredEvent>`. Redis Streams use `<millisecondsTime>-<sequenceNumber>` as entry IDs by default, but the application needs clean long-to-ID mapping.

### What was tried
Considered using Redis Sorted Sets (ZADD with seq as score), but this loses Redis Streams' native features: consumer groups (for future cross-node distribution), built-in XTRIM capacity management, and ordered append semantics.

### Root cause / mechanism
Redis Stream IDs accept arbitrary positive integers as the first component. Using `<seq>-0` as explicit IDs maps application longs cleanly to stream entry IDs:
- `XADD key <seq>-0 field value` — append with explicit seq-based ID
- `XRANGE key (<sinceSeq>-0 + COUNT <limit>` — exclusive range maps to `seq > sinceSeq`
- `XTRIM key MAXLEN ~ <max>` — capacity-based trimming works correctly

The critical caveat: `XTRIM MINID` interprets the ID prefix as millisecond timestamps. With seq-based IDs (e.g., `42-0`), MINID treats `42` as epoch milliseconds (January 1, 1970), which silently trims everything or nothing depending on the threshold. This was caught independently by three adversarial design review dimensions.

### Fix
Use `XADD <key> <seq>-0 payload <json> createdAt <epochMillis>` for appends. Use `XRANGE <key> (<sinceSeq>-0 + COUNT <limit>` for replay. For capacity retention, use `XTRIM <key> MAXLEN ~ <max>` (works correctly with any ID format).

For time-based TTL, do NOT use `XTRIM MINID`. Instead, iterate with `XRANGE <key> - + COUNT 100`, check the `createdAt` field value against the threshold, and `XDEL` expired entries. Repeat until a non-expired entry is found. This is O(n) for expired entries but correct with seq-based IDs.

### Why this is non-obvious
The XTRIM MINID incompatibility is silent — it doesn't error, it just produces incorrect trimming because it interprets sequence numbers as timestamps. A developer implementing time-based retention would naturally reach for MINID (it's the documented mechanism) and get silently wrong behaviour. The workaround (XRANGE + XDEL scan) is less elegant but the only correct approach with non-timestamp IDs.

### Alternatives considered
- **Timestamp-based stream IDs**: Natural for XTRIM MINID but loses the clean long seq mapping. Application-level seq would need a separate counter and the stream ID would be decorrelated from the seq.
- **Redis Sorted Sets**: `ZADD` with seq as score, `ZRANGEBYSCORE` for replay. Works but loses Streams' consumer groups, XTRIM, and append-only semantics — important for future cross-node distribution.
- **Redis Lists + Counter**: LPUSH with seq embedded. Replay requires scanning — poor fit for the access pattern.
