### Symptom
Checking `PRAGMA data_version` across independent JDBC connections always reports "unchanged" even after another process (e.g. Python's `worklog.py`) has written and committed new rows.

### Context
A Java service opens a read-only SQLite connection per query via `SQLiteDataSource`. It checks `PRAGMA data_version` on each query, compares against a stored `AtomicLong`, and wants to increment a generation counter when the DB changes externally. The external writer is a Python script using `sqlite3.connect()`.

### What was tried (didn't work)
Stored the `data_version` value from connection A, opened connection B later, compared. The values were always equal even after confirmed external writes. The assumption was that `data_version` tracks database-level mutations — it doesn't.

### Root cause
`PRAGMA data_version` is a **per-connection** counter. It tracks changes that occur while that specific connection is alive. Each new `getConnection()` call creates a fresh SQLite handle that independently computes `data_version` from the current database state. Two connections opened at different times — even if the DB was modified between them — may report the same `data_version` because each connection sees the state at its open time.

### Fix
Use file modification time instead:

```java
private final AtomicReference<FileTime> lastMtime = new AtomicReference<>();

void checkFreshness() {
    var mtime = Files.getLastModifiedTime(dbPath);
    var prev = lastMtime.getAndSet(mtime);
    if (prev != null && !prev.equals(mtime)) {
        generationCounter.increment();
    }
}
```

Near-zero cost (one stat call), works across independent connections, works across processes.

### Why this is non-obvious
The SQLite documentation describes `PRAGMA data_version` as detecting database modifications — a developer naturally reaches for it when building change detection. The per-connection scoping is not prominently documented and only surfaces when using connection-per-query patterns (common in Java JDBC).

### Alternatives considered
- **File mtime** (chosen) — simplest, near-zero cost, works across processes. Resolution is filesystem-dependent (typically 1s on HFS+/APFS).
- **WAL-aware file change counter** — more precise but requires reading WAL internals, not exposed via JDBC.
- **Polling with a dedicated long-lived connection** — `data_version` works correctly on a single connection that stays open, but adds connection management complexity for a read-only service.
