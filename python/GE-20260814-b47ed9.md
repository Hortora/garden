### Symptom

`pytest.raises(InvalidTransition)` does not catch the exception even
though the traceback clearly shows `InvalidTransition` was raised.
Similarly, `isinstance(exc, InvalidTransition)` returns `False` for
an exception that prints as `InvalidTransition`.

### Context

A module `project/lifecycle.py` is importable two ways:

1. `sys.path.insert(0, "project/"); from lifecycle import InvalidTransition`
2. `from project.lifecycle import InvalidTransition`

Production code uses path 1. Test code uses path 2. The exception
class from path 1 is a different Python object than from path 2.

### Root cause

Python's import system keys modules by their dotted name in
`sys.modules`. When `project/` is on `sys.path`, `import lifecycle`
creates `sys.modules['lifecycle']`. When importing via the package,
`from project.lifecycle import ...` creates
`sys.modules['project.lifecycle']`. These are **two separate module
objects** with **two separate copies of every class**.

`isinstance()` and `except` clauses compare by object identity, not
by name. A class from `lifecycle.InvalidTransition` is not the same
object as `project.lifecycle.InvalidTransition`.

### Fix

Ensure test imports and production imports use the same module path:

```python
# Both production and test code use the same import path
import sys
sys.path.insert(0, str(Path(__file__).parent.parent / "project"))
from lifecycle import InvalidTransition  # same object everywhere
```

Or use relative imports consistently within a proper package structure.

### Why this is non-obvious

The traceback shows the same class name. `type(exc).__name__` returns
`"InvalidTransition"`. `str(type(exc))` shows the full module path —
but only if you think to check it. The mismatch is invisible in normal
debugging output. Even experienced Python developers get bitten because
the symptom ("raises was not raised") contradicts what the traceback
shows.

### Alternatives considered

- Catching `Exception` and checking `type(exc).__name__` — works as a diagnostic but defeats the purpose of type-safe exception handling.
- Restructuring into a proper package with `__init__.py` and relative imports — correct long-term fix but requires refactoring the entire import structure.
