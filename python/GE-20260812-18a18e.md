### Symptom
Arrow keys (up/down) navigate a scrollable `RichLog` content area instead of a sibling action panel. App-level `BINDINGS` for `up`/`down` never fire.

### Context
A layout with a side panel (action list) and a `RichLog` content area. The panel defines navigation via app-level BINDINGS. The RichLog has focus by default and has built-in `scroll_down`/`scroll_up` bindings for `down`/`up` keys.

### Root cause
Textual routes key events to the focused widget first. The focused widget's BINDINGS consume the key before the app or sibling widgets see it. App-level BINDINGS only fire if no focused widget handles the key.

### Fix
Three changes required:

1. Make the target panel focusable: `can_focus = True` as a **class variable** (not metaclass syntax)
2. Define BINDINGS on the panel itself, not the app
3. Call `panel.focus()` on mount to give it initial focus

```python
class ActionPanel(Widget):
    can_focus = True
    BINDINGS = [
        ("up", "move_up", "Up"),
        ("down", "move_down", "Down"),
        ("enter", "select_action", "Select"),
    ]
```

Note: `Widget(can_focus=True)` metaclass syntax may not work reliably — always use the class variable form.

### Why this is non-obvious
App-level BINDINGS feel like they should be global. The Textual docs describe BINDINGS at the app level as the standard pattern. The fact that a widget's built-in bindings silently shadow app bindings is not prominently documented. The RichLog's scroll bindings are inherited and invisible in your code.
