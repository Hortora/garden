### Symptom
Loading a 50MB `.npz` file and indexing per-element in a loop (`data['temporal'][i]` for i in range(5000)) causes 1.7GB memory allocation and eventually triggers OOM kills.

### Context
Common pattern when converting `.npz` training data to lists of per-sample tuples for PyTorch DataLoader consumption.

### Root cause
`np.load()` returns an `NpzFile` object. Each `data['key']` access calls `__getitem__` which decompresses the full compressed array from disk. With 5000 iterations, the same ~50MB array is decompressed 5000 times. While Python's GC collects intermediate arrays, the allocation pressure causes massive memory churn and peak usage far exceeding the data size.

### Fix
Extract the array to a local variable before the loop:

```python
# Bad — decompresses 'temporal' on every iteration
data = np.load('file.npz')
samples = [(data['temporal'][i], data['labels'][i]) for i in range(N)]

# Good — decompress once, index the local array
data = np.load('file.npz')
temporal = data['temporal']  # decompress once
labels = data['labels']      # decompress once
samples = [(temporal[i], labels[i]) for i in range(N)]
```

### Why this is non-obvious
`data['key']` looks like a simple dict lookup. Nothing in the numpy docs warns that NpzFile re-decompresses on each access. The symptom (OOM kill) appears as a system-level memory issue, not a numpy error, making it hard to attribute to this line of code.
