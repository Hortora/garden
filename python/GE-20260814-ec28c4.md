### Symptom

A function parameter documented as overridable silently uses the built-in
default even when the caller explicitly passes an empty dict `{}`.

### Context

Idiomatic Python uses `dispatch = dispatch or EFFECT_DISPATCH` to set
defaults. When the caller passes `dispatch={}` (an intentional empty
override meaning "no effects registered"), `bool({})` evaluates to
`False`, so `or` falls through to the built-in default.

### What was tried (didn't work)

A test passed `dispatch={}` to verify that unknown effects raise
`KeyError`. The test passed silently — no error was raised — because the
real dispatch table (with all effects registered) was used instead of
the empty override.

### Root cause

Python's `or` operator evaluates the truthiness of the left operand.
Empty containers (`{}`, `[]`, `set()`, `""`) are falsy. The pattern
`x = x or default` treats an intentional empty value identically to
`None`.

### Fix

Use an explicit `None` check:

```python
# Wrong — silently ignores empty dict
dispatch = dispatch or EFFECT_DISPATCH

# Right — only falls back when truly unset
if dispatch is None:
    dispatch = EFFECT_DISPATCH
```

### Why this is non-obvious

The `x = x or default` pattern is so common in Python that it reads as
correct at a glance. The falsy edge case only surfaces when an empty
container is a valid, intentional value — which is the case for override
parameters, feature-flag dicts, and allow/deny lists.

### Alternatives considered

- Using `dispatch if dispatch else EFFECT_DISPATCH` — same falsy problem.
- Using a sentinel object (`_UNSET = object()`) — works but heavier than needed; `None` check is sufficient when `None` is never a valid parameter value.
