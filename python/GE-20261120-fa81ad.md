# A keyword argument named like a positional parameter raises TypeError at the call, outside the function's own try/except

## Symptom

A "never raises" recorder, `record(action, **details)`, wraps its whole body in `try/except Exception`. A caller passes a detail that happens to be called `action`. The program dies with:

```
TypeError: record() got multiple values for argument 'action'
```

## Context

Logging, tracing, metrics and audit helpers commonly take one fixed argument and arbitrary keyword details, and are called from places that must not fail because of them.

## Root cause

Argument binding happens before the function body runs. The collision between the positional `action` and the keyword `action=` is detected by the interpreter while building the frame, so the `try` inside the function is never entered. The exception belongs to the caller.

## Fix

Make the fixed parameters positional-only. A keyword with the same name then goes into `**details`:

```python
def record(action: str, /, repo=None, branch: str = "", **details) -> bool:
    try:
        ...
    except Exception as error:
        warn(error)
        return False
```

## Why this is non-obvious

The function's contract ("never raises") is true of its body and is what the tests check. The failure needs a caller to choose a detail name that matches a parameter, which is likely for natural names such as `action`, `name`, `type` or `repo`, and it surfaces in the caller's path, not in the helper.

### Alternatives considered

- Prefixing parameters with an underscore: reduces collisions, does not remove them.
- Taking details as one dict argument: safe, but every call site gets noisier.
