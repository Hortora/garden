## Path.write_text() truncates before writing — crash loses prior state

### Symptom

A progress-tracking file (`KEY=VALUE` pairs, one per line) loses ALL prior
entries when a crash occurs during an update cycle. The file ends up empty
or with only the latest entry.

### Context

Any Python script that maintains state in a flat file using the pattern:

```python
def write_progress(path, key, value):
    data = read_progress(path)    # read all entries
    data[key] = value             # update dict
    lines = [f"{k}={v}" for k, v in data.items()]
    path.write_text("\n".join(lines) + "\n")  # REWRITE entire file
```

`Path.write_text()` calls `open(path, 'w')` which truncates the file to
zero bytes BEFORE writing new content. If the process crashes, is killed,
or raises an exception between truncation and write completion, the file
is empty — all prior entries are lost.

### What was tried (didn't work)

The pattern was documented as "append-only" and assumed crash-safe. Multiple
design specs referenced this claim without verifying the implementation.
The actual code was read-modify-write with truncating rewrite.

### Root cause

`Path.write_text()` → `open(path, 'w')` → truncates to zero bytes → writes
new content. The truncation is immediate and irreversible. The write may
never complete.

### Fix

Atomic write-then-rename using `os.replace()`:

```python
import os
from pathlib import Path

def write_progress(path: Path, key: str, value: str) -> None:
    data = read_progress(path)
    data[key] = value
    lines = [f"{k}={v}" for k, v in data.items()]
    path.parent.mkdir(parents=True, exist_ok=True)
    tmp = path.with_suffix('.tmp')
    tmp.write_text("\n".join(lines) + "\n")
    os.replace(tmp, path)  # atomic on POSIX
```

`os.replace()` is atomic on POSIX — the old file survives until the rename
completes. A crash during `tmp.write_text()` leaves the `.tmp` file
partially written but the original file is untouched.

### Why this is non-obvious

`Path.write_text()` looks safe — it's a high-level convenience method that
hides the truncation. The name suggests "write this text to the file," not
"delete the file contents first, then write." The pattern `read → modify →
write_text()` appears in many codebases and works correctly unless the
process crashes mid-write. The failure mode is silent — no exception, no
error, just an empty or partial file on the next read.

### Alternatives considered

- **Append-only with scan** (`open(path, 'a')`, scan for last value per
  key on read): truly crash-safe against partial writes, but more complex
  read logic and growing file size.
- **SQLite/shelve**: overkill for simple KEY=VALUE state tracking.
- **fcntl.flock()**: prevents concurrent access but doesn't fix the
  truncation problem within a single process.

The atomic write-then-rename pattern is the simplest fix that eliminates
the crash window entirely. It matches `lifecycle.py`'s `write_state()`
which already uses this pattern correctly.
