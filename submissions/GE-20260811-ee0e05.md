## What it achieves

Enables a TUI application to manage multiple concurrent LLM CLI sessions (Claude, Aider, Gemini, or any interactive CLI) across repos and slots, with attach/detach, status polling, and session lifecycle — without the TUI needing to embed a terminal emulator or build CLI-specific remote APIs.

## The technique

Instead of building attach/detach or remote control into the TUI, delegate session multiplexing to tmux:

1. **Create** — `tmux new-session -d -s soredium-<repo>-<issue> <cli_command>` with cwd set to the project
2. **Attach** — TUI suspends itself, runs `tmux attach-session -t <name>`, resumes on detach
3. **Status** — `tmux has-session -t <name>` (exit code 0 = running)
4. **Kill** — `tmux kill-session -t <name>`

The TUI's home screen polls session status on refresh and shows indicators (running/idle/paused) per repo/slot. The user attaches by selecting a running entry.

## Why this is non-obvious

The instinct when building a TUI that manages CLI sessions is to embed a terminal emulator widget or build process I/O automation (reading stdout, sending keystrokes). Both are complex and fragile — terminal emulation is a deep rabbit hole, and I/O automation breaks across CLI versions. Tmux is already installed everywhere, handles all terminal complexity, and works with any CLI without the CLI knowing it's being managed. The TUI becomes a tmux session manager rather than a terminal emulator.

## When to use it

- TUI needs to launch and manage interactive CLI processes
- Multiple concurrent sessions needed (across repos, slots, or projects)
- The CLI processes are interactive (not scriptable via API)
- Attach/detach semantics are required (sessions outlive the TUI view)
