## Symptom

Native memory grows steadily during repeated ONNX inference calls even though
all tensors are allocated inside `Arena.ofConfined()` blocks that close cleanly.
No OOM, no crash — just a silent handle leak that accumulates over time.

## Context

When wrapping OnnxRuntime's C API via Java FFM/Panama (`SymbolLookup` +
`MethodHandle` downcalls), you create ORT tensors via `OrtCreateTensorWithDataAsOrtValue`.
The tensor's *backing data* lives in a `MemorySegment` allocated from a confined
`Arena`. When the arena closes, the backing memory is reclaimed.

But the ORT C API also allocates an internal `OrtValue` handle — a native pointer
managed by ORT's own allocator. This handle is **not** tied to the Java Arena.
Closing the arena does **not** call `OrtReleaseValue` on the handle.

## What was tried (didn't work)

Relying on `Arena.ofConfined()` try-with-resources to clean up all native resources.
This works for the `MemorySegment` backing data but silently leaks the ORT handle.

## Root cause

Java FFM Arenas manage `MemorySegment` lifecycle — they free the backing memory
when the arena closes. But ORT's `OrtCreateTensorWithDataAsOrtValue` allocates
a separate native handle through ORT's internal allocator. Two independent
native resource lifecycles:

1. `MemorySegment` (arena-managed) — freed on arena close ✓
2. `OrtValue` handle (ORT-managed) — requires explicit `OrtReleaseValue` ✗

The arena has no knowledge of the ORT handle, and ORT has no knowledge of the arena.

## Fix

Call `session.releaseValue(tensor)` (which wraps `OrtReleaseValue`) for every
tensor created via `createTensor()`, even inside a confined arena scope:

```java
try (var arena = Arena.ofConfined()) {
    MemorySegment data = arena.allocateFrom(ValueLayout.JAVA_LONG, values);
    MemorySegment tensor = session.createTensor(data, byteSize, shape, type, arena);

    MemorySegment[] outputs = session.runRaw(inputNames, new MemorySegment[]{tensor},
                                              outputNames, arena);
    // ... use outputs ...

    for (MemorySegment out : outputs) session.releaseValue(out);
    session.releaseValue(tensor);  // ← THIS LINE — without it, ORT handle leaks
}
// Arena close frees MemorySegment backing — but ORT handles are already released above
```

Both input AND output tensors need explicit release. Outputs are typically
remembered (they were already released in the codebase), but inputs are easy
to forget because "the arena will clean them up."

## Why this is non-obvious

The `Arena.ofConfined()` pattern creates a strong mental model: "everything
allocated in this scope is freed when the scope ends." For pure FFM operations
this is true. But when a C library allocates its own handle *wrapping* the
arena-managed memory, the arena only frees half the resource. The leak is
silent — no error, no warning, no crash until memory pressure builds up.

### Alternatives considered

- Using `Arena.ofAuto()` (GC-triggered) — doesn't help; the ORT handle is
  still a separate allocation that GC doesn't know about.
- Registering a Cleaner on the Arena — FFM doesn't expose a hook for
  "arena is closing, run this cleanup." The Arena API is designed for memory
  segments, not arbitrary native handles.
