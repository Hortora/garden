# sherpa-onnx native lib JARs contain JNI libs, not C API libs — FFM needs the shared-lib tarball

### Symptom
`SymbolLookup.libraryLookup()` fails to find `SherpaOnnxCreateOfflineRecognizer` after extracting the native library from `sherpa-onnx-native-lib-osx-aarch64-1.13.6.jar`.

### Context
sherpa-onnx publishes multiple native library formats on every GitHub release. Choosing the wrong one wastes time.

### Root cause
The `-native-lib-*.jar` assets contain `libsherpa-onnx-jni.dylib` — the JNI wrapper library. It exports JNI symbols (`Java_com_k2fsa_sherpa_onnx_*`), not the C API symbols (`SherpaOnnxCreateOfflineRecognizer`).

For Java FFM/Panama bindings, you need `libsherpa-onnx-c-api.dylib` from the `-shared-lib.tar.bz2` assets.

### Fix
Download the correct asset:

| Purpose | Asset pattern | Contains |
|---------|--------------|----------|
| JNI (traditional Java) | `sherpa-onnx-native-lib-{platform}-{ver}.jar` | `libsherpa-onnx-jni.dylib` |
| FFM/Panama | `sherpa-onnx-v{ver}-{platform}-shared-lib.tar.bz2` | `libsherpa-onnx-c-api.dylib` + `libonnxruntime.dylib` |

Note: `libonnxruntime.dylib` must also be loaded before `libsherpa-onnx-c-api.dylib` — it's a runtime dependency.

### Why this is non-obvious
Both assets are native libraries for the same project on the same release page. The naming doesn't clearly distinguish JNI from C API. The JNI JAR is listed alongside the C API tarball, and a developer looking for "the Java native lib" will naturally grab the JAR first.
