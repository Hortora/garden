# sherpa-onnx FFM struct layout requires exact match of ALL nested model sub-configs — 17 types, not 5

### Symptom
SIGSEGV at `_platform_strlen` when calling `SherpaOnnxCreateOfflineRecognizer` via FFM downcall. The crash occurs inside the native library when it reads config struct fields, not in Java code.

### Context
Defining `MemoryLayout.structLayout()` for sherpa-onnx's `SherpaOnnxOfflineRecognizerConfig` to use with Java FFM/Panama. The config struct embeds `SherpaOnnxOfflineModelConfig` which contains sub-structs for every supported model type.

### What was tried (didn't work)
1. Defined MemoryLayout with 5 model sub-types (transducer, paraformer, nemo_ctc, whisper, tdnn) — the ones visible in older documentation. Struct size: 280 bytes. SIGSEGV.
2. Fixed whisper encoder/decoder field order (encoder first in C header, had decoder first). Still SIGSEGV.
3. Added 2 missing int32 fields to whisper sub-config (enable_token_timestamps, enable_segment_timestamps). Still SIGSEGV — the struct was still too small.

### Root cause
`SherpaOnnxOfflineModelConfig` in v1.13.6 contains **17** model type sub-configs, not 5. The full list: transducer, paraformer, nemo_ctc, whisper, tdnn, sense_voice, moonshine, fire_red_asr, dolphin, zipformer_ctc, canary, wenet_ctc, omnilingual, medasr, funasr_nano, fire_red_asr_ctc, qwen3_asr, cohere_transcribe. Total struct size: ~504 bytes (vs 200 bytes with 5 types). The C library reads fields at their real offsets — our undersized allocation caused it to read past the allocation into uninitialised memory.

Additionally, the whisper sub-config has 3 int32 fields (tail_paddings, enable_token_timestamps, enable_segment_timestamps), not 1. This shifts all subsequent offsets by 8 bytes (12 bytes + 4 padding vs 4 bytes + 4 padding).

### Fix
Abandon exact MemoryLayout definitions. Allocate 4096 bytes zero-filled and set fields at known byte offsets:

```java
MemorySegment config = arena.allocate(4096);
config.fill((byte) 0);
config.set(ValueLayout.JAVA_INT, 0, 16000);    // feat_config.sample_rate
config.set(ValueLayout.ADDRESS, 48, arena.allocateFrom(encoderPath)); // whisper.encoder
// ...
```

This matches the C pattern: `memset(&config, 0, sizeof(config))` then set specific fields. Extra zeros beyond the struct size are in our arena and never read by the C library.

### Why this is non-obvious
The C header is ~4700 lines. The model config embeds sub-structs for model types most users never touch. Documentation examples show only the 3-4 fields you actually set — they don't mention the 17 nested sub-configs that determine the struct's total size. The SIGSEGV occurs in `_platform_strlen` (reading a string field), which misleads toward a string encoding issue rather than a struct size issue.

### Why this fix
Exact MemoryLayout definitions are fragile — every sherpa-onnx release that adds a model type changes the struct size and shifts offsets. The 4096-byte approach is version-resilient: new model types are appended at the end (zeros = "not configured"), and the fields we set (whisper, tokens, provider) are at fixed offsets near the beginning.

### Alternatives considered
- **jextract auto-generation:** Would produce correct layouts from the C header. Not available in our build environment. Would need regenerating on every version bump.
- **Querying sizeof at runtime:** No C API function returns struct size. Would require a companion C program.
