# Oversized zero-filled allocation for FFM config structs — version-resilient alternative to exact MemoryLayout

### Context
When binding to C libraries with large, evolving config structs via Java FFM/Panama, defining exact `MemoryLayout.structLayout()` is fragile. Adding a field to any embedded sub-struct changes the parent struct's size and shifts all subsequent field offsets. This is common in actively developed C libraries (e.g., sherpa-onnx, FFmpeg, OpenSSL).

### Technique
Allocate a generously oversized `MemorySegment` (e.g., 4096 bytes), zero-fill it, and set specific fields at known byte offsets:

```java
MemorySegment config = arena.allocate(4096);
config.fill((byte) 0);

// Set only the fields you need — everything else stays zero
config.set(ValueLayout.JAVA_INT, 0, 16000);          // sample_rate
config.set(ValueLayout.ADDRESS, 48, arena.allocateFrom(path)); // model path
config.set(ValueLayout.JAVA_INT, 112, 2);             // num_threads
```

This mirrors the standard C pattern:
```c
SherpaOnnxOfflineRecognizerConfig config;
memset(&config, 0, sizeof(config));
config.feat_config.sample_rate = 16000;
// set specific fields...
```

### Why this works
- C libraries that use `memset(&config, 0, sizeof(config))` treat zero as the default for all fields
- NULL pointers (zero) mean "not configured" for optional string/pointer fields
- Zero integers mean "use default" for thread counts, flags, etc.
- The oversized allocation is in your own Arena — bytes beyond the struct are never read by the C library
- New fields appended in future versions default to zero — the binding doesn't break

### Why this is non-obvious
The "proper" FFM approach is `MemoryLayout.structLayout()` with named fields and VarHandles. This gives type safety and computed offsets. But it requires matching EVERY field of EVERY nested sub-struct exactly — for sherpa-onnx, that's 17 model type sub-configs totalling 500+ bytes. One wrong field count or missed padding causes SIGSEGV. The oversized allocation trades type safety at the layout level for version resilience at the binary level.

### When NOT to use this
- When the C library requires non-zero defaults for fields you don't set
- When you need VarHandle-based access for type safety
- When the struct is small and stable (exact MemoryLayout is cleaner)
- When using jextract (auto-generates correct layouts from the header)
