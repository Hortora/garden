## Problem

WebSocket tests that send messages immediately after receiving READY (or equivalent handshake event) flake under load. The connection appears ready, but the heartbeat thread hasn't completed its first ACK round-trip. If the heartbeat timer fires before the ACK is processed, the client detects a "missed ACK" and kills the connection — losing any in-flight messages.

## Technique

Wait for the **second** server-received heartbeat before sending test messages. The second heartbeat proves the first ACK was successfully processed by the client:

1. Client sends heartbeat #1 → server receives it (count = 1), sends ACK
2. Client receives ACK #1, sets `ackReceived = true`
3. Client sends heartbeat #2 → server receives it (count = 2)

If the ACK from step 1 had NOT been processed, the client would have detected a missed ACK between steps 1 and 3 and closed the connection. Reaching count = 2 proves the connection survived its first full heartbeat cycle.

```java
// Server-side: track received heartbeats
private final CopyOnWriteArrayList<String> receivedHeartbeats = new CopyOnWriteArrayList<>();

public int getReceivedHeartbeatCount() {
    return receivedHeartbeats.size();
}

// Test: wait for stable connection before sending messages
private void awaitStableConnection() {
    Awaitility.await()
            .atMost(10, TimeUnit.SECONDS)
            .until(() -> server.getReceivedHeartbeatCount() >= 2);
}
```

## Why this is non-obvious

Waiting for just one heartbeat is the intuitive approach — "the heartbeat fired, the connection works." But one heartbeat only proves the client *sent* a heartbeat, not that the ACK was *processed*. The race window between sending heartbeat #1 and processing its ACK is exactly where flaky tests fail. The second heartbeat is a proof-of-liveness for the full round-trip, not just one direction.

### Alternatives considered

- `Thread.sleep(N)` — fragile, doesn't adapt to load
- Waiting for 1 heartbeat — proves send but not ACK processing
- Mocking the heartbeat timer — hides the real timing behaviour
