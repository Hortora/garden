# Maven local repo isolation breaks cross-build SNAPSHOT resolution

## Symptom

`ClassNotFoundException` or `NoClassDefFoundError` for classes that
definitely exist in the SNAPSHOT jar in `~/.m2/repository`. The build
compiles fine — failure appears at runtime during framework
bootstrapping (e.g. Quarkus CDI augmentation, Spring context init).

## Context

Multi-repo workspace where:
- Repo A uses `-Dmaven.repo.local=/project/.m2` (via `.mvn/maven.config`)
- Repo B builds with default settings (installs to `~/.m2/repository`)
- Both share `0.2-SNAPSHOT` versions

Repo B is a dependency of Repo A.

## What was tried (didn't work)

- Rebuilding Repo B with `mvn clean install` — installs to
  `~/.m2/repository` but Repo A resolves from `/project/.m2`.
- Checking the jar contents in `~/.m2/repository` — the class IS there.
- Forcing `-U` on Repo A's build — `-U` only affects remote repos,
  not local resolution order.

## Root cause

Maven's `-Dmaven.repo.local` sets an isolated local repository. When
Repo B installs to `~/.m2/repository` (default), Repo A never sees the
update because it resolves exclusively from `/project/.m2`.

The `/project/.m2` may contain a stale SNAPSHOT from a previous GitHub
Packages download or an earlier build. Maven uses it without checking
the default repo.

The build compiles because the stale jar has the same classes the
compiler needs. The NEW class (added in a recent build of Repo B) only
exists in `~/.m2/repository` — not in the stale jar in `/project/.m2`.

## Fix

Build dependency repos with the same local repo as the consumer:

```bash
mvn clean install -f /path/to/repo-B/pom.xml \
    -Dmaven.repo.local=/project/.m2 \
    --settings=/project/slot-settings.xml
```

Or configure `slot-settings.xml` to declare the global `~/.m2/repository`
as a repository with `updatePolicy=always`:

```xml
<repository>
  <id>host-m2</id>
  <url>file:///Users/me/.m2/repository</url>
  <snapshots><updatePolicy>always</updatePolicy></snapshots>
</repository>
```

### Why this is non-obvious

The failure is silent at compile time. The stale jar satisfies all
compile-time dependencies. The missing class is only referenced via
reflection, CDI annotation scanning, or runtime classpath discovery.
The `ClassNotFoundException` names a class that exists in the "right"
`.m2` but not the one Maven is using — you have to know which `.m2`
Maven is actually resolving from.
