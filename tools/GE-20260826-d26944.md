### Symptom

A workspace got stuck at `closing:promoted` after a blog publishing failure. The promote step (mechanical) returned ERROR, but the LLM called `step_done=promote` anyway. The lifecycle advanced to `closing:promoted`, then the session ended before completing remaining steps. A new session detected stale progress, reset it, and the workspace was irrecoverable without manual intervention.

### Context

The orchestrator has two step types: mechanical (executed by Python scripts) and judgment (yielded to the LLM). Mechanical steps are completed by the orchestrator's own `run_loop`. Judgment steps are completed by the LLM calling `step_done=<name>`. But `step_done` accepted any step name — including mechanical ones.

### Root cause

No validation that `step_done` was appropriate for the step type. The LLM received an ERROR result for the promote step and, following fallback instructions, called `step_done=promote` to force past it. This marked promote as "done" in close-progress, allowing the lifecycle transition `promote_pass` to fire, advancing the state irreversibly.

### Fix

Build a set of mechanical step names from the step list. `apply_step_done` rejects calls for mechanical steps:

```python
MECHANICAL_STEPS = {s.name for s in STEPS if s.step_type == "mechanical"}

def apply_step_done(workspace, step, produced=None, mechanical_steps=None):
    if mechanical_steps and step in mechanical_steps:
        return {"ERROR": "invalid_step_done", "STEP": step,
                "REASON": "Cannot mark mechanical step as done"}
    update_close_progress(workspace, step, "done")
```

### Why this is non-obvious

The step_done parameter was designed for judgment steps where the LLM is the executor. Nobody anticipated the LLM would call it for mechanical steps — those are "owned" by the orchestrator. But when the LLM receives an ERROR and its fallback handler says to mark the step done, it doesn't distinguish between step types. The parameter is a string — it has no type safety.

### Why this fix

Rejecting at the parameter level is simpler and more robust than validating at the lifecycle layer. The lifecycle transition (promote_pass) fires unconditionally once promote is marked done — adding validation there would require the lifecycle to know about close-progress error states, coupling two layers.

### Alternatives considered

- **Lifecycle transition validation** — check that no fallback entries exist before firing promote_pass. Fragile: depends on fallback naming conventions and couples lifecycle to close-progress internals.
- **SKILL.md instruction hardening** — tell the LLM never to call step_done for mechanical steps. Insufficient: LLMs rationalize past instructions under pressure.
- **Separate parameters** — `judgment_done=` vs `step_done=`. Adds API surface without preventing misuse (LLM could still call the wrong one).
