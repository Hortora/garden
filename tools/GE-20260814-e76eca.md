### Symptom
After `mvn install` of a dependency, `mvn compile` on the consumer still fails with `cannot find symbol` for newly added classes. The local SNAPSHOT jar (`-SNAPSHOT.jar`) contains the class, but Maven uses a stale timestamped remote jar (e.g. `-20260813.115059-302.jar`).

### Context
When `mvn -U` or `mvn dependency:resolve -U` downloads a SNAPSHOT from a remote repository, Maven caches the timestamped jar alongside the local SNAPSHOT jar. Maven's resolver metadata (`_remote.repositories`, `resolver-status.properties`, `maven-metadata-*.xml`) tracks which version to use. The remote timestamped version takes precedence over the local install even when the local jar is newer.

### What was tried (didn't work)
1. `mvn install` of the dependency — writes `-SNAPSHOT.jar` but remote metadata still wins
2. Deleting only the timestamped jar — resolver still references it via metadata
3. `-nsu` flag — prevents new downloads but doesn't change resolution priority
4. `-o` (offline) flag — still uses cached remote metadata

### Root cause
Maven's SNAPSHOT resolution prefers the remote timestamped artifact over the local install when remote metadata files exist. The `_remote.repositories` marker and `resolver-status.properties` control which artifact Maven selects. Simply installing locally doesn't update these markers.

### Fix
Delete ALL remote artifacts and metadata, then reinstall:

```bash
# Nuke the entire SNAPSHOT directory
rm -rf ~/.m2/repository/io/example/my-artifact/1.0-SNAPSHOT

# Reinstall from source
mvn install -f /path/to/artifact/pom.xml -DskipTests
```

Or selectively remove only the remote timestamped jars and metadata:

```bash
rm ~/.m2/repository/io/example/my-artifact/1.0-SNAPSHOT/*-[0-9]*.jar
rm ~/.m2/repository/io/example/my-artifact/1.0-SNAPSHOT/maven-metadata-*.xml
rm ~/.m2/repository/io/example/my-artifact/1.0-SNAPSHOT/resolver-status.properties
rm ~/.m2/repository/io/example/my-artifact/1.0-SNAPSHOT/_remote.repositories

mvn install -f /path/to/artifact/pom.xml -DskipTests
```

### Why this is non-obvious
The local `-SNAPSHOT.jar` visibly contains the class (`javap` confirms). Maven's dependency tree shows the correct artifact. Nothing in the build output indicates a different jar is being used at compile time. The resolver metadata files are Maven internals that most developers never inspect.
