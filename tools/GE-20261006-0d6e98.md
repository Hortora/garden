## Symptom

`ide_replace_text_in_file` returns `{"success": true, "replacements": 1}` but the file on disk still has the old content. A subsequent `mvn compile` compiles the old content and fails with the same error the edit was supposed to fix.

Reading the file with the `Read` tool after the IDE edit confirms the old content is still on disk.

## Context

The IntelliJ MCP plugin's `ide_replace_text_in_file` uses IntelliJ's Document API to modify the file in the IDE's virtual file system (VFS). The Document API change is visible to all IDE tools (PSI, indexer, diagnostics) but may not be flushed to disk immediately. IntelliJ's auto-save runs on a timer (default ~15 seconds) or on focus loss.

When a build tool (Maven, Gradle) runs immediately after the IDE edit, it reads from disk — not from IntelliJ's VFS — and sees the old content.

## What was tried (didn't work)

- `ide_sync_files` after the edit — this syncs disk→IDE (refreshes VFS from disk), which actually reverts the in-memory change back to the old disk content
- Waiting and retrying the build — sometimes works if auto-save fires, but unreliable

## Fix

Use the `Edit` tool (with `replace_all: true` for find-and-replace) instead of `ide_replace_text_in_file` when the change must be visible to external build tools. The `Edit` tool writes directly to disk.

For structural code edits (adding methods, editing class declarations), `ide_edit_member` / `ide_insert_member` / `ide_replace_member` are preferred — these appear to flush to disk reliably because they trigger PSI-level modifications that IntelliJ treats as "document changed" events.

## Why this is non-obvious

The tool reports success with the replacement count. There is no indication that the change hasn't been persisted. The natural assumption is that a successful edit is on disk. The `ide_sync_files` tool name suggests it could solve this, but it syncs in the wrong direction.
