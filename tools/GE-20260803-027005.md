### Symptom

Running 6 embedding models sequentially through a benchmark harness (2421-entry corpus × 14 scenarios × 2 query types) exceeds process timeout limits. The full run takes ~15 minutes on CPU; process supervisors kill it at the 10-minute mark, losing all results.

### Context

ML benchmark scripts typically run all models in a loop and save a single combined results file at the end. When individual models take 1-5 minutes each, the total exceeds common process timeout limits (10 minutes for Claude Code Bash, similar for CI runners).

### Fix

Run models in groups that fit within the timeout, save partial results per group, then merge:

```python
# 1. Run fast models together (stays under timeout)
# python3 -m benchmark_runner model_a model_b model_c

# 2. Save partial results before the next group overwrites
# shutil.copy2('results/benchmark.json', 'results/benchmark_partial1.json')

# 3. Run slow models individually
# python3 -m benchmark_runner slow_model

# 4. Merge all partials
import json
from pathlib import Path

merged = {}
for partial in Path('results').glob('benchmark_partial*.json'):
    merged.update(json.loads(partial.read_text()))
# Add the final run's results
merged.update(json.loads(Path('results/benchmark.json').read_text()))
Path('results/benchmark.json').write_text(json.dumps(merged, indent=2))
# Clean up partials
```

Group models by inference speed — put the slowest models (large context windows, high parameter counts) in their own run.

### Why this is non-obvious

The natural approach is to fix the timeout (increase it, run in background, use a job scheduler). But when the process supervisor is external and non-configurable (CI runner, Claude Code sandbox), the workaround is to structure the benchmark itself for partial saves — a data engineering solution to a process management problem.
