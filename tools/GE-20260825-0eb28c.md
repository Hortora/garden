## Continuation spec references prior spec's decisions — avoids patching reviewed documents

### Symptom
A reviewed and validated design spec needs expansion — new sections covering gaps the original didn't address. Editing the reviewed document risks introducing inconsistencies or invalidating the review.

### Context
After adversarial review (3 rounds, 18 findings, 3 revisions), a design spec's 12 decisions were validated. The implementation was attempted and reverted because the spec lacked mechanical wiring detail. The spec needed expansion, not revision.

### Fix
Write a new "continuation spec" that:
1. Lists the prior spec's decisions as settled foundation (by reference, not by restating)
2. States which decisions are NOT reopened
3. Adds new decisions (D13-D18) only for the gaps
4. References the prior spec for architecture, action types, lifecycle mapping
5. Focuses entirely on what the prior spec didn't cover

### Why this is non-obvious
The natural instinct is to edit the existing spec — add sections, expand tables, fill gaps. But a reviewed spec is a validated artifact. Patching it creates three risks: (a) edits may subtly contradict validated decisions, (b) the review is invalidated — the document changed after review, (c) it's hard to see what's new vs what was already validated. A continuation spec gets fresh-document clarity while keeping the prior spec as a stable, reviewed reference.
