### Symptom
In hierarchical MCP models (two meta-tools replacing N domain tools), the operation catalog shown via `casehub_model` scrolls out of the LLM's context window in long conversations. The LLM then guesses parameter names and shapes, leading to errors.

### Context
Flat MCP tools have JSON Schema in the tool definition — always in the system prompt, never scrolls away. Hierarchical models show the schema once during navigation. In long multi-step sessions, this ephemeral schema is the primary failure mode.

### Fix
Include the expected parameter schema in validation error messages. When the LLM constructs wrong params, the error reinjects the schema into context:

```
Invalid params for echo: Unknown parameter 'msg'.
Expected: message: String (required)
```

The LLM now has the schema back in context and self-corrects on retry. Worst case: one wasted round-trip — same cost as a flat tool with a typo.

### Why this is non-obvious
The natural instinct is to treat validation as error prevention (stop bad input). The insight is that validation errors are also a context recovery mechanism — they solve the ephemeral model problem by reinjecting the schema at exactly the moment the LLM needs it. This converts a fundamental architectural downside (ephemeral model output) into a bounded cost (one extra round-trip).

### Why this fix
Alternatives considered: caching model output in the conversation, requiring the LLM to re-call casehub_model before every action, or embedding full schemas in the tool definition. Validation-as-reinjection requires zero changes to the MCP protocol, zero changes to the LLM's workflow, and activates only when actually needed (schema has drifted out of context).
