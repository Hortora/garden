### Symptom
A mode flag (e.g. `trackerDriven`, `testMode`, `bypassBilling`) correctly skips
checks at the entry point but silently applies those checks in downstream code
paths — queue drain, deferred retry, background processing. The entry point works;
the system still fails.

### Context
Any system where:
1. A flag changes behavior at the point of entry (skip validation, bypass economy checks, use lenient limits)
2. The data passes through multiple downstream code paths (queues, schedulers, retry loops)
3. Each downstream path has its own version of the same gate

The flag is typically set in the error-handling or fallback paths (auto-resolution,
rerouting) but not the normal/happy path where the input matches directly.

### Root cause
The flag is set conditionally — only when error recovery triggers — rather than
declaratively from the input's identity. When the input takes the happy path
(direct match, no fallback needed), the flag stays `false` and downstream gates
apply.

### Fix
Set the flag from the **input's identity**, not the **resolution path**:

```java
// Wrong — only set in error recovery
boolean trackerDriven = false;  // stays false on happy path
if (building == null) {
    // auto-resolution path
    trackerDriven = true;  // only set here
}

// Right — set from the input's declared identity
boolean trackerDriven = intent.trackerDriven();  // set by the producer
```

Then audit every downstream code path that gates on the flag:
- Queue drain (supply/resource checks when dequeuing)
- Deferred retry (re-entering the same method with different state)
- Background processing (cron jobs, schedulers, event handlers)

### Why this is non-obvious
The flag works correctly for all error cases — auto-resolution, rerouting, fallback
paths all set it. The bug only manifests on the **happy path** where input matches
directly and no error recovery is needed. This is the most common case, but it's
the one path where the flag isn't set.

Aggregate metrics hide the issue further: the system reports 99.1% accuracy and the
error breakdown says "wrong_building_type" — but per-type diagnostic data shows
every remaining rejection is actually "insufficient_resources" from the unflagged
happy path.

### Why this fix
Setting the flag from the input's identity (a field on the record/message) rather
than the resolution path makes the flag declarative and audit-friendly. You can grep
for all reads of the field and verify each code path respects it. Resolution-path
flags require tracing every branch to confirm the flag is set.

### Alternatives considered
- **Global mode flag on the container** (e.g. `emulatedGame.setTrackerMode(true)`) — too coarse; a container might process mixed inputs
- **Tag-prefix heuristic** (check `tag.startsWith("r-")`) — fragile; other input sources may share the prefix (CmdEvent-derived intents also use `r-` tags)
- **Skip all gates unconditionally** — breaks non-tracker use cases that depend on economy validation

### Diagnostic-first corollary
The issue description said "wrong_building_type" was the root cause (354 rejections).
Building an aggregate rejection-reason diagnostic showed every remaining rejection
was actually "insufficient_resources". Without the diagnostic, the fix would have
targeted the wrong code path indefinitely.

**Rule: before fixing, build a per-category rejection counter. The rejection reason
tells you which code path to fix.**
