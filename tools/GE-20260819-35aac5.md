## LLM-generated detail text breaks dedup across sessions

### Symptom / context
A findings persistence system using `(check, detail)` as the dedup key accumulated duplicate entries for the same finding across sessions. The same code issue at the same location appeared multiple times because each session described it differently.

### Root cause
LLMs generate freeform text non-deterministically. The same finding — "missing error handling in sync.py line 42" — might be described as "No error handling for network timeout in sync.py" in session 1 and "sync.py:42 lacks exception handling for HTTP failures" in session 2. Different `detail` strings, same finding.

### Fix
Use a stable `location` field as the primary dedup anchor instead of `detail`:

```python
def _dedup_key(f: dict) -> tuple:
    loc = f.get("location")
    if loc:
        return (f.get("check", ""), loc, f.get("branch"))
    # Fallback for legacy entries without location
    return (f.get("check", ""), f.get("detail", ""), f.get("branch"))
```

Location formats: `src/sync.py:42` (file:line), `spec:req-3` (spec reference), `plan:add-integration-tests` (plan item), `branch:issue-200` (branch reference). These are structurally stable across sessions — the file and line don't change unless the code changes.

`detail` remains as the human-readable description but is NOT part of the dedup key when `location` is present.

### Why this is non-obvious
Dedup by content description is the natural approach — it works for human-written systems where the same person uses the same words. The failure mode only appears when multiple LLM sessions write to the same store, which is uncommon outside agentic workflow systems.
