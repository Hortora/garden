### Symptom
An SC2 economy emulator produces nearly deterministic worker mining cycles (σ=0.34 ticks, 87% of cycles exactly 5 ticks) while real SC2 produces wide variance (σ=2.54, range 2–23 ticks). Weeks of collision model parameter tuning — collision radius, speed factors, acceleration, direction-dependent severity — improved variance but couldn't match SC2's distribution shape.

### Context
Any simulation that processes agents in a fixed iteration order (e.g. `LinkedHashMap`, array index, insertion order) will produce deterministic emergent behaviour even when the underlying physics model has all the right ingredients for variance. SC2 is described as "mostly deterministic" with randomness "mainly for cosmetic reasons."

### Root cause
SC2 randomizes the processing order of events within each game loop (documented in [PySC2 §Determinism and Randomness](https://github.com/google-deepmind/pysc2/blob/master/docs/environment.md#determinism-and-randomness)). For mining: which worker reaches a patch first, which deposits first, and collision resolution priority all vary randomly per loop.

Two specific randomness sources:
1. **Update order** — random per game loop, determines event processing sequence
2. **Weapon speed** — ±1 to +2 game steps between shots (combat only, not mining)

### Fix
Shuffle worker processing order each game loop. In Java: `Collections.shuffle(workerList)` at the start of each loop iteration. This is not a stochastic formula overlaid on deterministic physics — it's what SC2 actually does. The variance emerges naturally from non-deterministic ordering interacting with collision resolution and patch contention.

### Why this is non-obvious
The PySC2 docs describe update order randomness in the context of High Templar feedback duels — the connection to mining cycle variance is never made. A developer tuning collision parameters would never suspect that iteration order is the root cause, because the collision model has the right ingredients (speed reduction, lateral push, patch contention). The parameters look like they should produce variance — they just can't when every loop processes the same worker first.

### Why this fix
Parameter tuning (collision radius, speed factors, direction-dependent severity) improved σ from 0.34 to 2.02 but hit a ceiling — the distribution shape remained wrong because the same workers always "won" contention. Shuffling processing order lets different workers win on different loops, producing the right-skewed distribution SC2 exhibits.

### Broader principle
In any agent-based simulation, deterministic processing order suppresses emergent variance. If your aggregate metrics match but per-agent timing distributions don't, check whether iteration order is creating implicit priority. The fix is always the same: randomize processing order at the granularity where contention occurs.

### Alternatives considered
- Stochastic collision delay (random delay proportional to density) — rejected: formula overlaid on physics, not what SC2 does
- Direction-dependent collision severity alone — improved σ from 0.34 to 2.02 but hit ceiling without processing order randomization
- Increased collision radius — improved variance but coupled mean and variance (couldn't tune independently)
- Per-worker path memory — complex, high implementation cost, doesn't address the root cause
