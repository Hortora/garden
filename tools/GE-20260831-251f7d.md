### Symptom / Context

When writing tests for duplicate commit detection between a fork and its
upstream, cherry-picking a commit from fork into blessed (upstream)
produces a commit with the SAME SHA — not a different one. The duplicate
detection finds nothing because there is no duplicate: git resolved both
commits to the same object.

### Root cause

Git computes a commit SHA from: tree hash + parent hash + author/committer
info + message. When two repos share the same bare ancestry (fork model)
and the histories haven't diverged, a cherry-pick of commit A onto the
same parent produces an identical tree, identical parent, and identical
message — resulting in the same SHA.

Only when an independent commit exists on the upstream (diverging the
parent hash) does the cherry-pick produce a genuinely different SHA.

### Fix

When testing duplicate detection, always add an independent commit to the
upstream BEFORE cherry-picking:

```python
# Diverge history first
(blessed / "upstream-only.txt").write_text("upstream work")
git(blessed, "add", ".")
git(blessed, "commit", "-m", "chore: upstream work")

# NOW cherry-pick — parent hash differs, so SHA will differ
git(blessed, "cherry-pick", fork_sha)
```

### Why this is non-obvious

The assumption "cherry-pick always creates a new SHA" is common and
usually correct in practice (upstream repos normally have independent
activity). It fails in test scenarios where both repos start from the
exact same state with no divergence. The symptom is confusing: the
duplicate detection test passes with no duplicates found, even though
the setup appears correct.
