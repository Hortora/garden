## Sandbox-first architecture validation — prove in isolation before migrating

### Stack
TypeScript, Vitest (happy-dom), Playwright

### Symptom
Re-architecting a working subsystem in-place led to 24 hours of instability — each fix created new edge cases, and the working functionality degraded during iteration.

### Context
Replacing a dockview-based floating frame system with a composable Group/Organiser architecture. The existing frames and tabs worked well. The problem was only with the accordion toggle — but modifying the code in place risked breaking what worked.

### What was tried (didn't work)
1. Modifying the existing code in place — every fix for accordion toggling broke frame positioning or tab lifecycle
2. Adding a mutation pipeline to order operations — addressed timing symptoms but not root cause (two competing layout systems)

### Fix
Build a standalone sandbox in an isolated directory (`frame-sandbox/`) with zero imports from the existing system:

1. **Isolated primitives** — new implementations of the core concepts (Group, TabOrganiser, AccordionOrganiser, FreeLayoutOrganiser) with no dependency on the existing code
2. **Unit tests first** — 37 vitest tests with happy-dom proving the data model, DOM structure, and content preservation across organiser toggles
3. **Real integration** — the sandbox uses the actual ContentFactory rendering pipeline via an activation callback, proving the integration path works
4. **Playwright tests** — 6 browser tests proving drag, resize, tab switching, accordion expand/collapse, and 3-level nesting in a real browser
5. **Migration plan second** — only after the sandbox was stable, write the plan to replace the existing code using the proven primitives

The sandbox and the existing code coexist — the sandbox is a new component type (`frame-sandbox`) that doesn't touch any existing files except adding an activation handler.

### Why this is non-obvious
The instinct is to modify the existing code incrementally — "just fix the toggle." But when the architecture is fundamentally wrong (two competing layout systems), incremental fixes compound rather than converge. Building from scratch in isolation eliminates the risk of breaking working functionality and provides a clean proof that the new architecture works before committing to the migration.

### Alternatives considered
- **Modify in place with feature flags** — still risks regressions and creates a patchwork of old + new code
- **Branch-based prototype** — better than in-place but still modifies existing files, making rollback messy
- **Standalone sandbox** (chosen) — zero risk to existing code, clean proof, migration plan written from evidence not theory
