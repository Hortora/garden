## Convention

In the soredium design-review framework, review capabilities are classified as either lifecycle **modes** or dimensional **types**. Decision review is a mode.

**Modes** (lifecycle-bound): `pre-review`, `spec-review`, `code-review`, `final-review`, `decision`. Each mode gets its own dedicated prompt builder functions (`_build_decision_review_reviewer_prompt()`, etc.) and mode generator in setup.py (`_MODE_GENERATORS["decision"]`). Modes dispatch via explicit `if mode == "decision":` branches in `build_reviewer_prompt()` and `build_implementor_prompt()`.

**Types** (dimensional): `coherence`, `structure`, `robustness`, `crosscutting`. Types share a common prompt builder (`_build_typed_reviewer_prompt()`) parameterised by type briefs (`_TYPE_BRIEFS` dict). Types run as parallel or ordered dimensions within a single lifecycle point.

## Why this distinction matters

When adding a new review capability, the classification determines where code goes:

- **New mode** → add dedicated `_build_<mode>_reviewer_prompt()` and `_build_<mode>_implementor_prompt()` functions, add `_MODE_GENERATORS["<mode>"]` in setup.py, add dispatch branch in both prompt builder entry points
- **New type** → add a brief to `_TYPE_BRIEFS` dict, add to `REVIEW_TYPES` tuple — no new functions needed

Misclassifying a mode as a type (or vice versa) leads to either insufficient prompt customisation (mode squeezed into the typed template) or unnecessary code duplication (type with a dedicated builder when a brief would suffice).

## Alternative

A unified dispatch model where all review capabilities route through a single parameterised builder. This would reduce the mode/type split but lose the ability to deeply customise mode-specific prompts (e.g., decision review's exploration-depth calibration has no equivalent in dimensional types).
