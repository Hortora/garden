## Bulk Java record migration via compile-error-driven ide_replace_text_in_file

### Symptom

Adding a field to a widely-used Java record (60+ call sites across production and test code) — need to update every constructor call.

### Context

Java records have a single canonical constructor. Adding a field changes every call site. With 60+ sites across 13 files, manual editing is impractical. IntelliJ's built-in "Change Signature" doesn't handle records well. The `ide_replace_text_in_file` MCP tool with text matching is the right tool — but you need the list of files.

### Fix

1. **Compile production code first** (`mvn clean compile`) — verify the record itself and its production callers are correct
2. **Compile tests** (`mvn test-compile`) — collect the error list: unique file paths from `[ERROR]` lines
3. **Group by pattern** — most test constructors share the same last-arg pattern (e.g. all end with `"test")`). Use `ide_replace_text_in_file` with the common suffix to batch-process entire files in one call
4. **Handle outliers individually** — multi-line constructors or unique string args get individual `ide_replace_text_in_file` calls matching the exact closing text

Example: adding `AssessmentSource.DROOLS` as 5th arg to `PatternAssessment`. Most test calls end with `"test")` — a single replace of `"test")` → `"test", AssessmentSource.DROOLS)` hit 29 sites in one file.

### Why this is non-obvious

The instinct is to write a script that parses Java and adds the argument. But IntelliJ MCP's `ide_replace_text_in_file` with simple text matching is faster and safer — it operates through IntelliJ's Document API so the index stays consistent. The key insight is using the compiler error output as the file list rather than grep.
