### Symptom

Embedding 2421 documents with jina-embeddings-v2-base-code takes ~2:25 on CPU vs ~90 seconds for nomic-embed-text — roughly 1.6x slower per batch despite similar parameter counts (161M vs 137M). Initial batches are dramatically slower (~2.5 min for the first batch vs ~4s for nomic), giving a misleading impression of 30-50x slowdown.

### Context

When benchmarking embedding models for code-domain retrieval, jina-code's 8192 max context window (vs 512 for nomic) results in attention computation that scales quadratically with sequence length, even when actual input texts are shorter than 512 tokens.

### Root cause

JinaBERT uses ALiBi (Attention with Linear Biases) positional encoding to support 8192 tokens. While ALiBi is more memory-efficient than absolute position embeddings for long contexts, the attention matrix still scales with the model's configured context window on CPU. The first batch is disproportionately slow due to JIT compilation and memory allocation for the larger attention buffers.

### Fix

When benchmarking models with large context windows on CPU:

1. **Expect cold-start overhead** — the first batch will be 30-50x slower than steady state due to JIT and memory allocation. Don't extrapolate total time from the first batch.
2. **Steady-state throughput** is ~1.6x slower than 512-context models of similar size, not 30-50x.
3. **Run individually** when benchmarking multiple models — memory pressure from prior model loading compounds the slowdown.

### Why this is non-obvious

ALiBi is marketed as enabling efficient long-context processing. The expectation is that a 161M model with ALiBi would have similar inference speed to a 137M model with standard position embeddings, regardless of max context. The cold-start amplification makes the problem appear much worse than steady-state reality.
