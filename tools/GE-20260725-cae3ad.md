### Symptom
HyDE query expansion (generating hypothetical documents from queries) is net-negative on a corpus despite correct per-leg embedding separation. Every variation tried produces -2 to -2.5 percentage points precision loss. The hypothetical documents look plausible but consistently degrade results.

### Context
A garden retrieval service using five-signal retrieval (BGE-M3 dense + sparse + BM25 + ColBERT rescoring + cross-encoder reranking) with adaptive score filtering. Four HyDE approaches benchmarked across 14 real-world scenarios:

| Approach | Precision | Delta |
|----------|-----------|-------|
| No expansion (baseline) | 61.6% | — |
| Double-retrieval HyDE (two cycles, RRF merge) | 59.4% | -2.2pp |
| Single-retrieval HyDE (one cycle, per-leg separation) | 59.4% | -2.2pp |
| Inverted HyDE (index-time query generation via local LLM) | 59.2% | -2.5pp |

### Root cause
Weller et al., "When do Generative Query and Document Expansions Fail?" (Findings of EACL 2024) tested 11 expansion techniques across 24 retrieval models and 12 datasets. Finding: **strong negative correlation between retriever performance and expansion benefit.** Expansion improves weak models but harms strong ones.

The mechanism: expansions add information (improving recall) but also add noise that makes it harder to distinguish between the top relevant documents, introducing false positives. When the retriever already has high recall and precision, the noise dominates the benefit.

For domain-specific corpora with specialised vocabulary (Java class names, CDI annotations, Qdrant API references), generic LLM hypotheticals use plausible but wrong vocabulary — further degrading the dense embedding signal.

### Fix
Don't use expansion on strong multi-signal retrievers. The decision framework:

- **Weak retriever** (single dense embedding, no reranking): expansion likely helps — try it.
- **Strong retriever** (multi-signal + cross-encoder): expansion likely hurts — benchmark before enabling.
- **Domain-specific corpus**: expansion hurts more because LLMs generate generic vocabulary instead of the exact terms in the corpus.

If you've already built a strong pipeline (dense + sparse + BM25 + reranking), invest in corpus quality (curation, entry scoring) rather than query/document expansion.

### Why this is non-obvious
HyDE is widely recommended in RAG literature and tutorials as a general-purpose improvement. The assumption "more semantic context = better retrieval" is intuitive. The failure mode — that expansion noise outweighs expansion recall on strong retrievers — is counter-intuitive and requires benchmarking to detect. Without the Weller et al. finding, the natural response to negative HyDE results is "tune the prompt" or "try a different approach," not "stop expanding."

### Why this fix
The four-approach benchmark eliminates prompt quality, retrieval architecture, and index-time vs query-time as variables. The result is consistent across all approaches: -2 to -2.5pp. The Weller et al. finding explains the mechanism: it's not the implementation, it's the interaction between expansion and retriever strength.

### Alternatives considered
- **Better prompts**: Domain-tuned HyDE prompt with confidence gating. Tried — the prompt was well-tuned, the model (Claude) is capable. Didn't help.
- **Per-leg embedding separation**: Dense uses hypothetical, sparse/BM25 use original. Eliminates the "all legs use searchText()" problem from the original HyDE benchmark. Didn't help.
- **Single-retrieval mode**: Remove the double-retrieval + RRF merge to eliminate fusion noise. Didn't help.
- **Inverted HyDE**: Generate queries at index time instead of documents at query time. Grounds expansion in actual corpus content. Didn't help.
