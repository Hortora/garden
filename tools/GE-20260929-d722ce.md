### Symptom

Multiple processes launched in parallel all targeting the same git repository fail with exit code 128 on `git add -A` or `git commit`. Only one process succeeds — the others fail because they cannot acquire the `.git/index.lock` file.

### Context

This occurs when spawning concurrent background processes that each need to stage and commit files in a shared git repository. In this case, three design-review agents were launched in parallel, each creating a workspace directory under `~/reviews/` and then calling `git add -A` and `git commit` in the shared `~/reviews/` repo. Two of three failed.

### What was tried (didn't work)

Launching all three processes simultaneously with the expectation that git would handle concurrent writes. Git's index lock is a hard exclusive lock — there is no queuing or retry mechanism built in.

### Root cause

Git uses an exclusive lock file (`.git/index.lock`) for all staging and commit operations. When multiple processes call `git add` or `git commit` concurrently, only one acquires the lock. The others fail immediately with `fatal: Unable to create '.git/index.lock': File exists.`

This is by design — git does not support concurrent writes to the same repository. The `index.lock` mechanism prevents index corruption but provides no queuing.

### Fix

Serialize the git operations: let the first process complete its git operations before launching the others. Alternatively, use separate git repositories per process (each workspace gets its own `.git`), or add a retry loop with jitter around the `git add/commit` calls.

For the review agent case: launch the processes one at a time (so each completes its `_init_review_git()` setup before the next starts), or have each workspace be its own git repo instead of sharing a parent repo.

### Why this is non-obvious

The failure is silent from the Python `subprocess.run(check=True)` perspective — it raises `CalledProcessError` with exit code 128 but the error message about `index.lock` is in stderr, which may not be surfaced depending on error handling. The fix is also non-obvious because the processes are writing to *different directories* within the same repo — the expectation is that non-overlapping file paths wouldn't conflict, but git's index is repo-global.
