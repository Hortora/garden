## Symptom

Dispatch tables that map internal catalog indices to domain actions silently
break when the catalog grows between versions. The same index value maps to
a different entry, causing wrong dispatch (e.g., an upgrade research command
interpreted as a movement order). No error is raised — the index is valid,
just pointing at the wrong slot.

## Context

Any system where serialized data uses positional catalog indices rather than
stable identifiers. The canonical case: game replay files that record ability
commands as `abilLink` (position in the ability array). When a new ability is
inserted between versions, all subsequent indices shift by the insertion count.

Applies broadly to: game engine data catalogs, binary protocol formats with
positional enum values, database schemas where auto-increment IDs shift after
bulk inserts, and any message format using "slot N" references into a growing
array.

## What was tried (didn't work)

1. **Per-version dispatch tables** — duplicating the entire dispatch table for
   each schema version. Works but doesn't scale: each table is hundreds of
   entries, and the actual mappings (index-to-action) are identical — only
   the base offset differs.

2. **Empirical correlation** — matching events statistically (nearest temporal
   match). High-frequency generic events dominate the correlation, producing
   false matches regardless of filter heuristics (no-target, selection-size,
   deduplication).

3. **Stable ID lookup** — using the system's published stable identifiers
   (e.g., `stableid.json` in SC2). These map to a different numbering system
   (API IDs vs catalog indices) with no documented bridge.

## Root cause

Catalog indices are positional — they depend on the catalog's current contents.
When entries are inserted (never deleted or reordered), all subsequent indices
shift by the insertion count. The delta is constant across the entire catalog
for a given version pair.

## Fix

Compute the offset between two known versions by comparing a single known
mapping (e.g., one entry whose identity is certain in both versions). Apply
the offset as a subtraction before dispatching:

```java
// AbilityProfile enum with per-version offset
V4_9_3(0),   // baseline
HSC_2025(2); // two abilities inserted between versions

// In the dispatch method — normalize before switching
int normalized = rawIndex - profile.offset();
return switch (normalized) {
    case KNOWN_CONSTANT_A -> handleA();
    case KNOWN_CONSTANT_B -> handleB();
    // ... all constants defined relative to the baseline version
};
```

The dispatch table is written once (for the baseline version). New versions
only need the offset value. Verified across 5 datasets spanning 7+ years
and 34K+ build numbers — a single +2 offset handled all versions after the
insertion point.

### Alternatives considered

- **Remapping table per version**: correct but O(N) per version where N is
  catalog size. The offset is O(1) per version.
- **Version-branched dispatch**: switch on version then dispatch. Duplicates
  the entire dispatch table per version.

## Why this is non-obvious

The natural instinct is to maintain a separate dispatch table per version —
the "delta approach" (compute offset, apply subtraction) is only viable when
the catalog growth pattern is insertions-only. Recognizing that the growth
IS insertions-only (and computing the insertion count from a single known
mapping) requires understanding the catalog's internal structure, which is
typically undocumented.
