## Structured warnings as LLM fallback signal when extracting mechanical scripts from LLM workflows

### Stack
Python, Claude Code skills

### Symptom / Context
When replacing LLM subagent dispatches with deterministic Python scripts, the scripts are faster and cheaper but lose the LLM's ability to adapt to unexpected input — malformed files, unusual git output, missing dependencies. Pure scripts either fail silently on edge cases or require exhaustive error handling that approaches LLM complexity.

### The technique
Structure scripts to emit a `warnings` array (JSON) or `FALLBACK=yes` flag (KEY=value) alongside their normal output. The warnings list describes what the script couldn't confidently handle — not errors that should stop execution, but ambiguities the calling LLM should investigate.

The calling skill reads the script output and, if warnings are non-empty, investigates just the flagged pieces inline using the same commands the script would have run. The script handles the deterministic fast path (90%+ of runs); the LLM handles the edge cases that need judgment.

### Fix / Implementation

**JSON output pattern (data-gathering scripts):**
```python
result = {
    "commits": [...],
    "journal_validation": {...},
    "warnings": []  # empty = script handled everything
}

# Flag ambiguous cases instead of guessing
if line.startswith("###") and not line.startswith("### "):
    result["warnings"].append(f"possible malformed entry: {line}")

# Flag missing dependencies instead of failing
if not hashes_script.exists():
    result["warnings"].append(f"section_hashes.py not found — drift check skipped")
```

**KEY=value output pattern (action scripts):**
```python
if result.returncode != 0:
    conflict_detail = result.stderr.strip()
    git(project, "rebase", "--abort")
    print("ERROR=REBASE_CONFLICT")
    print(f"ERROR_DETAIL={conflict_detail}")
    print("FALLBACK=yes")  # signal: LLM should investigate
```

**Skill-side fallback:**
```markdown
If `warnings` is non-empty: investigate each warning inline — run
the relevant git/file commands yourself to resolve what the script
flagged. The script handles the fast path; you handle edge cases.
```

### Why this is non-obvious
The natural instinct is binary: either keep it as an LLM subagent (full flexibility, high token cost) or extract it to a script (fast, cheap, brittle). The hybrid — scripts that signal ambiguity for selective LLM intervention — preserves the LLM's judgment where it matters without paying for it on every run.

### Alternatives considered
- **Full LLM subagent:** Works but burns tokens on deterministic operations (git log, file reads, gh API calls) that never need judgment
- **Pure script with exhaustive error handling:** Approaches LLM complexity for edge cases; still can't handle truly novel situations
- **Script with hard failures on ambiguity:** Forces the user to re-run or debug; the LLM could have resolved it automatically
