### Symptom
`ide_replace_text_in_file` succeeds with `replacements: 1` but the target file in the slot clone is unchanged. No error, no warning.

### Context
Working in a slot-based multi-clone setup (e.g. `slots/2/trellis` is a clone of `hortora/trellis`). The IntelliJ workspace was opened with `ide_open_workspace` pointing to the main repo's sidecar, not the slot's sidecar. All subsequent `ide_replace_text_in_file` calls with `project_path` pointing to the main repo edit the main clone silently.

### What was tried (didn't work)
Called `ide_replace_text_in_file` with `project_path: /path/to/main/trellis/sidecar` — the edit succeeded in the main clone. The slot 2 file was never touched. Only discovered by running `grep` on the slot file and finding the original content unchanged.

### Root cause
`ide_open_workspace` and all subsequent IntelliJ MCP tool calls use `project_path` to determine which opened project to operate on. When multiple clones of the same repo exist, each must be opened as a separate workspace project. The MCP doesn't validate whether the file being edited is actually within the project at `project_path` — it just finds the file relative to whichever project is identified by that path.

### Fix
Open the slot's sidecar as its own workspace before any edits:
```typescript
ide_open_workspace({
  modules: ["/path/to/slots/2/trellis/sidecar"],
  project_path: "/path/to/slots/2/trellis/sidecar"
})
```
Then use the slot's `project_path` in every subsequent tool call. File paths in the tool call are relative to the project root — omit the leading path that matches `project_path`.

### Why this is non-obvious
The tool call succeeds with a positive confirmation (`replacements: 1`). There is no error, no warning, and no indication that the edit landed in a different clone. The only way to detect it is to verify the target file after the edit.

### Alternatives considered
- Using `Edit` tool directly — blocked by IntelliJ-first hook on .ts/.java files
- Symlinking slot files to main — breaks git tracking
