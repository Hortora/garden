### Symptom

When migrating Java files from a flat package (e.g. `io.casehub.blocks.agentic.social`) to subpackages in another repo (e.g. `io.casehub.neocortex.cognition.mood`, `.drive`, `.strategy`), naive package replacement produces broken imports.

### Context

Large-scale cross-repo migration where:
- Source has a flat package with 80+ types (all in one package, no imports needed between them)
- Target splits into subpackages by domain
- IDE cross-project move tools don't work (see GE-20260929-ffbc2d)

### Root cause

Two distinct problems:

1. **Nested prefix collision:** If the source has subpackages (e.g. `social.drive`, `social.narrative`), a simple `replace("social.", "cognition.")` corrupts nested package names. The replacement for `social.drive.DriveAxis` produces `cognition.DriveAxis` (wrong) instead of `cognition.drive.DriveAxis`.

2. **Implicit same-package references:** Types that were in the same flat package referenced each other without imports. After splitting into subpackages, `CognitiveImpact` (in `.core`) references `MoodSignal` (in `.mood`) but has no import statement — the compiler can't resolve it.

### Fix

**Two-pass approach:**

**Pass 1 — Package replacement with ordered prefix matching.** Process source package prefixes longest-first to avoid nested collisions:

```python
OLD_PKG_PREFIXES = [
    "io.casehub.blocks.agentic.social.drive.adaptation",  # longest first
    "io.casehub.blocks.agentic.social.drive",
    "io.casehub.blocks.agentic.social.narrative",
    "io.casehub.blocks.agentic.social",                    # shortest last
]
```

Replace the `package` declaration with the target subpackage. Replace import statements using the same ordered prefix list.

**Pass 2 — Cross-subpackage import resolution.** Build an index of `TypeName → subpackage` by scanning all migrated files. Then for each file, find imports pointing at the root package (e.g. `import io.casehub.neocortex.cognition.DriveAxis`) and redirect to the correct subpackage (`import io.casehub.neocortex.cognition.drive.DriveAxis`).

### Why this is non-obvious

The naive approach (single find-replace on the old package prefix) appears to work until compilation reveals dozens of broken imports. The two failure modes are independent — you can fix prefix ordering and still hit the same-package reference problem. Both passes are needed for a clean migration.
