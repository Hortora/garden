### Symptom
A pipeline accumulates narrow fix commits — each fixing one edge case in
one step's state-probing logic, leaving other steps vulnerable to the same
edge case. Fix ratio exceeds 60%.

### Context
Multi-entity pipelines (e.g., multi-repo lifecycle orchestrators) where each
step independently probes entity state via subprocess calls (git branch
existence, commits ahead, dirty status). Each probe handles its own edge
cases. New configurations (zero commits ahead, no feature branch, already
landed) surface as crashes in whichever probe didn't anticipate them.

### What developers normally do
Probe entity state at the point of use — each step runs `git rev-list --count`
or `git branch --list` when it needs the answer. This feels natural because
each step "knows what it needs." But it means N steps × M edge cases = N×M
potential failure points, each discovered and fixed independently.

### Fix
Classify all entities into an exhaustive enum at pipeline entry. Every step
reads the classification — no step probes raw state directly.

```python
class RepoDisposition(Enum):
    HAS_WORK = "has_work"           # feature branch, commits ahead > 0
    EMPTY_BRANCH = "empty_branch"   # feature branch, zero commits ahead
    NO_BRANCH = "no_branch"         # no feature branch exists
    ALREADY_LANDED = "already_landed"

@dataclass(frozen=True)
class RepoState:
    path: Path
    name: str
    disposition: RepoDisposition
    commits_ahead: int
    # ... all state computed once
```

Steps that only apply to `HAS_WORK` repos filter by disposition. No probing,
no edge cases to miss. New dispositions are added to the enum — they're
visible to every step simultaneously.

### Why this is non-obvious
The point-of-use pattern feels simpler: each step asks one question and acts
on the answer. The cost is hidden — it only surfaces as a fix ratio that
creeps upward over months. In one real pipeline, 35 fix commits (63% of all
pipeline commits) were attributable to runtime probing. Each fix was correct
but narrow — the same edge case existed in other probes but hadn't crashed
there yet.

### Alternatives considered
- **Add edge cases to each probe as discovered** — the status quo. Correct but
  O(N×M) fixes. Each fix addresses one probe, leaving others vulnerable.
- **Shared helper that probes state** — centralizes the git call but not the
  classification. Each step still interprets raw results differently.

### Caveats
- Requires the state space to be enumerable. If entities can be in genuinely
  unbounded states, the enum approach breaks down.
- The classification must be immutable (`frozen=True`). If steps can mutate
  the classification, you re-introduce the same class of bugs.
- If entity state changes mid-pipeline (external mutations), a refresh
  mechanism is needed — but this is rare in practice for lifecycle pipelines.
