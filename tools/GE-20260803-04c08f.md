## epic_manager.status() safe_exit reports true mid-batch when a prior batch completed

### Symptom
`status()` returns `safe_exit: True` while work is actively in progress mid-batch — the work-end gate would allow closing without warning.

### Context
An epic has multiple batches. Batch 1 is complete. Batch 2 has issue #12 done and issue #13 active. `status()` reports `safe_exit: True` because `completed_batches > 0`.

### Root cause
`status()` computed `safe_exit` as `completed_batches > 0` — "has any batch ever completed." This is the wrong question for the work-end gate, which needs "are we at a batch boundary right now?"

Meanwhile, `advance()` correctly computed `safe_exit = batch_complete` per-transition — True only when the last issue in a batch is completed. The two functions had different semantics for the same concept.

### Fix
Replace the scalar check with a boundary check:

```python
def _is_at_batch_boundary(plan, completed_batches):
    if completed_batches == 0:
        return False
    current_issue = plan["current_issue"]
    if current_issue == 0:
        return True  # all done
    current_batch_num = plan["current_batch"]
    for batch in plan["batches"]:
        if batch["number"] == current_batch_num:
            if not batch["issues"]:
                return True
            first_issue = batch["issues"][0]
            return first_issue["number"] == current_issue and not first_issue["done"]
    return False
```

Safe exit is True when: at least one batch is complete AND the active issue is the first undone issue in its batch with no done issues in that batch (i.e., no work started in the current batch).

### Why this is non-obvious
`advance()` and `status()` both return a `safe_exit` field but compute it differently. `advance()` is called per-transition and gets it right. `status()` is called for state queries (gates, display) and had a simpler but incorrect formula. The bug is invisible during normal epic iteration — it only surfaces when a gate checks `status()` mid-batch after a prior batch completed.

### Alternatives considered
- **Use `advance()`'s return value for gates** — rejected because `advance()` mutates state (ticks checkboxes, updates markers). Gates need a read-only query.
- **Track `safe_exit` as persistent state in the file** — rejected as unnecessary; it's derivable from batch completion state and doesn't need to be stored.
