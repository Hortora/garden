### Symptom

Step B requires step A. Both are in the same pipeline run. Step A executes successfully and is marked done in the progress file. Step B's dependency check still fails because `ctx.done("step_a")` returns False.

### Context

The orchestrator engine reads progress from a file into `ctx.progress` (a dict) once at the start of `run_loop`. As mechanical steps complete, the engine writes updates to the progress file via `update_close_progress()` but does not update the in-memory `ctx.progress` dict. Within the same loop iteration, subsequent steps see the stale snapshot.

This matters when adding structural dependency checks (`requires`) because two mechanical steps in the same phase can both execute within a single `run_loop` call.

### What was tried (didn't work)

- Adding `requires` declarations and checking `ctx.done(req)` — always False for steps completed in the current invocation
- Re-reading the progress file each iteration — too expensive and creates TOCTOU issues

### Root cause

`ctx.progress` is populated once from `read_close_progress(workspace)` before the loop. `update_close_progress()` writes to the file but the dict is never refreshed. The `done()` method reads from the dict, not the file.

### Fix

Create a `_mark_done()` helper that updates both the file and the in-memory dict atomically:

```python
def _mark_done(ctx, step_name: str, status: str = "done") -> None:
    update_close_progress(ctx.workspace, step_name, status)
    ctx.progress[step_name] = status
```

Replace all `update_close_progress(ctx.workspace, step.name, "done")` calls in `run_loop` with `_mark_done(ctx, step.name)`.

### Why this is non-obvious

In the original design, `run_loop` yields to the caller after each judgment step. The caller re-invokes the orchestrator which re-reads progress fresh. Within-loop staleness was never a problem because mechanical steps didn't depend on each other — they just ran in list order. Adding structural dependencies (`requires`) exposes the snapshot problem for the first time.
