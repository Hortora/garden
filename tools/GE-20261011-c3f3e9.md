### Symptom

Step `land` requires `rebase`, but `rebase` only runs in non-MAIN modes. When the pipeline runs in MAIN mode, `rebase` is mode-filtered out and never appears in progress. The dependency check blocks `land` even though the dependency is structurally irrelevant in this mode.

### Context

Pipeline steps declare which modes they participate in (e.g., `rebase` has `modes={BRANCH, SLOT, SYNC, CYCLE}` but not MAIN). The engine filters steps by mode at entry. Steps also declare dependencies via `requires=("rebase",)`. When a required step is filtered out, checking `ctx.done(req)` returns False because the step was never executed — correctly, because it doesn't apply.

### Fix

Build `active_step_names` from the mode-filtered step list and only enforce requires for steps that are present:

```python
active_step_names = {s.name for s in steps}  # after mode filtering

for step in steps:
    if step.requires:
        unmet = [r for r in step.requires
                 if r in active_step_names and not ctx.done(r)]
```

Dependencies on steps outside the active set are considered satisfied — the step doesn't exist in this pipeline configuration, so its dependency is vacuously true.

### Why this is non-obvious

The intuitive approach is to treat all declared dependencies as hard constraints. But pipeline modes create configurations where some steps are structurally absent. Without the `active_step_names` filter, any step with a cross-mode dependency would need per-mode requires declarations or conditional requires logic. The set-based filter is simpler and correct: if the step isn't running, its dependents don't need to wait for it.
