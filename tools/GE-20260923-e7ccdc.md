## Progressive Resolution for Cognitive Knowledge Graphs

### Symptom / context

When building a knowledge graph that tracks goals, intentions, or plans,
the natural approach is uniform resolution — every goal gets the same
level of structural detail (sub-goals, dependencies, decomposition).
This creates two problems:

1. **Wasted computation** — decomposing distant or irrelevant goals into
   sub-goal graphs spends LLM/processing effort where no decision depends
   on the result.
2. **Graph noise** — fully decomposed distant goals clutter the graph
   with detail that obscures the structurally important nearby goals.

### Root cause / the non-obvious insight

Graphics rendering solved this decades ago with **level-of-detail (LOD)**:
render nearby objects at high fidelity, distant objects as low-poly
placeholders. The same principle applies to knowledge graphs.

Not all goals need the same structural detail. Resolution should depend on:

| Factor | Low resolution (single node) | High resolution (sub-goal graph) |
|--------|------------------------------|----------------------------------|
| Time proximity | Far off | Imminent |
| Overlap with other goals | None detected | Shared sub-goals/dependencies |
| Decision relevance | No pending decision needs structure | Prioritization requires understanding scope/cost |
| Execution readiness | Not being considered | About to be submitted for execution |

### The technique

Maintain a **variable-resolution knowledge graph** where:

1. **Distant/irrelevant goals** are single nodes with a prose description
   and metadata (priority, horizon, affect). No sub-goal decomposition.

2. **Approaching/overlapping goals** get progressively decomposed into
   sub-goal nodes connected by typed dependency edges (enables, blocks,
   requires, decomposes-into).

3. **Resolution is bidirectional** — managed by an async consolidation
   cycle (not real-time):
   - **Expand**: approaching goals or newly-overlapping goals trigger
     LLM-based cognitive decomposition → sub-goal nodes created
   - **Prune**: distant goals whose sub-goals haven't been accessed →
     collapse back to single node (detail re-derivable when needed)
   - **Merge**: shared sub-goals across parent goals detected via
     embedding similarity → merge nodes, create cross-parent edges
   - **Revise**: dependency state changes (blocker resolved, new info) →
     update graph structure
   - **Decay**: goals with no activity and declining affect → reduce
     priority, suggest dormancy

4. **Resolution level** tracked as a node property (`low`/`medium`/`high`)
   so downstream consumers know how much structural detail is available.

### Why this is non-obvious

Most knowledge graph systems maintain uniform detail — every node gets
the same treatment. The insight that cognitive effort should follow
decision relevance (not completeness) comes from:

- **ACT-R cognitive architecture** — activation-based retrieval means
  rarely-accessed structures decay. The brain doesn't maintain full
  resolution on everything.
- **Soar cognitive architecture** — subgoaling is triggered by impasses
  (decision needs), not maintained preemptively.
- **BDI agent architecture** — deliberation (goal selection) requires
  understanding goal structure, but only for goals under consideration.

The async consolidation cycle is key — resolution changes happen during
"sleep" (idle periods), not during active processing. This mirrors
human sleep consolidation where the brain prunes irrelevant detail and
strengthens relevant connections.

### Practical application

In a Java/Quarkus MindMap-based knowledge graph:

```java
@ApplicationScoped
@Priority(35)
public class GoalResolutionPhase implements ConsolidationPhase {
    // Runs during idle periods via ConsolidationScheduler
    // Steps: Prune → Expand → Merge → Revise → Decay
    
    private void expand(String tenantId) {
        // Find goals with urgency > 0.7 and resolution = "low"
        var approaching = store.search(
            MindMapQuery.of(tenantId, 100)
                .withSubgraphType("goal")
                .withProperties(Map.of("resolution", "low")));
        
        for (var goal : approaching) {
            if (parseDouble(goal.property("urgency").orElse("0")) > 0.7) {
                var result = decomposer.decompose(
                    goal.property("description").orElse(""), 
                    contextNodes, tenantId);
                // Create sub-goal nodes with decomposes-into edges
                // Update parent resolution to "high"
            }
        }
    }
}
```

### Alternatives considered

- **Full resolution always** — decompose every goal immediately. Wastes
  LLM calls on distant goals, clutters the graph. Doesn't scale.
- **No decomposition** — treat all goals as atomic. Loses the ability
  to detect shared sub-goals, estimate effort, or understand dependencies.
- **On-demand decomposition** — decompose only when explicitly requested.
  Misses the consolidation benefits (overlap detection, dependency
  discovery) that emerge from background processing.
