### Symptom
HANDOFF.md in the engine project contained issues from the work repo (#329, #330, #298, #152, #328). Branch detection showed a work-repo branch (`issue-97-workitem-event-mesh`) as the active workspace branch for an engine session. No error or warning surfaced.

### Context
Multi-repo setup where each project repo has a `wksp` symlink pointing to a subdirectory in a shared workspace git repo (e.g. `engine/wksp -> ../work/engine/`). The workspace holds per-project methodology artifacts (HANDOFF.md, blog, plans, specs). Tooling (`ctx.py`) resolves the workspace path by following the symlink.

### What was tried (didn't work)
Initially suspected the handover skill was writing to the wrong HANDOFF or that work-end was updating the wrong repo. Checked slot routing, work-end routing — all appeared correct. The tooling was doing exactly what it was told; it was being told the wrong thing.

### Root cause
On 2026-08-02, the engine `wksp` symlink was changed from `../work/engine` (correct — engine's subdirectory in the shared workspace) to `../work` (wrong — the workspace repo root, which is the work project's workspace). Every tool that followed the symlink — HANDOFF reads/writes, branch detection, issue cross-references — silently operated on work's context instead of engine's.

### Fix
Check the symlink target and restore:
```bash
# Diagnose — what does wksp point to now?
readlink engine/wksp
# → ../work  (wrong — should be ../work/engine)

# Trace when it changed via git history
git log --format="%h %ai %s" -- wksp
git show <commit>:wksp
# Walk commits to find when the target changed

# Fix
ln -sfn ../work/engine engine/wksp
```

### Why this is non-obvious
The symptom (wrong issues in HANDOFF) points at the handover skill, the work-end skill, or slot routing — not at a symlink. The symlink change was buried in a commit that also contained substantive code changes. All tooling continued working without errors; the only signal was semantically wrong content in an artifact that isn't validated at write time.

### Alternatives considered
- Checking if the handover skill was querying the wrong GitHub repo — ruled out because `OWNER_REPO` was correct; the issue references came from conversation context, not from `gh issue list`
- Checking if slots were routing to the wrong workspace — ruled out because slots live at a different path and don't share the `wksp` symlink
