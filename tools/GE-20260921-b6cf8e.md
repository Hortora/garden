# IntelliJ MCP ide_replace_text_in_file with DOTALL (?s) regex silently eats across Java method boundaries

## Symptom
Using `(?s)@ToolArg\(.*?"\) ` to strip multi-line `@ToolArg` annotations from Java source files destroys method body code. The non-greedy `.*?` matches across method boundaries because `")\` patterns appear inside string literals in the method body.

## Context
Bulk removal of `@ToolArg` annotations from a 2253-line Java file (`QhorusMcpTools.java`). Single-line annotations stripped cleanly, but 7 multi-line `@ToolArg` annotations required DOTALL mode to span lines.

## What was tried
- `@ToolArg\([^)]*\) ` (without DOTALL) — failed on annotations containing `)` inside strings like `"Comma-separated contributor names (BARRIER channels only)"`
- `(?s)@ToolArg\(.*?"\) ` (DOTALL non-greedy) — matched from `@ToolArg(name = "allowed_types",` through into the method body, stopping at the first `") ` inside a string literal in `throw new IllegalArgumentException("...")` several lines later

## Root cause
DOTALL `(?s)` makes `.` match newlines, so `.*?` scans across line boundaries. The "end" pattern `") ` (quote-paren-space) appears in Java string literals inside the method body — the regex engine stops there, not at the annotation's closing paren. The result is silent deletion of method body code between the annotation and the first matching string literal.

## Fix
Never use DOTALL regex for annotation removal on Java files via `ide_replace_text_in_file`. Instead:

1. Use a Python script with balanced-paren counting to process the file
2. Write the result to a temp file (non-`.java` extension to avoid hooks)
3. Move the result into place with `mv`

The Python approach correctly tracks parenthesis depth and only removes the annotation, preserving all method body code.

## Why this is non-obvious
Non-greedy `.*?` is normally the safe choice for avoiding over-matching. But DOTALL removes the line-boundary safety net, and Java source files contain the same characters (`"`, `)`) in both annotation syntax and string literals. The corruption is silent — no error from the replacement tool.

### Alternatives considered
- Using `ide_structural_search_replace` (SSR) for annotation removal — SSR is AST-aware and would be correct, but it doesn't support matching arbitrary annotation patterns with string concatenation across lines
- Removing annotations line-by-line without DOTALL — works for single-line annotations but can't handle multi-line `@ToolArg` with description string concatenation
