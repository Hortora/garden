### Symptom

During a wrap/close sequence, the LLM skipped `write_content` (diary) after `forage` failed — even though the two steps are independent. The orchestrator's IoC principle ("the LLM cannot skip what it cannot see") was violated.

### Context

A yield-based orchestrator drives a close/wrap sequence: Python yields one action at a time, the LLM executes it, then calls back. The `skip_step=<name>` parameter lets the LLM skip a step when it fails or the user declines. The orchestrator is supposed to prevent the LLM from making routing decisions.

### Root cause

`skip_step=` accepted any step name and marked it as skipped in progress — no validation that the step had been yielded by the orchestrator. The LLM could pre-emptively skip future steps it hadn't seen yet.

### Fix

Track `last_yielded` in close-progress. Every `_yield_judgment` and `_yield_user_input` writes the step name to `last_yielded` before returning. `validate_skip()` rejects `skip_step` when it doesn't match `last_yielded`. Don't clear `last_yielded` on skip — let the next yield overwrite it, preventing cascading skips.

```python
def validate_skip(workspace, step):
    progress = read_close_progress(workspace)
    last = progress.get("last_yielded", "")
    if last and step != last:
        return {"ERROR": "invalid_skip", "LAST_YIELDED": last}
    update_close_progress(workspace, step, "skipped")
    return None
```

### Why this is non-obvious

The IoC design was correct in principle — the orchestrator yields one step at a time, and the LLM can only act on what's yielded. But `skip_step` was a backdoor: it operated on step names as strings with no validation against the yield state. The LLM could rationalize "forage failed, skip all sweeps" and pre-emptively mark future steps as skipped.

### Why this fix

Not clearing `last_yielded` on skip is the key design choice. If you clear it, the LLM can chain: skip forage → last_yielded is empty → skip protocol (lenient path allows it) → skip write_content. Leaving `last_yielded` set to the skipped step means the next skip attempt hits a mismatch and is rejected. Only the orchestrator's next yield overwrites it.

### Alternatives considered

- **Consecutive skip counter** — refuse after N consecutive skips. Too arbitrary and doesn't prevent the first invalid skip.
- **Clear last_yielded on skip** — creates a lenient window where cascading skips are possible.
- **Return step_skipped without entering run_loop** — changes the API contract; every skip would need an extra orchestrator call.
