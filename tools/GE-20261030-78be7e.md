### Symptom / context
Building a binary data processing pipeline (e.g. audio download → denoise → STT transcription → text cleanup) typically leads to a custom pipeline framework with its own routing, retry, error handling, and resource cleanup logic.

### What developers typically do
Build a bespoke pipeline framework: a chain of processing stages with explicit wiring, custom retry logic, manual resource cleanup on failure, and configuration-driven routing. Or use a reactive-streams library (Project Reactor, Mutiny) which handles backpressure but not retry/timeout/routing at the orchestration level.

### The technique
Step-based workflow engines designed for agent/human task orchestration (playbooks, Temporal workflows, Airflow DAGs) can model binary data pipelines when step types declare typed I/O contracts:

1. **Each processing stage is a step type** with explicit `inputType()` and `outputType()` — e.g. `StreamingStep<String, InputStream>` for media download, `StreamingStep<byte[], TranscriptionResult>` for STT.

2. **The workflow engine provides orchestration for free** — per-step retry with configurable backoff, timeout, error handling, conditional routing via match/cases, and CloudEvent triggers.

3. **A compiler fusion pass** detects consecutive type-compatible steps (where `consumer.inputType().isAssignableFrom(producer.outputType())`) and fuses them into a single execution unit — near-native piped execution with automatic `AutoCloseable` resource cleanup on mid-chain failure.

4. **The pipeline is YAML-configurable** — consuming applications author their own pipeline definitions with application-specific retry/timeout requirements, without writing pipeline framework code.

The key insight: the typed step contract (`inputType → outputType`) is the same abstraction as a Unix pipe or a Java `Function<I, O>` — the workflow engine just adds orchestration semantics around it.

### Why this is non-obvious
Most developers think of workflow engines as human/agent task orchestrators (assign ticket → wait for review → escalate) and wouldn't consider them for binary data processing. The mental model is "workflows are for coordination, pipelines are for data." But the step execution model — input, transform, output, with decorators for retry/timeout — is exactly a pipeline stage. The workflow engine's existing infrastructure (triggers, routing, error handling, persistence) is strictly more capable than a custom pipeline framework.

### Alternatives considered
- **Custom pipeline framework**: purpose-built, but duplicates retry/timeout/routing logic that the workflow engine already provides
- **Reactive-streams (Mutiny/Reactor)**: handles backpressure and composition, but doesn't provide per-stage retry, timeout, or YAML-configurable routing
- **CDI observer chain**: decoupled but adds event hops and loses the typed composition
