### What
Extract handler details from SKILL.md into separate files (e.g., `handlers/review.md`, `handlers/handoff_write.md`). The SKILL.md dispatch table says "read `handlers/X.md`" — the LLM loads handler details only when the orchestrator yields that action. The SKILL.md itself has one instruction: call the orchestrator and follow its output.

### The technique
Before (700-line SKILL.md with inline handlers):
```markdown
## The Loop
Call orchestrator, dispatch by ACTION...

### Handler: handoff_write
[60 lines of detailed HANDOFF.md writing instructions]

### Handler: sweep_config
[30 lines of sweep checklist UI]
```

After (130-line SKILL.md with lazy references):
```markdown
## The Loop
Call orchestrator, dispatch by ACTION...

| ACTION | Do |
|--------|----|
| handoff_write | Read `handlers/handoff_write.md` |
| sweep_config  | Read `handlers/sweep_config.md`  |
| forage        | Invoke forage SWEEP              |
```

The handler files exist in `handlers/` but the LLM doesn't read them until the orchestrator yields that action.

### Why this is non-obvious
The intuition is that more detail in the SKILL.md means better execution. The opposite is true: the LLM reads all 700 lines, identifies the most concrete actionable instruction (e.g., "write HANDOFF.md using this template"), and goes straight to that — skipping the abstract orchestrator loop. Reducing the SKILL.md to one instruction ("call the orchestrator") removes alternative paths the LLM could shortcut to.

This was observed repeatedly: LLMs skipping the orchestrator loop to write HANDOFF.md directly, skipping review sub-steps because the forcing function handler described what happens after review, and jumping to sweep results without presenting the checklist. In each case the LLM latched onto the most concrete handler and skipped the machinery that sequences them.

### Why this fix
The simpler alternative — adding "DO NOT SKIP THE ORCHESTRATOR" warnings — was tried and failed. Warning text is processed at the same priority as handler text. The LLM reads the warning, reads the handler, and decides the handler is more actionable. Removing the handler text from the SKILL.md is the only reliable prevention: the LLM can't shortcut to instructions it hasn't read.

### Alternatives considered
- Stronger warnings/HARD-GATE blocks in the SKILL.md — tried, failed. LLMs process warnings as suggestions, not constraints.
- Hook-based enforcement (blocking commits without orchestrator progress) — complementary, not sufficient alone. The hook catches the result but doesn't prevent the LLM from wasting a session trying to bypass the orchestrator.
