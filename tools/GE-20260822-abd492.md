## ide_edit_member destroys class when member name matches class name

### Symptom
Calling `ide_edit_member` with `member=ClassName` on `class=ClassName` replaces the **entire class declaration** — all fields, methods, inner classes, and the class signature itself are deleted. Only the replacement content survives.

### Context
When editing a constructor that has the same name as its enclosing class (all Java constructors), the `member` parameter is ambiguous. `ide_edit_member` resolves the ambiguity by matching the **class declaration** rather than the constructor, because the class declaration is also a valid match for `member=ClassName`.

The result message confirms the destructive interpretation: `"Replaced class 'ClassName' entirely"`.

### Root cause
`ide_edit_member` uses the member name to locate the target AST node. When the member name equals the class name, the tool finds two candidates: the constructor and the class declaration itself. It selects the class declaration, replacing the entire class body with the provided content.

### Fix
Use `ide_replace_text_in_file` for constructor edits instead of `ide_edit_member`:

```
ide_replace_text_in_file(
    file: "path/to/File.java",
    searchText: "<old constructor signature and body>",
    replaceText: "<new constructor signature and body>"
)
```

Alternatively, if you must use `ide_edit_member`, use the `line` parameter to disambiguate — pass the line number of the constructor, not just the member name:

```
ide_edit_member(
    file: "path/to/File.java",
    class: "ClassName",
    member: "ClassName",
    line: 54,   // constructor line, not class declaration line
    content: "<new constructor>"
)
```

### What was tried (didn't work)
- `ide_edit_member` with `member=ClassName` — destroyed the class
- Had to `git checkout -- path/to/File.java` to restore

### Why this is non-obvious
The tool accepts the call without warning and reports success. The response says "Replaced class 'ClassName' entirely" which could be misread as "replaced the constructor within the class." The data loss is silent and total — discovered only when the next build fails with missing methods/fields.
