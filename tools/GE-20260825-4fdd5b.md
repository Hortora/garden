# Python set iteration order breaks state tracking when multiple transitions fire atomically

## Symptom
An audit script that tracks lifecycle state progression via progress-file diffs produced non-deterministic results — sometimes advancing correctly through `closing:review → closing:verified → closing:promoted`, sometimes regressing to an earlier state. The orchestrator's dry-run sequence would cycle infinitely instead of completing.

## Context
A close-sequence orchestrator fires multiple lifecycle transitions within a single call (e.g. `review_pass`, `promote_pass` in one invocation). The audit script detects which transitions fired by diffing `.close-progress` keys between calls, stored as a Python `set`. It then updates `current_meta_state` by iterating the diff and applying each lifecycle advancement.

## What was tried (didn't work)
Iterating `new_done` (a `set`) and updating `current_meta_state` for each lifecycle key found:
```python
for s in new_done:
    if s in LIFECYCLE_ADVANCEMENT:
        current_meta_state = LIFECYCLE_ADVANCEMENT[s]
```
Last-write-wins with non-deterministic iteration: if `promote_pass` (→ `closing:promoted`) processes before `review_pass` (→ `closing:verified`), the state goes backwards.

## Root cause
Python sets have no guaranteed iteration order. When multiple lifecycle transitions are in `new_done`, the last one processed wins. If a lower-phase transition iterates last, `current_meta_state` regresses. The orchestrator's stale-progress detector then sees progress ahead of `meta_state` and deletes all progress, causing an infinite loop.

## Fix
Compare all candidates against a phase ordering and take the highest:
```python
PHASE_ORDER = ["closing:review", "closing:verified", "closing:promoted",
               "closing:pushed", "closing:merged", "closing:stamped", "idle", "drained"]

highest = current_meta_state
for s in new_done:
    if s in LIFECYCLE_ADVANCEMENT:
        candidate = LIFECYCLE_ADVANCEMENT[s]
        if PHASE_ORDER.index(candidate) > PHASE_ORDER.index(highest):
            highest = candidate
current_meta_state = highest
```

## Why this is non-obvious
The code looks correct on first read — iterating a set and updating state for each match is a natural pattern. The bug only manifests when multiple lifecycle keys appear in the same diff, which requires the orchestrator to fire multiple transitions in one call. In unit tests with a single transition per call, the code works perfectly.

### Why this fix
Phase-ordering comparison is O(n) in phase count (small constant) and handles any number of concurrent transitions correctly. An alternative (sorting the set by phase before iterating) would also work but adds unnecessary complexity — we only need the maximum.

### Alternatives considered
- Sorting `new_done` by phase order before iterating — works but over-engineered for "take the max"
- Using an ordered container (list) instead of set for progress tracking — would fix this but sets are correct for the diff operation
