### Symptom
`ide_move_file` with `project_path=/path/to/engine` and `file=api/src/main/java/...` creates
the destination file in a different project's `api/` module (e.g. the platform repo) instead of
the engine's `api/` module. The source file is deleted from the correct project.

### Context
Multi-project IntelliJ workspace (platform + engine + blocks + neocortex) where both `platform`
and `engine` have an `api/` Maven module. The `project_path` parameter scopes which project
handles the request, but the file path `api/src/main/java/...` is ambiguous — IntelliJ resolves
it to whichever project's module it finds first.

### What was tried (didn't work)
- Setting `project_path` to the engine root — files still went to platform
- Using the module-prefixed path (`api/src/main/java/...`) — ambiguous across projects

### Root cause
IntelliJ's VFS resolves relative file paths across ALL open projects in the workspace, not just
the one specified by `project_path`. The `project_path` is a routing hint for the MCP server,
but the underlying refactoring engine searches the full workspace for the path match.

### Fix
Use the path format that IntelliJ reports via `ide_find_file` — typically `src/main/java/...`
without the Maven module prefix. This resolves unambiguously within the specified project
because the source root is project-scoped. Verify with `ide_find_file` first to get the exact
path IntelliJ uses for the file.

### Why this is non-obvious
The `project_path` parameter suggests that all operations are scoped to that project. The fact
that file resolution still spans the entire workspace is undocumented and contradicts the
expected behaviour of project-scoped operations.
