### Symptom
Complex UI component logic (z-order management, spatial navigation algorithms, layout presets) is hard to TDD because the test environment (happy-dom) can't fully simulate the third-party library (Dockview, xterm.js).

### Context
Building a workspace view component (`trellis-workspace-view`) with Dockview for frame management. The component has significant pure logic: z-order counters with compaction, spatial navigation via Euclidean distance in directional half-planes, 5 layout preset algorithms. Testing all of this through the component's DOM interface is fragile and slow.

### Fix
Extract pure logic into separate modules. Each module exports functions testable without any DOM:

```
workspace-zorder.ts      → bringToFront(), compactFrames(), normalizeForSave()
workspace-spatial-nav.ts → findSpatialTarget()
workspace-organisers.ts  → sideBySide(), stacked(), grid(), mainSidebar(), focus()
```

Each module gets its own `.test.ts` file with focused unit tests (14 + 9 + 12 = 35 tests). The component test file verifies wiring only: "does createFrame() track z-indices?", "does togglePin() switch z-tiers?", "does _serializeLayout() normalize?" — 22 integration-style tests.

Result: 57 new tests with full coverage, no DOM mocking needed for the core logic. Test execution: ~500ms total.

```typescript
// workspace-zorder.ts — pure, no DOM dependency
export function bringToFront(counter: number, pinned: boolean) {
  const next = counter + 1;
  const zIndex = pinned ? 10000 + next : next;
  return { zIndex, counter: next, needsCompaction: next > 5000 };
}

// workspace-view.ts — imports and wires
import { bringToFront as zBringToFront } from './workspace-zorder.js';

bringToFront(frameId: string) {
  const pinned = this._pinnedFrames.has(frameId);
  const result = zBringToFront(this._normalMaxZ, pinned);
  // ... apply to internal state and DOM
}
```

### Why this is non-obvious
The natural approach is to test everything through the component. When the component's DOM environment is limited (mock libraries, no ResizeObserver), developers often skip tests or write fragile DOM-inspection tests. Extracting pure functions feels like unnecessary abstraction until you see the test coverage difference: 35 pure function tests execute in <100ms with zero flakiness vs. DOM-based tests that depend on mock fidelity.
