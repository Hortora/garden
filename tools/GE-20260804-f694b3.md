## tmux new-session -c sets default-path but shell inherits parent process CWD

**ID:** GE-20260804-f694b3
**Stack:** tmux 3.x, Java ProcessBuilder

### Symptom

`tmux new-session -d -s name -c /desired/path` creates a session, but the shell inside it reports `getcwd: cannot access parent directories: No such file or directory`. The pane's current path (via `#{pane_current_path}`) shows the Java process's working directory, not `/desired/path`.

### Context

Creating tmux sessions from a Java backend (ProcessBuilder) or any headless process where the parent's CWD may not match the desired session directory. Common when the backend runs from a build directory, worktree, or temporary location that may not exist at the time the tmux shell starts.

### Root cause

tmux's `-c` flag sets the session's `default-path` option — which is used as the starting directory for **new windows and panes created later**. The initial shell spawned by `new-session` inherits `getcwd()` from the process that ran tmux, not from the `-c` path. If the parent process's CWD no longer exists (e.g. a deleted git worktree), the shell starts with a broken working directory.

### Fix

Send an explicit `cd` after session creation:

```java
public void createSession(String name, String workingDir)
        throws IOException, InterruptedException {
    run("tmux", "new-session", "-d", "-s", name, "-c", workingDir);
    sendKeys(name, "cd " + workingDir + " && clear\n");
}
```

The `clear` removes the `cd` command and any getcwd error from the visible terminal output.

### Why this is non-obvious

The `-c` flag appears to do what you want — tmux's man page says it sets "the working directory for the session." The actual behaviour (sets default-path for future windows, not initial shell CWD) is only apparent when the parent process's CWD differs from the `-c` path. When they match (the common case), `-c` appears to work correctly.
