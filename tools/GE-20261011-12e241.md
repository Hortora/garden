### Symptom

Step dependency checks always fail when the required step uses per-repo fan-out. A step declaring `requires=("rebase",)` returns an unmet dependency error even after rebase completes successfully for all repos.

### Context

Pipeline orchestrators that fan out steps across multiple repos track progress with compound keys: `rebase:engine`, `rebase:soredium`, etc. The base step name `rebase` is never written to progress. A naive `ctx.done("rebase")` always returns False.

### What was tried (didn't work)

- Checking `ctx.done(req)` directly against the progress dict
- Checking `ctx.steps_executed` (populated within the loop but not reliable across invocations)

### Root cause

The progress tracking system uses flat keys with `step:repo` naming for per-repo fan-out. There is no single `step=done` entry for the base step name. Any dependency check that looks for the base name will never find it.

### Fix

Add a `_per_repo_done()` helper that scans progress for all keys matching `step:*` and verifies all are in a done state:

```python
def _per_repo_done(ctx, step_name: str) -> bool:
    prefix = f"{step_name}:"
    repo_keys = [k for k in ctx.progress if k.startswith(prefix)
                 and not k.endswith("_attempt") and not k.endswith("_produced")]
    if not repo_keys:
        return False
    done_states = ("done", "skipped", "skipped_error")
    return all(ctx.progress[k] in done_states for k in repo_keys)
```

The requires check uses both: `ctx.done(r) or _per_repo_done(ctx, r)`.

### Why this is non-obvious

The per-repo fan-out mechanism is an implementation detail of the orchestrator callbacks, invisible to the engine layer where dependency checking runs. The engine has no concept of "per-repo" — it just sees steps. The compound key convention is implicit, not documented in the step definition.

### Alternatives considered

- Marking the base step name done after all repos complete: rejected because it would require the fan-out callback to know when all repos are done, coupling the callback to the step list
- Using `ctx.steps_executed` instead of progress: rejected because it only tracks the current invocation, not prior invocations in a multi-call orchestrator loop
