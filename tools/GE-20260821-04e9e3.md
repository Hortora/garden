### Symptom
Running `git stash -u` to set aside a prior session's broken changes also captures the current session's in-progress IntelliJ MCP edits. After `git stash pop`, restoring the stash, and `git restore .`, the current session's work is lost.

### Context
IntelliJ MCP tools (`ide_edit_member`, `ide_insert_member`, `ide_replace_text_in_file`) write directly to disk without git staging. When prior session changes exist as unstaged modifications alongside current session MCP edits, `git stash -u` captures both indistinguishably. A subsequent `git restore .` to discard the prior session's changes also discards the current session's uncommitted MCP work.

### Root cause
MCP tools bypass git — they write to the filesystem, not to the index. Git cannot distinguish between "changes I made this session via MCP" and "changes from a prior session." `git stash` treats all unstaged modifications equally.

### Fix
**Always commit MCP changes before stashing.** The workflow:

1. Stage and commit your current session's MCP edits (even as WIP)
2. THEN stash or restore prior session changes
3. Your committed work is safe regardless of stash/restore operations

Alternatively, stage specific files before stashing:
```bash
git add path/to/files-I-changed-via-MCP
git stash --keep-index  # stashes only unstaged changes, keeps index
```

### Why this is non-obvious
In normal IDE workflow, developers save files and git-add them — the two actions are conceptually linked. MCP tools decouple them completely: the file is modified on disk but git knows nothing about it. The mental model of "stash my uncommitted work" breaks because MCP edits ARE uncommitted work, but the developer thinks of them as "done" because the tool reported success.
