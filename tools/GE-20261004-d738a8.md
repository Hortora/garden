### Symptom
Aggregate statistical correlation across N event logs shows a high-frequency generic command as the modal candidate near target events, masking the real causal command.

### Context
When correlating two event streams (e.g., server-side "upgrade completed" events with client-side "command issued" events), the standard modal algorithm (GE-20260522-a575c3) collects all commands within a time window and picks the most frequent. In noisy streams where generic commands fire constantly (e.g., a train-unit command firing thousands of times), the generic command dominates the modal even though the actual causal command fires exactly once per target event.

### What was tried (didn't work)
- Aggregate correlation across 118 instances — returned the wrong event (a train command) as the modal candidate for upgrade research
- Frequency-based discovery — same noise floor, same wrong answer
- Wider/narrower correlation windows — doesn't help when noise is frequency-dominated
- Excluding known event types from candidates — helps partially but the discovery pipeline also filtered null-identifier events, hiding valid commands

### Root cause
The signal-to-noise ratio is too low for aggregate correlation. The causal command fires once per event; the generic commands fire hundreds of times in the same window. No statistical threshold separates them.

### Fix
Dump ALL events from a single instance where the target is known to occur. Filter by expected duration derived from domain knowledge (e.g., research time = 1590 game loops). The causal command appears at exactly the expected temporal offset — immediately identifiable by inspection.

```
# Pseudocode
for each target_event in oracle_ground_truth:
    expected_cause_time = target_event.completion - known_duration
    for cmd in ALL_commands(same_player, window=[0, 5000]):
        if abs(cmd.time - expected_cause_time) < tolerance:
            print(cmd)  # This is the signal
```

### Why this is non-obvious
The standard approach (aggregate → modal) is the established pattern (GE-20260522-a575c3). The failure mode is silent — the algorithm returns a confident result (high count), but the result is wrong. You don't know the modal is noise until you zoom into a single case and see that the expected-time filter reveals a completely different event.

### Alternatives considered
- Building-ownership inference — attempted but wrong premise; the causal event existed in the data, it was just invisible to the discovery pipeline's filter
- Time-window deduplication — doesn't address the root cause (missing signal, not duplicate signal)
