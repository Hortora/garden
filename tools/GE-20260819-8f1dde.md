## JSONL vs JSON for append-heavy persistence

### Symptom / context
Multiple concurrent sessions writing findings to the same JSON file caused silent data loss — read-modify-write cycles where session A reads, session B reads, both modify, A writes, B overwrites A's changes.

### Root cause
JSON array format (`[{...}, {...}]`) requires reading the entire file, parsing, appending, serializing, and writing the entire file back. The lock must be held for the entire duration — O(file) lock hold time.

### Fix
Switch to JSONL (one JSON object per line). Writers blind-append a single line under an advisory flock. Lock hold time is O(line) — a single write syscall, microseconds.

```python
import fcntl, json
from pathlib import Path

def append_finding(path: Path, finding: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    with open(path, "a") as fh:
        fcntl.flock(fh, fcntl.LOCK_EX)
        try:
            fh.write(json.dumps(finding) + "\n")
        finally:
            fcntl.flock(fh, fcntl.LOCK_UN)
```

Dedup and status resolution move to the reader side — readers group entries by a dedup key, take the latest timestamp for status, and the highest severity across the group.

Compaction (archiving old resolved entries) is the only read-rewrite operation and uses atomic rename (`os.rename`) under the same flock.

### Why this is non-obvious
The natural instinct is to use a JSON array — it's simpler to read and reason about. The concurrent write race only surfaces when multiple sessions work in the same workspace, which is common in slot-based multi-repo workflows but rare in single-developer setups. The fix requires shifting dedup responsibility from writer to reader.

### Alternatives considered
- SQLite: heavier dependency, overkill for append-heavy workloads with infrequent reads
- JSON with file locking: works but O(file) lock hold time causes contention under concurrent writes
- Separate files per finding: eliminates races but creates filesystem clutter and makes reading expensive
