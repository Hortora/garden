### Symptom
Work-end fails because the workspace feature branch has no implementation commits — only a stale close stamp from a previous issue. Design artifacts (specs, plans, decisions) are missing from the workspace branch.

### Context
A multi-repo project uses a `wksp` symlink in the project repo to point to a companion workspace repo. The symlink was accidentally pointing to a subdirectory of a different project repo (`casehub/work/engine` — a module inside the casehub-work project) instead of the actual workspace repo (`public/casehub/engine`).

### What was tried (didn't work)
- Running work-end — failed with `clean_tree: fail` and mismatched branch state
- Checking workspace branch commits — found only a close stamp from issue #333, not #510
- Creating a fresh workspace branch from main — the design artifact commits were on the wrong repo's main

### Root cause
The `wksp` symlink resolved to a valid git-managed directory, so all git operations succeeded — `git checkout -b`, `git add`, `git commit` all worked. But the git repo was the casehub-work project, not the workspace. Scaffold commits, spec commits, and plan commits all landed in the wrong repo undetected.

Detection only happened at work-end when the workspace branch was found to have no relevant commits.

### Fix
Verify the symlink target is the correct workspace repo, not just a valid git directory. Check that `git -C $(readlink wksp) remote get-url origin` matches the expected workspace remote, not a project remote.

### Why this is non-obvious
Every git operation succeeds. The directory exists, is git-managed, and accepts commits. The wrong-repo condition is invisible until branch closure — potentially an entire session later. Files written to disk appear in the right place (the symlink resolves correctly for filesystem access), but they're tracked by the wrong git repo.
