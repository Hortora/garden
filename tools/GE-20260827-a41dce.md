## ide_replace_text_in_file edits IntelliJ document buffer not disk — git rebase commits stale conflict markers

### Symptom

After resolving a git rebase conflict using `ide_replace_text_in_file`, the conflict markers are still present in the committed file. The build fails with syntax errors from the unresolved `<<<<<<<`/`=======`/`>>>>>>>` markers, despite the tool reporting "Replaced 1 occurrence(s)" successfully.

### Context

During `git rebase`, a conflict is detected. The user resolves it by calling `mcp__intellij-index__ide_replace_text_in_file` to replace the conflict block with the correct content. The tool reports success. Then `git add <file> && git rebase --continue` is run. The rebase completes, but the committed file still contains the original conflict markers.

### What was tried (didn't work)

- Calling `ide_replace_text_in_file` with the exact conflict marker text as `searchText` and the resolved content as `replaceText` — tool reports success but the file on disk is unchanged
- Running `git add` immediately after the IDE edit — stages the stale disk version

### Root cause

`ide_replace_text_in_file` operates on IntelliJ's in-memory Document model, not the filesystem directly. The edit is applied to the document buffer and is visible to subsequent IDE operations (diagnostics, navigation). However, IntelliJ flushes document changes to disk asynchronously — there is no guarantee the file is written before the next non-IDE tool call runs.

When `git add` reads the file from disk immediately after the IDE edit, it sees the pre-edit state (with conflict markers intact). The `git rebase --continue` commit then captures the unresolved conflict.

### Fix

Use the `Edit` tool (Claude Code's built-in file editor with `replace_all: true`) for git conflict resolution instead of `ide_replace_text_in_file`. The `Edit` tool writes directly to disk, so `git add` always sees the resolved content.

```
Edit(file_path=<path>, old_string=<conflict block>, new_string=<resolved content>, replace_all=true)
```

Alternatively, call `ide_sync_files` after `ide_replace_text_in_file` to force IntelliJ to flush its document buffers to disk before running git commands. But this adds an extra step that's easy to forget.

### Why this is non-obvious

The tool reports "Replaced 1 occurrence(s)" — complete success. The symptom (conflict markers in the committed file) appears in a different tool (`git`) long after the edit, making the causal chain hard to trace. The developer's mental model is "I edited the file, then staged it" — the async document buffer is invisible.

### Alternatives considered

- Always using `Edit` tool for all source file edits — too broad; `ide_replace_text_in_file` works correctly for normal (non-rebase) edits because IntelliJ flushes before its own operations. The issue is specific to crossing from IDE operations to git operations.
- Calling `ide_sync_files` before every `git add` — defensive but adds ceremony. Better to use the right tool for the context.
