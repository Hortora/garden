### Context
Java records are immutable — no setters, no `with()` methods, no copy-and-modify. When you need to wrap or replace one component of a record (e.g. decorating a strategy field), the only option is to construct a new instance passing all other components through unchanged.

### Technique
Construct a new record instance, copying all components except the one being decorated:

```java
// ExecutionModel is a record with 10 components
// Want to wrap the routing strategy with a resource-limiting decorator
var capped = new ExecutionModel<>(
    wrappedRouting,              // ← decorated component
    model.decomposition(),       // ← passed through
    model.activation(),
    model.aggregation(),
    model.termination(),
    model.candidateSupplier(),
    model.failurePolicy(),
    model.listeners(),
    model.task(),
    model.patternType()
);
```

This is the Java record equivalent of Kotlin's `copy()` or Scala's `copy()`. It's verbose but type-safe — the compiler catches missing or mistyped components.

### Why this is non-obvious
Developers reaching for immutable decoration in Java typically look for:
1. A `with()` or `toBuilder()` method — records don't have these
2. Lombok's `@With` — not applicable to records
3. Subclassing — records are implicitly final

The full-constructor approach feels wrong ("surely there's a better way") but is actually the idiomatic pattern. The verbosity is the cost of immutability without language-level copy syntax.

### When to use
- Decorating a single strategy/policy on a configuration record
- Testing with modified configuration (swap one component for a mock)
- Applying cross-cutting concerns (wrapping routing, activation, etc.)

### When NOT to use
- If you control the record: add a `withX()` method instead
- If the record has >12 components: consider a builder pattern instead of raw construction
