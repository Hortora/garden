### Symptom
After `git rebase origin/main`, the child branch has zero commits ahead of main. All work-in-progress commits vanish silently — git reports "skipped previously applied commit" as hints but does not error.

### Context
Branch B is stacked on branch A (B branched from A's tip). Branch A is squash-merged to main (all of A's commits condensed into one). When B runs `git rebase origin/main`, git sees B's commits as "previously applied" because A's squashed content already covers the tree state those commits produced.

### What was tried (didn't work)
- `git rebase origin/main` — all commits dropped with "skipped previously applied commit" hints
- No `--reapply-cherry-picks` flag was passed (the hint mentions it but it's easy to miss)

### Root cause
Git's patch-id-based deduplication during rebase compares the diff of each commit against what's already on the target. When the parent branch was squash-merged, the squash commit's diff encompasses all the changes that the child's base commits also produce. Git concludes they're already applied and skips them — including the child's own unique commits if they touch the same files.

### Fix
Use `git cherry-pick <range>` instead of `git rebase` when the parent was squash-merged:

```bash
# Find the pre-rebase HEAD from reflog
git reflog | grep "rebase (start)"
# e.g. HEAD@{4}: rebase (start): checkout origin/main
# The commit before that is the pre-rebase HEAD

# Reset to main and cherry-pick the child's commits
git reset --hard origin/main
git cherry-pick <first-child-commit>..<pre-rebase-HEAD>
```

Alternatively, pass `--reapply-cherry-picks` to rebase:
```bash
git rebase --reapply-cherry-picks origin/main
```

### Why this is non-obvious
The data loss is silent — git doesn't error, it prints "skipped previously applied commit" as a hint that's easy to miss in verbose output. The branch appears to rebase successfully with zero commits, which looks like "nothing to do" rather than "everything was dropped". The reflog is the only recovery path.
