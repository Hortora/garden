## Symptom

After running `ide_optimize_imports` on a Java source file in a slot-cloned repository, wildcard imports are silently removed:

- `import io.casehub.aml.api.model.*;` → removed
- `import java.util.*;` → removed
- `import static org.hamcrest.Matchers.*;` → removed

Maven compilation then fails with cascading "cannot find symbol" errors for every type that was resolved only via the wildcard.

## Context

Slot-based workflows clone a repo into an isolated directory (e.g. `slots/6/aml/`) for parallel work. When IntelliJ opens these via `ide_open_workspace`, the project's language level defaults to '5' (Java 1.5) instead of inheriting from `pom.xml`'s `maven.compiler.source`/`target` (21).

At language level '5', records, sealed interfaces, and types that the IDE can't resolve through its index appear as unknown symbols. The import optimizer concludes the wildcard imports are unused (because it can't see any resolved references) and removes them.

## What was tried (didn't work)

1. Running `ide_optimize_imports` expecting it to clean up unused imports only — instead it removed needed ones
2. Restoring individual imports manually after each breakage — tedious and error-prone with cascading failures

## Root cause

IntelliJ's `optimize_imports` action trusts its own type resolution to determine import usage. In slot projects with language level '5', the type resolver cannot see Java 14+ records or types behind wildcard imports that it can't resolve at that language level. The optimizer sees zero usages → removes the import → compilation fails.

## Fix

Avoid `ide_optimize_imports` in slot-cloned projects entirely. If accidentally used:

1. Run `mvn test -pl <module> -am` immediately to detect breakage
2. Check `git diff` for removed wildcard imports
3. Restore removed imports using `ide_replace_text_in_file`

The `reformat=true` default on `ide_edit_member` and `ide_insert_member` also triggers import optimization — set `reformat: false` if the file uses wildcard imports that must be preserved.

### Why this is non-obvious

`ide_optimize_imports` is safe in fully-configured IntelliJ projects. The destructive behaviour only manifests in slot clones where the language level misconfiguration is invisible — there's no warning, no error, just silently removed imports followed by unrelated-looking compile failures.
