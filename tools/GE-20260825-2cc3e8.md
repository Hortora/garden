## Orchestrator stubs pass sequence tests — tests verify action order but not script invocations

### Symptom
A data-driven orchestrator with a STEPS list passes all tests (23 tests, 100% green) despite every mechanical step being stubbed — marking steps as "done" in a progress file without calling any subprocess.

### Context
When building an orchestrator that walks a step sequence and yields ACTION= lines at judgment points, the natural testing approach is: mark prior steps done, call the orchestrator, assert the next ACTION= is correct. This verifies the sequence logic perfectly but never checks whether mechanical steps actually invoke their scripts.

### Root cause
The tests operate at the wrong abstraction layer. They test the orchestrator's sequencing logic (which action comes next given this progress state) but not its execution logic (does this step call subprocess.run with the correct arguments). A step that does `update_close_progress(ws, "land", "done")` and a step that does `_run_script(["work_end_execute.py", "land", ...])` then `update_close_progress(ws, "land", "done")` produce identical progress state — the tests can't distinguish them.

### Fix
Integration tests must mock `_run_script` (not the progress file) and assert the mock was called with specific arguments:

```python
def test_land_calls_correct_script(tmp_path, monkeypatch):
    calls = []
    def capture(cmd, workspace, **kw):
        calls.append(cmd)
        return {"LANDED": "yes", "LANDED_SHA": "abc123"}
    monkeypatch.setattr("work_end_orchestrator._run_script", capture)
    # ... setup progress to reach the land step ...
    run_orchestrator(args)
    land_calls = [c for c in calls if "land" in str(c)]
    assert any("work_end_execute.py" in str(c) for c in land_calls)
```

### Why this is non-obvious
The sequence tests feel comprehensive — they walk the full close sequence and verify every action in order. "All tests pass" creates false confidence. The gap is invisible until a real close fails because scripts were never called.

### Why this fix
Mocking at the subprocess boundary (not the progress boundary) is the only way to verify execution without running real scripts. The test asserts the command that would be executed, not the side effect of execution.

### Alternatives considered
- Running real scripts in tests: too slow, requires real git repos, flaky
- Checking progress file contents: same false-green problem — stubs write identical progress
- Code coverage: stubs are covered code — they execute, they just don't do useful work
