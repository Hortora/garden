### Symptom

A Maven module has pre-existing compilation errors in files you didn't modify (e.g. `WorkerGrantOrchestrator.java` has `ResourceId` type mismatches from a dependency update). Your new files (`DefaultErrorClassifier.java`) are correct but Maven cannot compile the module at all — `mvn test -pl runtime` fails before reaching your test.

### Context

Multi-module Maven project where one module has accumulated compilation errors from upstream dependency changes not yet adapted. Your changes are in the same module but unrelated to the failing code. Maven compiles the entire module — it cannot skip failing files to test yours.

### Fix

Use `ide_diagnostics` with the `file` parameter and `severity: "errors"` to verify individual files:

```
ide_diagnostics(
    project_path: "/path/to/project",
    file: "runtime/src/main/java/.../DefaultErrorClassifier.java",
    severity: "errors"
)
```

IntelliJ analyses the file independently using its PSI model — it resolves imports, checks types, and reports errors without requiring the full module to compile. If `problemCount: 0`, the file is correct regardless of other files in the module.

Check the test file the same way to verify it also compiles.

### Why this is non-obvious

The natural reaction to "Maven can't build the module" is either to fix the pre-existing errors first (scope creep) or to defer testing until someone else fixes them (blocked). Using IntelliJ's per-file analysis as a compilation verification bypass is not an obvious alternative because `ide_diagnostics` is primarily thought of as a linting/inspection tool, not a compilation checker.
