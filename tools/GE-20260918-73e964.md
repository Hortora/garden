## Symptom

You pin a dependency version in a parent BOM's `<dependencyManagement>`:

```xml
<!-- parent-bom/pom.xml -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>io.quarkus.platform</groupId>
            <artifactId>quarkus-bom</artifactId>
            <version>3.39.3</version>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
        <!-- Explicit override — should win over quarkus-bom's 5.5.6 -->
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>rest-assured</artifactId>
            <version>6.0.1</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

A consuming POM imports this parent BOM:

```xml
<!-- consumer/pom.xml -->
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>parent-bom</artifactId>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

`mvn dependency:tree` shows `rest-assured:5.5.6` — the quarkus-bom version wins. The explicit 6.0.1 override is silently ignored.

## Context

Within the parent BOM itself, explicit entries DO override imported BOM versions (first-party Maven behaviour). But when the parent BOM is consumed via `<scope>import</scope>` by another POM, the flattened result loses the override precedence.

## Root cause

Maven BOM import flattens the imported BOM's dependency management. The quarkus-bom import within the parent BOM is processed first (import order), setting `rest-assured` to 5.5.6. The explicit `rest-assured:6.0.1` declaration should override it within the parent's own context — and it does if you build the parent directly. But when the parent is itself imported as a BOM, the consuming POM receives the flattened result where the import-order resolution already happened.

## Fix

Pin the version override in the **consuming POM's** `<dependencyManagement>`, **before** the BOM import that manages the conflicting version:

```xml
<!-- consumer/pom.xml -->
<dependencyManagement>
    <dependencies>
        <!-- Override BEFORE the BOM import -->
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>rest-assured</artifactId>
            <version>6.0.1</version>
        </dependency>
        <!-- BOM import follows -->
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>parent-bom</artifactId>
            <type>pom</type>
            <scope>import</scope>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Explicit declarations in the consuming POM always take precedence over imported BOMs.

## Why this is non-obvious

Within the parent BOM, the override works correctly (verified with `mvn dependency:tree` on the parent). The failure only manifests one level up — in the consumer. You'd reasonably expect a BOM to export its resolved dependency management, but import flattening discards the override precedence chain.
