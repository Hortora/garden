### Symptom
As an application grows capabilities, the MCP tool count grows linearly — each new feature adds new tools. At 40+ tools (IntelliJ MCP scale), context cost is high and tool discovery becomes a problem for the LLM.

### Context
Designing an agent control plane for an Electron+Quarkus application (Trellis) where the model and capabilities will grow unpredictably. The issue explicitly required ~6 tools, not hundreds.

### Technique
Use a small number of category tools (6) with a model tree as the discovery layer. The model response describes available actions per node — the LLM calls `trellis_model()` to discover what it can do, then calls the appropriate category tool. New capabilities extend the model (via `ModelProvider` SPI), not the tool list.

The tool list provides coarse capability discovery (what Trellis can do at the category level). The model provides fine-grained discovery (what actions are available on this specific node). Context cost stays constant as capabilities grow.

Category tools: `trellis_model`, `trellis_navigate`, `trellis_terminal`, `trellis_agent`, `trellis_lifecycle`, `trellis_workspace`.

### Why this is non-obvious
The natural MCP pattern (IntelliJ, filesystem tools) is one tool per operation. The insight is that MCP's tool definitions ARE the discovery mechanism — hiding everything behind a generic dispatch loses that. But a model tree provides an alternative discovery layer that MCP alone doesn't offer. The balance is category tools (MCP-native discovery) + model (on-demand detail discovery).

The comparison to IntelliJ is instructive: IntelliJ needs 40+ tools because it has no model. If it had a `ide_model()` that returned the IDE state tree with available actions, it could have fewer tools too.
