### Symptom
After a SNAPSHOT API change added a parameter to `PlanTrace(...)`, a find-replace of `Map.of())` → `Map.of(), null)` fixed all PlanTrace constructor calls but also corrupted `adapt(scored, Map.of())` and `scored(Map.of())` calls in test files — adding an unwanted `null` argument.

### Context
A neocortex SNAPSHOT added `variantId` (7th arg) to the `PlanTrace` record constructor. All 25 call sites needed updating. The pattern `Map.of())` (Map.of followed by closing parens) appeared in both PlanTrace constructors and unrelated method calls.

### Root cause
The replacement pattern `Map.of())` → `Map.of(), null)` matches any call that ends with `Map.of()` as its last argument — not just PlanTrace constructors. The closing `)` after `Map.of()` belongs to the outer call, and the pattern doesn't distinguish which outer call it is.

### Fix
Use structural replacement (IntelliJ `ide_replace_text_in_file` with a specific enough pattern) or target the constructor name explicitly:

```
# Too broad — matches any call ending with Map.of()
Map.of())  →  Map.of(), null)

# Correct — target the specific constructor
new PlanTrace("$1", "$2", "$3", "$4", $5, Map.of())
→ new PlanTrace("$1", "$2", "$3", "$4", $5, Map.of(), null)
```

After a broad replacement, always verify compilation before committing — the false positives surface as "wrong number of arguments" errors.

### Why this is non-obvious
The pattern looks safe — `Map.of())` seems unique enough. But Java method calls nest, and the closing paren belongs to the enclosing call, not to `Map.of()`. The damage is silent until compilation.
