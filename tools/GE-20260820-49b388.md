### Symptom
Every git operation in the affected repo emits:
```
error: unable to normalize alternate object path: /original/path/.git/objects
```
The repo appears corrupted — `git status`, `git log`, `git diff` all error.

### Context
When `git clone --shared` or `git clone --reference <path>` is used, git writes an absolute path to the source repo's `.git/objects` directory in `.git/objects/info/alternates`. This saves disk space by sharing object storage between clones.

If the source repo is later moved (renamed, archived to a different directory, or deleted), the absolute path in the alternates file breaks. The clone's git operations fail because git cannot resolve the object store.

This commonly occurs in automation that manages multiple repo clones (CI/CD pipelines, workspace managers, slot-based development environments) where repos are created with `--shared` for speed and later archived or reorganized.

### What was tried (didn't work)
- Investigating the error as git corruption (fsck, re-clone)
- Looking for missing packfiles or loose objects
- The error message does not mention "alternates" or the moved directory

### Root cause
`git clone --shared` writes an absolute filesystem path to `.git/objects/info/alternates`. Git resolves this path on every operation to borrow objects from the source. When the source moves, the path is stale.

### Fix
Repack the affected repo to internalize all borrowed objects, then remove the stale alternates entry:

```bash
# Internalize all objects from alternates into the local pack
git -C /path/to/affected/repo repack -a -d -l

# Remove the alternates file (or edit to remove just the broken line)
rm /path/to/affected/repo/.git/objects/info/alternates
```

The `-l` flag is important — it tells repack to only process local objects and the alternates, not remote packs.

After this, the repo is fully self-contained and no longer depends on the source.

### Prevention
Before moving or archiving a repo that was used as a `--shared` clone source:
1. Scan sibling repos for `objects/info/alternates` entries referencing the repo being moved
2. Repack each affected repo to sever the dependency
3. Then move the source safely

### Why this is non-obvious
The error message (`unable to normalize alternate object path`) does not mention that the path refers to a moved directory, nor does it suggest `repack` as the fix. A developer unfamiliar with git's alternates mechanism would likely investigate corruption, re-clone, or search for missing objects — none of which address the root cause. The connection between `git clone --shared` (used at creation time) and a broken alternate (surfacing months later when the source moves) is not intuitive.

### Alternatives considered
- **Update the alternates path** to point to the new location — simpler but fragile if the target moves again. Repack is more robust because it makes the repo self-contained.
- **Re-clone the repo** — works but loses any local branches, stashes, or config. Repack preserves everything.
