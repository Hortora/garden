### Symptom
After modifying `LeafItem.completed` or `LeafItem.active` on items returned by `flatten_leaves()`, calling `rewrite_plan()` writes the original unmodified tree.

### Context
`flatten_leaves()` constructs new `LeafItem` dataclass instances from `QueueItem` objects in the tree. The `LeafItem` dataclass is a separate type — not a reference to the original `QueueItem`.

### Root cause
Python dataclass construction creates new objects. `flatten_leaves()` builds `LeafItem(issue_number=item.issue_number, ...)` — these are copies of the values, not references to the `QueueItem` nodes in the tree.

### Fix
Modify `QueueItem` objects directly in `tree.queue` (or recursively in `item.children` for epic subtrees). Use `flatten_leaves()` only for read-only iteration — finding indices, computing totals, displaying state.

### Why this is non-obvious
The flattened list feels like a view over the tree — you'd expect mutations to propagate. The types are also close enough (`LeafItem` has the same field names as `QueueItem`) that the copy semantics aren't apparent from the API.
