### Symptom
GOAP A* planner outputs a linear action sequence. Converting to a DagPlan with sequential dependencies (each node depends on the previous) misses parallelism opportunities — actions with independent preconditions could execute concurrently.

### Context
Implementing `GoapDecompositionStrategy.buildDagPlan()` — mapping a GOAP plan to a `DagPlan<LeafTask>` with real causal dependencies.

### Technique
Maintain an `effectToNodeId` map (`Map<String, String>`) that tracks which DagNode produces each effect key. For each planned action:

1. Look up its precondition keys in `effectToNodeId` to find dependency nodes
2. Create the DagNode with those dependencies
3. Register the action's effect keys in `effectToNodeId` pointing to this node

```java
Map<String, String> effectToNodeId = new HashMap<>();
for (int i = 0; i < planned.size(); i++) {
  GoapAction action = planned.get(i);
  String nodeId = "goap-" + i;
  Set<String> dependsOn = new HashSet<>();
  for (String precondKey : action.preconditions().keySet()) {
    String depNodeId = effectToNodeId.get(precondKey);
    if (depNodeId != null) dependsOn.add(depNodeId);
  }
  nodes.add(new DagNode<>(nodeId, goalStep, dependsOn, JoinType.ALL_OF));
  for (String effectKey : action.effects().keySet()) {
    effectToNodeId.put(effectKey, nodeId);
  }
}
```

### Why this is non-obvious
The straightforward approach is sequential chaining (`dependsOn = previous`). The effectToNodeId map produces a real causal graph that's forward-compatible — when `DefaultGoalDecomposer` lifts its linear-chain restriction, GOAP plans automatically benefit from parallel execution without any code changes.
