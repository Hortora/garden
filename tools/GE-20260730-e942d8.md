### Symptom
SQLite lookups silently return no results when the path used for storage differs from the path used for lookup. Specifically: `record_work_start` stores `/tmp/repo` but `record_work_end` looks up `/private/tmp/repo` (or vice versa). The lookup fails, no event is recorded, and the worklog silently drops lifecycle events.

### Context
On macOS, `/tmp` is a symlink to `/private/tmp`. Depending on how a path is constructed — user input, `os.getcwd()`, `git rev-parse --show-toplevel`, `Path.resolve()` — the same directory can appear as either `/tmp/...` or `/private/tmp/...`. SQLite string comparison treats these as different paths.

### What was tried (didn't work)
Exact string matching on stored paths (`WHERE r.path=?`). Works when paths are consistent, silently fails when any path in the chain traverses a symlink differently between write and read.

### Root cause
Path strings are compared, not path identities. Two strings that resolve to the same filesystem location are treated as different if the strings differ.

### Fix
Normalize all paths at the storage/lookup boundary with `Path.resolve()`:

```python
def _norm(path: str) -> str:
    return str(Path(path).resolve())

# On write (ensure_repo):
path = _norm(path)

# On lookup (_find_work_item):
normalized = _norm(repo_path)
row = conn.execute("... WHERE r.path=?", (normalized,))

# Fallback for pre-normalization records:
if not row:
    row = conn.execute("... WHERE wi.branch=? AND wi.state != 'ended'", (branch,))
```

The fallback (branch-only match) handles records written before normalization was added — it finds the work item by branch name regardless of stored path.

### Why this is non-obvious
The `/tmp` → `/private/tmp` symlink is invisible in normal use. `ls /tmp` and `ls /private/tmp` show the same files. The mismatch only surfaces in string comparisons — and when the comparison is inside a `@safe`-decorated function that swallows exceptions, the failure is completely silent.
