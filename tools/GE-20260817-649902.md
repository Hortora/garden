### Symptom

`work_end_context.py` reports `clean_tree: fail` with "workspace has uncommitted changes" even though all meaningful work is committed. The dirty file is `engine/design/.meta` showing as deleted (`D`). Writing the file back (via `git checkout`, `git show > file`, or Python `Path.write_text()`) temporarily fixes it, but the file gets deleted again within seconds — sometimes between two consecutive commands.

### Context

The casehub workspace lifecycle migrated from `design/.meta` to `.plan` for tracking branch state. The old `.meta` file is still committed in workspace git repos that were created before the migration. The new lifecycle tooling (ctx.py, lifecycle.py) uses `.plan` exclusively and something in the toolchain actively deletes `.meta` from disk.

This creates an unresolvable dirty-tree state: git sees `.meta` as tracked-but-deleted, `work_end_context.py` checks `git status --porcelain -- .` and considers any output as dirty, and the file cannot be kept on disk because something deletes it.

### Fix

Remove the stale `.meta` from git tracking:

```bash
git -C /path/work rm engine/design/.meta
git -C /path/work commit -m "chore: remove stale .meta — lifecycle moved to .plan"
```

This is the correct fix because `.meta` is genuinely obsolete. The lifecycle state now lives in `.plan`. Keeping `.meta` in git history is harmless (git log preserves it), but keeping it tracked causes persistent dirty-tree failures.

### Why this is non-obvious

The symptom ("workspace has uncommitted changes") points toward uncommitted work, not a migration artifact. The `.meta` file is infrastructure — developers don't interact with it directly. The phantom deletion makes debugging confusing: you write the file, verify it exists, run the check, and it fails because the file was deleted between your verification and the check. The root cause (lifecycle migration leaving tracked files behind) is only discoverable by reading the lifecycle.py source to understand that `.plan` replaced `.meta`.
