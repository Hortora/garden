## IntelliJ MCP edits target the IDE's open project, not the shell CWD

### Symptom

After using `ide_insert_member` or `ide_edit_member` to add test methods, Maven reports the original test count (e.g. 5 tests) instead of the expected new count (e.g. 7 tests). The new methods exist in the file when read with `cat` or `Read`, but Maven doesn't compile them. `javap` on the compiled class confirms the new methods are absent.

### Context

In a slot-based workflow, the working directory is a git clone at `/slots/180/engine/` while IntelliJ has the original repo open at `/casehub/engine/`. The `project_path` parameter on IDE tools determines which project receives the edits. When `project_path` points to the original repo, all file modifications go there — even though Maven runs against the slot clone.

### Root cause

IntelliJ MCP tools write to the project's Virtual File System (VFS). The VFS is anchored to the project IntelliJ has open, identified by `project_path`. If the shell's working directory (where Maven runs) is a different clone of the same repo, the edits land in the wrong copy. There is no automatic detection or warning when the two diverge.

### Fix

Before any IDE edit operations, open the working directory as a project in IntelliJ:

```
ide_open_project(path: "/Users/dev/slots/180/engine", autoLink: true)
```

Then use `project_path: "/Users/dev/slots/180/engine"` on all subsequent IDE tool calls. Verify with `ide_index_status(project_path: "...")` that the correct project is indexed.

### Why this is non-obvious

The `project_path` parameter is optional on most IDE tools — when omitted or ambiguous, the tool routes to whichever matching project IntelliJ already has open. In single-repo setups this works transparently. The failure mode is completely silent: the tool reports success, the file appears modified when read (because both `Read` and IDE tools can see the original repo), but Maven compiles from the clone where nothing changed.
