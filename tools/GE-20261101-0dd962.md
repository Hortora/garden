### Symptom
Adversarial design review (coherence dimension, deep degree) found naming
collisions with sibling types but missed that the spec was modelling a concept
that already existed at a different abstraction layer.

### Context
Engine#1282 coordination vocabulary spec defined `RoleArchetype` with a value
for "the agent that receives and executes delegated work." The coherence review
caught collisions with `Participation.PARTICIPANT` and
`MeshParticipation.REACTIVE` (same package tree), leading to rename
→ RESPONDENT. A subsequent search proposed WORKER (modern agentic consensus).
The human then identified that `Worker` is already a first-class platform
concept hierarchy (Worker → FlowWorker, PlaybookWorker, CamelWorker,
AgentWorkerFunction) — the spec was reinventing a concept the platform
already owns.

### Root cause
Coherence reviewers were briefed to check completeness, consistency, and gaps
against the *spec's immediate neighbourhood* — sibling packages, related SPIs,
existing types in the same module. They did not zoom out to the platform-level
concept map to ask: "Does this concept already exist at a different layer?"

### Fix
When briefing coherence reviewers for vocabulary/type specs, add an explicit
check: "Do any proposed types model concepts that already exist at a different
abstraction layer in the platform? Check the capability-ownership map and the
Worker/Work/WorkItem concept hierarchy."

### Why this is non-obvious
The natural approach for coherence review is horizontal scanning (sibling
types, same package level). Vertical scanning (checking whether a concept
exists at a different abstraction layer) requires knowledge of the platform's
full concept hierarchy, which isn't visible from a single spec's neighbourhood.
