### Symptom
Worklog functions appear to succeed — no error output, no exception — but record nothing to the database. Tests pass (importing from `scripts/worklog.py` source) while runtime silently drops events (importing from `~/.claude/lib/worklog.py` installed copy).

### Context
`worklog.py` is copied (not symlinked) to `~/.claude/lib/` for runtime use. Every public function is wrapped with a `@safe` decorator that catches **all** exceptions and prints a warning. When new keyword arguments are added to a function signature in the source but the installed copy retains the old signature, the caller passes kwargs the installed version doesn't accept.

### What was tried (didn't work)
- Checked the source `worklog.py` — correct signature, tests pass
- Checked the calling code — correct kwargs being passed
- No error output anywhere — the `@safe` decorator converted the `TypeError` into a `WARN=worklog_error` line on stdout, which was not being checked

### Root cause
The `@safe` decorator wraps every worklog function:
```python
def safe(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        try:
            return fn(*args, **kwargs)
        except Exception as e:
            print(f"WARN=worklog_error detail={e}")
            return None
    return wrapper
```
When the installed copy has `def record_slot_archive(conn, slot_number, family_root)` but the caller passes `promoted=["workspace:2"]`, the `TypeError: got an unexpected keyword argument` is caught and silently printed. The caller sees no failure.

### Fix
After modifying `scripts/worklog.py`, sync the installed copy immediately. The source and installed copy must have identical signatures.

### Why this is non-obvious
The decorator is correct in its design — worklog failures should not block the workflow. But it creates an invisible failure mode: the function call looks successful, the return value (`None`) is the same as the `@safe` fallback, and the warning is printed to stdout where it's mixed with other KEY=VALUE output and easy to miss.

### Alternatives considered
- Symlinking instead of copying — rejected because `~/.claude/lib/` may be on a different filesystem and Claude Code doesn't follow symlinks in all contexts
- Version pinning — overkill for a single-file library with one consumer
