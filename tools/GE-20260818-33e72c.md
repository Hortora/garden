### Symptom
Large web component library (~100 `@customElement` classes) needs ARIA compliance enforcement. No way to prevent new components from shipping without ARIA attributes.

### Context
Custom ESLint rules for Lit template literals are complex to build and maintain. axe-core validates rendered DOM but requires a browser/jsdom environment and component fixtures — too heavy for a lint-phase check. Need a lightweight static check that catches obvious omissions at build time.

### Fix
A Node.js script (`aria-check.mjs`) that scans all source files for `@customElement` declarations and checks whether the file contains any ARIA pattern:

```javascript
const ARIA_PATTERNS = [
  /role[=:"']/,
  /aria-[a-z]/,
  /setAttribute\(\s*['"]role['"]/,
  /setAttribute\(\s*['"]aria-/,
  /override\s+aria[A-Z]/,
  /\.role\s*=/,
];
```

For each `@customElement` file, if none of the patterns match, report a failure with the file path. Exit with code 1 if any component fails.

**Ratchet approach:**
1. Add `"aria-check": "node scripts/aria-check.mjs"` to `package.json`
2. Run as a warning in CI initially (existing backlog of non-compliant components)
3. After backlog is cleared, promote to build-breaking: add to the `test` script chain

This lets teams adopt incrementally — new components are caught immediately while existing gaps are tracked via a GitHub issue.

### Why this is non-obvious
Most teams either skip accessibility validation entirely or attempt a big-bang fix of all components before adding CI enforcement. The ratchet approach — warn on existing gaps, block on new additions — avoids both extremes. The regex-based check is deliberately simple: it doesn't validate correctness (that's axe-core's job), just presence. A component with `role="button"` but missing `aria-label` will pass the static check but fail axe-core — the two checks are complementary layers.
