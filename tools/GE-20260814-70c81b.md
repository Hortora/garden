### Symptom
After calling `plan_manager.advance()`, the plan shows TWO issues checked off and the active marker has jumped past the intended next issue.

### Context
`advance()` reads the plan, finds the active leaf, marks it completed, marks the next leaf active, and rewrites the file. If called a second time (e.g. during error recovery or debugging), it finds the NEW active leaf and advances again.

### Root cause
`advance()` is a pure state machine step — it operates on whatever the current file state is. There is no lock, nonce, or "already advanced this issue" guard. Each call is a complete read-modify-write cycle.

### Fix
Call `advance()` exactly once per user action. If you need to inspect the result, use `parse_plan()` + `flatten_leaves()` to read state without mutating. If advance was called erroneously, fix the plan tree directly via `parse_plan()`, modify `QueueItem` objects in `tree.queue`, then `rewrite_plan()`.

### Why this is non-obvious
The function name suggests a declarative intent ("advance to the next issue") rather than an imperative step ("move the pointer forward once"). A second call looks harmless — it isn't.
