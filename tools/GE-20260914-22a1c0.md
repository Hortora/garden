# Stateful orchestrators: mechanical steps need auto-skip, not user escalation

**Stack:** Python, orchestrator patterns
**Tags:** orchestrator, retry, state-machine, error-handling

### Symptom

A multi-step orchestrator with progress tracking stalls permanently when a mechanical step (push, promote, merge) fails structurally. The retry loop exhausts attempts, escalates to the user, but the user has no mechanism to advance — the step is mechanical (can't be marked done by the user) and the skip validation rejects because it wasn't the last yielded step.

### Context

Re-entrant orchestrators that yield control between steps (script exits, caller re-invokes) track progress in a file. When a step fails, the orchestrator retries on re-invocation. After MAX retries, it must decide: escalate or auto-skip.

### Root cause

Treating mechanical and judgment failures identically. Judgment steps (write a blog, review code) benefit from user escalation — the user can provide the missing judgment. Mechanical steps (push to remote, create worktree) fail for structural reasons the user cannot fix inline — the failure is deterministic.

### Fix

Classify steps into two retry policies:

```python
# Judgment steps: escalate after MAX retries
if step.step_type == "judgment" and attempt > MAX:
    return {"ACTION": "user_input", "CONTEXT": "step_failed", ...}

# Mechanical steps: auto-skip after MAX retries, verify catches gaps
if step.step_type == "mechanical" and attempt >= MAX:
    update_progress(step.name, "skipped_error")
    continue  # loop advances to next step
```

Key design elements:
- `skipped_error` is a distinct terminal state from `done` and `skipped` — tracked separately in reports
- A downstream verification step (defense-in-depth) catches gaps left by auto-skipped steps
- `skipped_error` is recognized by all `done()` checks so the loop advances past it

### Why this is non-obvious

The natural instinct when designing retry logic is a single policy: retry N times, then escalate. This works when the user always has a useful action. In orchestrators mixing mechanical and judgment steps, the user has no action for structural mechanical failures — escalation is a dead end, not a recovery mechanism.

### Alternatives considered

- **Fix skip validation to accept mechanical steps** — still requires the LLM to know about and use `skip_step=`, which is an instruction-following dependency (the exact failure class the orchestrator was designed to eliminate)
- **Document `force_done=` escape hatch** — same problem: relies on the LLM using an undocumented parameter correctly under pressure
