## Per-boundary verification and per-close forcing functions are different scopes

### Symptom / context
When designing a unified audit system, the decision to retire a per-boundary verification discipline (VBC — "run the command, read the output, then claim the result") was justified by claiming the work-end forcing function ("resolve all findings before close") replaced it. A decision review caught the conflation.

### Root cause
Two verification mechanisms that sound similar serve different scopes:

- **Per-boundary verification:** "Did you actually run the test before claiming it passes?" Applies at every completion boundary — commits, PRs, task completion, agent delegation. Prevents false claims.
- **Per-close forcing function:** "Are all accumulated findings resolved before merging?" Applies only at branch close. Ensures nothing survives unaddressed.

Folding per-boundary into per-close loses the mid-work verification gates entirely. A developer could claim "tests pass" without running them for 5 commits, and only face accountability at branch close — by which point the false claims have compounded.

### Fix
Keep both mechanisms:
- Per-boundary verification → preserve as a protocol (not a standalone skill, but a referenced principle)
- Per-close forcing function → new system that reads accumulated findings and requires resolution

The forcing function is additive, not a replacement.

### Why this is non-obvious
The two mechanisms use similar language ("verify before claiming done") and apply to overlapping situations. The natural instinct during simplification is to merge them. The scope difference only becomes visible when you trace what happens between boundaries — the forcing function at close doesn't catch mid-work false claims.
