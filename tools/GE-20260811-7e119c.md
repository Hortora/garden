### Symptom
After building a `.plan` from an epic's `Covers:` list, `work next` advances through wrong issues — docs/chore issues instead of the actual implementation tasks referenced in the epic.

### Context
A slot's `.slot` file carries `Covers: 189,190,228,...` — bare issue numbers extracted from the epic's child issues. The epic body references them as `casehubio/platform#228`, `casehubio/ledger#189`, etc. (cross-repo qualified). The plan builder resolves these bare numbers against the parent repo.

### Root cause
The `Covers:` list strips repo qualification. When the plan builder resolves `#228`, it queries `casehubio/parent#228` (a docs issue: "sync casehub-qhorus deep-dive") instead of `casehubio/platform#228` (the actual task: "GraphQL foundation module"). Every issue number collision between the parent repo and the cross-repo targets produces a wrong entry.

### Fix
The plan builder must resolve issue numbers using the repo qualification from the epic body, not bare numbers against the parent repo. The epic body contains the full references (`casehubio/platform#228`), which should be preserved through to the `.plan`.

### Why this is non-obvious
The plan *looks* correct — it has issue numbers and titles. The titles are real issues that exist. You don't discover the mismatch until you try to work the issues and find they're unrelated docs tasks, not the implementation work the epic describes.
