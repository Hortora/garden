### Symptom
Streaming speech-to-text truncates the last 1-3 words of every utterance. The user says "hello my name is Mark" but the transcript returns "hello my name".

### Context
Using a streaming transducer model (Zipformer) via sherpa-onnx's online recognizer. Audio arrives as PCM frames via WebSocket. When the user stops speaking, `finalResult()` is called immediately — but the decoder's internal chunk buffer still has unprocessed audio.

### Root cause
Streaming transducer models process audio in chunks (e.g., 160ms for Zipformer with chunk-16-left-128). The decoder only emits text when it has accumulated enough frames for a complete chunk plus look-ahead context. When `finalResult()` is called, the last partial chunk hasn't been decoded yet — those trailing words are silently lost.

There is no "input finished" API in sherpa-onnx's online recognizer to signal end-of-stream.

### Fix
Feed a burst of silence (1 second at 16kHz) into the recognizer before reading the final result. This gives the decoder enough trailing context to process the last chunk:

```java
public TranscriptionResult finalResult() {
    flushWithSilence();
    String text = applyCleanup(readResult());
    return new TranscriptionResult(text, text.isEmpty() ? "" : "en", 1.0);
}

private void flushWithSilence() {
    float[] silence = new float[16000]; // 1 second at 16kHz
    acceptSamples(silence, 16000);      // feeds to decoder + decodes
}
```

### Why this is non-obvious
The decoder returns whatever it has without error — there's no indication that words are missing. The truncation is consistent (always the trailing words) but the amount varies with speech cadence, making it look like a recognition quality issue rather than a buffering bug. The fix (feeding fake audio) is counterintuitive.
