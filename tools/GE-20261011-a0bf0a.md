# Config classes as self-documenting architecture

## Symptom
Cognitive pipeline had ~44 hardcoded constants across 11 files. No single
place explained what each parameter did, why it had that value, or what
the literature said about it.

## Context
A cognitive simulation implements CAPS (Mischel & Shoda, 1995),
Rescorla-Wagner learning (1972), Klinger Current Concerns (1971), and
Gray's RST (1982). Each theory has parameters with empirically-grounded
defaults. These were scattered as magic numbers.

## Fix
Make each config class a self-documenting reference. An LLM or developer
reading just the config class — without any other codebase knowledge —
should understand:

**Class-level Javadoc:**
- What subsystem this configures (one paragraph)
- The psychological model it implements (cite the theory)
- How parameters interact with each other

**Per-property Javadoc:**
- What the parameter controls (behavioral description, not implementation)
- Valid range and units
- Default value and why (cite specific finding)
- What happens at extremes (higher = X, lower = Y)
- Related parameters

```java
/**
 * Configuration for CAPS weight updating during behavioral reinforcement.
 *
 * Implements Rescorla-Wagner associative learning with Pearce-Hall
 * attention modulation.
 *
 * @see Rescorla & Wagner (1972). Classical Conditioning II, pp. 64-99.
 * @see Pearce & Hall (1980). Psychological Review, 87(6), 532-552.
 */
@ConfigMapping(prefix = "casehub.caps.weight-update")
public interface CapsWeightUpdateConfig {

    /**
     * Rate at which prediction precision grows after confirmed predictions.
     * Higher = network becomes "sure of itself" faster, reducing learning.
     * Range: [0.0, 1.0]. Default 0.1 per Pearce-Hall attention decay rates.
     */
    @WithDefault("0.1")
    double precisionGrowthRate();
}
```

A companion `cognitive-pipeline-defaults.properties` file mirrors every
property with inline literature citations as comments.

## Why this is non-obvious
The standard approach is to extract constants into config and document them
separately (README, wiki, design doc). This technique makes the config
itself be the documentation — the type system ensures they stay in sync,
and the Javadoc is the single source of truth for both the value and its
justification.

Most config documentation says "what" but not "why." Adding literature
citations makes each default defensible and challengeable — you can look
up the paper to decide if the default applies to your context.
