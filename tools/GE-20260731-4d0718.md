### Symptom
Specs and blog entries on closed branches never reached workspace main. Discovered weeks later by a hygiene scan, not by any error during the close operation. The close completed "successfully" — stamp written, branch marked closed, issue closed on GitHub.

### Context
An artifact promotion pipeline with two layers: a leaf script (`artifact_promote.py`) that promotes individual files via `git checkout <branch> -- <path>`, and an orchestrator (`close_artifacts.py`) that scans for artifacts, routes them, calls the leaf script, and writes a completion stamp.

### Root cause
Three independent error-handling decisions, each individually reasonable:

1. **Bare `except CalledProcessError: pass`** in the leaf script's checkout loop. Intent: skip files that don't exist on the branch. Effect: swallows ALL git errors — lock files, corrupt refs, path mismatches — with no diagnostic output.

2. **`PROMOTED=0` treated as success** by the orchestrator. The leaf script exits 0 with `PROMOTED=0` when all files are skipped. The orchestrator checks only the exit code, not the count. Stamp written, close continues.

3. **`PUSHED=no` printed but never checked.** The leaf script catches push failures and prints `PUSHED=no` but still exits 0. The orchestrator assigns `project_pushed = out.get("PUSHED") == "yes"` but never reads the variable. Files committed to local main are lost on the next `git pull --rebase`.

Each bug is benign in isolation: (1) file-not-found is a legitimate skip; (2) zero promoted is valid when nothing routes to that destination; (3) test environments have no remote, so push always "fails."

In combination: git error → file silently skipped → PROMOTED=0 → no failure recorded → stamp written → branch closed → file stranded forever.

### Fix

**Leaf script:** Replace bare `except: pass` with error tracking — report `SKIPPED=N` and `SKIPPED_PATHS=<paths>` with per-file error detail on stderr. Distinguish `PUSHED=skipped` (no remote) from `PUSHED=failed` (remote exists, push failed).

**Orchestrator:** Check `PROMOTED=0` when artifacts were expected — record as failure, block the stamp. Check `PUSHED=failed` — record as failure.

### Why this is non-obvious

Each error path was tested in isolation and passed. The test environment masked bug #3 entirely — no remote means push always fails, but the test still passes because exit code is 0. The compound failure only manifests when all three bugs are present AND a real git error occurs during promotion — a condition that never appeared in unit tests.

### Why this fix

Fixing only the orchestrator (checking PROMOTED=0) catches the immediate symptom but leaves the leaf script silently swallowing errors. Fixing only the leaf script (logging skips) provides diagnostics but still writes the stamp. Both layers needed changes — the leaf script reports what happened, the orchestrator decides what it means.

### Alternatives considered

- **Make PROMOTED=0 a hard error in the leaf script** — rejected because zero promoted is legitimately valid when files don't exist on the branch (scan-source and branch can be different in slot mode).
- **Make push failure a hard error unconditionally** — rejected because test environments have no remote, and not all deployments use remotes. Instead, distinguish no-remote (skip) from failed-push (error).
