### Symptom

`git -C /path/work/engine status --porcelain -- .` reports files as deleted (`D engine/design/.meta`) even though the file exists on disk at `/path/work/engine/design/.meta`. Writing the file back with `git checkout -- engine/design/.meta` or `git show HEAD:engine/design/.meta > file` appears to succeed but the file is not found afterward.

### Context

A workspace directory structure where `work/` is a git repo and `work/engine/` is a subdirectory (not a submodule). Scripts pass `work/engine/` as the workspace path. `git -C work/engine/` resolves to the `work/` repo (git walks up to find `.git/`). All paths are then relative to `work/`, not `work/engine/`.

The committed path is `engine/design/.meta` (from `work/`'s perspective), but from the directory `work/engine/`, the expected path is `design/.meta`. This mismatch causes:
- `git status` showing paths with `engine/` prefix
- `git checkout` restoring files to wrong locations
- `git show HEAD:design/.meta` failing (wrong tree path)

### Root cause

`git -C <path>` sets the working directory but does NOT set the git root. Git walks upward from `<path>` to find `.git/`. If a parent directory is a git repo, git operates on the parent. All relative paths in the output are relative to the parent repo root, not the `-C` directory.

### Fix

When the workspace is inside a parent git repo, always use the parent repo root as the git directory and qualify paths explicitly:

```bash
# Wrong — ambiguous path context
git -C /path/work/engine status --porcelain -- .

# Right — explicit repo root + path
git -C /path/work status --porcelain -- engine/
```

Or detect the nesting at startup:
```bash
REPO_ROOT=$(git -C /path/work/engine rev-parse --show-toplevel)
# If REPO_ROOT != /path/work/engine, you're in a nested context
```

### Why this is non-obvious

`git -C <dir>` looks like it scopes all operations to `<dir>`. The man page says it "runs as if git was started in `<path>`" — which is true, but git then finds the nearest `.git/` by walking up. The `-C` flag does not create an isolation boundary. Paths in output (`git status`, `git diff`) use the actual repo root, not the `-C` directory.
