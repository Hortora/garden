# Composite simulation constant — a constant absorbing two independent physical effects calibrates for one scenario and breaks in others

## Symptom

A simulation constant passes calibration on a controlled scenario (small scenario, single-map) but produces consistent error across diverse production data. Tweaking the constant fixes one regime but breaks another. The error varies in unexpected ways across conditions you didn't use for calibration.

## Context

A simulation has a constant `HARVEST_DURATION = 66` calibrated against a specific test scenario. It passes. But across production data (different maps, different scenarios), it under-produces by 16%.

Investigation: the constant was set after a code change that shortened walks by ~18 loops (from edge-to-edge targeting). The harvest constant was inflated by 34 loops (2 legs × ~17 loops/leg) to compensate. The constant now represents: `real_harvest(32) + walk_compensation(34) = 66`.

## Root cause

A single constant absorbed two independent effects:
1. The actual physical duration of one phase (harvest time inside the geyser: 32 loops — constant across all conditions)
2. A walk-shortening artifact from the arrival threshold (depends on distance, which varies)

When the constant is decomposed and the walk-shortening is instead modelled as approach docking, it calibrates correctly across all distances.

## Fix

Always decompose simulation constants into one constant per physical effect:

```
// BAD: one constant absorbing harvest + walk compensation
GAS_HARVEST_DURATION = 66

// GOOD: separate constants for independent effects
GAS_HARVEST_DURATION = 32   // measured from profiler: time inside building
GAS_APPROACH_DOCKING = 11.5 // calibrated: entry overhead (queuing, animation)
```

The decomposition rule: each constant should correspond to one measurable physical phenomenon. If you can't name a single physical phenomenon for the constant, it's composite.

## Diagnostic

If you've calibrated a constant against a controlled scenario but the production data shows error that varies with a parameter you didn't control for — suspect a composite constant. The varying parameter (here: geyser-to-base distance) is leaking through the absorbed effect.

## Why this is non-obvious

The composite constant passes all calibration tests. The dual-run scenario is specifically designed so both effects have fixed values — the constant absorbs both and produces zero error. Only when the absorbed variable (walk distance) changes does the composite fall apart. A developer calibrating on a single map would never see the problem.

The pattern is especially subtle in physics simulations because the standard workflow is: measure, calibrate, test on same scenario → pass. Cross-scenario validation is not standard practice.

### Alternatives considered
- Tried sweeping the composite constant to find a better single value — optimal value was map-specific, confirming the composite nature
- Tried per-distance calibration tables — rejected (over-fitting; better to model the physics correctly)
