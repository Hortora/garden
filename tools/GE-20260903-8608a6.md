# Track unparsed lines as a format-evolution signal

### Symptom
A regex-based parser silently drops lines it can't match. Downstream consumers see an empty or partial result and proceed — the format evolved but the parser didn't, and nobody noticed.

### Context
Structured text files (e.g. markdown with semantic sections) are often parsed with regexes that match known line patterns. When the format adds new syntax variants, lines using the new syntax don't match the existing regex and are silently discarded.

### Fix
When parsing structured sections, collect lines that start with the expected prefix (e.g. `- `) but don't match the full regex. Surface them as metadata alongside the parsed result:

```python
@dataclass(frozen=True)
class PlanState:
    fields: dict[str, str]
    queue_items: list[QueueItem]
    unparsed_lines: list[str]  # lines the regex couldn't match
```

In the parser loop:
```python
elif section == "## Queue":
    m = _ITEM_RE.match(line)
    if m:
        queue_items.append(...)
    elif stripped.startswith("- "):
        unparsed_lines.append(stripped)
```

### Why this is non-obvious
Most parsers either match or skip — there's no third state. Adding an `unparsed_lines` collection creates a self-diagnosing system: if the format evolves and the regex doesn't, the unparsed lines accumulate as a visible signal rather than silently disappearing. Tests can assert `unparsed_lines == []` to catch format drift automatically.
