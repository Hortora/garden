### Symptom
`.claude` and `.worktrees` appear as untracked files (`?? .claude` in `git status`) despite `.claude/` and `.worktrees/` being listed in `.gitignore`.

### Context
Slot-based development clones create symlinks (not directories) for shared configuration: `.claude -> /path/to/shared/.claude`. Git treats symlinks as regular files, not directories. A `.gitignore` pattern with a trailing slash (`name/`) is a directory-only pattern — it matches directories but not files or symlinks.

`git ls-files --others --exclude-standard` respects `.gitignore` and correctly reports the symlinks as untracked because the trailing-slash pattern doesn't match them.

### What was tried (didn't work)
- Assumed `.gitignore` was correctly configured (the entries were there, just with trailing slashes)
- Checked if the `.gitignore` modifications were staged vs committed (they were in the working tree)

### Root cause
Git's `.gitignore` pattern matching treats trailing-slash patterns as directory-only matchers. Symlinks to directories are files in git's data model, not directories. The pattern `.claude/` matches the directory `.claude/` but not the symlink `.claude`.

### Fix
Add both patterns — with and without trailing slash:

```gitignore
.claude
.claude/
.worktrees
.worktrees/
```

The bare pattern (no trailing slash) matches any file or symlink named `.claude`. The trailing-slash pattern matches the directory. Together they cover both cases.

### Why this is non-obvious
The `.gitignore` file already appeared to have the right entries. The trailing slash is invisible in most editors and its semantic distinction (directory-only matching) is rarely encountered because most `.gitignore` targets are directories. The symptom (untracked files) doesn't point toward a pattern-matching subtlety — it looks like `.gitignore` is broken.

### Alternatives considered
- Remove trailing slashes entirely from all `.gitignore` entries — works but loses the explicit directory-matching intent for actual directories
- Use `!.claude` negation patterns — solves the wrong problem (negation un-ignores, doesn't add ignoring)
