### Symptom

Two applications consuming the same shared UI component library (e.g. blocks-ui-channel-activity) both work individually, but one silently falls behind on upstream enhancements. New features, accessibility improvements, and API changes get wired in the app that gets attention — the other app looks increasingly stale with no warning.

### Context

Occurs when two apps independently build composition layers over the same shared components. Each app has its own data fetching, WebSocket/SSE wiring, layout management, and property binding. The shared components themselves are identical — the duplication is in the wiring code that connects them to the backend and arranges them in the UI.

### Root cause

Every upstream component enhancement must be wired twice — once per composition layer. There is no mechanism to keep them in sync. The duplication is invisible because the wiring code is app-specific (different REST endpoints, different push mechanisms, different layouts), so it doesn't look like duplication at first glance.

### Fix

Make one app both a standalone product AND a reusable library that the other consumes. Extract the common composition logic (data fetching, push subscriptions, cursor management, panel mounting) into a shared module with strategy injection points for the parts that genuinely differ (layout, context headers, backend endpoint shape). The second app becomes a consumer that plugs in its own strategies rather than maintaining a parallel composition layer.

### Why this is non-obvious

The two composition layers look different enough that they don't register as duplication — different REST endpoints, different push mechanisms, different layouts. The staleness is silent: nothing breaks, nothing warns. The app that falls behind just looks slightly dated until someone compares them side by side.

### Alternatives considered

- **Accept the duplication and budget for keeping both current** — rejected because discipline-based solutions fail when attention is asymmetric
- **Kill one app** — rejected when both apps serve legitimate different use cases (standalone chat vs embedded in orchestration dashboard)
