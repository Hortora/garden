### Symptom
Cached entity state oscillates between "present" and "absent" as observation coverage changes, causing downstream consumers to react to phantom state transitions.

### Context
Any system that caches observed state for entities that can leave the observer's field of view: game AI with fog-of-war, distributed sensor networks, microservice health caches with intermittent connectivity, or any last-known-good state cache.

### What was tried (didn't work)

**Volatile (only current observation):** Entity is "present" only while actively observed. The moment vision drops, the entity is treated as gone. This causes oscillation — downstream consumers see repeated appear/disappear transitions as observation coverage fluctuates. In game AI, a building that leaves fog-of-war would be treated as destroyed every time a scouting unit moves away.

**Timed eviction:** Cache the state for a fixed duration (e.g., 2 minutes), then expire. The threshold is arbitrary — too short causes premature retraction (entity still exists but cache expired), too long delays genuine retraction (entity was destroyed minutes ago). No single timeout fits all scenarios.

**Permanent (never retract):** Once observed, treat as present forever. Handles fog-of-war correctly but cannot detect destruction, removal, or state changes. Downstream consumers operate on increasingly stale data.

### Root cause
The three approaches conflate two distinct signals:
- "I observed the location and the entity is absent" (positive counter-evidence → retract)
- "I can no longer observe the location" (loss of coverage → no information → don't change state)

### Fix
**Sticky-until-contradicted:** Cache the last observed state. Retract only when BOTH conditions are met:
1. The observer has active coverage of the entity's last known location
2. The entity is absent from the current observation

```java
// Retraction condition
boolean buildingPresent = currentObservation.stream()
    .anyMatch(b -> b.tag().equals(cachedTag));
if (!buildingPresent && hasVisionOf(cachedLocation)) {
    // Positive counter-evidence: we can see the location, entity is gone
    cache.remove(cachedTag);
}
// If we can't see the location: keep the cached state (fog)
```

This gives the correct behavior in all cases:
- Entity leaves observation → state persists (correct: we don't know if it's gone)
- Entity is observed again → state refreshes (correct: confirming it's still there)
- Location re-observed without entity → state retracted (correct: positive evidence of absence)

### Why this is non-obvious
Most developers default to either volatile (reactive, event-driven mindset) or timed eviction (familiar from HTTP caches). The sticky-until-contradicted pattern requires separating "loss of observation" from "observed absence" — a distinction that doesn't exist in most cache invalidation models where the data source is always reachable.
