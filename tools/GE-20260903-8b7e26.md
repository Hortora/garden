# Inline regex parsers silently drop items on format evolution

### Symptom
A corruption detector fires a false positive warning ("state: active but all issues CLOSED") at session start. The `.plan` file has 3 uncompleted queue items, but the check reports zero.

### Context
Multiple modules parse the same `.plan` file format using independent inline regexes. The canonical parser (`plan_manager.py`) handles `owner/repo#N` format. A consumer module (`corruption.py`) has its own regex that only handles `#N`. When the format evolved to include cross-repo references, the consumer's regex silently dropped items it couldn't match — returning an empty list instead of erroring.

### What was tried (didn't work)
- Each false positive was fixed individually by updating the specific consumer's regex or adding a skip condition
- This happened 4 times across 5 commits to the same file — each fix addressed one check but left the underlying pattern intact

### Root cause
Regex-based parsing of structured text silently drops non-matching lines. When the format evolves (new syntax variants), only the canonical parser gets updated. Consumer parsers see "no items" and proceed — the empty result is indistinguishable from a genuine empty queue. The downstream check (corruption detection) uses the empty result to conclude "no remaining work" and fires a false positive.

The failure cascade:
1. Format adds `owner/repo#N` variant alongside `#N`
2. Canonical parser updated, consumer regex not
3. Consumer regex returns 0 matches (silent, no error)
4. Downstream check: "queue empty + covers closed = corruption"
5. Warning fires at every session start until someone traces it

### Fix
Extract a single parser module (`plan_io.py`) that all consumers import from. The parser handles all format variants and exposes an `unparsed_lines` field that surfaces what the regex couldn't match — turning silent data loss into a visible signal.

```python
@dataclass(frozen=True)
class PlanState:
    fields: dict[str, str]
    queue_items: list[QueueItem]
    unparsed_lines: list[str]  # format-evolution signal
```

### Why this is non-obvious
The symptom (false corruption warning) completely misleads about the root cause (parser can't parse new format). The regex doesn't error — it returns an empty list. The consumer code handles empty lists correctly (returns None = "no inconsistency found"). The false positive fires from a different check that aggregates the empty result. Tracing from symptom to root cause requires following data flow across 3 functions.

### Why this fix
The individual-fix approach (updating each consumer's regex) fails because it's a game of whack-a-mole. Every format evolution requires finding and updating N independent regex patterns. The structural fix (single parser) reduces N to 1.

### Alternatives considered
- Updating each consumer's regex independently — tried 4 times, same class of bug recurred
- Shared types module imported by both plan_manager and consumers — introduces cross-directory dependency without benefit over a dedicated reader module
