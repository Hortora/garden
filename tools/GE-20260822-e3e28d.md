## Context

A slot clone is behind `origin/main` (e.g. 95 commits). A dependency module (say, `runtime`) won't compile from source because an upstream API (`platform-api`) changed its types. The compilation error is in `runtime`, but the new work is in a completely separate module (`react/`) that depends on `runtime` only for a factory class.

## The technique

Use the slot's pre-built `.m2` cache to resolve the stale-but-functional jar:

```bash
mvn compile -f react/pom.xml -Dmaven.repo.local=/path/to/slot/.m2
```

The slot's `.m2` contains a `runtime` jar from before the API break. The new module compiles against that jar's API surface. The runtime module's source-level compilation error is irrelevant — the jar was built when the code was consistent.

## Why this works

Maven resolves SNAPSHOT dependencies from the local `.m2` repository. If the jar exists there (installed before the API drift), Maven uses it without recompiling. The new module only needs the dependency's class signatures, not its source.

## When it doesn't work

- The new module needs types or methods added in the 95 missing commits
- The API surface of the dependency changed in a way the new code touches
- The jar in `.m2` is genuinely incompatible (method signature changes)

### Why this is non-obvious

The natural instinct is to fix the compilation error first (rebase, fix the API migration) or to skip the broken module entirely. But when the error is in an unrelated module and the rebase involves resolving conflicts in 95 commits, the `.m2` workaround lets you keep building and testing the new module in isolation. Once the rebase happens later, everything compiles from source again.
