## Symptom

Slot numbering collisions despite making the DB the authority for number allocation. The DB returns `MAX(slot_number) + 1`, but the write that persists the new slot number is wrapped in `@safe` (catches all exceptions, prints a warning, continues). When the write silently fails, the next read sees the old max and allocates the same number.

## Context

A worklog module uses `@safe` decorator on all recording functions — exceptions are caught and logged, never propagated. This is correct for informational event logging. But when the DB became the authority for slot numbering (reads determine the next number), the write path stayed `@safe`.

## Root cause

**Authoritative reads + best-effort writes** is architecturally incoherent. If you trust the DB to tell you the next valid number, you must also trust it to persist that number — which means write failures must propagate.

The `@safe` pattern is designed for informational/observational stores where the store's absence doesn't change behavior. The moment a store becomes authoritative (its content drives decisions), every write to it becomes a correctness requirement.

## Fix

Remove `@safe` from the specific write functions that are on the authoritative path. Other writes can stay best-effort.

The key insight is **selective authority**: not every function in the module needs to change. Only the writes that feed authoritative reads must propagate errors. For slot numbering:
- `reserve_slot_number()` — no `@safe` (allocates the number)
- `confirm_slot_create()` — no `@safe` (confirms the reservation)
- `record_slot_archive()` — keeps `@safe` (informational, drift detection catches lag)

## Why this is non-obvious

The `@safe` decorator is invisible at the call site — every function looks the same. The pattern works well for 95% of worklog functions. The failure mode only appears when a function that was informational gets promoted to authoritative, and the decorator stays because "it's always been there."

The design review surfaced this: "authoritative reads without authoritative writes is incoherent" — a principle that's obvious once stated but easy to miss when evolving an existing system incrementally.

### Alternatives considered

- Remove `@safe` from all worklog functions — rejected because most writes are genuinely informational and should not block operations
- Add a separate "strict" module — rejected as unnecessary indirection; selective removal is simpler
- Reserve-first pattern (insert pending row before disk operations) — adopted as complementary; prevents the dead-end where disk exists but DB doesn't know about it
