### Symptom
After `add_repo()` succeeds (prints `ADDED=<repo> SLOT=<N>`), the clone's `origin` remote points to the local source path instead of the GitHub fork. Pushes go to the wrong place.

### Context
`create_slot()` (line 578) calls `configure_slot_remotes(clone_dest, repo_path)` for every repo it clones — this renames `origin` to `local` and adds the fork as `origin`. `add_repo()` (line 698) does not call `configure_slot_remotes()` on the project clone. It only calls it for the workspace clone (line 765).

### Root cause
Implementation gap in `add_repo()` — the remote configuration step was not ported from `create_slot()`.

### Fix
After calling `add_repo()`, manually fix the remotes:

```bash
git -C /path/to/slot/repo remote rename origin local
git -C /path/to/slot/repo remote add origin https://github.com/fork/repo.git
git -C /path/to/slot/repo remote add upstream https://github.com/org/repo.git
git -C /path/to/slot/repo fetch origin
```

Or call `configure_slot_remotes()` directly after `add_repo()`:

```python
from slot_manager import configure_slot_remotes
configure_slot_remotes(clone_path, original_path)
```

### Why this is non-obvious
The function prints `ADDED=` success. No warning about unconfigured remotes. The problem only surfaces when you try to push or when you inspect remotes and notice `origin` points to a local path.
