## Symptom

Claude Code sessions in slot directories (or any terminal tab) silently fail to save transcripts. `/resume` shows no sessions. Session UUID directories exist in `~/.claude/projects/<key>/` with subagent metadata and tool results, but no `.jsonl` transcript files.

The diagnostic is a red herring: running `env | grep CLAUDE` from within a Claude Code session ALWAYS shows `CLAUDE_CODE_CHILD_SESSION=1` — Claude sets it for all subprocess environments (Bash tool calls). Its presence does not mean the session itself is a child session.

## Context

Claude Code sets `CLAUDE_CODE_CHILD_SESSION=1` in the environment of every subprocess it spawns. When a new Claude Code instance starts, it checks if this variable is already present in the inherited environment. If so, it treats itself as a child/nested session and disables transcript saving to avoid duplicates.

The problem occurs when a terminal emulator (iTerm2, Terminal.app) is launched from a context where `CLAUDE_CODE_CHILD_SESSION=1` was set — for example, if iTerm2 was relaunched via a shell command from within a Claude session, or from a process that inherited the variable. Once the terminal app has it, every tab, window, and shell it spawns inherits it. Every Claude Code session in those shells becomes a "child" that never saves transcripts.

## What was tried (didn't work)

- Checking `~/.zshrc`, `~/.zprofile`, `~/.bashrc` for the variable — not set there
- Checking `~/.claude/settings.json` env block — not there
- Checking hooks and shell snapshots — not present
- Checking tmux — not running
- Checking process ancestry: Terminal.app -> login -> zsh -> claude — no Claude parent
- Interpreting `CLAUDE_CODE_CHILD_SESSION=1` in `env` output as the cause — this is the trap; it appears in ALL sessions

## Root cause

The terminal emulator process itself (e.g. iTerm2 PID) had `CLAUDE_CODE_CHILD_SESSION=1` in its environment. This was inherited from whatever context launched or relaunched iTerm2. Since the terminal app is the ancestor of all shells, every shell inherits the variable, and every Claude Code session launched from those shells detects it on startup and disables transcript saving.

## Fix

Add to `~/.zshrc` (or equivalent):

```bash
unset CLAUDE_CODE_CHILD_SESSION
```

This strips the variable from every new shell regardless of how it was inherited. Additionally, quit and relaunch the terminal app from Spotlight, Finder, or the Dock (not from a terminal) to clear it from the terminal app's own environment.

### Why this fix

The `unset` in the shell profile is defense-in-depth — it protects against future re-contamination regardless of how the terminal is launched. Relaunching the terminal from a clean context (launchd via Spotlight/Dock) gives it a fresh environment without the variable.

### Why this is non-obvious

1. The variable appears in ALL Claude Code sessions when you check `env`, making it look like normal behavior — you can't distinguish a broken session from a working one by checking env from inside it
2. The variable is not set in any user-controlled config file (shell profile, settings, hooks) — it's inherited from the terminal app's process environment
3. The symptom (missing transcripts) has no error message or warning — sessions appear to work normally, you only notice when `/resume` returns nothing
4. Process ancestry shows no Claude Code parent — the contamination happened at a higher level (the terminal app itself)

### Alternatives considered

- Checking if `claude -c` (--continue flag) caused it — ruled out, both `claude` and `claude -c` processes showed the same behavior
- Shell snapshot contamination — checked all snapshots, none contained the variable
- Claude Code version change — ruled out, working and broken sessions ran the same version simultaneously
- Server-side transcript storage change — ruled out, working sessions on the same machine still saved locally
