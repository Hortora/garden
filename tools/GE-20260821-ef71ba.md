### What it does
`ide_structural_search_replace` can perform bulk API migrations across an entire codebase in a single operation. A structural pattern with `$variable$` wildcards matches AST nodes, not text — so it handles multi-line expressions, nested calls, and varying formatting.

### Example
Migrating `DesiredNode` from a 4-arg to 3-arg constructor (dropping the `type` parameter):

```
searchPattern:  new DesiredNode($id$, $type$, $spec$, $gating$)
replacePattern: new DesiredNode($id$, $spec$, $gating$)
```

This replaced 512 call sites across 85 files in one operation.

### Key gotcha: FQN search works, FQN replace fails
- **Search with FQN works:** `new io.casehub.desiredstate.api.DesiredNode($id$, $type$, $spec$, $gating$)` — found 247 matches
- **Replace with FQN fails silently** (returns `null` error)
- **Replace with short name works:** `new DesiredNode($id$, $type$, $spec$, $gating$)` — found and replaced 512 matches (more because it includes test and example files resolved by simple name)

Use FQN for search-only (verification), short name for search-and-replace.

### Why this is non-obvious
Text-based search-and-replace (regex) can't reliably handle Java constructor calls that span multiple lines, have nested expressions as arguments, or use varying whitespace. AST-aware structural search handles all of these. The FQN asymmetry (works for search, fails for replace) is undocumented.
