### Symptom

Loading a Blizzard API ladder replay (downloaded via `download_replays.py`) into SC2 headless via a manual WebSocket connection returns `StartReplay error 1: MissingReplay` with no error details. SC2 starts fine, ping succeeds, but every replay fails silently.

### Context

Blizzard's replay API provides anonymized 1v1 ladder replays in bulk (hundreds of thousands per game version). These replays have a different MPQ archive structure than normal replays:

**Normal replay MPQ files (14):**
`replay.attributes.events`, `replay.details`, `replay.details.backup`, `replay.game.events`, `replay.gamemetadata.json`, `replay.initData`, `replay.initData.backup`, `replay.load.info`, `replay.message.events`, `replay.resumable.events`, `replay.smartcam.events`, `replay.sync.events`, `replay.sync.history`, `replay.tracker.events`

**Blizzard API replay MPQ files (6):**
`replay.attributes.events`, `replay.details.backup`, `replay.game.events`, `replay.gamemetadata.json`, `replay.initData.backup`, `replay.load.info`

Missing: `replay.details`, `replay.initData`, `replay.tracker.events`, and all sync/message/smartcam files. Only `.backup` versions of details and initData are present.

### What was tried (didn't work)

1. Manual WebSocket connection to SC2 with `RequestStartReplay(replay_data=bytes)` — MissingReplay error
2. Using `replay_path` instead of `replay_data` — same error
3. Passing `-dataVersion` flag matching the replay's DataVersion hash — same error
4. Restarting SC2 between attempts — same error
5. Using `RequestReplayInfo` — also returns MissingReplay error 1

### Root cause

SC2's replay loader expects `replay.initData` (not `replay.initData.backup`) in the MPQ archive. The `.backup` suffix is an anonymization artifact. When connecting manually via WebSocket, SC2 doesn't handle the backup→standard file mapping.

PySC2's `run_configs` module handles this correctly because it:
1. Extracts the replay version from `replay.gamemetadata.json`
2. Starts SC2 with the correct `-dataVersion` flag
3. Uses its own temp-file management that the SC2 client recognizes
4. Handles the replay loading through a higher-level abstraction that maps backup files

### Fix

Use PySC2's `run_configs` to manage SC2 instead of manual WebSocket connection:

```python
from pysc2 import run_configs
from s2clientprotocol import sc2api_pb2 as sc_pb

# Extract version from replay metadata
version = ".".join(meta["GameVersion"].split(".")[:-1])

# PySC2 handles -dataVersion, temp dirs, and replay format
rc = run_configs.get(version=version)
with rc.start(want_rgb=False) as controller:
    info = controller.replay_info(replay_data)  # Works!
    req = sc_pb.RequestStartReplay(
        replay_data=replay_data,
        options=sc_pb.InterfaceOptions(raw=True, score=True),
        observed_player_id=1,
    )
    controller.start_replay(req)  # Works!
```

### Why this is non-obvious

The MissingReplay error gives no details — it doesn't say "initData not found" or "backup format not supported." The natural assumption is that the replay data is corrupted or the version is wrong. The 3.16.1 static replay packs, 4.9.x API packs, and 4.10.x API packs all have the identical stripped format, so version isn't the variable. AlphaStar trained on these exact replays (confirmed in DeepMind's AlphaStar-Unplugged README), proving they're loadable — but only through PySC2, not through raw protobuf API calls.

### Why this fix

PySC2 is the only documented path that successfully loads Blizzard API replays. Manual WebSocket + protobuf connections fail regardless of flags passed. The abstraction layer in PySC2's run_configs handles the backup format transparently.

### Alternatives considered

- Manual WebSocket connection with various flag combinations — failed
- Using s2protocol to decode tracker events directly from the file — impossible, tracker events stream doesn't exist
- Repackaging the MPQ archive to rename .backup files — mpyq is read-only, no Python MPQ writer available
