### Symptom
`AttributeError: 'dict' object has no attribute 'is_done'` thrown deep inside a loop engine, far from where the wrong type was passed.

### Context
During migration from raw `dict[str, str]` progress tracking to a typed `Progress` class, one orchestrator (`wrap_orchestrator.py`) was updated to use the new `OrchestratorContextBase` dataclass (which declares `progress: Progress`) but still loaded progress via `read_close_progress()` which returns a raw dict. Python dataclasses don't enforce type annotations at runtime, so the dict was silently accepted at construction time.

### What was tried (didn't work)
- The error appeared on `ctx.done(step.name)` inside `run_loop` — a method several call frames away from where the context was constructed
- The traceback pointed to `shared_steps.py:81` (`self.progress.is_done(step)`) which gave no hint that `progress` was the wrong type

### Root cause
Python dataclasses accept any value for annotated fields — `progress: Progress = field(...)` doesn't reject a raw dict at construction time. The type mismatch only surfaces when a method specific to `Progress` (like `is_done()`) is called, which can happen much later and in a completely different module.

### Fix
Replace `read_close_progress(workspace)` (returns `dict[str, str]`) with `Progress.load(workspace)` (returns `Progress` object) at the call site. The `Progress` class supports dict-like access (`get()`, `__getitem__`, `__contains__`, `items()`) for backward compatibility, so duck-typed code that only uses dict methods still works — but code that uses `Progress`-specific methods like `is_done()` or `is_per_repo_done()` now gets the right type.

### Why this is non-obvious
The bug was invisible at the construction site and only manifested when a specific code path was exercised. Static type checkers (mypy) would catch this, but in a codebase without strict type checking, the mismatch can persist for weeks until the right combination of steps triggers the `is_done()` call. The partial duck-typing compatibility (dict has `get()` which `Progress` also has) means most code paths work fine — only the `Progress`-specific methods fail.

### Alternatives considered
- Could add runtime type checks in `OrchestratorContextBase.__post_init__` — rejected as overly defensive for a dataclass
- Could make `Progress` inherit from dict — rejected as it conflates the abstraction
