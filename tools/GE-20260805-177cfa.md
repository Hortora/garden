### Symptom
`mvn compile` fails with `cannot find symbol` for classes that ARE present in the JAR at `~/.m2/repository/`. Purging and reinstalling to `~/.m2` has no effect. Build failures persist across `mvn clean`, `-U` flag, and manual JAR replacement.

### Context
Slot clones created via `work-slot` include `.mvn/maven.config` with `-Dmaven.repo.local=<slot-path>/.m2`. This gives each slot its own isolated Maven local repository. When a cross-repo SNAPSHOT dependency is rebuilt and installed to `~/.m2`, the slot's `.m2` retains the old version.

### What was tried (didn't work)
- `mvn clean install -U` — re-downloads stale SNAPSHOT from GitHub Packages
- Purging `~/.m2/repository/io/casehub/<artifact>/` and reinstalling — slot doesn't use `~/.m2`
- `mvn -o` (offline mode) — fails because Maven plugins (surefire, compiler) aren't cached in the slot's `.m2` either
- `-nsu` flag alone — blocks SNAPSHOT metadata updates but doesn't address the stale JAR already in the slot's `.m2`

### Root cause
`-Dmaven.repo.local` in `.mvn/maven.config` redirects all Maven resolution to `<slot>/.m2/`. The slot's `.m2` was populated at slot creation time. Subsequent `mvn install` in dependency repos writes to `~/.m2`, not the slot's `.m2`. The two repositories diverge silently.

### Fix
Sync from `~/.m2` to the slot's `.m2` before building:

```bash
rsync -a --delete ~/.m2/repository/io/casehub/ <slot>/.m2/io/casehub/
```

Then build with `-nsu` to prevent Maven from re-downloading stale SNAPSHOTs from the remote:

```bash
mvn clean compile -nsu
```

The `--delete` flag removes timestamped remote SNAPSHOT JARs (`*-20260731.231234-22.jar`) that Maven would otherwise prefer over the locally-installed `*-SNAPSHOT.jar`.

### Why this is non-obvious
The `.mvn/maven.config` file is a single line that's easy to miss. `mvn dependency:build-classpath` was the diagnostic that revealed the slot path — showing JARs resolved from `<slot>/.m2/` instead of `~/.m2/repository/`. Without that command, the symptom looks like a corrupted dependency or a remote resolution race.

### Why this fix
`rsync --delete` is preferred over `cp` because Maven's timestamped SNAPSHOT resolution picks the newest timestamp, not `*-SNAPSHOT.jar`. Without `--delete`, old timestamped JARs survive and win the resolution.

### Alternatives considered
- Removing `-Dmaven.repo.local` from `.mvn/maven.config` — breaks slot isolation (slots would share `~/.m2` and conflict)
- Symlinking `<slot>/.m2` → `~/.m2` — defeats the purpose of per-slot isolation
