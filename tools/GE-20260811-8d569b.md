## git `<rev>:<path>` resolves from repo root even with `-C <subdir>`

**ID:** GE-20260811-8d569b
**Stack:** git (all versions)

### Symptom

Verification commands using `git -C <subdir> cat-file -e <rev>:<path>` report files as missing even though they exist. Push verification, promotion checks, and branch file listings all produce false negatives when the working directory is a subdirectory of the repo.

### Context

When a tool runs git commands with `-C <subdir>` to target a specific repo from a non-root location, the `-C` flag correctly sets the working directory for most operations (`add`, `commit`, `status`, `push`, `checkout`). However, the `<rev>:<path>` syntax (used in `cat-file`, `ls-tree`, `show`, `diff`) is a tree-object lookup, not a filesystem operation — it always resolves `<path>` relative to the repository root, regardless of `-C`.

### Root cause

`-C` changes the CWD for git's process, which affects filesystem-relative operations. But `<rev>:<path>` parses `<path>` as a tree-path — a lookup into the git tree object for the specified revision. Tree paths are always rooted at the repository root, because the tree object represents the full repository structure.

```bash
# Repo at /workspace/ with subdir /workspace/engine/

# These work — filesystem operations respect -C
git -C /workspace/engine add specs/foo.md        # adds engine/specs/foo.md
git -C /workspace/engine status                  # shows engine/ changes

# This FAILS — tree-path ignores -C
git -C /workspace/engine cat-file -e main:specs/foo.md
# Looks for /workspace/specs/foo.md (repo root), NOT /workspace/engine/specs/foo.md

# Correct: use the full tree path from repo root
git -C /workspace/engine cat-file -e main:engine/specs/foo.md
```

### Fix

When using `<rev>:<path>` from a subdirectory, compute the repo-root-relative path:

```bash
# Option 1: prefix with the subdir path
SUBDIR=$(git -C /workspace/engine rev-parse --show-prefix)
# Returns "engine/" — the path from repo root to CWD
git -C /workspace/engine cat-file -e "main:${SUBDIR}specs/foo.md"

# Option 2: always run from repo root
TOPLEVEL=$(git -C /workspace/engine rev-parse --show-toplevel)
git -C "$TOPLEVEL" cat-file -e main:engine/specs/foo.md
```

### Why this is non-obvious

The `-C` flag creates a strong expectation that all paths are relative to the specified directory. This is true for `add`, `commit`, `status`, and most other commands. The `<rev>:<path>` syntax is the exception — it looks identical to a relative path but resolves differently. The git documentation buries this in the gitrevisions(7) man page under "specifying a blob" without connecting it to `-C` behaviour.

### Alternatives considered

- Prepending `./` to make paths CWD-relative (e.g., `main:./specs/foo.md`) — this does NOT work; git does not support CWD-relative tree paths.
