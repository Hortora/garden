# SQLite FK constraint silently blocks record deletion when except-pass swallows IntegrityError

## Symptom

After a failed operation, the cleanup handler removes the directory from disk but the database record stays as `active`. Subsequent listing shows the record as active with no corresponding directory — a db/disk drift that only reconciliation detects.

## Context

A slot creation function reserves a DB row (`state='pending'`), confirms it (`state='active'` + event log entry), then runs post-confirmation validation. If validation fails, the rollback handler tries to delete the DB row. The handler wraps the deletion in `except Exception: pass` because it's best-effort cleanup.

## Root cause

`PRAGMA foreign_keys=ON` is set on every connection. The `events` table has `slot_id INTEGER REFERENCES slots(id)` with no `ON DELETE CASCADE`. When `confirm_slot_create` succeeds, it calls `_log_event()` which inserts an `events` row referencing the slot's `id`. The subsequent `DELETE FROM slots WHERE id=?` raises `sqlite3.IntegrityError` because the events row still references it. The `except Exception: pass` swallows the error silently.

The directory cleanup succeeds (it's just `shutil.rmtree`), but the DB row survives — creating divergence that only a reconciliation scan would detect.

## What was tried (didn't work)

- `DELETE FROM work_item_issues ... DELETE FROM work_items ... DELETE FROM slots` — still fails because `events.slot_id` FK is not in the cascade chain
- Adding `ON DELETE CASCADE` to the events FK — would work but changes the schema contract for an append-only audit log

## Fix

Use a state transition instead of deletion. Transition the slot to `state='failed'` rather than deleting it:

```python
def fail_slot(conn, slot_number, family_root):
    conn.execute(
        "UPDATE slots SET state='failed' WHERE slot_number=? AND family_root=?",
        (slot_number, family_root),
    )
    conn.commit()
```

This preserves the audit trail (event log rows remain intact), avoids the FK violation entirely, and follows the existing state-machine pattern. The `failed` state is naturally handled by reconciliation as another divergence class, and pending/failed slots are reusable on the next creation attempt.

### Why this is non-obvious

The FK constraint is defined in the schema setup function, not near the deletion code. The `except Exception: pass` in the rollback handler means the failure is completely invisible — no error message, no log entry, no exception. The only symptom is db/disk drift that appears much later during listing or reconciliation, with no trace back to the failed cleanup.

### Alternatives considered

- Adding `ON DELETE CASCADE` to the events FK — rejected because the events table is an append-only audit log; cascading deletes would destroy forensic evidence of what happened
- Deleting events first, then the slot — rejected because it still destroys audit history and adds complexity for a case that state transition handles cleanly
