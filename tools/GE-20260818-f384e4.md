### Symptom
Hours of uncommitted work (~20 files) silently disappear from the working tree with no error, no warning, and no stash entry. The session that lost work sees a clean tree where files used to exist.

### Context
Two automated sessions (or processes) share the same git working tree. Session A has uncommitted changes (modified and untracked files). Session B runs a workflow that requires `git rebase`, which needs a clean working tree. Session B's automation cleans the tree — typically via `git reset --hard HEAD` — to satisfy the rebase prerequisite, destroying Session A's changes.

### What was tried (didn't work)
- Checking `git reflog` — shows `reset: moving to HEAD` but the uncommitted file contents are gone
- Checking `git stash list` — empty (no stash was created)
- Checking `git fsck --lost-found` — uncommitted changes to untracked files are never in the object store

### Root cause
`git rebase` requires a clean working tree. Automated workflows that encounter a dirty tree often use `git reset --hard` to clean it, because the workflow assumes exclusive ownership of the working tree. When another session has uncommitted work there, `reset --hard` destroys it permanently. Untracked files are especially vulnerable — they were never in git's object store, so no recovery mechanism exists.

### Fix
Add an unconditional `git stash push -u -m "safety stash before <operation>"` before any automated `git rebase`, `git reset`, or `git checkout` that could modify the working tree. The `-u` flag includes untracked files. Named stash messages make recovery discoverable.

```python
def safety_stash(repo: str, operation: str) -> bool:
    status = git(repo, "status", "--porcelain")
    if status.returncode != 0 or not status.stdout.strip():
        return False
    msg = f"safety stash before {operation}"
    result = git(repo, "stash", "push", "-u", "-m", msg)
    return result.returncode == 0
```

Call unconditionally — even when higher-level guards say the tree "should" be clean. Defense-in-depth: the stash costs nothing when the tree is clean (returns False), and saves everything when it isn't.

### Why this is non-obvious
Each automated session assumes exclusive access to the working tree — an implicit contract that git does not enforce. The clean-tree prerequisite for rebase is well-known, but developers don't usually think of it as a data-destruction vector because humans naturally have exclusive access to their working directory. In multi-session automation, "dirty tree from another source" is a normal state, not an error — but the rebase pathway treats it as something to be cleaned away.

### Alternatives considered
- **Worktree-per-session**: Each session gets its own `git worktree`. Eliminates the shared-tree problem entirely, but adds setup cost and disk usage. Best for planned parallel work; doesn't protect ad-hoc sessions.
- **Lock file (.claude-active-session)**: Marker file that other sessions check before mutating. Fragile — crashes leave stale locks, and the marker needs cross-process coordination.
- **Proactive commit enforcement**: A Stop hook that warns about uncommitted changes after every turn. Reduces the window but doesn't eliminate it — the commits need to happen before another session can act.
