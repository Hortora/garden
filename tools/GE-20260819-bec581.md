## Design-review lifecycle points as fillable slots for different execution models

### Symptom / context
Design-review had a "Post-implementation" lifecycle point planned in review-tiers.md but marked as "future" for over a month. The adversarial multi-round execution model (external sessions, watchdog crons, ~/reviews/ workspaces) didn't fit a pre-merge code audit gate that needed to be fast and inline.

### Root cause
The lifecycle taxonomy (what to review at what point) was coupled to the execution model (how to review it). Post-implementation review needed the same dimensions (conformance, coherence, structure, robustness) but a fundamentally different execution model (inline single-pass, no adversarial rounds).

### Fix
Treat lifecycle points as slots that different skills can fill:

```markdown
| Lifecycle | Executor | Dimensions | Execution model |
|-----------|----------|------------|-----------------|
| Post-spec | design-review | coherence, structure, robustness | Multi-round adversarial |
| Post-implementation | branch-audit | conformance, coherence, structure, robustness | Inline single-pass |
| Pre-ship | (future) | robustness, readiness | TBD |
```

`review-tiers.md` maps lifecycle points to dimensions and depths. Different skills fill those slots with their own execution models. The shared vocabulary (four dimensions) enables cross-lifecycle comparison of findings without coupling the review mechanisms.

Update `review-tiers.md` to reference the executor skill rather than embedding the execution model: `"Implemented by: branch-audit"` instead of describing the future model inline.

### Why this is non-obvious
The natural instinct is to extend design-review with a new `--type code` flag, keeping everything in one skill. This couples the taxonomy to the execution model — every lifecycle point inherits the adversarial machinery whether it needs it or not. Separating taxonomy from execution requires recognizing that the lifecycle model and the review skill are independent concerns.
