### Symptom
After using `ide_move_file` to extract types from module A to module B (same package), test files in module A fail with "cannot find symbol" errors even though module A has a Maven compile dependency on module B.

### Context
When extracting types to a new module (e.g. moving `LevelEvent.java` from `blocks/` to `summarisation-api/`), `ide_move_file` correctly moves the file and reports affected references. But it also removes import statements from files in the source module that previously resolved the type via same-package visibility.

In a split-package setup (both modules use `io.casehub.blocks.summarisation`), types that were accessible without an import (same package) now require an explicit import because they're in a different module (different JAR). The Maven dependency makes them available on the classpath, but the Java compiler still needs the import.

### What was tried (didn't work)
- Moving all 10 files with `ide_move_file` — IntelliJ removes wildcard imports like `import io.casehub.blocks.summarisation.*` from files that used to be in the same package as the moved types, even though those files still need the import via the Maven dependency.

### Root cause
IntelliJ's move refactoring optimizes imports in the source module based on the file's new location. It sees that `LevelEvent` is no longer in the same package/module and removes the import. But it doesn't check whether a Maven dependency makes the type available — it treats the cross-module boundary as "type no longer accessible" and removes the import rather than adding an explicit one.

### Fix
After moving files with `ide_move_file`, re-add wildcard imports to affected consumer files:

```java
// In test/source files that lost their imports:
import io.casehub.blocks.summarisation.*;
```

Check compilation after each batch of moves — `mvn --batch-mode test -pl <module>` reveals which files need import restoration.

### Why this is non-obvious
The `ide_move_file` result reports "affected files" and warns about accessibility, but the warnings reference every use site (150+ warnings for a widely-used type), making it hard to distinguish "needs import added" from "already fine." The move succeeds, the source module's pom.xml has the dependency, and the only signal is a compile error on the next build.
