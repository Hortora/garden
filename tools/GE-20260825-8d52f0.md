### Problem

Extracting 30+ fields from a large class (e.g. `CaseDefinition` → `CaseDefinitionSpec`) with 270+ call sites across 15+ modules. Direct extraction breaks everything simultaneously — the codebase won't compile until every caller is updated.

### Why this is non-obvious

The temptation is to make the structural change (move fields, update type signatures) and then fix all compilation errors. But with 270+ sites, the "break everything" approach means you can't compile or test until everything is migrated — and any mistake cascades.

### Technique

**Phase 1 — Delegation (nothing breaks):**
1. Create the target type with all extracted fields, getters, setters
2. Add a field of the target type on the source class
3. Make all existing getters/setters delegate to the target type
4. Update any code that accesses fields directly (e.g. Builder inner classes)
5. Compile and run all tests — everything passes because the public API is unchanged

**Phase 2 — Caller migration (incremental):**
1. Update callers module by module to use `source.getTarget().getField()` instead of `source.getField()`
2. Remove delegation getters from the source class as callers are migrated
3. Remove orphaned field declarations from the source class

Each step is compilable and testable. The delegation layer is the safety net.

### Alternatives considered

- **Break-and-fix:** Move fields directly, fix all 270+ compilation errors. Risk: hours of uncompilable state, easy to miss sites, no incremental testing.
- **IDE Move Members refactoring:** IntelliJ's Move Members can handle simple cases but struggles with cross-module Maven projects, inner class Builders that access private fields, and methods that use the moved fields indirectly.
