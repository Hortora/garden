### Symptom

LLM extraction pipeline produces structured JSON that passes basic JSON validation but silently deviates from the requested schema in three ways:

1. **Format drift** — requested a list of objects, got a dict with `{dominant, secondary}` keys (action_tendencies)
2. **Vocabulary drift** — requested 22 canonical OCC emotion types, got 65 types including invented ones (despair, frustration, grief) while 3 canonical types (happy-for, sorry-for, gloating) never appeared
3. **Field omission** — edge objects occasionally missing required `target` field, crashing downstream dedup
4. **Nesting drift** — justification fields nested inside parent objects (`pad.pad_justification`) instead of at the sibling level the schema requested

### Context

Discovered during cognitive corpus extraction from a Frida Kahlo biography using Claude Haiku 4.5. The extraction prompts list exact field names, types, and allowed values. The LLM treats these as suggestions — it uses natural language synonyms (sympathy instead of sorry-for), restructures output to what feels natural (nesting justifications inside their parent), and occasionally drops fields it considers optional.

### Root cause

LLMs optimise for natural language plausibility, not schema compliance. A prompt saying "use ONLY these 22 types" is a soft constraint — the LLM will use natural language alternatives when they feel more contextually appropriate. Structured output mode helps but doesn't eliminate drift for complex schemas with controlled vocabularies.

### Fix

Three-layer defense:

1. **Post-extraction normalisation** — map non-canonical values to nearest canonical type. Preserve `original_type` for audit trail. This catches vocabulary drift without losing data.
2. **Structural guards** — check for required fields before processing (`if not e.get('target'): continue`). This catches field omission without crashing.
3. **Nested field extraction** — explicitly check parent objects for nested children (`pad.get('pad_justification')`) and promote to expected level. This catches nesting drift.

Do NOT rely on stricter prompts alone — they reduce drift frequency but don't eliminate it.

### Why this is non-obvious

The extraction appears to work — JSON parses, fields are present, values look reasonable. The drift is silent: 88% of OCC emotions were canonical (looks fine at a glance), but 12% were invented types that downstream code doesn't handle. The missing 3 canonical types were never flagged because the coverage checker counted all emotions equally. Only a full vocabulary audit revealed the problem.

### Alternatives considered

- **Stricter prompts** — "Use ONLY these 22 types" reduces drift from 12% to ~5% but doesn't eliminate it. Not sufficient alone.
- **JSON Schema validation** — catches format and field issues but not vocabulary drift (any string passes schema validation for string fields).
- **Tool use / function calling** — enum parameters constrain vocabulary but add complexity and may not be available in all pipeline contexts.
