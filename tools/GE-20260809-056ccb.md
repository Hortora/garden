### Symptom

After restoring a pre-built Qdrant snapshot and cursor from a CI pipeline, the engine re-embeds the entire garden corpus (~90 minutes) instead of only processing delta entries added since the snapshot.

### Context

The Hortora engine uses `FlatChangeSource` to detect new garden entries via a file-system cursor. The cursor file (`garden.cursor`) records absolute file paths from the machine that performed the indexing. When the snapshot and cursor are packaged on a CI runner (e.g. `/home/runner/work/garden-corpus/`) and restored on a user's machine (`~/.hortora/garden/`), no cursor paths match the local filesystem. `FlatChangeSource` treats every entry as new.

The failure is silent — no error, no warning. The engine simply re-indexes everything, which takes ~90 minutes for a 2,600-entry corpus. The user sees slow startup but has no indication that the snapshot restore was effectively useless.

### Root cause

Cursors store absolute file paths as their change-detection key. Path comparison is exact-match — there is no path normalization or rebasing at load time.

### Fix

Rebase cursor paths at distribution time using a placeholder:

**At packaging (CI):**
```bash
GARDEN_ABS=$(cd garden-corpus && pwd)
sed "s|$GARDEN_ABS|__GARDEN_PATH__|g" ~/.hortora/cursors/garden.cursor > artifacts/garden.cursor
```

**At install (user machine):**
```bash
sed "s|__GARDEN_PATH__|$GARDEN_PATH|g" artifacts/garden.cursor > ~/.hortora/cursors/garden.cursor
```

This ensures cursor paths match the local garden location, and delta detection correctly identifies only entries added after the snapshot was created.

### Why this is non-obvious

The natural assumption is that restoring a snapshot + cursor is sufficient for instant startup. The cursor format is opaque (serialized Java state), so the absolute-path dependency isn't visible without inspecting the cursor content. The failure mode — silent full re-indexing — looks like "slow startup" rather than "broken cursor", making it hard to diagnose.

### Alternatives considered

- **Content-hash cursors:** Hash file contents instead of tracking paths. Would eliminate the portability problem entirely but requires changes to `FlatChangeSource` in the upstream `casehub-corpus` module — out of scope for the installer.
- **Relative-path cursors:** Store paths relative to the garden root. Same upstream change requirement.
- **Skip cursor distribution:** Let the engine re-index on first startup. Works but defeats the purpose of shipping a snapshot (90-min wait).
