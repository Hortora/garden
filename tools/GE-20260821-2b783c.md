### Symptom

Running `mvn -f /path/to/other/repo/pom.xml compile` fails with "The specified user settings file does not exist" pointing to a `.mvn/slot-settings.xml` in the current working directory — not in the target project.

### Context

Multi-repo slot workflows where the shell CWD is in one repo (e.g. `blocks-ui/components/channel-activity`) but the Maven command targets a different repo via `-f`. The CWD repo has its own `.mvn/` directory with a `maven.config` that references `slot-settings.xml`.

### Root cause

Maven resolves `.mvn/` configuration files (including `maven.config`) relative to the current working directory, not relative to the POM specified by `-f`. This is by design — `.mvn/` is a "Maven project directory" feature, but Maven determines the project directory from CWD, not from `-f`.

### Fix

Always `cd` to the target project directory before running Maven, or use a background command with `cd /target/dir && mvn compile`:

```bash
cd /path/to/target/repo && mvn compile
```

Alternatively, use absolute paths and ensure the CWD has no `.mvn/` directory.

### Why this is non-obvious

The `-f` flag strongly implies "run Maven as if this is the project" — developers expect all project-relative resolution (including `.mvn/`) to follow the `-f` target. The actual behavior (CWD for `.mvn/`, `-f` for pom.xml only) is a subtle split that only surfaces in multi-repo setups where different repos have different `.mvn/` configurations.
