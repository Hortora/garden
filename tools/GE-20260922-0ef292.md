### Symptom
A Maven plugin (spring-generator) was `mvn install`-ed from the canonical repo with a bug fix. Running `mvn generate-sources` in a slot clone still produced the old (buggy) output — no errors, no warnings, no indication that a stale artifact was being used.

### Context
The casehub slot infrastructure creates per-slot clones under `slots/198/`. Each slot has its own `.m2/` directory used as a local Maven repository. Maven resolves SNAPSHOT artifacts from this slot-local `.m2/` before checking the global `~/.m2/repository/`.

When `mvn install` runs on the canonical repo (outside any slot), the fresh artifact is written to `~/.m2/repository/`. The slot-local `.m2/` retains the old artifact from the last time `mvn install` ran inside that slot.

### What was tried (didn't work)
- Verified the global `.m2/repository/` jar had the fix (timestamp matched, `javap` confirmed new classes)
- Ran `mvn generate-sources` with `-X` — no indication which `.m2/` was being used
- Only the `Writing tracking file` debug line (`slots/198/.m2/...`) revealed the resolution source

### Root cause
Maven's local repository resolution checks the project-local `.m2/` directory (configured via `<localRepository>` in the slot's `settings.xml` or via `-Dmaven.repo.local`) before the global `~/.m2/repository/`. SNAPSHOT artifacts in the slot-local cache take precedence, and Maven does not compare timestamps between multiple local repositories.

### Fix
Copy the fresh artifact from the global to the slot-local `.m2/`:
```bash
cp ~/.m2/repository/io/casehub/<artifact>/<version>/<artifact>.jar \
   slots/198/.m2/io/casehub/<artifact>/<version>/<artifact>.jar
```

Or delete the slot-local entry to force re-resolution:
```bash
rm -rf slots/198/.m2/io/casehub/<artifact>/<version>/
```

### Why this is non-obvious
Maven silently resolves from the slot-local cache with no log message distinguishing it from the global repository. The `-X` debug output shows `Skipped remote request` but does not show which local repository provided the artifact. Only the `Writing tracking file` path reveals the slot-local `.m2/` is being used. A developer who just ran `mvn install` on the canonical repo has every reason to believe the fresh artifact is in use.
