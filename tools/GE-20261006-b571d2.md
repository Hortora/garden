## Symptom

When tokenizing multi-word search queries for per-token synonym expansion, compound terms like "coffee shop" get split into "coffee" and "shop" — each normalised independently, losing the compound meaning entirely. "coffee" might expand to unrelated senses, and "shop" loses the specific "coffee shop" → "café" mapping.

## Context

Building a cache key generator that normalises each token in a search query via a `TermNormalizer` backed by WordNet. The tokenizer splits on whitespace, then normalises each token independently. Compound terms in WordNet (stored as `coffee_shop` internally) are invisible to this pipeline.

## What was tried (didn't work)

Maintaining a static compound word list — requires manual curation, doesn't scale, and goes stale as the dictionary evolves.

## Fix

Use the normalizer itself as the compound detector. Before normalising individual tokens, try the space-joined bigram:

```java
int i = 0;
while (i < tokens.length) {
    if (i + 1 < tokens.length) {
        String bigram = tokens[i] + " " + tokens[i + 1];
        ExpandedTerm bigramResult = normalizer.normalize(bigram, domain);
        if (!bigram.equals(bigramResult.canonical()) || bigramResult.variants().size() > 1) {
            // Normalizer recognised it as a compound — use it
            expansions.put(bigram, bigramResult);
            canonical.append(bigramResult.canonical());
            i += 2;
            continue;
        }
    }
    // Fall back to unigram
    ExpandedTerm result = normalizer.normalize(tokens[i], domain);
    canonical.append(result.canonical());
    i++;
}
```

WordNet stores "coffee shop" as `coffee_shop`. extJWNL's `lookupIndexWord()` handles the space-to-underscore conversion internally, so passing "coffee shop" (with a space) works transparently.

### Why this is non-obvious

The standard approach is either: (a) maintain a compound word list, or (b) use a dedicated compound splitter/joiner. This technique requires neither — it leverages the dictionary as its own compound detector with zero additional infrastructure. The key insight is that the normalizer's return value (passthrough vs non-passthrough) is itself the signal for whether a bigram is a recognised compound.

### Alternatives considered

- **Static compound word list** — requires manual curation, grows stale, doesn't cover domain-specific compounds that might be added to the normalizer later.
- **N-gram tokenization** — try all n-grams up to some length, pick the longest match. More general but O(n²) and adds complexity for marginal benefit over greedy bigrams.
- **Pre-processing with a dedicated compound splitter** — external NLP dependency (e.g., Stanford NLP) for a problem the normalizer already solves.
