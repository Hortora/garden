### Symptom
LLM tool selection accuracy degrades when the total tool count across all connected MCP servers exceeds ~20-30 tools. The LLM picks wrong tools, hallucinates parameter names, or ignores available tools entirely.

### Context
Most individual MCP servers have 5-15 tools. The problem emerges at the aggregate level — a developer with filesystem (5), GitHub (10), Slack (5), database (8), search (3), browser (5) tools already has 36 tools before adding any domain-specific server. Each additional server's tools degrade selection accuracy for ALL tools, including other servers'. No official MCP guidance exists for this scenario.

### Fix
The hierarchical model pattern: replace N domain tools with two meta-tools:
- `model` — navigable operation catalog (discovery)
- `action` — generic dispatch (execution)

This collapses N tools to 2 in the tool definition, preserving context budget for other MCP servers. The LLM navigates the catalog via model, then dispatches via action. Validated with Claude: LLM correctly navigates domains, selects operations, and constructs complex nested params including record field expansion.

Key complementary technique: path-based param validation with schema in error messages (see GE-20260814-6b054e) makes the approach self-healing when the catalog scrolls out of context.

### Why this is non-obvious
The MCP ecosystem focuses on per-server tool design. No published guidance addresses what happens when tool count exceeds the LLM's effective selection capacity. The natural assumption is "more tools = more capability." In practice, tool count is a shared budget across all servers — being a good citizen means minimizing your footprint, especially for platform-scale systems with many operations.
