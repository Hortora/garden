## Symptom

A branch has `chore: branch closed` stamp, the GitHub issue is CLOSED, the hortora worklog shows the slot as `active` with no end events, and the code never reached main. Slot audits that check branch stamps or GitHub issue state report "done" — but the work is lost on an unmerged branch.

## Context

work-end performs several steps: squash commits, rebase onto main, merge to main, stamp the branch, close the GitHub issue, archive the slot. If the merge step fails or is skipped (e.g. rebase conflicts, session interrupted), later steps (stamp, issue close) can still execute independently. The result is a branch that LOOKS closed but whose code never landed.

Discovered during a systematic audit of slot 54 (engine#813). Four slots (54, 46, 57, 84) had this exact pattern — ~8,800 lines of production code sitting on stamped-closed branches that never merged. Previous slot audits missed all four because they checked the wrong signals.

## What was tried (didn't work)

1. Checking `git log` for `chore: branch closed` stamp — present, but lies
2. Checking `gh issue view` for CLOSED state — closed, but lies
3. Checking branch commit SHAs on main — correct approach but missed squash-merged commits (different SHAs)

## Root cause

work-end's steps are not atomic. The stamp and issue closure can succeed independently of the merge. The hortora worklog accurately tracks this (slot state=`active`, work_item `ended_at`=null, zero end events in the events table) but no audit was querying it.

## Fix

Query hortora worklog.db directly:

```sql
SELECT s.slot_number, wi.branch, wi.state, s.archived_at
FROM slots s
JOIN work_items wi ON wi.slot_id = s.id
WHERE s.state = 'active' AND s.archived_at IS NULL
```

Cross-reference with actual content on main — don't rely on SHAs (squash merges produce different SHAs). Instead, check whether the branch's key files/directories exist on main:

```bash
git ls-tree --name-only origin/main -- <new-module-directory>/
```

If the directory doesn't exist on main, the work never landed regardless of branch stamps or issue state.

## Why this is non-obvious

Branch stamps and GitHub issue state are the natural audit signals. Both are authoritative for their respective domains (git history, issue tracker). The failure mode is that work-end treats them as independent operations rather than a single atomic transaction — so they can be individually correct while the overall outcome is wrong. The hortora worklog is the only source of truth that tracks the full lifecycle, but it's not the first place anyone thinks to check.

### Why this fix

Querying worklog.db catches the gap because the worklog only transitions to `ended` when the full lifecycle completes. Unlike branch stamps (which can be written independently) and issue state (which can be closed independently), the worklog requires an explicit end event that only fires after successful merge.
