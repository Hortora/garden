# A test that hands the code the right input passes with the rule deleted: break the rule on purpose before trusting it

## Symptom

A new rule is added ("in this mode, always use location A, never B") with end-to-end tests. The tests pass. They also pass with the rule removed.

## Context

The test harness passes the location to the code explicitly, and passes A. Nothing in the test ever offers B, so the rule is never needed to get the right result. A later bug, where one step still used B, is invisible.

## Technique

Two cheap steps, in this order:

1. **Make the harness supply the wrong answer the real caller would supply.** If production callers in the old mode report B, hand the pipeline B and assert that B is untouched afterwards (bytes and version-control status) and that A changed.
2. **Delete the rule and run the tests.** Replace the deciding function's body with the old behaviour (`return None`). Every test that claims to pin the rule must fail. Restore it with a checkout, not by retyping.

```
with the rule broken on purpose:   8 failed
with the rule in place:            8 passed
```

A test that survives step 2 is describing the harness, not the code.

## Why this is non-obvious

The tests read correctly and exercise the full sequence, so they look like strong evidence. The gap is in what the fixture hands over, which is easy to copy from an existing test that predates the rule. Running the mutation takes a minute and is the only direct evidence that the test can fail.

### Alternatives considered

- Reviewing the tests by reading: missed the gap; the harness argument looked like setup.
- A mutation-testing framework over the whole suite: sound, but slow on suites that build real repositories; one hand-made mutation at the rule is enough here.
