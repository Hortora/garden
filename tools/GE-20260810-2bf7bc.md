### Problem

Integrating a complex third-party UI library (panel management, charting, rich editors) into a platform's component system. The library has its own DOM management, lifecycle, and API surface. Direct exposure couples the platform to the library's versioning and API stability. Full wrapping duplicates the library's logic.

### Pattern

Split into two layers:

**Engine** — pure state manager. Owns the data model (frame positions, tab order, z-indices). Source of truth for all state queries and mutations. Never imports the library. Serializable for persistence.

**Backend** — rendering implementation. Wraps the library behind a stable interface. Receives state from the engine, translates to library API calls. Reports user interactions back to the engine via callbacks.

```
Consumer → Engine (pure state) → Backend (library wrapper) → Library (DOM)
              ↑                        |
              └── callbacks ───────────┘
```

### Key design decisions

1. **Content factory at attach() time** — the backend receives a factory function when attached to a container. Both initial rendering and dynamic additions use the stored factory. This lets the library's internal lifecycle (e.g. Dockview's `createComponent` callback) integrate naturally.

2. **Escape hatch** — `backend.unwrap(): unknown` returns the raw library instance. Typed as `unknown` to avoid leaking library types into the platform API. Advanced consumers cast it. Documented as unstable — mutations via `unwrap()` are invisible to the engine.

3. **Lazy loading** — the backend factory is async (`createDockviewBackend(): Promise<Backend>`). The library is `await import()`-ed at first use. Zero cost for consumers who don't use the component. CSS is injected idempotently via a data attribute marker.

4. **Re-render survival** — engine serializes state before teardown, backend is destroyed, new backend created with saved state on re-render. The engine is the persistence layer, not the library.

### Suitability

Works well when:
- The library manages its own DOM (Dockview, Monaco, xterm)
- The platform has its own state management and persistence patterns
- Multiple consumers need different content inside the library's containers
- Library upgrades should be internal, not API-breaking

Less useful when:
- The library is render-only (no internal state to diverge from)
- Only one consumer exists (wrapper overhead not justified)
- The library's API IS the desired public API

### Why this is non-obvious

The obvious approaches — expose the library directly (coupling) or wrap everything (duplication) — both have well-known problems. The engine/backend split seems like over-engineering until you encounter re-render survival: when the platform tears down and rebuilds DOM (e.g. dock-workbench zone rearrange), the library instance is destroyed. Without a separate state layer, all frame positions, tab order, and z-indices are lost. The engine makes persistence and re-render free because state was never in the library.
