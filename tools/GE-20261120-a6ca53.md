# git cherry-pick onto the commit's own parent can produce the identical SHA, so no second commit exists

## Symptom

A test builds a "duplicate commit" by committing on a feature branch, checking out the base, and cherry-picking that commit. The code under test then reports no duplicates. `git merge feature` says "Already up to date" or fast-forwards. The test passes or fails depending on machine speed and on which identity git is configured with.

## Context

The commit is cherry-picked onto its own parent. Tests run with a fixed `user.name` / `user.email` (a hermetic `GIT_CONFIG_GLOBAL`), and the whole sequence finishes within one second.

## Root cause

A commit's SHA is a hash of its tree, parent, author line, committer line and message. Cherry-pick keeps the author name, email and **author date**. Picked onto the same parent, the tree and parent are the same too. The only thing that can differ is the committer line, and with the same identity inside the same second that is identical as well. Git writes the same object: the "new" commit is the original.

## Fix

Give the pick a different committer date, and assert the two SHAs differ:

```python
picked = subprocess.run(
    ["git", "-C", repo, "cherry-pick", feat_sha], capture_output=True, text=True,
    env={**os.environ, "GIT_COMMITTER_DATE": "2030-01-01T00:00:00 +0000"})
assert rev_parse(repo, "HEAD") != feat_sha
```

## Why this is non-obvious

Cherry-pick is thought of as "make a copy". It usually does make a new object, because in real use the committer or the clock differs. Making test identities deterministic, which is good practice, is exactly what removes the difference. The failure then looks like a bug in the code that searches for duplicates.

### Alternatives considered

- `sleep 1` between the commits: works, slows the suite, still fragile.
- A different committer identity for the pick: works, but the date is simpler to set per command.
