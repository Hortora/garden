### Symptom
A script runs `git checkout main` (succeeds) then `git pull --rebase origin main` (fails with conflict). The script reports success, but the repo is in a "rebase in progress" state with HEAD detached. All subsequent `git checkout` calls fail with "cannot checkout: you are in the middle of a rebase".

### Context
Automated branch-closing scripts that checkout main and pull the latest changes. When local main has diverged from origin (e.g., another session pushed while this one was running), the pull --rebase can conflict. The script checked the checkout result but treated the pull as "non-fatal if fails."

### What was tried (didn't work)
- Ignoring the pull result and continuing — leaves the repo in a broken state that blocks all future checkouts
- Retrying the full checkout_main script — `git checkout main` now fails because rebase is in progress

### Root cause
`git pull --rebase` on conflict enters an interactive rebase state: HEAD is detached, `.git/rebase-merge/` or `.git/rebase-apply/` directories exist, and the repo is locked until `git rebase --abort` or `git rebase --continue` is called. Unlike `git pull` (merge mode), which leaves you on the target branch with conflict markers, `git pull --rebase` detaches HEAD entirely.

### Fix
Three-part defense:

1. **Before checkout**: abort any in-progress rebase from a prior failed run
2. **After pull --rebase**: check the return code and abort the rebase if it failed
3. **After all operations**: verify HEAD is actually on `main` before reporting success

```python
def _abort_rebase_if_needed(repo_path):
    rebase_dir = Path(repo_path) / ".git" / "rebase-merge"
    rebase_apply = Path(repo_path) / ".git" / "rebase-apply"
    if rebase_dir.exists() or rebase_apply.exists():
        git(repo_path, "rebase", "--abort")

def _safe_pull_rebase(repo_path, remote, branch="main"):
    r = git(repo_path, "pull", "--rebase", remote, branch)
    if r.returncode != 0:
        _abort_rebase_if_needed(repo_path)
```

### Why this is non-obvious
The distinction between `git pull` (merge) and `git pull --rebase` failure modes is subtle. With merge, you stay on the target branch with conflict markers — the repo is usable. With rebase, HEAD detaches and the repo is locked. Scripts that treat pull as "non-fatal" are correct for merge mode but dangerous for rebase mode. The `.git/rebase-merge` and `.git/rebase-apply` directories are the only reliable indicators — `git status` shows "rebase in progress" but scripts often don't parse that output.
