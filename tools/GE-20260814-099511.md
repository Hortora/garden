### Symptom
`mvn compile` in a slot project fails with `cannot find symbol` for a class that was just added to a dependency and installed via `mvn install` on the host.

### Context
Work-slot creates parallel clone-based workspaces with `.mvn/maven.config` containing `-Dmaven.repo.local=<slot>/.m2`. This redirects all Maven dependency resolution to the slot's local repository. When a dependency (e.g. `casehub-engine-api`) is updated in the host repo and installed with `mvn install`, the install writes to `~/.m2` (global) — the slot's `.m2` never sees the update.

### What was tried (didn't work)
1. `mvn install` from the dependency repo — writes to global `~/.m2`, invisible to slot
2. `mvn dependency:resolve -U` in the slot — pulls stale remote SNAPSHOT, overwrites with older version
3. Deleting timestamped remote jars from slot `.m2` — new metadata files still point to stale versions
4. `-nsu` (no snapshot updates) flag — still resolves from stale cached metadata
5. `-o` (offline) flag — same result

### Root cause
The slot's `.mvn/maven.config` forces `-Dmaven.repo.local=<slot>/.m2`. This is a completely separate Maven repository from `~/.m2`. Installing a dependency on the host writes to `~/.m2` which the slot's Maven process never consults.

### Fix
Install the dependency explicitly into the slot's local repository:

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 26) mvn install -f /path/to/dependency/pom.xml -DskipTests -Dmaven.repo.local=/path/to/slot/.m2
```

Or install with `-pl <module> -am` to include ancestor POMs:

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 26) mvn install -f /path/to/parent/pom.xml -pl api -am -DskipTests -Dmaven.repo.local=/path/to/slot/.m2
```

### Why this is non-obvious
The slot's `.mvn/maven.config` is infrastructure plumbing — developers don't think about it when running `mvn install` on the dependency. The symptom (class not found) looks like a compilation error, not a dependency resolution error. The jar in `~/.m2` clearly contains the class (`javap` confirms it), making the failure seem impossible.

### Alternatives considered
- Symlinking slot `.m2` to global `~/.m2` — defeats slot isolation purpose
- Using `mvn install` with no `-Dmaven.repo.local` flag — installs to wrong location
