### Symptom
A `.gitignore` entry with a trailing slash (e.g. `.casehub-packages/`) does not ignore a symlink that points to a directory. `git status` shows it as `??` (untracked) instead of `!!` (ignored). `git check-ignore -v` returns exit code 1 (not ignored) or `fatal: pathspec is beyond a symbolic link`.

### Context
Monorepo slot clones that symlink shared dependency directories from a parent repo. The `.gitignore` was authored for the parent where `.casehub-packages` is a real directory. In the slot clone, it's a symlink.

### What was tried (didn't work)
- `.casehub-packages/` in `.gitignore` — fails silently; symlink still shows as untracked
- `git check-ignore -v .casehub-packages/` — `fatal: pathspec is beyond a symbolic link`
- `git check-ignore -v .casehub-packages` (without slash) — exit 1, not matched

### Root cause
Git's trailing-slash pattern (`foo/`) explicitly means "only match directories." Git treats symlinks as files regardless of what they point to — a symlink to a directory is still a file entry in the index. The trailing slash pattern skips it entirely.

### Fix
Remove the trailing slash from the `.gitignore` pattern:

```gitignore
# Before (fails for symlinks):
.casehub-packages/

# After (works for both real directories and symlinks):
.casehub-packages
```

The bare pattern matches any path component with that name, whether it's a file, directory, or symlink.

### Why this is non-obvious
The `.gitignore` docs recommend trailing slash for directories to avoid accidentally ignoring files with the same name. This creates a habit of always using `foo/` for directory patterns. When the path becomes a symlink (e.g. in a clone or worktree), the pattern silently stops matching — no warning, no error in normal usage.

### Why this fix
The bare pattern without trailing slash is the only pattern form that matches all three path types (file, directory, symlink). The trailing slash is a specificity optimization that breaks when the filesystem representation changes.
