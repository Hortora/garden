### Symptom

After extracting a module's types from repo A to repo B, both repos compile and pass tests — but repo A still contains the original files. The duplication is invisible because each repo resolves its own copy independently. No compilation error, no test failure, no warning.

### Context

Cross-repo code extraction (moving types from one Maven repo to another) during platform refactoring. The source types were copied to the target repo and new implementations were built there, but the originals in the source repo were never deleted.

### What was tried (didn't work)

Manual copy of Java files from source repo to target repo, followed by building and testing the target. The source repo was not cleaned up because it still compiled — the old types had no visible consumers after the target repo was self-sufficient.

### Root cause

Copy-based extraction creates a fork, not a move. Both copies compile independently. The source repo's consumers silently bind to the local copy even though the canonical version is now in the target repo. Over time, the copies can diverge (different bug fixes applied to different copies), and consumers in the source repo never benefit from improvements in the target.

### Fix

Open both repos in a single IntelliJ workspace (`ide_open_workspace` with both module paths). Use **refactor-move** (`ide_move_file`) to relocate each type from source to target. IntelliJ:
1. Moves the file to the target package
2. Updates all import statements across both repos
3. Deletes the original file

This is atomic — no orphans possible. The source repo immediately fails to compile if any consumer still references the old location, making cleanup gaps visible.

### Why this is non-obvious

The copy approach appears to work — both repos compile, tests pass, everything looks clean. The duplication only surfaces when someone audits both repos side-by-side, which may never happen. In the observed case (neocortex #895/896 → connectors), 20+ types were duplicated for months before #908 discovered the problem.

### Why this fix

IDE refactor-move is the only approach that guarantees atomicity. Manual file deletion after copy requires auditing every consumer across repos — error-prone when repos have dozens of modules with transitive dependencies.

### Alternatives considered

- **Manual copy + manual delete** — works but requires exhaustive consumer audit across all modules in the source repo. Easy to miss consumers in test scope or optional dependencies.
- **Script-based migration** — can automate the delete + import rewrite, but fragile for complex import patterns (wildcard imports, static imports, same-name types in different packages).
