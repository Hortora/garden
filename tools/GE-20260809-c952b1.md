### Symptom
Two frameworks need to compose: a DSL layer (producing execution models/plans) and an execution engine (providing durability, retry, recovery). Building execution infrastructure in the DSL duplicates the engine. Compiling the DSL to engine primitives loses the DSL's expressiveness.

### Context
When a builder DSL produces rich execution models (e.g. multi-agent orchestration with routing, aggregation, termination strategies) and a separate engine provides durable worker execution (persistence, retry, audit), neither "DSL owns execution" nor "engine owns everything" works cleanly. The DSL's iteration model doesn't map to the engine's reactive dispatch, and the engine's primitives can't express the DSL's composition patterns.

### Fix
Use the engine's `WorkerFunctionHandler` SPI (or equivalent handler/plugin interface) as the composition boundary:

1. **Guest framework** (DSL): produces an execution model and provides an in-process driver
2. **Host framework** (engine): provides a handler SPI that receives work, returns results, and wraps execution with durability
3. **Bridge handler**: implements the host's handler SPI, creates the guest's driver internally, and bridges sub-agent dispatch to the host's runtime API

```
Host dispatches work → Bridge Handler → Guest Driver runs
                                         ↓
                                    Agent dispatch → Host Runtime.execute()
                                         ↓
                                    Host handles retry, audit, persistence
```

Key design choices:
- **Direct-call agents bypass the bridge** — in-process lambdas (test agents, simple functions) call directly without host overhead
- **External agents go through the host** — get retry, audit, EventLog for free
- **Composed agents recurse** — nested patterns use the same bridge, getting durability at every level
- **The model is constructed at definition time, not serialized** — function references (lambdas, strategies) live in memory on the handler, not in persistent storage

### Why this is non-obvious
The natural instinct is binary: either the DSL compiles down to engine primitives (losing expressiveness) or the DSL builds its own execution infrastructure (duplicating the engine). The guest/host pattern preserves both: the DSL keeps its full composition model, the engine keeps its full durability infrastructure, and the handler SPI is the narrow interface between them. The key insight is that the handler boundary IS the durability boundary — everything inside runs in-process, everything outside is durable.
