### Symptom
Eviction policy uses `idleMs × memoryFactor` to score cache entries for eviction. High-memory entries that were recently used score ~0 (because idleMs ≈ 0), making memory pressure invisible to the eviction queue. A 500MB entry used 1 second ago survives while a 50MB entry idle for 10 minutes gets evicted.

### Context
Any capacity-bounded cache or pool managing resources with different costs — agent session pools (tmux sessions with varying RSS), database connection pools, container orchestrators, cloud instance schedulers. The eviction policy needs to balance "how long since last use" with "how much is this costing."

### Root cause
Multiplicative scoring makes one signal irrelevant when the other approaches zero. `idle × memory` means idle=0 → score=0 regardless of memory. The two signals are not independent factors of the same quantity — they're independent reasons to evict.

### Fix
Use additive scoring: `idleSeconds + (memoryMB / normalizer)`.

```java
double evictionScore(Instant now) {
    long idleSeconds = Duration.between(lastInteraction, now).toSeconds();
    double memoryMB = lastMemoryBytes / (1024.0 * 1024.0);
    return idleSeconds + (memoryMB / 10.0);
}
```

With this formula:
- 500MB, 0s idle: score = 0 + 50 = 50 (visible to eviction)
- 10MB, 0s idle: score = 0 + 1 = 1
- 10MB, 60s idle: score = 60 + 1 = 61
- 500MB, 60s idle: score = 60 + 50 = 110

The normalizer (10.0) controls how many seconds of idle time 1MB of memory is "worth." Tune per domain.

### Why this is non-obvious
The multiplicative formula *looks* right — "idle time weighted by memory" is intuitive English. But multiplication makes memory a no-op at zero idle time, which is exactly when memory pressure matters most (all entries recently used, need to pick the most expensive one).
