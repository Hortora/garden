### Symptom

After fixing a bug in a dependency repo and running `mvn install`, the consuming project still uses the old (broken) SNAPSHOT jar. The build succeeds but tests fail with the pre-fix behaviour. The jar file timestamp in `~/.m2` is stale.

### Context

The dependency repo lives in a git worktree or clone-based slot that has `.mvn/maven.config` containing `-Dmaven.repo.local=<slot>/.m2`. This is used for build isolation — each slot gets its own Maven local repository to avoid cross-contamination between parallel development branches.

### Root cause

Maven's `-Dmaven.repo.local` in `.mvn/maven.config` is inherited by all `mvn` invocations in that directory tree, including `mvn install`. The jar is written to `<slot>/.m2/repository/...` instead of `~/.m2/repository/...`. The consuming project resolves SNAPSHOTs from the global `~/.m2` and never sees the updated artifact.

### Fix

Pass the global repo explicitly when installing for cross-slot consumption:

```bash
mvn -f /path/to/dependency/pom.xml clean install -DskipTests \
  -Dmaven.repo.local=/Users/<user>/.m2/repository
```

The explicit `-Dmaven.repo.local` on the command line overrides the `.mvn/maven.config` value.

### Why this is non-obvious

`mvn install` is universally expected to write to `~/.m2/repository`. The `.mvn/maven.config` override is completely silent — no log output indicates the redirection. The install succeeds, the jar IS written (just to the slot's `.m2`), and the consuming project's build also succeeds (it finds a jar in global `.m2` — just the stale version). Both sides report success while using different artifact versions.

### Alternatives considered

- Symlinking slot `.m2` to global: breaks isolation, defeats the purpose of slot-level `.m2`
- Running `mvn install` from outside the slot directory: still picks up `.mvn/maven.config` via the `-f` flag if the pom is inside the slot
