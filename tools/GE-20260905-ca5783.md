### Context
Adding a component to a Java record (e.g. `LevelEvent` gaining a 4th component `tenancyId`) breaks every constructor call site. For records with widespread use (200+ call sites across multiple modules), manual migration is impractical.

### Technique
IntelliJ's `ide_structural_search_replace` operates at the AST level and handles nested expressions that text regex cannot:

```
Search:  new LevelEvent<>($arg1$, $arg2$, $arg3$)
Replace: new LevelEvent<>($arg1$, $arg2$, $arg3$, null)
```

**Key capabilities:**
- `$variable$` matches any expression, including nested constructors like `new EventLevel("L1", 0)` — text regex would break on the inner parentheses
- Scoped execution: `scope: "project_test_files"` applies one replacement (null) while `scope: "project_production_files"` applies a different one (propagated value)
- Cross-module: run separately per module with different `project_path` values

**Real example:** 248 call sites migrated in 4 invocations:
- summarisation-api test files: 165 replacements (null tenancyId)
- summarisation-api production: 2 replacements (propagated tenancyId — done separately via text replace)
- blocks production: 2 replacements (null)
- blocks test + example files: 79 replacements (null)

### Why this is non-obvious
Most developers would reach for sed/regex, which fails on nested constructors. IntelliJ's SSR is IDE-only — it's not available from command-line tools. The `project_test_files` vs `project_production_files` scope split enables different replacement strategies for the same pattern in a single pass, which isn't possible with text tools.
