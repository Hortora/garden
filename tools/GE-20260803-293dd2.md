### Symptom

A state machine stores its state in a file on a git branch (e.g. `.meta` in a workspace). Some transitions (pause, cleanup) switch the branch to main — after which the state file is no longer in the working tree. If state is written before the switch, a crash between write and switch leaves orphaned state. If state is written after the switch, the file isn't accessible.

### Context

Work lifecycle systems where `.meta` tracks lifecycle state on a feature branch. The `work_pause` transition must write `state: paused` to `.meta` AND switch both repos to main. The `cleanup` transition must write the final state AND return to main. In both cases, the branch switch makes `.meta` inaccessible from the new branch.

### What developers typically do

Write state before the branch switch (optimistic write). This works until a crash occurs between the write and the switch — the state file says "paused" but the repos are still on the feature branch.

### Fix

Split the transition protocol into three phases:

1. **`transition()` — validate only.** Read current state, check the transition table, return a `TransitionResult` with effects lists. No state written.

2. **`commit_transition()` — verify + write.** Execute pre-commit effects (the work that must happen while still on the branch), then re-read state to detect concurrent modification, then write the new state atomically (temp file + `os.replace()`). This is the commit point.

3. **Post-commit effects.** Execute branch switches and cleanup AFTER state is committed. If these fail, state reflects completed work — the next session detects the state and re-runs the missing cleanup.

```python
# Phase 1: validate
result = transition(meta_path, 'work_pause')
# result.effects = ['wip_commit']
# result.post_commit_effects = ['switch_to_main', 'push_stack']

# Phase 2: execute pre-commit effects, then commit
execute_effects(result.effects)
commit_transition(meta_path, result)  # writes state: paused

# Phase 3: post-commit effects (branch switch)
execute_effects(result.post_commit_effects)  # switch to main
# .meta is now inaccessible — but state was already written
```

### Why this is non-obvious

The two-phase pattern (validate then write) is well-known. The three-phase split is needed specifically because of the git branch model — the state file's accessibility depends on which branch is checked out. Most state machine implementations don't have this constraint. The insight is that some effects must run AFTER the state is committed because they make the state file inaccessible — and that's safe because state already reflects the completed transition.
