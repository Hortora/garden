### Symptom
Units cluster at wrong map positions far from bases and resources when replaying SC2 replays. Probes appear to walk through mountains and huddle in areas with no minerals or gas — typically at positions that are exactly half the correct coordinates.

### Context
When parsing SC2 `.SC2Replay` files via the Scelight library, two event systems provide unit positions:

- **Tracker events** (`UnitBornEvent.getXCoord()`/`getYCoord()`) — used for unit birth positions, mineral/geyser locations
- **Game events** (`CmdEvent.getTargetPoint().getXFloat()`/`getYFloat()`) — used for movement orders, Smart/right-click commands

Both return coordinates that look like valid map positions within map bounds.

### What was tried (didn't work)
1. Checked for a constant playable-area offset between coordinate systems — the difference was not constant
2. Checked if Y-axis was flipped — ratios didn't match a flip
3. Suspected IPv6/IPv4 rendering issue in the browser — coordinates were wrong in the data itself

### Root cause
The two event systems use **different coordinate scales**. Tracker events use the full map grid resolution (e.g. a mineral at position `(125, 42)`). Game events use exactly **half** that resolution (the same mineral targeted by a Smart command appears as `(62.5, 21.3)`).

Cross-referencing confirmed the 2x ratio:
- Mineral tracker position `(125, 42)` → game event target `(62.5, 21.3)` → ratio `125/62.5 = 2.0`, `42/21.3 ≈ 2.0`
- Mineral tracker position `(131, 46)` → game event target `(65.5, 23.3)` → ratio `131/65.5 = 2.0`, `46/23.3 ≈ 2.0`

No documentation exists for this mismatch in Scelight, the SC2 protocol specification, or any public source.

### Fix
Multiply game event target point coordinates by 2 when extracting movement orders:

```java
float x = tp.getXFloat() * 2;
float y = tp.getYFloat() * 2;
```

### Why this is non-obvious
Both event types return float/int coordinates that look like valid map positions. The values are within map bounds in both cases — a position of `(62.5, 21.3)` on a `160x208` map doesn't trigger any bounds check. The mismatch is only discoverable by cross-referencing a known entity's position from both event sources. The 2x ratio is exact but not documented anywhere.

### Alternatives considered
- Applying a constant offset (playable area origin) — ruled out because the difference scaled with position, not a fixed shift
- Y-axis flip — the ratio was consistent across both axes, not a single-axis issue
