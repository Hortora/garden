## Symptom

Write tool reports success, but the file on disk contains the old content. The "file modified since read" error appears on the next Write attempt, but doesn't explain that the previous Write's content was lost.

## Context

During a ctx.py refactoring (issue #202), the Write tool successfully wrote a 270-line refactored version. A linter or formatter hook ran immediately after, reverting the file to its pre-write state. The system reminder showed "ctx.py was modified by the user or a linter" with the **original** file content — confirming the write was overwritten.

The next Write attempt failed with "File has been modified since read" because the file state tracker saw the linter's version, not the Write tool's version.

## What was tried (didn't work)

1. Write tool — succeeded but content was reverted by linter
2. Re-reading and re-writing — hit "modified since read" error
3. Had to Read the file again (resetting the tracker), then Write again

## Root cause

The Write tool and linter hooks have a race condition. The Write tool marks the file as "written" in its state tracker, but the linter immediately overwrites the file. The state tracker doesn't detect that its content was replaced — it only detects that the file was "modified."

## Fix

After any Write to a file that may have linter hooks, immediately verify the content is actually on disk before proceeding:

```bash
grep -n "expected_unique_string" /path/to/file.py
```

If the content isn't there, Read the file again to reset the tracker, then Write again.

## Why this is non-obvious

The Write tool reports success. There's no error. The only signal is a system reminder mentioning "modified by the user or a linter" — which is easy to miss in a long session. The content loss is completely silent.
