git ls-tree implicitly limits its output to entries under the current working
directory. When you use `git -C <subdir> ls-tree <rev>:<path>`, the tree object
resolves correctly (the path lookup works from the repo root) but the OUTPUT is
filtered to only entries whose full path starts with the CWD prefix. This
produces silent empty results — returncode 0, no stderr, just no stdout.

`git cat-file -e` does NOT apply this filter. The same `<rev>:<path>` that
returns true from cat-file returns empty from ls-tree when run from a subdirectory.

### Symptom
`git -C /repo/subdir ls-tree --name-only main:subdir/blog` returns empty output
(rc=0) even though `git -C /repo ls-tree --name-only main:subdir/blog` correctly
returns `entry.md`.

### Root cause
ls-tree applies an implicit CWD-based path filter on its output. When the
tree-ish already drills into a subtree via `<rev>:<path>` syntax, the entries
are relative to that subtree — but the CWD filter still expects them to match
the full repo-root-relative prefix. They never match, so everything is filtered.

### Fix
Add `--full-tree` to ls-tree calls that operate from a subdirectory:

```bash
git -C /repo/subdir ls-tree --full-tree --name-only main:subdir/blog
```

`--full-tree` disables the CWD-based filtering. cat-file calls need no fix.

### Why this is non-obvious
The behavior is completely silent — rc=0, no error, no warning. cat-file with
the same path works correctly, leading you to assume ls-tree should too. The
git documentation mentions `--full-tree` but does not explain that the default
behavior filters by CWD, or that this interacts badly with `<rev>:<path>` syntax.
