### Symptom

`ide_create_file` with `project_path=/path/to/slot/platform` silently creates files in `/path/to/canonical/platform` (the main clone) instead of the slot directory. No error is reported — the tool returns success.

### Context

When using casehub's slot system (parallel git clones at `slots/NNN/repo`), IntelliJ has the canonical clone (e.g. `/Users/dev/casehub/platform`) open as a workspace. The slot clone at `/Users/dev/casehub/slots/181/platform` has the same Maven project name ("platform"). When `ide_create_file` receives a project_path pointing to the slot, IntelliJ resolves it to the already-open canonical project by matching on project name, not path.

### What we tried (didn't work)

1. Passing the slot's absolute path as `project_path` — still resolved to the canonical clone
2. `ide_open_project` with the slot path — returned "Project 'platform' is open and ready" (matching the canonical clone by name)
3. `ide_open_workspace` with the slot path as a module — appeared to open but `ide_read_file` couldn't find files at the slot-relative path

### Root cause

IntelliJ's project resolution uses project name as the primary key, not filesystem path. When two directories produce the same Maven project name, the first-opened project wins. The MCP plugin's project_path parameter is used for disambiguation but the underlying IntelliJ API resolves by name first.

### Fix

Use the `Write` tool (which operates on absolute filesystem paths) for new files in the slot directory. `Write` is allowed by hooks for new files. For existing file edits, use `Edit with replace_all: true` which also uses filesystem paths directly.

For file moves/copies between clones: delete from the source repo and recreate in the target using `Write`. `ide_move_file` only works within a single IntelliJ project.

### Why this is non-obvious

The tool returns success — there's no indication that the file was created in the wrong location. The developer only discovers the problem when `mvn compile` reports "Nothing to compile — all classes are up to date" (because the source files aren't where Maven expects them). The 33 files created this way must be deleted from the wrong location and recreated in the correct one.

### Why this fix

Using filesystem-based tools (`Write`, `Edit`) bypasses IntelliJ's project name resolution entirely. It's less elegant than semantic IDE operations but reliable when working across multiple clones of the same repo.

### Alternatives considered

- Opening the slot as a separate IntelliJ workspace: failed due to name collision
- Using bash `cp`/`mv`: blocked by IntelliJ-first hooks that enforce IDE tools for Java files
- Symlinking the slot into the IntelliJ workspace: would cause other issues with git state
