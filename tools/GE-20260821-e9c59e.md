## Symptom

Need to find slots where work-end didn't complete — code was written but never merged to main.

## Context

The hortora worklog.db tracks slot lifecycle state independently of git (branch stamps) and GitHub (issue state). When work-end fails partway through, git and GitHub can both show "done" while the worklog accurately reflects the incomplete state.

## Fix

Three tables, three queries:

```sql
-- Find active slots that were never archived
SELECT slot_number, state, created_at, archived_at
FROM slots
WHERE state = 'active' AND archived_at IS NULL;

-- Cross-reference with work items that never ended
SELECT s.slot_number, wi.branch, wi.state, wi.ended_at
FROM work_items wi
JOIN slots s ON wi.slot_id = s.id
WHERE wi.state = 'active' AND wi.ended_at IS NULL;

-- Verify by checking events — only slot-create, no end events
SELECT e.event_type, e.timestamp
FROM events e
WHERE e.slot_id = (SELECT id FROM slots WHERE slot_number = <N>)
ORDER BY e.timestamp;
```

Filter out test paths (`WHERE r.path NOT LIKE '/private/%'`) when joining with the repos table — the worklog includes pytest fixture paths.

To verify the code never landed on main, check whether the branch's key files exist:

```bash
git ls-tree --name-only origin/main -- <new-module-directory>/
```

Don't rely on commit SHAs — squash merges produce different SHAs.

## Why this is non-obvious

The natural audit signals (branch stamps, GitHub issue state) are both wrong in this failure mode. The worklog.db is an operational database — not the first place a developer thinks to look for lifecycle state. But it's the only source that tracks the full end-to-end lifecycle and only transitions on successful completion.
