### The technique

In a YAML-based DSL, parameterised constructs (like `wait:`, `match case`) that hold
both a configuration value and child actions traditionally use a container key for the
children:

```yaml
# Before — container key ceremony
- wait: fast-signal
  do:
    - log: { message: "arrived" }
```

The container key (`do:`, `steps:`, `then:`) exists solely because of a misconception
that a YAML mapping can only hold one key-value pair. In fact, a YAML mapping can have
any number of keys — the constraint is that a node must be either a mapping OR a sequence,
not both. Multiple keys in the same mapping are standard YAML.

The fix: treat child actions as sibling keys in the same mapping. The parser strips
known configuration keys and resolves the remaining keys as the action body using
existing resolution logic:

```yaml
# After — inline sibling keys
- wait: fast-signal
  log: { message: "arrived" }

# Multiple actions — use block (existing structural grouper)
- wait: fast-signal
  block:
    - log: { message: "step 1" }
    - log: { message: "step 2" }
```

### Parser implementation

```typescript
// Strip config keys, resolve the rest as a step
const rest = Walker.stripKeys(branchObj, ['wait']);
const branchStep = Object.keys(rest).length > 0
  ? [Walker.resolveOne(rest, catalog, depth + 1, seenNames)]
  : [];
```

The `resolveOne()` function already classifies keys by type (reserved, decorator,
catalog action) — no new dispatch logic needed.

### Where container keys ARE needed

Semantic branch labels that distinguish multiple branches are not ceremony:
- `then:`/`else:` on `if:` — distinguish true/false branches
- `catch:`/`finally:` on `try:` — distinguish error handling paths
- `cases:` on `match:` — the array of case objects

These stay because they carry meaning beyond "here are the children."

### Why this is non-obvious

The natural instinct when designing a YAML DSL is to reach for a container key
whenever a construct needs both configuration and children. The YAML spec doesn't
forbid multiple keys — the limitation is mixing collection types (mapping vs sequence)
in one node, not the number of keys. Most DSL designers (and LLMs) default to a
wrapper key without questioning whether the mapping itself can carry the children
as sibling keys.
