## Symptom

Developer expects SSE (Server-Sent Events) for server→client push updates —
the standard unidirectional pattern. Writes SSE endpoints (`@RestStreamElement`,
`Multi<SseEvent>`) that never reach the frontend because the platform uses
WebSocket transport exclusively.

## Context

The CaseHub platform originally used `SSEManager` for push updates. This was
replaced by a unified WebSocket push stack with bidirectional topic management.
`SSEManager` was removed from production code. The change was driven by the
need for cursor recovery (client tells server what it last received) and
topic subscription management — both require client→server messaging that
SSE cannot provide.

## The technique

### Backend

Add three dependencies and create a `@WebSocket` endpoint:

```xml
<dependency>
  <groupId>io.casehub</groupId>
  <artifactId>casehub-pages-push</artifactId>
</dependency>
<dependency>
  <groupId>io.casehub</groupId>
  <artifactId>casehub-pages-push-runtime</artifactId>
  <scope>runtime</scope>
</dependency>
<dependency>
  <groupId>io.quarkus</groupId>
  <artifactId>quarkus-websockets-next</artifactId>
</dependency>
```

The endpoint delegates to `TopicRegistry`, `EventStore`, and `PushRequest.parse()`:

```java
@WebSocket(path = "/push")
public class AppPushEndpoint {
    @Inject TopicRegistry topicRegistry;
    @Inject EventStore eventStore;

    @OnTextMessage
    void onMessage(WebSocketConnection conn, String message) {
        PushRequest request = PushRequest.parse(message);
        switch (request) {
            case PushRequest.Listen listen -> {
                topicRegistry.listen(connId, listen.topics());
                // replay missed events from EventStore
                conn.sendTextAndAwait(PushMessage.ack(...));
            }
            case PushRequest.Unlisten unlisten -> { ... }
        }
    }
}
```

Broadcast events from CDI observers:

```java
@Inject EventBroadcaster broadcaster;

void onEvent(@ObservesAsync SomeEvent event) {
    broadcaster.broadcast("topic:name", Map.of("key", "value"));
}
```

### Frontend

```typescript
import { createEventConnection } from '@casehubio/pages-data';

const conn = createEventConnection(`ws://${location.host}/push`);
conn.listen(['topic:one', 'topic:two']).catch(() => {});
```

blocks-ui components consume via `PushMixin` from `pages-component` —
`list-pane`, `work-item-inbox`, and `kpi-metric-row` all support it.

### Wire protocol

- Client→Server: `{ op: "listen", id: "req-1", topics: [...], since: { "topic": lastSeq } }`
- Server→Client: `{ op: "event", topic: "...", payload: {...}, seq: N }`
- Cursor recovery: client sends `since` map; server replays missed events from `EventStore`

## Why this is non-obvious

SSE is the textbook choice for server→client push — simpler, works through
proxies, no upgrade negotiation. A developer building real-time updates would
naturally reach for `@RestStreamElement` / `Multi<SseEvent>` in Quarkus. The
endpoints compile and run, but `EventConnection` on the frontend never
connects to them — it speaks WebSocket exclusively.

### Alternatives considered

- **SSE per endpoint** — simpler, but no cursor recovery (client can't tell
  server what it missed during reconnection), no topic management (separate
  endpoint per event type), no bidirectional communication.
- **Polling** — simplest, but wastes bandwidth and adds latency.

The `ConnectionRegistry` + `SessionSender` + `@WebSocket` endpoint pattern is
identical boilerplate across CaseHub apps (helpdesk, FSI trading, AML) — a
candidate for extraction into `casehub-pages-push-runtime` as a shared bean.
