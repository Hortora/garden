# CbrCaseSummary from scan() omits confidence — must query CbrCaseEntity directly for outcome reporting

## Symptom

`CbrCaseMemoryStore.scan()` returns `List<CbrCaseSummary>` which has `caseId`, `entityId`, `caseType`, `producerAgentId`, `trustScore`, `storedAt` — but no `confidence`, `outcome`, `outcomeDetail`, or `lastOutcomeAt`. Building an outcome report (entries sorted by declining confidence) is impossible from `scan()` results alone.

## Root cause

`CbrCaseSummary` is a lightweight projection designed for listing and pagination. It was designed before outcome tracking was a consumer use case. The record deliberately omits large fields (`problem`, `solution`, `features`) for performance, but also omits the small outcome-related fields.

## Fix

Query `CbrCaseEntity` directly via `EntityManager` for outcome reporting:

```java
List<CbrCaseEntity> cases = em.createQuery(
        "SELECT e FROM CbrCaseEntity e WHERE e.caseType = :ct AND e.tenantId = :t AND e.lastOutcomeAt IS NOT NULL",
        CbrCaseEntity.class)
    .setParameter("ct", caseType)
    .setParameter("t", tenantId)
    .getResultList();
```

This bypasses the SPI — `CbrCaseEntity` is an implementation detail of `casehub-neocortex-memory-cbr-jpa`. A proper fix would either enrich `CbrCaseSummary` with optional outcome fields, or add a dedicated `scanWithOutcomes()` method to the SPI.

## Why this is non-obvious

The SPI appears complete — `store()`, `recordOutcome()`, `scan()`, `retrieveSimilar()` cover the full lifecycle. The gap only surfaces when you try to BUILD an outcome report from the SPI alone. The `trustScore` field in `CbrCaseSummary` looks like it might be `confidence` (both are `Double`), but they are semantically different: `trustScore` is producer trust, `confidence` is predictive quality.
