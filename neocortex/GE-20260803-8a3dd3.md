# CbrCaseMemoryStore.store() creates duplicates — no upsert, must check existence first

## Symptom

Calling `CbrCaseMemoryStore.store()` multiple times with the same `caseId` creates duplicate rows in the database. `recordOutcome()` then operates on the first row only, leaving orphan duplicates with stale data.

## Root cause

`JpaCbrCaseMemoryStore.store()` always creates a new `CbrCaseEntity` with `UUID.randomUUID()` as the primary key and calls `em.persist()`. There is no existence check or upsert logic. The `caseId` field is not a unique constraint — it's just a query key used by `recordOutcome()`.

## Fix

Check for an existing case before calling `store()`:

```java
boolean exists = !em.createQuery(
        "SELECT e.id FROM CbrCaseEntity e WHERE e.caseId = :cid AND e.tenantId = :t",
        String.class)
    .setParameter("cid", caseId)
    .setParameter("t", tenantId)
    .getResultList()
    .isEmpty();

if (!exists) {
    cbrStore.store(cbrCase, caseType, entityId, domain, tenantId, caseId, scope);
}
cbrStore.recordOutcome(caseId, tenantId, outcome);
```

This requires injecting `EntityManager` alongside `CbrCaseMemoryStore`, which breaks the SPI abstraction. A proper fix would add `storeIfAbsent()` or upsert semantics to the SPI.

## Why this is non-obvious

The SPI method name `store()` suggests idempotent storage. The `caseId` parameter looks like a natural key for upsert. Nothing in the interface contract or Javadoc indicates that duplicate caseIds are permitted.
