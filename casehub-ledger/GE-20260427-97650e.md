## Symptom

Adding a second `@ApplicationScoped` class implementing `LedgerEntryRepository` causes Quarkus boot failure:

```
Found 4 deployment problems:
[1] Ambiguous dependencies for type LedgerEntryRepository and qualifiers [@Default]
    injection target: LedgerRetentionJob#ledgerRepo
    available beans: AgentMessageLedgerEntryRepository, MessageLedgerEntryRepository
```

The library (`quarkus-ledger`) injects `LedgerEntryRepository` by interface type, and CDI sees two candidates.

## Root cause

CDI requires exactly one active bean per injection point. `@ApplicationScoped` on both implementations makes both active. The quarkus-ledger library's internal beans (`LedgerRetentionJob`, `LedgerVerificationService`, `TrustScoreJob`) inject `LedgerEntryRepository` by interface — they cannot be changed.

## Fix

Mark the **new** implementation `@Alternative` during the transitional period while both coexist. The old implementation remains the active primary; the new one is injected only when explicitly referenced by concrete type.

```java
@Alternative
@ApplicationScoped
public class MessageLedgerEntryRepository implements LedgerEntryRepository {
    // ...
}
```

Once the old implementation is deleted, remove `@Alternative` — the new one becomes the sole active bean automatically.

## Why this is non-obvious

Tests that inject the concrete type (`MessageLedgerEntryRepository`) still compile and pass — CDI resolves concrete-type injections without ambiguity. The failure only manifests in the library's interface-typed injection points, which you don't control. The error message names the library beans, not your new class, so the root cause is not immediately obvious.

### Alternative — when both implementations must remain active (intentional competition)

**Context:** Multiple competing CDI implementations coexist intentionally — a trust routing mechanism selects one at runtime. Marking any `@Alternative` would remove it from CDI selection and break the selection mechanism.

**Symptom:** `AmbiguousResolutionException` in all `@QuarkusTest` injection points that inject the seam interface (e.g. `@Inject @CaseType("starcraft-game") StrategyTask strategyTask`).

**Fix:** Inject the concrete type in tests instead of the seam interface:
```java
// Before (ambiguous — 3 competing StrategyTask implementations in L6):
@Inject @CaseType("starcraft-game") StrategyTask strategyTask;

// After (concrete type — no ambiguity):
@Inject @CaseType("starcraft-game") DroolsStrategyTask strategyTask;
```

The seam interface injection remains valid in `@Any Instance<StrategyTask>` (which CDI resolves by discovering all beans — ambiguity only applies to single-bean injection points). Tests that need all implementations use `@Any Instance<>`.

**When this applies:** The injection point is in a test, not in production code. Production code should inject `@Any Instance<StrategyTask>` (the registrar) or `StrategySelector` (to read which was selected). Concrete-type injection in production code would bypass the selection mechanism.

## Variant — Upstream library removes @Alternative from its own bean (SNAPSHOT regression)

**Context:** Consumer provides a non-`@Alternative` subclass of a library `@Alternative` bean — the established qhorus pattern for providing DEFAULT CDI beans (e.g. `QhorusLedgerEntryRepository` implements `LedgerEntryRepository`, `QhorusLedgerMerkleFrontierRepository` extends `JpaLedgerMerkleFrontierRepository`). This worked because the parent was `@Alternative` (inactive unless selected), so only the consumer's subclass was `@Default`.

**Symptom:** After a SNAPSHOT update of `casehub-ledger`, all `@QuarkusTest` modules fail with `AmbiguousResolutionException` on `LedgerEntryRepository` and `LedgerMerkleFrontierRepository` — 24-30 deployment problems. The error lists three competing beans: the library's JPA implementation, the consumer's subclass, and a `@DefaultBean` producer.

**Root cause:** The upstream SNAPSHOT removed `@Alternative` from `JpaLedgerEntryRepository` and `JpaLedgerMerkleFrontierRepository`. Both the library class and the consumer's subclass are now `@Default`. The `@DefaultBean` no-op producer (from `LedgerCoreProducer`) correctly yields to either, but the two non-`@DefaultBean` implementations compete.

**Fix:** Exclude the upstream JPA implementations via `quarkus.arc.exclude-types`:

```properties
quarkus.arc.exclude-types=io.casehub.ledger.runtime.repository.jpa.JpaLedgerEntryRepository,\
  io.casehub.ledger.runtime.repository.jpa.JpaLedgerMerkleFrontierRepository
```

This must be set in every module's test `application.properties` that defines its own `quarkus.arc.exclude-types` (Quarkus replaces, not merges, the property). For the runtime module's main `application.properties`, it propagates to dependent modules automatically.

**Why non-obvious:** The SNAPSHOT update has no changelog entry for removing `@Alternative`. The error manifests in the consumer project, not the library. If the consumer's main branch already has an unrelated compile error (as qhorus did), the CDI ambiguity is invisible until the compile error is fixed — the two failures mask each other.
