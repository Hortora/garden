## Context

When building cognitive state for AI agents (beliefs, trust, intentions, fears, judgments), the instinct is to create separate dedicated stores: `BeliefStore`, `TrustStore`, `IntentionStore`, each with its own data model, lifecycle, and query API. This fragments cross-concept queries ("why does agent A distrust agent B?" requires joining across trust, belief, and episodic stores) and scales linearly with new concept types.

## Technique

Use the Thing API's trait projection (`Thing.as(Interface.class)`) to provide typed per-concept views on a unified knowledge graph. Each cognitive concept is a node type registered via TypeRegistry; each concept-specific API is a trait interface projected onto the node via dynamic proxy.

```java
// Type check
node.is("belief")                     // → true

// Typed access via trait projection
node.as(Belieflike.class)             // → subject(), revised(), priorValue()
node.as(Intentional.class)            // → goal(), viable()
node.as(Evaluative.class)             // → target(), valence()

// Collection queries via CognitiveProfile
var beliefs = cognitiveProfile.query(agentId, "belief")
    .nodes().stream()
    .map(n -> n.as(Belieflike.class))
    .toList();
```

No separate store classes needed. The graph is the single source of truth. Trait interfaces give the same typed API surface as dedicated stores. Cross-concept queries come for free (graph traversals spanning beliefs + trust + episodic events).

## Why this is non-obvious

The default architectural choice — separate stores per concept — is well-established and feels natural. Each store is simple, testable, and has clear ownership. The non-obvious insight is that the Thing API's dynamic proxy projection provides the SAME per-concept typed API without separate classes, while preserving cross-concept queryability that separate stores make painful. The facade pattern is typically implemented as explicit wrapper classes; here, the data model (Thing + traits) IS the facade.

### Alternatives considered

- **Separate stores with cross-store query service** — preserves per-concept simplicity but requires an explicit correlation layer that duplicates graph traversal logic
- **Unified store with manual type checking** — eliminates separate classes but loses type safety; callers must cast and check types manually
- **Thing.as() with static type constants** — what was chosen; provides both type safety and unification

Validated via multi-agent debate (3 agents: unified advocate, separate advocate, mediator). Soar/ACT-R cognitive architecture research supports unified long-term storage with separate working buffers — the three-tier model provides exactly this.
