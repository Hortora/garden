### Context
When a module needs to scan for annotations from a provided-scope dependency (e.g., MicroProfile GraphQL annotations in a library that doesn't compile against them), importing the annotation classes creates a compile-time dependency that may be inappropriate.

### Technique
Match annotations by fully-qualified name string instead of importing the class:

```java
// Instead of:
// import org.eclipse.microprofile.graphql.Query;
// if (method.isAnnotationPresent(Query.class)) { ... }

// Use:
for (var ann : method.getAnnotations()) {
    if (ann.annotationType().getName()
            .equals("org.eclipse.microprofile.graphql.Query")) {
        // Read annotation values via reflection:
        String value = (String) ann.annotationType()
                .getMethod("value").invoke(ann);
    }
}
```

This works because annotation instances are always present at runtime if they have `@Retention(RUNTIME)`, regardless of whether the annotation class is on the compile classpath.

### Why this is non-obvious
Most Java developers reach for `isAnnotationPresent(Class)` or `getAnnotation(Class)` which require importing the annotation type. The string-based approach using `annotationType().getName()` is rarely shown in examples but is the standard technique for annotation processing in plugin/extension architectures where compile isolation matters.
