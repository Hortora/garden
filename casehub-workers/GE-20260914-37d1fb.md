## Symptom

`HttpEndpointResolver` injected via CDI in a different module (e.g. `casehub-soc`) has an empty `resolvedEndpoints` map. Calls to `resolve(capabilityTag, tenancyId)` always throw `WorkerProvisioningException: no route found` — even though `casehub.workers.http.endpoints.*` config properties are present and correctly formatted.

No error at injection time. No warning at startup. The bean is `@ApplicationScoped` and CDI resolves it without complaint.

## Context

Discovered when designing `HttpContainmentExecutor` for casehub-soc (#50). The initial design (D1) proposed injecting `HttpEndpointResolver` to reuse the workers HTTP config infrastructure. The post-spec review caught that the endpoint map would always be empty.

## What was tried (didn't work)

1. **Direct injection** — `@Inject HttpEndpointResolver resolver` in `HttpContainmentExecutor`. CDI resolves it, but `resolve()` throws at runtime because the map was never populated.
2. **Calling `initialize()` manually** — impossible from outside the package. The method has default (package-private) visibility: `void initialize()`.

## Root cause

`HttpEndpointResolver.initialize()` is **not** `@PostConstruct`. It is a package-private method called explicitly by `HttpWorkerRuntime.initialize()` during the worker runtime lifecycle boot sequence:

```java
// HttpWorkerRuntime.java
@Override
public Uni<Void> initialize() {
    return Uni.createFrom().item(() -> {
        resolver.initialize();  // <-- this is the only caller
        status = WorkerRuntimeStatus.RUNNING;
        return null;
    }).replaceWithVoid();
}
```

Without `HttpWorkerRuntime` in the CDI context (or without its lifecycle orchestrator calling `initialize()`), the resolver's `resolvedEndpoints` map stays empty. The three-tier resolution (SPI routes → config properties → EndpointRegistry) never executes.

## Fix

Don't inject `HttpEndpointResolver` from outside the `workers-http` module. Build your own config reader that reads the same config property format. The parsing logic is ~30 lines:

```java
@ApplicationScoped
public class ContainmentEndpointResolver {
    private static final String PREFIX = "casehub.soc.containment.endpoints.";

    @Inject Config config;

    private final Map<String, ContainmentEndpoint> endpoints = new HashMap<>();

    @PostConstruct
    void init() {
        for (String key : config.getPropertyNames()) {
            if (key.startsWith(PREFIX)) {
                // group by tag, extract url/method/timeout-seconds
            }
        }
    }
}
```

Use your own config namespace (e.g. `casehub.soc.containment.endpoints.*`) rather than the workers namespace. This avoids both the lifecycle coupling and any future config key conflicts.

## Why this is non-obvious

The bean is `@ApplicationScoped` and CDI-injectable — there is no compile-time signal that it requires external initialization. The `initialize()` method is package-private, so you can't even see it from outside the module without reading the source. The failure mode is silent: the map is empty, not null, so no NPE — just "no route found" at dispatch time, which looks like a config problem rather than a lifecycle problem.

### Alternatives considered

- **Making `initialize()` public** — would fix the immediate problem but exposes an initialization method that callers must remember to call. `@PostConstruct` would be better but may conflict with the worker runtime lifecycle ordering.
- **Depending on `workers-common` and running `HttpWorkerRuntime`** — pulls in the entire worker runtime infrastructure (fault pipeline, async completion registry) just to get config resolution. Disproportionate dependency for the need.
