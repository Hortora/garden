### Symptom
`Uni.createFrom().item(() -> blockingWork).await().atMost(Duration.ofMillis(50))` does not cancel the blocking supplier when the timeout fires. The call blocks for the full duration of the supplier, then throws `TimeoutException` only after the supplier returns.

### Context
Pattern execution handler (`PatternWorkerFunctionHandler`) used `driver.execute(model, input).await().atMost(budget)` to enforce a time budget. The driver's `execute()` wraps its loop in `Uni.createFrom().item(() -> { while(...) { ... } })`. Agent invocations inside the loop sleep or block for hundreds of milliseconds.

### What was tried (didn't work)
1. `Uni.createFrom().item(...).await().atMost(Duration.ofMillis(50))` — appears to set a timeout but the subscriber thread IS the thread running the supplier, so the timer cannot fire until the supplier yields.

### Root cause
`Uni.createFrom().item(Supplier)` evaluates the supplier **synchronously on the subscribing thread**. When `.await()` is called, it subscribes on the current thread, which blocks executing the supplier. The `atMost()` timer is scheduled but can never fire because the same thread is blocked inside the supplier.

This is fundamentally different from `Uni.createFrom().completionStage()` or `emitOn(executor)`, where the work runs on a different thread and the subscriber thread is free to handle the timeout.

### Fix
Run the blocking work on a virtual thread and use `Future.get(timeout)` for real cancellation:

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var future = executor.submit(() ->
        driver.execute(model, inputData).await().indefinitely());
    result = future.get(effectiveTimeoutMs, TimeUnit.MILLISECONDS);
} catch (TimeoutException e) {
    driver.cancel();
    return WorkerResult.expired("Time budget exceeded");
}
```

Do NOT use `CompletableFuture.supplyAsync()` (ForkJoinPool default) in Quarkus — the ForkJoinPool has the wrong classloader and throws `JtaContextProvider not a subtype`. Use `Executors.newVirtualThreadPerTaskExecutor()` instead.

### Why this is non-obvious
The API name `atMost()` strongly suggests "cancel after this duration." The Mutiny docs describe it as a timeout. Nothing in the API signals that it only works for async Uni chains — `item()` and `completionStage()` look interchangeable from the subscriber's perspective.

### Why this fix
`Future.get(timeout)` with a virtual thread executor is the only approach that provides real cancellation for synchronous blocking work. `emitOn(executor)` before `await()` would also work but changes the threading model for the entire Uni chain. The virtual thread approach is surgical — it moves only the blocking work off the subscriber thread.

### Alternatives considered
- `emitOn(executor)` before `await()` — works but changes threading for the entire chain, not just the timeout
- `CompletableFuture.supplyAsync()` — ForkJoinPool classloader issues in Quarkus (see Root cause)
- Checking elapsed time inside the driver loop — requires modifying the driver internals, breaks separation of concerns
