## Symptom

Adding `@Transactional` to a method that writes to two separate H2 in-memory datasources (e.g. `default` and `qhorus`) causes:

```
org.hibernate.exception.GenericJDBCException: Unable to acquire JDBC Connection
  [Exception in association of connection to existing transaction]
```

The error message suggests a connection pooling issue, but the root cause is JTA transaction enlistment.

## Context

A Quarkus application with dual datasources (common in CaseHub apps: `default` for domain tables, `qhorus` for ledger/channel tables). The method worked fine without `@Transactional` — each service call managed its own transaction independently. Adding `@Transactional` to wrap them atomically triggers the failure.

## What was tried (didn't work)

- Checking connection pool configuration — pools were fine
- Looking for nested transaction issues — no nesting
- Checking if the test had an existing transaction context — `@QuarkusTest` does NOT auto-wrap tests in transactions

## Root cause

Quarkus Agroal's default transaction mode for JDBC datasources is `enabled` (local transactions only). When `@Transactional` spans two datasources, Narayana JTA needs both datasources to support XA enlistment. H2 supports XA but Agroal doesn't use it by default — the JTA coordinator can't associate the second datasource with the transaction.

## Fix

Add `quarkus.datasource.jdbc.transactions=xa` to **both** datasources:

```properties
quarkus.datasource.jdbc.transactions=xa
quarkus.datasource.qhorus.jdbc.transactions=xa
```

This tells Agroal to use XA transaction enlistment, allowing Narayana to coordinate the two-phase commit across both H2 instances.

## Why this is non-obvious

The error message ("Exception in association of connection to existing transaction") points toward connection management, not transaction enlistment configuration. The Quarkus documentation for dual datasources doesn't mention that XA must be explicitly enabled for `@Transactional` methods spanning datasources — it works implicitly for PostgreSQL (which defaults to XA-capable) but not for H2.

### Why this fix

The alternative — removing `@Transactional` and relying on per-service transactions — breaks atomicity. If the ledger write succeeds but the position update fails, the database is inconsistent. XA enlistment is the correct solution because it enables the JTA coordinator to manage both datasources in a single global transaction with proper two-phase commit.

### Alternatives considered

- Removing `@Transactional` entirely — breaks atomicity guarantee across datasources
- Using a single datasource — architectural constraint requires separate datasources for domain and ledger tables
- Programmatic transaction management via `UserTransaction` — more complex, same XA requirement
