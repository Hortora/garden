## Symptom

When a `OneTimeTask` handler calls `scheduler.schedule()` to reschedule itself
(e.g. for manual cron rescheduling), the call fails with a duplicate primary key
violation or silently does nothing:

```
ERROR: duplicate key value violates unique constraint "scheduled_tasks_pkey"
Detail: Key (task_name, task_instance)=(...) already exists.
```

## Context

Common pattern when implementing cron-like recurring behaviour on top of
`OneTimeTask` — the handler executes, then schedules the next occurrence
with the same instance ID.

## Root cause

db-scheduler's execution lifecycle for OneTimeTask:

1. Scheduler picks the task row (`picked = true`)
2. Handler executes (your code runs here)
3. **After handler returns**, the completion handler deletes the row

Step 2 runs **while the row still exists** with `picked = true`. If the handler
calls `scheduler.schedule(task.instance(sameId, data), nextTime)`, it tries to
INSERT a row with the same `(task_name, task_instance)` primary key that's still
in the table.

## Fix

Use a unique instance ID for each rescheduled execution. Append a
discriminator (epoch millis, counter, or generation) to the base ID:

```java
private void rescheduleIfCron(TaskInstance<MyData> inst) {
    String cron = inst.getData().cronExpression();
    if (cron == null) return;

    Instant next = computeNextCronTime(cron);
    if (next != null) {
        String baseId = inst.getId().contains("#")
            ? inst.getId().substring(0, inst.getId().lastIndexOf('#'))
            : inst.getId();
        String newId = baseId + "#" + next.toEpochMilli();
        scheduler.schedule(task.instance(newId, inst.getData()), next);
    }
}
```

The old row is deleted by the completion handler after the method returns.
The new row has a different instance ID, so no conflict.

## Why this is non-obvious

The natural approach is to reuse the same instance ID — "I'm rescheduling
the same logical task." The execution lifecycle (handler runs before row
deletion) is not documented in the db-scheduler README. The `RecurringTask`
type handles this internally, but `OneTimeTask` with manual rescheduling
exposes the race.
