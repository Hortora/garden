### Symptom
`@QuarkusTest` startup fails with `Table "WORK_ITEMS" not found` on a Flyway
delta migration (`V42__escalation_fields.sql`) that ran fine before a migration
consolidation.

### Context
When Flyway migrations are consolidated — merging V1 through V44 into a single
V1 initial schema — any remaining delta migrations (V41, V42) that reference
the old table name will silently pass in production (where schemas were migrated
incrementally and the table exists under the old name) but fail on fresh schemas
(test mode with `clean-at-start=true`) where only the consolidated V1 ran.

### Root cause
The consolidation renamed `work_items` to `work_item` in V1 but V42 still
referenced `work_items`. Production databases had both names because the
original migration history created the table as `work_items`. Fresh H2 test
databases only had `work_item` from the consolidated V1.

### What was tried (didn't work)
- Adding a Flyway migration location override in the downstream app
- Creating a view alias (`CREATE VIEW work_items AS SELECT * FROM work_item`)
  — H2 views don't support `ALTER TABLE`
- Flyway `ignoreMigrationPatterns` — doesn't skip execution, only state tracking

### Fix
Fix the stale delta migration to use the correct table name. After any
consolidation, grep all remaining delta migrations for the old name:

```bash
grep -r "old_table_name" db/*/migration/V[0-9]*.sql
```

### Why this is non-obvious
The consolidation itself passes all tests (V1 creates the correct schema).
The stale deltas only fail when a downstream app pulls the JAR and runs
`clean-at-start=true` — which may be a different repo, different team,
weeks later.
