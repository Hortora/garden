## JUL loggers created before JBoss LogManager installation silently lose messages in Quarkus

**See also:** GE-20260603-83883c covers handler chain reset during test bootstrap (different mechanism). GE-20260607-876d7e covers Level.WARN vs Level.WARNING identity mismatch.

### Symptom

Two classes in the same package (`io.casehub.neocortex.mindmap.intelligence.consolidation`), both using `java.util.logging.Logger` with `private static final` fields, both logging at INFO level. `ExperienceConsolidationPhase`'s INFO log appears in test output. `DefaultGraduationScorer`'s INFO log does not appear. Same log level, same package, same Logger API.

The startup log shows:
```
ERROR: The LogManager accessed before the "java.util.logging.manager" system property
was set to "org.jboss.logmanager.LogManager". Results may be unexpected.
```

### Context

Quarkus bridges JUL to JBoss Logging by setting `java.util.logging.manager` to `org.jboss.logmanager.LogManager`. This must happen before any JUL Logger is created. JUL `Logger` instances are created when the class containing `Logger.getLogger(...)` is loaded — via static field initialization.

If a class is loaded before the system property is set (e.g., during CDI bean discovery or dependency resolution), its Logger gets the default JDK `ConsoleHandler` instead of the JBoss bridge. The JDK ConsoleHandler may have a different effective level or simply not route to Quarkus's log configuration.

### What was tried (didn't work)

1. Verified both classes use the same Logger API (`java.util.logging.Logger`)
2. Verified both are in the same package (same log category prefix)
3. Assumed Quarkus log level configuration applies uniformly — it does, but only to loggers created after the bridge is installed
4. Checked for exceptions swallowing the log — no exceptions found

### Root cause

Class loading order. `DefaultGraduationScorer` is loaded during CDI bean creation (it's `@DefaultBean @ApplicationScoped` — CDI validates it exists even if it's overridden). Its static `Logger.getLogger(...)` field initializes before `java.util.logging.manager` is set. The resulting Logger is bound to the default JDK LogManager, not JBoss LogManager.

`ExperienceConsolidationPhase` is loaded slightly later (after CDI setup completes), so its Logger gets the JBoss bridge correctly.

### Fix

Use JBoss Logging instead of JUL in Quarkus applications:

```java
// Instead of:
private static final java.util.logging.Logger LOG =
    java.util.logging.Logger.getLogger(MyClass.class.getName());

// Use:
private static final org.jboss.logging.Logger LOG =
    org.jboss.logging.Logger.getLogger(MyClass.class);
```

If JUL must be used (portability requirement), ensure the system property is set early — add to `maven-surefire-plugin` argLine:
```xml
<argLine>-Djava.util.logging.manager=org.jboss.logmanager.LogManager</argLine>
```

### Why this is non-obvious

Same package, same log level, same Logger API, same log configuration. The difference is entirely invisible — it depends on class loading order, which is non-deterministic and changes between test runs. The `ERROR: The LogManager accessed before...` message at startup is the only clue, but it's easy to dismiss as a benign warning.

During debugging, this was a red herring that consumed investigation time — the missing log suggested the scorer method was never called, when in fact it was the logger that was broken, not the code path.
