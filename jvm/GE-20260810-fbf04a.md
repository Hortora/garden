### Symptom
Category-level DRL rules intended to fire once per `ArchetypeCategory` fire N times when the `DataStore` contains N `PatternAssessment` items of the same category. Combined signal rules compound the problem — they also fire per-assessment. With 3 COMPOSITION assessments at confidence ≥0.6 and a DEFENSIVE_HOLD phase, army weight reaches 67% after normalisation — extreme distortion, not weight adjustment.

### Context
A `DominanceWeightRuleUnit` has a `DataStore<PatternAssessment>` populated from a scouting broker. Each `PatternAssessment` has an `archetype()` with a `category()` (RUSH, TIMING, HARASS, MACRO, TECH, COMPOSITION). The DRL rules match on category:
```drl
/patternStore[$arch: archetype(), confidence >= 0.6,
              archetype().category() == ArchetypeCategory.COMPOSITION]
```
The mental model is "this fires once for the COMPOSITION category." The reality is it fires once per DataStore item whose category is COMPOSITION.

### What was tried (didn't work)
Salience-based mutual exclusion — doesn't apply. Salience controls firing *order*, not whether rules fire (see GE-20260418-58cae8). DRL-level `accumulate` to pick highest-confidence per category — adds complexity to rules that should stay simple and stateless.

### Root cause
Drools DataStore pattern matching treats each item independently. A rule matching `/patternStore[condition]` creates one activation per matching item — there is no implicit grouping by any field. This is correct Drools behaviour, but the mental model of "one rule per category" is wrong.

### Fix
Deduplicate in Java before DataStore insertion. Keep only the highest-confidence assessment per `ArchetypeCategory`:
```java
static List<PatternAssessment> deduplicateByCategory(List<PatternAssessment> assessments) {
    if (assessments.size() <= 1) return assessments;
    return new ArrayList<>(assessments.stream()
        .collect(Collectors.toMap(
            a -> a.archetype().category(),
            a -> a,
            (a, b) -> a.confidence() >= b.confidence() ? a : b))
        .values());
}
```
Call this in `resolve()` before the DataStore insertion loop. DRL rules stay simple — they assume one assessment per category.

### Why this is non-obvious
The DRL syntax reads as a category-level filter: "when there's a COMPOSITION assessment." The per-item semantics are invisible unless you trace activations or hit pathological inputs. In single-assessment scenarios (common in testing), behaviour appears correct.

### Why this fix
Java-side dedup is preferable to DRL-level dedup because: (a) rules stay stateless and testable with single-assessment inputs, (b) the dedup policy (highest-confidence wins) is a business decision that belongs in the strategy layer, not in declarative rules, (c) `accumulate` in DRL with category grouping adds substantial complexity and interacts poorly with combined signal rules that also match the same store.

### Alternatives considered
- DRL `accumulate` with category grouping — rejected: adds complexity, interacts poorly with combined signal rules
- `no-loop` on rules — irrelevant: the problem is multiple activations from different DataStore items, not re-firing from the same item
- Salience-based exclusion — doesn't work: salience controls order, not mutual exclusion (GE-20260418-58cae8)
