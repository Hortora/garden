### Symptom

Compilation fails with "cannot find symbol" for a method that clearly exists when you inspect the JAR with `javap`. The JAR at the SNAPSHOT path in `~/.m2/repository/` shows the old field names, but the compiler sees different (renamed) field names.

### Context

Occurs when a dependency's SNAPSHOT JAR has been locally installed (`mvn install`) from a branch with renamed fields, but the timestamped JAR file at the same path retains the old bytecode. Maven's SNAPSHOT resolution can pick up a different physical JAR than the one at the obvious filesystem path.

### Root cause

Maven resolves SNAPSHOT artifacts through metadata, not by the filesystem path you'd naively inspect. A local `mvn install` writes a new JAR with the same SNAPSHOT version but potentially different content. `javap -cp path/to/artifact-0.2-SNAPSHOT.jar` may read a stale cached copy while Maven compilation uses the freshly installed one.

### Fix

Use `mvn dependency:copy-dependencies` to extract the exact JAR Maven resolves:

```bash
mvn dependency:copy-dependencies -pl <module> \
  -DincludeArtifactIds=<artifact-id> \
  -DoutputDirectory=/tmp/dep-check

javap -p -cp /tmp/dep-check/<artifact>.jar <fully.qualified.ClassName>
```

This shows the bytecode Maven actually compiles against.

### Why this is non-obvious

`javap` on the SNAPSHOT path in `~/.m2` seems authoritative — the path matches, the version matches. The mismatch is invisible unless you know Maven's internal resolution can diverge from the filesystem path.
