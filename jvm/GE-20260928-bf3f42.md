## Symptom

Design review recommends migrating a Java enum to an `EnumSet`-wrapping record for better
semantics (e.g. lossless `merge()` across arbitrary action combinations). The migration
compiles for all runtime code but breaks annotation-based declarations that use the enum
as an attribute type.

## Context

Java annotation attribute types are limited to: primitives, `String`, `Class<?>`, enums,
annotations, and arrays of these. Records, classes, and interfaces are not permitted as
annotation attribute types. This is a language-level constraint (JLS §9.6.1) that is
enforced at compile time.

When an enum is used as an annotation attribute:
```java
@interface Node {
    HumanGating humanGating() default HumanGating.NONE;
}
```

Replacing `HumanGating` with a record breaks every `@Node(humanGating = ...)` declaration
with a compile error. The annotation processor that reads these values also uses
`HumanGating.valueOf(annotationValue.asEnum())` which only works with enums.

## What was tried (didn't work)

Replacing `public enum HumanGating` with `public record HumanGating(Set<StepAction> gatedActions)`.
Runtime code compiled. Annotation declarations and annotation-processor code did not.

## Root cause

JLS §9.6.1 restricts annotation element types. Records are not in the permitted set.
This is not a compiler bug — it is a fundamental language design constraint.

## Fix

Keep the enum for now. Add the new values to the existing enum and improve the logic
within the enum's methods. If the enum must eventually become a record:

1. Introduce a separate enum for the annotation surface (e.g. `HumanGatingValue`)
2. Update the annotation processor to convert `HumanGatingValue` → `HumanGating` record at build time
3. The runtime uses the record; annotations use the enum

This two-type approach is the standard pattern for annotation-constrained types that need
richer runtime semantics.

## Why this is non-obvious

The constraint is invisible until you try the migration. Design reviews that recommend
"replace enum X with a record/class Y" don't naturally consider annotation surfaces
because annotations are processed at build time and rarely appear in the same analysis
scope as runtime type design. The compiler error message is clear, but the design
implication (need a two-type split) is not.
