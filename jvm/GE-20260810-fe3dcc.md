### Symptom
REST endpoints return HTTP 500 with `{"message": "Internal server error", "status": 500}` instead of the expected 404, 422, or 409 when service methods throw `jakarta.ws.rs.NotFoundException`, `WebApplicationException(msg, 422)`, or `ClientErrorException(msg, 409)`.

### Context
Any Quarkus project that depends on `casehub-ledger-rest` and Jandex-indexes it via `quarkus.index-dependency.ledger-rest.*` in `application.properties`. The `LedgerExceptionMapper` is a `@Provider` implementing `ExceptionMapper<RuntimeException>`.

### What was tried (didn't work)
- Checked for missing `@TestSecurity` / `FixedCurrentPrincipal` setup (red herring — correlated but not causal)
- Searched for custom `ExceptionMapper` or `@ServerExceptionMapper` in the consumer project (none found)
- Enabled RESTEasy trace logging (no server-side exception logged — the mapper silently converts)
- Checked OIDC errors (warning present but unrelated to the 500s)

### Root cause
`LedgerExceptionMapper.toResponse()` only recognizes `LedgerNotFoundException`, `IllegalArgumentException`, and `IllegalStateException`. Everything else — including all `WebApplicationException` subclasses — falls through to the default 500 response. JAX-RS spec resolution walks the class hierarchy and picks `ExceptionMapper<RuntimeException>` as the nearest superclass mapper, bypassing Quarkus's built-in `WebApplicationException` handling.

### Fix
Add a project-local `ExceptionMapper<WebApplicationException>` — the more specific generic type wins JAX-RS resolution:

```java
@Provider
public class WebApplicationExceptionMapper implements ExceptionMapper<WebApplicationException> {
    @Override
    public Response toResponse(WebApplicationException exception) {
        return exception.getResponse();
    }
}
```

### Why this is non-obvious
The symptom (HTTP 500) gives no indication that a third-party exception mapper is intercepting. The server logs show no exception trace — the mapper silently returns 500 for unrecognized types. The correlation with `FixedCurrentPrincipal` setup was misleading because tests that injected it happened to test success paths (no exceptions thrown).

### Why this fix
A project-local mapper is a clean workaround that doesn't require modifying the upstream library. The JAX-RS spec guarantees the most specific mapper wins, so `ExceptionMapper<WebApplicationException>` always beats `ExceptionMapper<RuntimeException>` for WebApplicationException and all its subclasses.

### Alternatives considered
- Fix upstream in casehub-ledger-rest (correct long-term fix, tracked as ledger#191, but blocked on release cycle)
- Exclude `LedgerExceptionMapper` via `quarkus.arc.exclude-types` (doesn't work — `@Provider` isn't a CDI bean, discovery is via Jandex)
