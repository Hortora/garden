## QdrantGrpcClient.checkVersionsCompatibility() poisons the gRPC channel on startup — all RPCs fail immediately until backoff fires

### Symptom

3 of 4 first gardenSearch MCP calls fail with connection errors. All succeed on retry. The engine is running, HTTP health check responds, but Qdrant queries fail with `StatusRuntimeException: UNAVAILABLE`.

### Context

The Hortora engine and Qdrant both run as launchd services with `RunAtLoad=true`. No startup ordering — the engine can start before Qdrant's gRPC port (6334) is listening.

### Root cause

`QdrantGrpcClient.newBuilder(host, port, useTls)` sets `checkCompatibility = true`. During `grpcBuilder.build()`, this triggers `checkVersionsCompatibility()` — a **blocking** gRPC health check.

When Qdrant isn't ready, the connection attempt fails. The `ManagedChannel` transitions to **TRANSIENT_FAILURE** state with exponential backoff (initial ~1s in gRPC-Java's Netty transport).

The exception is silently caught and logged as a warning. The `QdrantClient` object is still returned — it looks healthy.

**Critical behavior:** In gRPC-Java, when the channel is in `TRANSIENT_FAILURE` and `waitForReady` is NOT configured (the default), **all RPCs fail immediately** with `UNAVAILABLE`. They do not wait for reconnection. The channel only attempts to reconnect when its internal backoff timer fires.

`CollectionMigration.onStartup()` makes another gRPC call that also fails, potentially extending the backoff window.

### Fix

Add a startup readiness probe with retry before any collection checks:

```java
private boolean waitForQdrant(int maxRetries, long delayMs) {
    for (int attempt = 1; attempt <= maxRetries; attempt++) {
        try {
            qdrantClient.listCollectionsAsync().get();
            Log.infof("Qdrant ready (attempt %d/%d)", attempt, maxRetries);
            return true;
        } catch (ExecutionException e) {
            Log.warnf("Qdrant not ready (attempt %d/%d): %s",
                      attempt, maxRetries, e.getCause().getMessage());
            if (attempt < maxRetries && delayMs > 0) {
                try { Thread.sleep(delayMs); }
                catch (InterruptedException ie) { Thread.currentThread().interrupt(); return false; }
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            return false;
        }
    }
    Log.warn("Qdrant readiness check exhausted");
    return false;
}
```

Call at the start of `onStartup()`. The successful `listCollectionsAsync()` call forces the gRPC channel through the READY transition before any MCP calls arrive.

### Why this is non-obvious

The `QdrantClient` object is returned successfully despite the failed health check. The channel looks usable. The first few MCP calls arrive during the gRPC backoff window and get instant UNAVAILABLE rejections — but the error message says "Qdrant may be unavailable" which is misleading (Qdrant IS available by then, the gRPC channel just hasn't reconnected yet). The "retry fixes it" pattern makes it look like a timing issue rather than a poisoned channel state.

### Why this fix

`waitForReady` on the channel would also work but requires a cross-repo change to `casehub-neocortex-rag`'s `QdrantClientProducer`. The readiness probe is engine-side only and ensures the channel is in READY state before MCP calls arrive.

### Alternatives considered

- Configure `waitForReady` on the gRPC channel — correct but cross-repo change
- Add retry in `SearchResource.searchLocal()` — adds latency to every failed call, not just startup
- launchd dependency ordering — macOS launchd doesn't support `after=` style dependencies
