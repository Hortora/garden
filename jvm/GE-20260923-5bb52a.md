### Symptom
`NoUniqueBeanDefinitionException` — Spring finds both a JPA implementation and a NoOp fallback for the same SPI interface. Example: `expected single matching bean but found 2: springAccessControlProvider, noOpAccessControlProvider`.

### Context
A code generator translates Quarkus `@DefaultBean` methods to Spring `@Bean` with `@ConditionalOnMissingBean`. The Quarkus method returns the concrete type directly (e.g., `NoOpAccessControlProvider`), not the interface. The generated Spring `@ConditionalOnMissingBean` has no explicit type argument.

### What was tried (didn't work)
1. Bare `@ConditionalOnMissingBean` on the generated NoOp bean — doesn't suppress when a real implementation exists
2. Ordering auto-configs with `@AutoConfigureOrder` — both beans still register because they check different types

### Root cause
`@ConditionalOnMissingBean` without an explicit `value` attribute defaults to the annotated method's return type. For `NoOpAccessControlProvider noOpAccessControlProvider()`, it checks for `NoOpAccessControlProvider`, not `AccessControlProvider`. The JPA module's `springAccessControlProvider` provides `AccessControlProvider` (the interface), not `NoOpAccessControlProvider` (the concrete type). Both conditions pass — both beans register.

This is a semantic gap between Quarkus `@DefaultBean` (which checks all assignable types) and Spring `@ConditionalOnMissingBean` (which checks only the specified type, defaulting to the method return type).

### Fix
When generating `@ConditionalOnMissingBean` for `@DefaultBean` translations, resolve the SPI interface from the return type's class hierarchy and specify it explicitly:

```java
// In the generator: resolve first non-java interface
if (isDefaultBean && concreteReturnType == null && effectiveType != null) {
    for (DotName iface : effectiveType.interfaceNames()) {
        String ifaceName = iface.toString();
        if (!ifaceName.startsWith("java.") && !ifaceName.startsWith("jakarta.")) {
            spiInterface = ifaceName;
            break;
        }
    }
}

// In the writer: use SPI interface for @ConditionalOnMissingBean
if (d.spiInterface() != null) {
    builder.addAnnotation(AnnotationSpec.builder(CONDITIONAL_ON_MISSING_BEAN)
            .addMember("value", "$T.class", toClassName(d.spiInterface()))
            .build());
}
```

Generated output: `@ConditionalOnMissingBean(AccessControlProvider.class)` — now correctly suppressed when a JPA implementation exists.

### Why this is non-obvious
The Quarkus `@DefaultBean` and Spring `@ConditionalOnMissingBean` look equivalent but have different type-matching semantics. The mismatch only surfaces when both a real implementation and a fallback are on the classpath — which may not happen until integration testing with the full starter.
