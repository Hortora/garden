### Symptom

`completionManager.removeCompletion(info -> info.name().equals(templateName))` throws `NullPointerException` because `info.name()` returns null for some `CompletionInfo` entries.

### Context

When cleaning up completions during resource deregistration, the natural approach is to filter by the template name: `removeCompletion(info -> info.name().equals(name))`. This iterates ALL registered completions. Some entries have null names (likely internal/framework completions), causing NPE on the `equals()` call.

### Root cause

`CompletionInfo.name()` can return null for certain completion entries in the manager's internal collection. The `Predicate<CompletionInfo>` passed to `removeCompletion()` is applied to every entry including these.

### Fix

Reverse the equals call so the non-null side is the receiver:

```java
// Before — NPE when info.name() is null
completionManager.removeCompletion(info -> info.name().equals(templateName));

// After — null-safe, templateName is guaranteed non-null
completionManager.removeCompletion(info -> templateName.equals(info.name()));
```

### Why this is non-obvious

`CompletionInfo.name()` is declared as `String name()` with no `@Nullable` annotation. The natural expectation is that a feature's name is always non-null. The null values only appear when iterating the full collection, not when accessing a specific completion by name.
