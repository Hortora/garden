### Symptom

`ChannelBackend.post()` implementation that calls `TopicReader.find()`, `MembershipReader.findByChannel()`, or any JPA store method fails with:

```
ContextNotActiveException: Cannot use the EntityManager/Session because
neither a transaction nor a CDI request context is active.
```

The gateway logs the error and continues — the message is silently dropped for the failing backend. No exception propagates to the caller of `MessageService.dispatch()`.

### Context

`ChannelGateway.fanOut()` spawns a virtual thread per registered backend via `Thread.ofVirtual().start()`. The `post()` callback executes on this virtual thread, OUTSIDE the dispatch transaction and without a CDI request scope. This is documented in the `HumanParticipatingChannelBackend` Javadoc ("post() must catch all exceptions internally") but the JPA/scope implication is not.

### What was tried (didn't work)

1. Calling `TopicReader.find(channelId, topicName)` inside `post()` to resolve topic IDs for the WebSocket protocol — fails because `JpaTopicStore` uses the `@PersistenceUnit("qhorus")` EntityManager which requires an active transaction or request context.

2. Injecting `@RequestScoped` beans (like `SecurityIdentity` via `CurrentPrincipal`) from `post()` — fails with the same `ContextNotActiveException`.

### Root cause

`ChannelGateway.fanOut()` uses `Thread.ofVirtual().start()` for each backend. Virtual threads do not inherit the caller's CDI request scope or JTA transaction. The `post()` method runs in an isolated context with no database access and no request-scoped bean resolution.

### Fix

Use only the data passed in the `OutboundMessage` parameter. Do not query the database from `post()`. `OutboundMessage` carries `topic()` (name), `sender()`, `content()`, `correlationId()`, `artefactRefs()`, `target()`, `type()`, `senderActorType()`, `inReplyTo()`, and `sequenceId()` — everything needed for WebSocket broadcasting without additional queries.

```java
@Override
public void post(ChannelRef channel, OutboundMessage message) {
    // Use message.topic() directly — don't call topicReader.find()
    broadcaster.pushMessage(channel, message);
}
```

For commitment state changes, use `CommitmentStateChangedEvent` observation with `@Observes(during = TransactionPhase.AFTER_SUCCESS)` instead of querying commitments inside `post()`.

### Why this is non-obvious

The `post()` method signature accepts a `ChannelRef` which contains the channel UUID — it's natural to assume you can look up related data. The virtual thread isolation is invisible at the API level. The gateway silently catches and logs the exception, so the failure only manifests as missing WebSocket messages — not a startup error or a compile error.
