## @ConfigMapping validates all required properties at startup even when feature group is disabled

### Symptom

Quarkus fails to start with missing config errors for properties like
`casehub.cbr.retention.domain` — even though `casehub.cbr.retention.enabled`
defaults to `false`. Every app that transitively pulls in the module must add
config lines for a feature it doesn't use.

### Context

A common pattern for optional features: a `@ConfigMapping` interface with
`enabled()` defaulting to `false` and siblings like `domain()` and
`caseTypes()` that are only meaningful when enabled. The expectation is that
SmallRye Config skips validation of siblings when the feature is off.

```java
@ConfigMapping(prefix = "casehub.cbr.retention")
public interface CbrRetentionConfig {
    @WithDefault("false")
    boolean enabled();

    String domain();           // no @WithDefault — required
    List<String> caseTypes();  // no @WithDefault — required
}
```

### Root cause

SmallRye Config validates **all** required `@ConfigMapping` properties at
startup — there is no concept of conditional validation based on a sibling
property's value. The `enabled()` default has no effect on whether `domain()`
and `caseTypes()` are validated.

### Fix

Add `@WithDefault("")` to properties that should be optional when the feature
is disabled. Validate at runtime in the scheduler/service, only when
`enabled=true`:

```java
@WithDefault("")
String domain();

@WithDefault("")
List<String> caseTypes();
```

```java
void purgeExpired() {
    if (!config.enabled()) return;
    if (config.domain().isBlank()) {
        throw new IllegalStateException(
            "casehub.cbr.retention.domain must be set when enabled=true");
    }
    // ...
}
```

### Why this is non-obvious

The `enabled()` pattern creates a strong mental model that the entire config
group is gated. Developers expect SmallRye to skip validation of sibling
properties when the feature flag is off — similar to how Spring's
`@ConditionalOnProperty` works. The actual behaviour (validate everything
regardless) is never explicitly documented.

### Alternatives considered

- `Optional<String>` for domain — works but changes the API contract at every
  call site. `@WithDefault("")` + runtime validation is simpler.
- `@ConfigMapping` sub-groups with `@IfBuildProperty` — overkill for runtime
  feature flags; build-time gating is a different concern.
