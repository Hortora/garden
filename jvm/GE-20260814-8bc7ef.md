### Symptom
`@QuarkusTest` tests fail with `RuntimeException: Failed to start quarkus`. The stack trace shows `ConfigValidationException` listing required config properties like `casehub.memory.retention.domain`, `casehub.cbr.trust-retention.case-types` that "could not be found in any config source."

### Context
Running `mvn --batch-mode -o test` (offline flag) when upstream dependencies define `@ConfigMapping` beans with required properties. The offline flag prevents Maven from resolving metadata from GitHub Packages, but the real issue is that Quarkus config validation runs eagerly at startup and fails when upstream-provided defaults aren't resolvable.

Non-`@QuarkusTest` unit tests (plain JUnit 5) are completely unaffected — they don't start the CDI container.

### What was tried (didn't work)
- Running individual `@QuarkusTest` test classes — same failure (container-wide)
- Assuming the error was a startup bug in the application code

### Root cause
Quarkus `SmallRyeConfig` validates all `@ConfigMapping` interfaces at startup, including those contributed by transitive dependencies. When running offline, some dependencies' config defaults may not be on the classpath, causing validation to fail before any test code runs. The error message ("Failed to start quarkus") obscures the actual cause (missing config properties from upstream modules).

### Fix
Run targeted non-`@QuarkusTest` unit tests to validate logic changes:
```bash
mvn --batch-mode -o test -pl app -Dtest="TestClassA,TestClassB"
```
For full `@QuarkusTest` integration testing, refresh the GitHub Packages token and run without `-o`.

### Why this is non-obvious
The symptom "Failed to start quarkus" suggests an application startup bug, not a config validation issue. Developers naturally investigate their own startup code, CDI wiring, or Flyway migrations — not upstream config properties from transitive dependencies. The offline flag compounds the misdirection because it's a build-level concern causing a runtime-level error.
