## @TestHTTPResource gives http:// URI for WebSocket endpoints

### Symptom
`HttpClient.newHttpClient().newWebSocketBuilder().buildAsync(uri, listener)` fails with `IllegalArgumentException: invalid URI scheme: http` when `uri` comes from `@TestHTTPResource("/push")`.

### Context
Writing a `@QuarkusTest` for a `@WebSocket(path = "/push")` endpoint. `@TestHTTPResource` is the standard Quarkus way to inject the test server's base URL for a given path. The test uses Java's built-in `HttpClient` WebSocket client to connect.

### What was tried (didn't work)
Using `@TestHTTPResource("/push")` directly as the WebSocket URI — the injected `URI` has scheme `http://`, not `ws://`.

### Root cause
`@TestHTTPResource` always injects an `http://` (or `https://`) URI regardless of the endpoint type. It resolves the test server's HTTP base URL and appends the path. It has no awareness of whether the path is a WebSocket endpoint. Java's `HttpClient` WebSocket builder requires `ws://` or `wss://` scheme — it does not auto-upgrade from `http://`.

### Fix
String-replace the scheme before building the WebSocket connection:

```java
@TestHTTPResource("/push")
URI pushUri;

@Test
void connects() throws Exception {
    var wsUri = URI.create(pushUri.toString().replace("http://", "ws://"));
    var ws = HttpClient.newHttpClient().newWebSocketBuilder()
            .buildAsync(wsUri, listener).join();
    // ...
}
```

For HTTPS test profiles, also handle `https://` → `wss://`.

### Why this is non-obvious
`@TestHTTPResource` is presented as the canonical way to get test endpoint URIs in Quarkus. When testing a WebSocket endpoint, the natural expectation is that it returns a `ws://` URI for a `@WebSocket` path. The error "invalid URI scheme: http" points at the URI but doesn't suggest the fix — the developer may look at the WebSocket client configuration, Quarkus config, or test profile rather than the URI scheme.
