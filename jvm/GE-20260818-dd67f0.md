## Context

ThreadLocal markers that gate behaviour — e.g. a `FederationSyncContext` that activates a pass-through mode for a store decorator. The manual `activate()` / `deactivate()` pattern risks ThreadLocal leaks if code between them throws an exception.

```java
// BAD — leaks on exception
FederationSyncContext.activate();
try {
    store.put(shadow);
} finally {
    FederationSyncContext.deactivate();  // easy to forget the finally
}
```

## Fix

Implement `AutoCloseable` on the context class. Return the context instance from `activate()`. Use try-with-resources.

```java
public final class FederationSyncContext implements AutoCloseable {
    private static final ThreadLocal<Boolean> ACTIVE = ThreadLocal.withInitial(() -> false);

    private FederationSyncContext() {}

    public static FederationSyncContext activate() {
        ACTIVE.set(true);
        return new FederationSyncContext();
    }

    @Override
    public void close() {
        ACTIVE.remove();
    }

    public static boolean isActive() {
        return ACTIVE.get();
    }
}

// Usage — leak-proof
try (var ctx = FederationSyncContext.activate()) {
    store.put(shadow);
}
// ThreadLocal cleaned up even if store.put() throws
```

## Why this is non-obvious

ThreadLocal patterns in most codebases use manual activate/deactivate or set/remove. `AutoCloseable` is mentally associated with I/O resources (streams, connections, locks), not with ThreadLocal state markers. The pattern is simple once seen but rarely used in practice — most ThreadLocal context management code in the wild uses the manual pattern.
