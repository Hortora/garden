### Symptom
A CDI audit flags beans as having "unnecessary CDI" because they have zero
`@Inject` fields. Removing `@ApplicationScoped` causes no compile error
but beans silently disappear from `Instance<T>` iteration at runtime.

### Context
Automated CDI audits that use injection count as a proxy for CDI necessity.
Beans with zero `@Inject` fields are flagged for annotation removal.

### What was tried (didn't work)
Trusting an audit that counted `@Inject` fields per class and flagged
classes with zero injections as not needing CDI. Seven classes were flagged:
five `Ganglion` SPI implementations, one `ActionRiskClassifier` with a
`@RiskClassifier` qualifier, and one `YamlCaseHub` subclass.

### Root cause
Three mechanisms make zero-injection beans legitimate CDI beans:

1. **Programmatic discovery via `Instance<T>`** — beans iterated via
   `Instance<Ganglion>` must be `@ApplicationScoped` to appear. The
   injection happens at the *consumer*, not the bean itself.
2. **Qualifier-based lookup** — beans carrying qualifier annotations
   (e.g. `@RiskClassifier`) are resolved by the qualifier, not by
   injection into the bean.
3. **Stale audit data** — the audited class may have gained `@Inject`
   fields since the audit was run.

### Fix
Before removing CDI annotations from a zero-injection bean, check:

1. Is it consumed via `Instance<T>` anywhere? (`grep "Instance<SuperType>"`)
2. Does it carry a CDI qualifier annotation?
3. Is the audit data current? (Re-read the actual source.)

If any answer is yes, the bean needs its scope annotation.

### Why this is non-obvious
Injection count is an intuitive proxy for CDI dependency — if a bean
injects nothing, it appears self-contained. But CDI beans serve two
roles: *consumer* (injecting dependencies) and *discoverable*
(being found by consumers). The second role is invisible when you
only look at the bean's own fields.

### Why this fix
Checking the three mechanisms (Instance<T>, qualifiers, stale data)
catches all known false positives. A blanket "zero injections =
unnecessary CDI" rule will silently break runtime discovery.

### Alternatives considered
- Adding a comment like `// Needed for CDI discovery` on each bean — rejected because it requires maintenance and doesn't prevent future audits from re-flagging
- Using `@Named` instead of `@ApplicationScoped` — wrong scope semantics; `@Named` is for EL resolution, not programmatic discovery
