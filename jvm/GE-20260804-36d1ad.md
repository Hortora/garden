### Symptom
Initial assumption: bridge modules between casehub-work and casehub-qhorus need `casehub-qhorus` (runtime) as a compile dependency to access `MessageService.dispatch()` and `ChannelService.findByName()`.

### Context
Building `casehub-work-qhorus` — a bridge module that posts messages to Qhorus channels and reads channel metadata. The spec assumed a runtime dependency based on the class names used in the design (`MessageService`, `ChannelService`).

### Root cause
The Qhorus api module (`casehub-qhorus-api`) already provides the necessary SPI interfaces:
- `MessageDispatcher.dispatch(MessageDispatch)` → `DispatchResult` — full dispatch capability
- `ChannelReader.findByName(String)` → `Optional<Channel>` — channel lookup
- `ConsumerMessaging extends MessageDispatcher` — `MessageService` implements this at runtime

The runtime classes (`MessageService`, `ChannelService`) implement these api interfaces. CDI injection of the interface type resolves to the runtime bean at deploy time.

### Fix
Depend on `casehub-qhorus-api` at compile scope instead of `casehub-qhorus`:

```xml
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-qhorus-api</artifactId>
</dependency>
```

Inject the interface types:
```java
@Inject MessageDispatcher messageDispatcher;
@Inject ChannelReader channelReader;
```

### Why this is non-obvious
The Qhorus DESIGN.md documents services by their runtime class names (`MessageService`, `ChannelService`), not by their SPI interface names. The api module's `ConsumerMessaging extends MessageDispatcher` chain is only visible by reading the source. A developer following the DESIGN.md would naturally reach for the runtime dependency.
