## Symptom

Generated code implementing `Flow.Subscriber<T>` parameterizes `onSubscribe` as
`public void onSubscribe(Flow.Subscription<? super T> subscription)` — this fails
to compile with "type Flow.Subscription does not take parameters".

## Context

When generating code that implements `java.util.concurrent.Flow.Subscriber<T>`,
the natural assumption is that all four Flow interfaces follow the same generic
pattern. Three of four do:

- `Flow.Publisher<T>` — generic
- `Flow.Subscriber<T>` — generic
- `Flow.Processor<T, R>` — generic
- `Flow.Subscription` — **NOT generic**

The `onSubscribe` method signature is `void onSubscribe(Flow.Subscription subscription)`
— no type parameter.

## Root cause

The JDK Flow API has an asymmetric generic design. `Flow.Subscription` is a plain
interface with just `request(long)` and `cancel()` — there's no type-specific
information it needs to carry, so the JDK designers didn't parameterize it. But
the visual pattern of the other three interfaces strongly suggests it should be.

## Fix

When generating `Flow.Subscriber<T>` implementations, use the raw type for
`onSubscribe`:

```java
// WRONG — won't compile
public void onSubscribe(Flow.Subscription<? super String> subscription) { ... }

// CORRECT
public void onSubscribe(Flow.Subscription subscription) { ... }
```

## Why this is non-obvious

The pattern of the other three interfaces (all generic) creates a strong expectation
that `Flow.Subscription` is also generic. Hand-written code rarely hits this because
IDE autocompletion fills in the correct signature. Code generators that construct
method signatures from type patterns will reproduce the wrong assumption.

### Alternatives considered

- Parameterizing all Flow types uniformly and casting — rejected, won't compile
- Using Reactive Streams `org.reactivestreams.Subscription` instead — also not generic, same design
