### Symptom
Integration tests that previously passed now timeout on `awaitAndApproveGate()` — the gate WorkItem is never created. The error looks like a gate creation bug or engine regression.

### Context
The investigation triage worker (#112) replaced a stub that always returned `SAR_WARRANTED` with real rule-based logic evaluating entity type, risk score, and pattern findings. Low-risk cases (STRUCTURING, LAYERING, VELOCITY_ANOMALY with stub entity-resolution returning CORPORATE/0.35) now correctly return `FALSE_POSITIVE` — no SAR is drafted, no gate is created.

### Root cause
Tests were written when the stub always returned `SAR_WARRANTED`, so every investigation went through the full SAR path: sar-drafting → PlannedAction(SAR_FILING) → gate WorkItem. After triage, only HIGH_RISK_JURISDICTION (triggers SHELL_COMPANY hard gate → SAR_WARRANTED) follows the SAR path. The test expectations didn't change when the flow did.

### Fix
- Low-risk tests: remove `awaitAndApproveGate()`, drain directly (case completes via `investigation-cleared` goal)
- Tests requiring the SAR path: use `FlagReason.HIGH_RISK_JURISDICTION` which deterministically triggers SAR_WARRANTED via the SHELL_COMPANY hard gate

### Why this is non-obvious
The timeout symptom looks like a gate creation bug or engine regression — not a triage logic change. The connection between FlagReason, entity-resolution stub output, triage scoring, and gate creation spans four layers. The fix requires understanding the full triage flow to know which FlagReason values produce which outcomes.
