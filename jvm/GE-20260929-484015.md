### Symptom
StrippedReplayFeatureExtractor produces ~35-60% fewer UnitBorn events than oracle
replays for workers (SCV, Probe, Drone) and combat units (Marine, Zergling, Roach).
The under-count pattern suggests missing abilLink mappings, but all known training
abilLinks have 88-100% match rates when CmdEvents are present.

### Context
When an SC2 player selects multiple production buildings or Larva and presses a
train hotkey once, the game engine dispatches the command to each selected unit
sequentially. The game events stream records this as:

1. One `CmdEvent` (id=27) with the abilLink and abilCmdIndex — for the first selected unit
2. N-1 `Event(id=103)` continuation events — one per additional selected unit
3. `SelectionDeltaEvent` (remove=Mask, add=1) between each continuation — removing the consumed unit

Scelight's `GameEventFactory.create()` switch statement has no case for id=103.
It falls through to `super.create()`, producing a generic `Event` instance. Any
code that iterates only `CmdEvent` instances misses the continuations entirely.

### What was tried (didn't work)
- Checked for missing abilLink mappings — all known training abilLinks had 88-100% match rates
- Verified game events are identical between oracle and stripped replays — confirmed identical
- Checked for null-abilLink CmdEvents as hidden train commands — they're move/rally commands
- Cross-referenced oracle UnitBorn against CmdEvents via nearest-neighbor timing — too noisy with 11 replays

### Root cause
Event(id=103) (`CommandManagerState`) is the SC2 engine's auto-repeat mechanism for
multi-selection commands. Scelight doesn't parse it into a typed class, so it's invisible
to any `instanceof CmdEvent` check. A player selecting 5 Larva and pressing 'Z' generates
1 CmdEvent + 4 Event(id=103) = 5 train commands, but only the first is processed.

### Fix
In the game event processing loop, track the last trained unit type and loop. When
Event(id=103) arrives from the same player within a 30-game-loop window of the last
train command, generate an additional TrainIntent for the same unit type:

```java
} else if (raw.getId() == 103
           && raw.getUserId() == userId
           && lastTrainUnit != null
           && raw.getLoop() - lastTrainLoop <= 30) {
    var repeatTrain = new TrainIntent(null, lastTrainUnit);
    tagCounter = handleTrain(repeatTrain, raw.getLoop(), playerId,
                             state, syntheticEvents, tagCounter);
    lastTrainLoop = raw.getLoop();
}
```

Exclude warp-in commands — they already chain via Event(id=104) CmdUpdateTargetPoint.

### Why this is non-obvious
The symptom (60% under-count across all unit types) looks exactly like missing abilLink
mappings. Diagnostic analysis confirms the existing mappings work correctly (88-100%
match rate). The actual cause — an unlisted event type in the parser's factory — is
invisible unless you trace the raw game event stream and correlate with oracle data.

### Why this fix
A time-windowed approach (30 game loops) filters out non-training Event(id=103)
occurrences that fire for other command manager state changes. The alternative —
inspecting the Event struct for abilLink data — isn't feasible because scelight
doesn't expose typed fields on generic Events.

### Alternatives considered
- Modifying scelight's GameEventFactory to parse Event(id=103) as a CmdEvent — more
  correct but requires forking/modifying the parser library
- Using selection size at CmdEvent time to predict repeat count — fragile because
  selection state tracking has its own edge cases
