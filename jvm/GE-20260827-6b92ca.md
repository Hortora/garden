### Symptom
WebSocket binary messages cause `BinaryDecodeException: No binary codec handles the type class java.nio.ByteBuffer`. The WebSocket connection closes immediately after any binary frame is received.

### Context
Using `quarkus-websockets-next` (not the legacy `quarkus-websocket`). The `@OnBinaryMessage` handler parameter is declared as `java.nio.ByteBuffer`.

### What was tried (didn't work)
- Assumed `ByteBuffer` is a standard binary type that would be handled natively
- The connection appeared to work for text messages — only binary frames triggered the error
- Error is logged server-side but the client sees the connection simply close with no explanation

### Root cause
`quarkus-websockets-next` has built-in codecs for `byte[]`, Vert.x `Buffer`, and `String` — but NOT for `java.nio.ByteBuffer`. There is no automatic conversion. The legacy `quarkus-websocket` module supported `ByteBuffer` natively, which makes this a migration trap.

### Fix
Change the parameter type from `ByteBuffer` to `byte[]`:

```java
@OnBinaryMessage
public void onBinary(byte[] data) {
    var floatBuf = java.nio.ByteBuffer.wrap(data)
        .order(ByteOrder.LITTLE_ENDIAN).asFloatBuffer();
    // process...
}
```

### Why this is non-obvious
`ByteBuffer` is the standard Java NIO binary type. Every other WebSocket framework (Jetty, Tyrus, legacy Quarkus) accepts it. The error message names the type but doesn't suggest the fix. The connection drops silently on the client side.
