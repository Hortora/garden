## SQLite unclosed Statement from PRAGMA holds lock — SQLITE_BUSY on subsequent statements

**Symptom:** `SQLITE_BUSY: cannot commit transaction - SQL statements in progress` on the statement AFTER a PRAGMA, not on the PRAGMA itself. The PRAGMA appears to succeed.

**Context:** Any Java code executing SQLite PRAGMAs via `conn.createStatement().execute("PRAGMA ...")` without closing the `Statement`. Commonly occurs during database initialization when setting `journal_mode`, `foreign_keys`, or `busy_timeout`.

### What was tried (didn't work)
- Wrapped the PRAGMA in try-catch assuming it failed — but the exception occurs on the next statement, not the PRAGMA
- Assumed `SQLITE_BUSY` meant a concurrent connection conflict — but there was only one connection

### Root cause
`conn.createStatement().execute("PRAGMA journal_mode=WAL")` creates a `Statement` object that is never closed. SQLite PRAGMAs that return results (like `journal_mode` which returns the new mode) leave the `Statement` in an active state. The unclosed `Statement` holds an internal lock. When the next `createStatement().execute()` runs on the same connection, SQLite cannot auto-commit the previous statement and throws `SQLITE_BUSY`.

### Fix
Wrap every `createStatement()` in try-with-resources — even for PRAGMAs:

```java
try (var s = conn.createStatement()) {
    s.execute("PRAGMA journal_mode=WAL");
}
try (var s = conn.createStatement()) {
    s.execute("PRAGMA foreign_keys=ON");
}
```

### Why this is non-obvious
PRAGMAs look like simple fire-and-forget commands — not queries that return result sets. The mental model of `execute("PRAGMA ...")` is "set a config value," not "execute a query that holds resources." The error occurs on the NEXT statement, not the PRAGMA itself, so the debugging path leads to inspecting the wrong line. The `SQLITE_BUSY` message ("SQL statements in progress") points at concurrency, not resource management — misleading when there's only one connection.
