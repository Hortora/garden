### Symptom
`banCircularDependencies` from MojoHaus extra-enforcer-rules is configured and passes, but two repos still can't be built from a clean local Maven repository — each requires the other's artifacts installed first.

### Context
Multi-repo Maven ecosystem where repos share `groupId` (e.g. `io.casehub`). Repo A has module A1 depending on artifact from Repo B, and Repo B has module B1 depending on artifact from Repo A. Both use `provided` scope. The enforcer rule passes on every module in both repos.

### What was tried (didn't work)
- `banCircularDependencies` with `searchTransitive=true` (default) — passes because it checks if the building module's own `groupId:artifactId` appears in its dependency tree. A1 ≠ A2, so no self-cycle detected.
- `bannedDependencies` with artifact prefix denylist — works but requires enumerating every forbidden repo, doesn't scale across N repos.
- `bannedDependencies` with allowlist (ban all `io.casehub:*`, exempt own prefix + declared upstreams) — works but leaf repos have large allowlists.

### Root cause
`banCircularDependencies` checks for exact `groupId:artifactId` self-reference in the transitive tree. It does NOT detect cross-module cycles where A1→B→A2 (A1 and A2 are different artifacts in the same repo). Additionally, `provided` scope dependencies are not resolved transitively, so the chain breaks even if the same artifact appeared.

This is tracked as mojohaus/extra-enforcer-rules#84 — "New rule to prevent circular dependencies in a maven project (not just a module)".

### Fix
Write a standalone Python script that:
1. Reads repo names from a CSV (or scans a directory)
2. Parses `pom.xml` `<dependencies>` sections (NOT `<dependencyManagement>`) across all repos
3. Maps each `io.casehub` artifactId to its owning repo by scanning module pom.xml files
4. Builds a directed repo→repo graph
5. Runs DFS cycle detection
6. Reports cycles with artifact-level evidence

Run as a CI check or pre-merge gate. ~150 lines of Python, stdlib only, runs in seconds.

### Why this is non-obvious
The plugin name `banCircularDependencies` strongly implies it catches all circular dependency scenarios. The gap between "artifact-level self-cycle" and "repo-level build-ordering cycle" is not documented on the plugin page — you only discover it when the rule passes but the build still can't bootstrap.
