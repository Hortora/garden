### Symptom

`catch (PersistenceException e)` after `em.flush()` never fires when a UNIQUE
constraint is violated. The `ConstraintViolationException` propagates uncaught.
When `tokenise()` runs inside a caller's `@Transactional` boundary, the JTA
transaction is also doomed — `em.clear()` cannot unmark the rollback flag, and
retry operations in the same transaction fail.

### Context

A non-CDI-bean class (`InternalActorIdentityProvider`) receives an
`EntityManager` CDI proxy from a `@Produces` method. Concurrent threads call
`tokenise(actorId)` which does SELECT → INSERT → flush. The losing thread's
`em.flush()` throws when the UNIQUE constraint fires.

### What was tried (didn't work)

```java
try {
    em.persist(identity);
    em.flush();
} catch (PersistenceException e) {
    if (e.getCause() instanceof ConstraintViolationException) {
        em.clear();
        // retry SELECT — never reached
    }
}
```

The catch block is never entered. The raw
`org.hibernate.exception.ConstraintViolationException` (which extends
`HibernateException`, not `PersistenceException`) passes straight through.

### Root cause

Quarkus's CDI Session proxy (`Session_Synthetic_ClientProxy`) delegates
`flush()` directly to Hibernate's `SessionImpl.flush()`, which throws
`org.hibernate.exception.ConstraintViolationException`. The JPA compatibility
layer that would wrap it in `jakarta.persistence.PersistenceException` is not
in the CDI proxy's call chain. These are independent class hierarchies —
`ConstraintViolationException` extends `JDBCException` extends
`HibernateException` extends `RuntimeException`, while `PersistenceException`
is a separate `RuntimeException` subclass.

### Fix

Two changes needed:

**1. Catch both exception shapes:**
```java
catch (RuntimeException e) {
    if (e instanceof ConstraintViolationException
            || e.getCause() instanceof ConstraintViolationException) {
        // handle race
    }
    throw e;
}
```

**2. Isolate the INSERT in REQUIRES_NEW** to prevent JTA transaction doom:
```java
try {
    return QuarkusTransaction.requiringNew().call(() -> {
        em.persist(identity);
        em.flush();
        return identity.token;
    });
} catch (RuntimeException e) {
    if (e instanceof ConstraintViolationException
            || e.getCause() instanceof ConstraintViolationException) {
        // retry SELECT in the caller's (still-alive) outer transaction
        return em.createNamedQuery(...)...findFirst().orElseThrow(...);
    }
    throw e;
}
```

The REQUIRES_NEW suspends the outer JTA transaction. The constraint violation
only dooms the inner transaction. After the inner TX rolls back, the outer TX
resumes cleanly.

### Why this is non-obvious

The JPA specification says `EntityManager.flush()` throws
`PersistenceException`. A developer following the spec writes
`catch (PersistenceException)` and the catch block is silently bypassed.
The CDI proxy's exception pass-through is invisible — no error, no warning,
just an uncaught exception propagating past the handler that was written to
catch it.

### Alternatives considered

- **@Transactional(REQUIRES_NEW) on the method** — doesn't work because
  `InternalActorIdentityProvider` is constructed by a CDI producer, not a CDI
  bean, so interceptors don't fire.
- **Extract to a CDI bean** — works but requires a new class just for one
  method call. `QuarkusTransaction.requiringNew()` is simpler.
