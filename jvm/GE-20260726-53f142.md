### Symptom
`ConcurrentHashMap.computeIfAbsent()` throws `IllegalStateException: Recursive update` instead of the expected domain exception when the mapping function fails and tries to clean up by calling `remove(key)` on the same map.

### Context
Reactive code using `Uni.memoize().indefinitely()` with `.onFailure().invoke(err -> cache.remove(key))` works because the failure handler runs asynchronously — outside the `computeIfAbsent` call. When migrating to blocking, the natural translation puts `cache.remove(key)` inside the `computeIfAbsent` lambda's catch block, which triggers ConcurrentHashMap's recursive modification protection.

### What was tried (didn't work)
```java
// BROKEN — "Recursive update" exception
channels = layoutCache.computeIfAbsent(key, k -> {
    try {
        return initializeLayout(caseId);
    } catch (RuntimeException e) {
        layoutCache.remove(k);  // ← modifies map inside computeIfAbsent
        throw e;
    }
});
```

### Root cause
`ConcurrentHashMap.computeIfAbsent()` holds the bucket lock while the mapping function executes. Any call to `remove()`, `put()`, or another `computeIfAbsent()` on the same map from within the lambda triggers the recursive-update guard. The reactive `Uni.memoize()` pattern defers failure handling to an asynchronous callback, so the map modification happens after the lock is released.

### Fix
```java
// Move error recovery outside computeIfAbsent
try {
    channels = layoutCache.computeIfAbsent(key, k -> initializeLayout(caseId));
} catch (RuntimeException e) {
    layoutCache.remove(key);  // ← safe: outside the lambda
    throw e;
}
```

### Why this is non-obvious
The reactive `Uni.memoize()` pattern naturally separates the computation from its error recovery via `.onFailure()`, which runs after the Uni pipeline completes. This temporal separation happens to avoid the recursive-update constraint without the developer ever knowing it exists. The blocking translation looks equivalent but violates an invariant that was invisibly satisfied.

### Alternatives considered
- **Pre-check + putIfAbsent:** Compute first, then `putIfAbsent`. Loses the atomicity of `computeIfAbsent` — two threads could compute simultaneously.
- **Wrapper Uni inside computeIfAbsent:** Keep reactive internally, `.await()` inside the lambda. Still holds the bucket lock during the entire await — worse.
