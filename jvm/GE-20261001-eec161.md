### Symptom
`BeanCurrentlyInCreationException` — Spring detects a circular reference between `@Bean` methods in an `@AutoConfiguration` class. Example: `Error creating bean with name 'messageService': Requested bean is currently in creation`.

### Context
A CDI-based Quarkus application has mutual dependencies between `@ApplicationScoped` beans (e.g., `ChannelService` → `ChannelGateway` → `MessageService` → `EnforcementExecutor` → `MessageService`). CDI handles these transparently via lazy client proxies. When converting to a Spring `@AutoConfiguration` with `@Bean` methods, the same dependency graph fails.

### What was tried (didn't work)
1. `spring.main.allow-circular-references=true` in `application.properties` — **only works for component-scanned beans** with setter/field injection. `@Bean` method parameters are resolved eagerly before the method is called; this property has no effect on them.
2. `ObjectProvider<ChannelService>` as a parameter — calling `.getObject()` inside the `@Bean` method still triggers immediate resolution, hitting the cycle.
3. Splitting into multiple `@Configuration` classes with `@DependsOn` — doesn't break the cycle, only reorders evaluation.

### Root cause
Spring's `@Bean` method semantics are fundamentally different from CDI's proxy-based injection:

- **CDI:** `@ApplicationScoped` beans get client proxies. A circular dependency A → B → A works because A's proxy is created immediately (no actual construction), B receives the proxy, and A is constructed lazily on first method call.
- **Spring `@Bean`:** All method parameters are resolved and fully constructed before the method is invoked. There is no proxy layer. A → B → A is a hard cycle.

`spring.main.allow-circular-references=true` enables early bean reference exposure for **component-scanned** beans (via `DefaultSingletonBeanRegistry.addSingletonFactory`). This doesn't apply to `@Bean` methods because the bean instance doesn't exist until the method returns — there's nothing to expose early.

### Fix
Use `@Lazy` on the specific parameter that creates the cycle:

```java
@Bean
public MessageService messageService(@Lazy ChannelService channelService, ...) {
    return new MessageService(channelService, ...);
}
```

`@Lazy` on a `@Bean` method parameter creates a CGLIB proxy for that parameter. The proxy defers resolution until the first method call, breaking the cycle the same way CDI proxies do.

**Requirements:**
- The parameter type must be non-final (CGLIB can't proxy final classes)
- Only one direction of the cycle needs `@Lazy` — identify the least-used path
- Multiple cycles may exist — each needs its own `@Lazy` annotation

For complex CDI-style graphs with many cycles, consider refactoring the auto-config to use `@PostConstruct`-style wiring (construct without the circular dep, set it after via a setter).

### Why this is non-obvious
The `allow-circular-references` property name strongly suggests it handles all circular references. Its documentation doesn't distinguish between component injection and `@Bean` method injection. Developers migrating from CDI expect the same proxy behaviour and are surprised when the "standard" fix doesn't work. The `@Lazy` parameter annotation is a Spring-specific mechanism with no CDI equivalent (CDI proxies are always lazy).
