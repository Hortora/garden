## Symptom

When adopting a simulation framework for an SPI that already has a stateful
in-memory reference implementation (ref module), the natural instinct is to
choose one or the other: simulation replaces ref, or ref stays and simulation
is skipped. Neither gives you the full picture — simulation provides predictable
corpus data for scenarios but can't maintain state across CRUD operations; ref
provides stateful CRUD but isn't corpus-driven or journal-recorded.

## Context

Surfaces when an SPI has both read operations (list, get) and write operations
(create, update, delete) — CRUD SPIs like CalendarPlatform or ChatPlatform. The
simulation framework's corpus strategies return data from YAML files, which is
perfect for reads but breaks state coherence for writes (create followed by list
returns the same corpus data, not the newly created entity).

## Solution

Keep both. The CDI decorator stack composes them naturally:

```
Caller → SimulatedDecorator (generated @Decorator, priority APPLICATION+200)
       → [Ref (if on classpath) | NoOp (@DefaultBean, if not)]
```

The decorator checks `strategy.canResolve(input)` for each method:
- If a strategy exists: return corpus data (simulated path)
- If no strategy: delegate to the underlying bean (ref or NoOp)

This gives three composable modes with zero additional code:

| Mode | Overlay | Delegate | Use case |
|------|---------|----------|----------|
| Scenario | Active — strategies intercept | Ref or NoOp | Predictable corpus data for scenario paths |
| Test | Inactive | Ref seeded directly | Stateful integration testing |
| Interactive | Inactive | Ref seeded with corpus data | Realistic starting state, real CRUD behavior |

The decorator always records to the simulation journal, even when delegating. This gives
observability across all modes.

For CRUD SPIs: configure corpus strategies for **read methods only**. Write methods delegate
to the ref for state coherence. Scenarios needing create→list coherence skip corpus for list
methods too, letting them delegate to the ref.

## Why this is non-obvious

The instinct is to view simulation and ref as competing implementations — pick one. The
CDI decorator precedence model (`@Decorator` > normal bean > `@DefaultBean`) naturally
layers them without any explicit wiring. The decorator intercepts selectively based on
strategy configuration, not based on which bean is the delegate. This means the same
decorator works with any delegate — ref, NoOp, or a real provider — and the mode is
determined entirely by runtime configuration (which strategies are active), not by
classpath composition.

### Alternatives considered

- **Replace ref with simulation-only** — loses stateful CRUD. A scenario calling
  `createEvent()` then `listEvents()` gets corpus data regardless of the create.
- **Keep ref, skip simulation** — loses corpus-driven predictability, journal recording,
  and overlay stack integration with the scenario engine.
- **Separate simulation wrapper class** — hand-written per SPI, duplicates the
  intercept-or-delegate logic the decorator already generates.
