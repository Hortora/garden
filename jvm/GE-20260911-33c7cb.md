# AdaptiveFilter enforces minResults even when all scores are below scoreFloor

## Symptom

`AdaptiveFilter.filter()` returns results even when every candidate's score is below the configured `scoreFloor`. Tests expecting an empty result set fail because minResults items are always returned.

## Context

When migrating from a hand-rolled adaptive filter to the upstream `AdaptiveFilter`, existing tests expected `results.isEmpty()` when all CE scores were negative and the floor was 0.0. The upstream implementation guarantees at least `minResults` items regardless of the floor.

## Root cause

`AdaptiveFilter` treats `minResults` as a hard guarantee — the score floor trims results only above the minimum. This is by design: the caller asked for at least N results, so they get N even if the scores are poor.

## Fix

Update expectations: `minResults` overrides `scoreFloor`. If you need "empty when nothing is good enough", set `minResults=0`. If you want diagnostic information about how many were below floor, compute it separately before calling the filter.

```java
int floorFiltered = (int) candidates.stream()
        .filter(r -> boostedScore(r, boostWeight) < scoreFloor)
        .count();
List<SearchResult> filtered = AdaptiveFilter.filter(candidates, requestedLimit, options);
// floorFiltered tells you how many were below floor
// filtered.size() may be > 0 even when floorFiltered == candidates.size()
```

## Why this is non-obvious

Hand-rolled adaptive filters typically return empty when all candidates fail the floor check — that's the intuitive behavior. The upstream API's minResults guarantee is a design choice that prioritizes "always return something useful" over "respect the floor strictly". The interaction between scoreFloor and minResults isn't documented.
