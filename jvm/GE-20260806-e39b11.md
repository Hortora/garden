### Symptom
After adding `DetectionNodeSpec` to a sealed `DeploymentNodeSpec` interface, compilation failed in files not listed in the implementation plan — `DeploymentApprovalEvaluator` had 2 switch expressions that needed new arms, in addition to the expected 2 in `DeploymentNodeProvisioner`.

### Context
A sealed interface used in multiple switch expressions across different classes. The new permit was planned for the provisioner and adapter — but any class that pattern-matches on the sealed type also breaks.

### Root cause
Java sealed type switch exhaustiveness is enforced at compile time. Every `switch(spec)` expression where `spec` is a sealed type must cover all permits. Adding a permit is a cross-cutting change — the compiler finds all sites, but the developer may not have anticipated them.

### Fix
After adding the sealed permit, compile immediately and fix all exhaustiveness errors before writing any implementation code. Search for all switch expressions that reference the sealed type:
```
ide_search_text query="switch (spec)" filePattern="*.java"
```
Or grep for pattern-matching cases on the sealed interface's existing permits.

### Why this is non-obvious
The plan listed provisioner, adapter, and compiler as touch points — the SPI quad. It did not list the approval evaluator, which has its own independent switches for risk classification and summary generation. A developer following only the SPI quad checklist would be surprised by compilation failures in approval code.
