### Symptom

Flyway migration fails with `SQL State: 42001` when running against H2 in PostgreSQL compatibility mode (`MODE=PostgreSQL`). Two distinct failures:

1. `CREATE UNIQUE INDEX idx_name ON table(col) WHERE status = 'VALUE'` — H2 does not support partial unique indexes (the `WHERE` clause on `CREATE INDEX`)
2. `id UUID PRIMARY KEY DEFAULT gen_random_uuid()` — H2 does not support `DEFAULT` directly after `PRIMARY KEY` on a UUID column

### Context

Common in CaseHub projects using dual-datasource: H2 for dev/test, PostgreSQL for production. Flyway migrations written for PostgreSQL syntax fail silently or with cryptic errors on H2.

### Root cause

H2's PostgreSQL compatibility mode (`MODE=PostgreSQL`) emulates some PostgreSQL SQL syntax but not all. Partial indexes and `DEFAULT` on `PRIMARY KEY` columns are PostgreSQL-specific features with no H2 equivalent.

### Fix

1. **Partial indexes:** Replace with a regular composite index on `(col, status)`. Enforce the uniqueness constraint in application code (e.g., check-then-insert with retry on conflict). For production PostgreSQL, add the partial index via a profile-specific migration if needed.

2. **UUID generation:** Remove `DEFAULT gen_random_uuid()` from DDL. Generate UUIDs in Java constructors (matching the existing pattern in other entity tables).

```sql
-- Instead of:
CREATE TABLE arena_run (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    ...
);
CREATE UNIQUE INDEX idx_inflight ON arena_run(instrument) WHERE status = 'IN_FLIGHT';

-- Use:
CREATE TABLE arena_run (
    id UUID PRIMARY KEY,
    ...
);
CREATE INDEX idx_instrument_status ON arena_run(instrument, status);
```

### Why this is non-obvious

The `MODE=PostgreSQL` setting suggests full PostgreSQL compatibility. The H2 documentation does not explicitly list which PostgreSQL features are unsupported in compatibility mode. The error messages (`expected "HASH, CONSTRAINT, COMMENT..."`) point to syntax parsing, not feature support — misleading when debugging.

### Constraints

Applies when using H2 for dev/test with PostgreSQL for production. Not relevant if using Testcontainers with real PostgreSQL for tests.

### Alternatives considered

- Testcontainers with PostgreSQL — eliminates H2 compatibility issues but adds Docker dependency to test suite
- `quarkus.flyway.clean-at-start=true` — only addresses stale migration state, not the syntax incompatibility
