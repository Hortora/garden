### Symptom
Engine startup hangs for 5+ minutes (normal: 10-25s), then JVM crashes with SIGSEGV in `pthread_mutex_lock` inside ONNX Runtime's parallel executor (`EndParallelSectionInternal`). The crash thread is a `@Scheduled` worker, not the main thread.

### Context
`@Scheduled(every = "6h")` fires its first invocation **immediately at startup** on a worker thread — not after the first interval. If the main thread is still inside `CollectionMigration.onStartup()` loading the ONNX model (`MultiModalEmbedder` via DJL), both threads access ONNX Runtime's native thread pool concurrently.

### What was tried (didn't work)
- Restarting the service — crashed again on second attempt
- Checking model file integrity — files were fine (3MB BGE-M3, 87MB reranker)
- Suspecting JDK 26 incompatibility — same JDK worked on previous non-concurrent startups

### Root cause
Race condition in ONNX Runtime's `ThreadPoolTempl::EndParallelSectionInternal` on ARM64. The reconcile thread runs ONNX inference (via `ingestionService.reconcile()`) while the main thread is still initialising the ONNX session. Both threads enter the native parallel executor, and the mutex lock in `libc++` crashes with SIGSEGV.

### Fix
Add `delayed = "60s"` to the `@Scheduled` annotation:
```java
@Scheduled(every = "${hortora.reconcile.interval:6h}",
           delayed = "60s",
           concurrentExecution = ConcurrentExecution.SKIP)
void reconcile() { ... }
```
This defers the first reconcile invocation until 60 seconds after Quarkus reports ready, ensuring the ONNX model is fully loaded before any inference runs.

### Why this is non-obvious
The symptom (slow startup + crash) looks like a model loading or memory issue. The SIGSEGV stack trace points to `pthread_mutex_lock` in the threading layer, not to anything ONNX-session-related. The root cause — that `@Scheduled(every=...)` fires immediately — is not intuitive from the annotation name, and the `delayed` parameter is easy to overlook.

### Why this fix
`delayed = "60s"` is the minimal change. Alternatives: making the scheduler observe a "model ready" CDI event (more coupling), or configuring ONNX Runtime's intra-op thread count to 1 (kills inference performance). The 60s delay is safe because normal startup takes 10-25s.

### Alternatives considered
- `ORT_NUM_THREADS=1` environment variable — not a real ONNX Runtime env var; thread count is set via SessionOptions API in the upstream inference module
- Startup event ordering — `@Observes @Priority` only controls synchronous startup observers, not `@Scheduled` threads
- Process isolation for reconcile — overkill for a timing fix
