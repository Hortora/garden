## jsonschema2pojo oneOf generates Object return type

### Symptom

After changing a JSON Schema field from `type: string` to `oneOf: [string, object]`, the generated Java class compiles but all call sites fail with `incompatible types: Object cannot be converted to String`.

### Context

Adding per-expression language override syntax to a YAML-parsed case definition. Expression fields (e.g. `when`, `condition`) needed to accept both plain strings and single-key maps (`{ jq: ".expr" }`). The JSON Schema change was:

```yaml
# Before
when:
  type: string

# After — using $ref to shared definition
when:
  $ref: "#/$defs/ExpressionOrOverride"

ExpressionOrOverride:
  oneOf:
    - type: string
    - type: object
      maxProperties: 1
      additionalProperties:
        type: string
```

### Root cause

jsonschema2pojo cannot represent `oneOf: [string, object]` as a single Java type. Since `String` and `Map` have no common supertype other than `Object`, the generated getter returns `Object`:

```java
// Before: public String getWhen()
// After:  public Object getWhen()
```

This breaks every call site that passes the result to a method expecting `String`.

### Fix

Read expression values from the raw `JsonNode` instead of the generated schema model accessors. The schema model's `Object` return type ensures Jackson accepts both strings and maps without deserialization errors; the raw node provides the actual type discrimination:

```java
// Instead of: registry.create(schemaBinding.getWhen(), expressionLang)
// Use:        resolveExpression(rawBindingNode.get("when"), registry, expressionLang)
```

The `resolveExpression` helper checks `isTextual()` vs `isObject()` on the raw JsonNode.

### Why this is non-obvious

The `oneOf` change looks like a schema-level concern that shouldn't affect Java call sites. A developer making the schema change would not anticipate that `getWhen()` silently changes from `String` to `Object`. The compilation errors appear at every call site simultaneously — not at the schema change point. The fix (raw JsonNode) also reverses the usual expectation: you'd expect to use the typed model, not bypass it.
