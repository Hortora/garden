## Symptom

All `@QuarkusTest` classes that use REST Assured for HTTP assertions fail with:

```
java.lang.NullPointerException
  at java.base/java.lang.Class.isAssignableFrom(Native Method)
  at org.codehaus.groovy.runtime.metaclass.ClosureMetaClass.invokeOnDelegationObject(ClosureMetaClass.java:367)
  at org.codehaus.groovy.runtime.metaclass.ClosureMetaClass.invokeMethod(ClosureMetaClass.java:324)
  at io.restassured.internal.RequestSpecificationImpl$_sendHttpRequest_closure27.doCall(RequestSpecificationImpl.groovy:1484)
```

Tests compile fine. The NPE occurs at runtime during HTTP request dispatch. No version mismatch warning at startup.

## Context

Quarkus 3.39.x pulls Groovy 5.0.8 via its BOM. REST Assured 5.5.6 (also from the Quarkus BOM) only supports Groovy 4.x. The Groovy 5 metaclass resolution passes `null` to `Class.isAssignableFrom`, causing the NPE deep in Groovy internals.

The stack trace gives no indication this is a version incompatibility — it looks like a Groovy bug or a REST Assured bug, sending you down the wrong investigation path.

## What was tried (didn't work)

- Cleaning target directories and rebuilding
- Killing zombie surefire processes (suspecting port conflicts)
- Checking for test code errors

## Root cause

REST Assured 5.5.x is incompatible with Groovy 5.x. Groovy 5 changed the metaclass method resolution in `ClosureMetaClass`, and REST Assured's Groovy-based `RequestSpecificationImpl` relies on the Groovy 4 behaviour. The null argument to `isAssignableFrom` comes from Groovy 5's new delegation resolution path not finding the expected type.

## Fix

Pin REST Assured 6.0.1 in `<dependencyManagement>` **before** the Quarkus BOM import:

```xml
<dependencyManagement>
    <dependencies>
        <!-- Must come BEFORE quarkus-bom to override its 5.5.6 -->
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>rest-assured</artifactId>
            <version>6.0.1</version>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>rest-assured-common</artifactId>
            <version>6.0.1</version>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>json-path</artifactId>
            <version>6.0.1</version>
            <scope>test</scope>
        </dependency>
        <dependency>
            <groupId>io.rest-assured</groupId>
            <artifactId>xml-path</artifactId>
            <version>6.0.1</version>
            <scope>test</scope>
        </dependency>
        <!-- quarkus-bom import follows -->
    </dependencies>
</dependencyManagement>
```

REST Assured 6.0.1 has native Groovy 5 support. All four artifacts must be pinned — pinning only `rest-assured` leaves transitive `json-path` and `xml-path` on 5.5.6.

## Why this is non-obvious

The NPE stack trace points to Groovy metaclass internals, not a version conflict. `Class.isAssignableFrom` at native method level suggests a JVM or Groovy bug. The Quarkus BOM manages both Groovy and REST Assured versions — you'd expect them to be compatible since they're in the same BOM. The incompatibility arises because the Quarkus BOM bumped Groovy to 5.x but didn't bump REST Assured to 6.x in the same release.

### Why this fix

Pinning in the consuming POM before the BOM import is required because Maven BOM-within-BOM imports don't propagate explicit overrides as expected (see GE-20260918-73e964). REST Assured 6.0.1 (not 6.0.0) is needed because 6.0.0 still pulled its own Spring version onto the classpath.

### Alternatives considered

- Pinning Groovy back to 4.x: breaks other Quarkus 3.39 internals that depend on Groovy 5
- Excluding Groovy from REST Assured and letting the BOM version win: same crash, the issue is in REST Assured's compiled Groovy code, not the Groovy runtime version
