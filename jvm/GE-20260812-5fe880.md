## Quarkus cross-JAR orm.xml mapped-superclass discovery works correctly

**ID:** GE-20260812-5fe880
**Stack:** Quarkus, Hibernate ORM, JPA, Jandex
**Symptom:** No symptom — this is a false alarm. The concern was that Quarkus's Jandex build-time scanning might not discover `<mapped-superclass>` declarations in `orm.xml` files located in dependency JARs (not the application JAR). This turned out to work correctly.
**Context:** When stripping JPA annotations from API module classes and moving them to `orm.xml` in a runtime module, there was concern (casehubio/ledger#189 T1.2a) that the cross-JAR arrangement would break Quarkus's entity discovery.

### What was tried (didn't work)
- Worried that Jandex indexing would miss orm.xml from dependency JARs — this concern was unfounded
- Considered keeping JPA annotations in the API module to avoid the risk — unnecessary

### Root cause
Not a bug. Quarkus Hibernate ORM's build-time augmentation processes `orm.xml` files from all JARs on the classpath, not just the application JAR. The Jandex index is used for annotation scanning, but `orm.xml` processing follows standard JPA semantics: the persistence provider reads `META-INF/orm.xml` (and files referenced by `<mapping-file>`) from the entire classpath.

### Fix
No fix needed — proceed with the cross-JAR orm.xml arrangement. Tested with a 3-JAR chain:
- `CaseLedgerEntry` (engine-ledger JAR) extends `JpaLedgerEntry` (ledger-runtime JAR) extends `LedgerEntry` (ledger-api JAR)
- `orm.xml` in the runtime JAR declares `LedgerEntry` as `<mapped-superclass>`
- All 899 tests passed (832 runtime + 67 engine-ledger)

### Why this is non-obvious
Quarkus replaces much of standard Hibernate's runtime scanning with Jandex-based build-time augmentation. When you know that, it's reasonable to worry that `orm.xml` from dependency JARs might be skipped — Jandex indexes are per-JAR, and Quarkus documentation doesn't explicitly state that cross-JAR `orm.xml` is supported. The concern is heightened when the `<mapped-superclass>` is in a different JAR from the `orm.xml` that declares it. A developer could easily spend time building workarounds (keeping annotations in the API module, duplicating orm.xml) for a problem that doesn't exist.
