### Symptom
Integration test dispatches a worker with `ExecutionMode.REINVOKED`. Quartz logs confirm the job started and the worker function executed. But the test assertion on a case context key (e.g. `.monitored != null`) times out after 15 seconds. No error, no exception, no log indicating failure.

### Context
`QuartzWorkerExecutionJob` checks `executionMode` from EventLog metadata. For non-TRANSIENT workers (REINVOKED, PERSISTENT), a `WorkerOutcome.Success` return suppresses `WorkflowExecutionCompleted` — the PlanItem stays RUNNING and worker output is never applied to the case context. Only `WorkerOutcome.Completed` triggers PlanItem completion and output application.

This is correct production behaviour — REINVOKED workers are long-lived and their intermediate `Success` returns should not complete the PlanItem. But in integration tests that assert on context output, the worker appears to run but produce nothing.

### Root cause
The test used `ExecutionMode.REINVOKED` on a binding whose worker returns `WorkerResult.of(Map.of("key", "value"))` — which is `WorkerOutcome.Success`. With REINVOKED, Success suppresses completion, so the output map never reaches the case context via `WorkflowExecutionCompletedHandler`.

### Fix
For integration tests that verify dispatch and output application (not execution mode semantics), use the default `ExecutionMode.TRANSIENT`. TRANSIENT workers apply output normally on Success.

Reserve REINVOKED/PERSISTENT in tests that specifically test completion suppression or accumulated state threading.

```java
// Wrong — output never reaches context
Binding.builder()
    .name("monitor")
    .capability(cap)
    .on(new ScopeActivatedTrigger())
    .lifecycleScope(LifecycleScope.COMPOUND)
    .participation(Participation.COMPANION)
    .executionMode(ExecutionMode.REINVOKED)  // suppresses output
    .build();

// Right — output applied normally
Binding.builder()
    .name("monitor")
    .capability(cap)
    .on(new ScopeActivatedTrigger())
    .lifecycleScope(LifecycleScope.COMPOUND)
    .participation(Participation.COMPANION)
    // TRANSIENT is the default — no executionMode() call needed
    .build();
```

### Why this is non-obvious
The Quartz log shows the job executed successfully. No error is logged. The worker function runs and returns a result. The only clue is that `WorkflowExecutionCompleted` is never published — but that event is internal to the engine and not logged at INFO level. The test just times out, and the natural debugging path ("is the worker being dispatched? yes. is it running? yes. is it returning data? yes.") all checks pass.
