## Symptom

A CDI audit (automated or manual) flags `@ApplicationScoped @Named` beans as having "unnecessary CDI" because they have zero `@Inject` fields. The audit recommends removing `@ApplicationScoped`. Doing so silently breaks CDI-based strategy selection — `Instance<>` consumers no longer discover the bean.

## Context

Common in codebases using the CDI strategy/plugin pattern: an interface (e.g. `KiteStrategy`) has multiple `@Named` implementations selected at runtime via `@Inject Instance<KiteStrategy>`. Each implementation is pure logic with no field injections — it just implements the interface. An automated audit scanning for "beans that don't inject anything" flags all of them.

## What was tried (didn't work)

Trusting the audit output at face value — removing `@ApplicationScoped` from classes flagged as "zero injections." The application compiles but `Instance<>` iteration returns an empty set at runtime.

## Root cause

The audit checks only the **injector** side ("does this class inject anything?") but misses the **consumer** side ("is this class injected by others?"). CDI serves two purposes:

1. **Dependency injection** — injecting dependencies into the class (`@Inject` fields)
2. **Dependency provision** — making the class discoverable by others (`@ApplicationScoped` + `@Named`)

A bean with zero `@Inject` fields still needs `@ApplicationScoped` if it is consumed via `Instance<>` elsewhere.

## Fix

Before removing CDI annotations from a "zero injections" bean, check both directions:

1. **Injector side:** Does the class have `@Inject` fields? (the audit already checks this)
2. **Consumer side:** Is the class injected by others? Search for:
   - `Instance<InterfaceName>` — CDI programmatic lookup
   - `@Named("qualifier")` — CDI qualifier (implies the bean is selected by name)
   - `@Inject InterfaceName` — direct injection of the interface

Only remove CDI annotations if the bean has zero injections AND zero consumers.

```java
// These four classes have zero @Inject fields but are ALL consumed
// via @Inject Instance<KiteStrategy> in DroolsTacticsTask:

@ApplicationScoped @Named("direct")
public class DirectKiteStrategy implements KiteStrategy { /* pure math */ }

@ApplicationScoped @Named("terrain-aware")
public class TerrainAwareKiteStrategy implements KiteStrategy { /* pure math */ }

// Removing @ApplicationScoped from either breaks:
@Inject Instance<KiteStrategy> kiteStrategies;  // now returns empty
```

## Why this is non-obvious

"Zero injections" sounds definitive — if a class doesn't inject anything, CDI seems unnecessary. The mental model is "CDI = getting things injected into me." But CDI's other role — making the class discoverable to others — is invisible when you only inspect the class in isolation. The audit methodology has a systematic blind spot for the consumer side.

### Alternatives considered

- Checking `@Named` presence as a heuristic — catches some cases but misses unnamed `@ApplicationScoped` beans consumed via `Instance<InterfaceType>` without qualifiers.
- IDE "find usages" on the class — correct but manual; the audit was meant to automate this.
