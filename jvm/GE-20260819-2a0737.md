### Symptom

A REST resource injects a dashboard service for all channel operations, but most endpoints only need the underlying domain service interfaces. The dashboard service adds name-based addressing and aggregation queries — but individual operations (post message, add reaction, list members) pass straight through to the same domain interfaces the consumer could call directly.

### Context

A dashboard service was created to provide: (1) name→UUID channel resolution, (2) aggregated overview queries (channel list with counts, cross-channel feed), (3) timeline formatting. Individual channel operations (messages, reactions, members, topics, commitments) were added to the same service for consistency, but they don't use any dashboard-specific logic — they just resolve the name and call the domain API.

### Root cause

The dashboard service started as a convenience for name-based addressing. Individual operations were added alongside aggregation queries because they needed the same name resolution. Over time, the service became the de facto API layer — even though only the aggregation queries genuinely need it.

### Fix

Split the concerns: individual channel operations go through the domain consumer interfaces directly (with a simple name→UUID resolver at the REST boundary). The dashboard service shrinks to aggregation-only queries that genuinely need cross-entity joins (channel listing with counts, cross-channel feeds, instance overview).

### Why this is non-obvious

The coupling looks intentional — all operations go through one service, the code is clean, and it works. The problem only surfaces when a second consumer wants to use the same domain operations without the dashboard wrapper, and discovers it either depends on the whole dashboard service or must reimplement the individual operations.
