## Symptom

All `@QuarkusTest` tests in a downstream app fail with:

```
UnsatisfiedResolutionException: Unsatisfied dependency for type
io.casehub.platform.identity.ReactiveAgentIdentityVerificationService
- injection target: io.casehub.ledger.runtime.service.identity.ReactiveAgentIdentityVerificationService#delegate
```

The downstream app does not use identity verification at all. The error references types from two different transitive dependencies.

## Context

Three-level transitive chain: `app → casehub-qhorus → casehub-ledger → casehub-platform-identity`. The ledger jar (built Jul 21) has a CDI bean that `@Inject`s `ReactiveAgentIdentityVerificationService` from platform-identity. The platform-identity jar (rebuilt Jul 23) removed that class entirely. Maven resolves the latest SNAPSHOT of each artifact independently — no consistency check across the chain.

The compilation succeeds because no app code references the removed class directly. The failure only surfaces at Quarkus augmentation time when Arc validates all CDI injection points, including those in transitive dependencies.

## What was tried (didn't work)

- Adding `casehub-platform-identity` as an explicit dependency — the class no longer exists in the jar
- Checking the dependency tree — both jars are present, the class is simply gone from the newer SNAPSHOT

## Root cause

SNAPSHOT version skew across a transitive dependency chain. The intermediate dependency (casehub-ledger) was compiled against an older SNAPSHOT of the leaf dependency (casehub-platform-identity) that still had the class. When the leaf SNAPSHOT was rebuilt without it, the intermediate jar's CDI injection point became unsatisfiable.

## Fix

**Immediate (downstream app):** Exclude the broken bean package via Quarkus Arc config:
```properties
quarkus.arc.exclude-types=io.casehub.ledger.runtime.service.identity.**
```

**Proper (upstream):** Rebuild casehub-ledger against the current platform-identity SNAPSHOT so the stale reference is removed at source.

## Why this is non-obvious

The symptom — a CDI error referencing types the app doesn't use — gives no indication that the root cause is a SNAPSHOT version mismatch between two transitive dependencies. The natural instinct is to check if a dependency is missing from the classpath, but both jars are present. The actual problem is that a class was removed from one jar while another jar still references it, and this only fails at CDI validation time, not at compilation.

### Alternatives considered

- Adding the missing class back as a local stub — rejected because it masks the real problem and creates a maintenance burden
- Downgrading platform-identity to the version that has the class — rejected because it would revert other fixes in the newer SNAPSHOT
