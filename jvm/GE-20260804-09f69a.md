## jakarta.ws.rs.* wildcard import clashes with java.nio.file.Path

### Symptom

Compilation error: `incompatible types: java.nio.file.Path cannot be converted to java.lang.annotation.Annotation` on lines using `Path.of(...)` or method parameters typed as `Path`.

### Context

A JAX-RS resource class uses `import jakarta.ws.rs.*` (wildcard) and also needs `java.nio.file.Path` for filesystem operations (reading files, resolving paths). The wildcard import pulls in `jakarta.ws.rs.Path` (the annotation), which shadows `java.nio.file.Path`.

### Root cause

`jakarta.ws.rs.*` imports all types from the JAX-RS package, including `jakarta.ws.rs.Path` (the `@Path` annotation for REST endpoints). When the code references `Path` unqualified, the compiler resolves it to `jakarta.ws.rs.Path` (the annotation) rather than `java.nio.file.Path` (the interface). The error message is confusing because it refers to annotation conversion, not the expected "cannot find symbol."

### Fix

Replace the wildcard import with explicit imports for the JAX-RS annotations you actually use:

```java
// Instead of:
import jakarta.ws.rs.*;

// Use explicit imports:
import jakarta.ws.rs.Consumes;
import jakarta.ws.rs.DELETE;
import jakarta.ws.rs.GET;
import jakarta.ws.rs.POST;
import jakarta.ws.rs.QueryParam;
```

Then `import java.nio.file.Path` works without conflict. Alternatively, keep the wildcard and use `java.nio.file.Path` fully qualified everywhere — but explicit imports are cleaner.

### Why this is non-obvious

The error message (`cannot be converted to java.lang.annotation.Annotation`) doesn't mention import conflicts or name shadowing. IDEs may auto-add the wildcard import when multiple JAX-RS annotations are used, silently introducing the conflict. The compilation error only appears on lines using `Path` for filesystem operations — the `@Path("/api/...")` annotation usage compiles fine, making it look like a problem with the filesystem code rather than an import issue.
