## Symptom

`cannot find symbol` errors for getters/setters that clearly exist in the YAML schema definition. Example: `getContextType()` or `getSignal()` on `io.casehub.model.CaseDefinition` — the field is in `schema/src/main/resources/schema/CaseDefinition.yaml` but the compiler says it doesn't exist.

## Context

The casehub-engine uses a custom code generator (`codegen/`) that reads YAML schema files and produces Java model classes via jsonschema2pojo into `schema/target/generated-sources/jsonschema2pojo/`. Dependent modules (`api/`, `runtime/`, etc.) declare a Maven dependency on the `casehub-engine-schema` JAR — they resolve the compiled schema model from the local Maven repository, not from the generated sources directory.

## What was tried (didn't work)

- Running `mvn generate-sources -pl codegen,schema` — regenerates the sources but doesn't install the JAR
- Running `mvn test -pl api` directly — the `api` module's `compile` phase resolves the schema JAR from the local repo, which still contains the pre-change model
- Installing platform to the host `~/.m2` — irrelevant if the engine uses a slot-specific local repo

## Root cause

Maven's `-pl api` builds only the `api` module. The `generate-sources` phase for `schema/` runs automatically in a full reactor build but is skipped when building a single module. The `api` module's dependency on `casehub-engine-schema` is a JAR dependency, not a source dependency — it reads the compiled JAR from the local Maven repository, not the generated sources on disk.

## Fix

After changing any YAML schema file, run both generate and install before building dependent modules:

```bash
mvn generate-sources install -DskipTests -pl codegen,schema
```

Then build the dependent module:

```bash
mvn test -pl api -Dtest=YourTest
```

The `generate-sources` phase regenerates the Java model from YAML. The `install` phase compiles and installs the updated JAR to the local Maven repo where dependent modules can find it.

## Why this is non-obvious

The `generate-sources` phase runs automatically during a full `mvn install` build — so developers who always build the full reactor never see this. The problem only surfaces when using `-pl` to build a single module after a schema change, which is common during TDD cycles where you want fast feedback on a single test class. The error message (`cannot find symbol`) gives no hint that the issue is a stale dependency JAR rather than a missing field.
