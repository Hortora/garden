## CDI decorators in library JARs with Jandex are discovered by Arc but lifecycle callbacks ignored

**ID:** GE-20260806-46f5e2
**Stack:** Quarkus 3.36.x, quarkus-arc, Jandex
**Symptom:** A CDI `@Decorator` defined in a library JAR that includes a Jandex index (`META-INF/jandex.idx`) IS discovered and activated by Quarkus Arc — method interception works correctly. However, `@PostConstruct` and `@PreDestroy` callbacks on the decorator are silently ignored. The decorator appears completely inactive because its initialization never runs.
**Context:** Multi-module Maven or Gradle builds where CDI decorators are defined in shared library modules. The library JAR includes a Jandex index for bean discovery. The consuming Quarkus application correctly discovers and activates the decorator, but lifecycle callbacks are never invoked.

### What was tried (didn't work)
- Adding `META-INF/jandex.idx` to the library JAR — decorator is discovered, but @PostConstruct still not called
- Adding `quarkus.index-dependency` config alongside the Jandex index — makes no difference
- Verifying decorator activation by checking method interception — interception works, lifecycle doesn't
- Moving the decorator to the consuming application — same result (same root cause as GE-20260806-93549d)

### Root cause
Same root cause as GE-20260806-93549d: Quarkus Arc does not invoke `@PostConstruct` or `@PreDestroy` lifecycle callbacks on `@Decorator` beans, regardless of where the decorator is defined. The multi-module aspect adds confusion because developers also suspect the problem might be related to bean discovery across module boundaries — but discovery works fine; it's the lifecycle that's broken.

### Fix
Two approaches:

1. **Keep decorator logic in the library JAR, wire CDI decorator in the consuming application** — define the wrapping logic as a plain class in the library, then create the `@Decorator` CDI bean in the Quarkus application module where you can control initialization explicitly.

2. **Use a @Produces-site wrapper pattern instead** — avoid `@Decorator` entirely. Keep the wrapping logic as a plain class in the library JAR, and apply it in the `@Produces` method that creates the original bean. The producer method has full access to injected config and can conditionally wrap. See GE-20260806-842ee0 for the full pattern.

### Why this is non-obvious
In a multi-module build, when a decorator doesn't work as expected, the natural assumption is that the problem is bean discovery across module boundaries. Developers spend time debugging Jandex indexing, `quarkus.index-dependency` configuration, and classpath issues. The actual problem — that Arc doesn't call lifecycle callbacks on decorators — is completely unrelated to the multi-module aspect. This misdirection compounds the debugging time.

### Why this fix
The `@Produces`-site wrapper pattern (option 2) is preferred because it avoids the Arc limitation entirely and works cleanly across module boundaries. The library provides the wrapper class; the consuming application's producer method applies it with full control over initialization.
