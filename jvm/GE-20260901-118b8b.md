## Symptom

Adding `dss-pades-pdfbox` and `dss-cades` to your Maven project compiles but fails at runtime with three distinct errors depending on which missing dependency you hit first:
- `NoClassDefFoundError: eu/europa/esig/dss/token/Pkcs12SignatureToken` — missing `dss-token`
- `ExceptionInInitializerError: No implementation found for IUtils` — missing `dss-utils-apache-commons`
- `NoClassDefFoundError: eu/europa/esig/dss/validation/SignedDocumentValidator` — missing `dss-validation` (declared `<optional>` in `dss-pades`)

## Context

EU DSS (Digital Signature Services) is the European Commission's reference implementation for PAdES/CAdES/XAdES signing. Version 6.x split the monolithic library into ~20 Maven modules. The signing service modules (`dss-pades-pdfbox`, `dss-cades`) pull their compile-time dependencies transitively, but three runtime-essential modules are NOT transitive.

## What was tried (didn't work)

Adding only the documented high-level modules (`dss-pades-pdfbox`, `dss-cades`, `dss-service`) — compiles, fails at runtime.

## Root cause

- `dss-token` (contains `Pkcs12SignatureToken`, `KSPrivateKeyEntry`, `SignatureTokenConnection`) is a standalone module — not depended on by any of the signing modules
- `dss-validation` (contains `SignedDocumentValidator`, `Reports`) is declared `<optional>true</optional>` in `dss-pades` — Maven does not pull optional deps transitively
- `dss-utils-apache-commons` (or `dss-utils-google-guava`) provides the `IUtils` SPI — DSS uses `ServiceLoader` at runtime

## Fix

Declare all three explicitly alongside the signing modules:

```xml
<dependency>
  <groupId>eu.europa.ec.joinup.sd-dss</groupId>
  <artifactId>dss-token</artifactId>
  <version>${dss.version}</version>
</dependency>
<dependency>
  <groupId>eu.europa.ec.joinup.sd-dss</groupId>
  <artifactId>dss-validation</artifactId>
  <version>${dss.version}</version>
</dependency>
<dependency>
  <groupId>eu.europa.ec.joinup.sd-dss</groupId>
  <artifactId>dss-utils-apache-commons</artifactId>
  <version>${dss.version}</version>
</dependency>
```

Additionally, the 4.x→6.x package rename (`eu.europa.ec.markt.dss` → `eu.europa.esig.dss`) means most online examples have wrong import paths.

## Why this is non-obvious

The compile succeeds because the signing service APIs don't reference token/validation/utils types directly — they're used internally via interfaces. The three runtime failures appear one at a time (fix one, discover the next), making diagnosis slow. The `<optional>` on `dss-validation` is invisible unless you read `dss-pades`'s published pom.
