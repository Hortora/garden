### Symptom
REST endpoints return HTTP 403 Forbidden in demo/jar mode despite `quarkus.http.auth.permission.permit-all.paths=/*` and `quarkus.http.auth.permission.permit-all.policy=permit` being configured. Profile shows "demo activated" in logs.

### Context
A Quarkus app with `@RolesAllowed` on REST resources, OIDC disabled in demo profile (`quarkus.oidc.enabled=false`), and HTTP permit-all configured. Works fine in `quarkus:dev` mode (where `quarkus.security.auth.enabled-in-dev-mode=false` disables all security). Fails when running from the packaged jar (`java -jar quarkus-run.jar`).

### What was tried (didn't work)
- `quarkus.http.auth.permission.permit-all.policy=permit` — allows path-level access but `@RolesAllowed` is a method-level CDI interceptor that requires an actual `SecurityIdentity` with the declared roles
- `quarkus.security.auth.enabled-in-dev-mode=false` — only works in `quarkus:dev` mode, has no effect in jar/production mode
- `quarkus.http.auth.proactive=false` — defers authentication but doesn't bypass `@RolesAllowed` check when it fires
- `quarkus.security.auth.enabled=false` — this property does not exist in Quarkus

### Root cause
Quarkus security has two independent layers:
1. **HTTP permission policies** (`quarkus.http.auth.permission.*`) — path-level, handled by Vert.x routing
2. **CDI security annotations** (`@RolesAllowed`, `@Authenticated`) — method-level, handled by the security interceptor

`permit` policy at the HTTP layer allows the request to reach the resource, but the CDI interceptor still checks `SecurityIdentity.getRoles()` against `@RolesAllowed`. With OIDC disabled, there's no authentication mechanism to create a `SecurityIdentity`, so every request is anonymous with no roles — and `@RolesAllowed` rejects it.

`auth.enabled-in-dev-mode=false` works because it disables BOTH layers entirely — a dev-mode-only shortcut with no production equivalent.

### Fix
Create a profile-scoped `IdentityProvider` that creates an authenticated identity for anonymous requests:

```java
@ApplicationScoped
@Alternative
@Priority(300)
@IfBuildProfile("demo")
public class DemoIdentityProvider implements IdentityProvider<AnonymousAuthenticationRequest> {

    @Override
    public Class<AnonymousAuthenticationRequest> getRequestType() {
        return AnonymousAuthenticationRequest.class;
    }

    @Override
    public Uni<SecurityIdentity> authenticate(AnonymousAuthenticationRequest request,
                                               AuthenticationRequestContext context) {
        return Uni.createFrom().item(QuarkusSecurityIdentity.builder()
                .setPrincipal(() -> "demo-admin")
                .addRole("household-admin")
                .addRole("household-member")
                .setAnonymous(false)
                .build());
    }
}
```

This intercepts anonymous requests before `@RolesAllowed` fires and provides a `SecurityIdentity` with the required roles. `@IfBuildProfile("demo")` ensures it only activates in the demo profile.

### Why this is non-obvious
The permit-all HTTP permission is expected to "permit all" — but it only permits at the path routing layer, not at the CDI annotation layer. The `auth.enabled-in-dev-mode` property creates a false expectation that a similar production-mode property exists. The actual fix requires understanding that Quarkus security has two independent enforcement layers and that `@RolesAllowed` needs a real `SecurityIdentity`, not just path permission.
