### Symptom

After `mvn install` succeeds in repo A (e.g. casehub-ledger), repo B (e.g. casehub-aml) still resolves the old SNAPSHOT from before the install. Compilation fails with "cannot find symbol" for classes that were just renamed and installed.

### Context

When Maven's `settings.xml` configures a custom `<localRepository>` (e.g. `/project/worktrees/30/.m2`), `mvn install` in repo A writes to that custom path. But repo B may resolve its `settings.xml` differently — if it inherits a different settings file or the custom path is relative and resolves differently from a different CWD — and reads from `~/.m2/repository` instead.

Additionally, old timestamped SNAPSHOT jars (e.g. `casehub-ledger-0.2-20260730.095553-251.jar`) persist in `~/.m2/repository` alongside the freshly installed local SNAPSHOT. Maven may resolve the timestamped remote SNAPSHOT instead of the local install.

### What was tried (didn't work)

1. `mvn install` from repo A — succeeded but installed to custom path
2. `mvn compile` in repo B — failed because it reads from standard `~/.m2/repository`
3. Deleting old timestamped jars manually — helped but fragile

### Root cause

Maven resolves `<localRepository>` from `settings.xml` per invocation. If different repos use different effective settings (different user, different `settings.xml` path, or relative path that resolves differently), `mvn install` writes to one location and `mvn compile` reads from another.

### Fix

Force the standard local repo path explicitly when installing cross-repo SNAPSHOTs:

```bash
mvn -f /path/to/repo-A/pom.xml install -DskipTests -Dmaven.repo.local=/Users/<user>/.m2/repository
```

Check the effective local repo path first:
```bash
mvn help:effective-settings 2>/dev/null | grep localRepository
```

### Why this is non-obvious

`mvn install` reports BUILD SUCCESS. The artifact is installed — just in the wrong location. The consuming repo's compilation error ("cannot find symbol") points to the renamed class, not to a repository resolution issue. The connection between "install succeeded" and "class not found" requires checking two different Maven local repo paths.

### Alternatives considered

- Symlinks between the two local repo directories — brittle and platform-dependent
- Using `mvn install:install-file` to manually place the jar — works but doesn't install the POM or transitive metadata
