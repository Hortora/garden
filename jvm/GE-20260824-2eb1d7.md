# victools/jsonschema-generator custom module patterns for type replacement and post-processing

## Technique

When generating JSON Schema from Java types via reflection, the runtime Java types often don't match the desired schema structure — marker interfaces produce empty `{ type: object }`, records have different field names than the YAML convention, and flat class hierarchies need nesting. victools provides two extension points that handle these cases cleanly.

### CustomDefinitionProvider — full type replacement

Use `forTypesInGeneral().withCustomDefinitionProvider()` to intercept specific types and return a hand-crafted schema. The provider receives a `ResolvedType` and returns `CustomDefinition` or `null` (delegate to default).

```java
builder.forTypesInGeneral().withCustomDefinitionProvider((type, context) -> {
    if (type.getErasedType() == Worker.class) {
        ObjectNode schema = context.getGeneratorConfig().createObjectNode();
        schema.put("type", "object");
        schema.put("additionalProperties", true);
        // ... build properties ...
        return new CustomDefinition(schema);  // single-arg constructor
    }
    return null;
});
```

**Key detail:** The constructor is `CustomDefinition(ObjectNode)`, not `CustomDefinition(ObjectNode, DefinitionType)` — the two-arg form takes a boolean. Using `DefinitionType.STANDARD` as the second arg causes a compilation error.

Use for: empty marker interfaces, sealed interfaces that need named-property `oneOf` instead of discriminator-based `oneOf`, records with field names that differ from the schema convention.

### TypeAttributeOverride — post-processing

Use `forTypesInGeneral().withTypeAttributeOverride()` to modify schemas after victools generates them. Receives the generated `ObjectNode`, the type scope, and the generation context.

```java
builder.forTypesInGeneral().withTypeAttributeOverride((schema, scope, context) -> {
    if (scope.getType().getErasedType() == CaseDefinition.class) {
        ObjectNode props = (ObjectNode) schema.get("properties");
        ObjectNode specSchema = context.getGeneratorConfig().createObjectNode();
        ObjectNode specProps = specSchema.putObject("properties");
        // Move fields from root to nested object
        for (String field : fieldsToNest) {
            specProps.set(field, props.get(field));
            props.remove(field);
        }
        props.set("spec", specSchema);
    }
});
```

Use for: restructuring flat schemas into nested ones, adding `unevaluatedProperties`, removing unwanted fields.

### Module ordering matters

Modules that add global post-processing (e.g. `unevaluatedProperties: false` on all objects) will overwrite `additionalProperties` set by type-replacement modules if they run without exclusions. Maintain an exclusion set:

```java
private static final Set<Class<?>> EXCLUDED = Set.of(Worker.class, CaseCompletion.class);

builder.forTypesInGeneral().withTypeAttributeOverride((schema, scope, context) -> {
    if (EXCLUDED.contains(scope.getType().getErasedType())) return;
    // ... apply global override ...
});
```

Register type-replacement modules before post-processing modules in the `SchemaGeneratorConfigBuilder`.

## Why this is non-obvious

The victools documentation covers basic module creation but doesn't show patterns for handling the common case where Java runtime types fundamentally differ from the desired schema structure (different field names, marker interfaces, sealed hierarchies needing named-property oneOf). The `CustomDefinition` constructor API is also surprising — the intuitive `new CustomDefinition(schema, DefinitionType.STANDARD)` doesn't compile.

### Alternatives considered
- JavaParser source analysis — richer type info but requires source files for all dependencies; reflection works with compiled JARs naturally
- Rolling a custom reflection walker — reimplements what victools handles for simple cases (records, enums, validation annotations)
- Jackson schema generation (`JsonSchemaGenerator`) — limited Draft 4 support only, no Draft 2020-12
