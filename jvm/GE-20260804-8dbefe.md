## What happens

After deleting a CDI event class (e.g. `PlanItemFaultedEvent`) from an upstream module, downstream modules that previously compiled against it retain the class reference in their embedded Jandex index (`META-INF/jandex.idx`). When a Quarkus application depends on the downstream module via SNAPSHOT, augmentation scans all Jandex indexes on the classpath and attempts to load every referenced class — throwing `ClassNotFoundException` for the deleted class.

### Symptom

```
Caused by: java.lang.ClassNotFoundException: io.casehub.engine.common.spi.event.PlanItemFaultedEvent
    at io.quarkus.bootstrap.classloading.QuarkusClassLoader.loadClass(QuarkusClassLoader.java:579)
```

The stack trace shows `ApplicationImpl.<clinit>` — the error fires during Quarkus startup, before any application code runs.

### Context

- Multi-module Maven project with `0.2-SNAPSHOT` dependencies resolved from `~/.m2`
- Upstream module (`engine-common`) deleted three CDI event record classes
- Upstream module was rebuilt and installed — the deleted classes are NOT in its JAR
- Downstream module (`work-engine-adapter`) was NOT rebuilt — its JAR still has a Jandex index referencing the deleted classes
- The downstream module's **source code** has no references — `grep` finds nothing
- The application (`devtown-app`) depends on both modules

### What was tried (didn't work)

- `mvn clean install` on the upstream module only — does not touch downstream JARs
- `mvn clean test` on the application — still fails because the stale downstream JAR is in `~/.m2`
- Checking source code for remaining references — none exist; the reference is only in the binary Jandex index

### Root cause

Jandex indexes are generated at build time by the `jandex-maven-plugin` and embedded in the JAR. They capture all class references visible to the module at build time — including CDI observer method parameter types, injection point types, and annotation targets. When a referenced class is deleted upstream, the Jandex index in the downstream JAR becomes stale. Quarkus augmentation trusts the Jandex index without checking whether the referenced classes actually exist on the classpath.

### Fix

Rebuild and install the downstream module to regenerate its Jandex index:

```bash
mvn install -DskipTests -pl engine-adapter -f /path/to/work/pom.xml
```

To find which JARs have stale references, scan all SNAPSHOT JARs:

```python
import zipfile, glob
for jar in glob.glob('/path/to/.m2/repository/io/company/*/0.2-SNAPSHOT/*-SNAPSHOT.jar'):
    with zipfile.ZipFile(jar) as z:
        if 'META-INF/jandex.idx' in z.namelist():
            data = z.read('META-INF/jandex.idx')
            if b'DeletedClassName' in data:
                print(f'Stale ref in: {jar}')
```

### Why this is non-obvious

- The deleted class has zero source-code references in the downstream module — `grep` finds nothing
- The error looks like a missing dependency, not a stale index
- `mvn clean` on the application clears the application's build output but doesn't touch `~/.m2` SNAPSHOT JARs
- Jandex indexes are binary — you can't `grep` a JAR's `jandex.idx` for text; you need to read raw bytes
