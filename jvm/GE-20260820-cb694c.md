## Symptom

Need to identify which case a `WorkItemLifecycleEvent` belongs to (e.g., to update case context when a work item reaches ESCALATED status). The event has no `caseId()` method.

## Context

`WorkItemLifecycleEvent` provides `workItemId()`, `status()`, `tenancyId()`, `callerRef()`, and `workItem()` — but no direct case ID accessor. The case ID is encoded in the `callerRef` string.

## What was tried (didn't work)

Looking for `event.caseId()` or `event.workItem().caseId()` — neither exists.

## Root cause

The engine encodes the case ID into the work item's `callerRef` via `PlanItemCallerRef.encode(caseId, planItemId)`, producing the format `case:<UUID>/pi:<planItemId>`. The work API is decoupled from the engine — it has no direct case reference.

## Fix

Use the sealed `CallerRef` interface to parse the encoded string:

```java
import io.casehub.work.engine.CallerRef;

CallerRef ref = CallerRef.parse(event.callerRef());
if (ref == null) return; // unparsable callerRef
UUID caseId = ref.caseId();
```

`CallerRef` is a sealed interface with two implementations: `PlanItemCallerRef` (format: `case:<UUID>/pi:<id>`) and `GateCallerRef` (format: `case:<UUID>/gate:<N>`). Both expose `caseId()`.

## Why this is non-obvious

The expectation is that an event about a work item linked to a case would carry the case ID directly. The indirection through `callerRef` string encoding is an API design artifact of the work module's decoupling from the engine.
