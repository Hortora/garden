## Symptom

Adding `casehub-eidos-org` (runtime scope) to a Quarkus app causes `UnsatisfiedResolutionException` for `DispositionSignalStore`, `DispositionHealth`, `DispositionEvolution`, `DispositionProfileStore` at CDI startup. These are eidos-core SPIs that the consuming app doesn't implement.

## Context

You want to use the eidos org model (`OrgStructure.define()`, `OrgRegistry`) to define agent hierarchies. The `casehub-eidos-org` runtime JAR has a Jandex index — its beans are auto-discovered. `OrgBootstrap` (an `@ApplicationScoped` startup observer) injects `OrgRegistry` and `Instance<OrgRegistrar>`. But other beans in the JAR (e.g. `OrgGoalCompiler`) inject eidos-core SPIs that the consumer doesn't provide.

## What was tried (didn't work)

1. Adding `casehub-eidos-org` at runtime scope — CDI fails with unsatisfied eidos-core injection points
2. `quarkus.arc.exclude-types` for the problematic beans — unreliable for Jandex-indexed JARs

## Root cause

`casehub-eidos-org` is a full runtime module designed for apps that use the complete eidos stack (org + core + disposition). Individual features (org model only) aren't independently consumable because the JAR's CDI graph assumes eidos-core beans are present.

## Fix

Don't use `casehub-eidos-org` (runtime). Use only the API and in-memory implementation:

```xml
<!-- API — OrgStructure DSL, OrgRegistry interface -->
<dependency>
  <groupId>io.casehub</groupId>
  <artifactId>casehub-eidos-org-api</artifactId>
</dependency>
<!-- In-memory implementation — @Alternative @ApplicationScoped -->
<dependency>
  <groupId>io.casehub</groupId>
  <artifactId>casehub-eidos-org-memory</artifactId>
  <scope>compile</scope>
</dependency>
```

Add `InMemoryOrgRegistry` to `quarkus.arc.selected-alternatives`. Call `OrgStructure.define()` directly (e.g. in a CaseHub's `augment()` method) instead of using the `OrgRegistrar` SPI — `OrgBootstrap` is in the runtime JAR you're not including.

## Why this is non-obvious

The natural expectation is that `casehub-eidos-org` is the correct runtime for org model features. The transitive eidos-core dependency is invisible until CDI startup fails — and the error messages reference types (`DispositionSignalStore`) that seem completely unrelated to agent org structure.
