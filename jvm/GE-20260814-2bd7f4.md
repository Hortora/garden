### Symptom
Need to write audit/persistence records triggered by an SPI call, but the SPI contract is synchronous and side-effect-free (no I/O, no CDI events, no JPA writes).

### Context
Engine SPIs like `PlanningStrategy.select()` are called inside a planning cycle that owns its own transactional context. Writing to a different datasource (e.g. ledger on the qhorus PU) from inside `select()` risks the dual-datasource `@Transactional` anti-pattern. Firing CDI events can trigger re-entrant evaluation cycles.

### What was tried (didn't work)
- Writing `LedgerEntry` directly inside `select()` — dual-datasource transaction conflict with the engine's planning loop.
- Firing `Event.fireAsync()` from `select()` — async observer writes context, which triggers re-evaluation of binding conditions (re-entrant cycle).
- Firing synchronous `Event.fire()` from `select()` — observer runs in the same transaction boundary, but context writes trigger side effects.

### Root cause
The SPI contract (`select()` returns `List<Binding>`) is designed as a pure filter. Audit writes are side effects that belong outside the SPI call, driven by downstream engine lifecycle events.

### Fix
Use an `@ApplicationScoped` `ConcurrentHashMap<UUID, PendingDecision>` as a bridge:

1. Inside `select()`: store the decision in the map (in-memory only — no I/O)
2. An `@ObservesAsync` observer on a downstream engine event (e.g. `WorkerDecisionEvent`) reads from the map via `take(caseId)` and writes the audit record

```java
@ApplicationScoped
public class PendingStore {
    private final ConcurrentHashMap<UUID, PendingDecision> pending = new ConcurrentHashMap<>();
    public void put(PendingDecision d) { pending.put(d.caseId(), d); }
    public PendingDecision take(UUID caseId) { return pending.remove(caseId); }
}

// In the observer (runs outside the planning cycle transaction):
void onWorkerDecision(@ObservesAsync WorkerDecisionEvent event) {
    PendingDecision d = pendingStore.take(event.caseId());
    if (d == null) return;
    ledgerRepository.save(buildEntry(d), d.tenancyId());
}
```

### Why this is non-obvious
The natural instinct is to write the audit record where the decision is made. The SPI signature gives no hint that side effects are prohibited — it's a convention enforced by the engine's internal threading and transaction model, not by the type system.
