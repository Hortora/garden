## Symptom

All `@QuarkusTest` classes fail during test discovery with `ClassSelector resolution failed` and `Could not load class`. The error appears to be a classloading issue, but the actual root cause is buried in the Quarkus bootstrap log: `Failed to resolve artifact io.casehub:casehub-eidos-eval:jar:0.2-SNAPSHOT`.

Compilation succeeds — `mvn compile test-compile` passes. Only the test runtime fails.

## Context

Multi-repo project where SNAPSHOT dependencies are built locally (`mvn install`) and also declared in a remote Maven repository (GitHub Packages). The artifact exists in `~/.m2/repository/` but was never published to the remote. `_remote.repositories` contains both entries:
```
artifact-0.2-SNAPSHOT.jar>=           # locally installed
artifact-0.2-SNAPSHOT.jar>github=     # tracked against remote
```

## What was tried (didn't work)

1. Reinstalling from source (`mvn install -pl eval -DskipTests`) — `_remote.repositories` retains the `github` entry alongside the local entry
2. Running with `-o` (offline mode) — Quarkus resolver reports "Cannot access github in offline mode and the artifact has not been downloaded from it before"
3. Deleting `.lastUpdated` files — no effect, the issue is the `_remote.repositories` tracking, not a failure cache

## Root cause

Standard Maven's dependency resolver accepts locally-installed artifacts even when `_remote.repositories` tracks them against a remote repo. Quarkus's `ApplicationDependencyResolver` (used during `@QuarkusTest` bootstrap) does NOT — it requires the artifact to be resolvable from the declared remote repository. Since the artifact was never published to GitHub Packages, the remote check fails, and Quarkus treats this as a fatal resolution error.

The blast radius is total: because Quarkus bootstraps the entire application dependency model during test discovery, ONE unresolvable artifact kills ALL `@QuarkusTest` classes in the module — not just tests that directly depend on the missing artifact.

## Fix

None known — this is an open issue. Workarounds:

1. **Publish the artifact** to the remote registry (GitHub Packages) so the remote check succeeds
2. **Run non-Quarkus tests separately** with `-Dtest=SpecificTest1,SpecificTest2` to bypass the bootstrap resolver entirely
3. **Remove the remote tracking** by deleting `_remote.repositories` AND the `resolver-status.properties` for the artifact, then reinstalling — but this is fragile and may not survive the next Maven metadata update

### Why this is non-obvious

The symptom (`ClassSelector resolution failed`) looks like a classloading or compilation error, not a dependency resolution issue. The standard Maven build passes — `compile` and `test-compile` both succeed. The actual dependency error is only visible in the Quarkus bootstrap log, which is logged at a different level and often scrolls past in the test output. Additionally, the standard Maven resolver's acceptance of locally-installed artifacts creates the expectation that `mvn install` is sufficient.

### Alternatives considered

- Removing `>github=` lines from `_remote.repositories` manually — fragile, reverts on next build
- Using a `host-m2` file:// repository — Quarkus resolver still checks the `github` remote
