# Panache named-PU: raw JPQL via getEntityManager() fails with UnknownEntityException but Panache list/count/find work

### Symptom

In a multi-PU Quarkus setup with a named persistence unit (e.g. `qhorus`), calling:

```java
repo.getEntityManager().createQuery(
    "SELECT c.obligor, COUNT(c) FROM CommitmentEntity c WHERE c.state IN ?1 GROUP BY c.obligor HAVING COUNT(c) >= ?2")
```

throws:

```
org.hibernate.query.sqm.UnknownEntityException: Could not resolve root entity 'CommitmentEntity'
```

But Panache's own methods on the same `PanacheRepositoryBase<CommitmentEntity, UUID>` work fine:

```java
repo.count("obligor = ?1 AND state IN ?2", obligor, states);  // works
repo.list("state IN ?1", states);                               // works
repo.find("obligor = ?1", obligor).firstResultOptional();       // works
```

### Context

- Multi-PU setup: `quarkus.hibernate-orm.qhorus.datasource=qhorus`
- Entity package included: `quarkus.hibernate-orm.qhorus.packages=io.casehub.qhorus.runtime`
- `CommitmentEntity` is in `io.casehub.qhorus.runtime.message` (sub-package of the configured package)
- `CommitmentPanacheRepo` has no `@PersistenceUnit` annotation — it's a plain `@ApplicationScoped` class

### What was tried (didn't work)

1. `repo.getEntityManager().createQuery(JPQL)` — `UnknownEntityException`
2. `@PersistenceUnit("qhorus") EntityManager em; em.createQuery(JPQL)` — also `UnknownEntityException`
3. `repo.list("state IN ?1", states)` + Java stream grouping — **works**

### Root cause

`PanacheRepositoryBase.getEntityManager()` returns the **default PU's** EntityManager, not the one for the named PU the entity belongs to. The default PU has no knowledge of `CommitmentEntity`.

Panache's own methods (`list`, `count`, `find`) work because they resolve the entity from the **generic type parameter** at **build time** via bytecode enhancement. They never parse entity name strings from JPQL — they already know the entity class and route to the correct PU internally.

Raw JPQL via `getEntityManager().createQuery()` goes through Hibernate's JPQL parser, which requires the entity to be registered in that specific PU's metamodel. Since `getEntityManager()` returns the default PU's EM, and the entity isn't registered there, the parser fails.

### Fix

For aggregate queries that Panache doesn't support natively (GROUP BY, HAVING, window functions), use Panache's `list()` to fetch matching entities and perform aggregation in Java:

```java
@Override
public Map<String, Long> findObligorsExceedingCount(int minCount) {
    return repo.<CommitmentEntity>list(
                    "state IN ?1", List.of(CommitmentState.OPEN, CommitmentState.ACKNOWLEDGED))
            .stream()
            .filter(c -> c.obligor != null)
            .collect(Collectors.groupingBy(c -> c.obligor, Collectors.counting()))
            .entrySet().stream()
            .filter(e -> e.getValue() >= minCount)
            .collect(Collectors.toMap(
                    Map.Entry::getKey, Map.Entry::getValue,
                    (a, b) -> a, LinkedHashMap::new));
}
```

This trades DB-level efficiency (all matching rows loaded into JVM) for correctness (Panache handles entity resolution). Acceptable for moderate data volumes; for production scale, investigate native SQL queries.

### Why this is non-obvious

Panache's built-in methods work perfectly — `list()`, `count()`, `find()` all resolve the entity correctly in the named PU. Only raw JPQL via `getEntityManager().createQuery()` fails. The inconsistency between Panache method success and JPQL failure **in the same repository class** is the trap — there's no indication that `getEntityManager()` returns a different PU's EM than the one Panache uses internally.

### Alternatives considered

- **Inject `@PersistenceUnit("qhorus") EntityManager` directly** — also failed with the same error, suggesting the entity registration issue is deeper than just which EM is returned
- **Native SQL query** — would work but bypasses JPA entity mapping and requires manual result mapping
- **Panache `list()` + Java grouping** — chosen approach; functional, testable, matches the InMemory store pattern
