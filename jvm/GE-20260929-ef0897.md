### Symptom
Compilation error: "reference to setValue is ambiguous — both method setValue(String, JsonNode) and method setValue(String, Supplier<JsonNode>) match" when passing `MAPPER.valueToTree(map)` directly as the second argument to `Scope.setValue()`.

### Context
Building a JQ expression evaluator that injects `$secret` and `$config` scope variables. The `Scope.setValue()` method has two overloads — one taking `JsonNode`, one taking `Supplier<JsonNode>`. When `ObjectMapper.valueToTree()` returns `JsonNode`, the compiler sees both overloads as applicable because `JsonNode` could match either the direct type or be wrapped in a lambda.

### Root cause
Java overload resolution ambiguity. `MAPPER.valueToTree(secretsMap)` returns `JsonNode`, which is a valid match for both `setValue(String, JsonNode)` and `setValue(String, Supplier<JsonNode>)` (the latter via lambda wrapping). The compiler cannot determine which overload the programmer intended.

### Fix
Assign the `valueToTree()` result to a local `JsonNode` variable before passing to `setValue()`:

```java
// Fails to compile — ambiguous overload
childScope.setValue("secret", MAPPER.valueToTree(secretsMap));

// Compiles — local variable disambiguates
JsonNode secretsNode = MAPPER.valueToTree(secretsMap);
childScope.setValue("secret", secretsNode);
```

The explicit local variable declaration gives the compiler enough type information to resolve to the `setValue(String, JsonNode)` overload.

### Why this is non-obvious
The `valueToTree()` return type is `JsonNode`, which should unambiguously match the `JsonNode` overload. The ambiguity only arises because `Supplier<JsonNode>` is a functional interface, and the compiler considers whether the expression could be interpreted as a lambda — even though `valueToTree()` is clearly not a lambda. The fix (assigning to a local variable) feels redundant but is the standard Java pattern for resolving this class of overload ambiguity.
