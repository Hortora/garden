### Symptom

SIGSEGV at `Ort::Env::Env(OrtLoggingLevel, char const*)+0x38` when creating a sherpa-onnx online recognizer (streaming STT). JVM crash dump shows `si_addr: 0x0000000000000018` — null pointer dereference at offset 0x18.

The crash happens inside `SherpaOnnxCreateOnlineRecognizer` → `OnlineRecognizerImpl::Create` → `Ort::Env::Env()`. The FFM downcall into native code succeeds — the crash is internal to the native library.

### Context

`~/.casehub/native/sherpa-onnx/1.13.6/osx-arm64/` contains both `libsherpa-onnx-c-api.dylib` and `libonnxruntime.dylib`. The sherpa-onnx release ships matched pairs. During a prior debug session, `libonnxruntime.dylib` (v1.27.1) was renamed to `.1.21.bak` and replaced with a v1.18.0 build.

### Root cause

sherpa-onnx is compiled against ONNX Runtime headers that define `ORT_API_VERSION = 27`. At native library load time, the C++ static initialiser calls:

```cpp
const OrtApi* Global<void>::api_ = OrtGetApiBase()->GetApi(ORT_API_VERSION);
```

ORT 1.18.0 only supports API versions [1, 18]. `GetApi(27)` prints a diagnostic to stdout — `"The requested API version [27] is not available, only API versions [1, 18] are supported in this build"` — then returns NULL.

Subsequent code dereferences the null API table:

```cpp
inline const OrtApi& Ort::GetApi() noexcept { return *Global<void>::api_; }
// api_ is NULL → CreateEnv dereferences at offset 0x18 → SIGSEGV
```

### What was tried (didn't work)

1. Changed CDI scope from `@ApplicationScoped` to `@Singleton` + startup observer — moved the crash to startup but didn't fix it.
2. Suspected ARM64 ORT thread-safety (per GE-20260803-e363e6) — valid secondary concern but not the primary cause.
3. Checked `--enable-native-access=ALL-UNNAMED` in JVM args — present in pom.xml but absent from actual command line; however, FFM calls executed successfully (crash was inside native code, not at the Java/native boundary).

### Fix

Restore the matching `libonnxruntime.dylib` that shipped with sherpa-onnx 1.13.6:

```bash
# The backup contained ORT 1.27.1 (misnamed as .1.21.bak)
mv ~/.casehub/native/sherpa-onnx/1.13.6/osx-arm64/libonnxruntime.dylib \
   ~/.casehub/native/sherpa-onnx/1.13.6/osx-arm64/libonnxruntime.dylib.1.18.wrong
mv ~/.casehub/native/sherpa-onnx/1.13.6/osx-arm64/libonnxruntime.dylib.1.21.bak \
   ~/.casehub/native/sherpa-onnx/1.13.6/osx-arm64/libonnxruntime.dylib
```

Verify the version string: `strings libonnxruntime.dylib | grep -E '^1\.[0-9]+\.[0-9]+$'` should show `1.27.1`.

### Why this is non-obvious

The ORT diagnostic message (`"The requested API version [27] is not available"`) is printed to stdout by the native library *before* returning NULL. But the crash was happening on a Vert.x worker thread — whose stdout was not being monitored. The JVM crash dump (`hs_err_pid*.log`) shows the SIGSEGV stack trace but NOT the ORT diagnostic.

The error only surfaced when the crash was moved to the main thread (via a CDI `@Observes StartupEvent` eager init), where Quarkus captures stdout. Without that detour, the symptom (SIGSEGV in `Ort::Env::Env`) looked identical to the ARM64 concurrent-access bug documented in GE-20260803-e363e6, leading the investigation down the wrong path.

### Alternatives considered

- **Thread serialisation only** — would not fix the crash because the library version mismatch causes NULL regardless of threading.
- **Downgrade sherpa-onnx to match ORT 1.18** — would require finding an old sherpa-onnx build compiled against API v18; impractical and loses features.
- **Build ORT 1.27.1 from source** — the backup file already contained the correct version, making this unnecessary.

### Caveats

- The backup file was named `.1.21.bak` but actually contained ORT 1.27.1 — always verify with `strings` rather than trusting filenames.
- sherpa-onnx release archives ship matched `libonnxruntime.dylib` + `libsherpa-onnx-c-api.dylib` pairs. Never swap one without the other.
- The eager CDI init (startup observer) is retained as defense-in-depth against the separate ARM64 thread-safety bug (GE-20260803-e363e6), even though it wasn't the primary fix here.
