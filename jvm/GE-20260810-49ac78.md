### Symptom
Case stalls after SLA breach policy returns `BreachDecision.Exhausted`. The WorkItem reaches `ESCALATED` status (terminal), but the case context is never updated — the PlanItem stays `DELEGATED` forever.

### Context
Implementing SOC SLA breach policy. When all escalation tiers are exhausted, the policy returns `Exhausted`. The work module sets `WorkItemStatus.ESCALATED`. The engine's `PlanItemCompletionApplier` is called but does nothing.

### Root cause
`PlanItemCompletionApplier.applyStatus()` had no `case ESCALATED:` in its switch statement. It hit `default`, logged a warning, returned `false` — and the output mapping was never applied.

```java
// Before fix — ESCALATED hits default:
switch (status) {
    case COMPLETED: item.markCompleted(); break;
    case REJECTED:  item.markRejected(); break;
    case FAULTED:   item.markFaulted(); break;
    case EXPIRED:   item.markFaulted(); break;
    // ... no ESCALATED case
    default: LOG.warnf("Unhandled..."); return false;
}
```

### Fix
Fixed in casehubio/work#341. Added `case ESCALATED: item.markFaulted(); break;` to the switch.

Application-side complementary fix: the YAML binding's `outputMapping` must handle null outcome (no analyst selected one during ESCALATED):

```yaml
outputMapping: >-
  { analystDecision: (if .outcome == null then "escalated" else ... end) }
```

### Why this is non-obvious
`BreachDecision.Exhausted` was added to the sealed interface (GE-20260604-work) but the engine adapter's status handler was never updated to process the corresponding `WorkItemStatus.ESCALATED`. The WorkItem status enum and the PlanItem status handler are in different modules with no compile-time coupling.
