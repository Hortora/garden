## Symptom

After DTW retrieval returns similar past game timelines, re-running
`DtwSimilarity.compute()` to extract the alignment path always maps the
last query observation to the last case observation — even when the query
is a 3-minute prefix and the case is a 10-minute full game. There is no
"lookahead window" after the alignment point because the alignment point
IS the end of the case.

## Context

CBR temporal matching: query with a partial game timeline (live game, first
N minutes) against stored full-game timelines. Goal: find where the current
game aligns in similar past games, then extract what happened NEXT (the
lookahead) as a prediction.

The spec assumed DTW alignment would give a subsequence match point — "the
last query step maps to step s_k in the past game, and steps after s_k are
the prediction." This assumption is wrong for standard DTW.

## Root cause

Standard DTW forces full endpoint alignment. The cost matrix starts at
`cost[0][0] = 0` and the optimal path ends at `cost[n][m]`. The backtrace
always starts at `(n, m)` — meaning the last query element (index n-1)
maps to the last case element (index m-1). This is by mathematical
definition, not a bug.

Subsequence DTW (open-end DTW) allows the query to match a subsequence of
the case by initialising the first row to zero and finding the minimum in
the last row. Standard DTW does not do this.

## Fix

Separate the two concerns:
- **DTW score** tells you WHICH past games are similar to the current trajectory
- **Timestamp matching** tells you WHERE you are in those games

After DTW retrieval ranks similar games, use a simple timestamp lookup to
find the alignment point:

```java
private static int findClosestTimestampIndex(
        List<Map<String, FeatureValue>> timeline, double targetMinute) {
    int closest = 0;
    double minDiff = Double.MAX_VALUE;
    for (int i = 0; i < timeline.size(); i++) {
        double minute = ((FeatureValue.NumberVal) timeline.get(i).get("minute")).value();
        double diff = Math.abs(minute - targetMinute);
        if (diff < minDiff) { minDiff = diff; closest = i; }
    }
    return closest;
}
```

Then the lookahead window is `caseTimeline[alignmentIdx + 1 .. alignmentIdx + N]`.

## Why this is non-obvious

The DTW alignment path looks like exactly the right tool for subsequence
matching — it maps each query step to a case step. A developer would
naturally assume the last alignment pair gives the "current position" in
the longer sequence. The math says otherwise: both endpoints are always
anchored.

### Why this fix

Timestamp matching is simple, correct, and avoids the need for a
subsequence DTW implementation. Since the timelines use real-time
timestamps (game minutes), the closest-timestamp lookup gives the same
alignment point that subsequence DTW would produce — without the
algorithmic complexity.

### Alternatives considered

- **Subsequence DTW** — initialize first row of cost matrix to zero, find
  minimum in last row. Correct but requires modifying the DTW implementation
  or adding a new mode to the library. Rejected: timestamp matching is
  simpler and the library doesn't expose subsequence mode.
- **Truncate stored cases to query length** — only DTW-compare the first N
  steps. Loses the full-game similarity signal (a game that diverges after
  minute 3 scores the same as one that stays similar for 10 minutes).
