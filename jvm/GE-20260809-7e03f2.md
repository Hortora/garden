### Symptom

`ReconciliationLoop.casRetryMutations` fails with `DanglingDependencyException` under concurrent graph modifications when fault policies return `AddDependency` mutations alongside `AddNode` mutations.

### Context

The CAS retry loop in `ReconciliationLoop` applies accumulated fault mutations to the latest graph version. Its invariant: *"Mutations are graph-structural and safely re-applicable to any graph version."* This held when fault policies returned only `AddNode` mutations — adding a node is idempotent regardless of graph version.

When `FaultPolicy.addReviewNode()` was updated to return `[AddNode, AddDependency]` (review node + dependency edge to the faulted node), the invariant broke.

### What was tried (didn't work)

1. **Leaving withDependency strict** — `AddNode` succeeds (idempotent), then `AddDependency` throws because the faulted node was removed by a concurrent thread between evaluation and CAS application. Exception propagates unhandled, fault counter already incremented but mutations not applied.

### Root cause

`ImmutableDesiredStateGraph.withDependency()` validated that both endpoint nodes exist and threw `DanglingDependencyException` if either was missing. This is correct for graph construction (factory.of) but breaks CAS retry safety — the graph may have changed between fault evaluation and mutation application.

### Fix

Make `withDependency()` return `this` (no-op) when either endpoint node is absent:

```java
if (!nodes.containsKey(from) || !nodes.containsKey(to)) {
    return this;
}
```

Move the strict validation to `DefaultDesiredStateGraphFactory.of()` — construction-time validation is preserved, CAS retry safety is restored.

### Why this is non-obvious

The CAS retry invariant was implicit — documented only as a code comment. Adding `AddDependency` to the fault policy path seemed safe because `FaultPolicyEngine` already handled dependency mutations separately. The failure only manifests under concurrent graph modification — a race condition between fault evaluation and CAS application that's invisible in single-threaded tests.

### Why this fix

Splitting validation between factory (strict) and mutation (permissive) preserves both guarantees without adding a flag parameter or a separate method. The factory catches programming errors at construction time; the mutation method is safe for optimistic concurrency.

### Alternatives considered

- **Filter stale mutations in the CAS loop** — rejected because the loop is mutation-type-agnostic and adding type-specific filtering would break its generality.
- **Add a `strictMode` parameter to withDependency** — rejected as API pollution; the two call sites (factory vs CAS) have clear split points.
