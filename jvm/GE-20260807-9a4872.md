### Symptom
NullPointerException during JSON serialization of a Java record. The stack trace points to a `@JsonProperty` method calling `.get()` on a null record component — but the method works fine for locally-constructed instances.

### Context
A Java record has a `@JsonIgnore`-annotated component (e.g. an internal metadata map not meant for the JSON response). Derived `@JsonProperty` methods are added to expose computed values from that component. The record is both constructed locally (where the component is always populated) and deserialized from external JSON (e.g. federated API responses).

### What was tried (didn't work)
Assumed the methods were correct because they worked for all locally-constructed instances. Looked for serialization configuration issues. The federation integration test (which deserializes upstream JSON) was the only failure — misleading toward a test setup problem rather than a null-safety issue.

### Root cause
`@JsonIgnore` on a record component tells Jackson to skip that field during deserialization. But Java records use a canonical constructor — Jackson must provide a value for every parameter. For ignored components, Jackson passes `null`. Since records are immutable, the null is permanent. Any `@JsonProperty` method that dereferences the ignored component without null-checking will NPE — but only for deserialized instances, never for locally-constructed ones.

### Fix

Null-guard every derived `@JsonProperty` method that references a `@JsonIgnore`-annotated component:

```java
public record SearchResult(
        String id,
        String title,
        @JsonIgnore Map<String, String> metadata) {

    // BAD — NPE when deserialized from external JSON
    @JsonProperty
    public String author() { return metadata.get("author"); }

    // GOOD — null-safe for deserialized instances
    @JsonProperty
    @JsonInclude(JsonInclude.Include.NON_NULL)
    public String author() { return metadata != null ? metadata.get("author") : null; }
}
```

### Why this is non-obvious
1. The NPE stack trace points to serialization, not deserialization — debugging starts in the wrong place
2. The code works perfectly for locally-constructed instances (explicit constructors default to `Map.of()`)
3. `@JsonIgnore` reads as "skip this field" but its effect on record canonical constructors (injecting null rather than a default) is unintuitive
4. The bug only surfaces when the same record type is both constructed locally AND deserialized from external JSON — a pattern common in federated/multi-service architectures
