### Symptom

`IllegalArgumentException: "solution must not be blank"` when constructing a `FeatureVectorCbrCase` with an empty string `""` as the solution field.

### Context

Using `CbrCaseMemoryStore` to persist data that isn't a problem/solution episode — e.g., user behavioral profiles, agent metadata, or annotation records. The data maps naturally to features but has no meaningful "solution" text. The constructor requires both `problem` and `solution` to be non-null AND non-blank.

### What was tried (didn't work)

- Passing `""` (empty string) as solution — fails the `isBlank()` check in the compact constructor
- Passing `null` — fails the `requireNonNull` check
- Looking for a `FeatureVectorCbrCase.of()` factory that omits solution — none exists

### Root cause

`FeatureVectorCbrCase` is a record designed for the CBR episodic pattern (problem → solution → outcome). Its compact constructor validates: `Objects.requireNonNull(solution)` then `if (solution.isBlank()) throw`. There is no constructor overload or factory method that omits the solution field. The validation is intentional for the episodic use case but makes the type awkward for non-episodic storage.

### Fix

Use a placeholder string like `"-"` for the solution field:

```java
var cbrCase = new FeatureVectorCbrCase(
    summaryText, "-", null, null, features, null, producerAgentId);
```

The placeholder passes validation and is semantically inert — retrieval similarity operates on features, not on the solution text. The `problem` field carries the meaningful text (profile summary, entity description).

### Why this is non-obvious

The `FeatureVectorCbrCase` record has 7 constructor parameters. A developer storing non-episodic data would naturally try empty string for unused fields — that's the standard Java idiom for "not applicable." The runtime validation rejects this silently at construction time, not at store time, so the error surfaces immediately but the cause (blank check on a field you consider irrelevant) is not intuitive.

### Alternatives considered

- Creating a custom `CbrCase` implementation without solution validation — adds a new type to maintain and diverges from the platform's standard case representation
- Using a `UserProfileStore` SPI that hides the CbrCase convention internally — this is the recommended approach (blocks `CbrUserProfileStore` does this), but the placeholder is still needed inside the adapter
