### Symptom
Adding a `DataStore<OuterClass.InnerRecord>` to a Drools Rule Unit compiles
successfully in Java and shows no IntelliJ errors. The DRL
`import com.example.OuterClass.InnerRecord` is valid DRL syntax.

At Quarkus augmentation time (test or dev boot), the build fails:
```
KieMemoryCompilerException: cannot find symbol
  symbol:   class OuterClass$InnerRecord
  location: package com.example
```

### Context
Occurs when a public record (or class) nested inside a CDI bean is used as
the generic type parameter of a Drools `DataStore<T>` field on a Rule Unit.
The DRL import resolves correctly in the IDE but the Kie memory compiler
generates Java source using `OuterClass$InnerRecord` notation, which the
in-memory javac cannot resolve.

### What was tried (didn't work)
- `import com.example.OuterClass.InnerRecord` in DRL — valid DRL syntax but codegen still fails
- `mvn clean` to force regeneration — same error
- Checking Jandex index — the nested class IS indexed (the outer class is `@ApplicationScoped`)

### Root cause
The Drools Quarkus deployment extension (`DroolsAssetsProcessor#generateSources`)
generates Java source files that reference the nested type using JVM internal notation
(`OuterClass$InnerRecord`) instead of Java source notation (`OuterClass.InnerRecord`).
The KieMemoryCompiler compiles these generated sources with an in-memory javac that
cannot resolve the `$` separator — it's valid in `.class` file names but not in Java
source code.

### Fix
Promote the nested record to a top-level type in its own file:

```java
// Before — fails at Drools codegen
public class StrategyTaxonomy {
    public record SignatureSpec(...) {}  // nested
}
// DataStore<StrategyTaxonomy.SignatureSpec> — KieMemoryCompiler: cannot find symbol

// After — works
public record SignatureSpec(...) {}  // top-level file
// DataStore<SignatureSpec> — codegen succeeds
```

### Why this is non-obvious
The error only surfaces at Quarkus augmentation time — Java compilation passes,
IntelliJ shows no errors, and the DRL import syntax is correct. The generated
source files in `target/generated-sources/drools/` show the `$` notation but
are not normally inspected. A developer would reasonably expect nested public
records to work as DataStore type parameters since they work everywhere else
in Quarkus CDI.

### Why this fix
The alternative — patching the Drools codegen to use `.` instead of `$` — is
an upstream fix. Promoting to a top-level type is the only application-level
workaround and has no architectural downsides (the nested record was a
convenience, not a design requirement).

### Alternatives considered
- Patching Drools codegen upstream — correct long-term fix but not actionable for the current project
- Using a wrapper class as the DataStore type — adds unnecessary indirection
- Keeping the nested class and using a different fact insertion mechanism — Drools Rule Units require DataStore, no alternative path
