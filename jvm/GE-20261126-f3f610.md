### Symptom

Two deployment modules both register `SyntheticBeanBuildItem` for the same bean type (e.g. `TtsModelRegistry`, `AvatarConfigBean`). No build error — Quarkus happily registers both. At runtime, `@Inject` of that type throws ambiguous dependency resolution.

### Context

Common pattern: a deployment module guards bean registration with `hasAppBean()`:

```java
private static boolean hasAppBean(BeanDiscoveryFinishedBuildItem beanDiscovery, Class<?> beanType) {
    return !beanDiscovery.beanStream()
            .withBeanType(beanType)
            .filter(b -> !b.isDefaultBean() && !b.isSynthetic())
            .collect()
            .isEmpty();
}
```

This guard filters out both `@DefaultBean` and synthetic beans — it only detects **app-provided** beans. When two deployment modules both use this guard and both register synthetic beans for the same type, neither sees the other's registration, and both proceed.

### Root cause

`!b.isSynthetic()` in the guard deliberately excludes synthetic beans from the check. The intent is "skip registration if the app already provides this bean." But it also means two deployment modules' synthetic beans are invisible to each other.

### Fix

Consolidate discovery and bean registration into a single deployment module. Have the other module consume the shared `BuildItem` instead of doing its own discovery:

```java
// Module A produces the build item
@BuildStep
AvatarConfigBuildItem discoverAvatarConfig() { ... }

// Module B consumes it — no duplicate discovery, no duplicate beans
@BuildStep
List<SyntheticBeanBuildItem> registerSpeechBeans(AvatarConfigBuildItem config) { ... }
```

The alternative — removing `!b.isSynthetic()` from the guard — would break the common pattern where a default-priority synthetic bean should be overridable by another synthetic bean.

### Why this is non-obvious

The guard pattern looks correct and is widely used in Quarkus extensions. The failure only surfaces when two independently-developed deployment modules happen to register the same bean type, which typically only happens during consolidation or modularisation work. There's no build-time error — the ambiguity only appears at runtime injection.
