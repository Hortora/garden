## Symptom

Thread count grows unboundedly in a long-running process with WebSocket reconnection logic. No errors, no warnings — just silent accumulation of executor threads.

## Context

When building a WebSocket client with automatic reconnection (exponential backoff loop), creating a new `HttpClient` per connection attempt seems natural — fresh client for a fresh connection. But each `HttpClient.newBuilder().build()` allocates its own internal thread pool (executor). When the old client is abandoned without being closed, its thread pool stays alive.

## What was tried (didn't work)

- Creating `HttpClient` inside the reconnect loop — appeared to work but leaked threads on every reconnection cycle.

## Root cause

`HttpClient` allocates an internal `Executor` (thread pool) when none is provided via `.executor()`. This executor is never cleaned up when the `HttpClient` reference is dropped. In Java 21+, `HttpClient` implements `AutoCloseable`, but the close must be called explicitly.

## Fix

Hoist the `HttpClient` to a field — create once, reuse across reconnections:

```java
// Field-level — created once, closed on shutdown
private final HttpClient httpClient = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(10))
        .build();

private void connectLoop() {
    while (running.get()) {
        try {
            webSocket = httpClient.newWebSocketBuilder()
                    .buildAsync(URI.create(wsUrl), new Listener())
                    .join();
            // ...
        }
    }
}

public void disconnect() {
    running.set(false);
    httpClient.close(); // Java 21+ AutoCloseable
}
```

## Why this is non-obvious

No error or warning is produced. The leaked threads are daemon threads, so the process doesn't hang on shutdown. The leak is only visible via thread dumps or monitoring — and only after many reconnection cycles, which may take hours or days in production.
