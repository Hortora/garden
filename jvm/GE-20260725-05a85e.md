# Shared algorithm contract widening — activating a previously-ignored parameter silently breaks callers

### Symptom / Context

`ScoreFusion.rrf()` accepted `ScoredLeg.weight()` as a record field but ignored it — all legs contributed equally via `1/(k + rank + 1)`. When the algorithm was updated to multiply by `leg.weight()`, a downstream caller (`QdrantCbrCaseMemoryStore.fuseAndScore()`) silently regressed: it passed CC-derived weights (0.3, 0.15, etc.) computed for a different fusion strategy. Under the old code these were harmless; under the new code they skewed RRF rankings.

### Root cause

The `weight` field was part of the `ScoredLeg` record from the start, but `rrf()` never used it. Callers treated it as "CC-only metadata" and passed CC-derived values unconditionally. When `rrf()` started respecting the field, the implicit contract changed without any compile-time signal.

### Fix

Caller-side guard: when `fusionStrategy == RRF`, construct all legs with `weight=1.0` regardless of what CC weights would compute. This preserves the pre-change equal-contribution behavior.

```java
boolean useEqualWeights = query.fusionStrategy() == FusionStrategy.RRF;
double featureWeight = useEqualWeights ? 1.0 : (1.0 - query.vectorWeight());
```

The general pattern: **when activating a previously-ignored parameter in a shared algorithm, grep all callers and add guards where the new behavior would change existing semantics.**

### Why this is non-obvious

The field already existed on the record — no API signature changed, no deprecation warning fired, no compilation error surfaced. The developer "just made the code use a field it already had." The regression was caught by adversarial design review, not tests, because the old tests passed (they used weight=1.0 which produces identical results under both old and new algorithms).

### Why this fix

Fixing at the caller (guard) rather than the algorithm (special-casing RRF to ignore weights) preserves the algorithm's generality. The algorithm correctly uses weights; callers that don't want weighting explicitly pass equal weights. This scales to future callers who may genuinely want weighted RRF.

### Alternatives considered

- **Algorithm-side guard** (if strategy == RRF, ignore weights inside `rrf()`): rejected because it couples the algorithm to domain-specific strategy concepts and prevents legitimate weighted RRF use cases.
- **Separate `rrfUnweighted()` method**: rejected — API duplication for what is a caller responsibility.
