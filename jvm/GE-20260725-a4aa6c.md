### Symptom
Downstream validation fails with "unknown X" errors (e.g. "references unknown
template: style-guide") even though registrar beans exist on the classpath and
would provide the missing content.

### Context
A `CdiTemplateRegistry` bean uses `@PostConstruct` to discover
`Instance<TemplateRegistrar>` CDI beans and register their templates. An
`InMemoryTemplateRegistry` bean with `@Alternative @Priority(1)` replaces it
in tests. The alternative starts with an empty store — no `@PostConstruct`,
no registrar discovery.

When `AgentDescriptorBootstrap` validates descriptor template refs against
the injected `TemplateRegistry`, it sees the empty alternative and rejects
all refs.

### What was tried (didn't work)
1. Assumed the alternative would inherit or delegate the `@PostConstruct`
   behaviour — it doesn't. CDI alternatives fully replace the bean; no
   lifecycle method delegation occurs.
2. Tried having `CdiTemplateRegistry` delegate to `new InMemoryTemplateRegistry()`
   — failed because the runtime module doesn't depend on persistence-memory.

### Root cause
CDI `@Alternative` fully replaces the original bean. The `@PostConstruct` on
`CdiTemplateRegistry` never fires because that bean is never instantiated.
The alternative must independently implement the same self-population logic.

### Fix
Add `@PostConstruct` + `Instance<TemplateRegistrar>` discovery to the
alternative bean:

```java
@Alternative @Priority(1) @ApplicationScoped
public class InMemoryTemplateRegistry implements TemplateRegistry {

    @Inject @Any Instance<TemplateRegistrar> registrars;

    @PostConstruct void init() {
        if (registrars != null) {
            for (var r : registrars) {
                r.templates().forEach(this::register);
            }
        }
    }
    // ... register(), resolve(), all() as before
}
```

### Why this is non-obvious
The `@Alternative` documentation focuses on type replacement — it doesn't
warn that lifecycle methods (`@PostConstruct`) on the replaced bean are lost.
Developers expect "alternative = same contract, different implementation" but
the contract here includes self-population behaviour that isn't part of the
interface.
