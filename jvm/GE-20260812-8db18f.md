### Symptom
Runtime error (`TypeError: e.onTitlebarDoubleClick is not a function`) after
manually copying newer dist files into the `.casehub-packages/` portal
directory and rebuilding with `mvn package`. The build succeeds but the
bundle contains the old code.

### Context
Project uses Maven `dependency:unpack` to extract an NPM package artifact
(`casehub-pages-npm-0.2-SNAPSHOT.jar`) into a Yarn Berry `portal:` resolution
directory (`.casehub-packages/packages/pages-runtime/dist/`). When the
published SNAPSHOT is stale but the source repo has newer modules, manually
copying dist files into the portal is the natural workaround.

### What was tried (didn't work)
1. Copied newer `.js`/`.d.ts` files from the source repo into the portal directory
2. Ran `mvn package` — Maven printed "already unpacked" suggesting files were preserved
3. Build succeeded with no errors — esbuild bundled without complaints
4. Runtime: `TypeError` on a method that exists in the copied files but not in the artifact

### Root cause
Maven's `dependency:unpack` with `overWrite=false` (the default for SNAPSHOT jars)
checks the jar timestamp against a marker file, not individual extracted files. When
it decides to re-extract (or when the marker is missing), it extracts the full jar
content, overwriting all files in the target directory — including manually added ones.
The "already unpacked" message means "the jar hasn't changed since last extraction",
not "your files are untouched." But even when it doesn't re-extract, the esbuild
bundle may resolve from a cached intermediate rather than the portal directory.

### Fix
Don't manually copy files into the portal directory. Instead, publish a new SNAPSHOT
of the NPM artifact from the source repo before consuming it:

```bash
# In the source repo (e.g. casehub-pages)
yarn build
mvn deploy -pl packages/pages-npm -DskipTests

# Then in the consumer repo
mvn dependency:unpack -U  # force re-download
mvn package
```

If you can't publish (no deploy rights, CI-only), use a local install:
```bash
mvn install:install-file -Dfile=casehub-pages-npm-0.2-SNAPSHOT.jar \
  -DgroupId=io.casehub -DartifactId=casehub-pages-npm -Dversion=0.2-SNAPSHOT \
  -Dpackaging=jar
```

### Why this is non-obvious
The "already unpacked" message creates false confidence that manual copies survived.
The build succeeds because esbuild resolves type declarations from the portal (which
may have the new `.d.ts` files) but bundles JavaScript from a different resolution
path or cache. The error only surfaces at runtime, in a minified stack trace, with
no connection to the stale artifact.
