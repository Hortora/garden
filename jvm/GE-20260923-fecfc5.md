# Micrometer timer for cold Mutiny Multi streams must use deferred + onTermination

### Symptom

Timer records near-zero duration when wrapping a `Multi<T>` return value — the timer measures method-call-to-return, not the actual stream processing time.

### Context

When instrumenting an SPI that returns `Multi<AgentEvent>` (cold reactive stream), wrapping the method call with `Timer.Sample` captures only the time to create the `Multi` object — not the time from subscription to stream completion.

### Root cause

`Multi` is a cold stream — it doesn't execute until subscribed. `Timer.start()` before the method call and `sample.stop()` after it measures object creation (~0ms), not stream execution.

### Fix

Use `Multi.createFrom().deferred()` to start the timer on subscription, and `onTermination()` to stop it on completion, failure, or cancellation:

```java
public Multi<AgentEvent> invoke(AgentSessionConfig config) {
    return Multi.createFrom().deferred(() -> {
        counter.increment();
        Timer.Sample sample = Timer.start();
        return delegate.invoke(config)
                .onTermination().invoke(() -> sample.stop(timer));
    });
}
```

Key points:
- `deferred(() -> ...)` — the lambda runs on subscription, not on method call. Timer starts when the stream actually begins.
- `onTermination()` — fires on completion, failure, AND cancellation. All three paths stop the timer.
- `Timer.start()` without a registry argument uses the clock from the registry the timer was registered with.
- The counter increment is inside `deferred` too — it counts actual invocations, not Multi object creations.

### Why this is non-obvious

The naive approach (wrap the method call) looks correct and passes basic tests — the timer records a value, it's just wrong. The bug only surfaces under load or when comparing timer values to wall-clock observations. Most Micrometer examples show blocking method instrumentation where this distinction doesn't exist.
