# CDI-discovered functional interfaces with implicit category: all-instances × all-categories iteration requires self-filtering

## Stack

Java 21, Jakarta CDI, Quarkus

## Symptom

An orchestrator iterates all CDI-discovered `DriveGoalMapper` implementations
for all above-threshold drive axes. Each mapper receives `DriveIntensity`
parameters for axes it wasn't designed for. A curiosity mapper called with
COMPETENCE intensity silently returns a CURIOSITY proposal carrying the
COMPETENCE intensity value (0.9 instead of 0.3). Priority ranking by
intensity then selects the wrong proposals.

No error. No exception. The proposals look valid — only the `driveIntensity`
field is wrong.

## Context

CDI `Instance<DriveGoalMapper>` discovers all implementations. The
orchestrator doesn't know which mapper handles which axis — the SPI is a
generic `@FunctionalInterface` without axis metadata. The natural iteration
pattern is:

```java
for (DriveIntensity intensity : aboveThresholdAxes) {
    for (DriveGoalMapper mapper : mappers) {
        DriveGoalProposal proposal = mapper.evaluate(agentId, tenantId, intensity);
        if (proposal != null) proposals.add(proposal);
    }
}
```

This calls every mapper with every axis intensity. Each mapper reads its own
source orchestrator and always returns its own axis type — but uses whatever
intensity value was passed.

## Root cause

The SPI doesn't declare which category (axis) each implementation handles.
The all-mappers × all-axes loop is correct for CDI discovery, but each
mapper must self-filter by checking the incoming category parameter.

## Fix

Each mapper checks `intensity.axis()` at the top of `evaluate()`:

```java
public @Nullable DriveGoalProposal evaluate(String agentId, String tenantId,
                                             DriveIntensity intensity) {
    if (intensity.axis() != DriveAxis.CURIOSITY) return null;
    // ... actual evaluation
}
```

This is a one-line guard per implementation. The nested loop pattern stays
unchanged — self-filtering is the contract.

## Why this is non-obvious

The pattern looks correct at a glance: iterate all active drives, evaluate
all mappers, collect non-null proposals. Each mapper returns proposals for
its own axis regardless of input, so the axis in the output is always
correct. The bug is only in the numeric intensity value — a field that's
easy to overlook because it's plausible at any value in [0, 1].

### Alternatives considered

- Map each mapper to its axis at registration time (e.g., `Map<DriveAxis, DriveGoalMapper>`).
  Rejected: requires the SPI to declare its axis, breaking the generic functional interface pattern.
- Add a `DriveAxis axis()` method to the SPI. Rejected: couples every implementation to
  axis identity when some mappers might intentionally be cross-axis in the future.
