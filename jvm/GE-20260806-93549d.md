## Quarkus Arc silently skips @PostConstruct on CDI @Decorator beans

**ID:** GE-20260806-93549d
**Stack:** Quarkus 3.36.x, quarkus-arc
**Symptom:** A CDI `@Decorator` bean is active and correctly intercepts method calls on the decorated interface, but `@PostConstruct` and `@PreDestroy` lifecycle callbacks on the decorator are never invoked. No error, no warning — completely silent.
**Context:** Any Quarkus application using CDI `@Decorator` beans that rely on `@PostConstruct` for initialization (e.g. opening database connections, resolving config, registering listeners). The decorator appears completely broken because its initialization never runs, even though method interception works fine.

### What was tried (didn't work)
- Adding `@PostConstruct` to the decorator class — method never called
- Adding `@PreDestroy` to the decorator class — method never called
- Adding logging to the lifecycle methods to verify — nothing appears in logs
- Checking if the decorator is actually discovered (it is — method interception works)

### Root cause
Quarkus Arc does not invoke `@PostConstruct` or `@PreDestroy` lifecycle callbacks on `@Decorator` beans. This is a deliberate (or at least known) limitation of the Arc CDI implementation. The decorator subclass generated by Arc handles method delegation but does not wire up lifecycle callback invocation. Standard CDI beans get lifecycle support; decorators do not.

### Fix
Use one of two workarounds:

1. **Lazy initialization in decorated methods** — check if initialized on first method call and initialize then:

```java
@Decorator
@Priority(100)
public class MyDecorator implements MyService {
    @Inject @Delegate MyService delegate;

    private volatile boolean initialized = false;

    private void ensureInitialized() {
        if (!initialized) {
            // do initialization work here
            initialized = true;
        }
    }

    @Override
    public Result doWork() {
        ensureInitialized();
        return delegate.doWork();
    }
}
```

2. **Move initialization to the @Produces site** — wrap the bean in the producer method instead of using a decorator (see GE-20260806-842ee0 for the full pattern).

### Why this is non-obvious
The CDI spec says `@PostConstruct` should be called on managed beans after dependency injection. `@Decorator` beans ARE managed beans in the CDI model. A developer reading the spec would expect lifecycle callbacks to work. The fact that Arc silently skips them — without any warning or error — makes this particularly insidious. The decorator intercepts calls successfully, so it clearly exists as a bean, yet its lifecycle is incomplete.

### Why this fix
Lazy initialization in decorated methods is the simplest workaround when the decorator is the right architectural choice. Moving to a `@Produces`-site wrapper (Entry GE-20260806-842ee0) is better when initialization is complex or conditional, but requires restructuring the bean wiring.
