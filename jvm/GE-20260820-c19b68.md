## Symptom

`CbrCaseMemoryStore.retrieveSimilar()` returns memories from all agents in the domain, not just the querying agent. No error — the query succeeds but results include other agents' data.

## Context

Building agent-scoped memory operations (e.g., memory hygiene, personality evolution) where each agent should only process its own memories. `CbrQuery` has extensive `withX()` builder methods (`withMinSimilarity`, `withFilter`, `withWeights`, `withTemporalDecay`, `withScope`, `withScopeDecay`, `withRetrievalMode`, `withFusionStrategy`) suggesting comprehensive query expressiveness.

## What was tried (didn't work)

- Looking for `withProducerAgentId()` on `CbrQuery` — does not exist
- Using `withFilter()` with `CbrFilter` — filters operate on `FeatureValue` feature fields, not on `CbrCase` metadata fields like `producerAgentId`

## Root cause

`CbrQuery` is designed for similarity search over feature vectors, not identity filtering. `producerAgentId` is a metadata field on `CbrCase` (default method returning `null`, overridden by `FeatureVectorCbrCase`), not a queryable dimension. The `CbrFilter` sealed interface only supports feature-level predicates (`Contains`, `ContainsAll`, `HasMatch`, etc.).

## Fix

Post-filter `retrieveSimilar` results in Java:

```java
List<ScoredCbrCase<CbrCase>> memories = store.retrieveSimilar(query, CbrCase.class);

var agentMemories = memories.stream()
    .filter(m -> agentId.equals(m.cbrCase().producerAgentId()))
    .toList();
```

This is acceptable for bounded batch operations (memory hygiene, periodic maintenance). For high-frequency hot-path queries, consider storing `producerAgentId` as a feature value and using `withFilter()`.

## Why this is non-obvious

The 16 `withX()` builder methods on `CbrQuery` create a strong expectation that any query constraint can be expressed through the builder API. A developer building agent-scoped operations naturally expects `withProducerAgentId()` to exist alongside `withMinSimilarity()` and `withFilter()`. The absence is silent — no deprecation, no "use this instead" hint. The `CbrFilter` API looks like it might work but operates on a different level (feature values, not case metadata).

### Alternatives considered

- Storing `producerAgentId` as a `FeatureValue.StringVal` feature and filtering via `CbrFilter.contains()` — works but duplicates data already on the case record and couples the query to a specific feature key name
- Using `CbrQuery.withScope()` with agent-specific paths — scope is for hierarchical data partitioning, not identity filtering; misusing it conflates two concerns
