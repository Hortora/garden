### Symptom
`@QuarkusTest` fails with `UnsatisfiedResolutionException` for beans defined in a sibling Maven module (e.g. `quarkmind-core`), but only after `mvn clean`. Incremental builds work because the Quarkus augmentation cache retains the bean graph from a previous full build.

### Context
Multi-module Maven project where module A (`quarkmind-sc2`) depends on module B (`quarkmind-core`). Module B contains `@ApplicationScoped` beans but has no `beans.xml`, no Jandex index, and is not listed in module A's `quarkus.index-dependency.*` properties. Quarkus CDI discovers beans via Jandex indexing — without an explicit index, sibling module beans are invisible to the augmentation step.

### What was tried (didn't work)
- Running `mvn clean` then `mvn test` — fails with `UnsatisfiedResolutionException`
- Assuming Quarkus automatically indexes sibling modules in the same reactor — it does not
- Looking for `beans.xml` or Jandex plugin in the sibling module — neither present

### Root cause
Quarkus uses Jandex to discover CDI beans. For dependencies outside the application module, beans are only discovered if: (1) the dependency has a `META-INF/jandex.idx` (produced by `jandex-maven-plugin`), (2) the dependency has a `META-INF/beans.xml`, or (3) the dependency is listed in `quarkus.index-dependency.*` in `application.properties`. Without any of these, the beans compile fine but are invisible to CDI at runtime. Cached augmentation masks this because a previous build that DID have the beans indexed persists the graph.

### Fix
Add the sibling module to `quarkus.index-dependency` in the application module's `application.properties`:

```properties
quarkus.index-dependency.quarkmind-core.group-id=io.quarkmind
quarkus.index-dependency.quarkmind-core.artifact-id=quarkmind-core
```

### Why this is non-obvious
The error only appears after `mvn clean` — the stale augmentation cache from a previous successful build masks the missing index indefinitely. Developers can work for weeks without seeing the issue, then hit it after a clean build or CI run. The `UnsatisfiedResolutionException` message doesn't mention indexing — it just says the bean type has no matching producer.
