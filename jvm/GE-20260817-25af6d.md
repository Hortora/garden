### Symptom

Adding `casehub-pages-push-runtime` to a Quarkus app's `pom.xml` causes a build-time CDI unsatisfied dependency error during augmentation. The error message names `SessionSender` but doesn't indicate where the bean should come from.

### Context

`PushProducers` in `casehub-pages-push-runtime` produces four CDI beans: `TopicRegistry`, `EventStore` (`@DefaultBean`), `JsonWriter` (`@DefaultBean`), and `EventBroadcaster`. `EventBroadcaster`'s constructor requires a `SessionSender` — but `PushProducers` does **not** produce one, and there is no `@DefaultBean` for it anywhere in the module.

`EventStore` and `JsonWriter` both have `@DefaultBean` producers with sensible defaults (in-memory store, vanilla ObjectMapper). The asymmetry makes you expect `SessionSender` has one too.

### What was tried (didn't work)

1. Adding only `casehub-pages-push-runtime` dependency — CDI unsatisfied at augmentation
2. Looking for a `@DefaultBean SessionSender` in push or push-runtime — none exists

### Root cause

`SessionSender` is a `@FunctionalInterface` for sending messages to connected SSE/WebSocket clients. It has no sensible default because it depends on the transport layer (SSE endpoint, WebSocket session, etc.) which the consuming app owns. Unlike `EventStore` and `JsonWriter`, there is no generic fallback.

### Fix

Provide a no-op `SessionSender` producer in the consuming app:

```java
@ApplicationScoped
public class SocPushProducers {

    @Produces
    @ApplicationScoped
    SessionSender sessionSender() {
        return (connectionId, message) -> {};
    }
}
```

This satisfies the CDI dependency. The no-op is correct when using `EventBroadcaster` for event persistence (via `EventStore`) without real-time push delivery. When the app later adds SSE endpoints, replace with a real implementation.

### Why this is non-obvious

The three other dependencies of `EventBroadcaster` all have `@DefaultBean` producers in `PushProducers`. The pattern suggests the module is self-contained. The missing `SessionSender` default breaks the pattern silently — you only discover it when the CDI validation fails at build time.

### Alternatives considered

- Creating a `@DefaultBean` in the pages-push-runtime module itself — would be correct but requires a pages-push change (upstream fix).
