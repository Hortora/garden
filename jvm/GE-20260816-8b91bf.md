### Symptom

Quarkus application fails at startup with ambiguous route errors when adding sub-path endpoints to a foundation JAX-RS resource that share the same `@Path` base as an application resource. No compile error — only runtime failure.

### Context

Multi-module architecture where a foundation library (e.g. `qhorus-runtime`) provides a `ChannelResource` at `@Path("/api/channels")` and an integration-tier app (e.g. `chat-app`) has its own `ChatResource` at the same `@Path("/api/channels")`. Both are discovered via Quarkus classpath scanning. Initially they coexist because their sub-paths don't overlap. Adding sub-paths to the foundation resource that match existing app resource sub-paths causes the collision.

Related: GE-20260516-4bf0dc — `quarkus.arc.exclude-types` does not gate JAX-RS resources, so CDI exclusion cannot resolve this.

### Root cause

Quarkus/RESTEasy resolves JAX-RS routes at build time. Two resources with the same `@Path` base are allowed as long as no sub-paths collide. The moment a sub-path is added to one that matches the other (e.g. both have `POST /{id}/messages/{messageId}/reactions`), the build fails with an ambiguous route error.

### Fix

App-specific resources use an app-prefixed base path when the foundation resource owns the generic path:

```java
// Foundation (qhorus-runtime) — owns the generic path
@Path("/api/channels")
public class ChannelResource { ... }

// App (chat-app) — uses app-prefixed path for app-specific operations
@Path("/api/chat")
public class ChatResource { ... }
```

Frontend controllers accept `restBase` as config, so the path change is transparent to consumers.

### Why this is non-obvious

The collision is invisible until the moment sub-paths overlap. Two resources at the same base path work fine as long as their method+sub-path combinations are unique. This creates a false sense of safety — the collision is latent and only surfaces when a seemingly safe addition is made to the foundation resource.

### Alternatives considered

- Using `quarkus.arc.exclude-types` to exclude the foundation resource in apps that have their own — doesn't work (GE-20260516-4bf0dc)
- Merging app resources into the foundation resource via SPI — adds coupling, foundation shouldn't know about app-specific orchestration
