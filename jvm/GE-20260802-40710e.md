## WorkerResult.completed() vs WorkerResult.of() — lifecycle scope completion semantics

### The behaviour

`WorkerResult` has two success factory methods with critically different semantics in scoped execution modes:

| Factory | Outcome | PlanItem effect (non-TRANSIENT) |
|---------|---------|-------------------------------|
| `WorkerResult.of(output)` | `WorkerOutcome.Success` | Output applied, PlanItem stays **RUNNING** |
| `WorkerResult.completed(output)` | `WorkerOutcome.Completed` | Output applied, PlanItem transitions to **COMPLETED** |

In `QuartzWorkerExecutionJob.onSuccess()`:

```java
if (executionMode != null && executionMode != ExecutionMode.TRANSIENT) {
    if (!(workerResult.outcome() instanceof WorkerOutcome.Completed)) {
        // Success → output applied, PlanItem stays RUNNING
        return;
    }
}
```

### Why this matters

For A2A workers (and any external protocol worker), using `WorkerResult.of()` instead of `WorkerResult.completed()` causes PlanItems to never complete in scoped execution modes. The case stays RUNNING indefinitely with no error, no warning, and no log message. The output IS applied to the case context — everything looks correct except the PlanItem never transitions.

### Why this is non-obvious

Both methods say "success" — `of()` even looks like the natural default. The distinction between `Success` (output checkpoint) and `Completed` (lifecycle terminal) is only visible in `QuartzWorkerExecutionJob.onSuccess()` source code. No Javadoc, no CLAUDE.md entry at the time of discovery (added in engine#237 lifecycle scopes design, but buried in the spec). `WorkerResult.of()` is used in most examples and tests because most workers are TRANSIENT — where the distinction doesn't matter.

### Fix

Always use `WorkerResult.completed(output)` for workers that represent a complete unit of work (A2A task completed, MCP tool executed, flow workflow finished). Reserve `WorkerResult.of(output)` for scoped workers that emit intermediate results while staying alive.
