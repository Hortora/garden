### Symptom
Adding a second Maven module with `quarkus-maven-plugin` (or `packaging: quarkus`) to the same reactor as an existing Quarkus application fails during the augmentation phase. Errors include:
- `NoSuchMethodError: BeanProcessor$Builder.addSuppressConditionGenerator` (ArcProcessor)
- `SRCFG00011: Could not expand value platform.quarkus.native.builder-image` (config expansion)
- Various classpath conflicts between the two modules' augmentation contexts

### Context
Scaffold needed a web console (Quinoa + esbuild frontend) alongside its existing Quarkus backend. The initial design placed the frontend in a separate `scaffold-web` module with its own `quarkus-maven-plugin` and `quarkus-quinoa` dependency, following a separation-of-concerns pattern.

### What was tried (didn't work)
1. Separate `scaffold-web` module with `quarkus-maven-plugin extensions=true` — augmentation failed with ArcProcessor method errors
2. Passing missing config properties via `-D` flags — revealed deeper classpath conflicts
3. Attempting `scaffold-web` as a plain JAR with exec-maven-plugin (no Quinoa) — loses hot-reload capability

### Root cause
Quarkus's augmentation model is single-application. The `quarkus-maven-plugin` build goal creates a complete augmented application from the classpath. Two modules both running augmentation in the same reactor create conflicting deployment contexts — they share classpath elements but run independent augmentation passes that produce incompatible output.

### Fix
Place the `webui/` directory (with `package.json`, `esbuild.config.mjs`, `src/`) directly inside the Quarkus application module (e.g. `scaffold-backend/src/main/webui/`). This is the devtown pattern — one Quarkus module, one Quinoa build, one augmentation pass.

For headless deployments (no frontend), disable Quinoa via config property rather than module exclusion.

### Why this is non-obvious
The Maven multi-module pattern of separating frontend and backend into distinct modules is standard practice. Quarkus's single-application augmentation model isn't documented as a constraint against this pattern — the failure manifests as obscure classpath errors rather than a clear "not supported" message.
