### Symptom / Context

Phase detection test at the 12.0-minute boundary fails: expected `LATE` but got `MID`. The test converts minutes to game frames with `(long)(12.0 * 60 * 22.4)`, then the resolver converts back with `frame / 22.4 / 60.0` and compares against the 12.0 threshold. The round-trip should be identity — but isn't.

### What was tried (didn't work)

Direct cast `(long)(minutes * 60 * 22.4)` — the standard conversion pattern used everywhere in the SC2 codebase. Works for most values but silently fails at exact threshold boundaries (5.0, 12.0 minutes).

### Root cause

`22.4` is not exactly representable in IEEE 754 double-precision. The actual stored value is `22.399999999999998...`. So `12.0 * 60 * 22.4` evaluates to `16127.999...` instead of `16128.0`. The `(long)` cast truncates toward zero → `16127`. Converting back: `16127 / 22.4 / 60.0 = 11.9994...` which is less than the 12.0 threshold — phase resolves to MID instead of LATE.

### Fix

Use `Math.round()` instead of `(long)` cast for frame conversion:

```java
// Wrong — truncates at IEEE 754 boundaries
long frame = (long) (minutes * 60 * SC2Data.GAME_LOOPS_PER_SECOND);

// Correct — rounds to nearest, handles FP imprecision
long frame = Math.round(minutes * 60 * SC2Data.GAME_LOOPS_PER_SECOND);
```

### Why this is non-obvious

`22.4` looks like a clean constant — there's no visual hint that it can't be represented exactly in binary floating point. The truncation only manifests at exact threshold values (5.0, 12.0 minutes), which are the boundary test cases. All other test values (2.5, 4.99, 8.0, 11.99, 20.0) pass because the truncation doesn't cross a threshold. The failure is silent — no exception, no warning, just a wrong phase classification.
