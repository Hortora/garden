### Symptom

Models with the best tokenization of Java identifiers produce the worst retrieval precision, while models with mediocre tokenization score highest.

### Context

Hortora/engine#27 identified a vocabulary gap: BERT WordPiece fragments Java class names (`ConcurrentHashMap` → `concurrent ##has ##hma ##p`), hypothesizing this degrades retrieval. Evaluation of 6 models across 14 retrieval scenarios tested whether code-trained tokenizers improve precision.

### Root cause

Retrieval precision depends primarily on the training objective — contrastive similarity fine-tuning on large text pair datasets — not on tokenization quality. Models trained with MLM or code-understanding objectives (CodeBERT, UniXcoder) produce embedding spaces where all texts cluster together regardless of semantic similarity, even though their tokenizers preserve Java identifiers perfectly.

### Fix

When evaluating embedding models for retrieval, prioritize training objective over tokenizer architecture:

| Model | Avg tokens/id | Training | Retrieval precision |
|-------|--------------|----------|-------------------|
| nomic-embed-text | 4.8 (mediocre) | Contrastive (web text pairs) | **60.4%** |
| BGE-M3 | 5.3 (worst) | Contrastive (multilingual) | 56.4% |
| jina-code | 3.1 (best) | Contrastive (code pairs) | 54.1% |
| UniXcoder | 3.1 (best) | MLM + code understanding | 26.6% |
| CodeBERT | 4.0 | MLM (CodeSearchNet) | 2.0% |

The causal chain "bad tokenization → bad embeddings → bad retrieval" is broken at the second link. Tokenization affects how identifiers are represented internally, but the training objective determines whether the model produces discriminative embedding spaces for retrieval.

### Why this is non-obvious

The vocabulary gap hypothesis is mechanistically intuitive: if a model can't even represent `ConcurrentHashMap` as a meaningful unit, how can it produce good embeddings for it? The data shows this intuition is wrong — the internal representation matters less than the geometric structure of the embedding space, which is shaped by training, not tokenization.

### Why this fix

This reframes the model selection criterion. Instead of "find a model with better Java tokenization" (which led to evaluating code-domain models), the right question is "find a model with better contrastive training on technical prose" — a fundamentally different search direction.

### Alternatives considered

- Evaluated 4 code-domain models (CodeBERT, UniXcoder, jina-code, nomic-v1.5) as alternatives to nomic-embed-text — none improved retrieval despite better tokenization.
- jina-code came closest (54.1%) with both good tokenization AND retrieval training, but its code-pair training doesn't transfer well to NL↔NL retrieval on technical prose.
