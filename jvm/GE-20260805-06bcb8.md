### Symptom

A quality dashboard query on `AmlCaseProfileLedgerEntry` filtering by `outcome` for UPHELD/WITHDRAWN/FLAGGED rates returns zero results. The column exists and has data, but no rows match UPHELD, WITHDRAWN, or FLAGGED.

### Context

Building a quality analytics dashboard that segments SAR filing success rates by whether seed narratives were used. The `AmlCaseProfileLedgerEntry` has `narrative_seeded` and `seed_count` columns alongside an `outcome` column — naturally assumed to be the SAR regulatory outcome.

### Root cause

`AmlCaseProfileLedgerEntry.outcome` stores the **triage decision** — `SAR_WARRANTED`, `FALSE_POSITIVE`, `INCONCLUSIVE`. These are set at case completion by `AmlCaseProfileStoreObserver` from the investigation triage result.

The **regulatory SAR verdict** (UPHELD, WITHDRAWN, FLAGGED) arrives later via `SarOutcomeFeedbackService.recordOutcome()`, which writes a `LedgerAttestation` record with `verdict = SOUND` (UPHELD) or `verdict = FLAGGED` (WITHDRAWN or FLAGGED — both map to `AttestationVerdict.FLAGGED`).

The two are different lifecycle stages:
- `AmlCaseProfileLedgerEntry` — snapshot at investigation completion (case-level)
- `LedgerAttestation` — post-submission regulatory feedback (attestation-level)

### Fix

Quality queries must **join** the two entities:

```java
"SELECT p.narrativeSeeded, a.verdict, COUNT(p) " +
"FROM AmlCaseProfileLedgerEntry p, LedgerAttestation a " +
"WHERE p.subjectId = a.subjectId " +
"AND p.outcome = 'SAR_WARRANTED' " +
"AND a.capabilityTag = 'sar-drafting' " +
"AND a.trustDimension = 'investigation-accuracy' " +
"AND a.occurredAt = (" +
"  SELECT MAX(a2.occurredAt) FROM LedgerAttestation a2 " +
"  WHERE a2.subjectId = a.subjectId " +
"  AND a2.capabilityTag = a.capabilityTag " +
"  AND a2.trustDimension = a.trustDimension" +
") " +
"GROUP BY p.narrativeSeeded, a.verdict"
```

The correlated subquery ensures only the latest attestation per case is counted (handles SAR outcome revisions). Cases without attestations are excluded — their SAR hasn't been reviewed yet.

### Why this is non-obvious

The field is literally named `outcome` on a case profile ledger entry — the natural assumption is that it contains THE outcome. The two-entity split reflects the casehub-ledger architecture where `LedgerEntry` subclasses capture point-in-time snapshots and `LedgerAttestation` records capture post-hoc evaluations, but nothing in the API surface or column naming signals this distinction.

### Caveats

- `SarOutcomeFeedbackService.toVerdict()` maps both `SarVerdict.WITHDRAWN` and `SarVerdict.FLAGGED` to `AttestationVerdict.FLAGGED` — the original verdict is not preserved on the attestation. Quality dashboards can only distinguish UPHELD vs NOT-UPHELD, not WITHDRAWN vs FLAGGED.
- The join key is `subjectId` on both entities, set to the raw `caseId` UUID in both `AmlCaseProfileStoreObserver` and `SarOutcomeFeedbackService`.
