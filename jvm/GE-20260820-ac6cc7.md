## Symptom

A CDI interceptor in a Quarkus extension causes `LinkageError` at runtime when it
references types from another extension's API module. The interceptor works in
`QuarkusUnitTest` (deployment module tests) but fails in real `@QuarkusTest` or
application boot with:

```
java.lang.LinkageError: loader constraint violation: when resolving method
'io.casehub.ledger.api.model.AuditRecord.<init>(...ActorType...)'
```

## Context

Quarkus loads each extension's runtime JAR in its own classloader. When extension A's
interceptor constructs objects that reference types from extension B's API, the JVM's
linkage verification fails because the same class (e.g. `ActorType`) is loaded by two
different classloaders — the extension classloader for the interceptor, and the app
classloader for the API types.

`QuarkusUnitTest` in deployment module tests uses a different classloading model than a
real Quarkus application boot — everything loads in one classloader. So tests pass but
real usage fails.

## What was tried (didn't work)

1. **`parent-first-artifact` in `quarkus-extension.properties`** — adding
   `parent-first-artifact=io.casehub\:casehub-platform-api,io.casehub\:casehub-ledger-api`
   partially works but is fragile and doesn't cover all type resolution paths.
2. **Passing `null` for cross-extension types** — avoids the error but loses the
   semantic value of the type (e.g. `ActorType.AGENT` becomes `null`).

## Root cause

CDI interceptors run at request time in the extension classloader. Unlike
`@Record(RUNTIME_INIT)` recorder code (which runs in the app classloader at startup),
interceptor method invocations resolve types through the extension's own classloader.
When those types are defined in a different extension's API module, the JVM sees two
different Class objects for the same fully-qualified name and rejects the linkage.

## Fix

Keep the interceptor in the same module as the types it references. If the interceptor
needs types from the core extension's API, the interceptor belongs in the core extension's
runtime module — not in a separate extension.

The annotation definitions (pure marker annotations) can stay in the separate extension
module since they don't trigger classloader issues at the annotation-resolution level.

Pattern: annotation definitions in `extension-a/runtime`, interceptor implementation in
`core-extension/runtime` alongside the API types.

### Why this is non-obvious

The test suite (using `QuarkusUnitTest`) passes with the interceptor in the separate
extension. The failure only manifests in real application boot or `@QuarkusTest`. The
Quarkus documentation doesn't explicitly warn about this cross-extension interceptor
classloader boundary.

### Why this fix

Moving the interceptor to the core module follows the existing pattern used by
`ProvenanceCaptureInterceptor` — both the annotation and the interceptor live in the
same runtime module. The alternative (`parent-first-artifact`) is a classloader hint
that's fragile and doesn't generalize.
