### Symptom
`MojoExecutionException: Jandex index not found at /path/to/sibling/target/classes/META-INF/jandex.idx. Build the Quarkus module first.`

Occurs intermittently in cross-repo Maven reactor builds, especially with `-T 1C` (parallel threads). The file path exists in the source tree — the sibling module simply hasn't compiled yet when the generator runs.

### Context
Code-generator Maven plugins (e.g. `casehub-platform-spring-generator`) that read artifacts from sibling modules via filesystem path rather than Maven coordinates:
```xml
<configuration>
    <quarkusModule>${project.basedir}/../mindmap</quarkusModule>
</configuration>
```

In a single-repo build, Maven's reactor orders modules by `<module>` declaration order in the parent POM, which implicitly puts the Quarkus module before its `-spring` consumer. In a cross-repo aggregator (all repos pooled into one reactor), Maven sorts by declared `<dependency>` relationships — and the filesystem path creates no Maven dependency.

### What was tried (didn't work)
- Adding a `casehub.generators.skip=true` property to skip generators entirely in the reactor — works but is a symptom-level workaround that silences the generators rather than fixing ordering
- `-fae` (fail-at-end) — build continues past the error but reports failure

### Root cause
Maven's reactor ordering only considers `<dependency>`, `<parent>`, and `<plugin>` relationships declared in pom.xml. A plugin that reads from a sibling module's `target/` directory via filesystem path creates an invisible dependency that the reactor cannot see. With `-T 1C`, the race becomes non-deterministic.

### Fix
Add a `provided`-scope Maven dependency from each generator-consumer module to the filesystem-referenced module:
```xml
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-neocortex-mindmap</artifactId>
    <version>${project.version}</version>
    <scope>provided</scope>
</dependency>
```

`provided` scope is correct because:
- It establishes reactor ordering (Maven builds the dependency first)
- It doesn't pollute the transitive dependency graph (Spring Boot consumers don't pull in Quarkus modules)
- It's semantically accurate — the module is needed at build time for code generation, not at runtime

### Alternatives considered
- **Skip property on the generator plugin** — works as a quick workaround but doesn't fix ordering; generators simply don't run, so generated code must already exist
- **Declaring Maven deps from spring→quarkus modules with `compile` scope** — fixes ordering but leaks Quarkus dependencies into Spring Boot consumers' transitive graph

### Why this is non-obvious
The error message ("Build the Quarkus module first") implies a manual ordering problem. In single-repo builds, it never occurs because parent POM module order handles it. The failure only surfaces in cross-repo aggregators where modules from different repos are pooled — a setup that's unusual enough that the plugin author wouldn't have encountered it. The fix (`provided`-scope dependency for build ordering, not compilation) uses Maven's dependency mechanism for a non-compilation purpose.
