# SyntheticBeanBuildItem.addQualifier() silently removes @Default

## Stack
Quarkus 3.32, CDI (ArC)

## Symptom
After adding a custom qualifier to a `SyntheticBeanBuildItem`, existing
`@Inject` points for the bean type (without the qualifier) fail at startup
with `UnsatisfiedResolutionException` or `AmbiguousResolutionException`.

## Context
Building a Quarkus extension that registers synthetic CDI beans via
`SyntheticBeanBuildItem.configure(GoalCompiler.class)`. When adding a
qualifier for multi-graph disambiguation, all unqualified injection points
break.

## What was tried (didn't work)
Adding `.addQualifier().annotation(MyQualifier.class).addValue(...).done()`
to the synthetic bean builder — this removes `@Default` per CDI spec §2.3.1.

## Root cause
CDI spec: a bean with any custom qualifier automatically loses the `@Default`
qualifier. `SyntheticBeanBuildItem.addQualifier()` follows this rule, but
the API gives no hint that adding a qualifier is destructive to `@Default`.

## Fix
For single-bean apps that need to remain injectable without qualifiers,
do not add the qualifier. If multi-bean disambiguation is needed, use a
two-pass approach:

1. Count all beans of the type first (across all `@BuildStep` invocations)
2. Only add qualifiers when count > 1

Alternatively, register the bean twice — once with qualifier, once without —
but this creates CDI ambiguity for the unqualified case when multiple beans exist.

## Why this is non-obvious
The Quarkus `SyntheticBeanBuildItem` API is fluent and additive — `.addQualifier()`
reads like "also add this qualifier" rather than "replace @Default with this
qualifier". The CDI spec behavior is documented but not surfaced in the
Quarkus extension authoring docs.

### Alternatives considered
- Always add both `@Default` and the custom qualifier: creates ambiguity when
  multiple beans exist with `@Default`
- Use `@Named` instead of a custom qualifier: doesn't provide type-safe
  disambiguation
