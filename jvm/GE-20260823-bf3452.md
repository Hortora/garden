### Symptom
`mvn compile` fails with `ProjectCycleException`: `testing → deployment → testing`. The shared testing module can't depend on the domain module whose stubs it hosts.

### Context
Extracting inline test stubs (e.g. `StubChannelOperations implements ChannelProvisionHandler.ChannelOperations`) from a domain module's test class to a shared `testing/` module. The stub implements an interface defined inside the domain module's production code, not in a shared API module.

### Root cause
`ChannelProvisionHandler.ChannelOperations` is a domain-internal type in `casehub-ops-deployment`. For `testing/` to compile the stub, it needs `casehub-ops-deployment` as a dependency. But `casehub-ops-deployment` already depends on `casehub-ops-testing` for test fixtures — creating a cycle.

### Fix
Only extract stubs that implement API-level interfaces (from `*-api` modules) to the shared testing module. Keep stubs that implement module-internal types in the domain module's own `src/test/` directory.

Safe to extract: `StubAgentRegistry` (implements `AgentRegistry` from `eidos-api`), `StubChannelStore` (implements `CrossTenantChannelStore` from `qhorus-api`), `StubEndpointRegistry` (implements `EndpointRegistry` from `platform-api`).

Must stay in module: `StubChannelOperations` (implements `ChannelProvisionHandler.ChannelOperations` from `deployment`).

### Why this is non-obvious
The stubs look identical — same pattern, same structure. The dependency direction is invisible until Maven reports the cycle. The fix requires checking where each interface is defined, not just what the stub does.
