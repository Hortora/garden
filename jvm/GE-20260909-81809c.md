### The technique

Build a Maven plugin that scans a Quarkus module's Jandex index for `@Produces` methods and generates equivalent Spring Boot `@AutoConfiguration` classes. The Quarkus CDI wiring is the single source of truth — developers write CDI producers once, and the Spring equivalent is derived automatically.

### Mapping

| Quarkus input | Spring output |
|---|---|
| `@Produces @ApplicationScoped` | `@Bean` |
| `@Produces @DefaultBean` | `@Bean @ConditionalOnMissingBean` |
| `@Produces @Alternative @Priority(N)` | `@Bean @Primary` |
| `@ConfigProperty(name = "x")` | Skipped — needs manual `@Value` wiring |
| Class-level `@AutoConfiguration` | Generated with `@ConditionalOnClass` anchor |
| `AutoConfiguration.imports` registration file | Generated alongside source |

### Drift verification

A second Maven goal (`verify` phase) compares all `@Produces` return types against all `@Bean` return types. Any Quarkus bean without a Spring counterpart fails the build. Manual beans (for the ~20% the generator can't handle) coexist alongside generated beans — the verifier treats them equally.

### What this enables

For a platform with 47+ CDI-coupled modules, the generator eliminates ongoing maintenance of parallel Spring auto-configurations. Adding a `@Produces` method to the Quarkus module automatically generates the Spring `@Bean` method on next build. Forgetting the Spring side fails CI via drift verification.

### Why this is non-obvious

Most dual-framework approaches either duplicate code or introduce a shared abstraction layer. This technique keeps the existing Quarkus code as-is (zero refactoring of CDI wiring) and derives the Spring side mechanically. The key insight: `@Produces` methods already contain all the information needed — return type, parameter types, CDI qualifiers — to generate the Spring equivalent.
