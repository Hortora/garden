### Symptom
All test compilation in claudony fails with 11 errors in `NoOpJobScheduler.java`:
```
NoOpJobScheduler is not abstract and does not override abstract method exists(JobIdentifier)
exists(JobIdentifier) in NoOpJobScheduler cannot implement exists(JobIdentifier) in JobScheduler
```
Every method shows "cannot implement" — looks like a wholesale interface change.

### Context
`NoOpJobScheduler` is a test-scoped `@DefaultBean` that implements `JobScheduler` SPI from `casehub-engine-common`. The SPI changed all return types from `Uni<X>` (reactive) to synchronous (`void`, `boolean`, `int`). The SNAPSHOT resolved a newer version than what the test utility was written against.

### Root cause
The `JobScheduler` interface in `casehub-engine-common` was updated from reactive Mutiny types to synchronous types as part of engine SPI retirement (#184). The claudony test utility `NoOpJobScheduler` still had the old `Uni<Void>` / `Uni<Boolean>` / `Uni<Integer>` return types.

### Fix
Use `javap` to inspect the actual interface in the resolved JAR, then update the impl:
```bash
# Find the latest jar
find ~/.m2/repository/io/casehub/casehub-engine-common/0.2-SNAPSHOT -name "*.jar" -not -name "*sources*" | sort | tail -1

# Inspect the interface
javap -cp <jar-path> -public io.casehub.engine.common.spi.scheduler.JobScheduler
```
Then update `NoOpJobScheduler` to match: `Uni<Void>` → `void`, `Uni<Boolean>` → `boolean`, `Uni<Integer>` → `int`.

### Why this is non-obvious
The symptom (11 compilation errors in one file) looks project-specific, but the cause is a transitive SNAPSHOT interface change. The "cannot implement" error is confusing — the methods exist but with wrong return types, yet the compiler message doesn't show the type mismatch explicitly. Using `javap` on the resolved JAR is the diagnostic shortcut — it shows the actual interface methods without needing the source repo.

### Alternatives considered
- Reading the engine source code — but the engine repo wasn't in the slot; `javap` is faster and doesn't require checkout
- Excluding the test file from compilation — would leave the `@DefaultBean` missing, causing CDI errors in other tests
