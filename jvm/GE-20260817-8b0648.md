## Symptom

An annotation processor configured via Maven's `<annotationProcessorPaths>` runs without errors but produces no output. The processor scans Jandex indexes from dependency JARs using `getClass().getClassLoader().getResources("META-INF/jandex.idx")` and finds zero indexes.

## Context

When building a Quarkus module that depends on API JARs containing Jandex-indexed `@CallbackEligible` interfaces, the callback-generator APT should scan those indexes and generate decorator source files. The APT is configured in `annotationProcessorPaths` — Maven's recommended approach for annotation processors.

## What was tried (didn't work)

1. Added the generator JAR to `<annotationProcessorPaths>` in `maven-compiler-plugin` configuration
2. Verified the dependency JARs contain `META-INF/jandex.idx`
3. Enabled Maven debug output (`-X`) — confirmed the APT JAR was on the processor classpath
4. The APT ran (no errors), but `loadCombinedIndex()` returned null — zero Jandex indexes found

## Root cause

`<annotationProcessorPaths>` creates a **separate classloader** for annotation processors, isolated from the compilation classpath. The APT's `getClass().getClassLoader()` only sees JARs listed in `annotationProcessorPaths` and their transitive dependencies — NOT the project's compile dependencies where the Jandex indexes live.

This is by design in Maven: `annotationProcessorPaths` replaces the default annotation processor discovery (which uses the compile classpath) with an explicit, isolated processor path.

## Fix

Add the generator as a regular `provided`-scope dependency instead of using `annotationProcessorPaths`. javac discovers the APT via `META-INF/services/javax.annotation.processing.Processor` from the compile classpath, and the APT's classloader includes all compile dependencies:

```xml
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-platform-callback-generator</artifactId>
    <scope>provided</scope>
</dependency>
```

`provided` scope ensures the generator JAR is available at compile time but not included in the runtime artifact.

**Caveat with Quarkus:** Quarkus's `quarkus-maven-plugin` may interfere with standard APT discovery. If the APT still doesn't run, the processor may need to be reimplemented as a Quarkus build extension (`@BuildStep`) instead.

## Why this is non-obvious

The Maven documentation recommends `annotationProcessorPaths` as the modern way to configure annotation processors. Most APTs process annotations on the classes being compiled (which are always visible). An APT that reads resources from dependency JARs (like Jandex indexes) hits the classloader isolation silently — no error, no warning, just empty results.

### Alternatives considered

- **Adding all dependency JARs to `annotationProcessorPaths`**: Works but defeats the purpose of classpath isolation and creates maintenance burden as dependencies change.
- **Using `processingEnv.getFiler()` for resource access**: The standard APT approach for reading resources, but Jandex indexes are binary files in META-INF, and Filer access to dependency resources is implementation-dependent across compilers.
