### Symptom
An `EnvironmentObserver` implementation that takes more than 100ms to complete its `observe()` call always times out. The timeout fires silently — no configuration option prevents it.

### Context
The engine's `CaseContextChangedEventHandler.observations()` dispatches each observer on a virtual thread with a hardcoded 100ms timeout:

```java
CompletableFuture.supplyAsync(() -> observer.observe(ctx), virtualThreads)
    .orTimeout(100, java.util.concurrent.TimeUnit.MILLISECONDS)
    .join();
```

This exists to protect the tick loop from runaway deterministic observers (threshold checks, correlations). For LLM-backed observers or any observer with > 100ms latency, the timeout makes the SPI unusable.

### Root cause
The timeout value is a literal `100` in `CaseContextChangedEventHandler.observations()` (engine runtime-core, line ~1315). It is NOT read from `ObservationConfig` — which has `maxHistoryEntries`, `maxHistoryAge`, `maxObserversPerCase`, and `allowJqInterests`, but no timeout configuration. The rule evaluation timeout (`RuleConfig.ruleEvaluationTimeoutMs()`) IS configurable, but the observation timeout is not.

### Workaround
Do not implement `EnvironmentObserver` for slow operations. Instead, use the event-driven pattern: subscribe to context change events externally, process asynchronously, and write results back to the environment (signals, context writes) which triggers a new tick. The engine's deterministic observers handle bounded-latency patterns; the event-driven layer handles unbounded-latency interpretation.

### Why this is non-obvious
`RuleConfig.ruleEvaluationTimeoutMs()` is configurable — a developer would expect `ObservationConfig` to have a similar timeout configuration. The `EnvironmentObserver` interface itself gives no indication of a timeout constraint. The 100ms limit is discoverable only by reading the engine runtime source code.
