## HandlerResult pattern — engine-internal metadata channel

### The technique

When an engine-internal handler (`WorkerFunctionHandler`) needs to carry protocol-specific metadata (A2A endpoint, task ID, streaming flag) alongside its result, but the result type (`WorkerResult`) is a public API that consumer-written worker functions return — introduce a wrapper record at the engine-internal layer:

```java
public record HandlerResult(WorkerResult<?> result, Map<String, Object> protocolMetadata) {
    public HandlerResult(WorkerResult<?> result) {
        this(result, Map.of());
    }
}
```

The handler interface returns `HandlerResult`. The composite executor extracts `WorkerResult` for cross-cutting concerns (output schema evaluation) and preserves `protocolMetadata`. The metadata threads through the event chain into EventLog entries.

### Why this is non-obvious

The tempting alternative is adding metadata to `WorkerResult` itself — it's simpler and avoids a new type. But `WorkerResult` is in `casehub-worker-api` (foundation tier, consumer-facing). Adding engine-internal metadata there violates the same principle that motivated `ExecutionMetadata` being separate from `WorkerContext`. The wrapper pattern keeps the boundary clean: consumers see `WorkerResult`, the engine sees `HandlerResult`.

### Why this fix

The existing handlers (`SyncAgentWorkerFunctionHandler`, `FlowWorkerFunctionHandler`) just wrap with the convenience constructor — zero metadata, zero disruption. Only handlers that have protocol-specific metadata (A2A, and potentially MCP) use the full constructor. The cost is one new record and a mechanical return-type change across ~5 files.
