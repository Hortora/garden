### Symptom
Issue #86 specified creating a `LifeLedgerResource` at `/api/v1/ledger` to serve ledger entries and attestations. The natural instinct is to write a new JAX-RS resource wrapping `LedgerEntryRepository`.

### Context
casehub-life needed REST endpoints matching the `<blocks-audit-trail-viewer>` component's expected API shape: `GET /api/v1/ledger/entries?subjectId=...&tenancyId=...`, attestations per entry, and Merkle verification.

### Root cause
The `casehub-ledger-rest` module (a sibling of `casehub-ledger` in the ledger repo) already provides exactly these endpoints with the exact URL paths and response shapes. It was designed to be dropped in as a dependency.

### Fix
Add the dependency, Jandex index, and HTTP auth policy — zero life-specific Java code:

```xml
<dependency>
  <groupId>io.casehub</groupId>
  <artifactId>casehub-ledger-rest</artifactId>
</dependency>
```

```properties
quarkus.index-dependency.ledger-rest.group-id=io.casehub
quarkus.index-dependency.ledger-rest.artifact-id=casehub-ledger-rest
quarkus.http.auth.permission.ledger-api.paths=/api/v1/ledger/*
quarkus.http.auth.permission.ledger-api.policy=authenticated
```

### Why this is non-obvious
The ledger-rest module is optional and not mentioned in the main casehub-ledger consumer guide's quick-start. It's easy to miss that the platform already provides the exact REST surface you need, especially when the issue specification says "create a resource."

### Alternatives considered
- Writing a `LifeLedgerResource` in casehub-life wrapping `LedgerEntryRepository` — rejected because it duplicates foundation code and diverges from the canonical response shape
- Using qhorus EntityManager JPQL directly (the pattern used by `ExternalActorHistoryService`) — rejected because it would need to replicate the DTO mapping and endpoint paths that ledger-rest already provides
