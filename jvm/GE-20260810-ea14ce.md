### Symptom
`Instance<AgentRegistry>.isResolvable()` returns `false` in production code called from a `@QuarkusTest`, even though a `TestAgentRegistry implements AgentRegistry` inner class is `@ApplicationScoped` in the test class. The code silently returns early — no error, no log, no CDI exception.

### Context
Two `@QuarkusTest` classes (`GoalFormationIntegrationTest` and `GoalRevisionIntegrationTest`) each define an inner `@ApplicationScoped public static class TestAgentRegistry implements AgentRegistry`. Quarkus ARC discovers ALL test inner classes globally, regardless of which test is running or its `@TestProfile`. Both beans are discovered, creating a CDI ambiguity for `Instance<AgentRegistry>`.

### What was tried (didn't work)
- Added `@Unremovable` — doesn't resolve ambiguity, just prevents pruning
- Different `@TestProfile` configs — profiles don't scope bean discovery
- Renaming the inner class — different class names still implement the same SPI, ambiguity remains

### Root cause
Quarkus ARC scans all classes (including test inner classes) at build time. Two `@ApplicationScoped` beans of the same type without `@Alternative` creates CDI ambiguity. `Instance<T>.isResolvable()` returns `false` when ambiguous (not just when absent). The direct injection `@Inject TestAgentRegistry` works because it resolves by concrete type, masking the problem for the test class itself.

### Fix
Use `@Alternative @Priority(1)` on the inner bean that must win for `Instance<T>` resolution, or extract shared test beans into a single utility class that both tests inject. The alternative approach scopes cleanly — one test's `@Alternative` wins without breaking the other test's direct injection.

```java
@jakarta.annotation.Priority(1)
@jakarta.enterprise.inject.Alternative
@ApplicationScoped
public static class TestChatModelProvider implements ChatModelProvider { ... }
```

### Why this is non-obvious
`@Inject TestAgentRegistry` works perfectly — the test injects by concrete type. The ambiguity only surfaces via `Instance<AgentRegistry>` in production code called during the test. The symptom is "nothing happens" with no error, making it appear as a logic or config bug rather than a CDI issue.
