### Symptom
`ToolManager.newTool("my_tool").setServerName("casehub").register()` throws at startup:
```
java.lang.IllegalStateException: Invalid server name: casehub
  at io.quarkiverse.mcp.server.runtime.FeatureManagerBase$FeatureDefinitionBase.validate
```

The named server "casehub" is correctly configured (`quarkus.mcp.server.casehub.*` properties present) and `@Tool` methods on `@McpServer("casehub")` classes work fine.

### Context
When migrating a tool from annotation-based `@Tool` to programmatic `ToolManager.newTool()` registration (e.g. to use `setInputSchema()` for dynamic JSON Schema), the natural approach is to call `setServerName("casehub")` to keep the tool on the same named server. The API has the method, it compiles, but the runtime validation rejects it.

### What was tried (didn't work)
- `setServerName("casehub")` — fails with `IllegalStateException`
- `setServerNames("casehub")` — same validation path, same failure

### Root cause
The `FeatureManagerBase.validate()` method checks programmatic tool server names against a build-time-discovered list of known servers. Named servers registered via `@McpServer` annotations are processed by the deployment-time build step, but the runtime `ToolManager` validation uses a different server name registry that only includes explicitly configured servers, not annotation-discovered ones. The `InvalidServerNameStrategy` enum (`FAIL`/`IGNORE`) controls this but defaults to `FAIL`.

### Fix
Omit `setServerName()` entirely — programmatic tools register on the default server. In single-server deployments (the common case for library modules), all tools are served through the same HTTP endpoint regardless of which logical server they belong to.

```java
toolManager.newTool("casehub_action")
    .setDescription("Execute a CaseHub operation")
    .setInputSchema(schema)
    .setHandler(args -> { /* ... */ })
    .register();
// No setServerName() — registers on default server
```

### Why this is non-obvious
The `setServerName()` method exists on `ToolDefinition`, compiles without issue, and is the natural API to use when other tools on the same class use `@McpServer("casehub")`. The error message ("Invalid server name") is the same as GE-20260814 (missing config), but the cause is different — here the config exists and annotation-based tools work. The fix (omit the call entirely) is counterintuitive when you're trying to keep tools grouped on the same server.

## Variant — ResourceManager and CompletionManager

The same issue affects all programmatic Manager APIs, not just ToolManager:

```java
// All of these fail with "Invalid server name: casehub"
resourceManager.newResource("name").setServerName("casehub").setUri(...).register();
resourceTemplateManager.newResourceTemplate("name").setServerName("casehub").register();
completionManager.newCompletion("name").setServerName("casehub").register();
```

The fix is identical: make `setServerName()` conditional on config presence:
```java
@ConfigProperty(name = "casehub.mcp.server-name")
Optional<String> serverName;

// Only call setServerName when configured
var def = resourceManager.newResource("name").setUri(uri);
serverName.ifPresent(def::setServerName);
def.register();
```

This pattern was validated in `McpResourceRegistryBridge` (casehub-platform #241).

### Alternatives considered
- Setting `quarkus.mcp.server.invalid-server-name-strategy=ignore` — works but suppresses all server name validation globally, hiding real errors
- Using `McpServer.DEFAULT` constant explicitly — same as omitting the call, more verbose for no benefit
