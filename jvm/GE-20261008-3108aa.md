## @DefaultBean overridden by downstream @ApplicationScoped — completely silent, no error, wrong implementation runs indefinitely

**See also:** GE-20260626-a37306 covers the same mechanism but with an explicit error symptom. This entry covers the worse failure mode: completely silent wrong behavior.

### Symptom

Debug logging added to `DefaultGraduationScorer.score()` at INFO level never fires. The method appears unreachable. The jar was verified to contain the logging code. Log level configuration was verified (another class in the same package logs INFO successfully). No exceptions, no warnings, no CDI ambiguity errors.

### Context

`ExperienceConsolidationPhase` injects `Instance<GraduationScorer>`. The library provides `DefaultGraduationScorer` annotated `@DefaultBean @ApplicationScoped`. A downstream example module provides `ManorGraduationScorer` annotated `@ApplicationScoped` (no `@DefaultBean`). CDI resolves `ManorGraduationScorer` because `@DefaultBean` means "use only if no other bean exists."

The `ManorGraduationScorer` lacked a formative-memory bypass, scoring them at 0.39 (below the 0.5 threshold). Formation memories were silently skipped — cursor advanced, no error, no graduation. The wrong scorer ran for the entire development period.

### What was tried (didn't work)

1. Added INFO logging to `DefaultGraduationScorer.score()` entry — log never appeared
2. Verified the installed jar contained the logging bytecode (checked with zipfile)
3. Checked JUL vs JBoss LogManager configuration (red herring — both classes in same package)
4. Checked for silently swallowed exceptions in the consolidation loop
5. Checked for CDI bean resolution issues with `Instance<T>.isResolvable()`

### Root cause

`@DefaultBean` is designed to be silently overridden. When `ManorGraduationScorer` (`@ApplicationScoped`) exists on the classpath, CDI picks it over `DefaultGraduationScorer` (`@DefaultBean`) with no ambiguity exception and no log message. The developer adding the downstream scorer had no way to know a `@DefaultBean` existed in the library.

### Fix

Add CDI diagnostic output that logs the resolved bean class:

```java
Instance<GraduationScorer> scorer = ...;
if (scorer.isResolvable()) {
    var resolved = scorer.get();
    LOG.info("GraduationScorer resolved: " + resolved.getClass().getName());
}
```

When adding `@DefaultBean` to a library:
- Search the full classpath for other implementations: `ide_find_implementations` on the interface
- Document the `@DefaultBean` contract in the interface javadoc
- Consider logging the resolved class at startup in the consuming class

### Why this is non-obvious

No compile error. No runtime warning. No CDI ambiguity exception. The `@DefaultBean` annotation is specifically designed to yield silently. A developer adding a new `@ApplicationScoped` implementation in a downstream module has no indication they're overriding a library default — the override is invisible at the point of declaration.

### Alternatives considered

- `@Alternative @Priority` — explicit but requires consumer-side activation
- Qualifier annotations — breaks the "just works" SPI pattern
- CDI interceptor on `Instance.get()` — too invasive for diagnostics
