## Symptom

SSE subscriber hangs forever — `BroadcastProcessor.toHotStream().filter().select().first(1)`
never completes, even though CDI events fire and the observer runs.

## Context

Quarkus SSE endpoint using `BroadcastProcessor` to multiplex CDI `@ObservesAsync` events.
The observer composes a snapshot from store data before pushing to the processor.

## Root cause

The observer guards with `if (snapshot != null)` and the composition returns null when
underlying stores are empty (no data for that case). The event fires, the observer runs,
but nothing is pushed. Subscribers waiting on the hot stream see no events.

The `BroadcastProcessor` is a hot stream — events not pushed are permanently lost. There
is no replay or backfill mechanism.

## Fix

Always compose and push — treat "no data" as a valid state (e.g. IDLE), not as "no event."
The null guard belongs on the *composition inputs* (graceful defaults), not on the
*push decision*.

```java
// Wrong — silently drops events when stores are empty
var snapshot = composeSnapshot(caseId, tenancyId);
if (snapshot != null) {
    processor.onNext(new Event(caseId, snapshot));
}

// Right — always push, compose handles null inputs gracefully
var snapshot = compose(caseId, planModel, dagPlan, dagResult);
processor.onNext(new Event(caseId, snapshot));
```

## Why this is non-obvious

The null guard looks defensive and correct — why push empty data? But in a hot-stream
context, "no event" and "empty event" have different semantics. Subscribers distinguish
between "nothing happened yet" (no event) and "the system is idle" (IDLE event). The
guard conflates the two, and the failure mode is silent — no error, no log, just a hung
subscriber.

### Alternatives considered

- Lazy composition per subscriber (compose in `stream().map()` instead of the observer) — avoids the problem but moves blocking JPA calls onto the Mutiny I/O thread.
- Subscriber-count check before composing — `BroadcastProcessor` doesn't expose subscriber count; checking would race anyway.
