### Symptom

A foundation REST resource needs to notify an optional push module after mutations
(reactions, topic changes, member joins) so connected WebSocket clients get real-time
updates. But the foundation module (qhorus-runtime) must not depend on the push module
(qhorus-push) — push is optional and not every consumer needs it.

### Context

Multi-module Quarkus project where a REST resource in a core/runtime module performs
CRUD operations that should trigger real-time push notifications when a push module
is on the classpath. Without decoupling, the runtime module would need a compile
dependency on the push module, making push mandatory for all consumers.

### What was tried (didn't work)

- **Optional Maven dependency + Instance<>** — adds push to runtime's test classpath,
  causing CDI to discover push infrastructure beans (WebSocket endpoints, event stores)
  during tests. QhorusPushInfrastructure produces EventStore/TopicRegistry singletons
  that interfere with test setup.
- **SPI interface in API module** — works but requires many methods (one per mutation
  type), creating a large interface surface.

### Root cause

The standard approaches either couple the modules (optional dependency still affects
tests) or require verbose SPI interfaces. CDI events provide fire-and-forget notification
where the event type is the only shared dependency.

### Fix

Define a sealed interface with record variants in the shared API module:

```java
// In qhorus-api (shared dependency of both runtime and push)
package io.casehub.qhorus.api.event;

public sealed interface ChannelMutationEvent {
    record ReactionAdded(long messageId, String emoji) implements ChannelMutationEvent {}
    record ReactionRemoved(long messageId, String emoji) implements ChannelMutationEvent {}
    record MemberJoined(UUID channelId, ChannelMembership membership) implements ChannelMutationEvent {}
    record MemberLeft(UUID channelId, String memberId) implements ChannelMutationEvent {}
    record TopicCreated(UUID channelId, Topic topic) implements ChannelMutationEvent {}
    record TopicUpdated(UUID channelId, Topic topic) implements ChannelMutationEvent {}
    record TopicRemoved(UUID channelId, long topicId) implements ChannelMutationEvent {}
}
```

In the foundation REST resource (runtime module):

```java
@Inject Event<ChannelMutationEvent> mutationEvent;

@POST @Path("/{id}/messages/{messageId}/reactions") @Transactional
public Response addReaction(...) {
    reactionManager.react(msgId, emoji);
    mutationEvent.fire(new ChannelMutationEvent.ReactionAdded(msgId, emoji));
    return Response.ok().build();
}
```

In the push module's broadcaster:

```java
void onMutation(@Observes ChannelMutationEvent event) {
    switch (event) {
        case ChannelMutationEvent.ReactionAdded e -> broadcastReactionAppend(e.messageId(), e.emoji());
        case ChannelMutationEvent.ReactionRemoved e -> broadcastReactionRemove(e.messageId(), e.emoji());
        case ChannelMutationEvent.MemberJoined e -> broadcastMemberAppend(e.channelId(), e.membership());
        // ... exhaustive via sealed interface
    }
}
```

**Key properties:**
- If push module is not on classpath, events fire with no observers — CDI handles
  this gracefully, no error, no overhead.
- CDI `Event.fire()` is synchronous — the REST response waits for broadcast to
  complete, matching the original behavior.
- Sealed interface + pattern matching gives exhaustive compile-time checking.
- Zero coupling between runtime and push modules — only the API module is shared.

### Why this is non-obvious

The obvious approach is optional dependency + `Instance<Broadcaster>`. That works
at runtime but pollutes the test classpath — CDI discovers push beans during tests,
causing infrastructure conflicts. CDI events avoid this entirely because the event
type lives in the already-shared API module, and the observer is only discovered
when the push module is explicitly on the classpath. The sealed interface pattern
adds compile-time exhaustiveness that a plain CDI event hierarchy doesn't provide.
