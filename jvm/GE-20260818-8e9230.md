### Symptom

MVEL3 expression `transaction.amount > 100` throws at compile time when evaluated against a `Map<String, Object>` deserialized from JSON:

```
bad operand types for binary operator '>'
  first type:  java.lang.Object
  second type: int
```

### Context

MVEL3 is a transpiler — it generates Java source code and compiles it with an in-memory compiler. `MVEL.getTypeMap(evalContext)` infers types from the map's values. When Jackson's `ObjectMapper.convertValue(jsonNode, Map.class)` produces nested `LinkedHashMap` values, MVEL3 sees `Object` for nested property access chains because `Map.get()` returns `Object`.

### What was tried (didn't work)

- Direct `ObjectMapper.convertValue(jsonNode, Map.class)` → nested values are `LinkedHashMap`, MVEL3 can't type-resolve through them
- Casting in expressions (`((Integer) transaction.amount) > 100`) → ugly, defeats the purpose of natural property access

### Root cause

MVEL3 type inference goes one level deep in `Map<String, Object>`. The value type of `transaction` is `LinkedHashMap`, and `LinkedHashMap.get("amount")` returns `Object` in the generated Java source.

### Fix

Deserialize the JSON to the actual POJO before MVEL evaluation. When `PojoAdapterMvelExpression.toMap()` converts a POJO, nested property values retain their concrete Java types (`Transaction` object, not `LinkedHashMap`). MVEL3 then resolves `transaction.amount` as `Transaction.getAmount()` → `int`.

```java
// Bad: Map-based evaluation — nested access fails
Map<String, Object> contextMap = mapper.convertValue(jsonNode, Map.class);
platformMvel.compile(expr, Map.class, Boolean.class).eval(contextMap);

// Good: POJO-based evaluation — nested access works
Object pojo = new JacksonPojoBridge<>(contextClass).deserialise(jsonNode);
platformMvel.compile(expr, contextClass, Boolean.class).eval(pojo);
```

### Why this is non-obvious

MVEL2 (interpreted mode) handles Map property navigation at runtime. MVEL3's transpiler generates static Java source — the type system is fundamentally different, and the error appears at an unexpected phase (Java compilation, not MVEL parsing).

### Why this fix

The POJO path uses the same `PojoAdapterMvelExpression` that the platform already provides — it converts POJO → Map with typed values via JavaBean introspection. No new MVEL infrastructure needed.

### Alternatives considered

- Flatten nested maps before evaluation — loses structural fidelity, breaks expressions that reference parent objects
- Use MVEL2 interpreted mode — not available in MVEL3, which is a complete rewrite
- Thread type hints through the expression evaluator — unnecessary complexity when JacksonPojoBridge already solves it
