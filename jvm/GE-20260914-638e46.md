# APT-generated REST endpoints return 200 with null body instead of 404 for missing resources

## Symptom
After migrating from hand-written JAX-RS resources to APT-generated ones, GET-by-ID
endpoints return HTTP 200 with a JSON `null` body when the resource doesn't exist.
The old hand-written code returned 404.

## Context
When a code generator produces JAX-RS resources from SPI interfaces, the generated
code typically wraps every return value in `Response.ok(result).build()`. If the
service method returns `null` (e.g. "entry not found"), the generated resource
faithfully wraps `null` in a 200 response.

Hand-written resources had explicit null-checking:
```java
return repository.findById(id)
    .orElseThrow(() -> new NotFoundException("Entry not found: " + id));
```

Generated resources are a thin pass-through:
```java
public Response getEntry(UUID id, String tenancyId) {
    return Response.ok(spi.getEntry(id, tenancyId)).build();
}
```

## Root cause
The APT generator has no way to know which return values represent "not found" vs
legitimate results. It generates a uniform `Response.ok()` wrapper for all methods.
The service layer returns `null` for missing resources (correct for GraphQL where
null is valid), but the REST layer needs to map null → 404.

## Fix
Add a JAX-RS `ContainerResponseFilter` that converts 200-with-null-body to 404:

```java
@Provider
public class NullBodyTo404Filter implements ContainerResponseFilter {
    @Override
    public void filter(ContainerRequestContext req, ContainerResponseContext resp) {
        if (resp.getStatus() == 200 && resp.getEntity() == null) {
            resp.setStatus(404);
        }
    }
}
```

Alternatively, make the service throw a domain exception that the exception mapper
handles — but this adds REST-specific semantics to a framework-agnostic service layer.

### Why this is non-obvious
The semantic regression is invisible at compile time and only surfaces during
integration testing. A developer migrating from hand-written to generated endpoints
would expect the same HTTP status codes. The issue is that error-handling logic lived
in the hand-written resource layer, not in the service — so it's silently dropped
when the resource is replaced with generated code.

### Alternatives considered
- Making the service throw exceptions: works but couples the service to REST semantics,
  breaking GraphQL where null is the correct "not found" response.
- Adding null-checking to the generator itself: correct long-term fix but requires
  the generator to understand which methods represent "get by ID" vs "list" operations.
