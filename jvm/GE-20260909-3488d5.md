### Symptom

`ExpressionEngine.compile(expression, Object.class, Boolean.class)` throws:

```
ExpressionCompilationException: Failed to introspect POJO class: java.lang.Object
  Caused by: IntrospectionException: java.lang.Object not superclass of java.lang.Object
```

The error message is circular and misleading — suggests a class hierarchy issue.

### Context

When compiling MVEL expressions for generic contexts where the runtime type is unknown (e.g., YAML-declared predicates evaluated against pattern-specific types), the natural approach is to use `Object.class` as the context type and rely on MVEL's duck-typing.

### What was tried (didn't work)

Passing `Object.class` as the context type to `ExpressionEngine.compile()`. Java's `Introspector.getBeanInfo(Object.class, Object.class)` internally checks `stopClass.isAssignableFrom(beanClass)` — when both are `Object`, the superclass check fails.

### Root cause

`MvelExpressionEngine.PojoAdapterMvelExpression` calls `Introspector.getBeanInfo(contextType, Object.class)` to discover bean properties. When `contextType` IS `Object.class`, `Introspector` rejects it because the stop class (`Object`) is not a proper superclass of the bean class (also `Object`).

### Fix

Use `Map.class` instead of `Object.class` as the context type. MVEL evaluates Map keys as property accesses, so expressions like `"priority > 5"` work against `Map<String, Object>` contexts:

```java
@SuppressWarnings("unchecked")
var compiled = engine.compile(expression,
        (Class<Map<String, Object>>) (Class<?>) Map.class, Boolean.class);
```

For typed contexts where the class is known, use the specific class directly.

### Why this is non-obvious

The `ExpressionEngine.compile()` API accepts `Class<C>` for the context type with no documented restriction against `Object.class`. The error message ("java.lang.Object not superclass of java.lang.Object") doesn't point to the fix. The actual limitation is in `java.beans.Introspector`, not in MVEL or the ExpressionEngine.

### Alternatives considered

- Using MVEL's direct `MVEL.eval(expression, context)` — bypasses the ExpressionEngine SPI entirely, loses type-safe compilation and caching
- Deferring expression compilation to runtime when the actual context type is known — correct long-term approach but requires deferred compilation infrastructure
