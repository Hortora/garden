## Quarkus RAG ingestion cursor defaults to tmpdir — silent entry loss on reboot

### Symptom

After a machine reboot, the Hortora engine starts normally, Qdrant has its persisted data, but new entries written before the reboot are silently not re-ingested. `gardenStatus()` shows the correct count (entries already in Qdrant from before), but the cursor tracking is lost.

### Context

`casehub-neocortex-rag`'s `IngestionConfig.cursorDir()` defaults to `${java.io.tmpdir}/casehub-ingestion-cursors`. On macOS, `java.io.tmpdir` resolves to `/var/folders/XX/.../T/` which is cleaned on reboot.

The cursor is a JSON map of `{filename: lastModifiedTimestamp}`. It tracks which files have been ingested so only changes since the last cursor are processed.

### Root cause

After reboot:
1. Cursor file is gone (tmpdir cleaned)
2. Qdrant collection still exists (data persists in Podman VM disk)
3. `CorpusIngestionService.doProcessBinding()` finds no cursor → calls `fullScan()`
4. `fullScan()` returns all files as `ADDED`
5. All files are re-embedded and re-ingested — **but this is actually correct recovery**

The real risk is more subtle: if the engine was stopped mid-ingestion (some files processed, cursor partially advanced), and then reboots, the cursor is lost. The engine does a full scan which re-ingests everything — including files already in Qdrant. This creates duplicate Qdrant points for the same `sourceDocumentId`.

### Fix

Configure the cursor directory to a persistent location:

```properties
# application.properties
casehub.rag.ingestion.cursor-dir=${hortora.garden.path}/../cursors
```

This places the cursor at `~/.hortora/cursors/garden.cursor` which survives reboots.

After changing the config, copy the existing cursor:
```bash
cp /var/folders/.../T/casehub-ingestion-cursors/garden.cursor ~/.hortora/cursors/garden.cursor
```

### Why this is non-obvious

The `java.io.tmpdir` default is standard for JVM applications and works correctly during normal operation. The failure only manifests after a reboot — and even then, the engine appears to work correctly because Qdrant still has data. The silent failure is that cursor state is lost, which may cause duplicate ingestion or missed incremental updates depending on timing.

### Alternatives considered

- Storing cursor in Qdrant payload metadata — rejected: adds coupling between cursor management and vector storage
- Using a SQLite database for cursor state — overkill for a single file cursor
