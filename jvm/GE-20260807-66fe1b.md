**Symptom:** Contract test `lastNoiseDismissalTime` fails — `Optional.isPresent()` returns `false` even though matching rows exist in the database. The `MAX(closed_at)` aggregate returns a non-null value, but the result is silently discarded by the type-matching logic.

**Context:** JPA `@ApplicationScoped` bean using native SQL (`em.createNativeQuery(...)`) to compute `SELECT MAX(closed_at) FROM ras_outcome_record WHERE ...`. The `closed_at` column is `TIMESTAMP NOT NULL`. The result list contains one element but it is neither `java.time.Instant` nor `java.sql.Timestamp` — pattern matching against both types falls through.

**Root cause:** Hibernate's native query layer does not convert PostgreSQL `TIMESTAMP` results to `java.time.Instant`. The raw result type depends on the JDBC driver and Hibernate dialect — it may be `java.sql.Timestamp`, `java.time.LocalDateTime`, or another temporal type. Attempting `instanceof` checks against a fixed set of types is fragile and driver-dependent.

**Fix:** Use JPQL with the entity class instead of native SQL for typed aggregate queries:

```java
List<Instant> results = em.createQuery(
    "SELECT MAX(e.closedAt) FROM OutcomeRecordEntity e " +
    "WHERE e.situationId = :sid AND e.correlationKey = :ck " +
    "AND e.tenancyId = :tid AND e.classification = :cls",
    Instant.class)
    .setParameter("sid", situationId)
    .setParameter("ck", correlationKey)
    .setParameter("tid", tenancyId)
    .setParameter("cls", OutcomeClassification.NOISE)
    .getResultList();
```

JPQL with the entity's mapped field type (`Instant`) handles the conversion correctly — Hibernate knows the field mapping and applies the right type converter.

**Reserve native SQL** for operations JPQL cannot express: `INSERT ... ON CONFLICT DO NOTHING`, bulk `DELETE` with complex conditions, or non-standard SQL features.

### Alternatives considered
- Pattern matching against `Instant`, `java.sql.Timestamp`, `LocalDateTime` — fragile, driver-dependent, not future-proof.
- `addScalar("closed_at", StandardBasicTypes.INSTANT)` on the native query — ties the query to Hibernate internals.

**Why this is non-obvious:** The native query compiles, runs, and returns results — no exception is thrown. The `MAX()` value is simply not an `Instant`, so the method returns `Optional.empty()`. The failure is silent and only surfaces as a test assertion error. JPQL with the same aggregate function works correctly because Hibernate uses the entity field's type mapping.
