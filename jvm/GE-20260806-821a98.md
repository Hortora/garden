## Symptom

`jakarta.enterprise.inject.AmbiguousResolutionException` at build time — two beans qualify for the same injection point, both showing `qualifiers=[@Any, @Default]`. One is the upstream library's NoOp (e.g. `NoOpAttestationIntentWriter`), the other is the downstream application's real implementation (e.g. `DefaultAttestationIntentWriter`).

## Context

Multi-module Quarkus project where:
- Module A (upstream library) provides `@DefaultBean @ApplicationScoped NoOpFoo implements Foo` — a no-op fallback
- Module B (downstream application) provides `@DefaultBean @ApplicationScoped RealFoo implements Foo` — the real implementation
- Both are `@DefaultBean`, so both are "defaults" — CDI cannot resolve priority

This typically manifests when an **upstream SNAPSHOT changes** from `@DefaultBean` to plain `@ApplicationScoped`. Before the change, Module A's bean was `@DefaultBean` (lower priority) and Module B's bean was `@ApplicationScoped` (higher priority, displaces the default). After the change, both are `@ApplicationScoped`, creating ambiguity.

But the same bug exists when both modules independently use `@DefaultBean` — the displacement semantics of `@DefaultBean` only work when ONE bean is `@DefaultBean` and the OTHER is a regular `@ApplicationScoped` bean.

## What was tried (didn't work)

- Assuming `@DefaultBean` means "I'm the canonical default" — it doesn't. `@DefaultBean` means "I'm the fallback, displace me." Two fallbacks = ambiguity.
- Adding `@Priority` to the downstream bean alongside `@DefaultBean` — `@DefaultBean` and `@Priority` don't compose the way you'd expect.

## Root cause

`@DefaultBean` is a Quarkus Arc extension annotation meaning "only activate if no other bean satisfies this injection point." It is NOT "I am the default implementation." When both upstream and downstream use `@DefaultBean`, neither is displaced — both remain as candidates. CDI sees two `@Default`-qualified beans and throws `AmbiguousResolutionException`.

## Fix

The real implementation should NEVER be `@DefaultBean`. Remove `@DefaultBean` from the downstream application's implementation:

```java
// WRONG — both are @DefaultBean, ambiguous
@ApplicationScoped
@DefaultBean  // ← remove this
public class RealFoo implements Foo { ... }

// RIGHT — plain @ApplicationScoped displaces any @DefaultBean
@ApplicationScoped
public class RealFoo implements Foo { ... }
```

The upstream NoOp keeps `@DefaultBean` — that's correct, it IS the fallback. The downstream Real is the actual implementation — it should be `@ApplicationScoped` (which takes CDI priority over `@DefaultBean` automatically).

## Why this is non-obvious

The name `@DefaultBean` suggests "this is the default." A developer writing a real implementation naturally writes `@DefaultBean` thinking "this is the default implementation for this project." The actual semantic — "displace me if anything else exists" — is the opposite of what the name implies. The Quarkus docs explain the semantics but the name actively misleads.

### Alternatives considered

- `@Alternative @Priority(1)` on the downstream bean — works but is heavier than necessary. Plain `@ApplicationScoped` already displaces `@DefaultBean` without explicit priority.
- `quarkus.arc.exclude-types` to exclude the upstream NoOp — fragile, breaks if the upstream renames the class.
