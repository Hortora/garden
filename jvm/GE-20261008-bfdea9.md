### Symptom

A module that is intentionally CDI-free (pure Java, no Jakarta dependencies) needs to participate in a CDI decorator chain. Adding `@Decorator @Priority` annotations would require adding `jakarta.enterprise.cdi-api` as a dependency, breaking the module's tier contract.

### Context

In a multi-module Maven project with tiered dependencies, lower-tier modules (e.g. `caps-engine`) contain pure logic with no CDI. Higher-tier modules (e.g. `mindmap-intelligence`) have full CDI support. When a decorator's logic belongs in the lower tier but CDI wiring belongs in the higher tier, the two concerns need separation.

### Fix

Split the decorator into two classes across two modules:

**Lower tier (CDI-free):** Pure logic class that implements the SPI and takes the delegate via constructor:

```java
// caps-engine — no CDI dependency
public class SubThoughtSituationDecorator implements SituationClassifier {
    private final SituationClassifier delegate;

    public SubThoughtSituationDecorator(SituationClassifier delegate) {
        this.delegate = delegate;
    }

    @Override
    public List<SituationActivation> classify(String description, Map<String, String> metadata) {
        List<SituationActivation> base = delegate.classify(description, metadata);
        // decorator logic...
    }
}
```

**Higher tier (CDI-enabled):** Thin subclass with only CDI annotations:

```java
// mindmap-intelligence — has CDI
@Decorator
@Priority(70)
public class SubThoughtSituationCdiDecorator extends SubThoughtSituationDecorator {
    @Inject
    public SubThoughtSituationCdiDecorator(@Delegate @Any SituationClassifier delegate) {
        super(delegate);
    }
}
```

### Why this is non-obvious

The natural instinct is to put `@Decorator` directly on the class that has the logic. When that module can't have CDI dependencies, developers typically either add CDI as a `provided` dependency (breaking the tier contract) or duplicate the logic in the CDI-enabled module (violating DRY). The inheritance-based split preserves both the tier boundary and single-source logic.

### Alternatives considered

- Adding `jakarta.enterprise:jakarta.enterprise.cdi-api` as `<optional>true</optional>` to caps-engine — rejected because it pollutes the dependency graph for all consumers of caps-engine
- Moving the decorator logic to mindmap-intelligence — rejected because the classification mappings are caps-domain knowledge, not mindmap-domain
- Using a CDI `@Interceptor` instead — not applicable; decorators and interceptors serve different purposes
