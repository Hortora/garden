### Symptom

Integration test fails with `ConditionTimeoutException` — Awaitility polling never sees `status=completed`. Investigation appears stuck. Worker execution logs show repeated NPEs for `entity-resolution-agent` on retry attempts.

### Context

`@QuarkusTest` with surefire `rerunFailingTestsCount > 0`. Test starts an async investigation, approves an oversight gate, drains to completion, then calls `workItemService.complete(taskId, actorId, resolution, outcome)` to simulate compliance officer review.

### What was tried (didn't work)

1. Switching the investigation start endpoint (Layer 6 → Layer 9 → Layer 5) — all timed out
2. Combining sequential Awaitility blocks into a single polling loop — improved robustness but didn't fix this test
3. Increasing poll intervals — no effect

### Root cause

The `outcome` parameter passed to `workItemService.complete()` was `"APPROVED"` — not in the WorkItem's `completeOutcomes` list (`[file, clear, escalate]`). Run 1 throws `IllegalArgumentException` at the `complete()` call (AFTER the investigation successfully completed). Surefire retries the test. Runs 2 and 3 start in a JVM where Run 1's investigation left partial state — the `entity-resolution-agent` crashes on missing context keys, the investigation never completes, and Awaitility times out.

The developer sees the timeout (Runs 2/3) but not the real error (Run 1's `IllegalArgumentException`), because surefire's retry output buries Run 1's stack trace above the final failure report.

### Fix

Pass a valid outcome value from the WorkItem's `completeOutcomes` list:

```java
// Wrong — throws IllegalArgumentException
workItemService.complete(taskId, "officer-001", "SAR approved", "APPROVED");

// Right — "file" is in the allowed outcomes [file, clear, escalate]
workItemService.complete(taskId, "officer-001", "SAR approved", "file");
```

When debugging surefire rerun timeouts: always check Run 1's output first. The real error is often a fast failure (validation, NPE, assertion) that surefire retried, and the retry fails differently due to corrupted JVM state.

### Why this is non-obvious

The timeout in Runs 2/3 is a compelling but wrong diagnosis. The developer naturally focuses on the timeout (it's the final error), investigates thread pool exhaustion, endpoint stability, and Awaitility configuration — none of which are the cause. The real error (`IllegalArgumentException` with a clear message about allowed outcomes) is in Run 1's output, which surefire prints above the retry summary and is easy to scroll past.
