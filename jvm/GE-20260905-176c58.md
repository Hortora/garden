## Symptom

`verify(mock).method(eq("topic"), any())` reports "wanted but not invoked" even though Mockito's error message shows the exact expected interaction DID happen — on a different method overload. The error points to line N (the `String` overload) while the actual interaction was recorded on line M (the generic overload).

## Context

A Java class has two overloaded methods:

```java
public long broadcast(String topic, String payloadJson) { ... }    // line 20
public <T> long broadcast(String topic, T event) { ... }           // line 37
```

After type erasure, the generic method becomes `broadcast(String, Object)`. Both methods exist in the bytecode. Mockito tracks interactions per-method — a call to `broadcast(String, Object)` is recorded on a different method handle than `broadcast(String, String)`.

When test code calls `verify(mock).broadcast(eq("topic"), any())`, Java's overload resolution at compile time determines which method the verify targets. `any()` returns `null` of inferred type — both overloads are applicable, so Java picks the most specific: `broadcast(String, String)`. But the actual production code called `broadcast("topic", notification)` where `notification` is a `Notification` (not `String`), which dispatched to `broadcast(String, Object)`.

Result: verify checks one method, interaction recorded on another.

## What was tried (didn't work)

1. **Type witnesses:** `verify(mock).<Object>broadcast(eq("..."), any())` — type witnesses constrain type parameter inference but do NOT override Java's overload resolution rules. The compiler still picks the most specific applicable overload.

2. **Bare `any()`** — always resolves to the `String` overload because `null` (returned by `any()`) is assignable to `String`, and `broadcast(String, String)` is more specific than `broadcast(String, Object)`.

## Fix

Use typed matchers that make the `String` overload inapplicable:

```java
// For known payload types — forces generic overload because Notification is not String
verify(mock).broadcast(eq("topic"), any(Notification.class));

// For unknown/private payload types — Object is not assignable to String,
// so compiler must use the generic overload
verify(mock).broadcast(eq("topic"), any(Object.class));

// For total-count verification
verify(mock, times(2)).broadcast(anyString(), any(Object.class));
```

`any(Object.class)` has static return type `Object`. Since `Object` is NOT assignable to `String`, the `broadcast(String, String)` overload becomes inapplicable, and the compiler resolves to `broadcast(String, T)` with `T=Object`.

### Alternatives considered

- Type witnesses (`.<T>method(...)`) — do not work because they affect type parameter inference, not overload resolution. Java's JLS §15.12.2 selects the most specific applicable method before applying type witnesses.
- Casting the matcher result (`(Object) any()`) — technically works but is confusing and fragile.

## Why this is non-obvious

The Mockito error message is actively misleading. It shows:

```
Wanted but not invoked:
  mock.broadcast("topic", <any>);
However, there was exactly 1 interaction:
  mock.broadcast("topic", SomeObject[...]);
```

The "wanted" and "however" lines look identical in structure — same method name, compatible arguments. The only clue is the `-> at` line reference, which points to different line numbers in the source class. Without understanding that Mockito tracks overloaded methods as distinct method handles (even after erasure), the error looks like a Mockito bug, not a type system issue.
