# Quarkus Dev Services do not activate in pre-built jars started via ProcessBuilder

### Symptom
Starting a pre-built Quarkus fast-jar via `java -jar quarkus-run.jar -Dquarkus.profile=test` — the application fails to start because it cannot connect to PostgreSQL (or other Dev Services-managed resources). No container is auto-started despite the test profile being active.

### Context
Integration tests that start real Quarkus services as separate JVM processes using `ProcessBuilder`. The developer expects `-Dquarkus.profile=test` to activate Dev Services (auto-start PostgreSQL, Kafka, etc.) the same way `@QuarkusTest` does.

### What was tried (didn't work)
- Starting the jar with `-Dquarkus.profile=test` — profile activates test config overrides but Dev Services do not start
- Starting with `-Dquarkus.profile=dev` — same result; Dev Services require the Quarkus test/dev framework context

### Root cause
Quarkus Dev Services are part of the **augmentation** (build-time) process, not a runtime feature. They activate during:
1. `quarkus:dev` (development mode — the Quarkus Maven/Gradle plugin manages them)
2. `@QuarkusTest` (test mode — the JUnit extension manages them)

When running a pre-built jar via `ProcessBuilder`, augmentation already happened at build time. The runtime has no mechanism to start containers — it only reads the datasource config properties, which point to nothing.

### Fix
Provision the database externally in the test JVM and pass connection URLs as system properties to the Quarkus process:

```java
// In the test JVM — start PostgreSQL via Testcontainers
PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16-alpine");
pg.start();

// Pass to the Quarkus process via system properties
String reactiveUrl = "postgresql://" + pg.getHost() + ":" + pg.getFirstMappedPort() + "/" + pg.getDatabaseName();
// -Dquarkus.datasource.reactive.url=<reactiveUrl>
// -Dquarkus.datasource.jdbc.url=<pg.getJdbcUrl()>
// -Dquarkus.datasource.username=<pg.getUsername()>
// -Dquarkus.datasource.password=<pg.getPassword()>
```

### Why this is non-obvious
A developer familiar with Quarkus profiles expects `-Dquarkus.profile=test` to produce identical behavior to running inside `@QuarkusTest`. The mental model is "profile = behavior," but Dev Services are an augmentation-time feature, not a profile-activated feature. The Quarkus docs describe Dev Services as available "during development and testing" without clarifying the augmentation-time constraint.

### Alternatives considered
- Adding H2 fallback profiles to the service — works for JDBC but not for reactive PostgreSQL drivers (H2 doesn't support the Vert.x reactive client)
- Requiring a running PostgreSQL instance — less portable, harder in CI
