### Context
When extracting a Quarkus CDI module into a framework-neutral `-core` module for
dual Quarkus/Spring deployment, reactive session managers (Vert.x WebClient + Mutiny Uni
for lazy concurrent session init with `memoize().indefinitely()`) block the extraction of
the execution manager — even when the execution manager itself uses only JDK HttpClient.

The coupling point is a single call:
`sessionManager.getOrInitialize(serverName).await().indefinitely()` — a blocking bridge
from Mutiny Uni to get a session object.

### Symptom
The execution manager (pure JDK HttpClient, Jackson JSON-RPC, SSE parsing) can't move
to a -core module because it directly references the Vert.x/Mutiny-coupled session manager
class.

### What was tried (didn't work)
Moving the entire session manager to core — impossible because it creates `WebClient.create(vertx)`
and uses `Uni` throughout for async session init with Vert.x-native HTTP calls.

### Fix
Define a blocking SPI interface in the core module:

```java
public interface McpSessionProvider {
    McpSession getSession(String serverName);
    void invalidate(String serverName);
}
```

The execution manager takes `McpSessionProvider` (blocking) instead of the concrete
session manager. The Quarkus module's session manager implements the interface with a
one-line bridge:

```java
@Override
public McpSession getSession(String serverName) {
    return getOrInitialize(serverName).await().indefinitely();
}
```

Spring can provide a different implementation using JDK HttpClient for the MCP handshake.

### Why this is non-obvious
The instinct is to migrate the session manager itself (replace Vert.x with JDK HttpClient).
But the session manager's value is in its reactive caching (`memoize().indefinitely()`) and
concurrent dedup — reimplementing that with CompletableFuture is complex and error-prone.
The SPI recognises that the execution manager doesn't need reactivity — it just needs a
session. The blocking interface is the minimal seam.

### Root cause
The execution manager's dependency on the session manager is a *data* dependency (it needs
an `McpSession` object), not a *behaviour* dependency (it doesn't need reactive streams).
Introducing the SPI at that seam lets the data flow through a blocking interface while the
reactive lifecycle stays encapsulated.
