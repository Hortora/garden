## Map.copyOf rejects null values — silent NPE when copying record-derived maps

### Symptom

Bare `NullPointerException` with no message. Caught by an outer exception handler and surfaced as the string `"java.lang.NullPointerException"` — no stack trace, no field name, no indication which value was null or where it originated.

### Context

A Java record with nullable fields — `website`, `nextCursor` — is converted to a `Map<String, Object>` via a reflection-based `toMap()` utility that walks record components. The resulting map contains entries like `{website=null, nextCursor=null}`. This map is later passed to `Map.copyOf()` for an immutable snapshot.

### What was tried (didn't work)

1. **Direct step execution** — the operation succeeded. The map was created, used, and discarded without hitting `Map.copyOf`.
2. **Full playbook execution** — failed with the bare NPE. No indication which step or which field.
3. **Removing the `capture:` decorator** (which triggers the `Map.copyOf` path) — the step passed. This isolated the failure to a single code path.

### Root cause

`Map.copyOf()` (Java 10+) calls `Map.of()` internally, which rejects both null keys AND null values — throwing a bare `NullPointerException` with no message.

The upstream `Result.Success` constructor uses `LinkedHashMap` with `Objects.requireNonNull` on keys only — null values pass validation. This creates a contract gap: the map is valid at creation but invalid at copy.

```java
// Result.Success — allows null values ✓
output.forEach((key, value) -> snapshot.put(Objects.requireNonNull(key), value));

// Later, in the capture registration — rejects null values ✗
Map<String, Object> captured = Map.copyOf(result.output());  // NPE here
```

### Fix

Replace `Map.copyOf()` with the null-safe equivalent:

```java
Map<String, Object> captured = Collections.unmodifiableMap(
    new LinkedHashMap<>(result.output()));
```

Same immutability guarantee. Allows null values. Matches the pattern already used in the `Result.Success` constructor.

### Why this is non-obvious

`Map.of()` rejecting null keys is well-known. `Map.copyOf()` rejecting null *values* is less known — the Javadoc mentions it, but developers rarely encounter it because most manually-constructed maps don't have null values. When record fields are nullable (normal for domain models), a reflection-based `toMap()` preserves them faithfully, and the NPE appears far from the null's origin.

The diagnostic isolation is also worth noting. The operation worked in every test mode except one specific execution path. The systematic narrowing — direct execution (passes), playbook execution (fails), with capture (fails), without capture (passes) — was the only way to isolate the single `Map.copyOf` line in the capture code path.

### Alternatives considered

- **Filter null values in `Records.toMap()`** — rejected because null vs absent has different semantics in domain models. A `website=null` means "no website"; omitting `website` entirely could mean "not queried" or "field doesn't exist". The map layer should preserve what the record says.
- **Use `Map.ofEntries()` with null filtering** — same objection, plus it changes the contract for all callers.
