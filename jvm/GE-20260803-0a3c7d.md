### Symptom
Declaring `dispositionProfile` as a top-level map on the descriptor or as a `Map<String, Double>` inside `disposition:` either fails to parse or silently produces an empty profile.

### Context
The `AgentDisposition` record stores `dispositionProfile` as `List<DispositionValue>` where each `DispositionValue` has `term` (String) and `weight` (double). The YAML registrar expects this exact structure inside the `disposition:` block.

### Root cause
Two format mismatches are possible:
1. `dispositionProfile` declared at the descriptor level (outside `disposition:`) — ignored by the registrar
2. `dispositionProfile` declared as a map (`Se: 0.45, Fi: 0.20`) instead of a list of `{term, weight}` objects — Jackson cannot deserialize a map into `List<DispositionValue>`

### Fix
Declare as a list of `{term, weight}` objects inside `disposition:`:

```yaml
disposition:
  delegation: false
  dispositionProfile:
    - term: se
      weight: 0.45
    - term: fi
      weight: 0.20
    - term: te
      weight: 0.10
```

Wrong (map format — silently ignored or fails):
```yaml
dispositionProfile:
  Se: 0.45
  Fi: 0.20
```

Wrong (outside disposition block — ignored):
```yaml
disposition:
  delegation: false
dispositionProfile:
  - term: se
    weight: 0.45
```

### Why this is non-obvious
The Eidos API summary describes the profile as `Map<String, Double>` weights. The YAML format requires the Jackson-deserializable `List<{term, weight}>` structure — a different representation of the same data. The mismatch between API documentation and YAML format is the trap.
