### Symptom

Multi-tier fault escalation (retry → AI review → human review) requires knowing whether a previous tier was attempted. The naive approach checks external domain state (e.g. `PipelineWorld.ReviewState`), coupling the generic escalation mechanism to domain-specific state tracking.

### Context

In a desired-state runtime, fault policies react to node failures by mutating the graph (adding review nodes). Multi-tier escalation needs a guard: "only escalate to tier N+1 if tier N was attempted and hasn't resolved the issue." The existing `ProvisionEscalationFaultPolicy` checked `PipelineWorld` for review state — ~50 lines of hand-rolled, domain-coupled logic.

### Technique

Use the graph's own dependency structure as the escalation signal:

1. When a review node is created, add a dependency edge from it to the faulted node (`Dependency(reviewId, faultedId)`)
2. To check whether tier N was attempted, query `current.dependentsOf(faultedNodeId)` and check if any dependent has tier N's `NodeType`

```java
boolean previousTierPresent = current.dependentsOf(event.node()).stream()
        .map(depId -> current.nodes().get(depId))
        .filter(Objects::nonNull)
        .anyMatch(n -> n.type().equals(previousTierNodeType));
```

The graph IS the state. No external tracking, no ID-convention coupling, no domain-specific resolution checks.

### Why this is non-obvious

The natural instinct is to track escalation state separately — a map of node → current tier, or domain-specific review state. Using `dependentsOf()` for this purpose is counter-intuitive because dependency edges are typically thought of as ordering constraints (provision A before B), not as queryable state. The technique exploits the dual nature of dependency edges: they are both ordering constraints AND structural relationships that encode "this review node exists because of that faulted node."

### Caveats

- Review nodes MUST have dependency edges to the faulted node for this to work. `GraphMutations.addNodeDependingOn()` and `FaultPolicy.addReviewNode()` ensure this by default.
- Resolution requires removing the review node from the desired graph (not just changing its state). Lingering resolved review nodes would cause false-positive escalation detection.
- Each tier declares its `NodeType` so the guard can distinguish tier 1 review nodes from tier 2 review nodes among the dependents.
