### Symptom

MCP clients calling `resources/subscribe` with a template-resolved URI (e.g., `iot://devices/123/state` from template `iot://devices/{deviceId}/state`) receive a `Resource not found` error. The same URI works for `resources/read` — it resolves through the template manager correctly. But subscription fails silently or with an error.

### Context

When registering an MCP resource template via `ResourceTemplateManager.newResourceTemplate()`, the template handles `resources/read` correctly — the framework resolves the template variables and dispatches to the handler. However, `resources/subscribe` and `resources/unsubscribe` go through `ResourceManagerImpl.subscribe()`, which only checks `uriToResource` — a map that contains statically registered resources, not template-resolved URIs.

### Root cause

`ResourceManagerImpl.subscribe()` calls `getResource(uri)` which looks up `uriToResource.get(uri)`. This map is populated by `newResource().register()` (static resources) but NOT by template resolution. Template-resolved URIs are handled by `resourceTemplateManager.getInvoker()` in the read path, but the subscribe path doesn't fall through to the template manager.

```java
// ResourceManagerImpl.java — subscribe() only checks static resources
void subscribe(String uri, McpRequest mcpRequest) {
    ResourceInfo info = getResource(uri);  // only checks uriToResource map
    if (info == null || !matchesServer(info, mcpRequest)) {
        throw notFound(uri);  // template-resolved URIs always fail here
    }
    // ...
}
```

Compare with the read path which DOES fall through:
```java
// ResourceManagerImpl.java — getInvoker() checks templates as fallback
protected FeatureInvoker<ResourceResponse> getInvoker(String id, McpRequest mcpRequest, ...) {
    ResourceInfo resource = uriToResource.get(id);
    if (resource instanceof FeatureInvoker fi && ...) {
        return fi;
    }
    return resourceTemplateManager.getInvoker(id, mcpRequest, message);  // template fallback
}
```

### Fix

**Workaround (current):** For resources that need subscription, register them as individual STATIC resources via `ResourceManager.newResource()` instead of using a template. Each static resource gets its own `ResourceInfo` with `sendUpdateAndForget()`. This scales for small entity sets but not for IoT-class workloads.

**Proper fix (upstream):** `ResourceManagerImpl.subscribe()` should fall through to `resourceTemplateManager` when `getResource()` returns null, similar to how `getInvoker()` handles reads.

### Why this is non-obvious

The MCP protocol spec says clients can subscribe to any resource URI. The quarkus-mcp-server API provides `ResourceTemplateManager` and `ResourceInfo.sendUpdateAndForget()`. Nothing in the API or documentation suggests that templates and subscriptions are incompatible. The limitation is only visible by reading `ResourceManagerImpl.subscribe()` source code.
