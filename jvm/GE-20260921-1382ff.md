## Symptom

A CDI `@Decorator` generated from an `@SimulationEligible` annotation intercepts all
methods on the annotated interface. For flat SPIs (BankFeedPlatform — every method returns
data), corpus-based simulation strategies work perfectly. For capability-based SPIs
(ChatPlatform — methods like `messaging()` return sub-interfaces like `Messaging`), the
decorator intercepts at the wrong level: it intercepts `messaging()` but the actual data
methods (`send()`, `listChannels()`) live one level deeper on the returned capability
interface. Corpus YAML can produce data objects but cannot produce interface implementations.

## Context

Surfaces when extending a build-time annotation processor (like `SimulationDecoratorProcessor`)
to support composite/capability-based SPIs where the top-level interface is a factory for
sub-interfaces. The CDI `@Decorator` pattern requires a CDI-managed injection point — the
capability sub-interfaces are factory-returned objects, not CDI beans, so they can't have
their own independent decorators.

## What developers would normally try

1. Annotate each capability sub-interface with `@SimulationEligible` independently — fails
   because capabilities aren't CDI beans (they're returned by factory methods, not injected)
2. Auto-detect capability methods by return type heuristic (is it an interface? is it not
   in java.*?) — fragile, encodes domain knowledge in the framework, breaks when new wrapper
   types are introduced

## Solution

Extend the generator to support **recursive wrapper generation** via an explicit
`capabilities` attribute on the annotation:

```java
@SimulationEligible(name = "chat-platform",
    capabilities = {"messaging", "threading", "discovery", ...})
public interface ChatPlatform { ... }
```

The generator reads the `capabilities` list and for each listed method:
1. Finds the method on the SPI interface via Jandex
2. Generates a wrapper class implementing the return type's interface
3. Each wrapper method uses the same intercept-or-delegate pattern with **dotted
   qualified names**: `chat-platform.messaging.send`
4. The top-level decorator returns the wrapper, passing `delegate.messaging()` as
   the inner delegate

Methods NOT in `capabilities` get standard flat interception.

The `capabilities` attribute keeps domain knowledge (which methods return capabilities)
in the domain code (the SPI annotation), not in the framework. An auto-detection heuristic
was considered and rejected — it couples domain knowledge to framework internals and
requires an exclusion list that grows with every new wrapper type.

## Why this is non-obvious

The CDI `@Decorator` pattern works at the injection-point level. When an interface's
methods return other interfaces, the natural assumption is that each sub-interface needs
its own decorator. But capability objects aren't CDI-managed — they're constructed by
builders or factory methods. The solution requires the top-level decorator to generate and
return wrapping implementations of interfaces it doesn't own, using a naming convention
(dotted QNs) to connect corpus strategies across the boundary.

### Why this fix

An explicit `capabilities` attribute is better than auto-detection because the set of
capability methods is a domain decision, not a type-system property. A method returning
an interface might be a capability accessor (should wrap) or a data factory (should not
wrap). Only the SPI author knows which — and they already maintain the list when updating
the Builder, DefaultRecord, and degradation defaults.

### Alternatives considered

- **Auto-detection heuristic** — inspect return types, exclude java.*/jakarta.*/List/Map/Optional.
  Rejected: encodes domain knowledge in the framework; must be updated in a different repo
  with a different release cycle when new wrapper types appear.
- **@SimulationCapability on each sub-interface** — more annotation ceremony per SPI;
  one attribute on the parent annotation is simpler.
- **Hand-written simulation wrapper per SPI** — works but creates per-SPI maintenance
  burden; contradicts the "zero hand-written simulation code" principle.
