## Symptom

Design assumes `ImplementationRoutingStrategy` with `RunAll()` (fires both workers for the same capability) and `Selected(bindingNames)` controls which workers execute. Code compiles and tests pass structurally, but workers are not dispatched as expected at runtime.

## Context

When a case YAML binding fires for a capability with multiple registered workers, the engine must select which worker(s) to invoke. The `ImplementationRoutingStrategy` interface in `casehub-engine-api` has `select(context, candidates)` returning `ImplementationSelection` (sealed: `RunAll`, `Selected`, `RunNone`). This looks like the dispatch control point.

## Root cause

The actual binding dispatch path is:

1. `CaseContextChangedEventHandler.publishWorkerSchedule()` evaluates binding guards
2. `AgentCandidateFactory.buildCandidates()` matches workers to the capability
3. `ComposableAgentRoutingStrategy` (implementing `AgentRoutingStrategy`, not `ImplementationRoutingStrategy`) collects signals from `RoutingSignalProvider` implementations
4. Scores are blended; highest-scoring candidate wins
5. `RoutingResult.assigned(workerId, ...)` dispatches a **single** worker

There is no `RunAll()` dual-fire mechanism in this path. `ImplementationRoutingStrategy` and its sealed `ImplementationSelection` type are not referenced anywhere in the binding dispatch chain.

## Fix

Design against `ComposableAgentRoutingStrategy` and `RoutingSignalProvider`, not `ImplementationRoutingStrategy`. One worker fires per capability dispatch. Bootstrap mode uses neutral trust scores (0.5); the first worker in insertion order wins by `LinkedHashMap` stream ordering in `ComposableAgentRoutingStrategy.select()`.

## Why this is non-obvious

`ImplementationRoutingStrategy` is a public API in `casehub-engine-api` with concrete implementations (`NoOpImplementationRoutingStrategy`, `TrustWeightedImplementationRoutingStrategy`). It has `ImplementationCandidate(bindingName, workerName, capabilityName)` — exactly the shape you'd expect for binding dispatch. The actual dispatch mechanism (`ComposableAgentRoutingStrategy`) uses a different type hierarchy entirely. Without tracing the call chain from `CaseContextChangedEventHandler`, the wrong API is the natural choice.

### Alternatives considered

- Building dual bindings per capability in the YAML (one per worker) with `ImplementationRoutingStrategy` selecting between them — incorrect; bindings reference capabilities, not workers
- Assuming `RunAll()` fires both workers concurrently with first-to-complete semantics — no such mechanism exists in the engine
