### Summary

Use `@ObservesAsync CaseLifecycleEvent` to decouple domain-specific reactions from the CaseHub engine's case lifecycle. The event is a CDI async event fired on every auditable case transition — observers don't need to be in the engine module.

### Context

When a case reaches a terminal state (COMPLETED, FAULTED), domain modules often need side effects — updating a query store, sending notifications, triggering downstream workflows. Coupling these to the engine's internal state machine creates circular dependencies.

### Technique

Observe `CaseLifecycleEvent` from `io.casehub.engine.common.spi.event`:

```java
@ApplicationScoped
public class CveStatusObserver {
    @Inject CveStore cveStore;

    void onCaseLifecycleEvent(@ObservesAsync CaseLifecycleEvent event) {
        if (!"ops".equals(event.namespace()) || !"cve-response".equals(event.caseDefinitionName())) return;
        if (!"COMPLETED".equals(event.caseStatus()) && !"FAULTED".equals(event.caseStatus())) return;

        JsonNode context = event.contextSnapshot();
        // Extract domain data from context, perform side effect
    }
}
```

Key fields on `CaseLifecycleEvent`: `caseId` (UUID), `namespace`, `caseDefinitionName`, `caseStatus` (String — enum name), `contextSnapshot` (JsonNode — working layer at fire time), `eventType` (e.g. "CaseCompleted"), `satisfiedGoalName`/`satisfiedGoalKind`.

### Why this is non-obvious

The natural instinct is to hook into the case definition's completion expression or add a callback in the case descriptor's worker chain. But CaseLifecycleEvent fires *after* the engine's state transition completes — it's guaranteed consistent. Worker-chain approaches run *during* the transition and can see intermediate state.

### Caveats

- `contextSnapshot` is a point-in-time read-only copy — mutations have no effect
- `fireAsync` means the observer runs on a different thread — CDI request scope is not propagated
- Filter by both `namespace` AND `caseDefinitionName` — namespace alone is too broad
