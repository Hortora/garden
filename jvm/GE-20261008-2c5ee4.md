### Symptom

Settlement tracking silently breaks — `markFullyDispatched(signalId)` is never called
for some signals. The system self-corrects on the next evaluation cycle, masking the
problem. Under load with parallel worker completions, settlement timeouts accumulate.

### Context

A `CaseEvaluationSerializer` ensures at most one evaluation runs per case at a time.
When a submission arrives while an evaluation is active, the new evaluator is stored as
`pendingEvaluator` — a single-slot design that overwrites any previously pending evaluator.
Each submission carries a `signalId` for settlement tracking.

### What was tried (didn't work)

The original design coalesced by overwriting `pendingEvaluator`. This is correct for the
evaluator itself (re-reading context at execution time captures all prior mutations). But
each overwritten submission's `signalId` was lost — the settlement tracker never received
`markFullyDispatched()` for the dropped signal.

### Root cause

Coalescing conflates two concerns: the *work* to perform (which can be safely replaced
with the latest version) and the *metadata* about who requested the work (which must be
preserved across all coalesced submissions). Overwriting the evaluator is correct;
overwriting the metadata is a silent data loss.

### Fix

Separate the single-slot evaluator (overwrite is fine) from metadata accumulation
(must be additive). Add a `Set<UUID>` to the gate that collects signal IDs from all
coalesced submissions:

```java
private static final class CaseGate {
    final ReentrantLock lock = new ReentrantLock();
    boolean evaluating;
    Runnable pendingEvaluator;
    final Set<UUID> pendingSignalIds = new HashSet<>();  // accumulates, never overwrites
}
```

On submission when coalescing:
```java
gate.pendingEvaluator = evaluator;      // overwrite — latest wins
gate.pendingSignalIds.add(signalId);    // accumulate — all preserved
```

After the coalesced evaluation completes, `drainPending()` collects all accumulated
signal IDs and returns them to the caller for settlement.

### Why this is non-obvious

The coalescing logic passes existing tests — 3 submissions correctly produce 2 evaluations.
The test validates that the evaluator is coalesced (latest wins), which is correct. The
metadata loss only surfaces under concurrent worker completions when distinct signals
carry different settlement IDs — a timing-dependent scenario that doesn't occur in
sequential test setups.

### Caveats

The `Set<UUID>` is accessed under the gate's `ReentrantLock`, so no additional
synchronisation is needed. The set is cleared after drain, so memory growth is bounded
by the maximum coalescing depth (typically 1-2 entries).
