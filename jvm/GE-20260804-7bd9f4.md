### Symptom

Type inference failure or wrong argument binding when constructing `ScoredCbrCase` in test code.

### Context

Writing unit tests that mock `CbrCaseMemoryStore.retrieveSimilar()` return values. The intuitive parameter order is `(caseId, score, cbrCase)` — ID first, like most record constructors.

### Root cause

`ScoredCbrCase` is a Java record with the case object as the **first** parameter:

```java
// Canonical (8-arg):
ScoredCbrCase(C cbrCase, String caseId, double score, boolean reranked,
              Map<String, Double> featureSimilarities, Instant storedAt,
              Path scope, Double trustTrajectory)

// 3-arg convenience:
ScoredCbrCase(C cbrCase, String caseId, double score)
```

### Fix

```java
// Wrong — caseId first
new ScoredCbrCase<>("case-1", 1.0, false, Map.of(), planCbrCase)

// Correct — cbrCase first
new ScoredCbrCase<>(planCbrCase, "case-1", 1.0)
```

### Why this is non-obvious

Most record constructors in the codebase put the ID/key field first. `ScoredCbrCase` puts the payload first because the generic type parameter `C` drives inference — placing it first lets `var` declarations work without explicit type witness.
