## Symptom

Quarkus augmentation fails with `UnsatisfiedResolutionException` for a CDI bean in a transitive dependency. The bean references a class that was removed from another transitive dependency (SNAPSHOT version skew). The app itself never uses the bean.

## Context

A transitive dependency brings in a CDI bean annotated `@ApplicationScoped @DefaultBean @Unremovable`. The bean's `@Inject` field references a class that no longer exists in the resolved SNAPSHOT. Because the bean is `@Unremovable`, Arc cannot prune it — the unsatisfied injection point is fatal.

This differs from the common exclude-types use case (GE-20260529-0c23f1) where beans are excluded because the app *replaces* them with its own implementation. Here, the beans are excluded because their injection target was *removed upstream* — there's nothing to replace them with.

## Fix

Add to `application.properties`:
```properties
quarkus.arc.exclude-types=io.casehub.ledger.runtime.service.identity.**
```

The `.**` glob excludes all classes in the package and sub-packages. Arc skips these classes entirely during bean discovery — their `@Inject` points are never validated.

## Why this is non-obvious

The natural response to an `UnsatisfiedResolutionException` is to provide the missing bean — add a dependency, write a producer, or create a stub. When the target class doesn't exist at all (removed in a newer SNAPSHOT), none of these work. The insight is to exclude the *consumer* bean rather than provide the missing *target* — prevent the injection point from being evaluated rather than trying to satisfy it.

### Alternatives considered

- Adding a no-op stub implementation of the removed class — rejected because it creates a maintenance burden and masks the real problem (stale upstream dependency)
- Downgrading the SNAPSHOT that removed the class — rejected because it would revert other fixes
- Rebuilding the intermediate dependency — correct long-term fix but requires access to the upstream repo and a release cycle
