### Symptom
POST to an action endpoint (e.g. `/api/channels/{id}/pause`) returns HTTP 415 Unsupported Media Type. The endpoint has no request body parameter. No error message in the response body — just the bare 415 status.

### Context
A JAX-RS resource class annotated `@Consumes(MediaType.APPLICATION_JSON)` at class level. Most methods accept JSON request bodies. A few "action" endpoints (pause, resume) are body-less POSTs — they take only path parameters.

### What was tried (didn't work)
- Checked the endpoint path and method — correct
- Verified the endpoint method exists and is public — correct
- The 415 gives no indication that Content-Type negotiation is the problem

### Root cause
JAX-RS's `@Consumes` at class level applies to ALL methods, including those with no body parameter. When the client sends a POST without a `Content-Type: application/json` header (because there's no body), the JAX-RS runtime rejects the request before the method is invoked — the method signature is irrelevant.

### Fix
Override `@Consumes` at the method level for body-less endpoints:

```java
@POST
@Path("/{id}/pause")
@Consumes(MediaType.WILDCARD)
public Response pause(@PathParam("id") String id) {
    // ...
}
```

`MediaType.WILDCARD` accepts any Content-Type (or none). The class-level `@Consumes(APPLICATION_JSON)` still applies to all other methods.

### Why this is non-obvious
The 415 status code means "Unsupported Media Type" — but there IS no media type because there's no body. The mental model of `@Consumes` is "what this method can parse", which doesn't apply to body-less methods. The fix requires understanding that `@Consumes` is a content negotiation filter, not a body parser declaration.
