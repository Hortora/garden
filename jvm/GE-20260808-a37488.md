### Symptom
Test calls `expiryService.expireItem(workItemId)` on a WorkItem with a past deadline, then asserts the breach outcome. Intermittent `OptimisticLockException` because the Quartz scheduler also fires for the same item.

### Context
In `@QuarkusTest` with `quarkus.scheduler.start-mode=forced`, creating a WorkItem with a past `expires_at` immediately schedules a Quartz expiry job. If the test also calls `expireItem()`, both code paths update the same entity version.

### The technique
Don't fight the scheduler — let it do its job and poll for the outcome:

```java
// Instead of:
expiryService.expireItem(UUID.fromString(workItemId));
given().when().get("/life-tasks/" + workItemId)
    .then().body("candidateGroups", hasItem("household-admin"));

// Use Awaitility:
await().atMost(10, TimeUnit.SECONDS).untilAsserted(() ->
    given()
        .when().get("/life-tasks/" + workItemId)
        .then().statusCode(200)
        .body("candidateGroups", hasItem("household-admin")));
```

The Quartz job handles expiry within a few hundred milliseconds. Awaitility polls until the assertion passes, eliminating the race entirely.

### Why this is non-obvious
The natural testing instinct is to call the service method directly for deterministic control. But when the scheduler is active, direct calls create a race — the scheduler is already processing the same item. The insight is that the scheduler IS the production code path; testing it via Awaitility is actually more realistic than bypassing it with a direct service call.

### Alternatives considered
- Disabling the Quartz scheduler in tests (`start-mode=off`) — breaks other tests that rely on scheduled jobs
- Adding `@Retry` or try-catch around `expireItem()` — masks the race rather than eliminating it
- Using `Thread.sleep()` before `expireItem()` to let the scheduler finish first — fragile timing dependency
