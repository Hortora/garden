### Symptom

A Jandex-based code generator reading `@Produces` methods produces `Optional groups` instead of `Optional<List<String>> groups` — the generic type parameter is lost, causing a compilation error.

### Context

When building a Spring auto-configuration generator that reads Quarkus CDI `@Produces` methods from a Jandex index, parameters with generic types like `Optional<List<String>>` (from `@ConfigProperty`) are reported by Jandex with their erased type only. The generator emits the parameter type as-is, producing uncompilable Java source.

### Root cause

Jandex's `MethodParameterInfo.type()` returns the erased type (`java.util.Optional`) without generic arguments. Full generic type information requires `Type.asParameterizedType().arguments()` — but the generator's `ParameterDescriptor` only stores the raw type name string.

### Fix

Skip `@ConfigProperty`-annotated parameters in the generator — these need manual Spring `@Value` wiring anyway because the CDI `@ConfigProperty` → Spring `@Value` translation has semantic differences (Optional handling, collection binding, default values). Add a `hasConfigProperties()` check that filters these producers from auto-generation.

The manual Spring configuration class handles the config-backed beans with proper `@Value` annotations and correct types.

### Why this is non-obvious

The generator produces valid-looking code for 30 out of 32 producers. The 2 failures only surface at compile time, and the error message ("cannot find symbol: class Optional") doesn't point to the generic type erasure as the root cause — it looks like a missing import.
