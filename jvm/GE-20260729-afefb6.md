### Symptom
Maven builds in a git worktree fail with `401 Unauthorized` from GitHub Package Registry for every SNAPSHOT dependency. The error says the artifact is `(absent)` even though it exists in `~/.m2/repository`. All dependency resolution fails — the build never reaches compilation.

### Context
Git worktree slots (created by `work-slot` or similar tooling) may include a `.mvn/maven.config` file in the project root that sets `-Dmaven.repo.local=<slot-dir>/.m2`. This redirects Maven's local repository to an isolated, empty cache specific to the slot.

The main repo (at the original git checkout path) builds fine because it has no `.mvn/maven.config` and uses the standard `~/.m2/repository` where all dependencies are cached.

### What was tried (didn't work)
1. Checking `GITHUB_TOKEN` scopes — token was valid (`gist, read:org, repo`) but missing `read:packages`. This looked like the root cause but wasn't.
2. Adding `read:packages` scope via `gh auth refresh` — would have fixed remote fetching but didn't address why cached artifacts weren't used.
3. Fixing Maven `_remote.repositories` marker files — added `>github=` entries for locally-installed SNAPSHOTs. Maven still refused to use them.
4. Setting `<updatePolicy>never</updatePolicy>` on the GitHub repository definition — reduced remote checks but didn't fix resolution.
5. Symlinking the parent POM to fix `<relativePath>` resolution — fixed one layer but dependencies still failed.
6. Running `mvn dependency:resolve` from the main repo to cache dependencies — artifacts went to `~/.m2/repository` but the worktree used a different `.m2`.

### Root cause
`.mvn/maven.config` is a Maven feature that applies CLI arguments to every Maven invocation in the project directory. When it contains `-Dmaven.repo.local=<path>`, Maven uses that path instead of `~/.m2/repository`. The isolated repo is empty — no cached artifacts, no metadata, no `_remote.repositories` markers. Maven must fetch everything from remote repos, and when the remote returns 401, there's no fallback.

The file is invisible to most debugging because:
- `mvn -X` output buries the effective local repo path in hundreds of lines
- The 401 error message is identical whether the artifact is truly absent or just in a different local repo
- `.mvn/` is typically `.gitignore`d and doesn't show in `git diff`

### Fix
Remove or rename `.mvn/maven.config`:
```bash
rm <worktree>/<project>/.mvn/maven.config
rmdir <worktree>/<project>/.mvn  # if empty
```

Or edit it to point to the standard local repo:
```bash
echo "-Dmaven.repo.local=$HOME/.m2/repository" > .mvn/maven.config
```

### Why this is non-obvious
The 401 error is a perfect red herring. Every debugging path leads to GitHub token configuration, Maven `settings.xml` server entries, or `_remote.repositories` marker files. The actual cause — a hidden file redirecting the local repo — is in a different category entirely. The `.mvn/maven.config` file is rarely discussed, often `.gitignore`d, and its effect on dependency resolution is not documented in Maven's error messages.

### Why this fix
Removing `.mvn/maven.config` is preferred over fixing the isolated repo because the isolation was likely unintentional (a side effect of slot tooling). If isolation is genuinely needed, the config should be set up with a pre-populated `.m2` that mirrors the standard cache.

### Alternatives considered
- **Populating the isolated `.m2` by running `mvn dependency:resolve` from the worktree** — works but requires network access and valid auth for every new worktree. Defeats the purpose of using cached artifacts.
- **Symlinking `<slot>/.m2` → `~/.m2/repository`** — works but the symlink may confuse tools that check for directory existence or write lock files.
