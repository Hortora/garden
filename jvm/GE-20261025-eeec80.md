### The technique
When composing `SummarisationRunner` with async processing that may need to skip invocations (concurrency guards, circuit breakers, rate limiters), gate at the `EmissionPolicy` level rather than wrapping the `ContentSummariser`. This prevents the runner from draining the accumulator when processing should be skipped.

### Why it matters
`SummarisationRunner.tickWithPolicy()` drains the `EventAccumulator` BEFORE invoking the summariser. A `ContentSummariser` wrapper that skips invocation cannot return the drained events to the accumulator — they are lost. By suppressing emission at the policy level, the accumulator is never drained, and events remain buffered for the next tick.

### How to apply
Create a gate object that provides two views — a tracking summariser and a gating emission policy:

```java
public class InFlightGate<E, R> {
    private final ContentSummariser<E, R> delegate;
    private volatile CompletionStage<?> inflight;

    public InFlightGate(ContentSummariser<E, R> delegate) {
        this.delegate = delegate;
    }

    public ContentSummariser<E, R> summariser() {
        return (items, previous) -> {
            var stage = delegate.summarise(items, previous);
            inflight = stage;
            return stage;
        };
    }

    public <S> EmissionPolicy<E, S> gating(EmissionPolicy<E, S> policy) {
        return (buffer, state, now) -> {
            if (inflight != null && !inflight.toCompletableFuture().isDone())
                return false;
            return policy.shouldEmit(buffer, state, now);
        };
    }
}
```

Wire both views into the runner:
```java
var gate = new InFlightGate<>(llmSummariser);
var runner = SummarisationRunner.builder(
        gate.summariser().asSummariser(), outputBus, outputLevel)
    .emissionPolicy(gate.gating(EmissionPolicy.window(windowPolicy)))
    .build();
```

### Why this is non-obvious
The natural instinct is to wrap the processor — every other composition pattern in the summarisation framework (compaction, state management, output processing) works via processor wrapping or runner builder options. The EmissionPolicy is semantically about "when to emit" not "whether processing is available" — using it for concurrency control is a non-obvious semantic stretch that happens to match the runner's internal execution order perfectly.

### Generalisation
The pattern works for any skip condition, not just concurrency:
- **Rate limiting**: suppress emission if last invocation was < N seconds ago
- **Circuit breaker**: suppress emission if recent failure count exceeds threshold
- **Budget control**: suppress emission if token/cost budget is exhausted

In each case, the key insight is the same: suppress emission → accumulator keeps events → no data loss.
