### Symptom

Integration tests that approve an oversight gate and then drain to investigation completion intermittently timeout under full-suite thread pool pressure, even though each individual timeout (60s gate + 20s drain) seems generous.

### Context

Tests for async investigation flows follow a two-phase pattern: wait for a gate WorkItem to appear, approve it, then wait for the investigation to reach `status=completed`. Each phase uses a separate Awaitility block with its own timeout.

### What was tried (didn't work)

1. Increasing the Quartz thread pool — helps but doesn't eliminate the issue
2. Increasing individual timeouts — masks the structural problem

### Root cause

Sequential Awaitility blocks waste timeout budget. If the gate takes 50s of its 60s budget, the drain starts its own 20s countdown from zero. The investigation only needs 2 more seconds to complete, but the drain's 20s budget starts fresh — any delay past 20s fails the test even though 30s of the gate's budget went unused.

### Fix

Combine gate approval and drain into a single Awaitility polling loop. The gate approval is a guarded side effect inside the poll:

```java
private void awaitGateApprovalAndDrain(UUID caseId) {
    AtomicBoolean gateApproved = new AtomicBoolean(false);
    Awaitility.await()
        .atMost(60, TimeUnit.SECONDS)
        .pollInterval(300, TimeUnit.MILLISECONDS)
        .until(() -> {
            if (!gateApproved.get()) {
                List<WorkItemEntity> gates = findGateWorkItems(caseId);
                if (!gates.isEmpty()) {
                    workItemService.completeFromSystem(
                        gates.get(0).id, "test-mlro", "approved");
                    gateApproved.set(true);
                }
            }
            return "completed".equals(
                given().when().get("/api/layer6/investigations/" + caseId)
                    .then().extract().path("status"));
        });
}
```

One 60s budget covers the entire gate→completion sequence. No time wasted between phases. The `AtomicBoolean` guard ensures the gate is approved exactly once.

### Why this is non-obvious

The natural pattern (await gate → approve → await drain) reads clearly and maps to the logical sequence. The sequential timeout budget splitting is invisible until tests start failing under load — each individual timeout looks reasonable. The fix inverts the mental model: the terminal condition is investigation completion, and gate approval is a prerequisite side effect, not a separate phase.

### Alternatives considered

- **Single helper that calls both sequentially with a shared deadline** — would require custom Awaitility wrapper to pass remaining time from phase 1 to phase 2. More complex, same effect.
- **Retry annotation on the test** — masks the structural issue without fixing it. Tests still waste time on retries.
