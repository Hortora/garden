### Symptom
`SlaBreachPolicy.onBreach()` receives `SlaBreachContext` with `BreachedTask` — but `BreachedTask` has no payload access. Need to pass WorkItem metadata (e.g. priority tier) to the policy.

### Context
SOC SLA breach policy needs priority-differentiated escalation chains (P1 aggressive, P3 relaxed). The case context has priority, but by the time the policy fires, only `SlaBreachContext` is available — no case context, no WorkItem payload.

### Technique
Embed metadata in the hierarchical scope path via `scopeExpression` in the YAML binding:

```yaml
scopeExpression: >-
  "casehubio/soc/triage-review/" + (
    if .alert.severity == "CRITICAL" then "p1"
    elif .alert.severity == "HIGH" then "p2"
    else "p3"
    end
  )
```

The scope flows through: YAML → engine evaluation → `HumanTaskScheduleEvent.resolvedScope()` → `WorkItem.scope` → `Path.parse(item.scope)` → `SlaBreachContext.scope()`.

The policy extracts it:

```java
String last = context.scope().segments().getLast();
return switch (last) {
    case "p1" -> "P1";
    case "p2" -> "P2";
    default -> "P3";
};
```

### Why this is non-obvious
The scope path is designed for preference resolution hierarchy, not arbitrary metadata. Using it to encode priority tier is a pragmatic repurposing — it's the only field that flows from case context to `SlaBreachContext` besides `candidateGroups` and `title`.
