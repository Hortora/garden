### Symptom
ChatObservationRenderer applied ambient message compression per-thread using a verbatim threshold. With 15+ standalone chat messages in a channel, none were compressed — all rendered verbatim despite the threshold being 5.

### Context
`ChatDeltaReport.build()` groups messages by thread ID. Standalone messages (no `parentRef`) each get their own `ConversationThread` with `threadId` = the message's own ID. Each thread contains exactly 1 message, which is always below any reasonable ambient threshold.

### Root cause
The renderer iterated threads and called `renderAmbient(thread.messages(), sb)` per-thread. Each thread had 1 message, so `messages.size() <= ambientVerbatimThreshold` was always true — compression logic never triggered.

### Fix
Collect all ambient messages across all threads in a channel before applying the threshold. Separate priority threads (DIRECT/ELEVATED) from ambient, render priority threads verbatim individually, then render all ambient messages as a single batch through the compression check.

```java
var ambientMessages = new ArrayList<ClassifiedMessage>();
for (ConversationThread thread : report.threads(channelId)) {
    if (thread.highestPriority() == AttentionPriority.DIRECT
            || thread.highestPriority() == AttentionPriority.ELEVATED) {
        renderVerbatim(thread.messages(), sb);
    } else {
        ambientMessages.addAll(thread.messages());
    }
}
if (!ambientMessages.isEmpty()) {
    renderAmbient(ambientMessages, sb);
}
```

### Why this is non-obvious
The per-thread code compiles, runs, and passes simple tests (single-thread tests work fine). The bug only manifests when many standalone messages arrive — a scenario that is the primary use case for compression but only appears at realistic message volumes.
