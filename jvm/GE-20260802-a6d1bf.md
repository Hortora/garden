## Cross-encoder negative scores filtered by score floor — disable adaptive filtering when keywords are present

### What it achieves

Prevents the adaptive search filter from cutting keyword-matched results that the cross-encoder scores below zero due to semantic distance from the NL query.

### Context

A gardenSearch pipeline uses cross-encoder reranking after RRF fusion. The adaptive filter has a `scoreFloor` (default 0.0) that cuts entries below that score, and a `gapThreshold` (default 2.0) that cuts entries when the score drops sharply between consecutive results.

When keywords like `tmux` are provided alongside a semantically different NL query ("process management electron terminal WebSocket"), the cross-encoder correctly identifies that tmux command gotchas (send-keys, capture-pane, resize-pane) are semantically distant from "process management." It assigns negative scores. The score floor cuts them all — 2 results instead of 16.

### The technique

When keywords are present, disable both the score floor and the gap threshold:

```java
double gapThreshold = hasKeywords ? Double.MAX_VALUE : searchConfig.gapThreshold();
double scoreFloor   = hasKeywords ? Double.NEGATIVE_INFINITY : searchConfig.scoreFloor();
return adaptiveFilter(sorted, requestedLimit,
                      scoreFloor, gapThreshold,
                      searchConfig.minResults(), boostWeight);
```

Also increase the overfetch multiplier (2x → 3x) for keyword queries to ensure enough candidates reach the adaptive filter.

### Why this is non-obvious

The adaptive filter works correctly for pure NL queries — cutting low-scoring results improves precision. The failure mode only appears when keywords are used for domain-scoped recall ("give me everything about tmux") alongside a semantically different NL query. The cross-encoder's negative scores are technically correct (the entries ARE semantically distant from the query) but the keyword match makes them relevant by a different criterion the cross-encoder doesn't measure.
