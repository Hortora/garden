### Symptom / context

You have a single Qhorus channel carrying two distinct conversation types (e.g. a structured debate with rounds/priorities AND ad-hoc annotation threads). The natural instinct is to create separate channels per conversation type — but that means N+1 channels for N threads, lifecycle complexity for each channel (create, register backend, init gateway, manage instances), and cross-type queries requiring projection across multiple channels.

### Root cause / mechanism

`ChannelProjection<S>` processes every message on the channel via `apply()`. There is no built-in filter predicate. But `apply()` can return state unchanged for messages it doesn't care about — making metadata-based partitioning trivial.

### Fix / technique

Add a metadata key (e.g. `threadId`) to one conversation type's messages. Write two projections over the same channel:

**Projection A (debate):** skips messages where `threadId` is present in metadata — returns state unchanged.

```java
@Override
public ConversationState apply(ConversationState state, MessageView message) {
    Map<String, String> meta = ChannelMessageMeta.parseMeta(sentinel, message.content());
    if (meta.containsKey("threadId")) return state; // partition: skip thread messages
    // ... normal debate projection logic
}
```

**Projection B (threads):** skips messages where `threadId` is absent — only processes thread messages.

```java
@Override
public ThreadState apply(ThreadState state, MessageView message) {
    Map<String, String> meta = ChannelMessageMeta.parseMeta(sentinel, message.content());
    String threadId = meta.get("threadId");
    if (threadId == null) return state; // partition: skip debate messages
    // ... thread projection logic
}
```

Both projections are `@ApplicationScoped` CDI beans. The `ChannelBackend.post()` method routes WebSocket events based on the same key — thread messages go to `thread-entries`, debate messages go to `debate-entries`.

### Why this is non-obvious

The obvious approach — one channel per conversation type — is what most developers reach for. It's conceptually cleaner but operationally expensive: each channel needs `channelService.create()`, `channelGateway.initChannel()`, instance registration, and backend attachment. For N annotation threads on a document review, that's N+1 channels with full lifecycle management.

The metadata partition approach keeps everything in one channel with zero lifecycle overhead per thread. Cross-type queries (e.g. "show me the full debate summary including thread count") are a single projection call, not N+1 aggregated projections.

### Why this fix

The partition key approach leverages the existing `apply()` contract — returning state unchanged is explicitly designed for messages a projection doesn't handle. No framework extension needed, no custom filter predicate, no channel routing configuration. The partition is in the data, not the infrastructure.

### Alternatives considered

- **Separate channels per thread:** Clean separation but O(N) channel lifecycle overhead. Cross-thread queries require aggregating N projections. Rejected for operational cost at scale.
- **Single projection handling both types:** Possible but couples debate and thread state into one projection class. Violates single responsibility and makes each projection harder to test independently.
- **ChannelBackend-level filtering:** Route messages to different backends based on metadata. Rejected because backends handle delivery, not state projection — the concern is wrong.
