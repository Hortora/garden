## Symptom

`java.lang.IllegalArgumentException: key size` when parsing a WireMock-stubbed Google Drive `files.list` response. The error message gives no indication that it's a type mismatch — it just names the JSON key.

Full stack trace chain:
```
IllegalArgumentException: key size
  at JsonParser.parseValue → key size, field private java.lang.Long File.size
```

## Context

When writing WireMock tests for Google Drive API operations (`files.list`, `changes.list`), the natural response JSON uses numeric values for `size`:

```json
{"id": "f-1", "name": "Doc.txt", "mimeType": "text/plain", "size": 100}
```

This fails at runtime despite `File.size` being typed `java.lang.Long`.

## What was tried (didn't work)

- Assumed the numeric JSON value `100` would parse into `Long` — standard JSON-to-Java behaviour
- The error message `key size` suggested the field name was wrong, leading to checking field names and JSON structure before realising it was a type issue

## Root cause

Google's `google-api-client` JSON parser (`com.google.api.client.json.JsonParser`) expects the Drive API's `size` field to arrive as a JSON **string** (e.g. `"100"`), not a JSON number. This matches how the real Google Drive API serialises the field — the API returns `"size": "12345"` as a string, not an integer. The Java model declares `Long` but the parser resolves it from a quoted string, not a native JSON number.

## Fix

Quote the `size` value in WireMock response stubs:

```json
{"id": "f-1", "name": "Doc.txt", "mimeType": "text/plain", "size": "100"}
```

Not:
```json
{"id": "f-1", "name": "Doc.txt", "mimeType": "text/plain", "size": 100}
```

This applies to all numeric fields in Google Drive API responses used in WireMock stubs.

## Why this is non-obvious

A Java `Long` field would normally accept a JSON integer — that's standard Jackson/Gson behaviour. Google's custom JSON parser breaks this assumption. The error message (`key size`) doesn't mention types at all, and the real API returns the value as a string, so there's no opportunity to learn this from observing live responses unless you inspect the raw JSON carefully.

### Alternatives considered

- Using Jackson ObjectMapper to pre-serialise the Google model objects into the mock response — overkill for simple stubs and tightly couples tests to the model's serialisation quirks
- Setting the `size` field to `null` in the mock — loses the ability to test size-dependent logic
