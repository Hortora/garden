## Qhorus ChannelResource auto-mounts REST endpoints in consuming Quarkus apps

**Stack:** casehub-qhorus 0.2-SNAPSHOT, Quarkus 3.32

### Context

When building a channel creation endpoint for Claudony (#177), the initial design
planned a `MeshResource` proxy method that would inject `ChannelService` and call
`channelService.findOrCreate()` to expose channel creation via REST.

### What happened

After Qhorus shipped `ChannelResource` (qhorus#387) — a standard JAX-RS resource
with `@Path("/api/channels")` and `@ApplicationScoped` — the endpoint was
automatically available in Claudony's Quarkus app at `/api/channels` without any
Claudony-side code. No proxy, no delegation, no configuration.

Tests calling `POST /api/channels` with a channel creation payload returned 201
immediately. The existing `GET /api/mesh/channels` (Claudony's own endpoint)
and `POST /api/channels` (Qhorus's auto-mounted endpoint) coexist on different
paths without conflict.

### Why this is non-obvious

The natural assumption when a library provides a service is that the consuming
application must explicitly expose it via its own REST layer. Quarkus's JAX-RS
resource auto-discovery from indexed dependency JARs means `@Path`-annotated
classes in library dependencies become live endpoints automatically — no
`@Import`, no `@RegisterRestClient`, no explicit routing.

This eliminates an entire class of "proxy endpoint" code — thin pass-through
methods that inject a service and call it. If the library already has the right
REST contract, the consuming app can skip the proxy entirely.

### Technique

Before building a proxy endpoint that delegates to a library service, check
whether the library already provides a JAX-RS resource. If it does, and the
library is on the Quarkus classpath with Jandex indexing, the endpoint is
already live. Verify with:

```bash
curl -s http://localhost:<port>/<library-path> | head -20
```
