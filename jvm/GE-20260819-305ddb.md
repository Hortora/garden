## Drools record field change produces misleading CDI errors from stale augmentation cache

### Symptom

After adding a field to a Java record used as a Drools fact (e.g. `PatternAssessment`), `mvn test` fails with an `UnsatisfiedResolutionException` for an apparently unrelated CDI bean (`QhorusDashboardService`). The compilation succeeds. Individual unit tests pass. Only tests triggering Quarkus augmentation fail — with errors that have no visible connection to the record change.

### Context

A Java record (`PatternAssessment`) is used in Drools rule units (`DataStore<PatternAssessment>`) and in DRL pattern matching. Adding a new field to the record changes its constructor signature. The Drools code generator produces lambda classes (e.g. `LambdaPredicate1<PatternAssessment>`) that are cached in `target/` from the prior compile. The stale generated classes reference the old constructor shape. Quarkus augmentation picks up these stale classes and fails during CDI validation — but the error surfaces as an unrelated bean resolution failure, not as a record mismatch.

### Root cause

Quarkus augmentation cache is disk-based (`target/`). Generated Drools sources from a prior compile persist across incremental builds. When a record's shape changes, the generated Drools lambdas still reference the old shape. The augmentation process fails to reconcile this, but the error manifests as a CDI deployment exception rather than a compilation error.

### Fix

Always run `mvn clean` before compiling after changing a record used as a Drools fact:

```bash
mvn clean compile -pl <module>
```

### Why this is non-obvious

The CDI error (`UnsatisfiedResolutionException: QhorusDashboardService`) has zero textual connection to `PatternAssessment` or the record change. A developer would chase the CDI injection graph for hours before discovering the root cause is stale Drools-generated code in `target/`.
