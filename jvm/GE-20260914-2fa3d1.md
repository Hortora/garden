## Symptom

`ExpressionCompilationException: Failed to compile MVEL expression: faultType == "PROVISION_FAILED"` thrown at runtime during the first `eval()` call. The expression is syntactically valid and works when the first evaluated map contains the `faultType` key with a non-null value.

## Context

When using `MvelExpressionEngine` (from `casehub-platform-expression`) to compile expressions against `Map<String, Object>` contexts, compilation is **lazy** — it happens on the first `eval()` call via `LazyMapMvelExpression`. The compiled evaluator is then cached and reused for all subsequent calls.

The compilation calls `MVEL.getTypeMap(evalContext)` to infer types from the actual map keys and values. This determines what symbols the expression can reference.

The problem occurs when processing heterogeneous event streams — events with different payload shapes flowing through the same expression evaluation point. Example: a summarisation pipeline's `threshold-classify` level receives both fault events (with `faultType` field) and recovery events (without `faultType` field). The **first** event to reach the expression determines which symbols are resolvable.

## What was tried (didn't work)

1. Adding the key with `null` value (`payload.put("faultType", null)`) — `getTypeMap()` cannot infer a type from null, so the symbol remains unresolvable.

2. Reordering YAML rules to put the null-check rule first — doesn't help because all rules are evaluated against every event, and compilation happens on the first event regardless of rule order.

## Root cause

`MvelExpressionEngine.compileMapEvaluator()` calls `MVEL.getTypeMap(evalContext)` which builds a `Map<String, Type<?>>` from the context map. For each key:
- Non-null value → type is inferred from the value's class → symbol is resolvable
- Null value → no type can be inferred → symbol is NOT included in the type map
- Missing key → key is not in the map at all → symbol is NOT included

When the MVEL transpiler encounters `faultType` in the expression but `faultType` is not in the type map, it throws `UnsolvedSymbolException` from JavaParser's symbol resolver.

Once compiled successfully (with a context that HAS the key), the cached evaluator handles subsequent maps fine — even those missing the key (MVEL evaluates missing keys as null at runtime). The issue is strictly at compilation time.

## Fix

Ensure the **first** event to reach the expression always has all referenced keys with non-null values. Two approaches:

### Solution 1 — Event ordering (simplest)
Arrange the event source so the first event has the richest payload shape — the one containing all keys referenced by any expression rule.

```java
// In the simulator/event source, emit a fault event before any recovery events
events.add(fault("node-0", "agent", "PROVISION_FAILED", "initial", t));
events.add(recovery("node-1", "agent", t + 1000));
```

**Pros:** Zero overhead, no payload mutation.
**Cons:** Fragile — depends on event ordering which may not be controllable in production.

### Solution 2 — Payload normalisation (robust)
Normalise all event payloads to include all keys before they enter the pipeline. Missing keys get a sentinel non-null value that won't match any expression rule.

```java
// Recovery events include faultType with empty string (non-null, won't match any rule)
payload.put("faultType", "");
```

**Pros:** Works regardless of event ordering.
**Cons:** Requires knowing all possible keys across all event shapes upfront.

## Why this is non-obvious

MVEL3's lazy compilation is invisible — the expression appears to compile successfully (no error at `compile()` time). The failure only surfaces at `eval()` time, on the first call, and only when the first event happens to lack a key. In tests with controlled event ordering, this may never trigger. In production with unpredictable event ordering, it surfaces intermittently — a classic Heisenbug.

The null-value workaround (`put("faultType", null)`) is the intuitive fix but doesn't work because `getTypeMap()` skips null values entirely. This adds an extra hour of debugging on top of the initial discovery.

### Why this fix

The event-ordering approach is the pragmatic choice for controlled environments (tests, examples) because it requires zero code changes to the events themselves. For production pipelines with uncontrollable event ordering, payload normalisation is the only reliable option. A third option — fixing `getTypeMap()` to handle null values via `Optional.empty()` or `Object.class` fallback — would be the proper upstream fix but is outside consumer control.

### Alternatives considered

- **Separate pipelines per event type** — eliminates mixed shapes entirely but loses the ability to do cross-type phase detection in a single pipeline. Rejected because the whole point of `type-prefix` source matching is to handle multiple event types.
- **Pre-compiling with a synthetic context** — create a "template" map with all keys populated, compile against it, then use the compiled evaluator. Would work but `LazyMapMvelExpression` doesn't expose a pre-compilation hook.
