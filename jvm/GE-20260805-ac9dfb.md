# Quinoa HTTP forwarding hangs on macOS — IPv4/IPv6 dual-stack mismatch with Vite dev server

### Symptom
Quarkus starts successfully (`started in 4.2s`) but all HTTP requests to port 8080 hang indefinitely — curl connects but receives no response. The Quarkus log shows Quinoa forwarding to Vite's port, but requests never complete.

### Context
Quinoa in dev mode starts a Vite dev server and forwards unhandled HTTP requests to it. On macOS, `localhost` resolves to `::1` (IPv6). Vite binds to `localhost:5173` (IPv6 only). Quinoa's Vert.x HTTP client attempts to forward requests but the connection pipeline hangs — possibly due to dual-stack resolution or Vert.x preferring IPv4 for the forwarding connection while Vite only accepts IPv6.

### What was tried (didn't work)
- Setting `quarkus.quinoa.package-manager-install=false` — Quinoa still runs npm install (property may be ignored for fresh builds)
- Setting `quarkus.quinoa.package-manager-command.install=--version` — bypasses npm install but Quinoa still starts Vite and forwards
- Setting `quarkus.http.host=0.0.0.0` — Quarkus binds to all interfaces but Quinoa forwarding still hangs

### Root cause
Quinoa's HTTP forwarding pipeline between Quarkus and the Vite dev server has an IPv4/IPv6 mismatch on macOS. The exact failure point is inside Vert.x's HTTP client used by Quinoa's `ForwardedDevProcessor`.

### Fix
Disable Quinoa in demo/dev mode and run Vite standalone:

```properties
%demo.quarkus.quinoa.enabled=false
%demo.quarkus.http.host=0.0.0.0
```

Run two processes:
```bash
# Terminal 1: Quarkus API
JAVA_HOME=$(/usr/libexec/java_home -v 26) mvn quarkus:dev -pl app -Dquarkus.profile=demo

# Terminal 2: Vite frontend
npm run dev --prefix life-ui
```

Configure Vite to proxy API requests to the Quarkus server on IPv4:
```javascript
// vite.config.ts
proxy: {
  '/dashboard': 'http://127.0.0.1:8080',
  '/life-cases': 'http://127.0.0.1:8080',
  // ... other API paths
}
```

### Why this is non-obvious
The server reports "started in 4.2s" — there is no error, no warning, no timeout. Requests simply hang. The Quinoa log says "forwarding unhandled requests to port: 5173" which looks correct. The hang is silent and only manifests on macOS dual-stack — the same setup likely works on Linux where localhost resolves to IPv4 only.
