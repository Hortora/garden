## Symptom

`GardenMetadataExtractor` correctly extracts `tags` as `List<String>` into `ExtractionResult.listMetadata()`, but the `tags` array never appears in the Qdrant payload. The Qdrant payload index for `tags` exists (keyword type) but contains no data. Consumers reading the Qdrant payload directly (e.g., Grove's TagAnalyser) see zero results.

## Context

`ExtractionResult` carries two metadata maps:
- `metadata` (Map<String, String>) — string key-value pairs
- `listMetadata` (Map<String, List<String>>) — string-to-list pairs (tags, see_also)

`ChunkInput` mirrors this with 3-arg and 4-arg constructors:
- 3-arg: `ChunkInput(content, sourceDocumentId, metadata)` — sets `listMetadata = Map.of()`
- 4-arg: `ChunkInput(content, sourceDocumentId, metadata, listMetadata)` — preserves list metadata

`QdrantPointBuilder.buildPoint()` correctly iterates both maps and writes list values via `ValueFactory.list()`.

## What was tried (didn't work)

Initially suspected `GardenMetadataExtractor` wasn't extracting tags — but the extractor was correct. Then suspected `QdrantPointBuilder` wasn't handling list metadata — but it was correct. The bug was in the middle of the chain.

## Root cause

`CorpusIngestionService.chunkDocument()` created `ChunkInput` using the 3-arg constructor in both code paths (with and without document splitter):

```java
// Both paths used this:
new ChunkInput(result.body(), path, result.metadata())
// Instead of:
new ChunkInput(result.body(), path, result.metadata(), result.listMetadata())
```

The 3-arg constructor sets `listMetadata = Map.of()`, silently discarding all list metadata from the extraction result.

## Why this is non-obvious

The data loss was masked by string fallbacks. `GardenMetadataExtractor` writes both:
- `listMetadata.put("tags", tagStrings)` — the proper list (silently dropped)
- `metadata.put("tags_joined", String.join("|", tagStrings))` — pipe-separated string (flows through)

`SearchResult.tags()` reconstructs the list from `tags_joined`, so the REST API always returned correct tags. Only direct Qdrant payload consumers saw the missing data. The 3-arg constructor compiles cleanly and looks correct — the API surface makes the wrong call indistinguishable from the right one.

## Fix

**Resolved in:** casehub-neocortex-rag commit `6e0b815` (2026-08-10)

Use the 4-arg `ChunkInput` constructor to pass `result.listMetadata()` through:

```java
// No splitter path:
return List.of(new ChunkInput(result.body(), path, result.metadata(), result.listMetadata()));

// Splitter path:
chunks.add(new ChunkInput(segment.text(), path, result.metadata(), result.listMetadata()));
```

Requires a reindex to populate the Qdrant payload with the list metadata fields.

### Alternatives considered

- Flattening all list metadata into pipe-separated strings in the MetadataExtractor — rejected because it loses type information and forces all consumers to parse strings
- Extending the neocortex-rag SPI to remove the 3-arg constructor — rejected as a breaking API change affecting all consumers
