### Symptom
A third-party library registers `ExceptionMapper<RuntimeException>` which catches exceptions you need to handle differently (e.g. `WebApplicationException` subclasses that should preserve their status code).

### Context
When a dependency's `@Provider` `ExceptionMapper` uses a broad supertype like `RuntimeException`, it intercepts all subclass exceptions including JAX-RS's own exception hierarchy. You can't modify the library and can't easily exclude the provider from discovery.

### Technique
Register your own `ExceptionMapper` with a more specific generic type. JAX-RS spec (Section 4.3.1) mandates that when multiple mappers match, the one whose generic type is the nearest superclass of the thrown exception wins.

```java
@Provider
public class WebApplicationExceptionMapper
        implements ExceptionMapper<WebApplicationException> {
    @Override
    public Response toResponse(WebApplicationException exception) {
        return exception.getResponse();
    }
}
```

This mapper wins for `WebApplicationException` and all its subclasses (`NotFoundException`, `ClientErrorException`, `BadRequestException`, etc.) because `WebApplicationException` is more specific than `RuntimeException` in the type hierarchy.

### Why this is non-obvious
The natural instinct is to try to exclude the offending provider (`quarkus.arc.exclude-types`, Jandex exclusion) — but `@Provider` classes aren't CDI beans, so CDI exclusion mechanisms don't apply. The type-hierarchy resolution rule is in the JAX-RS spec but rarely needed because most exception mappers use specific types. The technique is invisible in standard documentation because it's a workaround for an unusual (library-imposed) situation.
