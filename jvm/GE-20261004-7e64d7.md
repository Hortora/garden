### Symptom
Extension-provided JPA repositories and services silently discard all data.
`save()` calls succeed but persist nothing. Queries return empty collections.
No errors, no warnings, no exceptions — the application appears to work but
no data reaches the database.

### Context
A Quarkus extension provides real implementations (e.g. JPA repositories) as
`@Alternative @ApplicationScoped` beans, with `@Produces @DefaultBean` NoOp
fallbacks in a producer class. The intent is that the real implementation
activates when a datasource is available, and the NoOp fills in when it isn't.

### What was tried (didn't work)
- Checking database schema — tables exist, migrations ran successfully
- Verifying EntityManager injection — `@LedgerPersistenceUnit EntityManager` resolves
- Tracing save calls — methods execute without exception
- Looking for transaction rollbacks — none found

### Root cause
`@Alternative` beans are **dormant by default** in CDI. They require explicit
activation via `quarkus.arc.selected-alternatives` in every consumer's
`application.properties`. Without this config, the `@DefaultBean` NoOp
producer wins — and NoOps silently succeed without persisting anything.

The dangerous part: no CDI error, no log warning, no exception. The NoOp
implementations return empty collections for reads and silently discard
writes. The application boots, handles requests, and returns empty results
without any indication that data is being thrown away.

### Fix
Replace `@Alternative` with `@ApplicationScoped @Priority(1)` on extension-
provided implementations:

```java
// Before — dormant unless consumer explicitly activates
@ApplicationScoped
@Alternative
public class JpaFooRepository implements FooRepository { ... }

// After — auto-displaces @DefaultBean without consumer config
@ApplicationScoped
@Priority(1)  // jakarta.annotation.Priority
public class JpaFooRepository implements FooRepository { ... }
```

The `@DefaultBean` NoOp is only used when no higher-priority bean exists.
`@Priority(1)` makes the real implementation always-active, displacing the
NoOp without any consumer configuration.

**Import change:** `jakarta.enterprise.inject.Alternative` → `jakarta.annotation.Priority`

### Why this is non-obvious
The `@Alternative` + `@DefaultBean` pattern looks correct at first glance —
it provides a fallback for deployments without a datasource. But the CDI spec
requires explicit activation for alternatives, which means every consumer must
add configuration that most developers don't know about. The NoOp fallback that
was intended as a safety net becomes a silent data sink.

### Alternatives considered
- Adding `quarkus.arc.selected-alternatives` to every consumer — works but
  fragile; every new consumer must remember to add the config
- Using `@IfBuildProperty` to conditionally exclude NoOps — too complex,
  doesn't handle the datasource-absent case
