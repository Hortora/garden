### Symptom
After rebuilding an upstream dependency to `~/.m2/repository`, builds in a slot (which uses `-Dmaven.repo.local=<slot>/.m2`) still use the old SNAPSHOT. The slot's `settings.xml` has a `file:///Users/dev/.m2/repository` remote with `<updatePolicy>always</updatePolicy>`, but Maven never checks it.

### Context
Slot-based development workflows where each slot has an isolated `.m2` to avoid cross-slot interference. When upstream repos are rebuilt to the host `~/.m2`, slots need to pick up the fresh SNAPSHOTs.

### What was tried (didn't work)
- `updatePolicy=always` on the file:// remote — Maven never checks because local copy exists
- `-U` flag — forces remote metadata refresh but still prefers the local artifact
- Copying the jar manually — Maven's resolver re-downloads from the remote (GitHub Packages) and overwrites the copy

### Root cause
Maven's SNAPSHOT resolution considers the local repository authoritative. If `<slot>/.m2/io/casehub/artifact/0.2-SNAPSHOT/artifact.jar` exists, Maven will not check any remote repository for a newer version — the `updatePolicy` only applies when the local copy is absent. The `_remote.repositories` marker file and `resolver-status.properties` reinforce this by caching the last resolution.

### Fix
Delete the entire artifact directory from the slot `.m2` — not just the jar, the whole directory tree including metadata:

```bash
rm -rf <slot>/.m2/io/casehub/<artifact>/0.2-SNAPSHOT
```

The next build will fail to find it locally, check the `file://` remote, find the fresh jar in `~/.m2/repository`, and download it.

### Why this is non-obvious
`updatePolicy=always` reads as "always check for updates" — but it only applies to remote repositories when the local copy is absent. The mental model is "Maven will prefer the newest SNAPSHOT" but the actual behaviour is "Maven will prefer the local SNAPSHOT unconditionally."
