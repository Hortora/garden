## Symptom

`UnknownEntityException: Could not resolve root entity 'Channel'` at runtime, even though the entity class is on the classpath, has a Jandex index, and is listed in `quarkus.hibernate-orm.<named-pu>.packages`.

## Context

Occurs in a multi-PU Quarkus setup where:
- Entities are assigned to a named PU (e.g. `quarkus.hibernate-orm.qhorus.packages=io.casehub.qhorus.runtime.channel`)
- JPA store classes inject `@Inject EntityManager em` without `@PersistenceUnit("qhorus")`
- The store then queries an entity that exists only in the named PU

## What was tried

- Added all entity subpackages to the named PU's `packages` config — entities are properly assigned to the named PU
- Rebuilt the library JAR with fresh Jandex index — entities are indexed
- Verified entity class has `@Entity` annotation — correctly annotated

None of these fix the problem because the entity IS discovered and assigned — it's just assigned to the wrong PU from the store's perspective.

## Root cause

In Quarkus, `@Inject EntityManager em` always injects the DEFAULT persistence unit's EntityManager. Each EntityManager is bound to exactly one PU. Queries through the default EntityManager cannot see entities registered with named PUs.

Quarkus does NOT route queries based on entity metadata. The PU is determined by the injection point, not by the entity being queried.

## Fix

Stores that query entities in a named PU must qualify their EntityManager injection:

```java
@Inject
@PersistenceUnit("qhorus")
EntityManager em;
```

If the stores are in an upstream library you can't modify, workaround options:
1. Move all entities into the default PU and use a single shared datasource
2. Provide `@Alternative @Priority` mock implementations that displace the broken stores
3. File an upstream issue for the library to qualify its EntityManager injections

## Why this is non-obvious

The natural assumption is that Hibernate/JPA resolves entities globally — if the entity is on the classpath and indexed, any EntityManager should find it. In single-PU setups this is true. The multi-PU case silently partitions the entity registry per PU, and unqualified injection always targets the default PU. No warning is emitted; the entity is discovered but invisible to the wrong PU.
