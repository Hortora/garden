### The gotcha

`LedgerEntry.canonicalBytes()` includes `supplementJson` in its hash input. `attach(supplement)` mutates `supplementJson` via `LedgerSupplementSerializer.toJson()`. The digest computed at `repository.save()` time is therefore a function of the supplement state.

If you save the entry first (digest D1 computed without supplement), then attach a supplement and re-save (content now hashes to D2), the Merkle chain contains D1 but the entry content matches D2. Chain verification fails.

### Symptom

No error at write time. The corruption is silent — it only surfaces when `LedgerVerificationService.verify()` runs and reports chain inconsistency for the affected subject.

### Context

The natural design for attaching metadata from a separate CDI observer (e.g. a `CaseOutcomeObserver` that runs after the entry-writing observer) is to query the entry back, attach, and re-save. This breaks because CDI observer ordering is not guaranteed, and even if ordered correctly, the re-save changes the digest.

The clinical-trial harness avoids this by attaching supplements inline in each `LedgerWriter` bean before the single `save()` call. AML initially designed a separate observer and caught the issue during plan review.

### Root cause

`LedgerEntry.canonicalBytes()` concatenates base fields, `supplementJson`, and `domainContentBytes()`:

```java
if (this.supplementJson != null && !this.supplementJson.isEmpty()) {
    canonical.append("|").append(this.supplementJson);
}
```

The digest is computed from `canonicalBytes()` during `save()`. Any mutation to `supplementJson` after that point changes the canonical representation without updating the digest.

### Fix

Attach all supplements before the single `repository.save()` call. Never query-back and re-save an entry to add supplements.

```java
// Correct: attach before save
entry.attach(MyComplianceSupplement.create(...));
repository.save(entry, tenantId);

// Wrong: separate observer that re-saves
// Observer A: repository.save(entry, tenantId);  ← digest D1
// Observer B: entry.attach(supplement);
//             repository.save(entry, tenantId);  ← digest D2, chain corrupt
```

### Why this is non-obvious

The `attach()` API looks like a simple setter — it doesn't signal that it participates in cryptographic integrity. A developer designing a supplement attachment pattern would naturally reach for a decoupled observer (separation of concerns), not realizing the Merkle chain constraint makes the save point a hard boundary for content mutation.
