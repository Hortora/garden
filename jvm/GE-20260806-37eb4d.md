### Symptom
CDI deployment fails with `Unsatisfied dependency for type T` even though a `@DefaultBean` implementation of T exists in an indexed jar. The `@DefaultBean` should activate when no other bean provides T — but it doesn't.

### Context
Jar A (e.g. casehub-blocks) provides `@DefaultBean @ApplicationScoped NoOpFooStore implements FooStore`. Jar B (e.g. casehub-qhorus) has a Jandex index and ships `@ApplicationScoped JpaFooStore implements FooStore` — a real JPA implementation that requires a datasource and Panache repo.

Consumer app indexes jar A via `quarkus.index-dependency` and transitively pulls in jar B (which auto-indexes via embedded Jandex). The consumer doesn't configure jar B's JPA infrastructure.

### What was tried (didn't work)
- Adding jar A to `quarkus.index-dependency` — already done; `@DefaultBean` is visible to CDI
- Verifying `@DefaultBean` and `@ApplicationScoped` annotations in bytecode — both present and correct
- Excluding `JpaFooStore` from CDI — partially works but doesn't explain the root cause

### Root cause
Quarkus `@DefaultBean` semantics: a `@DefaultBean` is eliminated from the bean set if ANY other bean of the same type exists. The Jandex-discovered `JpaFooStore` counts as "existing" — even though its own dependency chain (`ThreadSummaryPanacheRepo` → Panache → datasource) cannot be satisfied in the consumer app. Quarkus eliminates the `@DefaultBean` first, then validates the remaining beans, finds `JpaFooStore` can't be wired, and reports `Unsatisfied dependency for type FooStore`.

The error is confusing because it says "unsatisfied" (no bean) when the real problem is "wrong bean selected then that bean failed."

### Fix
Exclude the unwanted Jandex-discovered bean in the consumer's `application.properties`:

```properties
quarkus.arc.exclude-types=io.casehub.qhorus.runtime.store.jpa.JpaFooStore
```

This removes `JpaFooStore` from the bean set entirely, allowing the `@DefaultBean NoOpFooStore` to activate.

If the observer that injects `FooStore` also has other unsatisfied dependencies, exclude the observer itself — removing the entire dependency chain.

### Why this is non-obvious
The error message says "Unsatisfied dependency" for the interface type, not for the JPA store's dependencies. The natural response is "my @DefaultBean isn't being discovered" — but it IS discovered, it's just being eliminated by a bean the consumer never intended to use. The `@DefaultBean` documentation says it activates "when no other bean exists" but doesn't clarify that non-functional beans (with broken dependency chains) still count as "existing."
