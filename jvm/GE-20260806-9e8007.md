### Symptom
A "last N lines" implementation using backward newline scanning returns N-1 lines instead of N. The result starts one line too late.

### Context
Implementing `tailLines(name, count)` for session log files. Files end with `\n` (standard for append-only logs). The backward scan counts the trailing `\n` as a line boundary, consuming one of the N requested lines.

### Root cause
The trailing `\n` at EOF terminates the last line — it is not a separator between lines. A naive backward scan from `fileLength - 1` finds this `\n` first and counts it as a boundary, effectively skipping a line.

### Fix
Before counting line boundaries, check if the byte at `fileLength - 1` is `\n`. If so, start the scan from `fileLength - 2`:

```java
long pos = fileLength - 1;
raf.seek(pos);
if (raf.readByte() == '\n') pos--;

while (pos > 0 && newlinesFound < totalLines) {
    raf.seek(pos);
    if (raf.readByte() == '\n') newlinesFound++;
    pos--;
}
```

### Why this is non-obvious
The off-by-one is silent — the method returns valid data, just one line fewer than requested. Tests that don't check the exact line count pass. The fix is a single line but the diagnosis requires reasoning about whether `\n` at EOF is a terminator or separator.
