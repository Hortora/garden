### Symptom

Attempting to import `io.casehub.engine.planning.plan.PlanItem` or `io.casehub.engine.planning.registry.BlackboardRegistry` in the `casehub-engine` runtime module causes compilation failure: `package does not exist`.

### Context

The engine's module structure has `engine-runtime` and `engine-planning` as separate Maven modules. Despite `CaseContextChangedEventHandler` (in runtime) using `LoopControl` and other planning concepts, runtime does NOT have `casehub-engine-planning` as a compile dependency. The `LoopControl` interface is in `engine-api` — runtime injects it via CDI, and planning provides the concrete `PlanningStrategyLoopControl` bean discovered at runtime.

### Root cause

The engine uses CDI `Instance<>` injection to discover planning beans without compile-time coupling. This is an intentional architecture: runtime defines interfaces in `engine-api`, planning implements them, and CDI wires them at startup. Types like `PlanItem`, `CasePlanModel`, and `BlackboardRegistry` are planning-internal — not available to runtime code.

### Fix

Code that needs `PlanItem`, `BlackboardRegistry`, or other planning types must live in the `planning` module (or in a module that declares `casehub-engine-planning` as a compile dependency). For the engine-runtime module, interact with planning only through interfaces defined in `engine-api` or `engine-common` (e.g., `LoopControl`, `CasePlanModel` as a CDI bean).

### Why this is non-obvious

The runtime module's handlers appear to use planning concepts extensively. `CaseContextChangedEventHandler` calls `loopControl.select()` which returns planning types — but these are API interfaces, not planning implementations. The distinction between the API interface (in `engine-api`) and the implementation class (in `engine-planning`) is not documented in CLAUDE.md or any architecture doc. A developer adding a new service to runtime that needs PlanItem will naturally try to import it and hit a confusing compilation error.
