### Symptom
CDI validation fails with 25+ errors:
`Unsatisfied dependency for type jakarta.persistence.EntityManager and qualifiers [@Default]`

Beans that inject `@Default EntityManager` (standard JPA repositories) cannot be satisfied,
even though `quarkus-hibernate-orm` is on the classpath and the default datasource is configured.

### Context
Occurs when a Quarkus application composes multiple modules where one declares a **named**
persistence unit (e.g. `quarkus.hibernate-orm.qhorus.datasource=qhorus` with
`quarkus.hibernate-orm.qhorus.packages=io.casehub.qhorus.runtime`).

Before the named PU is added, Quarkus auto-assigns all discovered entities to the default PU
and produces a `@Default EntityManager`. Once a named PU appears, Quarkus switches to
**explicit package routing** — but only for the named PU. The default PU receives no explicit
packages and silently stops producing `@Default EntityManager`.

### What was tried (didn't work)
- Assumed scaffold was reactive-only (wrong — it has both blocking and reactive)
- Assumed stale Maven artifacts from cross-repo rebuild
- Tried removing new graphql module dependencies
- Full clean rebuild of all repos — same 25 failures
- All led away from the actual cause

### Root cause
Quarkus Hibernate ORM uses package declarations to route entities to persistence units.
When all PUs are unnamed (default), auto-assignment works. When **any** named PU declares
`packages`, Quarkus expects the default PU to also declare its packages explicitly.
Without it, the default PU has no entities assigned and no `@Default EntityManager` is produced.

### Fix
Add explicit package declarations for the default PU covering all entity packages
not claimed by named PUs:

```properties
# Default PU — covers engine, work, platform-acl entities
quarkus.hibernate-orm.packages=io.casehub.persistence.jpa,io.casehub.work.runtime,io.casehub.platform.acl.jpa
```

### Why this is non-obvious
The error message (`Unsatisfied dependency for EntityManager @Default`) strongly implies
Hibernate ORM is not configured or not producing an EntityManager at all. Nothing in the
error points to package routing. The failure is silent at configuration time — no warning
about unassigned entities or missing default PU packages. The CDI error appears only
at validation, after all build steps complete.

### Caveats
- Every entity package must be claimed by exactly one PU — unclaimed packages produce
  no EntityManager for beans in those packages
- When adding a new module with entities, update the default PU packages list
