### Symptom
`GoapDecompositionStrategyTest.decompose_highFailureRate_generatesContingency` fails with assertion error — the plan contains "alt-cap" instead of "primary-cap". The contingency generation code never runs because the primary action was never selected.

### Context
Testing `GoapDecompositionStrategy` contingency generation from CBR failure rates. Test provides experiences showing 83% failure rate for "primary-cap" and expects the planner to select "primary-cap" as primary (with a contingency attached), not "alt-cap".

### What was tried (didn't work)
- Setting primary cost=1.0 and alt cost=2.0 — expected the planner to pick the cheaper action
- Checking planner logic, blacklist configuration, contingency threshold — all correct

### Root cause
`enrichActions()` runs before `planner.plan()` and applies `GoapCostEnricher.enrichWithLearnedCosts()` using CBR experiences. With 83% failure rate, `actionCostFactors` computes: weighted score ≈ -0.74 → clamped to 0.1 → cost factor = 10.0. The enriched cost of primary-cap becomes 1.0 × 10 = 10.0, which is higher than alt-cap's 2.0. The planner selects alt-cap as the primary action.

### Fix
Make the primary action much cheaper than the alternative so the enriched cost still wins:

```java
// primary cost 0.1, alt cost 5.0 — after 10x enrichment: 0.1 × 10 = 1.0, still < 5.0
var primary = new GoapAction("primary-cap", Map.of(), Map.of("goal", true), 0.1);
var alt = new GoapAction("alt-cap", Map.of(), Map.of("goal", true), 5.0);
```

### Why this is non-obvious
The cost enrichment is hidden inside `enrichActions()` — a method that looks like it's about CBR cost learning, not about changing which action the planner selects. The test's intent (high failure rate → contingency attached) is correct, but the cost enrichment side-effect changes the planner's primary selection before contingency attachment runs. The symptom ("wrong action") points to the planner or blacklist, not to cost inflation.

### Alternatives considered
- Using a mock that bypasses enrichment — rejected because it wouldn't test the real decomposition pipeline
- Setting minCostSamples higher than the test data — rejected because it would disable cost enrichment entirely and miss real integration bugs
