## Quarkus Arc ignores synchronous @Observes in test-classpath @ApplicationScoped beans

### Symptom

An `@ApplicationScoped` bean in `src/test/java` with a synchronous `@Observes` method receives 0 events when `Event.fire()` is called. No error, no warning. The bean IS injectable (field injection works, assertNotNull passes), but the observer method is never invoked.

### Context

When testing CDI event firing in a `@QuarkusTest`:

```java
// src/test/java — event capture bean
@ApplicationScoped
public class EventCapture {
    final List<MyEvent> events = new ArrayList<>();
    void onEvent(@Observes MyEvent event) { events.add(event); }
}

// src/test/java — test class
@QuarkusTest
class MyTest {
    @Inject EventCapture capture;  // ← injected successfully, not null
    @Inject Event<MyEvent> event;  // ← injected successfully

    @Test void fires() {
        event.fire(new MyEvent(...));
        assertEquals(1, capture.events.size()); // ← FAILS: expected 1, got 0
    }
}
```

Meanwhile, production-classpath observers (`src/main/java`) for the same event type DO receive events during the same `@QuarkusTest`.

### What was tried (didn't work)

1. Static inner `@ApplicationScoped` class inside the `@QuarkusTest` class — same result (0 events)
2. Standalone `@ApplicationScoped` class in test package — same result (0 events)
3. Clean build (`mvn clean test`) to rule out stale augmentation cache — same result
4. Verified `Event` field injection works (assertNotNull passes) — injection works, delivery doesn't

### Root cause

Quarkus Arc discovers observer methods at build time during augmentation, which processes the application classpath (`target/classes`). Beans in the test classpath (`target/test-classes`) are discovered as CDI beans (so `@Inject` works), but their `@Observes` methods are NOT registered in the observer resolution table. This is an Arc implementation detail — standard CDI doesn't distinguish test vs production classpath.

### Fix

Don't test CDI event delivery via test-classpath observers. Instead:

### Solution 1 — Mock the Event in a unit test
**Approach:** Constructor-inject `Event<T>`, mock it with Mockito, verify `fire()` is called.
**Pros:** Fast, no Quarkus startup, works with any test framework.
**Cons:** Doesn't test actual CDI delivery chain.

```java
@SuppressWarnings("unchecked")
Event<MyEvent> mockEvent = mock(Event.class);
var service = new MyService(mockEvent);
service.doWork();
verify(mockEvent).fire(any(MyEvent.class));
```

### Solution 2 — Test the observer directly (unit test)
**Approach:** Test the observer bean in isolation with a mock broadcaster. This is the pattern used by `FsiDeliberationPushListenerTest`.
**Pros:** Tests the observer logic thoroughly without CDI.
**Cons:** Doesn't verify end-to-end wiring.

### Why this is non-obvious

The bean IS discovered by CDI (injection works, no unsatisfied dependency error). The natural expectation is that if CDI can create and inject the bean, it should also register its observer methods. The silent failure — no error, no warning, just 0 events — makes this particularly hard to diagnose.

### Why this fix

The production observer works. The event-to-observer chain is a CDI framework guarantee. Testing the observer logic in isolation (Solution 2) is more valuable than testing CDI delivery, which is infrastructure.
