### Symptom
-2.2pp precision regression (61.6% → 59.4%) in retrieval benchmark after
refactoring `embedBatch([text1, text2])` (batch=2) to individual
`embed(text1)` + `embed(text2)` (batch=1) calls. Same inputs, same model,
different retrieval results on a freshly re-indexed corpus.

### Context
Refactoring an embedding interface to route dense and sparse texts to separate
model calls instead of batching both through all models. The refactor appeared
purely internal — same inputs, same outputs, fewer unnecessary model calls.

### What was tried (didn't work)
Assumed the refactor was semantics-preserving since the same texts went to the
same models. The regression only surfaced in an end-to-end benchmark, not in
unit tests (which used deterministic stubs).

### Root cause
ONNX transformer models produce different embeddings for the same text at
different batch sizes. In a batch of 2, the shorter sequence is padded to match
the longer one. Padding tokens change the attention mask, which changes the
attention computation for all tokens — even those in the non-padded sequence.
The differences are small (order 1e-4 to 1e-3) but compound through cosine
similarity scoring to produce measurably different retrieval rankings.

### Fix
Preserve batch composition when refactoring embedding paths. If the old code
batched N texts together, the new code must also batch them together — even if
it only needs a subset of the results.

```java
// WRONG — changes batch composition
MultiModalEmbedding denseEmb = embedder.embed(denseText);   // batch=1
MultiModalEmbedding sparseEmb = embedder.embed(sparseText); // batch=1

// RIGHT — preserves batch composition
List<MultiModalEmbedding> batch = embedder.embedBatch(List.of(denseText, sparseText));
// cherry-pick: dense from [0], sparse from [1]
```

### Why this is non-obvious
The refactor looks safe — same text goes to the same model, just called
individually instead of batched. Transformer attention with proper masking
"should" ignore padding tokens. In practice, floating-point accumulation
order differs with different batch compositions, producing subtly different
results that compound through ranking.

### Why this fix
Preserving batch composition is cheaper than investigating model-level fixes.
The alternative — making ONNX output batch-invariant — would require changes
to the attention implementation or post-hoc normalization, neither of which
is controlled by the application layer.

### Alternatives considered
- Normalizing embeddings post-hoc to remove batch-dependent variance: rejected
  because the variance is in the attention computation, not the output norm
- Adding epsilon tolerance to retrieval scoring: rejected because it masks the
  problem rather than preventing it
