### Symptom
Generated `@Decorator` class fails to compile with `variable tenancyId is already defined` — but the duplicate declaration is in generated code, not hand-written code. The error points at a target/generated-sources file the developer didn't write.

### Context
A CDI `@Decorator` code generator (Jandex-based APT) emits method bodies that declare local variables for bookkeeping (e.g. `String tenancyId = currentPrincipal.tenancyId()`). When the delegate SPI method already has a formal parameter with the same name (e.g. `deregister(Path path, String tenancyId)`), javac reports a duplicate variable definition in the generated source.

### What was tried (didn't work)
Using a common variable name (`tenancyId`) for the generated local variable. This works for most SPI methods but silently collides with the subset that happen to have a parameter of the same name.

### Root cause
Generated method bodies share the local variable namespace with the delegate method's formal parameters. The generator emits the same local variable declaration in every method body without checking whether the delegate method already has a parameter of that name.

### Fix
Use a double-underscore prefixed name for generated locals: `__simTenancyId` instead of `tenancyId`. The prefix is unlikely to collide with any SPI parameter name.

An alternative is to scan the delegate method's parameter names (available via Jandex `MethodInfo.parameterName()`) and choose a unique name dynamically. This is more robust but adds complexity for marginal benefit — the `__` prefix convention is sufficient in practice.

### Why this is non-obvious
The error appears in generated source code that the developer didn't write and may not know how to find (target/generated-sources/annotations/). The compilation error message names the generated file, but the root cause is in the generator's code template — a different module entirely. The fix requires understanding both the generator's emit logic and the SPI interface's parameter names across all methods.
