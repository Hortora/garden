## Context

When registering workers for a capability that has both rule-based and LLM implementations, the LLM worker may require a runtime dependency (e.g., `langchain4j-anthropic`) that isn't on the classpath during development or testing. The `Agent.builder().model(ModelType.ANTHROPIC).build()` call fails eagerly at construction time (see GE-20260730-ae0fc4).

## Technique

Use `Worker.builder().noFunction().build()` to register the LLM worker as a placeholder. The routing strategy sees it as a candidate but it cannot execute. When the runtime dependency is added, replace `noFunction()` with the real `AgentWorkerFunction`.

```java
public static Worker create(ChatModel chatModel) {
    if (chatModel == null) {
        return Worker.builder()
                .name("llm-ioc-enrichment")
                .capabilityName("ioc-enrichment")
                .noFunction()
                .build();
    }
    // ... real AgentWorkerFunction when ChatModel is available
}
```

This preserves:
- Correct worker count in structural tests (6 workers, 2 per capability)
- Routing strategy awareness (the strategy sees both candidates)
- Bootstrap convention (rule-based wins by insertion order regardless)
- Clean activation path (swap `noFunction()` for real function when dependency arrives)

## Why this is non-obvious

The natural assumption is to skip registration entirely when the runtime isn't available — only create 3 workers instead of 6. But this changes the routing strategy's candidate set and can affect structural tests that verify worker count and capability coverage. `noFunction()` is a `WorkerFunction.None` sentinel that the builder accepts — it's not documented as a placeholder pattern.
