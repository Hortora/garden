### Symptom
JPA queries executed from `@RunOnVirtualThread` REST or GraphQL endpoints return
empty results silently — no exception, no warning, just wrong data. The same
service method works correctly when called from platform threads.

### Context
Quarkus RESTEasy Reactive with `@RunOnVirtualThread` dispatches method execution
to a virtual thread. The issue occurs when the endpoint delegates to a JPA-backed
service that lacks `@Transactional` on its methods. Particularly dangerous with
code generators (APT) that emit `@RunOnVirtualThread` without `@Transactional`.

### What was tried (didn't work)
- Assuming JPA queries would work on virtual threads the same as platform threads
- Relying on container-managed transaction wrapping (only applies to platform threads in RESTEasy Reactive)

### Root cause
On platform threads, Quarkus/Hibernate implicitly binds the JPA session to the
thread's request context. `@RunOnVirtualThread` dispatches to a new virtual thread
where this implicit binding doesn't occur. Without `@Transactional`, no JTA
transaction exists on the virtual thread, so Hibernate doesn't open or bind a
session. Queries execute without a persistence context and return empty.

### Fix
Always pair `@Transactional` with `@RunOnVirtualThread` on blocking endpoints.
`@Transactional` creates the JTA transaction that Hibernate uses to manage the
session on the virtual thread. `@Transactional(REQUIRED)` (the default) is safe
for all cases — no-op when no JPA is involved, cooperates with any downstream
transaction annotation.

```java
@Transactional
@RunOnVirtualThread
@GET
@Path("/entries")
public Response listEntries() {
    return Response.ok(repository.findAll()).build();
}
```

For generated code (APT processors), emit both annotations together under the
same guard condition (skip for streaming, webhook, and Uni-returning methods).

### Why this is non-obvious
1. No exception is thrown — queries silently return empty, making the bug
   appear to be a data issue rather than a transaction/session problem
2. The same code works on platform threads, so the bug only manifests when
   `@RunOnVirtualThread` is present
3. Quarkus documentation doesn't explicitly warn about this pairing requirement
4. Adding `@Transactional` to the service layer (downstream) also fixes it,
   but the root fix belongs at the dispatch boundary

### Alternatives considered
- Adding `@Transactional` only to service-layer beans — works but fragile;
  every consumer must discover the requirement independently
- Detecting JPA usage at compile time to conditionally emit `@Transactional` —
  over-engineered; the annotation is a no-op for non-JPA consumers
