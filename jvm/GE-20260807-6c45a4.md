### Symptom / context
You need module A (e.g. `runtime`) to call code in module B (e.g. `planning`), but the Maven dependency goes B→A, not A→B. Direct injection or method calls won't compile.

### What was tried (didn't work)
1. Placing GoalDecomposer in runtime — planning types (CasePlanModel, PlanItemDefinition, CompletionSemantics) not on runtime's classpath
2. Adding runtime→planning dependency — would create a circular dependency (planning already depends on runtime)
3. Event bus indirection — timing constraint required synchronous execution before CONTEXT_CHANGED

### Root cause / explanation
Multi-module Maven projects have strict unidirectional dependency chains. When the call direction opposes the dependency direction, CDI's dynamic bean discovery provides the bridge — the container sees all beans regardless of which module declared them, but the calling module needs a compile-time type to inject against.

### Fix
Define the SPI interface in a module both sides depend on (typically `common`), implement it in the higher module (`planning`), and inject via `Instance<SPI>` in the lower module (`runtime`):

```java
// common/src/main/java/.../spi/GoalDecomposer.java
public interface GoalDecomposer {
    void decompose(CaseInstance instance, CaseDefinition definition, MutableCaseContext context);
}

// planning/src/.../DefaultGoalDecomposer.java
@ApplicationScoped
public class DefaultGoalDecomposer implements GoalDecomposer { ... }

// runtime/src/.../CaseStartedEventHandler.java
@Inject Instance<GoalDecomposer> goalDecomposer;

if (goalDecomposer.isResolvable()) {
    goalDecomposer.get().decompose(instance, definition, context);
}
```

`Instance<>` provides transparent no-op when the implementing module is absent — the runtime module works correctly whether planning is on the classpath or not.

### Why this is non-obvious
The natural instinct is to put the implementation where it's called from (runtime), or to restructure dependencies. Neither works in a mature multi-module project. The CDI `Instance<>` pattern is documented for optional dependencies, but its use as an architectural boundary-crossing mechanism — where the SPI interface lives in a third module — is an established CaseHub convention (WorkOrchestrator, CaseOutcomeObserver) that isn't covered by Quarkus documentation.

### Why this fix
The SPI-in-common pattern is already established in the codebase (WorkOrchestrator uses the same approach per CLAUDE.md: "if an operational SPI takes CaseInstance or other common/internal/ types as parameters, it must go in common/spi/"). Following the existing convention over inventing a new indirection mechanism.

### Caveats
- The SPI interface can only use types available in `common` and its dependencies (typically `api`)
- `Instance.isResolvable()` (not `isUnsatisfied()`) is the correct guard — it returns true when exactly one bean matches
- The implementing bean must be `@ApplicationScoped` (or `@Singleton`) to be discovered by CDI
