### Symptom

After rebasing dependencies, the Quarkus application fails at build time with
dozens of `Unsatisfied dependency` CDI deployment errors for types that
previously resolved fine. Example: 57 errors for `CrossTenantCaseInstanceRepository`,
`EventLogRepository`, and similar JPA-backed types.

### Context

The application uses `quarkus.arc.exclude-types` to exclude engine-internal
CDI beans that require JPA stores the application doesn't provide:

```properties
quarkus.arc.exclude-types=io.casehub.engine.internal.**
```

The upstream engine module renamed its package from `io.casehub.engine.internal`
to `io.casehub.engine.runtime`. After a dependency rebase, the exclusion
pattern silently matches zero beans.

### What was tried (didn't work)

1. Cleared `~/.m2/repository/io/casehub/` and rebuilt all dependencies in
   order — CDI errors persisted
2. Checked for missing dependency declarations — all correct
3. Investigated specific CDI injection points — circular producer dependency
   made it look like a wiring bug

### Root cause

`quarkus.arc.exclude-types` uses glob patterns against fully-qualified class
names. When the upstream library renames a package, the glob silently stops
matching. No warning is logged. The previously-excluded beans become visible
to Arc's bean discovery, creating injection chains into types the application
doesn't provide (JPA repositories, cross-tenant stores).

The 57 CDI errors are a *consequence* of the exclusion miss, not the root cause.

### Fix

Update the exclusion pattern to match the renamed package:

```properties
quarkus.arc.exclude-types=io.casehub.engine.runtime.**
```

### Why this is non-obvious

The symptom (CDI unsatisfied dependencies) is completely disconnected from
the cause (package rename). The natural debugging path is to investigate the
specific CDI injection points, check for missing beans, or examine dependency
declarations — none of which reveal that an exclusion pattern stopped matching.
The fix is a one-line config change, but the diagnosis took examining the full
upstream diff to find the rename.

### Alternatives considered

- Adding mock `@Produces` methods for each missing type — would fix the
  symptom but not the root cause, and would need updating every time the
  upstream adds new beans
- Using `@IfBuildProfile` to conditionally enable beans — overly complex
  for what is a simple exclusion pattern issue
