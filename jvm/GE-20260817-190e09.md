**Symptom:** HQL bulk UPDATE with `SET d.endedAt = CURRENT_TIMESTAMP` throws `SemanticException`:

```
org.hibernate.query.SemanticException: Cannot assign expression of type
'java.sql.Timestamp' to target path 'd.endedAt' of type 'java.time.Instant'
```

**Context:** Entity field `private Instant endedAt` used in a bulk HQL update:

```java
em.createQuery("UPDATE DeliberationRecord d SET d.status = 'FAILED', "
    + "d.endedAt = CURRENT_TIMESTAMP WHERE d.status = 'IN_PROGRESS'")
    .executeUpdate();
```

The query looks valid — `CURRENT_TIMESTAMP` is standard HQL. But Hibernate 7's semantic type checker evaluates the SET assignment at parse time and rejects the type mismatch.

**What was tried (didn't work):**
- `CURRENT_TIMESTAMP` — rejected as `java.sql.Timestamp`
- `CURRENT_INSTANT` — not a valid HQL function

**Root cause:** Hibernate 7 introduced strict semantic type checking for HQL UPDATE SET assignments. `CURRENT_TIMESTAMP` resolves to `java.sql.Timestamp` in the type system, which is not assignable to `java.time.Instant`. This check happens at query parse time, not execution time. This contradicts GE-20260807-66fe1b's general guidance that "JPQL handles conversion correctly" — that applies to SELECT projections, not UPDATE SET assignments.

**Fix:** Use a query parameter with `Instant.now()`:

```java
em.createQuery("UPDATE DeliberationRecord d SET d.status = 'FAILED', "
    + "d.endedAt = :now WHERE d.status = 'IN_PROGRESS'")
    .setParameter("now", Instant.now())
    .executeUpdate();
```

Parameters go through Hibernate's type conversion layer, which correctly maps `java.time.Instant` to the database TIMESTAMP type.

### Why this is non-obvious

`CURRENT_TIMESTAMP` is standard HQL and works in SELECT clauses even with Instant-mapped columns (the result conversion handles it). The asymmetry — SELECT converts, SET rejects — is not documented. A developer who successfully used `CURRENT_TIMESTAMP` in SELECT queries has no reason to expect it fails in UPDATE SET.

### Why this fix

Query parameters let Hibernate's type system handle the conversion bidirectionally. Unlike `CURRENT_TIMESTAMP` (which is evaluated as a SQL function with SQL types), a parameter carries the Java type through the entire pipeline.

### Alternatives considered

- Native SQL `UPDATE ... SET ended_at = NOW()` — works but bypasses entity mapping and cache
- `CriteriaUpdate` with `currentTimestamp()` — same semantic check applies
