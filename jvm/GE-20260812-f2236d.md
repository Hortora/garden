### Convention
In a virtual-thread-aligned Quarkus/Mutiny codebase, `Uni<T>` stays on external-facing methods and is removed from internal SPI contracts.

**Keep Uni:** methods where the caller chains reactively on the result — `execute()`, `converse()`, pattern builder `execute()`. Also keep on `AgentInvoker.invoke()` where `Uni.join().all()` enables concurrent multi-agent dispatch.

**Remove Uni:** internal SPI methods where every implementation wraps synchronous logic and every consumer calls `.await().indefinitely()` — `route()`, `shouldActivate()`, `aggregate()`, `evaluate()`, `decompose()`.

### Known alternative
Keep Uni on everything for uniformity. This is a valid choice if the team values a single return-type pattern over reduced boilerplate. The trade-off: more ceremony at every call site, but no need to reason about which methods are "boundary" vs "internal."

### Rationale
The boundary test is: "does the caller compose reactively on this result, or does it consume it immediately?" If the answer is always `.await().indefinitely()`, the Uni wrapper is pure noise. Virtual threads make the thread-efficiency argument moot — blocking is free.
