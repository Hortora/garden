### Symptom

BGE-M3's XLM-RoBERTa SentencePiece tokenizer produces MORE token fragments than BERT WordPiece for Java class names and CDI annotations — the opposite of what's expected given SentencePiece's reputation as a superior tokenizer.

### Context

When evaluating embedding models for Java/Quarkus code-domain retrieval, BGE-M3 was expected to improve tokenization over nomic-embed-text's BERT WordPiece. XLM-RoBERTa BPE/SentencePiece is generally considered more capable than WordPiece for handling diverse vocabulary.

### Root cause

SentencePiece trained on multilingual web text fragments CamelCase identifiers at different boundaries than WordPiece. The multilingual vocabulary budget consumes capacity that could otherwise preserve programming identifiers. BGE-M3's tokenizer was not trained on code.

### Fix

Do not assume BGE-M3's tokenizer handles code identifiers better than nomic's WordPiece. Measured across 15 Java identifiers:

| Tokenizer | Avg tokens/identifier |
|-----------|----------------------|
| UniXcoder/jina-code (BPE, code-trained) | 3.1 |
| CodeBERT (BPE, code-trained) | 4.0 |
| nomic-embed-text (WordPiece) | 4.8 |
| **BGE-M3 (SentencePiece)** | **5.3** |

Key example — `@DefaultBean`:
- nomic (WordPiece): `@ default ##be ##an` (4 tokens)
- BGE-M3 (SentencePiece): `▁@ Def a ult Be an` (6 tokens)

BGE-M3's value for code-domain retrieval is its multi-modal capability (dense + sparse + ColBERT), not its tokenization quality.

### Why this is non-obvious

SentencePiece is widely regarded as superior to WordPiece for handling diverse vocabulary. The assumption that BGE-M3's XLM-RoBERTa tokenizer would naturally handle Java identifiers better than BERT WordPiece is intuitive but wrong — the training data composition matters more than the tokenizer architecture.

### Alternatives considered

- Assumed code-trained BPE tokenizers (UniXcoder, jina-code) would be best — confirmed at 3.1 avg tokens, but tokenization quality alone doesn't predict retrieval precision (see GE-20260803-f9d8ae).
