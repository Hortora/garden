### Symptom
Searching for a javadoc doclet that generates markdown output on JDK 21/22 returns multiple candidates (neuhalje/markdown-doclet, Abnaxos/markdown-doclet, Marklet) — but none of them work on modern JDKs.

### Context
The need arises when building RAG-indexable API references or LLM-friendly documentation from Java source. HTML javadoc is too verbose for LLM context windows; markdown is the target format.

### What was tried (didn't work)
- **neuhalje/markdown-doclet** — uses the pre-JDK 9 doclet API (`com.sun.javadoc`). Silently fails or throws `ClassNotFoundException` on JDK 17+. The README doesn't mention this limitation. Last released as 0.0.1.
- **Abnaxos/markdown-doclet** (pegdown-doclet) — same pre-JDK 9 API. GitHub issue #84 discusses JDK 9 port but it was never completed.
- **Marklet** — similar vintage, similar failure mode.
- **jdrupes-mdoclet v4.0** — supports JDK 21, but only handles markdown *input* (writing `///` comments); still generates HTML *output*.

### Root cause
JDK 9 (JEP 221) replaced the doclet API. All pre-2018 markdown doclets use the old API. The only tool that generates markdown *output* using the new API is jmarkdoc (Adam Bien), which requires JDK 25+ because it uses `jdk.javadoc` and `jdk.compiler` module features from that release.

### Fix
Install JDK 25+ alongside the production JDK. jmarkdoc analyzes source files — it doesn't compile or run the application. The JDK version constraint is on the tool, not the analyzed code.

```bash
# Run jmarkdoc with JDK 26 against JDK 22 source
/Library/Java/JavaVirtualMachines/jdk-26.jdk/Contents/Home/bin/java \
  -jar jmarkdoc.jar src/main/java docs/guides/api/
```

In CI: use `setup-java` with JDK 22 for the build step, JDK 26 for the doc generation step.

### Why this is non-obvious
The search results for "javadoc markdown doclet" return multiple promising-looking tools. None of them mention JDK version incompatibility prominently. A developer naturally tries the most-referenced tool (neuhalje), gets a cryptic failure, tries the next, and loses hours before discovering the ecosystem gap. The fix (dual JDK) is counterintuitive — most developers assume the tool must match the project's JDK.

### Alternatives considered
- Standard javadoc HTML → pandoc markdown conversion: fragile, messy output
- JavaParser-based custom extractor: works but reinvents what javadoc already does
- Upgrading the project to JDK 25+: too invasive just for doc generation
