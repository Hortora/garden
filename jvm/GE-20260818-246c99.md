### Convention
When a bridge interface needs types from both a core module and a protocol module that depends on core, place the bridge interface in the downstream agent/application module — not in core.

### Context
`ChatPerceptionBridge` references `ChatPerception` (from `quarkmind-chat-protocol`) and `ChatDeltaReport` (from `quarkmind-core`). Since `quarkmind-chat-protocol` depends on `quarkmind-core`, placing `ChatPerceptionBridge` in `quarkmind-core` creates a circular dependency: core → protocol → core.

### Alternative
Extract a third "bridge-api" module that both core and protocol can depend on. This adds Maven boilerplate for what is often a single interface — typically not justified until the bridge has multiple consumers.

### Rationale
The downstream module (agent) already depends on both core and protocol. Placing the bridge there adds zero new dependencies. The bridge is an application-tier integration concern, not a core abstraction — it wires two layers together, which is inherently a downstream responsibility.

### Why this is non-obvious
The bridge interface feels like a core abstraction — it defines how perception becomes actionable. The natural instinct is to place it alongside the other core SPIs. The circular dependency only surfaces at compile time, and the fix (moving one interface) feels like it weakens the core's API surface.
