## Symptom

A Quarkus `@BuildStep` that validates all methods annotated with a custom `@InterceptorBinding` (e.g. `@Audited`) unexpectedly finds the interceptor class's own `@AroundInvoke` method as a validation target. The interceptor carries the binding annotation at type level (required by CDI spec), so Jandex's `index.getAnnotations()` returns both the user-annotated business methods AND the interceptor's own methods.

The validation then fails because the interceptor's `audit(InvocationContext)` method naturally doesn't have the required parameter annotations (e.g. `@SubjectId`) that the build step enforces on business methods.

## Context

When writing a CDI interceptor for `@Audited`:
```java
@Interceptor
@Audited                    // ← type-level @InterceptorBinding (required by CDI)
@Priority(APPLICATION + 1)
public class AuditedInterceptor {
    @AroundInvoke
    public Object audit(InvocationContext ic) { ... }
}
```

The Jandex index sees `@Audited` on `AuditedInterceptor` (type-level), so `index.getAnnotations(AUDITED)` with `AnnotationTarget.Kind.CLASS` returns `AuditedInterceptor`. If the validator iterates that class's methods, it finds `audit(InvocationContext)` which has no `@SubjectId` parameter — and throws a validation error.

## Root cause

Jandex's `CombinedIndex.getAnnotations()` returns ALL annotation targets in the deployment archive — it does not distinguish between "business classes annotated by the user" and "interceptor classes that carry the annotation as a CDI binding marker."

## Fix

Skip `@Interceptor`-annotated classes in the build step:

```java
private static final DotName INTERCEPTOR = DotName.createSimple("jakarta.interceptor.Interceptor");

for (AnnotationInstance ann : index.getAnnotations(AUDITED)) {
    if (ann.target().kind() == AnnotationTarget.Kind.METHOD) {
        if (ann.target().asMethod().declaringClass().hasAnnotation(INTERCEPTOR)) continue;
        validateMethod(ann.target().asMethod());
    } else if (ann.target().kind() == AnnotationTarget.Kind.CLASS) {
        if (ann.target().asClass().hasAnnotation(INTERCEPTOR)) continue;
        // validate class methods...
    }
}
```

## Why this is non-obvious

The CDI spec requires the `@InterceptorBinding` annotation on both the target (user code) and the interceptor class. Jandex faithfully indexes both. A developer writing a build step validation would naturally iterate all annotation targets without considering that some of them are interceptor infrastructure, not user code. The error message ("@Audited on method 'AuditedInterceptor.audit' has no @SubjectId parameter") is confusing because the developer never annotated the interceptor with `@Audited` for validation purposes — CDI just requires it there.

### Alternatives considered

- Filtering by checking if the method has `@AroundInvoke` — fragile, misses `@AroundConstruct` and future interceptor method annotations
- Using a separate non-binding annotation for validation — breaks the CDI interceptor binding contract
