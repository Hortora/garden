## Symptom

`FlywayException: Found more than one migration with version 1` when starting a Quarkus application that depends on multiple modules with their own Flyway migrations.

## Context

A Quarkus app declares:
```properties
quarkus.flyway.locations=classpath:db/work/migration,classpath:db/memory/migration
```

Both modules provide `V1__*.sql` files. Flyway merges all locations into a single version timeline — two V1 files collide.

## Root cause

Flyway's multi-location configuration merges all migration files into one ordered sequence. Version numbers must be globally unique across all locations. When modules are developed independently, each starts at V1, causing collisions when composed.

## Fix

Use separate named Flyway datasources — one per module:

```properties
quarkus.flyway.locations=classpath:db/work/migration

quarkus.datasource.memory.db-kind=h2
quarkus.datasource.memory.jdbc.url=jdbc:h2:mem:app-memory;DB_CLOSE_DELAY=-1
quarkus.flyway.memory.migrate-at-start=true
quarkus.flyway.memory.locations=classpath:db/memory/migration
```

Each named Flyway instance has its own `flyway_schema_history` table and independent version sequence.

## Why this is non-obvious

The merged-location model works fine when all migrations belong to the same project. The failure only appears when independently-versioned modules are composed — which is the norm in multi-module platforms.
