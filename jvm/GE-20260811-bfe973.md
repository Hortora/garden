### Symptom
An automated CDI audit (parent#340) flagged 4 `@ApplicationScoped` classes as having "unnecessary CDI" based on low `@Inject` field counts (0-1 injections). 3 of 4 were false positives.

### Context
Quarkus extension projects use CDI for three purposes beyond state management:
1. **SPI displacement** — `@DefaultBean` provides a fallback; consumers override with their own bean
2. **Interface injection** — concrete class implements an interface; consumers inject the interface, CDI resolves the binding; `@Alternative @Priority` enables override
3. **CDI-managed dependencies** — `@Inject ObjectMapper` gets Quarkus's configured Jackson mapper, not a bare `new ObjectMapper()`

Injection count tells you nothing about whether CDI is structurally necessary.

### Root cause
The audit tool equated "few injections" with "unnecessary CDI". It checked dependency count but not whether the class participates in an SPI contract (implements an interface that other beans inject) or uses `@DefaultBean` for displacement.

### Fix
Before removing `@ApplicationScoped` from a class, verify all three:
1. **Does it implement an interface?** → Check if any bean injects that interface. If yes, CDI is required.
2. **Is it `@DefaultBean`?** → It exists to be displaced. CDI is the mechanism.
3. **Does it `@Inject` CDI-managed beans?** → Even one injection (e.g. `ObjectMapper`) means it needs CDI to get the correctly-configured instance.

Only remove CDI when ALL three are negative — the class is a plain utility with no interface, no `@DefaultBean`, and no injections.

### Why this is non-obvious
The audit heuristic ("zero injections = no CDI needed") is intuitive and works for application-layer beans. It fails systematically in extension projects where CDI's role is architectural (SPI wiring, displacement) rather than dependency management.

### Alternatives considered
- Considered removing CDI from all 4 flagged classes as the audit recommended — would have broken SPI override mechanisms for 3 of them
- Considered converting SPI classes to static utilities with manual wiring — rejected because it eliminates the consumer override capability that is the entire point of the SPI pattern
