### Symptom

`RoutingAgentProvider` logs `pool=disabled` at startup even though `agent-config.yaml` declares a `pools:` section. Each LLM call spawns a fresh CLI process with full auth handshake overhead.

### Context

The `casehub-platform-agent-session` artifact is split into two modules:
- `casehub-platform-agent-session-core` — pure Java library with pool types, session management, clearing policies
- `casehub-platform-agent-session` — Quarkus CDI module with `SessionBeans` producer that creates `SessionPoolRegistry` from agent-config YAML

### Root cause

Depending on `-core` only gives you the library types but no CDI producer. `SessionPoolRegistry` is never constructed, so `RoutingAgentProvider`'s factory receives `null` for the pool registry parameter and logs `pool=disabled`.

### Fix

1. Depend on the full CDI module, not just core:
```xml
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-platform-agent-session</artifactId>
</dependency>
```

2. Add Jandex index so Quarkus discovers the CDI beans:
```properties
quarkus.index-dependency.casehub-platform-agent-session.group-id=io.casehub
quarkus.index-dependency.casehub-platform-agent-session.artifact-id=casehub-platform-agent-session
```

3. Declare pools in agent-config.yaml:
```yaml
pools:
  voice:
    agent-id: speech-demo
    backend: claude
    max-active: 3
    salience: 2
    clearing:
      policy: every-call
```

### Why this is non-obvious

The `-core` module compiles and runs without errors — no missing class, no CDI unsatisfied dependency. The only signal is a log line (`pool=disabled`) that looks informational, not like a missing dependency. The module naming convention (`-core` = implementation, no suffix = CDI wiring) is a casehub platform convention that's easy to miss.
