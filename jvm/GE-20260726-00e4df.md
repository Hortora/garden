### Symptom
After issue #112 (investigation triage — rule-based classification), ALL existing `@QuarkusTest` integration tests that start an investigation and wait for the gate WorkItem timeout after 15 seconds with `ConditionTimeoutException`. No compilation error, no assertion failure — pure timeout.

### Context
The triage worker was a stub returning `SAR_WARRANTED` for every case. Issue #112 replaced it with `InvestigationTriageEvaluator` which computes a risk score from specialist findings. Test transactions using `FlagReason.STRUCTURING` or `FlagReason.LAYERING` produce entity type `CORPORATE` with risk score 0.35, which scores 0.42 total — below the SAR threshold of 0.6. The triage classifies these as `FALSE_POSITIVE`, the case exits via the `investigation-cleared` goal, and no SAR drafting or gate WorkItem ever happens.

### What was tried (didn't work)
1. Checking CDI wiring — the error looks like a CDI or engine issue (timeout, no error message)
2. Checking Hibernate session state — red herring; the Hibernate concurrency issue is a separate problem
3. Increasing timeout — the gate is never created regardless of wait time

### Root cause
The `entityResolutionWorker` stub maps `FlagReason` to entity type and risk score:
- `PEP_MATCH` → PEP (0.87)
- `HIGH_RISK_JURISDICTION` → SHELL_COMPANY (0.95)
- Everything else → CORPORATE (0.35)

`HardGateEvaluator` forces `SAR_WARRANTED` for `SHELL_COMPANY` entity type. Tests using `STRUCTURING` or `LAYERING` don't trigger any hard gate and score below the SAR threshold.

### Fix
Use `FlagReason.HIGH_RISK_JURISDICTION` for test transactions that need the SAR path. This maps to `SHELL_COMPANY` entity type, which triggers the `HardGateEvaluator.SHELL_COMPANY` hard gate → immediate `SAR_WARRANTED` regardless of risk score.

```java
var tx = new SuspiciousTransaction(
        "TXN-" + UUID.randomUUID(), "ACC-A", "ACC-B",
        new BigDecimal("50000"), "USD", Instant.now(),
        FlagReason.HIGH_RISK_JURISDICTION);  // triggers SHELL_COMPANY hard gate
```

### Why this is non-obvious
The timeout gives no indication that triage decided differently. The error message (`ConditionTimeoutException: Lambda expression was not fulfilled within 15 seconds`) points at gate WorkItem creation, not at triage. The connection between flag reason → entity type → risk score → triage decision → goal selection → whether the gate is ever created requires tracing through 5 layers of the investigation flow. A developer debugging the timeout would naturally check CDI wiring, Hibernate, and Quartz scheduling before suspecting triage classification.
