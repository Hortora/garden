## Symptom

An enforcement gate inside `MessageService.dispatch()` performs three side effects — dispatches an audit EVENT, pauses the channel, expires open commitments — then throws `EnforcementBlockedException`. After the throw, none of the side effects are visible: the channel is still unpaused, the commitments are still OPEN, and the audit EVENT message is gone (though its `LedgerEntry` survives because `LedgerWriteService.record()` uses `REQUIRES_NEW`).

## Context

The enforcement gate runs inside `dispatch()`, which is `@Transactional(REQUIRED)`. The gate calls `channelService.pause()` and `commitmentService.expireByChannel()`, both annotated `@Transactional` (defaulting to `REQUIRED`), so they join the outer transaction. The gate also dispatches an enforcement EVENT via a self-call to `dispatch()` — same transaction.

When the gate throws `EnforcementBlockedException` (an `IllegalStateException` subclass), the JTA transaction is marked for rollback. Every write performed within that transaction — the pause, the expiry, the EVENT message — is undone.

The watchdog system avoids this because `WatchdogEvaluationService.evaluateAll()` is a separate CDI bean that calls `MessageService.dispatch()` through the CDI proxy, and **does not throw after containment** — its transaction commits normally.

## What was tried (didn't work)

Performing enforcement actions (pause, expire, EVENT dispatch) inline in the `enforceIfRequired()` method before throwing. The actions execute successfully but are rolled back when the throw propagates through the `@Transactional` boundary.

## Root cause

JTA rollback semantics: any unchecked exception thrown from a `@Transactional` method marks the transaction for rollback. All side effects performed within that transaction are undone, regardless of whether they were performed by the current method or by called methods that joined the same transaction via `REQUIRED`.

## Fix

Extract enforcement execution to a separate CDI bean (`EnforcementExecutor`) annotated `@Transactional(REQUIRES_NEW)`. The bean is injected into `MessageService` and called through the CDI proxy — this is critical, because a direct method call (self-call) bypasses the proxy and the `REQUIRES_NEW` annotation has no effect.

```java
@ApplicationScoped
class EnforcementExecutor {

    @Inject MessageDispatcher messageDispatcher;
    @Inject ChannelService channelService;
    @Inject CommitmentService commitmentService;

    @Transactional(Transactional.TxType.REQUIRES_NEW)
    void execute(Channel ch, MessageDispatch dispatch,
                 List<TaggedAdvisory> violations, String tenancyId) {
        // 1. Dispatch audit EVENT — committed in this tx
        messageDispatcher.dispatch(/* EVENT builder */);
        // 2. If QUARANTINE: pause + expire — committed in this tx
        if (ch.enforcementMode() == EnforcementMode.QUARANTINE) {
            channelService.pause(ch.id());
            commitmentService.expireByChannel(ch.id());
        }
    }
}
```

The caller then throws after `execute()` returns. The REQUIRES_NEW transaction has already committed — its writes survive the outer transaction's rollback.

### Why this is non-obvious

The side effects execute successfully inside the gate method — no errors, no exceptions. The rollback is silent. A developer testing with InMemory stores (which don't participate in JTA transactions) would never see the problem — it only manifests with real JPA stores under JTA.

The same pattern (`REQUIRES_NEW` extraction for writes that must survive caller failure) is used by `ChannelCreateHelper.createInNewTransaction()` for channel creation race recovery and by `LedgerWriteService.record()` for ledger writes.

### Alternatives considered

- **Post-rollback dispatch via `TransactionSynchronization.afterCompletion(STATUS_ROLLEDBACK)`**: would fire after rollback but has no transaction context for the EVENT dispatch — the EVENT itself needs a transaction to persist.
- **CDI async event**: fires independent of transaction outcome but provides no audit trail in the channel timeline (no Message + LedgerEntry created).
