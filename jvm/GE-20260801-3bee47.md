### Symptom

`Cannot use the EntityManager/Session because neither a transaction nor a CDI request context is active. Consider adding @Transactional to your method to automatically activate a transaction, or @ActivateRequestContext if you have valid reasons not to use transactions.`

### Context

Worker functions registered via `Worker.builder().function(ctx -> {...})` in a `YamlCaseHub.augment()` method execute on Quartz scheduler threads (`QuarkusQuartzScheduler_Worker-N`). These threads have no active JTA transaction and no CDI request context. Any Panache Active Record call (`Entity.findById()`, `Entity.count()`, etc.) inside the worker function fails immediately.

The worker function is a plain `Function<Map<String, Object>, WorkerResult<Map<String, Object>>>` — not a CDI bean method, so `@Transactional` cannot be applied to it.

### What was tried (didn't work)

1. Adding `@Transactional` to the `augment()` method — does not propagate to the lambda's execution thread
2. Adding `@Transactional` to a private method called from the lambda — CDI self-invocation, interceptor not fired
3. Injecting a `@Transactional` CDI service — works for the service method, but the self-invocation issue applies to methods on the same CaseHub bean

### Root cause

The engine's `QuartzWorkerExecutionJob` fires worker functions on Quartz managed threads. Quartz thread pools are not CDI-managed — they have no request context and no JTA transaction association. The worker function interface (`Function`) has no CDI interceptor chain.

### Fix

Wrap Panache calls in `QuarkusTransaction.requiringNew()`:

```java
private Map<String, Object> buildSnapshot(UUID trialId) {
    return QuarkusTransaction.requiringNew().call(() -> {
        ClinicalTrial trial = ClinicalTrial.findById(trialId);
        // ... build snapshot from Panache queries
        return snapshot;
    });
}
```

`QuarkusTransaction.requiringNew()` programmatically begins a new JTA transaction on the current thread regardless of CDI context. The transaction commits when the `call()` lambda returns.

### Why this is non-obvious

The `augment()` method runs during CDI startup (has a transaction). The worker function's code LOOKS like it's part of the same class. Nothing in the engine API documentation warns that worker functions execute on Quartz threads without transaction context. The error only surfaces at runtime when the engine fires the binding — not at startup, not at case creation.

### Why this fix

`QuarkusTransaction.requiringNew()` is simpler than extracting a separate `@Transactional` CDI service bean. It's also correct regardless of whether the calling thread already has a transaction (Quartz: no; test thread: maybe). Extracting a service bean would work but adds indirection for a single method call.
