## Symptom

Adding a cross-cutting validation `@BuildStep` (e.g., `validateNoDuplicateGraphs`) to an
existing Quarkus deployment processor causes ALL `@RegisterExtension` tests in a multi-registration
test class to fail with the **wrong error message**. Tests expecting specific validation errors
("Duplicate node id", "references 'nonexistent'") instead get the cross-cutting validation's
error because inner classes from a **different** `@RegisterExtension` are picked up by the
Jandex index.

## Context

A test class like `CrossModelValidationTest` has multiple `@RegisterExtension static final
QuarkusUnitTest` fields, each with its own `withApplicationRoot(root -> root.addClasses(...))`.
Each registration is intended to test a different validation scenario with its own set of
inner classes.

The expectation is that `withApplicationRoot` isolates the classpath per test. But inner
classes of the test class are compiled into the same test classpath and are visible to the
Jandex index regardless of what `withApplicationRoot` declares.

## What was tried (didn't work)

Adding `validateNoDuplicateGraphs(List<DesiredStateGraphBuildItem>)` to
`DesiredStateAnnotationsProcessor` — the same processor class that all deployment tests
scan. The validation step picked up `DupDsA` and `DupDsB` inner classes in tests that
only intended to test "Duplicate node id" or "unresolved reference" scenarios.

## Root cause

Quarkus deployment tests using `@RegisterExtension` in the same class share the test
classpath. All inner classes (including `@DesiredState`-annotated interfaces and
`@DeclareNode`-annotated classes) are indexed by Jandex for **every** test registration,
not just the one that `addClasses()` them. A `@BuildStep` that scans
`index.getAnnotations(DESIRED_STATE)` sees all annotated inner classes across all test
registrations.

## Fix

Move cross-cutting validation build steps to a **separate processor class** in the module
that owns the cross-cutting concern (e.g., `YamlDesiredStateProcessor` in `yaml/deployment/`).
This way, the validation step is only on the classpath when the YAML module is present,
and the annotation-only deployment tests never see it.

### Alternatives considered

- **Update test assertions to accept either error message** — brittle; the wrong validation
  fires first and masks the intended error, so subsequent assertions also fail.
- **Move inner test classes to separate top-level files** — works but clutters the test
  structure and doesn't solve the fundamental index leakage.

## Why this is non-obvious

`withApplicationRoot(root -> root.addClasses(...))` strongly implies classpath isolation
per test registration. A developer adding a validation build step to an existing processor
wouldn't expect it to break unrelated tests that don't use the validated classes. The
Jandex index's broader scope (test classpath, not application root) is not documented.
