### Symptom
All YAML-configured preferences silently resolve to null. Trust gates, routing policies, and SLA thresholds all use defaults — no error, no warning. The application behaves as if no YAML configuration exists.

### Context
CaseHub Platform `ConfigFilePreferenceProvider` loads YAML files with scope-keyed entries. YAML scopes use tenancy-prefixed paths (e.g. `casehubio/devtown/trust-gate`). Callers use `SettingsScope.of(tenancyId, Path)`.

### What was tried (didn't work)
- Verified YAML file is loaded (no startup errors)
- Verified `casehub.platform.config.files` property points to correct classpath resources
- Checked `PreferenceKey` qualified names match YAML keys exactly

### Root cause
`ConfigFilePreferenceProvider.resolve()` walks `scope.scope()` (the `Path` from `SettingsScope`), not `scope.tenancyId()`. YAML keys are stored with the tenancy prefix as part of the `Path` (e.g. `Path.parse("casehubio/devtown/trust-gate")`). But callers wrote `SettingsScope.of("casehubio", Path.parse("devtown/trust-gate"))` — putting the tenancy in `tenancyId` instead of the path. The path segments never match.

### Fix
Include the tenancy prefix in the scope path:

```java
// Wrong — tenancy in tenancyId, not in path
SettingsScope.of("casehubio", Path.parse("devtown/trust-gate"));

// Correct — tenancy is part of the path hierarchy
SettingsScope.of("casehubio", Path.parse("casehubio/devtown/trust-gate"));
```

### Why this is non-obvious
The `SettingsScope` record has both `tenancyId` and `scope` fields. The natural assumption is that `tenancyId` participates in resolution — it doesn't. It's metadata only. The path must contain the full hierarchy including the tenancy prefix. No validation, warning, or error is emitted when the path doesn't match any YAML scope. Preferences silently return null, and callers fall through to defaults.
