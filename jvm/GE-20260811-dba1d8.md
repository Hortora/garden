# Fail-closed @DefaultBean for security SPIs

## Context

Quarkus CDI projects use `@DefaultBean` to provide fallback SPI implementations that activate when no consumer-provided alternative is on the classpath. The standard pattern is a no-op: return empty, do nothing, allow all. For non-security SPIs (preference stores, notification dispatch), this is correct — a missing capability means the feature is absent, not that it's insecure.

For security SPIs (scope validation, token verification, access control filters), a no-op `@DefaultBean` silently permits everything. A service that adds the security module as a dependency but forgets to provide an implementation gets no security — with no compile-time or runtime warning.

## The technique

Instead of a no-op that returns `Optional.empty()` (skip validation), the `@DefaultBean` returns a sentinel value that never matches any real credential or resource:

```java
@DefaultBean
@ApplicationScoped
public class FailClosedWorkerScopeExtractor implements WorkerScopeExtractor {

    private static final ResourceId NEVER_MATCH =
        new ResourceId("__deny__", "__no_scope_extractor_configured__");

    @Override
    public Optional<ResourceId> extractResourceId(ContainerRequestContext ctx) {
        return Optional.of(NEVER_MATCH);
    }
}
```

The filter compares the credential's resource scope against the extractor's result. Since `NEVER_MATCH` never equals any real `ResourceId`, every request with a worker credential gets a 403 — unless a real `WorkerScopeExtractor` is provided.

Services that genuinely want scope-free worker auth provide an explicit `PassthroughWorkerScopeExtractor` returning `Optional.empty()` — making the insecure choice deliberate.

## Why this is non-obvious

The platform's established convention is `@DefaultBean` no-ops that silently permit. Examples:
- `NoOpAccessControlProvider` — allows all access checks
- `NoOpWorkerCredentialStore` — stores nothing, finds nothing
- `MockPreferenceProvider` — returns defaults

A developer following the established pattern would naturally write `NoOpWorkerScopeExtractor` returning `Optional.empty()`. The distinction between "feature absent" (no-op is correct) and "security absent" (no-op is a vulnerability) is invisible in the code structure — both look like empty implementations of the same SPI.

This was caught as a HIGH finding during design review after the initial spec used the no-op pattern.

### Alternatives considered

- **Fail at startup** — throw from the `@DefaultBean` constructor if no alternative is found. Breaks services that add the module but don't need the SPI in all deployment profiles.
- **Log a warning** — returns empty but logs "no scope extractor configured." Still silently permits; the log is easily missed.
- **Require explicit opt-in** — no `@DefaultBean` at all; CDI fails with `UnsatisfiedResolutionException` if no implementation provided. Too aggressive for a library module that might be transitively included.
