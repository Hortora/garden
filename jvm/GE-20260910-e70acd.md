## Typed event wrappers for dynamic Vert.x EventBus address dispatch

### Context
When abstracting Vert.x EventBus with a framework-neutral `EventDispatcher` that routes by event type (not by address string), the Quarkus adapter maintains a `Map<Class<?>, String>` mapping event type to EventBus address. This works when each event type maps to exactly one address.

### The problem
Some handlers publish the same Java type to different addresses based on runtime state:
```java
// CaseStatusChangedHandler — publishes CaseInstance to dynamic address
String address = resolveStateAsString(newState); // CASE_COMPLETED or CASE_FAULTED
eventBus.publish(address, caseInstance); // same type, different addresses
```

A type→address map cannot handle this — `CaseInstance.class` maps to only one address.

### The technique
Introduce thin typed wrapper records so each address maps to a unique type:
```java
public record CaseCompletedEvent(CaseInstance caseInstance) {}
public record CaseFaultedEvent(CaseInstance caseInstance) {}
```

The core handler creates the appropriate wrapper:
```java
// Core POJO — dispatcher routes by wrapper type
if (newState == COMPLETED) {
    dispatcher.dispatch(new CaseCompletedEvent(caseInstance));
} else if (newState == FAULTED) {
    dispatcher.dispatch(new CaseFaultedEvent(caseInstance));
}
```

The Quarkus adapter's type→address map handles both:
```java
Map.entry(CaseCompletedEvent.class, EventBusAddresses.CASE_COMPLETED),
Map.entry(CaseFaultedEvent.class, EventBusAddresses.CASE_FAULTED),
```

Spring's @EventListener routes by type natively — each wrapper gets its own listener.

### Why this is non-obvious
The dynamic dispatch pattern (`resolveAddress(state)`) is idiomatic Vert.x — you wouldn't notice it breaks type-based routing until you try to build the type→address map and find 1:N mappings. The fix (wrapper records) is simple once you see the problem, but the problem is invisible until the map is constructed.

### Alternatives considered
- Address-based dispatch in the core (pass address string to dispatcher) — re-introduces framework coupling; Spring has no address-based equivalent
- Overloaded dispatch methods (`dispatch(String address, Object event)`) — breaks the @FunctionalInterface contract and adds address constants to the core
