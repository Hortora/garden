# Hibernate drop-and-create + sql-load-script bypasses Flyway version collisions for demo profiles

### Context
Multi-module Quarkus application with Flyway migrations from multiple classpath locations (e.g. `db/qhorus/migration`, `db/engine-ledger/migration`, `db/life/ledger/migration`). Two modules independently use the same Flyway version number (e.g. both have V2000), causing `Found more than one migration with version 2000` on startup. Production uses PostgreSQL with careful version coordination; demo mode uses H2 in-memory.

### Technique
For demo profiles, bypass Flyway entirely and use Hibernate's built-in schema management:

```properties
%demo.quarkus.flyway.migrate-at-start=false
%demo.quarkus.flyway."qhorus".migrate-at-start=false
%demo.quarkus.hibernate-orm.schema-management.strategy=drop-and-create
%demo.quarkus.hibernate-orm.sql-load-script=import-demo.sql
%demo.quarkus.hibernate-orm."qhorus".schema-management.strategy=drop-and-create
```

`drop-and-create` generates all tables from JPA entity annotations. `sql-load-script` loads demo data from a single SQL file after table creation. This avoids all Flyway version collisions, H2 syntax incompatibilities (partial indexes, multi-column ALTER TABLE, PL/pgSQL blocks), and cross-module migration ordering issues.

The `import-demo.sql` file uses H2-compatible SQL (CURRENT_TIMESTAMP, DATEADD) and covers all entities needed for the UI demo.

### Why this is non-obvious
The instinct is to fix all Flyway migrations for H2 compatibility. But when migrations span 5+ modules with independent version ranges, the fix cascade is substantial (partial indexes, PL/pgSQL, multi-column ALTER TABLE, SNAPSHOT API drift changing column names). Hibernate's schema generation from annotations sidesteps the entire problem for ephemeral demo databases where migration history doesn't matter.
