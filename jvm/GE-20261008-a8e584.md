### Symptom

A CDI observer method (`@Observes SomeEvent`) on a class instantiated via a `@Produces` method is never invoked. No error, no warning, no log output. The event fires correctly — other observers on non-produced beans receive it. The class compiles, the bean resolves via CDI injection, all other methods work.

### Context

When a CDI bean is created via a `@Produces` method (e.g. in a `DefaultBeans` class), the resulting instance is **producer-managed**, not **bean-managed**. CDI observer methods are only dispatched to beans discovered through bean-defining annotations (`@ApplicationScoped`, `@Singleton`, etc.). Producer-managed instances are invisible to the event dispatch mechanism.

```java
// In CognitionDefaultBeans.java — creates a producer-managed instance
@Produces @DefaultBean @Singleton
SubThoughtTickParticipant subThoughtTickParticipant(
        RuleBasedSubThoughtExtractor extractor,
        Instance<MentalModelOrchestrator> mentalModel,
        Instance<SubjectResolver> resolver) {
    return new SubThoughtTickParticipant(extractor, ...);
}
```

```java
// In SubThoughtTickParticipant.java — this observer NEVER fires
void onSubThoughtsEnriched(@Observes SubThoughtsEnriched event) {
    // Dead code — CDI won't dispatch to producer-managed instances
    asyncCache.put(event.agentId() + ":" + event.tenantId(), ...);
}
```

The entire async enrichment cache path was silently broken. Only discovered during a post-implementation audit — all tests passed because no test exercised the CDI event dispatch chain.

### What was tried (didn't work)

- The observer method compiled and looked correct
- The `@Produces` bean resolved correctly via `@Inject`
- All non-observer methods on the bean worked as expected
- Unit tests that called `handleEnriched()` directly passed

### Root cause

CDI spec §2.5.2: observer methods are discovered on managed beans and session beans. A producer method creates a contextual instance but does not make the produced class a managed bean — its lifecycle is controlled by the producer, not the container. The container never scans the produced class for observer methods.

### Fix

Extract the `@Observes` method into a dedicated `@ApplicationScoped` observer bean that injects the produced bean and delegates:

```java
@ApplicationScoped
public class SubThoughtsEnrichedObserver {

    @Inject
    SubThoughtTickParticipant participant;

    void onSubThoughtsEnriched(@Observes SubThoughtsEnriched event) {
        participant.handleEnriched(event);
    }
}
```

Remove the `@Observes` annotation from the produced class and rename the method to a plain package-private method (`handleEnriched`).

### Why this is non-obvious

The pattern compiles cleanly, the bean works for injection and method calls, and there is no compile-time or runtime warning. The observer is simply never called. In a codebase where the class could have been `@ApplicationScoped` directly but was produced via `@Produces` for optional-dependency reasons (using `Instance<T>.isResolvable()`), this is easy to miss during implementation and review.

### Why this fix

The alternative — making the class `@ApplicationScoped` directly — would require all constructor dependencies to be mandatory CDI beans. The `@Produces` pattern was chosen specifically because some dependencies are optional (`Instance<T>`). The observer-delegation pattern preserves the optional-dependency benefit while restoring CDI event dispatch.

### Alternatives considered

- Making `SubThoughtTickParticipant` directly `@ApplicationScoped` — rejected because it has optional dependencies that require `Instance<T>` unwrapping, which is cleaner in a producer method
- Using `@ObservesAsync` instead — wrong fix; the issue is not sync vs async dispatch, it's that the observer is never discovered at all
