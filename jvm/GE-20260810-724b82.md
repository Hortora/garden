### Symptom
Adding a `@ApplicationScoped SlaBreachPolicy` implementation and excluding `NoOpSlaBreachPolicy` via `quarkus.arc.exclude-types` has no effect — the NoOp policy still runs.

### Context
Implementing `SocSlaBreachPolicy` for SOC incident response. Initial assumption: CDI displacement pattern (same as `NoOpCapabilityHealth` exclusion from #20). But the policy was never invoked.

### What was tried (didn't work)
1. Added `SocSlaBreachPolicy` with `@ApplicationScoped`
2. Added `NoOpSlaBreachPolicy` to `quarkus.arc.exclude-types`
3. Expected the SOC policy to be injected — it wasn't

### Root cause
`ExpiryLifecycleService` resolves the policy at startup via `StrategyResolver`, not CDI injection:

```java
@PostConstruct
void init() {
    this.slaBreachPolicy = strategyResolver.resolve(
        SlaBreachPolicy.class, config.sla().breachPolicy());
}
```

The policy ID comes from config: `casehub.work.sla.breach-policy` (defaults to `"no-op"`). Both NoOp and custom policies coexist in CDI — the resolver picks by `id()`.

### Fix
Set the config property instead of CDI exclusion:

```properties
casehub.work.sla.breach-policy=soc-escalation
```

No `quarkus.arc.exclude-types` needed for `NoOpSlaBreachPolicy`.

### Why this is non-obvious
The `NoOpCapabilityHealth` from the same platform uses CDI displacement (`quarkus.arc.exclude-types`). Natural assumption: all NoOp* defaults follow the same pattern. But `SlaBreachPolicy extends NamedStrategy` — the `NamedStrategy` interface signals config-driven resolution, not CDI-driven.
