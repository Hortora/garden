## Context

When constructing a Nimbus `OctetKeyPair` for JWKS serialization from a JCA `KeyPairGenerator.getInstance("Ed25519")` key pair, the obvious path is `OctetKeyPairGenerator` — but that requires Google Tink at runtime (see GE-20260914-659d40). The `OctetKeyPair.Builder` needs a `Base64URL`-encoded raw 32-byte public key (the `x` parameter), but `EdECPublicKey` doesn't expose raw bytes directly.

## Fix

`EdECPublicKey.getEncoded()` returns X.509 SubjectPublicKeyInfo format — for Ed25519, this is exactly 44 bytes: 12 bytes of ASN.1 header followed by the 32-byte raw public key. Extract the last 32 bytes:

```java
EdECPublicKey pub = (EdECPublicKey) keyPair.getPublic();
byte[] encoded = pub.getEncoded();
byte[] rawPub = new byte[32];
System.arraycopy(encoded, encoded.length - 32, rawPub, 0, 32);

OctetKeyPair jwk = new OctetKeyPair.Builder(Curve.Ed25519, Base64URL.encode(rawPub))
        .keyID(kid)
        .keyUse(KeyUse.SIGNATURE)
        .build();
```

For the private key (needed when constructing a full key pair for signing):

```java
EdECPrivateKey priv = (EdECPrivateKey) keyPair.getPrivate();
byte[] privBytes = priv.getBytes().orElseThrow();

OctetKeyPair fullJwk = new OctetKeyPair.Builder(Curve.Ed25519, Base64URL.encode(rawPub))
        .d(Base64URL.encode(privBytes))
        .keyID(kid)
        .keyUse(KeyUse.SIGNATURE)
        .build();
```

## Why this is non-obvious

`EdECPublicKey` exposes `getPoint()` which returns an `EdECPoint` with a BigInteger y-coordinate and an `isXOdd` flag. Reconstructing the RFC 8032 32-byte representation from that requires understanding Edwards curve point encoding — bit manipulation of the y-coordinate with the x-oddness flag in the high bit. The `getEncoded()` shortcut (last 32 bytes of the X.509 SubjectPublicKeyInfo) bypasses all of that. This relationship between X.509 encoding and raw Ed25519 key bytes is not documented in JCA javadocs or Nimbus documentation — it follows from the ASN.1 structure defined in RFC 8410.
