### Symptom
WorkItem deadline extends indefinitely — the escalation fallback in a `Chained` decision never fires. No error, no log. The WorkItem just keeps getting extended on every breach cycle.

### Context
Implementing `SlaBreachPolicy` for SOC incident response. P3 priority used `Extend(12hr).thenOnBreach(EscalateTo(SOC_MANAGER))` intending: first breach extends, second breach escalates.

### What was tried (didn't work)
`thenOnBreach()` creates a `Chained(primary, fallback)` decision. The API is fluent and reads as sequential — "extend, then on next breach, escalate." This is wrong.

### Root cause
`ExpiryLifecycleService.executeBreachDecision()` processes `Chained` atomically within a single breach event:

```java
case BreachDecision.Chained chained:
    try {
        return executeBreachDecision(item, chained.primary(), ctx, now);
    } catch (BreachExecutionFailed e) {
        return executeBreachDecision(item, chained.fallback(), ctx, now);
    }
```

The fallback only runs if the primary throws `BreachExecutionFailed`. But `executeExtend()` never throws — it always succeeds by bumping `expiresAt`. So `Extend.thenOnBreach(EscalateTo)` = always Extend, EscalateTo unreachable.

Same issue: `EscalateTo.to(SOC_MANAGER).thenOnBreach(new Fail(...))` — EscalateTo with non-empty groups always succeeds, so Fail never fires.

The only way a primary fails is `executeEscalateTo()` with empty groups.

### Fix
Use pure stateless flat decisions — never `thenOnBreach()`. Cross-breach progression comes from `candidateGroups` updates:

```java
public BreachDecision onBreach(SlaBreachContext context) {
    Set<String> groups = context.task().candidateGroups();
    if (groups.contains(SOC_MANAGER))
        return new BreachDecision.Exhausted("SLA exceeded");
    return BreachDecision.EscalateTo.to(SOC_MANAGER).withDeadline(Duration.ofHours(24));
}
```

Each `EscalateTo` execution replaces `candidateGroups`. On the next breach, the policy reads the updated groups and returns a different decision. No state machine needed.

### Why this is non-obvious
The `thenOnBreach()` fluent API reads as "do this, then on next breach do that" — a temporal sequence. The actual semantics are "try this, catch failure, try that" — an atomic fallback within a single breach event. The naming is misleading and no Javadoc clarifies the execution model.

### Alternatives considered
- Using `Chained` for P3 extend-then-escalate — rejected because Extend never fails, so the fallback is unreachable
- Storing breach count in a separate table — rejected as unnecessary complexity; candidateGroups already serves as the state signal
