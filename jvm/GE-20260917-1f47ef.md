### Symptom

`NoSuchMethodError` at Spring Boot application startup:

```
Caused by: java.lang.NoSuchMethodError:
  'org.flywaydb.core.api.configuration.FluentConfiguration
   org.flywaydb.core.api.configuration.FluentConfiguration.cleanOnValidationError(boolean)'
```

The application boots fine under Quarkus. Only the Spring Boot variant crashes.

### Context

When a multi-module Maven project uses both Quarkus BOM (which pulls Flyway 12.0.0) and Spring Boot BOM (which expects Flyway 10.x), the Quarkus BOM wins dependency resolution. `cleanOnValidationError()` was removed in Flyway 12 but Spring Boot 3.4's `FlywayAutoConfiguration` still calls it.

### What was tried (didn't work)

- Excluding `flyway-core` from the Spring test classpath — still needed at compile scope for production
- Pinning Flyway 10.x for Spring modules — creates version conflicts with Quarkus modules in the same reactor

### Root cause

BOM ordering in `<dependencyManagement>`: the Quarkus BOM is imported before the Spring Boot BOM, so its Flyway 12.0.0 wins for all modules. Spring Boot's FlywayAutoConfiguration assumes Flyway 10.x API.

### Fix

For tests in Spring Data JPA modules within a Quarkus-dominated reactor:

```properties
# application.properties (test)
spring.flyway.enabled=false
spring.jpa.hibernate.ddl-auto=create-drop
```

This disables Flyway auto-configuration entirely and uses Hibernate DDL generation from entity annotations. The same Flyway migrations are tested in the Quarkus counterpart modules.

For production Spring Boot deployments (separate Maven project, not shared reactor): the Spring Boot BOM pulls Flyway 10.x naturally — no conflict.

### Why this is non-obvious

The `NoSuchMethodError` message names a method that sounds like a configuration option, not a removed API. The natural instinct is to check Flyway docs for the config property, not to suspect a BOM version conflict. The root cause is cross-framework BOM interaction — something that only surfaces in dual-framework repositories.

### Alternatives considered

- Using Flyway's `spring.flyway.locations` with the shared SQL migrations — fails because the Flyway 12 API is incompatible regardless of migration paths
- H2 `MODE=PostgreSQL` covers most dialect features, so Hibernate DDL from entity annotations produces equivalent schemas
