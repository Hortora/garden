### Symptom
A REST endpoint calls a `@Transactional` service method that updates an entity field (e.g. `setTrackDelivery(channelId, true)`), then immediately re-fetches the entity via `findById()`. The re-fetched entity has `null` for the field that was just set.

### Context
JAX-RS resource method (not `@Transactional`) calls a `@Transactional` CDI service method that returns `void`. The service method modifies the entity via JPA dirty tracking (sets a field on a managed entity — no explicit `flush()` or `persist()`). After the service method returns (and its transaction commits), the resource calls `findById()` to get the updated entity for the response.

### What was tried (didn't work)
- Verified the service method correctly sets the field on the entity
- Confirmed the store's `find()` method works correctly in isolation
- Checked that InMemory store implementations update correctly (they do — the issue is JPA-specific)

### Root cause
The `@Transactional` service method starts and commits its own transaction. JPA dirty tracking flushes the entity update at commit time. When `findById()` runs outside any transaction, it creates a new persistence context with a fresh L1 cache — but depending on the JPA provider and connection pool state, the new EntityManager may not see the just-committed data (connection reuse, isolation level, or cache coherency window).

### Fix
Make the calling method `@Transactional` so both the mutation and the re-fetch share the same persistence context:

```java
@PUT
@Path("/{id}/delivery-tracking")
@Transactional
public Response setDeliveryTracking(@PathParam("id") String id, DeliveryTrackingRequest req) {
    Channel ch = resolve(id);
    if (ch == null) return error(404, "Channel not found: " + id);
    channelService.setTrackDelivery(ch.id(), req.enabled());
    // Now findById shares the same persistence context — sees the dirty entity
    Channel updated = channelService.findById(ch.id()).orElseThrow();
    return Response.ok(toResponse(updated)).build();
}
```

The service method's `@Transactional(REQUIRED)` joins the endpoint's transaction. The entity mutation is visible in the shared L1 cache before commit.

### Why this is non-obvious
The mental model is "the service method committed, so findById should see it." In most cases with connection pooling and READ COMMITTED isolation, this works — making the failure intermittent and hard to reproduce. The root cause is not a transaction isolation issue but a JPA L1 cache lifetime issue: the EntityManager that did the dirty tracking is gone, and the new one may not immediately reflect the committed state. The fix (wrapping the caller in `@Transactional`) is counterintuitive — the caller has no mutations of its own.
