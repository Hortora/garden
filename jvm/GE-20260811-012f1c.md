### Symptom

A CDI audit flags classes as "unnecessary CDI — zero injections" based on having no `@Inject` fields or constructor parameters. Removing `@ApplicationScoped` from these classes causes `UnsatisfiedResolutionException` at deployment or `NoSuchMethodError` at test time.

### Context

Automated or manual CDI audits that scan for beans with zero `@Inject` dependencies and flag them for CDI removal. Common in large Quarkus projects where CDI bean count affects startup time and native image size.

### Root cause

"Zero injections" means the class injects nothing — but it says nothing about whether the class *is injected by others*. SPI implementations must be CDI beans so the container can discover and wire them at injection points. Three distinct patterns require CDI even with zero `@Inject` fields:

1. **SPI interface implementations** — `@ApplicationScoped` classes implementing an interface that is `@Inject`ed elsewhere. Arc must see the bean to satisfy the injection point.
2. **`@DefaultBean` fallbacks** — displacement semantics require both the default and the override to be scoped beans. Removing `@ApplicationScoped` breaks the displacement chain.
3. **Named strategy beans** — classes resolved by `StrategyResolver` or `Instance<T>` using their `id()` method. `@Unremovable @ApplicationScoped` keeps them in the container even without direct injection.

### Fix

Audit CDI beans on two axes, not one:

| Check | Safe to remove CDI? |
|-------|---------------------|
| Zero `@Inject` AND no interface AND not injected by others | Yes — use `new` at call sites |
| Zero `@Inject` BUT implements SPI interface | No — CDI needed for discovery |
| Zero `@Inject` BUT has `@DefaultBean` | No — CDI needed for displacement |
| Zero `@Inject` BUT resolved via `StrategyResolver` / `Instance<>` | No — CDI needed for container presence |
| Has `@Inject` fields or constructor params | No — CDI needed for injection |

To find what injects a class, use `ide_find_references` on the class symbol and look for field declarations or constructor parameters in other beans.

### Why this is non-obvious

The "zero injections" framing is intuitively compelling — if a class doesn't use CDI to get its dependencies, why does it need CDI? The answer is that CDI serves two roles: injecting dependencies *into* a bean, and making the bean *discoverable* by the container for injection *elsewhere*. Auditing only the first role misses the second entirely. In a project with 20+ SPI implementations, this mistake can cause dozens of deployment failures.

### Alternatives considered

- **Static analysis tool that checks both directions** — would be ideal but no standard Quarkus tooling does this. `quarkus-arc` unused-bean detection (`quarkus.arc.remove-unused-beans`) is conservative and keeps SPI impls, but doesn't help with manual audits.
- **Grep for the class name across the project** — catches direct references but misses interface-typed injection points where the SPI interface is injected, not the concrete class.
