### Symptom

When adding a new LLM-calling Worker to QuarkMind (e.g. a pattern classifier), you need audit trail logging (via `AdvisoryChannelBroker`) and deferred outcome evaluation (via `DeferredAdvisoryEvaluator`). Creating new CDI event types and observers for each worker type leads to duplicated infrastructure.

### Context

QuarkMind's advisory infrastructure uses `CompletionCallback` → `AdvisoryCompleted` CDI event → observers (`AdvisoryChannelBroker`, `DeferredAdvisoryEvaluator`, `AdvisoryCompletionObserver`). This event-driven chain is generic — it uses `advisorId` and `capability` strings to distinguish callers.

### Fix

Reuse `CompletionCallback` from `io.quarkmind.plugin.advisory` and fire `AdvisoryCompleted` with a distinctive `advisorId` (e.g. `"llm-classifier:pattern-fallback"`) and `capability` name. All downstream observers — audit channel, outcome evaluation, latency recording — activate automatically.

```java
CompletionCallback callback = (advisorId, capability, gameFrame,
        recommendation, confidence, latencyMs, gameStateSnapshot) -> {
    completedEvent.fire(new AdvisoryCompleted(
        advisorId, capability, gameFrame, recommendation,
        confidence, latencyMs, gameStateSnapshot));
};

Worker worker = LlmPatternClassifierWorkerFactory.createWorker(chatModel, callback);
```

The `advisorId` field distinguishes classifier calls from advisory calls in audit logs and outcome records. No new event types, observers, or channels needed.

### Why this is non-obvious

The natural instinct is to create a `ClassificationCompleted` event type with its own observer chain — the advisory infrastructure looks advisory-specific because of its naming. The insight is that the `AdvisoryCompleted` record and its observers are actually generic LLM-worker-completion infrastructure parameterised by string IDs, not advisory-specific logic.
