### Symptom
`NullPointerException: executor required` when constructing `PlanItemDefinition.Primitive` with `null` executor — despite the executor field being unused for structural children of a compound.

### Context
`PlanItemDefinition.Primitive` is used in two distinct roles: (1) as a structural child of a `Compound` definition, where it exists only to populate `childrenIndex` and provide a definition ID — executor is never read; (2) as a worker-backed plan item, where executor identifies the assigned worker. The compact constructor validates all fields including executor via `Objects.requireNonNull(executor, "executor required")`.

### Root cause
The validation was added after `DefaultGoalDecomposer` was written. The decomposer passes `null` for executor at line 202 when creating structural Primitives. This is a latent NPE — it has not fired in production because the decomposer's code path predates the validation addition (or the validation is only enforced at compile/test time in certain configurations). Any new code creating structural Primitives (e.g. `DefaultPlanAdaptationEvaluator`) hits the NPE immediately.

### Fix
Pass a placeholder `ExecutorRef` instead of null:
```java
new PlanItemDefinition.Primitive(
    primitiveId, step.description(),
    ExecutorRef.of(step.capabilityName(), null), null);
```

### Why this is non-obvious
The executor field is semantically meaningless for structural Primitives — the dispatch loop uses the binding name (from `Compound.scopedBindings()`), not the Primitive's executor. A developer creating a structural Primitive would reasonably expect to pass `null` for a field the runtime never reads.

### Alternatives considered
- Remove `requireNonNull(executor)` from the compact constructor — rejected because worker-backed Primitives legitimately need the validation
- Split Primitive into two types (structural vs executable) — cleaner but larger refactoring scope; tracked as a future improvement
