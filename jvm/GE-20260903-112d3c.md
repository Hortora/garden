### Symptom
Downstream project's `@QuarkusTest` fails during Quarkus code generation with:
`Failed to resolve artifact io.casehub:casehub-platform-yaml-core:jar:`
Maven also warns: `'dependencies.dependency.version' for io.casehub:casehub-platform-yaml-core:jar is missing`

The upstream project's source POM has the dependency with a correct `<version>` element. All unit tests in the upstream pass. The failure only appears in downstream consumers.

### Context
Multi-module Maven project using `maven-flatten-plugin`. Module A declares a dependency with `<version>${property}</version>`. During `mvn install`, the flatten plugin produces a simplified POM for the local repository. If the property is defined in a parent but the flatten mode doesn't preserve it, the installed POM contains a versionless `<dependency>` entry.

### What was tried (didn't work)
- Checking the source POM — version is present and correct
- Rebuilding the downstream project — same error
- Checking `~/.m2/repository` for the artifact — it exists at the correct version

### Root cause
The flatten plugin's simplification mode strips the `<version>` element when the version comes from a property it cannot resolve in the flattened context. The source POM is correct, but the installed flattened POM at `~/.m2/repository/<group>/<artifact>/<version>/<artifact>-<version>.pom` has a bare `<dependency>` without `<version>`. Maven's dependency resolver propagates this as a versionless transitive dependency, which Quarkus's `ApplicationDependencyResolver` cannot resolve.

A secondary symptom: failed resolution attempts create poisoned cache directories with literal `${property.name}` as the version path (e.g. `~/.m2/repository/io/casehub/artifact/${casehub.version}/`).

### Fix
Two-step fix:
1. Rebuild and re-install the upstream module: `mvn install -DskipTests` in the upstream project — regenerates the flattened POM
2. Clean poisoned cache entries: `rm -rf ~/.m2/repository/<group>/<artifact>/\${property.name}/`

Permanent fix: move the dependency's version management to the parent BOM's `<dependencyManagement>` section where the flatten plugin preserves it, rather than using a property in the module's own `<dependencies>`.

### Why this is non-obvious
The source POM is correct. The upstream project builds and tests pass. The error only surfaces in downstream consumers via transitive dependency resolution. Inspecting the installed POM in `~/.m2/repository` is not a standard debugging step — developers typically check the source POM and assume the installed version matches.

### Alternatives considered
- Adding the dependency directly to the downstream POM with an explicit version — works but defeats dependency management
- Using `mvn dependency:tree -Dverbose` — shows the gap but doesn't explain why the version is missing
