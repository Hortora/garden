### Symptom
Compiling an MVEL expression against a Java record type via
`MvelExpressionEngine.compile(expr, RecordType.class, Boolean.class)` throws
`ExpressionCompilationException` wrapping `UnsolvedSymbolException{context='fieldName'}`.

### Context
`MvelExpressionEngine` has two code paths: `LazyMapMvelExpression` (for Map contexts)
and `PojoAdapterMvelExpression` (for all other types). The POJO adapter uses
`Introspector.getBeanInfo(contextType, Object.class)` to discover properties, converts
the POJO to a `Map<String, Object>`, then lazy-compiles via `compileMapEvaluator()`.

For Java records, `Introspector` does find the record components, and `toMap()` produces
a correct map. But `compileMapEvaluator()` then calls `MVEL.getTypeMap(evalContext)` which
derives types from the map values. When a map value is an instance of a sealed interface
(e.g. `AgentRef`), MVEL3's transpiler fails to resolve method calls on the concrete type.

### What was tried (didn't work)
- Compiling with `RoutingCandidate.class` as context type — `UnsolvedSymbolException` on
  record component `ref`
- Expression `ref.name() == "specialist"` against a `RoutingCandidate` context

### Root cause
The MVEL3 transpiler cannot resolve method calls through sealed interface hierarchies
when the type is inferred from a runtime map value. The concrete type
(`AgentRef.ExternalAgent`) implements `name()` but the transpiler can't find it via the
sealed parent.

### Fix
Compile against `Map<String, Object>` directly and project record fields into a HashMap
before evaluation:

```java
@SuppressWarnings("unchecked")
var compiled = engine.compile(guardExpr,
        (Class<Map<String, Object>>) (Class<?>) Map.class, Boolean.class);
// At evaluation time:
var map = new HashMap<String, Object>();
map.put("ref", candidate.ref());
map.put("descriptor", candidate.descriptor());
compiled.eval(map);
```

### Why this is non-obvious
The error occurs at lazy compilation time (first `eval()` call), not at
`engine.compile()` time. The `compile()` call succeeds — it only creates the adapter.
The actual MVEL3 transpilation happens on first evaluation, making the failure
appear as a runtime error rather than a compilation error.
