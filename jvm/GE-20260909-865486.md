### Symptom

Schema tests checking for kebab-case type discriminators (e.g., `"first-match"`, `"round-robin"`) fail — the generated schema contains camelCase names (e.g., `"firstMatch"`, `"roundRobin"`) instead.

Jackson deserialization works correctly (it reads `@JsonSubTypes` annotations). Schema generation produces wrong discriminator values silently — no error, just incorrect schema content.

### Context

When using sealed interfaces with both Jackson `@JsonSubTypes(name = "kebab-case")` for YAML/JSON deserialization and victools `SealedHierarchyModule` for JSON Schema generation, the two systems derive discriminator values from different sources.

### What was tried (didn't work)

Using `new SealedHierarchyModule()` (no-arg constructor) and expecting it to read Jackson's `@JsonSubTypes` annotations for discriminator names. The module ignores Jackson annotations entirely.

### Root cause

`SealedHierarchyModule.defaultDiscriminator(Class<?> subtype)` generates names from the Java class simple name with lowercase first letter:

```java
static String defaultDiscriminator(Class<?> subtype) {
    String name = subtype.getSimpleName();
    return Character.toLowerCase(name.charAt(0)) + name.substring(1);
}
```

This produces `"firstMatch"` from `FirstMatch.class`, not `"first-match"` from `@Type(name = "first-match")`. The mismatch is silent — schema generates successfully with wrong values.

### Fix

Pass discriminator overrides extracted from Jackson `@JsonSubTypes` annotations:

```java
private static Map<Class<?>, Map<Class<?>, String>> buildDiscriminatorOverrides() {
    var overrides = new HashMap<Class<?>, Map<Class<?>, String>>();
    for (var sealedType : List.of(RoutingSpec.class, TerminationSpec.class, ...)) {
        var annotation = sealedType.getAnnotation(JsonSubTypes.class);
        if (annotation == null) continue;
        var subtypeMap = new HashMap<Class<?>, String>();
        for (var subType : annotation.value()) {
            subtypeMap.put(subType.value(), subType.name());
        }
        overrides.put(sealedType, subtypeMap);
    }
    return overrides;
}

// Pass to constructor
new SealedHierarchyModule(overrides);
```

### Why this is non-obvious

The `SealedHierarchyModule` constructor accepts `Map<Class<?>, Map<Class<?>, String>> discriminatorOverrides` but this parameter is undocumented — you have to read the source to discover it. The default behaviour (camelCase from class names) works for projects that don't use Jackson annotations, so the mismatch only surfaces when both systems target the same sealed interfaces.
