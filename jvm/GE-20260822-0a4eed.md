## Symptom

Compile error when importing `com.cronutils.parser.CronParser` or other
cron-utils classes in a project that depends on `com.github.kagkarlsson:db-scheduler:16.x`.

```
package com.cronutils.parser does not exist
```

## Context

db-scheduler v16 uses cron-utils internally for `CronSchedule` support.
Earlier versions (v14 and below) declared cron-utils as a transitive dependency.
v16 **shades** cron-utils into its own jar under a relocated package.

## Root cause

The `db-scheduler` v16 Maven artifact no longer declares `com.cronutils:cron-utils`
as a dependency. Instead, cron-utils classes are relocated to
`com.github.kagkarlsson.shaded.cronutils.*` inside the db-scheduler jar.

The `db-scheduler-16.11.0.pom` shows only `slf4j-api` and `jspecify` as
transitive dependencies.

## Fix

Use the shaded package path:

```java
import com.github.kagkarlsson.shaded.cronutils.model.Cron;
import com.github.kagkarlsson.shaded.cronutils.model.CronType;
import com.github.kagkarlsson.shaded.cronutils.model.definition.CronDefinitionBuilder;
import com.github.kagkarlsson.shaded.cronutils.model.time.ExecutionTime;
import com.github.kagkarlsson.shaded.cronutils.parser.CronParser;
```

The API is identical — only the package prefix changes.

## Why this is non-obvious

The db-scheduler README and migration guide do not mention the shading change.
The `CronSchedule` class in db-scheduler's public API uses cron-utils internally
but doesn't expose it. A developer computing next cron execution times independently
(outside db-scheduler's `Schedule` abstraction) will hit this.
