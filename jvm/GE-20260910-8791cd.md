### Symptom

A background scheduler iterates tenants and calls `phase.run(tenantId)` for each. The phase uses `ConcurrentHashMap` with a `swapAndReset()` pattern (atomically swap map references, return old map as snapshot). On the first tenant, `swapAndReset()` captures all accumulated data. On subsequent tenants, `swapAndReset()` returns an empty map — the data was already cleared.

Access counts for nodes in tenant-2+ are silently lost per flush cycle.

### Context

Occurs when:
- A `@Scheduled` or `ScheduledExecutorService` scheduler iterates `discoverTenants()` and calls phases per-tenant
- A phase accumulates global state (e.g. access counters from all tenants in a single `ConcurrentHashMap`)
- The phase swaps its state inside `run()`, which is called once per tenant

### What was tried (didn't work)

**Swap per tenant** — the obvious approach. Each `run(tenantId)` call does `swapAndReset()`. First tenant gets all data; subsequent tenants get empty snapshots. Data for non-first tenants is lost.

### Root cause

The swap-and-reset pattern assumes a single consumer per swap cycle. When the scheduler calls `run()` per-tenant, there are N consumers (one per tenant) per tick — but only one swap should happen per tick.

### Fix

Use a **tick-generation counter** to ensure the swap happens only once per scheduler tick:

```java
private AccessSnapshot cachedSnapshot;
private long lastSnapshotTick;
private long currentTick;

void beginTick() { currentTick++; }

@Override
public void run(String tenantId, List<String> subgraphPriority) {
    if (lastSnapshotTick < currentTick) {
        cachedSnapshot = tracker.swapAndReset();
        lastSnapshotTick = currentTick;
    }
    // cachedSnapshot is now shared across all tenant iterations within this tick
}
```

The scheduler calls `beginTick()` before iterating tenants. The phase swaps once on the first tenant call and reuses the cached snapshot for all subsequent tenants.

### Why this is non-obvious

The bug is silent — no exceptions, no errors. Access counts for the first tenant are correct. The symptom ("second tenant's access counts are always zero") only surfaces in multi-tenant deployments with active access tracking, and the per-cycle loss is self-correcting over time (new accesses are captured on the next tick), making it hard to detect via testing.

### Alternatives considered

- **Move swap to scheduler level** — passes snapshot as a parameter to `run()`. Changes the ConsolidationPhase SPI, which all phases implement.
- **Per-tenant tracker maps** — accumulate counts keyed by `(tenantId, nodeId)`. More memory, more complexity, but avoids the shared-state problem entirely.
