### What it does
A Java record component whose name and type match an interface method automatically satisfies that method — the record accessor IS the implementation. No `@Override` annotation needed.

```java
public interface NodeSpec {
    NodeType nodeType();
}

// The record component 'nodeType' auto-satisfies NodeSpec.nodeType()
record TestSpec(NodeType nodeType, String value) implements NodeSpec {}
```

### Practical application: configurable test specs
When an interface method returns a classification value (like a type enum), making that value a record component gives you configurable specs with zero boilerplate:

```java
// Convenience constructor for tests that don't care about type
record TestSpec(NodeType nodeType, String value) implements NodeSpec {
    TestSpec(String value) { this(NodeType.of("test"), value); }
}

// Usage — default type
new TestSpec("some-value")

// Usage — specific type for routing tests
new TestSpec(NodeType.of("database"), "pg-config")
```

### Why this is non-obvious
Most developers write explicit `@Override` methods on records when implementing interfaces. The record-component-as-implementation pattern is a language feature that's easy to overlook — especially when the interface was not designed with records in mind. The resulting code is more concise and the type is part of the record's identity (participates in equals/hashCode), which is often the desired semantics for test fixtures.
