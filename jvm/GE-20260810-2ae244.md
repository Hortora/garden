## Symptom
Replanned HTN execution silently fails with `RoutingDecision.Unresolvable("Sequence complete")` even though the revised plan has valid agents. The first plan execution works correctly; the replanned execution returns `Failed` immediately without dispatching any agents.

## Context
`SequentialRouting` uses an `AtomicInteger index` field that increments on each `route()` call. When an `ExecutionModel` carrying a `SequentialRouting` instance is used by one `OrchestratedDriver`, the index advances to `N` (number of agents). When that same model is reused with a new driver (e.g., after HTN re-planning produces a revised plan), the index is already past the new candidate list size — `route()` immediately returns `Unresolvable`.

## What was tried (didn't work)
- Checked termination conditions — correct
- Verified `ResultCollector` listener — correctly collecting results
- Inspected `ReplanContext` construction — correct mapping from collector to context
- Traced through `HtnExecutor.executeWithReplan()` — decomposition and model creation looked correct

The re-planned execution's `RoutingDecision` was never inspected because the driver's `executeIteration` returned `Failed` from the `onRoutingFailure` handler, not from termination — a different failure path than expected.

## Root cause
`SequentialRouting` is a stateful object. The `AtomicInteger index` field accumulates across driver lifetimes when the routing instance is shared via the `ExecutionModel`. After the first execution with N agents, `index == N`. The second execution calls `route()` with `index.getAndIncrement()` → returns `N`, which is `>= candidates.size()` for any plan — immediately `Unresolvable`.

## Fix
Create a fresh `SequentialRouting` instance per driver execution:

```java
private ExecutionModel<T> buildLocalModel(ExecutionModel<T> base, ...) {
    return new ExecutionModel<>(
        new SequentialRouting<>(),   // fresh instance, not base.routing()
        base.decomposition(), ...);
}
```

## Why this is non-obvious
`SequentialRouting` looks immutable — it's a small class with no setters. The statefulness is hidden inside `AtomicInteger`, which is a concurrency primitive that doesn't signal "this object mutates on read." The first execution always succeeds, so tests that don't exercise reuse never catch this. The failure manifests as a routing decision (`Unresolvable`), not a driver error — the stack trace points to the wrong layer.

### Why this fix
The alternative — resetting the index on the existing routing instance — would require adding a `reset()` method to `RoutingStrategy`, polluting the interface for one stateful implementation. Creating a fresh instance is zero-cost and makes the contract obvious: routing state is per-execution, not per-model.

### Alternatives considered
- **Add `reset()` to `RoutingStrategy` interface** — rejected; interface pollution for one implementation
- **Make `SequentialRouting` derive index from `TerminationContext.iterationCount`** — structurally correct but requires threading context into routing, which the current API doesn't support
- **Clone the model before each driver run** — wasteful; only the routing needs refreshing
