### Symptom
`UnsatisfiedResolutionException: Unsatisfied dependency for type jakarta.persistence.EntityManager` at Quarkus augmentation time. The error does not name the offending bean.

### Context
Consumer app uses `casehub-eidos-memory` which provides `@Alternative @Priority(1)` in-memory stores. Eidos adds a new `@IfBuildProperty` JPA store (e.g. `JpaDispositionSignalStore` from eidos#107). The JPA store requires `EntityManager` which the consumer doesn't provide (using H2 in-memory, not full JPA).

### What was tried (didn't work)
- Reading the error message for the bean name — it only says `EntityManager`, not which bean needs it
- Assuming existing `quarkus.arc.exclude-types` list was complete

### Root cause
`@IfBuildProperty` JPA stores are CDI-discovered at augmentation time regardless of whether the consumer has the matching build property set. Quarkus validates all injection points before checking build-time conditions. The consumer must explicitly exclude the bean via `quarkus.arc.exclude-types`.

### Fix
Add the new JPA store's fully qualified class name to `quarkus.arc.exclude-types` in the consumer's `application.properties`:

```properties
quarkus.arc.exclude-types=...,io.casehub.eidos.runtime.health.jpa.JpaDispositionSignalStore
```

### Why this is non-obvious
The error points at `EntityManager` (a JPA infrastructure type), not at the eidos bean that needs it. A developer unfamiliar with eidos internals would search their own code for EntityManager injection points. The actual cause is a transitive dependency introducing a new bean the consumer never asked for.
