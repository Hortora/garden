### Symptom
After renaming a Maven module (directory, artifactId, AND Java package), Quarkus `@QuarkusTest` fails at augmentation with `AmbiguousResolutionException`. The error lists the SAME bean class under BOTH the old and new package names:

```
AmbiguousResolutionException: Ambiguous dependencies for type LoopControl
  - CLASS bean [...io.casehub.blackboard.control.PlanningStrategyLoopControl...]
  - CLASS bean [...io.casehub.engine.planning.control.PlanningStrategyLoopControl...]
```

### Context
Multi-module Maven project. Module renamed from `blackboard` to `planning`, artifactId from `casehub-engine-blackboard` to `casehub-engine-planning`, package from `io.casehub.blackboard` to `io.casehub.engine.planning`. Two artifacts are present because stale build outputs survive the rename.

### What was tried (didn't work)
- `mvn clean install` on the renamed module — only cleans the NEW target/ directory
- Deleting the old artifact from `.m2` — misses the stale target/ classes

### Root cause
Two independent caches hold the old classes:
1. `target/classes/` contains compiled `.class` files under the OLD package path (Maven's incremental compiler doesn't detect that the source directory moved)
2. The local `.m2` repo contains the OLD artifact JAR (installed under the old artifactId)

Quarkus ARC builds its Jandex index from ALL JARs and class directories on the classpath. Both old and new classes are discovered, both implement the same interface, and CDI cannot resolve the ambiguity.

### Fix
Purge BOTH caches after a module rename:

```bash
# 1. Delete old artifact from local .m2
rm -rf ~/.m2/repository/io/casehub/casehub-engine-blackboard

# 2. Clean the renamed module's target directory
rm -rf planning/target/

# 3. Rebuild from clean
mvn install -DskipTests -pl planning
```

For worktree-specific `.m2` repos (`.mvn/maven.config` with `-Dmaven.repo.local=...`), purge from THAT repo, not the global `~/.m2`.

### Why this is non-obvious
The symptom (CDI ambiguity) points to a bean configuration problem, not a build hygiene problem. The error message shows two classes that look like duplicates — but they're in different packages, so a developer's first instinct is to check for a missing `@Alternative` or `@DefaultBean`, not to investigate stale build artifacts.
