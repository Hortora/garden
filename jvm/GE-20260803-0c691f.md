### Symptom

Implementing `jakarta.enterprise.inject.Instance<T>` directly in a unit test
stub class produces compilation errors:

```
select(java.lang.annotation.Annotation...) in StubInstance does not override
or implement a method from a supertype
```

The errors appear for `select()`, `isUnsatisfied()`, `isAmbiguous()`,
`isResolvable()`, `get()`, `destroy()`, `getHandle()`, `handles()`, and
`iterator()` — even though the method signatures look correct.

### Context

Unit tests for CDI decorators that use `Instance<T>` for optional
dependency injection (e.g. `Instance<EmbeddingModel>` where the model
may or may not be available). The tests run outside the CDI container
and need to provide stub `Instance` objects.

### What was tried (didn't work)

1. **Direct implementation** of `Instance<T>` with `@Override` on all
   methods — fails because `Instance` methods changed between CDI 4.0
   and 4.1 (some became default methods, some moved to sub-interfaces).
   The exact method signatures depend on the CDI API version on the
   classpath.

### Root cause

The `jakarta.enterprise.inject.Instance` interface evolves across CDI
specification versions. Methods that were abstract in CDI 4.0 became
default methods in 4.1, or their parameter types changed. A direct
implementation compiled against one version breaks when the classpath
provides another.

### Fix

Use `java.lang.reflect.Proxy` with method-name dispatch. Only handle
the methods you actually call — the Proxy handles everything else
by returning null:

```java
@SuppressWarnings("unchecked")
static <T> Instance<T> emptyInstance() {
    return (Instance<T>) java.lang.reflect.Proxy.newProxyInstance(
        Instance.class.getClassLoader(),
        new Class[]{Instance.class},
        (proxy, method, args) -> switch (method.getName()) {
            case "isResolvable" -> false;
            case "isUnsatisfied" -> true;
            case "isAmbiguous" -> false;
            case "get" -> { throw new IllegalStateException("No instance"); }
            case "iterator" -> java.util.Collections.emptyIterator();
            case "stream" -> java.util.stream.Stream.empty();
            case "hashCode" -> System.identityHashCode(proxy);
            case "equals" -> proxy == args[0];
            default -> null;
        });
}

@SuppressWarnings("unchecked")
static <T> Instance<T> presentInstance(T value) {
    return (Instance<T>) java.lang.reflect.Proxy.newProxyInstance(
        Instance.class.getClassLoader(),
        new Class[]{Instance.class},
        (proxy, method, args) -> switch (method.getName()) {
            case "isResolvable" -> true;
            case "isUnsatisfied" -> false;
            case "isAmbiguous" -> false;
            case "get" -> value;
            case "iterator" -> java.util.List.of(value).iterator();
            case "stream" -> java.util.stream.Stream.of(value);
            case "hashCode" -> System.identityHashCode(proxy);
            case "equals" -> proxy == args[0];
            default -> null;
        });
}
```

### Why this is non-obvious

The natural approach — `class StubInstance implements Instance<T>` — is
what most developers would try first. The compilation errors are
confusing because the method signatures *look* correct. The Proxy
approach avoids all version-specific method signature issues by
dispatching on method name rather than matching exact signatures.

### Why this fix

A Proxy is CDI-version-independent. Direct implementation requires
matching exact method signatures that change between CDI spec versions
— a maintenance burden that grows with each upgrade. The Proxy handles
any future API changes automatically as long as method names are stable
(which they are — it's the signatures that drift).

### Alternatives considered

- **Mockito** — not available as a test dependency in all modules; adds weight
- **Quarkus Arc test utilities** — only work inside `@QuarkusTest`, not plain unit tests
- **Wrapping in a custom interface** — changes production code to accommodate test needs
