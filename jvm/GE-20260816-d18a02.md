### Symptom
Adding a domain's GraphQL module to a composed application (e.g. scaffold) causes
CDI unsatisfied dependency errors for `EntityManager` or persistence store beans
that the GraphQL resolvers don't even use.

### Context
GraphQL resolver classes inject service SPIs (e.g. `ChannelReader`, `ConsumerMessaging`).
If the graphql module's pom.xml depends on the **runtime** module (which contains JPA
store implementations), those JPA beans are auto-discovered via Jandex and CDI tries
to satisfy their `EntityManager` injection — even though the resolvers never reference them.

### Root cause
Jandex indexes in runtime modules expose all CDI beans to any consuming application.
When the graphql module transitively brings in the runtime, the consuming app's CDI
context must satisfy every bean in the runtime — including JPA stores that need specific
persistence configurations.

### Fix
Make graphql modules depend on the **api** module only:

```xml
<!-- Good: api-only dependency -->
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-qhorus-api</artifactId>
</dependency>

<!-- Bad: brings in JPA stores via Jandex -->
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-qhorus</artifactId>
</dependency>
```

The consuming application (scaffold) separately declares which persistence backend
to wire. The graphql module only needs the SPI interfaces.

### Why this is non-obvious
The pattern of depending on the runtime module "for convenience" is common — it
ensures the graphql module can be tested standalone with the full runtime. The
problem only surfaces when the module is composed into a different application
with a different persistence topology. The Jandex auto-discovery is invisible
until CDI validation fails.

### Caveats
- Requires that service interfaces are in the api module, not the runtime
- If the graphql module uses internal runtime classes (e.g. `CaseInstance`),
  those must be extracted to the api module first
