### Symptom

`DependencyResolutionException` when adding `casehub-eidos-runtime` to a Maven POM:

```
Could not find artifact io.casehub:casehub-eidos-runtime:jar:0.2-SNAPSHOT
```

### Context

The eidos repository has a standard multi-module layout with directories named by role (`api/`, `runtime/`, `persistence-memory/`, etc.). Most CaseHub modules follow the convention where the directory name maps to the artifact suffix: `persistence-memory/` → `casehub-eidos-memory`.

### Root cause

The eidos runtime module breaks the convention. The directory is `runtime/` but the Maven artifact ID in `runtime/pom.xml` is `casehub-eidos` — not `casehub-eidos-runtime`. This is the main runtime artifact, not a sub-module.

| Directory | Artifact ID | Follows convention? |
|-----------|------------|-------------------|
| `api/` | `casehub-eidos-api` | Yes |
| `runtime/` | `casehub-eidos` | **No** |
| `persistence-memory/` | `casehub-eidos-memory` | Yes |
| `graph/` | `casehub-eidos-graph` | Yes |

### Fix

Use `casehub-eidos` as the artifact ID, not `casehub-eidos-runtime`:

```xml
<dependency>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-eidos</artifactId>
    <version>${casehub.version}</version>
</dependency>
```

### Why this is non-obvious

Every other CaseHub module uses the `<repo>-<directory>` naming convention. Inferring the artifact ID from the directory name is a reliable heuristic everywhere except here. The error is compounded by Maven caching `.lastUpdated` files from a failed remote lookup — even after installing eidos locally, the cached failure prevents resolution until the cache is manually cleared (`rm -rf ~/.m2/repository/io/casehub/casehub-eidos-runtime/`).

### Why this fix

The alternative — renaming the artifact to `casehub-eidos-runtime` — would break every existing consumer. The naming is intentional: `casehub-eidos` is the primary runtime artifact, following the same pattern as `casehub-engine` (which lives in `runtime/` but is artifact `casehub-engine`).
