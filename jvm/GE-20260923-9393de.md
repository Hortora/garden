### Symptom
After extracting entity types to base POJOs (`ActorTrustScore extends ActorTrustScoreBase`) and changing SPI interface return types to use the base type, existing implementations fail to compile: `findByActorId(String) in NoOpRepo cannot implement findByActorId(String) in SPI — return type Optional<ActorTrustScore> is not compatible with Optional<ActorTrustScoreBase>`.

### Context
Extracting JPA entity types from a runtime module to api-level base POJOs for dual-framework (Quarkus + Spring) deployment. SPI interfaces move to the api module and return base types. Implementations in runtime/JPA modules return entity subtypes.

### What didn't work
- Assuming covariant return types would apply through generics — Java does support covariant return types (`Entity` for `Base`), but NOT through generic type parameters (`Optional<Entity>` for `Optional<Base>`)
- Changing only the SPI interface return types without updating implementations

### Root cause
Java generics are invariant: `Optional<ActorTrustScore>` is NOT a subtype of `Optional<ActorTrustScoreBase>`, even though `ActorTrustScore extends ActorTrustScoreBase`. This is fundamental to Java's type system — generics use type erasure, and the JVM sees both as `Optional<Object>` at runtime. The compiler enforces invariance at compile time to prevent heap pollution.

Covariant return types only work for the raw return type, not for type parameters within generic wrappers.

### Fix
Change ALL implementation method signatures to use the base type in their generic wrappers. The implementation body can still construct and return entity instances — they're upcast automatically:

```java
// SPI interface (in api module)
Optional<ActorTrustScoreBase> findByActorId(String actorId);
List<ActorTrustScoreBase> findAll();

// Implementation (in runtime module) — MUST match generic parameter
@Override
public Optional<ActorTrustScoreBase> findByActorId(String actorId) {
    // Can still return an ActorTrustScore (entity) — it IS-A ActorTrustScoreBase
    ActorTrustScore entity = em.find(ActorTrustScore.class, actorId);
    return Optional.ofNullable(entity); // entity auto-upcast to ActorTrustScoreBase
}
```

When extracting entity types to base POJOs, plan for changing return types in EVERY implementation (JPA, in-memory, NoOp) — not just the SPI interface.

### Why this is non-obvious
Developers familiar with Java inheritance expect `Optional<SubType>` to be assignable to `Optional<SuperType>` — it works that way in Kotlin (`List<out T>`), Scala (`List[+T]`), and C# (`IEnumerable<out T>`). Java's invariant generics are a well-known language limitation, but the specific impact on SPI extraction (where you're extracting base types and expect implementations to "just work") catches developers mid-refactoring when the compiler rejects what looks like a valid override.
