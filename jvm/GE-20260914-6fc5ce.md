### Symptom

A `LinkedHashMap<String, String>` that counts how many decorator-wrapped objects contribute non-null values always shows exactly 1 entry, regardless of how many distinct delegates exist. The wrapped objects contribute correctly when iterated with a `StringBuilder` (no map), but the map-based count is always wrong.

### Context

A list of `PromptSection` objects is wrapped in a `DirectivePromptSection` decorator. Two code paths iterate the list:

1. **Prompt builder** — appends each section's output to a `StringBuilder`. Works correctly — all contributing sections appear in the output.
2. **Metrics counter** — stores each section's output in a `LinkedHashMap<String, String>` keyed by `section.getClass().getSimpleName()`. Always reports 1 section regardless of actual count.

The bug is invisible in the functional output (path 1). Only the measurement path (path 2) is broken, producing misleading metrics that led an entire investigation session to conclude "only 1 of 7 sections contributes" when 2–6 were actually contributing.

### What was tried (didn't work)

The metrics showed "1 section" on every turn for 4 turns. The investigation initially focused on why prompt sections were returning null — examining orchestrator state, tick ordering, and signal recording. All of these were red herrings because the sections WERE contributing; the measurement was wrong.

### Root cause

`getClass()` returns the runtime class of the object. For decorator-wrapped objects, the runtime class is the decorator — not the delegate. When all objects in a list are wrapped in the same decorator class, `getClass().getSimpleName()` returns the same string for every element. A `LinkedHashMap` keyed by this string silently overwrites previous entries, collapsing N distinct contributions to 1.

```java
// All sections wrapped in DirectivePromptSection
for (var section : cognition.promptSections()) {
    var text = section.contribute(ctx);
    if (text != null && !text.isBlank()) {
        // BUG: always "DirectivePromptSection" for every section
        sectionContent.put(section.getClass().getSimpleName(), text);
    }
}
// sectionContent.size() is always 0 or 1
```

### Fix

Expose the delegate's identity through the wrapper:

```java
class DirectivePromptSection implements PromptSection {
    private final PromptSection delegate;
    private final String delegateName;

    String delegateName() { return delegateName; }

    static PromptSection wrap(PromptSection section) {
        return new DirectivePromptSection(section,
            directiveFor(section.getClass().getSimpleName()),
            section.getClass().getSimpleName());
    }
}
```

Then use the delegate name as the map key:

```java
var sectionName = section instanceof DirectivePromptSection dps
        ? dps.delegateName() : section.getClass().getSimpleName();
sectionContent.put(sectionName, text);
```

### Alternatives considered

- **`instanceof` pattern matching to unwrap** — works but requires callers to know the specific wrapper type, coupling the measurement code to the decorator implementation
- **Adding `name()` to the PromptSection interface** — breaks the `@FunctionalInterface` contract, affecting all implementations

### Why this is non-obvious

The decorator pattern is designed to be transparent — callers shouldn't need to know they're talking to a wrapper. But `getClass()` breaks that transparency, and the failure mode is silent data loss in a map, not an error. The functional code path (StringBuilder) works perfectly, masking the bug in the measurement path. A developer debugging "only 1 section contributes" would naturally investigate why sections return null — not why the counting map has a key collision.
