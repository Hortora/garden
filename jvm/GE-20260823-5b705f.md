# TopicRegistry silently accepts slash-delimited topics — wildcard matching breaks

## Symptom

Push topics using `/` as separator (e.g. `incidents/{caseId}`, `work-items/summary`) are accepted by `EventBroadcaster.broadcast()` without error, but `topicSource` wildcard subscriptions (e.g. `incidents:*`) never match them.

## Context

`EventBroadcaster.broadcast()` validates that the topic doesn't contain `*` (wildcards) but performs no other topic format validation. Any non-wildcard string is accepted and stored in the `TopicRegistry` trie.

## Root cause

`TopicRegistry` hardcodes `:` as its segment delimiter in `split(":", -1)` across all methods — trie insertion, wildcard matching (`*`, `**`), validation, and connection lookup. A slash-delimited topic like `incidents/summary` is treated as a single opaque trie node. The wildcard `incidents:*` expands to "match any single segment after `incidents`" — but `incidents/summary` has no `incidents` segment (it's one segment: `incidents/summary`).

`isValidTopicOrPattern()` also splits on `:` — a subscription pattern like `incidents/*` is a single segment containing `*` but not equal to `*`, so it's invalid.

## What was tried (didn't work)

Using `/` as topic separator in C4 (incident/work-item) push broadcast calls while C1-C3 used `:`. The slash topics worked for direct (non-wildcard) subscriptions because `connections()` does exact trie lookups. The bug only manifests when wildcard subscriptions are needed.

## Fix

Use `:` as the topic separator for all broadcast calls. This is not a convention choice — it's enforced by TopicRegistry's trie infrastructure.

```java
// Wrong — silently degrades wildcard matching
broadcaster.broadcast("incidents/" + caseId, payload);

// Correct — trie segments work, wildcards match
broadcaster.broadcast("incident:" + caseId, payload);
```

## Why this is non-obvious

The API accepts both separators without complaint. The bug is silent — slash topics still deliver to directly-subscribed connections. It only breaks when a new subscriber uses wildcard patterns, which may happen much later (in our case, when composing both conventions on one page in C5b).
