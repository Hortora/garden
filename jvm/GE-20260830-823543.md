## Symptom

Embedding TSJ (ts2jvm) as a Maven dependency in another project and calling `JvmBytecodeCompiler.compile()` or `TsjEvaluator.evaluate()` fails with:

> TypeScript syntax bridge failed: Unable to resolve the `typescript` package.

or:

> Could not locate TypeScript syntax bridge script `emit-backend-tokens.cjs`.

The same code works perfectly when run from within the TSJ project directory.

## Context

TSJ compiles TypeScript to JVM bytecode. The compiler frontend uses a Node.js bridge script (`compiler/frontend/ts-bridge/emit-backend-tokens.cjs`) to parse TypeScript source into tokens that the JVM backend then compiles to bytecode. This script is invoked as a Node.js subprocess during compilation.

When TSJ is consumed as a Maven dependency (`dev.tsj:compiler-backend-jvm:0.1.1-SNAPSHOT`), the bridge script is NOT included in the JAR. The compiler looks for it relative to the project directory, which doesn't exist in the consuming project.

## What was tried (didn't work)

1. Installing the `typescript` npm package in the consuming project's workspace — fixes the "Unable to resolve typescript" error but not the missing bridge script
2. Adding TSJ JARs to the classpath — the bridge script isn't in any JAR
3. Setting working directory to the TSJ project — not practical for embedding

## Root cause

TSJ's Maven build does not package `emit-backend-tokens.cjs` as a classpath resource in `compiler-frontend.jar`. The script lives only as a source file at `compiler/frontend/ts-bridge/emit-backend-tokens.cjs`. The compiler resolves it via filesystem path relative to the project root — a pattern that works for CLI usage but breaks when TSJ is consumed as a library dependency.

TSJ is NOT fully "JVM-native" — it requires Node.js for the frontend parsing step. The JVM bytecode compilation and execution are JVM-native, but the TypeScript-to-token conversion delegates to Node.js.

## Fix

None available in TSJ 0.1.1-SNAPSHOT. The fix requires changes to TSJ itself:

1. Bundle `emit-backend-tokens.cjs` as a classpath resource in `compiler-frontend.jar`
2. At runtime, extract the script from the classpath to a temp directory (same pattern as extracting runner scripts — `Class.getResourceAsStream()` → `Files.copy()`)
3. Point the compiler at the extracted path

PR submitted: https://github.com/vgargatgit/tsj/pull/1 (adds `TsjEvaluator` embeddable API but does not fix the bridge script packaging).

**Workaround:** Use a Node.js subprocess executor (`npx tsx`) instead of TSJ for TypeScript evaluation. This achieves the same result (TS → JSON) without the JVM bytecode intermediate step.

## Why this is non-obvious

TSJ presents itself as a "TypeScript to JVM compiler" which implies JVM-native execution. The compiler and runner APIs exist and work correctly from the TSJ project. All 5 `TsjEvaluatorTest` tests pass when run from within TSJ. The failure only surfaces when consuming TSJ as an external Maven dependency — the symptom points to the `typescript` npm package, not to a missing bridge script. The real issue is a packaging gap, not a missing npm dependency.
