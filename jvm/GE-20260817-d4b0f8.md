## Symptom

`package io.casehub.platform.api.yaml does not exist` and similar `cannot find symbol` errors for platform types, despite the platform being freshly installed via `mvn install -DskipTests` in the host Maven repository.

## Context

Casehub engine slots (parallel work isolation) use `.mvn/maven.config` to set a slot-specific local Maven repository:

```
-Dmaven.repo.local=/Users/mdproctor/claude/casehub/slots/117/.m2
--settings=.mvn/slot-settings.xml
```

The slot settings include a `host-m2` repository profile that adds the host's `~/.m2/repository` as a file:// repository for fallback resolution. However, Maven SNAPSHOT resolution does not always check fallback repositories when a (stale) SNAPSHOT already exists in the local repo.

## What was tried (didn't work)

- Installing platform to the host `~/.m2/repository` — the slot's `maven.repo.local` overrides the default local repo, so the slot doesn't see it reliably
- Running the build without `-s` flag — the `.mvn/maven.config` applies automatically regardless

## Root cause

Maven resolves dependencies from the local repository first. When `maven.repo.local` is overridden to a slot-specific path, the host's `~/.m2/repository` becomes a remote-style repository (via the `host-m2` profile). Maven's SNAPSHOT metadata resolution for file:// repositories doesn't always re-check when a local copy exists — even if the local copy is older.

## Fix

Install the platform directly into the slot's Maven repository:

```bash
mvn install -DskipTests -Dmaven.repo.local=/path/to/slots/N/.m2 -f /path/to/platform/pom.xml
```

This ensures the slot's local repo has the latest SNAPSHOT JARs. The `-Dmaven.repo.local` flag must match the slot engine's `.mvn/maven.config` setting.

## Why this is non-obvious

The `.mvn/maven.config` is a hidden convention file that applies automatically — you don't pass it on the command line. The slot settings include a host-m2 fallback that appears to handle cross-repo resolution, but SNAPSHOT metadata caching means the fallback isn't always checked. The symptom (`package does not exist`) points at a missing dependency, not at a repo isolation issue.
