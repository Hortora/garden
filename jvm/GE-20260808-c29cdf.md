## ConcurrentHashMap stream().findFirst() is non-deterministic — test stubs with duplicate business keys return arbitrary results

**Symptom:** CDI-free test passes intermittently. A stub store returns the wrong record from `findByX()` — sometimes the initial record, sometimes the updated one.

**Context:** Test stubs backed by `ConcurrentHashMap<UUID, Entity>` where each `save()` generates a new UUID key. Business queries (`findByChannelAndBackend()`) use `.stream().filter(...).findFirst()`. When two entries match the filter (e.g., cursor saved at position 0, then saved again at position 100 with a different UUID), `findFirst()` returns whichever ConcurrentHashMap happens to iterate first — non-deterministic.

### What was tried (didn't work)
- Assumed `findFirst()` returns insertion order — ConcurrentHashMap has no insertion ordering
- Debug logging showed both entries present — the query was correct, the data model was wrong

### Root cause
`ConcurrentHashMap` iteration order is determined by hash bucket placement, not insertion order. `findFirst()` on a stream from `values()` returns the first element the bucket walk encounters. With synthetic UUID keys, two entries for the same business key (channel+backend) coexist because `save()` creates a new UUID each time instead of replacing by business key.

### Fix
Ensure test stubs enforce business-key uniqueness at the data level:
```java
// Bad — generates new UUID on every save, duplicates accumulate
public Entity save(Entity e) {
    UUID id = e.id() != null ? e.id() : UUID.randomUUID();
    store.put(id, e.toBuilder().id(id).build());
    return store.get(id);
}

// Good — key by business identity, not synthetic PK
public Entity save(Entity e) {
    String key = e.channelId() + ":" + e.backendId();
    store.put(key, e);
    return e;
}
```

Alternatively, use `computeIfAbsent`/`replace` patterns that enforce single-entry-per-business-key semantics.

### Why this is non-obvious
`findFirst()` looks deterministic because it always returns *a* result. The non-determinism is silent — the test passes with the "wrong" value often enough that the failure appears intermittent rather than systematic. A developer familiar with ConcurrentHashMap's lack of ordering might still miss this because the stub's `save()` method quietly creates duplicates rather than updating in place.
