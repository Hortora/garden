### What is undocumented
jmarkdoc's per-type markdown output includes structured headers for `**Kind:**` (interface/class/enum) and `**Package:**`, but does NOT include a structured section showing what the type implements or extends.

Type hierarchy information only appears if the original javadoc comment happens to mention it in prose (e.g., "implements `ActionRiskClassifier`" in a description paragraph). There is no generated "## Implements" or "## Extends" section.

### Why it matters
Cross-repo tooling that needs to build an implementation matrix (e.g., "which classes implement `AgentRoutingStrategy` across all repos?") cannot parse this from jmarkdoc output alone. The type hierarchy data must come from a different source — either source code grep or AST analysis.

### How it was discovered
Discovered while building a cross-repo SPI overlay script for CaseHub. The spec assumed doclet output would include structured type hierarchy data. Inspecting actual jmarkdoc output for engine-api revealed the gap.

### Workaround
For cross-repo implementation correlation, grep source files for `implements InterfaceName` rather than parsing doclet output. This catches direct implementations but misses indirect inheritance through abstract base classes.

```bash
# Grep source for direct implementations
grep -r "implements AgentRoutingStrategy" --include="*.java" /path/to/repos/
```
