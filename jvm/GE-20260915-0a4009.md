### Symptom
A generated `@Decorator` for a capability-based SPI (e.g. `ChatPlatform`) intercepts the wrong method. The decorator intercepts `messaging()` (which returns a `Messaging` capability object) instead of `messaging().send()` (the actual operation). Simulation returns a fake `Messaging` object instead of simulating individual sends.

### Context
When building a simulation framework that generates CDI `@Decorator` classes per `@SimulationEligible` SPI interface, the decorator intercepts each method declared on the interface. For flat interfaces where each method is a complete operation (`query(input) → result`), this works perfectly. For capability-based interfaces where methods return intermediate objects (`messaging() → Messaging`), the interception point is wrong.

### Root cause
CDI `@Decorator` operates at the interface method level. It wraps individual method calls on the decorated bean. When an interface returns a capability object, the decorator can only intercept the factory method — not the methods on the returned object. The returned capability object is outside the decorator's scope.

### Fix
Design SPIs as flat interfaces where each method is a complete request-response operation:

```java
// Good — flat, each method is a complete operation
@SimulationEligible(name = "bank-feed")
public interface BankFeedPlatform {
    List<Transaction> listTransactions(String accountId, DateRange range);
    Balance getBalance(String accountId);
    PaymentResult postPayment(PaymentRequest request);
}

// Bad — capability-based, decorator intercepts at wrong level
public interface ChatPlatform {
    Messaging messaging();     // decorator intercepts HERE
    Channels channels();       // not at messaging().send()
}
```

If an existing SPI is capability-based and cannot be flattened, provide a simulated capability object that delegates to the `SimulationRuntime` internally — but this requires hand-written code per capability, defeating the annotation processor's purpose.

### Why this is non-obvious
The CDI `@Decorator` pattern appears universal — "decorate any interface." The constraint that it only intercepts direct method calls (not methods on returned objects) is implicit in the CDI spec but not surfaced as a design constraint for SPI authors. A developer designing a new SPI would not naturally consider "will this interface work with a generated decorator?" unless they know about this limitation.

This insight was surfaced by a banking platform team evaluating the simulation framework for their `BankFeedPlatform` SPI — they noted it "strongly reinforces flat interface design for reasons we didn't even know yet."

### Caveats
- This applies to any CDI `@Decorator` pattern, not just simulation — callback decorators have the same constraint
- Flat interfaces may feel less OO than capability-based ones, but they map cleanly to REST endpoints, MCP tools, and generated decorators
- For SPIs that genuinely need capability objects (stateful sessions, builders), Path B (backend integration) is the correct simulation approach — register with the routing layer instead of using a decorator
