### Symptom
Issue filed as "needs CommitmentLifecycleEvent CDI event" — no observable event when an agent reviewer is dispatched via qhorus COMMAND message. The notification pipeline can observe human review assignments (WorkItemLifecycleEvent) but not agent dispatch.

### Context
Building a notification bridge for agent review dispatch in devtown. Human review assignments fire WorkItemLifecycleEvent(CREATED) which the existing ReviewAssignmentNotificationBridge observes. Agent dispatch goes through QhorusPrReviewService sending a COMMAND via MessageService.dispatch() — a different path.

### What was tried (didn't work)
The issue proposed three options: (1) Add CommitmentLifecycleEvent CDI event in Qhorus, (2) Hook in QhorusPrReviewService.startReview(), (3) Observe MessageObserverDispatcher output. All three assumed the existing infrastructure lacked the right event type.

### Root cause
MessageObserver already fires for all 9 speech-act types including COMMAND (line 399 of MessageService.dispatch()). The MessageReceivedEvent record was missing two fields that Message carries: `target` (who the COMMAND is directed at) and `actorType`. The fromMessage() factory method had access to both fields but didn't thread them through.

### Fix
Added `target` (String) and `actorType` (ActorType) to the MessageReceivedEvent record. Updated fromMessage() to extract both from Message. Devtown implements MessageObserver filtering on messageType == COMMAND — no new CDI event type needed.

### Why this is non-obvious
The issue was filed by the project author with the wrong diagnosis. The mental model was "commitment creation has no CDI event" → build one. The actual gap was two missing fields on an existing event. Tracing the message dispatch path to line 399 of MessageService and reading MessageReceivedEvent.fromMessage() was required to discover this — the SPI javadoc says "all 9 speech-act types fire" but doesn't list which fields are threaded through.

### Why this fix
Adding fields to an existing event record is a 2-line API change with zero new infrastructure. A CommitmentLifecycleEvent would have required a new CDI event type, a new emitter in CommitmentService, and a new observer pattern — solving the wrong problem at 10x the cost.

### Alternatives considered
- CommitmentLifecycleEvent: rejected — wrong abstraction level (commitment is created inside dispatch(), not a separate lifecycle event)
- Hook in QhorusPrReviewService: rejected — couples the notification to a specific devtown service instead of using the generic observer SPI
