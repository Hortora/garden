## Symptom

Adding `casehub-work` (runtime module) as a dependency to query WorkItems causes 80+ CDI deployment errors in the consumer:

```
Found 83 deployment problems:
[1] Unsatisfied dependency for type jakarta.persistence.EntityManager and qualifiers [@Default]
[2] Ambiguous dependencies for type io.casehub.platform.api.identity.CurrentPrincipal
...
```

The consumer only needs the `WorkItemStore` SPI interface and `WorkItemQuery` — not the JPA entities, services, REST endpoints, or timer jobs.

## Root Cause

`WorkItemStore` (the query SPI interface), `WorkItem` (a JPA `@Entity`), and `WorkItemQuery` (a value object) all live in the `casehub-work` runtime module alongside 60+ JPA-backed repositories, services, REST resources, and Quartz timer jobs. The runtime module IS a Quarkus extension (with a deployment processor) — its beans are registered via `AdditionalBeanBuildItem.setUnremovable()`, making `quarkus.arc.exclude-types` ineffective for extension-registered beans.

Even `casehub-work-persistence-memory` (the in-memory test store) transitively pulls the full runtime module.

## Fix

None currently available. Filed casehubio/work#337 to extract `WorkItemStore`, `WorkItem` (as a POJO), and `WorkItemQuery` into `casehub-work-api`. Until then, use a REST client tier to query work items from an external service instead of embedding the module.

## Why this is non-obvious

The `WorkItemStore` interface looks like a clean SPI — it has multiple implementations (JPA, MongoDB, InMemory) following the standard CDI priority ladder. A developer would naturally try to depend on the module containing the SPI interface. The module structure doesn't signal that depending on the interface forces the entire persistence stack.
