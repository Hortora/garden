## Core extraction breaks downstream test constructors

### Symptom
After a shared library (e.g. casehub-platform) extracts CDI beans to constructor-injected POJOs, downstream repos fail to compile with:
```
constructor SubjectViewOrchestrator in class SubjectViewOrchestrator cannot be applied to given types;
  required: SubjectViewEvaluator, SubjectViewStore, ViewMembershipTracker, PreferenceProvider
  found: no arguments
```

### Context
When extracting framework-neutral cores from CDI-coupled modules, classes that were previously `@ApplicationScoped` with field `@Inject` become POJOs with constructor parameters. The class itself keeps its name and package — zero consumer breakage for CDI consumers (the framework wires the constructor). But test code that constructs these types directly with `new ClassName()` breaks.

### What was tried (didn't work)
Nothing — the error is clear once you see it. The non-obvious part is **anticipating** which downstream repos will break.

### Root cause
CDI field injection (`@Inject` on fields) allows `new ClassName()` — the no-arg constructor exists. Constructor injection removes the no-arg constructor. Any code that constructs the class directly (typically tests using reflective field injection) breaks.

### Fix
Update downstream test code to pass constructor arguments:
```java
// Before (CDI field injection — no-arg constructor exists):
var orchestrator = new SubjectViewOrchestrator();
inject(orchestrator, "evaluator", viewEvaluator);
inject(orchestrator, "viewStore", viewStore);

// After (constructor injection — no-arg constructor gone):
var orchestrator = new SubjectViewOrchestrator(viewEvaluator, viewStore, tracker, prefProvider);
```

The fix is mechanical per call site. The hard part is discovering all affected repos — `grep -r 'new SubjectViewOrchestrator'` across the entire workspace.

### Why this is non-obvious
The extraction preserves the class name and package, so it looks like a non-breaking change. CDI consumers ARE unaffected (the framework handles constructor wiring). Only direct constructors in tests break — and those are in other repos you may not be looking at.

### Alternatives considered
- Adding a deprecated no-arg constructor — violates the extraction goal (core POJOs should not have framework-friendly constructors that hide required dependencies)
- Running cross-repo builds before merging — correct approach but easy to skip when the primary repo's build passes
