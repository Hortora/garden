### Symptom
`ObjectMapper.readerForListOf(StepDefinition.class).readValue(arrayNode)` throws
or returns unexpected results when the array node was built using
`ObjectNode.putPOJO("dependsOn", List.of())`.

### Context
Building test data or dynamic JSON trees using Jackson's `ObjectNode` API.
A record type (`StepDefinition`) has a `List<String> dependsOn` field.
The array node is constructed programmatically, then later deserialized
back to the record type.

### What was tried (didn't work)
`putPOJO("dependsOn", List.of())` — appears to work: the node exists,
`toString()` looks correct. But when the parent array node is deserialized
via `readerForListOf()`, the POJO-wrapped list is not a proper `ArrayNode`
and deserialization fails silently.

### Root cause
`putPOJO()` wraps the Java object in a `POJONode`, not an `ArrayNode`.
Jackson's `ObjectReader` expects structural JSON nodes (`ArrayNode`,
`ObjectNode`, `TextNode`, etc.) during deserialization. A `POJONode`
containing a `List` is not interchangeable with an `ArrayNode` — it's a
serialization-time wrapper, not a deserialization-compatible tree node.

### Fix
Use `node.set("key", mapper.createArrayNode())` instead of
`node.putPOJO("key", List.of())`:

```java
// WRONG — creates POJONode, breaks deserialization
node.putPOJO("dependsOn", List.of());

// RIGHT — creates ArrayNode, deserializes correctly
node.set("dependsOn", mapper.createArrayNode());

// For non-empty lists:
var arr = mapper.createArrayNode();
arr.add("value1");
arr.add("value2");
node.set("dependsOn", arr);
```

### Why this is non-obvious
`putPOJO()` is the natural API choice when you have a Java object to embed
in a tree. The resulting JSON output looks identical — `toString()` and
serialization produce the same `"dependsOn": []`. The failure only surfaces
during deserialization, and the error message (if any) doesn't point back
to the node type mismatch.
