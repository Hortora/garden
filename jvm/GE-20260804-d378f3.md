### Symptom
`curl http://localhost:8080/your/endpoint` returns `404 Resource not found` even though
Quarkus logs show the app started successfully on port 8080 with the endpoint registered.

### Context
Quarkus `mvn quarkus:dev` spawns two Java processes on the same port:
- The Maven launcher process binds to `*:8080` (all interfaces, including IPv6)
- The actual Quarkus app binds to `localhost:8080` (IPv4 loopback only)

On macOS, `curl localhost:8080` resolves to `[::1]:8080` (IPv6) first, which hits the
Maven launcher — not the actual app. The launcher returns 404 for all application routes.

### What was tried (didn't work)
- Checking if the app started (it did — logs confirmed)
- Verifying endpoint paths and HTTP methods
- Adding Content-Type headers

### Root cause
`lsof -i :8080` reveals two listeners:
```
java  PID1  *:http-alt (LISTEN)        ← Maven launcher (wildcard, catches IPv6)
java  PID2  localhost:http-alt (LISTEN) ← Quarkus app (IPv4 only)
```
curl connects via IPv6 (`[::1]`) and reaches the wrong process.

### Fix
Force IPv4 in curl:
```bash
curl -4 http://127.0.0.1:8080/your/endpoint
```

### Why this is non-obvious
The app logs show a successful start with the correct port. `lsof` shows two processes
on the same port but this is easy to miss. The 404 response looks like a routing problem,
not a process-targeting problem. IPv6 preference is invisible in normal curl output —
only `-v` reveals it's connecting to `[::1]`.
