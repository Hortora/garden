### Symptom
Audit identified ~30 classes with `@ApplicationScoped` and zero injected dependencies as "unnecessary CDI." Removing the annotation compiles cleanly but silently breaks runtime SPI discovery.

### Context
In Quarkus projects using the desiredstate pattern, domain modules are "standalone Jandex libraries activating by classpath presence — no config required." CDI bean scanning via Jandex IS the discovery mechanism. `Instance<FaultPolicy>` in a producer class discovers all `FaultPolicy` implementations across JARs.

### Root cause
`@ApplicationScoped` serves two purposes: (1) dependency injection — wiring dependencies, and (2) SPI discovery — making the class visible to `Instance<T>` queries. An audit using "zero injected dependencies" as a proxy for "doesn't need CDI" conflates injection with discovery.

### Fix
Before removing `@ApplicationScoped` from any class, verify it isn't discovered via `Instance<T>`, `@All`, or CDI `select()`. Search for `Instance<InterfaceName>` across the codebase. If the interface is consumed that way, the annotation is required regardless of whether the class has injected fields.

### Why this is non-obvious
The mental model "CDI = dependency injection" misses that CDI is also the service discovery layer. A class with no `@Inject` fields looks like it doesn't need CDI, but it may be the target of `Instance<T>` queries in a completely different module.

### Alternatives considered
- Remove CDI and use ServiceLoader instead — viable but would require rearchitecting the module activation pattern
- Use `@Dependent` instead of `@ApplicationScoped` — doesn't help; the issue is discovery, not scope
