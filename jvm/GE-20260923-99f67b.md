## Symptom

Compilation fails with `duplicate unconditional pattern` when using switch
pattern matching on a sealed interface with generic type parameters:

```java
sealed interface InvocationResult<T> {
    record Success<T>(T value) implements InvocationResult<T> {}
    record ParseError<T>(String error) implements InvocationResult<T> {}
    record AgentError<T>(String reason) implements InvocationResult<T> {}
}

// This FAILS to compile:
switch (result) {
    case InvocationResult.Success<ReviewFindings> s -> { ... }
    case InvocationResult.ParseError<ReviewFindings> pe -> { ... }
    case InvocationResult.AgentError<ReviewFindings> ae -> { ... }
}
```

The compiler reports `duplicate unconditional pattern` on the second and
third cases because type erasure makes all three patterns identical at
the bytecode level.

## Context

Occurs when a sealed interface has a type parameter and you attempt to
use the parameterised form in switch pattern matching. The Java compiler
cannot distinguish `Success<ReviewFindings>` from `ParseError<ReviewFindings>`
after erasure — both erase to the raw sealed interface type.

## Root cause

Java's switch pattern matching operates on erased types. Generic type
parameters are not available at runtime for pattern discrimination.
The sealed interface permits clause ensures exhaustiveness at the raw
type level, but parameterised patterns cannot add compile-time type
narrowing within the switch.

## Fix

Use `if/else` with `instanceof` and wildcard type parameters instead:

```java
if (result instanceof InvocationResult.Success<?> s) {
    var value = (ReviewFindings) s.value();
    // handle success
} else if (result instanceof InvocationResult.ParseError<?> pe) {
    // handle parse error
} else if (result instanceof InvocationResult.AgentError<?> ae) {
    // handle agent error
}
```

The wildcard `<?>` avoids the erasure collision. Cast the value inside
the body where needed.

## Why this is non-obvious

The sealed interface switch pattern works perfectly for non-generic sealed
types — Java developers accustomed to exhaustive switch on sealed types
expect the same pattern to work with generics. The error message
`duplicate unconditional pattern` doesn't mention generics or erasure,
making the root cause non-obvious.
