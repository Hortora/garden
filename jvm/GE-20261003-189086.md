## Symptom

Building a fallback chain with `recoverWithMulti` in a loop causes ALL
entries to execute during chain construction, not lazily when recovery
triggers. Test assertion `callCount == 1` fails with `callCount == 2`
even though only the first entry should have been invoked.

## Context

When composing ordered fallback chains (e.g., model fallback: try opus,
fall back to sonnet), the natural pattern is:

```java
Multi<Event> chain = Multi.createFrom().failure(exhaustedException);
for (int i = entries.size() - 1; i >= 0; i--) {
    var entry = entries.get(i);
    final Multi<Event> fallback = chain;
    chain = attemptInvoke(entry, config)    // ← EXECUTES HERE
        .onFailure(RetryableException.class)
        .recoverWithMulti(fallback);
}
```

`attemptInvoke()` is called eagerly during the loop iteration — its
side effects (API calls, session creation) execute immediately for
every entry, not when recovery triggers.

## Root cause

`recoverWithMulti(Multi)` accepts a `Multi` instance, not a `Supplier`.
The `Multi` passed as the primary stream (before `.onFailure()`) is
constructed when the line executes — and if construction has side effects
(calling a backend, creating a session), those fire immediately.

The recovery path (the Multi passed to `recoverWithMulti`) IS lazy — it
only subscribes on failure. But the PRIMARY stream is evaluated when the
composition line runs.

## Fix

Wrap the primary stream in `Multi.createFrom().deferred()`:

```java
Multi<Event> chain = Multi.createFrom().failure(exhaustedException);
for (int i = entries.size() - 1; i >= 0; i--) {
    var entry = entries.get(i);
    final Multi<Event> fallback = chain;
    chain = Multi.createFrom().deferred(() -> attemptInvoke(entry, config))
        .onFailure(RetryableException.class)
        .recoverWithMulti(fallback);
}
```

`deferred()` delays the `attemptInvoke()` call until subscription —
each entry is only invoked when the previous entry fails and recovery
triggers.

### Why non-obvious

`recoverWithMulti` LOOKS like it makes everything lazy — the recovery
Multi is only subscribed on failure. But the distinction between
"subscribing to a Multi" and "constructing a Multi" is subtle. A
developer familiar with reactive patterns expects the whole composition
to be lazy, but Mutiny's API accepts a Multi instance (not a Supplier),
so construction side effects are eager.

### Why this fix

`deferred()` is the canonical Mutiny wrapper for lazy Multi construction.
The alternative — `Uni.createFrom().deferred().onItem().transformToMulti()` —
is verbose and harder to read. `Multi.createFrom().deferred(Supplier<Multi>)`
is a direct solution.

### Alternatives considered

- Restructuring as a recursive Mutiny composition — more complex, same outcome
- Pre-resolving all entries and only invoking the selected one — loses runtime retry capability
