## pages-data wsSource uses 'subscribe' wire protocol, incompatible with EventBroadcaster's topic-based 'event' protocol

### Symptom

`wsSource("/ws/push", dataSetId("mydata"))` connects to the push WebSocket but never receives events broadcast via `EventBroadcaster.broadcast("topic:key", payload)`. No error — the subscription appears to succeed but the DataSink never receives data.

### Context

The pages push infrastructure has two wire protocol modes:

1. **subscribe** (dataset-oriented): client sends `{op: "subscribe", dataset: "name"}`, server responds with `{dataset: "name", ...data}`. Used by `wsSource` via `sendSubscribe()` in `push-wire.ts`.

2. **listen** (topic-oriented): client sends `{op: "listen", topics: ["pattern:*"]}`, server responds with `{op: "event", topic: "matched:key", payload: {...}}`. Used by `EventBroadcaster.broadcast()` on the Java backend.

`processWireMessage()` in `push-source.ts` handles these differently: `op: "event"` messages are dispatched to `config.eventTarget` (a DOM EventTarget) but NOT forwarded to dataset subscriptions. Dataset messages use `msg.dataset` for routing.

### Root cause

The two wire protocol modes are architecturally separate — `subscribe` is for server-managed datasets (query results, paginated data), while `listen/event` is for push event streams (real-time notifications). `wsSource` is built for the subscribe path. `EventBroadcaster` broadcasts on the event path. They share the same WebSocket endpoint but use different message routing.

### Fix

Create a custom `topicSource` DataSource adapter that uses the `listen` wire protocol:

```typescript
import type { DataSource, DataSink } from "@casehubio/pages-data";

export function topicSource(topics: string[]): DataSource {
  let ws: WebSocket | null = null;
  let sink: DataSink | null = null;

  return {
    connect(s: DataSink): void {
      sink = s;
      const proto = location.protocol === "https:" ? "wss:" : "ws:";
      ws = new WebSocket(`${proto}//${location.host}/ws/push`);
      ws.onopen = () => {
        ws!.send(JSON.stringify({ op: "listen", id: "1", topics }));
      };
      ws.onmessage = (e) => {
        const msg = JSON.parse(e.data);
        if (msg.op === "event" && msg.payload && sink) {
          sink.apply({ type: "snapshot", columns: [], rows: [msg.payload] });
        }
      };
    },
    disconnect(): void { ws?.close(); ws = null; sink = null; },
  };
}
```

Use with `composite()` for REST initial + WS live: `composite(fetchSource("/api/data"), topicSource(["topic:*"]))`.

### Why this is non-obvious

The APIs appear compatible — both use the same WebSocket endpoint (`/ws/push`), both deal with real-time data, and `wsSource` accepts a URL that matches the push endpoint. The incompatibility is hidden in the wire protocol layer: `subscribe` vs `listen` are different operations that route through different code paths in `processWireMessage()`.
