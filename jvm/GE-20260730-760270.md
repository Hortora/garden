### Symptom
CI compilation fails with `reference to setValue is ambiguous` while local build passes.
Error: both `setValue(String, JsonNode)` and `setValue(String, Supplier<JsonNode>)` match.

### Context
A library (`jackson-jq` `Scope`) adds a new `Supplier<T>` overload to an existing method.
The caller passes the result of `ObjectMapper.valueToTree()`, which returns `<T extends JsonNode> T`.
An explicit `(JsonNode)` cast is present but does not disambiguate.

CI resolves the newer library version via SNAPSHOT metadata; local Maven cache retains the
old version (single overload, no ambiguity). The build divergence is silent — no version
mismatch warning.

### What was tried (didn't work)
- `(JsonNode)` cast on the `valueToTree()` result — compiler still sees the generic bound
  and cannot determine whether the expression targets `JsonNode` or `Supplier<JsonNode>`.

### Root cause
`ObjectMapper.valueToTree()` is declared `<T extends JsonNode> T`. The Java compiler treats
the return type as an inference variable, not a concrete `JsonNode`. When the target method
has overloads accepting both `JsonNode` and `Supplier<JsonNode>`, the compiler cannot resolve
the ambiguity — the cast constrains the bound but does not eliminate the inference variable
from consideration.

### Fix
Extract the generic result to a typed local variable before passing to the overloaded method:
```java
// Before — ambiguous
childScope.setValue("secret", (JsonNode) MAPPER.valueToTree(secretsMap));

// After — unambiguous
JsonNode secretsNode = MAPPER.valueToTree(secretsMap);
childScope.setValue("secret", secretsNode);
```
The assignment to `JsonNode secretsNode` resolves the generic at the assignment, so `setValue`
receives a concrete `JsonNode` reference with no inference variable.

### Why this is non-obvious
The `(JsonNode)` cast *looks* correct and would work for any non-generic method. The failure
is specific to generic return types (`<T extends JsonNode> T`) where the compiler preserves
the inference variable through the cast. Most developers never encounter this because most
overloaded methods don't have both a concrete type and a functional-interface type accepting
the same bound.

### Alternatives considered
- Calling `valueToTree()` with an explicit type witness: `MAPPER.<JsonNode>valueToTree(...)` —
  works but is less readable and unfamiliar to most developers
