## Context

Implementing an undo/rollback endpoint on an event-sourced entity (e.g. a progress tracker) where state changes emit events with `previousState` and `currentState`. The entity also auto-detects backward movement (e.g. percentage decreasing) and emits `ROLLED_BACK` changeType — the same changeType the explicit rollback endpoint uses.

## Symptom

The naive algorithm — "find the most recent event, take its `previousState`" — oscillates on consecutive calls. Call 1 undoes the last change. Call 2 undoes the rollback (because the rollback itself emitted an event). The state ping-pongs between two values indefinitely.

Skipping `ROLLED_BACK` events doesn't work either: organic backward movement from normal state updates also emits `ROLLED_BACK`, so skipping them causes the undo to jump over legitimate state changes the user wants to undo.

## What was tried (didn't work)

1. **Skip ROLLED_BACK events in scan** — breaks when the user manually updates state backward (auto-detected as ROLLED_BACK). The undo skips that event and goes too far back.
2. **Take previousState of most recent event** — oscillates on consecutive calls.
3. **Match current state in event trail** — fragile when duplicate states exist.

## Fix

Build the **forward-state-sequence** from `CREATED` and `STATE_UPDATED` events only (filtering out `ROLLED_BACK`, `COMPLETED`, `FAILED`, `REACTIVATED`, `CHILD_ATTACHED`). Find the current state's position in this sequence and return the one before it.

```java
public ProgressInstance rollback(UUID id) {
    ProgressInstance instance = requireInstance(id);
    List<ProgressUpdatedEvent> events = eventStore.findByProgressId(id);

    // Build forward state list from CREATED + STATE_UPDATED only
    List<JsonNode> forwardStates = new ArrayList<>();
    for (ProgressUpdatedEvent e : events) {
        if (e.changeType() == ProgressChangeType.STATE_UPDATED
                || e.changeType() == ProgressChangeType.CREATED) {
            forwardStates.add(e.currentState());
        }
    }

    JsonNode currentState = instance.state();

    // Find current state in forward sequence, return the one before it
    for (int i = forwardStates.size() - 1; i >= 0; i--) {
        if (forwardStates.get(i).equals(currentState)) {
            if (i == 0) throw new IllegalStateException("No previous state");
            return applyRollbackState(instance, forwardStates.get(i - 1));
        }
    }

    // Current state not in forward sequence — was set by backward movement
    // Find the event that produced it and take its previousState
    for (int i = events.size() - 1; i >= 0; i--) {
        if (events.get(i).currentState().equals(currentState)
                && events.get(i).previousState() != null) {
            return applyRollbackState(instance, events.get(i).previousState());
        }
    }

    throw new IllegalStateException("No previous state");
}
```

**Why this works for all cases:**

- **Consecutive rollbacks:** After rollback #1, the ROLLED_BACK event is excluded from the forward sequence. The current state (now at position N-1) finds its predecessor at N-2. Each consecutive call walks one step further back.
- **Organic backward movement:** If the user sets state backward via normal update (auto-detected as ROLLED_BACK), the current state won't be in the forward sequence. The fallback path finds the event that produced it and undoes it — restoring the state before the backward movement.

## Why this is non-obvious

The natural instinct is event-trail scanning with changeType filtering. But the changeType ambiguity (same `ROLLED_BACK` for both organic and explicit rollback) makes filtering impossible without either adding a new changeType or a marker field. The forward-state-sequence approach sidesteps the ambiguity entirely by reconstructing the progression history and navigating it positionally.

### Alternatives considered

- Adding a separate `RESTORED` changeType for explicit rollback — works but adds a new enum value and requires all event consumers to handle it
- Thread-local flag to mark "this event came from the rollback endpoint" — fragile, doesn't survive serialization
- Storing a rollback counter on the instance — adds state that must be managed across reactivation and other lifecycle transitions
