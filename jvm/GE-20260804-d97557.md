### Symptom
Adding both `casehub-work` and `casehub-qhorus` as test dependencies for a bridge module (`casehub-work-qhorus`) causes 77 CDI deployment errors at `@QuarkusTest` startup:
- `AmbiguousResolutionException` for `CurrentPrincipal` — both extensions provide `@ApplicationScoped` implementations
- `UnsatisfiedResolutionException` for `EntityManager` — each uses named persistence units (`default` vs `qhorus`)

### Context
Bridge modules that depend on two independent Quarkus extensions at compile scope (api modules only) but need both runtimes on the test classpath. The extensions were designed independently and have overlapping CDI bean registrations.

### What was tried
- `@QuarkusTest` with both runtimes → 77 errors
- Adding `quarkus.arc.exclude-types` for conflicting beans → works but requires listing dozens of types and breaks on every upstream change
- `quarkus.arc.selected-alternatives` for in-memory stores → partial fix, still leaves CurrentPrincipal ambiguity

### Root cause
Quarkus ArC scans all Jandex-indexed beans on the classpath. Two extensions providing the same SPI bean (`CurrentPrincipal`) without `@Alternative` priority ordering creates an unresolvable ambiguity. The extensions are correctly independent — they shouldn't need to know about each other's CDI beans.

### Fix
Use plain JUnit tests (not `@QuarkusTest`) with recording doubles for the SPIs. The bridge module's production code depends only on api-level interfaces (`MessageDispatcher`, `ChannelReader`, `WorkItemCreator`, `WorkItemObserver`). These are trivial to implement as test doubles:

```java
// Recording MessageDispatcher for tests
adapter.messageDispatcher = dispatch -> {
    dispatched.add(dispatch);
    return new DispatchResult(1L, dispatch.channelId(), ...);
};
```

This tests the actual business logic without CDI wiring, avoids the classpath collision entirely, and runs in <100ms vs ~10s for `@QuarkusTest`.

### Alternatives considered
- **Massive exclude-types list**: works but brittle — breaks on every upstream change, hard to maintain
- **Shared CurrentPrincipal module**: would require platform-level refactoring across all repos — correct long-term but disproportionate for a bridge module test

### Why this is non-obvious
The natural instinct is to use `@QuarkusTest` for any Quarkus module. The 77-error explosion is overwhelming and the fix (exclude dozens of types) appears to be the "right" approach. The simpler answer — don't use `@QuarkusTest` at all for bridge modules that only consume api-level interfaces — is easy to overlook because it feels like you're testing less. In practice you're testing more of what matters (the bridge logic) and less of what doesn't (CDI wiring between two runtimes you don't control).
