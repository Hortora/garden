### Symptom
`TransactionRequiredException: Transaction is not active` thrown from a
`@PostConstruct` method annotated with `@Transactional`, despite the annotation
being present. All `@QuarkusTest` tests fail because Quarkus cannot start.

### Context
An `@ApplicationScoped @Startup` bean has a `@PostConstruct @Transactional` method
that calls `persistAndFlush()`. The transaction infrastructure is available (the
`TransactionScopedSession` exists and checks for a transaction), but no JTA
transaction is active.

### What was tried (didn't work)
Adding `@Transactional` to the `@PostConstruct` method — the annotation is present
but has no effect.

### Root cause
Quarkus ArC invokes `@PostConstruct` during bean creation (`_Bean.create()`) on the
raw instance, not through the CDI proxy or subclass interceptor chain. The
`@Transactional` interceptor (which wraps the call in a JTA transaction) is never
invoked because the lifecycle callback bypasses the interception mechanism.

Stack trace evidence:
```
at WorkItemTemplateYamlLoader.upsertByName(...)
at WorkItemTemplateYamlLoader.loadFromUrl(...)
at WorkItemTemplateYamlLoader.loadTemplates(...)
at WorkItemTemplateYamlLoader_Bean.create(Unknown Source)  ← direct, not via proxy
```

### Fix
Replace `@PostConstruct` with an `@Observes StartupEvent` method. Observer methods
ARE dispatched through the CDI proxy, so `@Transactional` interception works:

```java
// ❌ BAD: @Transactional silently ignored
@PostConstruct
@Transactional
void loadTemplates() { ... }

// ✅ GOOD: @Transactional intercepted via proxy dispatch
@Transactional
void loadTemplates(@Observes StartupEvent ev) { ... }
```

Remove `@Startup` from the class — `@Observes StartupEvent` already ensures eager
initialization. Stack trace with the fix shows the interceptor chain is active:
```
at WorkItemTemplateYamlLoader_Subclass.loadTemplates$$superforward(Unknown Source)
at WorkItemTemplateYamlLoader_Subclass$0.apply(Unknown Source)
at AroundInvokeInvocationContext.proceed(...)
```

### Why this is non-obvious
The CDI spec says interceptors apply to lifecycle callbacks (`@PostConstruct`,
`@PreDestroy`). A developer would expect `@Transactional` to work on `@PostConstruct`
because Quarkus claims CDI compliance. The failure is silent at build time — it only
manifests at runtime as a `TransactionRequiredException`, and the stack trace doesn't
hint that the interceptor was bypassed.

### Why this fix
`@Observes StartupEvent` is semantically equivalent to `@PostConstruct` for
eagerly-initialized beans, but observer methods are dispatched through the normal
CDI method invocation path where interceptors are applied. This is the simplest fix
that preserves startup-time initialization without programmatic transaction management.

### Alternatives considered
- Programmatic `UserTransaction.begin()/commit()` — works but verbose and error-prone
- Separate CDI bean with `@Transactional` method called from `@PostConstruct` — works
  (proxy interception on the second bean) but unnecessary indirection
