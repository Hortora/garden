## Symptom

Adding regex or explicit class patterns to `quarkus.arc.exclude-types` has no effect on certain beans — they remain in the CDI context despite being listed for exclusion. The bean count in `DeploymentException` stays identical regardless of exclude-types entries.

## Context

When a dependency is a Quarkus extension (has a `-deployment` module with `@BuildStep` methods), that extension's deployment processor can register beans via `AdditionalBeanBuildItem`. These beans bypass classpath discovery entirely — they are programmatically added to the bean archive during augmentation.

## Root Cause

`quarkus.arc.exclude-types` filters classpath-scanned bean discovery. `AdditionalBeanBuildItem` (especially with `.setUnremovable()`) registers beans through a separate code path that is not subject to the exclude-types filter. The beans are added after the exclusion filter has already run.

Extension deployment processors commonly register strategy beans, migration customizers, and SPI implementations this way — making them impossible to exclude via configuration alone.

## Fix

1. Check if the module has a `-deployment` artifact: `ls ~/.m2/repository/io/casehub/<module>-deployment/`
2. Read the deployment processor's `@BuildStep` methods to see which beans are force-registered
3. For beans registered via `AdditionalBeanBuildItem`: do not attempt to exclude them — remove the module dependency instead, or use CDI alternatives with higher `@Priority` to override them

## Why this is non-obvious

The `quarkus.arc.exclude-types` documentation does not mention this limitation. A developer adding a module dependency and seeing CDI errors would naturally reach for exclude-types — the standard documented mechanism. The fact that certain beans are immune to this mechanism is only discoverable by reading the extension's deployment processor source code.
