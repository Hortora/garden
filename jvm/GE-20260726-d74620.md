### Symptom
Updating a single SNAPSHOT dependency (e.g. `casehub-engine-api`) fixes one compilation error but immediately exposes another in a different module (`casehub-worker-api`, `casehub-platform-api`, `casehub-engine-flow`). Each fix creates a new failure — the cycle repeats 5-10 times before the project compiles.

### Context
Multi-repo Maven platform (casehub) where engine, work, ledger, platform, neocortex, and worker-api each publish independent `0.2-SNAPSHOT` artifacts. A breaking API change in one repo (e.g. engine removes `WorkerExecutionContext`, adds type parameter to `WorkerFunction`) propagates through transitive dependencies. Maven resolves each artifact's SNAPSHOT independently — the resolved set may span 3-4 different build timestamps, creating binary incompatibilities between modules that were internally consistent at build time.

### What was tried (didn't work)
1. Updating one dependency with `-U` flag — fixes one error, introduces another
2. Manually copying older timestamped jars to restore consistency — fragile, breaks again on next resolve
3. Excluding broken CDI beans one at a time — each exclusion creates a new unsatisfied dependency downstream

### Root cause
Maven SNAPSHOT resolution picks the latest available artifact per module independently. When repo A publishes a new SNAPSHOT that changes an API consumed by repo B, but repo B hasn't rebuilt yet, the resolved dependency set is internally inconsistent. The consumer project (repo C) sees the new API from A but the old implementation from B that still references the removed API.

### Fix
Update ALL platform SNAPSHOT dependencies simultaneously, not one at a time:
```bash
mvn dependency:resolve -U -Denforcer.skip=true
```
Then fix ALL compilation errors in a single pass before attempting to run tests. If a dependency module (e.g. `casehub-work-engine-adapter`) hasn't published a compatible SNAPSHOT, build and install it locally from its repo:
```bash
mvn install -f ../work/engine-adapter/pom.xml -Dmaven.test.skip=true -Denforcer.skip=true
```

### Why this is non-obvious
The natural instinct is to fix compilation errors incrementally — update the broken dep, fix the error, move on. With SNAPSHOT dependencies this creates a moving target: each `-U` resolution may pull a different timestamp for a different artifact, and the "fix" for one module may be incompatible with what another module expects. The key insight is that SNAPSHOT consistency is an all-or-nothing property across the dependency graph.

### Alternatives considered
- **Version pinning**: Pin each SNAPSHOT to a specific timestamp in `<dependencyManagement>`. Works but requires manual maintenance and breaks the purpose of SNAPSHOTs.
- **BOM-based alignment**: A parent BOM that publishes all module versions from the same CI build. Correct long-term solution but requires CI infrastructure changes.
