## Symptom

Adding `quarkus.index-dependency` for a multi-bean JAR (e.g. `casehub-blocks`) to discover one specific bean (e.g. `DecisionNarrativePipeline`) causes `AmbiguousResolutionException` for unrelated types — `Clock`, `AgentRoutingStrategy`, etc. — because Quarkus discovers ALL beans in the indexed JAR, not just the one you need.

## Context

You need `DecisionNarrativePipeline` from `casehub-blocks`. The JAR lacks a Jandex index, so its `@ApplicationScoped` beans aren't auto-discovered. The obvious fix — `quarkus.index-dependency.casehub-blocks.*` — discovers the pipeline but also discovers `ClockProducer`, `LlmAgentRoutingStrategy`, and other beans that conflict with beans already on the classpath.

## What was tried (didn't work)

1. `quarkus.index-dependency` for the jar — discovers all beans, causes ambiguity
2. `quarkus.arc.exclude-types` to suppress the unwanted beans — does NOT work on Jandex-indexed JARs (see GE-20260529-0c23f1)

## Root cause

`quarkus.index-dependency` is all-or-nothing per JAR. There is no per-class or per-package indexing. Once indexed, every `@ApplicationScoped`, `@Produces`, and `@Alternative` bean in the JAR enters the CDI graph. If the JAR was designed as a multi-feature library (routing, summarisation, scheduling all in one artifact), indexing it to get one feature activates all features.

## Fix

Don't index the JAR. Create a manual CDI producer that constructs the target bean directly:

```java
@ApplicationScoped
public class NarrativeCdiProducer {

    @Produces
    @ApplicationScoped
    DecisionNarrativePipeline pipeline(AgentProvider agentProvider) {
        return new DecisionNarrativePipeline(agentProvider);
    }

    @Produces
    @ApplicationScoped
    EventStreamBus<DecisionSignal> signalBus(DecisionNarrativePipeline pipeline) {
        return pipeline.signalBus();
    }
}
```

The producer injects only the dependencies the target bean needs (here `AgentProvider`, which is already on the CDI graph). No other beans from the JAR are activated.

### Alternatives considered

- **Index + exclude conflicting beans**: `exclude-types` doesn't suppress beans from Jandex-indexed JARs, so this fails silently — the beans stay active despite being listed
- **Split the JAR**: correct long-term fix but requires upstream changes

## Why this is non-obvious

The developer's first instinct is `index-dependency` — it's the documented Quarkus pattern for unindexed JARs. The documentation doesn't warn about the blast radius of indexing a JAR with many beans. The failure mode (ambiguity in unrelated types) doesn't point back to the recently-added index entry.

### Why this fix

Manual `@Produces` is the minimal-blast-radius approach — you get exactly the beans you need, nothing else. It also makes the dependency explicit in code rather than hidden in config.
