### Symptom

An ONNX model that uses padding masks (`padding_mask = (tensor.abs().sum(dim=-1) == 0)`) silently processes zero-padded windows as real data. The model produces incorrect classifications with no error — padding is not detected.

### Context

When serving a sequence model via ONNX Runtime (Java or Python), the input tensor may have variable-length content with zero-padded trailing windows. The model's internal padding mask detects empty windows by checking whether all features sum to zero. This pattern is common in transformer and attention-based architectures.

Feature normalization (z-score: `(x - mean) / std`) is applied before inference to match training-time normalization. The training pipeline normalizes each populated window independently and leaves padding as literal zeros.

### Root cause

If normalization is applied uniformly to the entire flattened tensor — including zero-padded windows — every zero becomes `(0.0 - mean) / std = -mean/std`, which is non-zero for any feature with a non-zero training mean. The padding mask (`abs().sum() == 0`) then fails to detect padded windows, and the model treats padding as meaningful input.

A related failure: availability flags (binary features indicating whether a modality block is populated) must also be computed before normalization. After z-score, raw zeros become non-zero, so `hasNonZeroBlock()` always returns true.

### Fix

Normalize only populated windows. Check whether a window is all-zero before applying z-score, and skip it if so:

```java
for (int w = 0; w < maxWindows; w++) {
    int base = w * featuresPerWindow;
    boolean isPopulated = false;
    for (int f = 0; f < featuresPerWindow; f++) {
        if (tensor[base + f] != 0.0f) { isPopulated = true; break; }
    }
    if (!isPopulated) continue; // preserve zeros for padding mask
    for (int f = 0; f < featuresPerWindow; f++) {
        if (normStd[f] > 0) {
            tensor[base + f] = (tensor[base + f] - normMean[f]) / normStd[f];
        }
    }
}
```

Compute availability flags from the raw (pre-normalization) tensor, not after z-score.

### Why this is non-obvious

The normalization loop looks correct — it applies the same transform the training pipeline used. The failure is invisible: no error, no exception, just degraded accuracy. The symptom (classification accuracy drops on short sequences but not long ones) is easy to misattribute to insufficient training data or model quality rather than a feature engineering mismatch.

### Alternatives considered

- Normalizing the entire tensor then re-zeroing padded windows afterward — works but is fragile; you need to know which windows were originally zero before normalization destroyed that information. Checking before is cleaner.
- Using NaN or a sentinel value for padding instead of zero — requires model architecture changes and is non-standard for ONNX export.
