### Symptom

`quarkus.arc.exclude-types=io.casehub.blocks.routing.agent.CbrAgentRoutingStrategy` has
no effect when `CbrAgentRoutingStrategy` is only produced by a `@Produces` method on
`BlocksBeans`, not directly annotated as a class bean. CDI ambiguity errors persist
despite the type being listed in exclude-types.

The same configuration worked in Quarkus 3.32 — upgrading to 3.39 breaks it silently
with no warning or error about the ineffective exclusion.

### Context

Multi-module Quarkus application where a library JAR (`casehub-blocks`) has an embedded
Jandex index and a `@ApplicationScoped` declaring class (`BlocksBeans`) with multiple
`@Produces` methods. The application excludes specific produced types to resolve CDI
ambiguities with its own implementations.

### What was tried (didn't work)

1. `quarkus.arc.exclude-types=io.casehub.blocks.routing.agent.CbrAgentRoutingStrategy`
   — the produced type name. No effect; the producer still fires.
2. Adding the produced type to the exclude list alongside other types that DO work
   (class beans like `MockCurrentPrincipal` are correctly excluded by the same mechanism).
3. `quarkus.arc.exclude-types` with wildcard patterns for the produced type's package.

### Root cause

`quarkus.arc.exclude-types` matches against the **bean class** during ArC's discovery
phase. For CLASS beans, the bean class is the annotated class itself — exclusion works.
For PRODUCER METHOD beans, the bean class is the **declaring class** (e.g. `BlocksBeans`),
not the return type. Listing the produced/return type excludes nothing because ArC never
matches it against producer return types.

### Fix

Exclude the **declaring class** entirely:

```properties
quarkus.arc.exclude-types=io.casehub.blocks.BlocksBeans
```

This removes ALL producer methods on that class. For any beans you still need from the
declaring class, provide application-level replacements:

```java
@ApplicationScoped
public class DevCbrOutcomeWeights implements CbrOutcomeWeights {
    private final CbrOutcomeWeights delegate = new DefaultCbrOutcomeWeights();
    @Override
    public Map<RoutingOutcome, Double> weights() { return delegate.weights(); }
}
```

### Alternative — @Alternative @Priority

Instead of excluding, make your bean win the ambiguity:

```java
@Alternative
@Priority(1)
@ApplicationScoped
public class MyRoutingStrategy implements AgentRoutingStrategy { ... }
```

This avoids excluding the declaring class but requires you to provide a complete
implementation rather than just displacing an unwanted producer.

### Why this is non-obvious

The property name `exclude-types` strongly implies it excludes beans by their produced
type. The same property works perfectly for class beans, creating an expectation that
it works uniformly. The failure is completely silent — no warning, no log message. The
only signal is that CDI ambiguity errors persist after adding the type to the exclude
list. Prior Quarkus versions (3.32) may have handled this differently, making the
behaviour change invisible during upgrades.

### Alternatives considered

- Excluding individual produced types (the intuitive approach) — doesn't work for producers
- Using `quarkus.arc.selected-alternatives` — requires `@Alternative` on the bean, can't annotate library classes
- Removing the Jandex index dependency — doesn't help when the library JAR has an embedded Jandex index
