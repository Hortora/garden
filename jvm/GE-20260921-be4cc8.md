### Symptom

Adding a new value to a Java enum that has classification methods (`isTerminal()`, `isActive()`) causes silent data corruption in JPA queries — even though you correctly update the classification methods. No compile-time error. No test failure unless you have coverage for the specific query path with the new value.

### Context

Any JPA entity that stores an `@Enumerated(STRING)` field and uses JPQL queries like `WHERE e.state NOT IN :terminalStates` is vulnerable. The query parameter is populated by a hand-maintained `List.of(...)` in the DAO, not by the enum's classification method.

### What was tried (didn't work)

Adding the new enum value and updating `isTerminal()` — expected all JPA queries to automatically include it. They don't: JPQL parameters are plain data, not method calls.

### Root cause

JPQL cannot invoke Java methods. When a DAO needs "all terminal states" for a WHERE clause, it must pass a `List<MyEnum>` as a parameter. Developers hard-code this list (`List.of(FULFILLED, DECLINED, FAILED, ...)`), creating a parallel definition of "terminal" that must be manually synced with the enum's `isTerminal()` method. The two definitions diverge silently on the next enum addition.

### Fix

Replace hard-coded lists with a static field derived from the enum's classification method:

```java
private static final List<CommitmentState> TERMINAL_STATES =
        java.util.Arrays.stream(CommitmentState.values())
                .filter(CommitmentState::isTerminal)
                .toList();

private List<CommitmentState> terminalStates() {
    return TERMINAL_STATES;
}
```

The `static final` ensures the stream runs once at class load, not per query. Future enum additions that update `isTerminal()` are automatically included — no second file to touch.

### Why this is non-obvious

The developer's mental model is: "I updated `isTerminal()`, so queries that check terminal states are correct." This is true for in-memory code but false for JPA queries. The compile-time type safety of `@Enumerated` enums masks the runtime divergence between the enum's classification and the hard-coded query parameter.

### Why this fix

`Arrays.stream(values()).filter(...)` is preferred over maintaining an `EnumSet` constant because it derives from the classification method directly — there's exactly one definition of "terminal" in the codebase. An `EnumSet` constant would be another hard-coded list, just in a different location.

### Alternatives considered

- Maintaining a `CommitmentState.terminalValues()` method that returns `EnumSet` — still couples to a second definition unless it delegates to `isTerminal()`. If it delegates, it's functionally identical to the stream approach but adds an API surface.
- Using JPA Criteria API instead of JPQL — avoids the problem entirely but requires rewriting all queries. Impractical for existing codebases.
