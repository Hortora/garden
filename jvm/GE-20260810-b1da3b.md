### Context
`Agent.builder()` uses LangChain4j's `ChatModel` for request-response without tool-calling support. When you need agents to make coordination decisions (report failure, decline task, call tools), the natural approach is LangChain4j's `AiServices` with `@Tool` annotations — but that's a different API surface.

### Technique
Instead of tool calling, define the coordination vocabulary as a structured JSON response schema in the system prompt:

```java
String systemPrompt = roleDescription + """
    You must respond with a JSON object containing:
    - "action": one of "report_failure", "report_decline", "report_completion", ...
    - "reason": explanation (required for failure/decline/completion)
    - "toolName": which tool to call (for "call_tool" action)
    """;

Agent agent = Agent.builder()
    .systemPrompt(systemPrompt)
    .model(chatModel)
    .build();

Map<String, Object> output = agent.execute(context).output();
String action = (String) output.get("action");
```

The orchestrator interprets the action field and routes accordingly. Tool calls are executed by the orchestrator after parsing, not by the agent directly.

### Why this is non-obvious
The standard approach for LLM tool calling is function-calling APIs (`@Tool`, `ToolSpecification`). Using structured JSON output instead decouples the LLM interaction from tool execution — the agent decides what to do, the orchestrator does it. This is cleaner for experiments comparing coordination protocols because both variants use identical agent construction; only the orchestrator differs.

### Alternatives considered
- LangChain4j `AiServices.builder()` with `@Tool` — works but introduces a different API surface from `Agent.builder()`, confounding framework comparison with coordination comparison
- Direct `ChatModel.chat()` with `ToolSpecification` — lower level but same confound
