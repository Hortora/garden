## Symptom

After adding a bean to `quarkus.arc.exclude-types`, CDI deployment still fails with `UnsatisfiedResolutionException` — but for the excluded bean, not for its dependents:

```
UnsatisfiedResolutionException: Unsatisfied dependency for type
io.casehub.qhorus.runtime.dashboard.QhorusDashboardService and qualifiers [@Default]
- declared on CLASS bean [...ChannelResource]
The following classes match by type, but have been skipped during discovery:
  - QhorusDashboardService was excluded in config
```

## Context

A Quarkus consumer application pulls in a library JAR (e.g. casehub-qhorus) that contains beans the consumer doesn't need. The consumer excludes them via `quarkus.arc.exclude-types`. But other beans in the same library JAR inject the excluded bean.

## What was tried (didn't work)

- Verified the class name in `exclude-types` was correct (it was — the error confirms "was excluded in config")
- Checked for CDI alternatives or `@DefaultBean` implementations
- The error message helpfully says the bean was excluded but unhelpfully doesn't suggest excluding the injector too

## Root cause

`quarkus.arc.exclude-types` removes the bean from CDI discovery but does NOT remove beans that inject it. `ChannelResource` (not excluded) declares `@Inject QhorusDashboardService` — since the service is excluded, the injection point is unsatisfied.

ArC validates all injection points at build time. Excluding a bean without excluding its consumers is a build-time error.

## Fix

Exclude the full injection chain — both the bean and all beans that inject it:

```properties
quarkus.arc.exclude-types=\
  io.casehub.qhorus.runtime.dashboard.QhorusDashboardService,\
  io.casehub.qhorus.runtime.api.ChannelResource
```

When a new SNAPSHOT adds more beans that inject the excluded type, those must also be excluded.

## Why this is non-obvious

The error message says the bean "was excluded in config" — which reads as "I did what you asked, but it still doesn't work." A developer would expect that excluding a bean means excluding it, not that they also need to exclude everything that touches it. The error tells you what's wrong but not what to add to the exclude list — you have to read the "declared on" line to find the injecting bean.

### Alternatives considered

- Using `@DefaultBean` no-op stub — correct for beans you own, not for third-party library beans
- Conditional bean activation via build profiles — more complex, doesn't solve the transitive problem
- Filing upstream to make the injecting bean use `Instance<>` with `isResolvable()` — correct long-term fix but requires library changes
