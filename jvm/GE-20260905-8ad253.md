### Symptom
After bulk-replacing `ContentSummariser<T>` → `ContentSummariser<T, SummaryResult>` across source files, `SummaryResult.text()` and `SummaryResult.annotations()` produce "cannot find symbol" errors. The class compiles but the `SummaryResult` inside it is a type variable, not the imported class.

### Context
Generifying an interface from one type parameter to two (e.g. `ContentSummariser<T>` → `ContentSummariser<T, R>`) requires updating all implementations. A bulk find-replace of `ContentSummariser<T>` → `ContentSummariser<T, SummaryResult>` correctly updates `implements` clauses but also matches `class` declarations:

```java
// Before: class LlmContentSummariser<T> implements ContentSummariser<T>
// After:  class LlmContentSummariser<T, SummaryResult> implements ContentSummariser<T, SummaryResult>
```

The `SummaryResult` in the class type parameters is now a **type variable** that shadows the import `io.casehub.qhorus.api.spi.SummaryResult`. Every reference to `SummaryResult` inside the class body resolves to the type variable (which has no methods) instead of the concrete class.

### What was tried (didn't work)
- `ide_replace_text_in_file` with `ContentSummariser<T>` → `ContentSummariser<T, SummaryResult>` — matches both class declarations AND implements clauses, creating the shadowing problem silently (compiles but methods are missing).

### Root cause
Java allows any identifier as a type parameter name. `<T, SummaryResult>` is syntactically valid — `SummaryResult` becomes a type parameter that hides the import. The compiler does not warn because both interpretations are legal.

### Fix
Only replace in `implements`/`extends` clauses and field/parameter declarations — not in the `class` declaration's own type parameter list. The class keeps its original arity:

```java
// Correct:
public class LlmContentSummariser<T> implements ContentSummariser<T, SummaryResult>
//                                 ^^^ — one type param (the class's own)
//                                                                    ^^^^^^^^^^^^^^ — concrete type (the import)
```

### Why this is non-obvious
The error messages ("cannot find symbol: method text()") point to the method call sites, not the type parameter declaration. The class declaration looks plausible — `<T, SummaryResult>` reads as if `SummaryResult` is a type binding, not a variable. Only careful inspection of the class-level generics reveals the shadowing.

### Alternatives considered
- IntelliJ structural search/replace (`ide_structural_search_replace`) — operates at the AST level and could distinguish `implements` clauses from class declarations, but the pattern matching for class declarations vs implements clauses requires different SSR templates per context.
