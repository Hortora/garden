## Symptom

After rebuilding and redeploying a Quarkus app, the browser continues serving the old version of static resources (JS, CSS, HTML). Page reload, tab close, and even restarting the browser context (Playwright MCP reconnect) do not fetch the updated files. ES module imports are particularly affected — they cannot be busted by URL navigation or hard reload.

## Context

Quarkus sets `cache-control: public, immutable, max-age=86400` on all static resources by default. The `immutable` directive tells the browser the resource will never change at this URL — the browser skips revalidation entirely for 24 hours. This is aggressive even for production and devastating for development iteration.

ES modules imported via `<script type="module">` with `import ... from '/path/file.js'` are cached by URL. The `immutable` header means neither `location.reload(true)` nor closing the tab clears the cached module. Only a URL change (e.g. `?v=2` query param) or a completely new browser context forces a fresh fetch.

## What was tried

- Page reload — no effect (immutable skips revalidation)
- Tab close + reopen — no effect (HTTP cache persists across tabs)
- Playwright MCP reconnect — no effect (browser context reuses disk cache)
- `fetch('/file.js', { cache: 'no-store' })` — works for programmatic fetch but not for `import` statements
- Adding `?v=N` to import URL — works but requires HTML change per deploy

## Root cause

Quarkus's default static resource caching is designed for production (content-addressed assets). In development or when iterating on static files served from JARs, the `immutable` header makes the browser ignore all content changes for 24 hours.

## Fix

Add to `application.properties`:

```properties
quarkus.http.static-resources.caching-enabled=false
```

This removes all cache-control headers from static resource responses, allowing normal browser caching behavior (revalidation on reload).

For production, consider using content-hashed filenames instead of relying on `immutable`.

### Why this is non-obvious

The `immutable` directive is uncommon enough that most developers don't know its semantics — it's not just `max-age`, it's "don't even check." The symptom looks like a server-side deployment issue (old file being served) when the problem is entirely client-side (browser refuses to ask for the new version).
