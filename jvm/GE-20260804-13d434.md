### Symptom

Quarkus build fails at CDI validation with:

```
AmbiguousResolutionException: Ambiguous dependencies for type
io.casehub.eidos.api.CapabilityHealth and qualifiers [@Default]
```

### Context

Adding `casehub-eidos` (runtime) as a dependency to a CaseHub application that already depends on `casehub-engine` (runtime). The application was previously working with engine's built-in no-op health probing.

### Root cause

Two `@DefaultBean @ApplicationScoped` implementations of `CapabilityHealth` become visible:

| Bean | Module | Behaviour |
|------|--------|-----------|
| `NoOpCapabilityHealth` | `casehub-engine` (runtime) | Always returns `CapabilityStatus.Ready()` |
| `DefaultCapabilityHealth` | `casehub-eidos` (runtime) | Real probing: degradation, exclusions, epistemic weakness, behavioral violations |

Both are `@DefaultBean` — Quarkus CDI cannot pick a winner. The engine provides the no-op fallback for apps that don't use eidos. Once eidos-runtime is on the classpath, both compete.

Related: GE-20260803-2dd865 (LeastLoadedAgentStrategy CDI ambiguity — same pattern, different bean pair).

### Fix

Exclude the engine's no-op in `application.properties`:

```properties
quarkus.arc.exclude-types=...,\
  io.casehub.engine.internal.worker.NoOpCapabilityHealth
```

This lets `DefaultCapabilityHealth` from eidos-runtime win as the sole `@DefaultBean`.

### Why this is non-obvious

The engine's `NoOpCapabilityHealth` is an internal class — not documented in any consumer guide. You only discover it exists when CDI validation fails. The error message names both beans but doesn't indicate which to keep. A developer unfamiliar with the eidos/engine layering might exclude the wrong one.
