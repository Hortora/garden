## Symptom

QuarkusUnitTest `.assertException()` tests report "The build was expected to fail" — the build succeeds silently because the extension's `@BuildStep` method is never invoked. The Quarkus app starts with `Installed features: [cdi]` and no extension log output.

## Context

When developing a new Quarkus extension (runtime + deployment modules), the deployment module contains `@BuildStep` methods that scan Jandex annotations. Testing validation rules with `QuarkusUnitTest` requires the full extension discovery chain: runtime JAR with `quarkus-extension.properties` → deployment JAR with `quarkus-build-steps.list` → both with `quarkus-extension.yaml`. Even with all metadata files present and both modules installed to `.m2`, the build step may not be invoked during `QuarkusUnitTest` augmentation for new extensions.

## What was tried (didn't work)

1. Added `META-INF/quarkus-extension.properties` to runtime module — still not discovered
2. Added `META-INF/quarkus-extension.yaml` to both runtime and deployment — still not discovered
3. Ran `mvn install` on both modules before test — still not discovered
4. Compared with a working reference extension (engine-annotations) — identical structure

## Root cause

QuarkusUnitTest resolves deployment artifacts via Maven coordinates during augmentation bootstrap. The exact failure mode for new extensions is unclear — the working reference extension has an identical structure but was established longer, suggesting possible caching or classpath ordering effects.

## Fix

Test build extension validation logic directly with the Jandex `Indexer` API instead of relying on QuarkusUnitTest extension discovery:

```java
private Index indexClasses(Class<?>... classes) throws IOException {
    Indexer indexer = new Indexer();
    for (Class<?> clazz : classes) {
        String resourceName = "/" + clazz.getName().replace('.', '/') + ".class";
        try (InputStream stream = clazz.getResourceAsStream(resourceName)) {
            indexer.index(stream);
        }
    }
    return indexer.complete();
}

@Test
void escalateAlone_throwsError() throws IOException {
    Index index = indexClasses(EscalateAloneService.class, Escalate.class);
    Map<String, MethodInfo> methods = new HashMap<>();
    processor.collectAnnotatedMethods(index, ESCALATE, methods);
    assertThatThrownBy(() -> processor.validateMethod(methods.values().iterator().next(), index))
        .isInstanceOf(IllegalStateException.class)
        .hasMessageContaining("requires @HumanApproval");
}
```

Make processor validation methods package-private. Include annotation classes in the index alongside the test service class.

## Why this is non-obvious

The documented Quarkus approach for testing deployment modules is `QuarkusUnitTest` with `@RegisterExtension`. The Jandex Indexer API is an internal API not documented for testing purposes. Developers would typically spend hours debugging extension discovery before considering direct Jandex testing.

### Alternatives considered

- QuarkusUnitTest with `setForcedDependencies()` — API exists but didn't resolve the discovery issue
- Creating a separate integration-test module — correct but heavyweight for validation logic
- Making processor methods public — unnecessarily wide access; package-private suffices
