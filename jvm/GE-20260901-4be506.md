## Symptom / Problem

jsonschema2pojo generates mutable JavaBean POJOs via JCodeModel. JCodeModel has no concept of Java records — it can only emit classes with getters/setters. When you need Java records (immutable, compact constructors, null-safe defaults) from JSON Schema, the tool appears unusable.

## Context

Building a Maven plugin that generates Java records from JSON Schema (YAML format). The schema uses JSON Schema 2020-12 features ($defs, $ref, oneOf, additionalProperties) that simpler alternatives (Cosium/json-schema-to-java-record) don't support.

## What developers would normally do

Write a standalone schema parser from scratch, or fork jsonschema2pojo and modify the output stage — both significant undertakings. Alternatively, hand-write the records and accept the drift risk.

## The technique

Use jsonschema2pojo as a **parsing library only** — its `SchemaStore`, `ContentResolver`, and schema resolution handle the hard parts ($ref resolution, type graph construction, `$defs` traversal). Then bypass `JCodeModel` entirely and emit record source text directly via StringBuilder.

```java
// Parse the schema using jsonschema2pojo's infrastructure
ObjectMapper yaml = new ObjectMapper(new YAMLFactory());
JsonNode root = yaml.readTree(schemaFile);
JsonNode defs = root.path("$defs");

// Walk $defs, extract type/field metadata into your own model
// (jsonschema2pojo's SchemaMapper.generate() is NOT called)

// Emit records as text — no JCodeModel dependency
StringBuilder sb = new StringBuilder();
sb.append("public record ").append(prefix).append(typeName).append("(\n");
// ... components, compact constructor, annotations
```

The POJO output path can still use the full jsonschema2pojo pipeline (SchemaMapper → JCodeModel → file output) for consumers that need mutable POJOs. Both paths share the schema parsing phase.

### Why this is non-obvious

jsonschema2pojo is designed as an end-to-end generator — the documented API is `SchemaMapper.generate()` which couples parsing to JCodeModel output. The internal schema model (Schema, SchemaStore) is not documented as a standalone parsing API. A developer looking at the tool sees "JSON Schema → POJOs" and assumes the pipeline is monolithic.

### Why this fix

The alternative — writing a JSON Schema parser from scratch — would reinvent $ref resolution, $defs traversal, and type graph construction. jsonschema2pojo has years of edge-case handling for these. Using it as a parsing library gets that for free while replacing only the output format.

### Alternatives considered

- **Cosium/json-schema-to-java-record** — purpose-built but lacks $defs, oneOf, additionalProperties support. Would require significant feature additions.
- **Standalone parser** — reinvents schema parsing that jsonschema2pojo already handles correctly.
- **Fork jsonschema2pojo** — full fork is heavyweight for replacing only the output stage.
