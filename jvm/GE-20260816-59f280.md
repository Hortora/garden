### Symptom

An integration-tier app (e.g. `chat-app`) builds reusable infrastructure (push WebSocket wiring, dataset builders, REST endpoints). A second integration-tier app (claudony) needs the same capabilities. The natural impulse is to add a Maven dependency from claudony to chat-app.

### Context

Multi-repo platform with a tier hierarchy: foundation (APIs, SPIs, runtimes) → integration (apps that wire foundation components together) → application (end-user facing). Each tier depends on layers below it, never sideways.

### Root cause

An integration-tier app accumulates infrastructure that is useful beyond its own scope. The infrastructure is generic (e.g. "push qhorus channel data over WebSocket") but lives in an app-specific repo because that's where it was first needed. Adding a Maven dependency between apps violates the tier hierarchy — the dependent app now inherits the other's application config, seed data, and Quarkus configuration, creating subtle conflicts.

### Fix

Promote the reusable pieces to a foundation module where both apps can consume them independently:

1. Identify which classes are app-specific vs. generic infrastructure
2. Move generic infrastructure to the appropriate foundation repo (e.g. push dataset wiring → `qhorus-push` module)
3. Both apps depend on the foundation module — neither depends on the other

The trigger for promotion is **two consumers**. One consumer = keep it where it lives. Two consumers = the infrastructure belongs in foundation.

### Why this is non-obvious

The "just add a dependency" approach is faster and the code already works. The tier violation feels harmless because both are "our apps." The problems are latent: any refactoring of the dependency app breaks the dependent app's build; application.properties, seed data, and Quarkus config leak across; the dependency app implicitly becomes a foundation component without the stability guarantees.

### Alternatives considered

- Split the source app into `app-core` (library JAR) + `app` (thin application): reduces config leakage but still creates an app-to-app dependency; the "core" module is a foundation component in disguise
- Duplicate the code in both apps: defeats consolidation, doubles maintenance
