## Symptom

`cannot find symbol` for a class that you just added to an upstream dependency and installed via `mvn install`. The class is confirmed present in the jar at `~/.m2/repository/...` (verified with `zipfile` or `jar tf`). The project compiles fine in other checkouts but fails in the slot worktree.

## Context

Casehub work-slot creates isolated project clones under `worktrees/N/`. Each slot has its own `.m2/` directory at the slot root (e.g. `worktrees/79/.m2/`). Maven resolves dependencies from this local repo first, shadowing `~/.m2/`.

When you run `mvn install` on an upstream dependency (e.g. casehub-ledger), it installs to `~/.m2/` by default. But a project in `worktrees/79/devtown/` resolves from `worktrees/79/.m2/` — which still has the old jar without your new class.

## What was tried (didn't work)

- Verified the class exists in `~/.m2` jar — it does
- Deleted `_remote.repositories` and Maven metadata — still fails
- Ran with `-o` (offline) — still fails
- Ran with `-U` (force update) — downloads remote SNAPSHOT, overwrites local install

## Root cause

Maven's `dependency:build-classpath` reveals the actual jar path on the classpath:
```
/Users/user/claude/casehub/worktrees/79/.m2/io/casehub/casehub-ledger/0.2-SNAPSHOT/casehub-ledger-0.2-SNAPSHOT.jar
```

This is NOT `~/.m2` — it's the slot's local `.m2`. The slot was created with its own Maven local repository, and all Maven builds within the slot resolve from there.

## Fix

Install to the slot's local repo explicitly:

```bash
mvn install -f /path/to/upstream/pom.xml -pl module -am -DskipTests \
  -Dmaven.repo.local=/path/to/worktrees/N/.m2
```

For example:
```bash
mvn install -f worktrees/79/ledger/pom.xml -pl runtime -am -DskipTests \
  -Dmaven.repo.local=worktrees/79/.m2
```

## Why this is non-obvious

The symptom — "cannot find symbol" for a class you just installed — naturally leads to checking `~/.m2`, verifying the jar contents, and clearing Maven caches. All of these confirm the class exists. The per-slot `.m2` directory is a build infrastructure concern invisible to the developer. The only way to discover it is via `mvn dependency:build-classpath` which reveals the unexpected path.

### Alternatives considered

- Symlinking the slot's `.m2` to `~/.m2` — rejected because other slots may need different SNAPSHOT versions
- Running `mvn install` without `-Dmaven.repo.local` and expecting it to work — this is the default behaviour that causes the problem
