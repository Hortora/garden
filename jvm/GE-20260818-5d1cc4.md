### Symptom
Every `@QuarkusTest` in claudony fails during Quarkus augmentation with:
```
DeploymentException: Found 7 deployment problems:
[1] Unsatisfied dependency for type CaseDefinitionRegistry and qualifiers [@Default]
    — injection target: parameter 'caseDefinitionRegistry' of GoalRevisionEvaluator constructor
    — The following classes match by type, but have been skipped during discovery:
      DefaultCaseDefinitionRegistry was excluded in config
```
Unit tests (plain JUnit, no `@QuarkusTest`) pass fine. Zero integration test coverage.

### Context
Claudony's `application.properties` uses `quarkus.arc.selected-alternatives` to exclude `DefaultCaseDefinitionRegistry` from CDI discovery. This worked when engine beans didn't inject it directly. A SNAPSHOT update to `casehub-engine` added `GoalRevisionEvaluator` and `GoalOutcomeRecorder` which constructor-inject `CaseDefinitionRegistry` — the excluded bean. Quarkus Arc validates the full bean graph at augmentation time, so the unsatisfied dependency blocks ALL `@QuarkusTest` startup.

### Root cause
Transitive SNAPSHOT drift: the engine's internal bean graph changed (new classes injecting `CaseDefinitionRegistry`), but claudony's Arc exclusion config wasn't updated to provide an alternative. The exclusion predates the new beans.

### Fix
None known as of 2026-08-18 — requires either:
1. Engine to not directly inject `CaseDefinitionRegistry` in the new beans (use optional injection or a factory), or
2. Claudony to provide a test-scoped `CaseDefinitionRegistry` alternative bean, or
3. Claudony to remove the exclusion and manage the side effects of having the full engine registry active

### Workaround
Run only non-`@QuarkusTest` tests: `mvn test -Dtest="ClaudonyChannelBackendTest"` (filter to specific test classes that don't need the Quarkus container).

### Why this is non-obvious
The symptom (CDI deployment failure) looks like a claudony bug, but the cause is a transitive SNAPSHOT change in casehub-engine. The `DefaultCaseDefinitionRegistry was excluded in config` hint in the error message is easy to miss in the 7-problem dump. A developer debugging this would likely look at claudony's own beans first, not at engine internals.

### Alternatives considered
- Updating the Arc exclusion config — insufficient because the new engine beans require the real registry, not just an alternative
- Adding a `@DefaultBean` mock — would compile but might mask real integration issues
