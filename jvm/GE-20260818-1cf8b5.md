## Single-entry volatile cache for evaluation-cycle POJO deduplication

### Context

An `@ApplicationScoped` bean performs an expensive transformation (e.g. Jackson deserialization) on every method call. When a single event triggers N calls against the same input state, the transformation runs N times redundantly.

### What developers would normally do

Reach for `ConcurrentHashMap` (multi-entry, needs size bounds and eviction), `ThreadLocal` (per-thread, heavier with virtual threads), or `CaseContext.onAnyChange()` listener subscription (reactive invalidation, lifecycle management).

### Technique

Use a single `volatile` field holding an immutable record:

```java
private volatile CachedPojo cachedPojo;

private record CachedPojo(CaseContext context, long version,
                           Class<?> contextClass, Object pojo) {}

private Object resolveTypedPojo(CaseContext context, Class<?> contextClass) {
    CachedPojo cached = this.cachedPojo;
    if (cached != null
            && cached.context == context           // identity check
            && cached.version == context.getVersion()  // version check
            && cached.contextClass == contextClass) {
        return cached.pojo;
    }
    Object pojo = deserialize(context, contextClass);
    this.cachedPojo = new CachedPojo(context, context.getVersion(), contextClass, pojo);
    return pojo;
}
```

Cache key semantics:
- `context ==` (identity) — different cases have different instances, no cross-case pollution
- `version ==` — monotonic counter increments on mutation, stale = re-deserialize
- `contextClass ==` — defensive against multi-type scenarios

### Why this is non-obvious

The natural instinct is `ConcurrentHashMap` (handles multiple contexts) or `ThreadLocal` (thread isolation). But the primary case is N evaluations firing in sequence for one context change — single-entry captures this exactly. The worst case under concurrency (two threads overwrite each other's entry) is identical to having no cache at all — never worse, often better. No GC pressure (one record allocation per miss), no eviction logic, no lifecycle management. The `volatile` provides visibility without `synchronized` or `AtomicReference`.

### Alternatives considered

- **ConcurrentHashMap** — handles interleaved cases but adds size bounds, eviction, and WeakReference complexity for marginal gain
- **ThreadLocal** — clean isolation per thread, but heavier with virtual threads and doesn't help when evaluations cross thread boundaries
- **Listener-based invalidation** (`onAnyChange()`) — reactive, correct, but adds subscription lifecycle and coupling to the context API
