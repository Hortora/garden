## Maven SNAPSHOT resolves remote timestamped JAR over local install when remote metadata has higher buildNumber

**Symptom:** `cannot find symbol` for a class that exists in the locally-installed `casehub-worker-api-0.2-SNAPSHOT.jar` but not in the older timestamped JAR from GitHub Packages (`casehub-worker-api-0.2-20260723.012836-15.jar`). Maven picks the remote JAR despite a more recent local install.

**Context:** When both `maven-metadata-local.xml` (from `mvn install`) and `maven-metadata-github.xml` (from a prior remote download) exist in the same SNAPSHOT directory, Maven's resolver compares them. The remote metadata had `buildNumber: 18` with a timestamp from July; the local had `localCopy: true` with a timestamp from today. Maven resolved the remote.

### What was tried (didn't work)

- `mvn install` to refresh the local JAR — local JAR is updated but metadata comparison still picks remote
- `-nsu` (no snapshot updates) — prevents checking remote for NEW metadata but doesn't override already-cached remote metadata
- `-o` (offline) — still resolves from cached remote metadata in the local `.m2`

### Root cause

Maven's SNAPSHOT resolution compares metadata across all configured repositories. The remote `maven-metadata-github.xml` with `buildNumber: 18` and `timestamp: 20260730` is treated as "newer" than the local metadata, even though `mvn install` wrote a more recent JAR. The resolver picks the timestamped JAR filename from the remote metadata.

### Fix

Remove the cached remote metadata files to force local-only resolution:

```bash
rm ~/.m2/repository/io/casehub/casehub-worker-api/0.2-SNAPSHOT/maven-metadata-github*.xml
```

Then re-run the build. Maven will use `maven-metadata-local.xml` as the only source.

### Why this is non-obvious

`mvn install` appears to succeed — the correct JAR is written. The error surfaces downstream in a consuming module with a generic "cannot find symbol" that doesn't mention metadata resolution. There's no warning that Maven chose a remote JAR over the local install.
