### Symptom
Codebase has dozens of SPI interfaces returning `Uni<T>` where every implementation wraps synchronous logic in `Uni.createFrom().item(() -> { ... })`, and every caller immediately calls `.await().indefinitely()`.

### Context
When Mutiny was adopted, wrapping everything in Uni was the recommended pattern — it preserved the option for async execution and composed well with reactive pipelines. With Java 21+ virtual threads, blocking a thread is free. The Uni wrapper becomes pure ceremony: `Uni.createFrom().item(() -> x)` at the producer, `.await().indefinitely()` at the consumer, for zero functional benefit.

### What was tried (didn't work)
Keeping Uni everywhere "for future flexibility" — but in practice, no implementation was ever async. The flexibility was theoretical; the boilerplate was real.

### Root cause
The motivation for Uni on SPIs was thread efficiency (don't block expensive platform threads). Virtual threads remove that motivation. Uni still has genuine value for concurrent composition (`Uni.join().all()` for parallel dispatch) and at API boundaries where callers chain reactively — but not for internal SPI contracts consumed synchronously.

### Fix
Audit all `Uni<T>` returns. For each, ask: "Does the caller chain reactively on this, or does it `.await().indefinitely()`?" If the latter, remove the Uni wrapper.

**Keep Uni on:**
- API boundaries (`execute()`, `converse()`) — callers chain on the result
- `AgentInvoker.invoke()` — concurrent multi-agent dispatch via `Uni.join().all()`

**Remove Uni from:**
- Internal SPIs consumed synchronously: `route()`, `shouldActivate()`, `aggregate()`, `evaluate()`, `decompose()`
- Internal methods: `runLoop()`, `cancel()`

The refactoring is mechanical: unwrap `Uni.createFrom().item()` at producers, remove `.await().indefinitely()` at consumers. In blocks, this touched 82 files but was a net reduction of 143 lines.

### Why this is non-obvious
The instinct is to keep Uni "because it's the reactive way" and "we might need async later." But virtual threads make the async future moot for synchronous logic — you get non-blocking behaviour for free without Uni. The insight is recognising that Uni's value is now context-dependent, not universal.

### Why this fix
Removing Uni from synchronous SPIs makes the code dramatically cleaner. Compare:
```java
// Before: 3 lines of ceremony
var decision = model.routing().route(ctx).await().indefinitely();
// After: 1 line
var decision = model.routing().route(ctx);
```
The reactive chain in CompositeTermination went from a Uni flatMap chain to a simple for loop. The code became easier to read, debug, and reason about.

### Alternatives considered
- Keep Uni everywhere for uniformity — rejected because the uniformity is superficial (every call site does .await().indefinitely())
- Use CompletableFuture instead of Uni — rejected because the few places that genuinely benefit from async (AgentInvoker) compose better with Uni than CF
- Remove Uni entirely including API boundaries — rejected because callers of execute() genuinely chain on the result
