### Symptom
A library module needs to disable or override config properties in other modules when it is present on the classpath — without requiring consumer code changes.

### Context
When building optional platform modules that subsume functionality from existing modules (e.g. a rate limiter that replaces per-provider concurrency semaphores), the new module needs to disable the old controls. Consumers should not need to update their `application.properties` — adding the new module to the classpath should be sufficient.

### What was tried (didn't work)
- CDI `@Observes StartupEvent` to programmatically override config — too late, beans already constructed with old values
- `@ConfigProperty` with fallback defaults — doesn't override, just provides defaults when absent
- Requiring consumers to add config overrides manually — violates the classpath-presence activation pattern

### Root cause
SmallRye Config resolves property values by ordinal priority. Default `application.properties` has ordinal 250, but library JARs with `META-INF/microprofile-config.properties` default to ordinal 100 — lower than the application. By explicitly setting `config_ordinal=200` in the library's properties file, the library's values win over another library's ordinal 100 defaults but lose to the application's ordinal 250.

### Fix
Ship a `META-INF/microprofile-config.properties` in the library JAR with an explicit ordinal:

```properties
# Ordinal 200 — overrides provider defaults (ordinal 100) when this module is on classpath.
# Deployers can re-enable provider settings with ordinal 300+ in application.properties.
config_ordinal=200
some.other.module.max-concurrent-sessions=0
another.module.max-concurrent-sessions=0
```

Priority chain: application.properties (250) > library override (200) > provider defaults (100).

### Why this is non-obvious
The technique inverts the normal config relationship — a library JAR is overriding another library's defaults, not providing its own. Most developers think of `microprofile-config.properties` as "defaults for my module" not "overrides for other modules." The ordinal mechanism makes this possible but the pattern isn't documented as a module subsumption strategy.
