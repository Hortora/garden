## DriveSource Map.put overwrites existing axis values — use DriveComposer modulation layer for cross-axis effects

### Symptom

Adding a new `DriveSource` implementation that returns `DriveIntensity` for axes already produced by existing sources (e.g., a NarrativeDriveSource returning CURIOSITY alongside the existing CuriosityDrive) silently overwrites the original value. No error, no warning. The original source's intensity is lost.

### Context

`DriveOrchestrator.tick()` collects `DriveIntensity` from all `DriveSource` instances into an `EnumMap<DriveAxis, DriveIntensity>` via `raw.put(axis, intensity)`. Each of the four existing sources returns exactly one axis (CURIOSITY, COMPETENCE, AFFILIATION, AUTONOMY). If a fifth source returns the same axis as an existing source, `Map.put` replaces the original value — standard Java map semantics.

This matters when designing cross-axis effects like narrative feedback or social norm modulation, where the effect should influence ALL four axes simultaneously based on contextual relevance. The natural instinct is to add a new `DriveSource` — but the SPI is structurally wrong for this.

### Root cause

`DriveSource` is an extraction SPI: one source, one axis, one raw intensity. It answers "how strong is this drive based on this data source?" Cross-axis effects answer a different question: "how should existing drives be amplified or dampened based on contextual state?" These are semantically different operations — extraction vs modulation — but both look like "something that affects drive intensity."

### Fix

Use `DriveComposer`'s modulation layer pattern. `DriveComposer.compose()` accepts `@Nullable Map<DriveAxis, Double>` — pre-computed modulation coefficients that amplify or dampen existing drive intensities after raw extraction. This sits alongside mood modulation and personality modulation as a third (or Nth) modulation layer.

```java
// Caller computes modulation coefficients from narrative/social state
Map<DriveAxis, Double> narrativeMod = NarrativeModulation.compute(narrativeState);
// Coefficients are applied inside compose() after raw extraction and mood/personality modulation
composer.compose(rawDrives, disposition, mood, narrativeMod, config, agentId, tenantId, now);
```

`DriveSource` is only correct for extracting raw intensity from a single data source for a single axis.

### Why this is non-obvious

The iteration pattern looks correct at a glance: evaluate all sources, collect results, compose. A `NarrativeDriveSource` that reads narrative state and returns intensity values compiles and runs without error. The overwrite is invisible because the resulting `DriveProfile` still has valid values for all four axes — they're just the wrong values. The bug only surfaces as behaviorally incorrect drive priorities (e.g., curiosity drive reflecting narrative salience instead of knowledge gap data).

### Alternatives considered

- Map each DriveSource to its axis at registration time (`Map<DriveAxis, DriveSource>`) — prevents multi-axis sources but doesn't solve the modulation semantic
- Add a `List<DriveAxis> axes()` method to DriveSource — couples every implementation to axis identity; doesn't help with the extraction-vs-modulation distinction
