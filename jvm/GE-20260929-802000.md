### Symptom
App module fails to compile with `'[' expected` and `-> expected` errors
pointing at APT-generated REST resource files in `target/generated-sources/annotations/`.
Errors appear at column positions inside method call arguments.

### Context
The `@McpDomain` annotation processor generates REST resource wrapper classes
for each API facade. When a facade method has a primitive `int` parameter
(e.g. `@QueryParam("limit") int limit`), the generated wrapper creates a
default value using `new int()` — which is invalid Java (primitives cannot
be instantiated with `new`).

### What was tried (didn't work)
- Clean build (`mvn clean compile`) — errors persist because the APT regenerates
  the same broken code
- Checking for stale generated sources — the sources ARE freshly generated, just wrong

### Root cause
The `@McpDomain` code generator's default-value logic treats all parameter types
uniformly, using `new <Type>()` for defaults. This works for reference types
(`new String()`, `new Object()`) but fails for Java primitives where the correct
default is the literal zero value (`0` for int, `false` for boolean, etc.).

### Fix
Change primitive parameter types to their boxed equivalents in `@McpDomain`
facade methods:

```java
// Before — generates invalid new int()
public Object recent(@QueryParam("limit") int limit) { ... }

// After — generates valid new Integer() (or null)
public Object recent(@QueryParam("limit") Integer limit) { ... }
```

This is also the correct semantic choice for REST/MCP parameters, which
are nullable (absent query params should be null, not 0).

### Why this is non-obvious
The compiler error points at generated source code in `target/`, not at the
original API facade class. The error message (`'[' expected`, `-> expected`)
gives no hint about primitive types. You need to read the generated code,
spot `new int()`, then trace back to understand the APT's default-value
generation strategy.

### Alternatives considered
- Fix the APT generator itself to handle primitives correctly (emit `0` for
  int, `false` for boolean, etc.) — correct long-term fix but requires a
  platform change. The boxed-type workaround is immediate and semantically
  better for REST/MCP anyway.
