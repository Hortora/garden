### Context

When adding optional dependencies (via `Instance<T>`) to an existing CDI
`@Decorator`, constructor injection forces all existing tests to update
their constructor calls. Field injection avoids this — existing tests
continue using the original constructor with no changes, while new tests
set the fields directly via package-private access.

### Technique

Keep the existing constructor with its original parameters. Add new
optional dependencies as `@Inject` fields:

```java
@Decorator
@Priority(200)
public class MyDecorator implements MySPI {

    private final MySPI delegate;
    private final MyExpander expander;

    // New optional dependencies — field injection
    @Inject @Any
    Instance<EmbeddingModel> embeddingModel;

    @Inject
    Instance<MeterRegistry> meterRegistry;

    @Inject
    ExpansionConfig config;

    @Inject
    public MyDecorator(@Delegate @Any MySPI delegate, MyExpander expander) {
        this.delegate = delegate;
        this.expander = expander;
    }

    private void optionalBehaviour() {
        // Null-safe — fields are null in unit tests unless explicitly set
        if (config == null || embeddingModel == null || !embeddingModel.isResolvable()) {
            return; // skip optional behaviour
        }
        // ... use embeddingModel.get() safely
    }
}
```

Tests set fields directly:

```java
var decorator = new MyDecorator(delegate, expander); // existing constructor
decorator.embeddingModel = presentInstance(model);    // set optional dep
decorator.config = stubConfig();                      // set config
```

### Why this is non-obvious

Constructor injection is generally preferred in CDI — field injection is
considered a code smell by many style guides. But for decorators with
established test suites, the pragmatic trade-off favours field injection:
zero test churn for existing tests, clean null-safety for the optional
path, and CDI still wires everything correctly at runtime.
