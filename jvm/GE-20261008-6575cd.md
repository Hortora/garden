## @IfBuildProperty(enableIfMissing=true) + @ConfigMapping — disabled test profile crashes with ConfigValidationException

### Symptom

A `@QuarkusTest` with a `@TestProfile` that sets a `@IfBuildProperty`-gated property to `"false"` causes Quarkus startup failure:

```
ConfigValidationException: SRCFG00050: casehub.qhorus.cache.enabled
in SysPropConfigSource does not map to any root
```

The test intends to verify that beans are absent when the gate is disabled. Instead, the application refuses to start.

### Context

This occurs when:
1. A `@IfBuildProperty(name = "x.y.enabled", stringValue = "true", enableIfMissing = true)` gates a CDI producer
2. The producer injects a `@ConfigMapping(prefix = "x.y")` interface
3. A `@TestProfile` sets `x.y.enabled=false` to test the disabled path
4. No other bean outside the gate injects the same `@ConfigMapping`

### Root cause

When `@IfBuildProperty` evaluates the property as not matching (`"false" != "true"`), it excludes all gated beans. If those were the only beans injecting the `@ConfigMapping`, ARC unregisters the config mapping entirely. SmallRye Config then sees the `x.y.enabled=false` property from the test profile's `SysPropConfigSource` but has no registered mapping for the `x.y` prefix — validation fails.

The contradiction: with `enableIfMissing=true`, you cannot rely on property absence to disable the gate (absence = enabled). You must set the property to `false`. But setting it triggers the `ConfigValidationException`.

### Fix

Change `enableIfMissing=true` to `enableIfMissing=false`:

```java
// Before — gate defaults to enabled, cannot test disabled path
@IfBuildProperty(name = "x.y.enabled", stringValue = "true",
                 enableIfMissing = true)

// After — gate defaults to disabled, test profile simply omits the property
@IfBuildProperty(name = "x.y.enabled", stringValue = "true",
                 enableIfMissing = false)
```

The disabled test profile omits the property entirely — absence = disabled. The enabled test profile (and production config) explicitly sets `x.y.enabled=true`. No orphaned properties, no `ConfigValidationException`.

This is also semantically correct for optional library modules — consumers opt in explicitly rather than getting the feature by default.

### Why this is non-obvious

The general rule "test profiles for disabled gates must NOT set properties under the gated prefix" is well-known (see GE-20260512-b3f32a). But with `enableIfMissing=true`, the developer faces a contradiction: you MUST set the property to disable the gate, but setting it crashes the application. The fix isn't "stop setting the property" — it's "change the gate's default" so that absence means disabled.
