### Summary

To emit CloudEvents that RAS ganglia can observe, inject `jakarta.enterprise.event.Event<io.cloudevents.CloudEvent>` and call `fireAsync()`. The `RasEngine` CDI bean observes `@ObservesAsync CloudEvent` and routes events to registered ganglia by matching `handledEventTypes`.

### Context

When building domain-specific event bridges (e.g. `SecurityAlertBridge`, `MarketConditionCloudEventPublisher`) that need to feed events into the RAS situation detection pipeline. The spec references a `CloudEventEmitter` abstraction, but the actual mechanism is CDI async events.

### What was tried

Searched for a dedicated `CloudEventEmitter` API — found `io.casehub.blocks.summarisation.cloudevents.CloudEventEmitter` which is for the summarisation pipeline output side (subscribes to an `EventStreamBus`), not a generic emitter. The actual emission path is standard CDI.

### Root cause

The RAS engine (`RasEngine.java`) has `void onCloudEvent(@ObservesAsync CloudEvent event)` — it's a CDI observer. Any CDI bean that fires a `CloudEvent` via `Event.fireAsync()` will reach all registered ganglia.

### Fix

```java
@Inject Event<CloudEvent> cloudEventSink;

void emitEvent(String type, byte[] data) {
    CloudEvent ce = CloudEventBuilder.v1()
        .withId(UUID.randomUUID().toString())
        .withType(type)
        .withSource(URI.create("/my-domain/source"))
        .withDataContentType("application/json")
        .withData(data)
        .build();
    cloudEventSink.fireAsync(ce);
}
```

### Why this is non-obvious

The spec's `@Inject CloudEventEmitter emitter` suggests a dedicated API. The actual `CloudEventEmitter` class in the blocks-summarisation module has a completely different purpose (wrapping `EventStreamBus` output). The CDI async event mechanism is undocumented as the RAS ingestion path — discoverable only by reading `RasEngine.java`.
