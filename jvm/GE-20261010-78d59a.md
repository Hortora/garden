# Decorator pass-through methods silently bypass cross-cutting concerns added later

### Symptom
A `ChannelManagerDecorator` implementing a `ChannelManager` interface had quorum enforcement on `create()`, `delete()`, `pause()`, `resume()`, and 10+ config mutation methods. But `findOrCreate()` delegated directly to the underlying service without any quorum check — a minority-partition node could create channels via `findOrCreate`, silently violating the system's quorum guarantee.

### Context
The decorator was built incrementally across multiple phases. Initially, `findOrCreate()` was a simple pass-through (`return delegate.findOrCreate(request)`). When quorum enforcement was added to other methods, `findOrCreate` was overlooked because it didn't "feel like" a write operation — it's a find-*or*-create, and the find path is indeed safe. But the create path is a write, and the quorum bypass was a correctness bug.

### What was tried (didn't work)
The bug was invisible in unit tests because the decorator test setup used a mock that returned `canServeWrites()=true`. Only a full entry-point audit (tracing every method in the decorator against the interface contract) caught it.

### Root cause
Temporal evolution gap: when a cross-cutting concern (quorum, auth, rate limiting, caching) is added to a decorator, every interface method must be audited — including ones that were initially pass-throughs. Methods added to the interface before the cross-cutting concern was introduced default to pass-through and miss the concern silently.

### Fix

```java
@Override
public FindOrCreateResult findOrCreate(ChannelCreateRequest request) {
    if (routingEnabled && !clusterManager.canServeWrites()) {
        throw new QuorumViolationException("minority partition");
    }
    return delegate.findOrCreate(request);
}
```

### Why this is non-obvious
The decorator had 10+ methods all correctly guarded. A code reviewer seeing the decorator for the first time would assume completeness. The single missing guard was on the one method whose name suggests read semantics ("find") but has a write side-effect ("or create"). The pattern is especially dangerous because it passes all existing tests — the failure only manifests under partition conditions with the specific `findOrCreate` call path.

### Alternatives considered
- Structural enforcement via abstract base class with a template method for the quorum check — rejected because it constrains the decorator implementation and the interface is CDI-managed (CDI decorators have their own lifecycle).
- Adding an integration test that disables quorum and checks every ChannelManager method — would catch this but is fragile against new interface methods.
