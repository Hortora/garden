# SmallRye JWT blocks WebSocket upgrades without explicit permit policy

## Symptom

WebSocket upgrade to `/ws/push?token=<valid-JWT>` fails with browser
error: "HTTP Authentication failed; no valid credentials available".
REST endpoints with the same JWT in an `Authorization: Bearer` header
work fine. No error in server logs.

## Context

Quarkus application with `quarkus-smallrye-jwt` for REST auth and
`quarkus-websockets-next` for WebSocket endpoints. Auth is configured
via `quarkus.http.auth.permission` for REST paths (e.g.
`/api/channels/*`). The WebSocket path (`/ws/*`) has no explicit
permission entry. An `HttpUpgradeCheck` implementation validates the
JWT from the `?token=` query parameter.

## What was tried (didn't work)

- Adding `@Authenticated` to the WebSocket endpoint — not the issue;
  the rejection happens before endpoint dispatch.
- Verifying the JWT is valid — it is; REST calls with the same token
  succeed.
- Checking `HttpUpgradeCheck` logic — it correctly parses and validates
  the token, but never gets called.

## Root cause

SmallRye JWT's HTTP security filter runs on ALL HTTP requests,
including WebSocket upgrade requests. It looks for credentials in the
`Authorization` header only — not in query parameters. Without an
explicit `permit` policy for the WebSocket path, the filter sees no
credentials and returns 401 before `HttpUpgradeCheck` can run.

The `HttpUpgradeCheck` is a Quarkus `websockets-next` mechanism that
runs after the HTTP security layer accepts the upgrade. If the security
layer rejects first, the check never executes.

## Fix

Add an explicit permit policy for WebSocket paths:

```properties
quarkus.http.auth.permission.ws-push.paths=/ws/push
quarkus.http.auth.permission.ws-push.policy=permit
```

The `HttpUpgradeCheck` implementation handles actual authentication
via the query parameter token. The permit policy only bypasses the
HTTP-layer JWT header check — it does not disable auth for the
WebSocket connection.

### Why this is non-obvious

The WebSocket endpoint has no security annotations, and the
`HttpUpgradeCheck` correctly validates tokens. The failure happens in
an invisible layer between HTTP routing and WebSocket dispatch. The
browser error message ("HTTP Authentication failed") doesn't indicate
which security mechanism rejected the request.
