### Symptom

`@QuarkusTest` integration tests using rest-assured GET requests fail with
`NullPointerException` at `java.lang.Class.isAssignableFrom(Native Method)`
deep inside Groovy's `ClosureMetaClass.invokeOnDelegationObject`. POST-based
tests in the same suite pass. The error has no mention of Spring Boot, Maven,
or BOM ordering — it looks like a Groovy/Java 26 compatibility issue.

### Context

Multi-module Maven project with Quarkus modules and a new Spring Boot
auto-configuration module. The Spring Boot dependencies BOM
(`spring-boot-dependencies`) was imported in the parent pom's
`<dependencyManagement>` alongside the Quarkus BOM (inherited from
casehub-parent). The intent was to make Spring Boot version management
available to all modules.

### What was tried (didn't work)

1. Importing Quarkus BOM explicitly before Spring Boot BOM in the same
   `<dependencyManagement>` — Maven "first wins" should give Quarkus
   precedence. **Still failed** — the Groovy version managed by Spring Boot
   isn't managed by the Quarkus BOM at all, so "first wins" doesn't apply.

### Root cause

Spring Boot 4.1.0's BOM manages Groovy at a version that's incompatible
with rest-assured's closure-based HTTP dispatch on Java 26. The Quarkus BOM
doesn't manage Groovy versions, so importing both BOMs at the parent level
gives Spring Boot's Groovy management uncontested control. The resulting
Groovy version breaks `ClosureMetaClass` delegation for GET response handling
(POST works because it uses a different code path in rest-assured).

### Fix

Import the Spring Boot BOM only in the module that needs it — not at the
parent level. The Spring auto-configuration module gets its own
`<dependencyManagement>` with the Spring Boot BOM. Quarkus modules never
see Spring-managed transitive versions.

```xml
<!-- connectors-spring/pom.xml — Spring BOM scoped to this module only -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-dependencies</artifactId>
      <version>${spring-boot.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

### Why this is non-obvious

The symptom is a Groovy NullPointerException in rest-assured internals —
nothing points to Maven dependency management as the cause. The "Quarkus BOM
first" fix that works for JUnit version conflicts (where both BOMs manage the
same artifact) doesn't work here because the Quarkus BOM doesn't manage
Groovy at all. The real fix is architectural: Spring Boot's BOM should never
be visible to Quarkus modules.

### Alternatives considered

- **Quarkus BOM first, Spring Boot BOM second** — doesn't help; Quarkus
  doesn't manage Groovy, so Spring's version wins regardless of import order
- **Excluding Groovy from Spring Boot BOM** — fragile; other managed versions
  could cause similar issues
- **Module-scoped BOM import** — correct; isolates Spring's dependency
  management to modules that actually need it
