## ConcurrentHashMap.values().stream().limit(N) silently excludes entries — search misses data non-deterministically

**See also:** GE-20260808-c29cdf covers `findFirst()` non-determinism. This entry covers `limit(N)` silently excluding entries that exist in the map.

### Symptom

`BehavioralSynthesisPhase` finds graduated cognitive nodes for one agent but not another. Both agents have graduated nodes in the same `InMemoryMindMapStore`. The code path is identical. One run finds both agents; the next run finds only one. Non-deterministic across JVM restarts.

### Context

`InMemoryMindMapStore` uses `ConcurrentHashMap<String, StoredNode>` for all nodes. The search method:

```java
return nodes.values().stream()
    .filter(n -> n.tenantId.equals(query.tenantId()))
    .filter(n -> query.type() == null || n.subgraphType().equals(query.type()))
    .limit(query.limit())  // limit = 40
    .toList();
```

With 120+ cognitive nodes across 14 subgraphs, `.limit(40)` grabs the first 40 by hash-bucket order. If the graduated nodes (which have `source-memory-id` property) hash to bucket positions 41+, they are silently excluded. The downstream filter finds zero graduated nodes and the agent is skipped.

### What was tried (didn't work)

1. Added diagnostic logging — confirmed the graduated nodes exist in the store
2. Manual search from the test (with limit 200) found all nodes — proving the data was there
3. Assumed insertion order — ConcurrentHashMap has no insertion ordering

### Root cause

`ConcurrentHashMap` iteration order is determined by hash-bucket placement, not insertion order. `.stream().limit(N)` takes the first N entries the bucket walk encounters. With synthetic UUID keys, the bucket positions are effectively random. The graduated nodes may or may not appear in the first N entries depending on their hash values.

The pattern `stream → filter(type) → limit(N) → filter(property)` is fundamentally broken when `N` is smaller than the total type-filtered population. The `limit` must come AFTER the property filter, not before it.

### Fix

Apply limits after filtering, not before:

```java
// BROKEN: limit applied before the meaningful filter
nodes.values().stream()
    .filter(typeFilter)
    .limit(40)              // ← random 40 entries
    .filter(graduatedFilter) // ← may find 0

// FIXED: limit applied after the meaningful filter
nodes.values().stream()
    .filter(typeFilter)
    .filter(graduatedFilter) // ← scans all entries
    .limit(20)               // ← caps the result set
```

Or use a search limit large enough to cover the entire collection (2000+).

### Why this is non-obvious

`HashMap` and `LinkedHashMap` have predictable ordering in practice (hash-based but stable within a JVM run, or insertion-ordered). Developers transfer that mental model to `ConcurrentHashMap`. But ConcurrentHashMap's internal structure (segmented bins, tree nodes) produces iteration orders that change between JVM versions, runs, and even between collections with different key sets. A test that passes 99 times can fail on the 100th because a new key's hash shifts bucket boundaries.
