## Stream.max() with secondary Comparator picks largest in ALL dimensions — reverse tiebreaker for smallest-key-on-tie

### Symptom

Test expects `"alpha_signal"` as the trigger signal type when two signals tie on pressure. Got `"beta_signal"` instead.

### Context

Building a `CapacityPressureMonitor` that identifies the highest-pressure signal type per actor. When multiple signal types share the same max pressure value, the trigger should be deterministic — first alphabetically.

### What was tried (didn't work)

```java
String trigger = pressureBySignalType.entrySet().stream()
    .max(Map.Entry.<String, Double>comparingByValue()
            .thenComparing(Map.Entry.comparingByKey()))
    .map(Map.Entry::getKey)
    .orElse("unknown");
```

Expected: on value tie, `comparingByKey()` sorts alphabetically, so `max()` picks `"alpha_signal"`.
Actual: picks `"beta_signal"`.

### Root cause

`Stream.max(comparator)` returns the maximum element according to the provided total order. With `comparingByValue().thenComparing(comparingByKey())`, the total order is: highest value first; on value tie, highest key (lexicographically last). `"beta_signal" > "alpha_signal"` in natural String order, so `max()` picks `"beta_signal"`.

The developer's mental model is "max by value, then pick first alphabetically on tie." But `max()` doesn't have a notion of "primary" vs "secondary" — it just picks the largest element in the composite comparator's total order. "First alphabetically" means SMALLEST key, which is the opposite of what `max()` selects.

### Fix

Reverse the secondary key comparator so that `max()` picks the smallest key on value tie:

```java
String trigger = pressureBySignalType.entrySet().stream()
    .max(Map.Entry.<String, Double>comparingByValue()
            .thenComparing(Map.Entry.<String, Double>comparingByKey().reversed()))
    .map(Map.Entry::getKey)
    .orElse("unknown");
```

`comparingByKey().reversed()` inverts the key comparison. Now `"alpha_signal"` is considered GREATER than `"beta_signal"` in the secondary comparison, so `max()` selects it.

### Why this is non-obvious

The natural reading of `comparingByValue().thenComparing(comparingByKey())` is "sort by value, then by key." In a sort-then-pick-first context (e.g. `sorted().findFirst()`), this reads correctly — the first element after sorting has the smallest value and smallest key. But `max()` picks the LAST element in that ordering, which has the largest key on value tie. The fix — reversing the tiebreaker — is counter-intuitive because you're saying "largest key first" to get the smallest.

### Alternatives considered

- `sorted(comparator).findFirst()` — works correctly without reversal but allocates an intermediate sorted stream. `max()` is O(n) with no allocation.
- `min(comparator.reversed())` — semantically equivalent to `max(comparator)` with reversed tiebreaker, but harder to read.
