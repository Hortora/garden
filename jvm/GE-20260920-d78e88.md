# graphql-generator APT @Valid on body params requires jakarta.validation-api on consuming module classpath

## Symptom

Adding `@McpDomain` to a module for the first time causes a compilation error in generated code:

```
[ERROR] .../target/generated-sources/annotations/.../GeneratedTemporalDriversResource.java:[37,46]
  package jakarta.validation does not exist
```

The error points at a file you didn't write — under `target/generated-sources/annotations/` — making it initially confusing.

## Context

The casehub `graphql-generator` APT scans `@McpDomain` interfaces and concrete classes, generating both `@GraphQLApi` resolvers and `@Path` JAX-RS REST resources. The generated REST resource emits `@Valid` on method parameters that take complex body types (records, POJOs). This requires `jakarta.validation-api` on the compile classpath.

Modules that already have `quarkus-hibernate-validator` or other validation-aware dependencies don't hit this — the API is already transitive. New modules adopting `@McpDomain` without these existing dependencies fail at compile time.

## What was tried (didn't work)

- Reading the graphql-generator source to understand why `@Valid` is emitted — it's unconditional on body parameters
- Checking if `quarkus-rest` transitively includes validation-api — it does not (see also GE-20260508-b4c9b4)

## Root cause

The graphql-generator APT unconditionally emits `@Valid` on body parameters in generated REST resources. The `jakarta.validation-api` dependency is not declared by the generator itself (it's a compile-time annotation processor, not a runtime dependency), so consuming modules must provide it.

## Fix

Add `jakarta.validation-api` to the consuming module's POM:

```xml
<dependency>
    <groupId>jakarta.validation</groupId>
    <artifactId>jakarta.validation-api</artifactId>
</dependency>
```

No version needed — managed by the Quarkus BOM.

## Why this is non-obvious

The compilation error is in generated code, not source you wrote. The `@Valid` annotation is emitted by the APT even if your service doesn't use validation. The fix (adding a dependency for an annotation you didn't write) is unintuitive — you'd expect the generator to either skip `@Valid` when validation isn't on the classpath, or declare the dependency itself.
