## Maven annotationProcessorPaths creates an isolated classpath — Jandex indexes from compile dependencies are invisible to the APT

**Stack:** Maven 3.x, Jandex 3.x, javax.annotation.processing

### Symptom

An annotation processor that scans Jandex indexes (e.g. `GraphQLResolverProcessor`) runs but finds zero annotated interfaces, even though the interfaces exist in a compile dependency and the dependency has a Jandex index. The processor logs "loaded N Jandex indexes" but the count is lower than expected and the target annotations are not found.

### Context

A multi-module Maven project where:
- Module A (`api/`) contains `@McpDomain`-annotated SPI interfaces with a Jandex index
- Module B (`rest/`) has `api/` as a compile dependency
- Module B configures `annotationProcessorPaths` with only the generator jar

```xml
<annotationProcessorPaths>
  <path>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-platform-graphql-generator</artifactId>
    <version>${version}</version>
  </path>
  <!-- api/ NOT listed — this is the bug -->
</annotationProcessorPaths>
```

### What was tried (didn't work)

- Verified the api jar has a Jandex index (`META-INF/jandex.idx`) — it does
- Verified the api jar is on the compile classpath — it is
- Expected the APT to scan Jandex indexes from compile dependencies automatically — it doesn't

### Root cause

When `annotationProcessorPaths` is specified, Maven creates a **completely isolated classpath** for annotation processors. This classpath contains ONLY the jars listed in `annotationProcessorPaths` — the project's compile classpath (including all `<dependency>` declarations) is NOT included.

APTs that scan Jandex indexes (via `Jandex.CompositeIndex.create()` or similar) only see indexes from jars on the annotation processor classpath. If the jar containing the annotated interfaces is only on the compile classpath but not in `annotationProcessorPaths`, the APT cannot see its Jandex index.

### Fix

List the SPI interface jar in `annotationProcessorPaths` alongside the generator jar:

```xml
<annotationProcessorPaths>
  <path>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-platform-graphql-generator</artifactId>
    <version>${version}</version>
  </path>
  <path>
    <groupId>io.casehub</groupId>
    <artifactId>casehub-ledger-api</artifactId>
    <version>${project.version}</version>
  </path>
</annotationProcessorPaths>
```

This places both the generator and the API jar on the annotation processor classpath. The APT can now scan the Jandex index from the API jar and discover the annotated interfaces.

### Why this is non-obvious

The compile classpath and annotation processor classpath are conceptually related — both participate in compilation. A developer naturally assumes that compile dependencies are visible to annotation processors. The Maven documentation for `annotationProcessorPaths` describes it as specifying "the classpath used for annotation processing" but does not explicitly state that it REPLACES (rather than augments) the compile classpath for processor discovery.

The confusion is amplified when the APT runs successfully (logs "loaded N Jandex indexes") — the N indexes come from transitive dependencies of the jars in `annotationProcessorPaths`, giving the impression the scanning is working. Only the count being lower than expected (and the annotated interfaces not being found) reveals the gap.
