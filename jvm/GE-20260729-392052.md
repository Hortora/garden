### Symptom
REST endpoints that throw `BadRequestException` (400), `NotFoundException` (404), or other JAX-RS exceptions return HTTP 500 instead of their declared status code.

### Context
A `@Provider ExceptionMapper<RuntimeException>` is registered to catch unhandled exceptions and return a generic 500 response.

### What was tried (didn't work)
- Checked that `BadRequestException` was being thrown correctly
- Verified no other exception mapper was interfering
- Assumed JAX-RS built-in handling would take priority over the custom mapper

### Root cause
`BadRequestException` → `ClientErrorException` → `WebApplicationException` → `RuntimeException`. A custom `ExceptionMapper<RuntimeException>` matches ALL `RuntimeException` subclasses — including JAX-RS exceptions that already carry their own HTTP status code. The custom mapper unconditionally returns 500, overriding the built-in status.

### Fix
Guard the catch-all mapper with an `instanceof` check:

```java
@Override
public Response toResponse(RuntimeException exception) {
    if (exception instanceof WebApplicationException wae) {
        return wae.getResponse();
    }
    LOG.error("Unhandled exception", exception);
    return Response.status(500).entity(...).build();
}
```

### Why this is non-obvious
JAX-RS has built-in handling for `WebApplicationException` that respects the status code. Most developers assume a custom `ExceptionMapper<RuntimeException>` only catches non-JAX-RS exceptions. But CDI/RESTEasy selects the most specific type match, and `RuntimeException` is a supertype of all JAX-RS exceptions — so the custom mapper wins. No warning is logged about the override.

### Alternatives considered
- Registering separate `ExceptionMapper<WebApplicationException>` with higher priority — works but duplicates logic. The `instanceof` guard is simpler.
