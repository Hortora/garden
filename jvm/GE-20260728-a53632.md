### Symptom
Runtime module needs to navigate vocabulary-specific structural relationships (e.g. shadow/opposite pairs in Jungian cognitive functions for disposition health probing) but cannot depend on the vocab module — that would make optional vocabularies mandatory for all consumers of the extension.

### Context
Multi-module Quarkus extension with strict dependency direction: api (shared) ← runtime (extension) and api ← vocab (optional). The runtime's `DefaultDispositionHealth` probe needs to find the "opposite" (shadow) of a disposition function to detect evolution conditions, but `JungianFunctionTerm.shadow()` lives in the vocab module.

### What most developers would do
Add the vocab module as a runtime dependency (makes optional vocabularies mandatory), or use `instanceof` checks after resolving through the registry (requires the class on the classpath anyway), or hardcode vocabulary-specific logic in the runtime (breaks extensibility).

### Fix
Add a default method to the SPI interface in the api tier:

```java
// In VocabularyTerm (api tier):
default Optional<VocabularyTerm> opposite() { return Optional.empty(); }
```

Vocabulary enums override with their structural knowledge:

```java
// In JungianFunctionTerm (vocab tier):
@Override
public Optional<VocabularyTerm> opposite() {
    return Optional.of(shadow());
}
```

The runtime resolves terms through VocabularyRegistry and calls `opposite()` generically:

```java
// In DefaultDispositionHealth (runtime tier):
private Optional<String> findOpposite(String vocabUri, String term) {
    return vocabRegistry.resolve(vocabUri, term)
            .flatMap(VocabularyTerm::opposite)
            .map(VocabularyTerm::value);
}
```

Pair with lambda-based marker interfaces when the runtime needs typed constants matching vocab enum names without compile-time coupling:

```java
// Runtime defines evolution types as lambdas — same names as JungianEvolutionType enum
static final EvolutionType DOMINANT_AUXILIARY_SWAP = () -> "DOMINANT_AUXILIARY_SWAP";
```

Consumers match by name: `type.name().equals(JungianEvolutionType.DOMINANT_AUXILIARY_SWAP.name())`.

### Why this is non-obvious
The natural instinct is to add a module dependency or use instanceof checks. The default-method approach keeps the module boundary clean — vocabularies that don't have structural relationships simply inherit the no-op default. No dependency added, no instanceof needed, full structural navigation available when the vocabulary supports it.

### Alternatives considered
- **Add runtime→vocab dependency:** Simple but changes the extension's dependency footprint — every consumer gets all well-known vocabularies whether they need them or not.
- **Runtime instanceof after registry resolve:** Requires the vocab class on the classpath, defeating the purpose of the separation.
- **Structural relationship SPI (separate from VocabularyTerm):** Over-engineered for a single method; adds an abstraction layer with no additional consumers.
