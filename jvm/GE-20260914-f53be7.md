## Jandex-based APT can't scan the compiling module's own index — SPI interfaces must live in a dependency JAR

**ID:** GE-20260914-f53be7
**Stack:** Jandex 3.x, javax.annotation.processing, Maven
**Symptom:** An annotation processor that scans `META-INF/jandex.idx` files (e.g. a code generator looking for `@McpDomain` interfaces) generates nothing, despite the annotated interface being in the same module. No error, no warning — just silent absence of generated code.
**Context:** When using an APT that reads Jandex indexes from the classpath (via `ClassLoader.getResources("META-INF/jandex.idx")`), the processor runs during the `compile` phase BEFORE `jandex-maven-plugin` produces the module's own index. The processor only sees indexes from already-compiled dependency JARs.

### What was tried (didn't work)
- Placed `@McpDomain` SPI interface in the same module as the service implementation — APT produced no output
- Verified the interface had the correct annotations — all correct
- Checked APT was registered and running — confirmed via `-Xmessage` notes from other scans
- Expected the jandex-maven-plugin execution order to produce the index before APT — it doesn't; APT runs inside `maven-compiler-plugin:compile`, jandex runs after

### Root cause
Maven compilation lifecycle ordering: annotation processing runs as part of `javac` compilation inside `maven-compiler-plugin:compile`. The `jandex-maven-plugin` runs in the `process-classes` phase — AFTER compilation completes. The APT classpath includes dependency JARs (which have their indexes already built), but the module's own `target/classes/META-INF/jandex.idx` does not exist yet when the processor runs.

### Fix
Place the SPI interface in a separate pre-compiled dependency module (e.g. `platform-api`). The SPI interface itself is pure Java with no module-specific dependencies — only the service implementation belongs in the consuming module. The dependency JAR's Jandex index is already built and available on the APT classpath.

```xml
<!-- In the consuming module's pom.xml -->
<annotationProcessorPaths>
    <path>
        <groupId>io.casehub</groupId>
        <artifactId>casehub-platform-graphql-generator</artifactId>
        <version>${project.version}</version>
    </path>
    <path>
        <!-- SPI interfaces live here — already indexed -->
        <groupId>io.casehub</groupId>
        <artifactId>casehub-platform-api</artifactId>
        <version>${project.version}</version>
    </path>
</annotationProcessorPaths>
```

### Why this fix
The SPI interface is a pure Java contract with zero module-specific dependencies. Moving it to the dependency module doesn't violate any boundary — it's the natural SPI location. The service implementation (which has module-specific dependencies like `CurrentPrincipal`, validators, etc.) stays in the consuming module.

### Why this is non-obvious
The APT compilation model is well-known, but the interaction with Jandex creates a silent failure that's hard to diagnose. There's no error message — the processor simply doesn't find the interface and generates nothing. The developer's mental model ("I put the annotation on the interface, the processor should see it") is correct for `javax.lang.model`-based APTs but wrong for Jandex-based APTs that read pre-built indexes.
