### Symptom

`PlanVersion` record is conceptually a plan-definition type (audit record for plan changes) and should live in `engine-api` per the module boundary protocol (PP-20260727-5267d2: "does a consumer need to import this type? → engine-api"). But placing it in `engine-api` causes a compilation failure because it references `CasePlanModelSnapshot`, which lives in `engine-common`.

```
[ERROR] cannot find symbol
[ERROR]   symbol:   class CasePlanModelSnapshot
[ERROR]   location: class io.casehub.engine.plan.snapshot.PlanVersion
```

### Context

Multi-module Java project with a layered dependency structure: `engine-api` ← `engine-common` ← `engine` (runtime). The boundary protocol's test — "does a consumer need to import this type?" — is necessary but not sufficient. The implicit constraint is: **can the type's imports resolve from the target module's dependencies?**

`engine-api` cannot depend on `engine-common` (that would create a circular dependency since `common` already depends on `api`). Any record in `engine-api` that references a type in `engine-common` will fail to compile regardless of where the record "conceptually" belongs.

### Root cause

The module boundary protocol addresses the consumer-facing question ("where should this type live for consumers?") but not the dependency-resolution question ("can this type compile in that module?"). When a type straddles the boundary — conceptually a plan-definition type but structurally dependent on execution-tier types — the dependency constraint wins.

### Fix

Place the record in `engine-common` alongside the types it references. The trigger and delta types (`PlanVersionTrigger`, `PlanVersionDelta`) that only reference `engine-api` types stay in `engine-api`. The composite record (`PlanVersion`) that ties them to an execution snapshot goes in `engine-common`.

### Why this is non-obvious

The protocol says "plan-definition types → engine-api" and `PlanVersion` is clearly a plan-definition concept. A developer following the protocol would place it in `engine-api` and only discover the error at compile time. The protocol's boundary test needs an addendum: "AND can the type's imports resolve from engine-api's dependency set?"

### Alternatives considered

- Making `CasePlanModelSnapshot` generic or using `Object` for the snapshot field — rejected because it loses type safety and makes the record less useful for consumers
- Moving `CasePlanModelSnapshot` to `engine-api` — rejected because it's genuinely an execution type with execution-tier dependencies of its own
