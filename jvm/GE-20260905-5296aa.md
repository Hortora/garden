## Stateless sweep-based controller converges without persistent state — finite resources guarantee termination

### Context

Building a periodic controller that must eventually resolve a condition (e.g. redistribute overloaded work, drain a queue, clean up stale resources). The natural instinct is to track state between sweeps — retry counts, escalation timers, last-action timestamps — to know what to do next.

### Technique

Make the controller stateless. Each invocation reads ground truth from the store (not from cached state), decides, acts, and exits. The periodic sweep provides retry for free — if the action didn't fully resolve the condition, the next sweep re-evaluates with fresh data and acts again.

Convergence is guaranteed when:
1. **Finite resources** — the condition involves a countable set (e.g. N open obligations, M stale entries)
2. **Monotonic progress** — each successful action reduces the count by ≥1
3. **Termination branches** — every decision path either makes progress, holds (condition resolved), or escalates (can't make progress)

Two guards handle edge cases:
- **Freshness guard** — skip re-triggering expensive operations (e.g. LLM calls) when nothing has changed since the last attempt. Check a monotonic counter (message count, sequence number) before acting.
- **Escalation guard** — when the action is requested but ALL attempts fail (e.g. no routing targets available), fire escalation instead of looping forever. A boolean flag within a single invocation — not persistent state.

Crash recovery is free. If the controller dies mid-action, the next sweep reads current state and picks up wherever things stand. Partially-completed actions are visible as ground truth (e.g. 2 of 5 items moved — next sweep sees 3 remaining).

### Why this is non-obvious

The instinct is to track state: "I tried compression twice, now escalate to redistribution." This requires persistent storage, complicates crash recovery, and creates stale-state bugs when external changes invalidate the tracker. The stateless alternative looks like it can't work — without memory, how does the controller know what it already tried?

The answer: it doesn't need to. The ground truth (resource count, current pressure, store timestamps) encodes everything the controller needs to decide. The policy maps current state to action — no history required. "Am I above the redistribute threshold with obligations to move?" is a present-tense query, not a historical one.
