### What happened

A Micrometer counter (`entries.processed`) was defined to count "entries reaching a terminal state" with outcome tags. An async virtual thread processes each entry while a periodic timeout sweep escalates stale entries. When the sweep escalates an entry that a virtual thread is still processing, both paths increment the counter — the sweep records `outcome=timeout` and the worker records `outcome=status-guard-abort` for the same entry.

### Symptom

The sum of all `entries.processed` outcome tags exceeds the actual number of distinct entries. Dashboard success/failure rate calculations become unreliable.

### Root cause

The counter tracks exit points in the processing code, not distinct entries. Two independent code paths (async worker thread and synchronous sweep) can act on the same entry when a timeout race occurs. Each path increments the counter independently because neither knows the other has already counted the entry.

### Fix

Document the double-counting explicitly in the metric spec. Dashboard builders must not naively sum all outcome tags to compute "total entries processed." Treat `status-guard-abort` as a secondary signal (the sweep already counted the entry as `timeout`). Alternatively, use a separate counter for guard aborts that doesn't contribute to the primary throughput metric.

### Why this is non-obvious

The "entries reaching a terminal state" definition reads as though each entry produces exactly one counter increment. The race window between sweep and worker is narrow and only visible under load. Unit tests with synchronous executors hide the race entirely — you need concurrent integration tests or production traffic to observe the double-count.

### Alternatives considered

- **Skip counter for status-guard-abort entirely:** Loses visibility into sweep-vs-worker races.
- **Use a distributed lock per entry:** Over-engineering for a metrics concern — the business logic is already correct (the status guard prevents execution after sweep).
- **Deduplicate via entry ID tracking in a Set:** Adds memory overhead and complexity for marginal metric accuracy improvement.
