## Quarkus @Scheduled methods silently reject arbitrary CDI bean parameters

**ID:** GE-20260910-c6f648
**Stack:** Quarkus 3.32, CDI (ArC)
**Symptom:** `@Scheduled` method with a CDI bean parameter compiles and the build passes, but at runtime the method either receives null or throws IllegalArgumentException. No compile-time error, no build-time warning.
**Context:** When extracting framework-neutral cores from CDI modules, a common pattern is to create `@Produces` beans in a producer class and add `@Scheduled` wrapper methods in the same class. If the wrapper takes the produced bean as a method parameter, the scheduler silently ignores it.

### What was tried (didn't work)
- Passing CDI beans as `@Scheduled` method parameters (e.g. `void retryTick(DeliveryRetryProcessor processor)`) — compiles, but processor is null/rejected at runtime
- Assuming `@Scheduled` works like `@Observes` which DOES support arbitrary CDI parameter injection — it doesn't

### Root cause
Quarkus `@Scheduled` methods are dispatched by the scheduler runtime, not by the CDI container. Unlike `@Observes` methods (which DO support CDI parameter injection via the container's event dispatch), `@Scheduled` methods have no parameter injection mechanism. The ArC compiler does not flag this as an error — it silently drops the parameter.

### Fix
Use `@Inject` field injection on the enclosing class, then reference fields from zero-arg `@Scheduled` methods:

```java
@ApplicationScoped
public class DispatchBeans {

    @Inject DeliveryRetryProcessor retryProcessor;
    @Inject DigestFlushScheduler digestScheduler;

    @Scheduled(every = "${casehub.delivery.retry.tick-interval:30s}")
    void retryTick() { retryProcessor.tick(); }

    @Scheduled(every = "${casehub.notification.digest.tick-interval:1m}")
    void digestTick() { digestScheduler.tick(); }
}
```

Do NOT pass beans as method parameters:

```java
// WRONG — parameter silently ignored at runtime
@Scheduled(every = "30s")
void retryTick(DeliveryRetryProcessor processor) {
    processor.tick(); // processor is null
}
```

### Alternatives considered
- Using `@Observes`-style parameter injection — rejected because `@Scheduled` is dispatched by the scheduler, not the CDI event system
- Constructor injection on the producer class — works but `@ApplicationScoped` producers with constructor params require careful CDI proxy handling

### Why this is non-obvious
`@Observes` and `@ObservesAsync` methods DO support arbitrary CDI parameter injection — so developers reasonably expect `@Scheduled` to work the same way. The Quarkus documentation doesn't explicitly call out that `@Scheduled` only accepts `ScheduledExecution` as a parameter. The silent compilation success makes this particularly dangerous — it passes all build-time checks and only fails at runtime.

### Why this fix
Field injection with `@Inject` is the idiomatic Quarkus pattern for `@Scheduled` beans. The scheduler invokes zero-arg methods; the enclosing bean's injected fields provide the dependencies. This is well-supported and tested across Quarkus versions.
