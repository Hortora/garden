### Symptom

After tightening a validation in a CDI registry's `@PostConstruct` path (changing a WARNING to an `IllegalArgumentException`), Quarkus fails to start for ALL `@QuarkusTest` classes in the module — not just the test you're working on.

Error: `java.lang.RuntimeException: Failed to start quarkus` with the validation exception buried in the cause chain. The error message does not identify which CDI bean triggered the failure.

### Context

Quarkus CDI (ArC) discovers ALL `@ApplicationScoped` beans across the entire test classpath at startup — including `static` inner classes of unrelated test files. When a registry's `@PostConstruct` method calls `registerKnownDefinitions()`, it iterates every discovered bean and validates it. A validation change affects every bean, not just the one you intended.

### Root cause

`@QuarkusTest` does not isolate CDI bean discovery per test class. ALL beans annotated `@ApplicationScoped` (including inner classes of other test files) are instantiated and registered during Quarkus startup. A stricter validation in the registration path becomes a global gate.

### Fix

When tightening validation in a CDI startup path, search the entire test classpath for beans that would fail the new validation:

```java
// Search for all test beans that define goals without completion expressions
ide_search_text(".goals(", filePattern="*Test*.java")
// Then check each for .completion( — those without it will fail
```

Fix ALL affected test beans before the validation change, not just the tests you're running.

### Why this is non-obvious

You'd expect that changing a WARNING to an exception only affects code that triggers the specific warning condition in the test you're running. But CDI bean discovery is module-wide — a `CaseHub` inner class in `ScheduleTriggerSimpleTest.java` affects `DefaultCaseDefinitionRegistryGoalWarningTest.java` because both classes are discovered in the same Quarkus startup.
