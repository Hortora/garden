## WebClient.create(Vertx.vertx()) per HTTP call silently leaks Vert.x event loop groups

### Symptom

No immediate error. Over time, thread count grows and file descriptors are exhausted. Each `Vertx.vertx()` call creates a new event loop group (default: 2× CPU cores threads) that is never shut down. In a Quarkus app handling moderate traffic, this produces hundreds of orphaned threads within hours.

### Context

A non-CDI helper class (e.g. OAuth2 token client, external API adapter) makes HTTP calls using Vert.x WebClient. The helper is instantiated inside a CDI producer, not as a CDI bean itself. Each HTTP method in the helper creates `WebClient.create(Vertx.vertx())` inline:

```java
private HttpResponse<Buffer> post(String url) {
    WebClient client = WebClient.create(Vertx.vertx());
    return client.postAbs(url).send()
            .toCompletionStage().toCompletableFuture()
            .get(30, TimeUnit.SECONDS);
}
```

### What was tried (didn't work)

- Creating `WebClient` per method call without `Vertx.vertx()` — `WebClient.create()` requires a `Vertx` instance, so developers reach for `Vertx.vertx()` as the obvious factory
- Calling `vertx.close()` after each request — breaks the WebClient's internal connection pool and defeats connection reuse

### Root cause

`Vertx.vertx()` is a factory that creates a **full Vert.x instance** with its own event loop group, file resolver, and internal timer. It is not a lightweight accessor — the method name is misleading. `WebClient.create(vertx)` wraps this instance but does not own its lifecycle. Neither the WebClient nor the Vertx instance is closed after the HTTP call completes. The event loop threads remain alive indefinitely.

In a Quarkus application, the framework manages a single `Vertx` instance (injectable via `@Inject Vertx vertx`). This managed instance is shared across the application and shut down when Quarkus stops.

### Fix

Inject the Quarkus-managed `Vertx` via CDI into the producer, pass it through the constructor, and create `WebClient` once as a field:

```java
// CDI producer passes Vertx
@Produces @Singleton
public MyClient create(@ConfigProperty(...) String apiBase,
                        Vertx vertx) {  // Quarkus-managed
    return new MyClient(apiBase, vertx);
}

// Helper creates WebClient once
public class MyClient {
    private final WebClient webClient;

    public MyClient(String apiBase, Vertx vertx) {
        this.webClient = WebClient.create(vertx);
    }

    private HttpResponse<Buffer> post(String url) {
        return webClient.postAbs(url).send()
                .toCompletionStage().toCompletableFuture()
                .get(30, TimeUnit.SECONDS);
    }
}
```

### Why this is non-obvious

`Vertx.vertx()` reads like a static accessor ("get the Vert.x instance"), not a factory ("create a new Vert.x runtime"). Developers familiar with patterns like `Logger.getLogger()` or `ObjectMapper` singletons expect `Vertx.vertx()` to return a shared instance. The leak is completely silent — no error, no warning, no log entry. The symptom (thread/FD exhaustion) appears hours or days later and looks like a JVM-level problem, not an application code issue.

### Alternatives considered

- Creating a static `Vertx` field in the helper class — avoids per-call creation but produces an unmanaged instance that outlives the Quarkus lifecycle and isn't shut down on hot-reload
- Using `@ApplicationScoped` on the helper class directly — would let CDI inject `Vertx`, but changes the class from a plain POJO to a CDI proxy, which may not be appropriate for all use cases (e.g. classes that need constructor parameters)
