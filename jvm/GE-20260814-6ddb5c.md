### Symptom
A JAX-RS endpoint returns 409 Conflict on every request, even after fixing and reloading the code that caused the original failure. The 409 persists until the entire Quarkus dev mode process is killed and restarted.

### Context
An endpoint uses a `ConcurrentHashMap.newKeySet()` as a concurrency guard (`guardStart`/`guardEnd` pattern) to prevent duplicate analysis runs. The guarded operation throws an exception. The `finally` block calls `guardEnd` — but the exception triggers a Quarkus class reload.

### Root cause
Quarkus dev mode reloads classes but preserves static fields and CDI singletons across reloads. The `ConcurrentHashMap` instance holding the guard keys survives the reload. The `guardEnd` in the `finally` block may or may not execute before the class reload — if the reload interrupts it, the key stays in the set permanently.

Even with a proper `try/finally`, the guard can get stuck if the exception propagates through Quarkus's error handling and triggers a reload before the `finally` block completes.

### Fix
Remove concurrency guards from endpoints where they're not essential (simple analysis runs), or make the guard self-healing:

```java
// Instead of a static guard that persists across reloads:
private static final Set<String> inProgress = ConcurrentHashMap.newKeySet();

// Use a guard with TTL or skip the guard entirely for non-critical operations
```

For critical guards, add a timeout-based cleanup or move the guard to a CDI `@RequestScoped` bean that is recreated per request.

### Why this is non-obvious
The `try/finally` pattern is the standard way to ensure cleanup. In a normal JVM lifecycle this works perfectly. Quarkus dev mode's class reload breaks the assumption that `finally` blocks always complete before the next request is served.
