### Symptom
Scenario starts (status "running"), but no character events, dialogue, or movement appear.
LlmSmokeTest passes — proving the LLM pipeline works. The UI shows an empty running scenario.

### Context
`ScenarioOrchestrator.runScenario()` validates that every character in `WorldState` has an
Eidos descriptor. The world YAML defines 17 characters, but only a configurable subset
(`manor.scenario.active-characters`) will actually run agent loops. Characters like `lazy-luke`
intentionally have no Eidos descriptor — they are world furniture, not active agents.

### What was tried (didn't work)
- Assumed the LLM integration was broken in dev mode (the handover said "character threads die on first LLM call")
- Added diagnostic logging to CharacterAgentLoop — but character threads were never created
- Checked API key configuration, process spawning, port conflicts

### Root cause
The validation loop at line 101 checked ALL 17 world characters for descriptors:
```java
for (var entry : world.characters().entrySet()) {
    if (agentRegistry.findById(entry.getKey(), ...).isEmpty()) {
        throw new IllegalStateException("No Eidos descriptor for character: " + entry.getKey());
    }
}
```
The `activeSet` filter was computed 10 lines later (line 110). Characters without descriptors
threw `IllegalStateException`, killing the `scenario-loop` virtual thread before any character
threads were created. The exception was uncaught — no error in the UI or REST response.

### Fix
Move the `activeSet` computation before the validation loop and skip non-active characters:
```java
var activeSet = activeCharactersConfig.filter(s -> !s.isBlank())
    .map(s -> java.util.Set.copyOf(java.util.Arrays.asList(s.split(","))))
    .orElse(null);
for (var entry : world.characters().entrySet()) {
    if (activeSet != null && !activeSet.contains(entry.getKey())) continue;
    // ... validate
}
```

### Why this is non-obvious
The symptom ("characters don't produce events") points directly at the LLM integration or
character loop, not at a validation ordering bug in the orchestrator. The LlmSmokeTest passing
reinforces the wrong hypothesis. The actual crash is in a virtual thread with no handler
propagating the error to the REST response or UI — the scenario appears to be running normally.

### Alternatives considered
- Adding descriptors for all 17 characters — rejected: most characters are world furniture, not active agents. Adding descriptors would require personality definitions for characters that don't need them.
