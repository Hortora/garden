### Context
A batch job detects a condition (e.g. safety signal), persists a domain record, creates a WorkItem for human review, and sends a notification (Slack/email). The naive approach puts all three in one `REQUIRES_NEW` transaction.

### What was tried (didn't work)
Single `REQUIRES_NEW` transaction containing domain persistence + WorkItem creation + notification. Three failures:

1. **No error isolation:** `WorkItemService.create()` throws → entire transaction rolls back → domain record lost. The spec claims "signal record persisted even if WorkItem creation fails" but the transaction boundary makes this impossible.

2. **Phantom notifications:** `Connector.send()` fires inside the transaction. If the transaction later rolls back (e.g. constraint violation during flush), the notification references a WorkItem that was never persisted. DSMB receives a Slack message for a non-existent WorkItem.

3. **Agroal pool exhaustion:** `Connector.send()` makes an HTTP call to Slack while holding a DB connection from the Agroal pool. Under concurrent load, all connections are held waiting on external HTTP responses. This is the exact anti-pattern that motivated the `DurableSponsorNotifier` rewrite (ARC42STORIES §9.4).

### Fix
Split into two phases with notification post-commit:

```java
void upsertSignalRecord(UUID trialId, DetectedSignal signal, String tenantId) {
    // Phase 1: persist domain record (always succeeds independently)
    UpsertResult result = QuarkusTransaction.requiringNew().call(() -> {
        // ... insert or update domain record ...
        return new UpsertResult(recordId, needsWorkItem);
    });

    // Phase 2: create WorkItem (separate transaction, try-catch)
    if (result.needsWorkItem()) {
        try {
            UUID workItemId = QuarkusTransaction.requiringNew().call(() -> {
                var wi = workItemService.create(/* ... */);
                // Update domain record with workItemId
                DomainRecord rec = DomainRecord.findById(result.recordId());
                if (rec != null) rec.workItemId = wi.id;
                return wi.id;
            });
            // Notification fires AFTER Phase 2 commits — no phantom messages
            notifier.notify(trialId, signal, workItemId);
        } catch (Exception e) {
            LOG.warnf(e, "WorkItem creation failed — domain record persisted, deferred to next run");
        }
    }
}
```

**Three anti-patterns avoided:**
- **Error isolation:** Phase 1 commits independently. WorkItem failure in Phase 2 does not roll back the domain record.
- **No phantom notifications:** `notifier.notify()` runs after Phase 2's transaction commits. If Phase 2 rolls back, no notification fires.
- **No Agroal exhaustion:** The external HTTP call (`Connector.send()`) runs outside any transaction boundary. No DB connection is held.

### Why this is non-obvious
The naive single-transaction approach compiles, passes basic tests, and "works" in dev. The three failure modes only manifest under specific conditions: WorkItem validation failure (rare), concurrent flush conflicts (load-dependent), and pool exhaustion (scale-dependent). A design review caught all three before implementation — the code would have shipped without them.

### Why this fix
The two-phase split is the minimal structural change. Alternatives (saga pattern, event-driven WorkItem creation, durable retry queue) add complexity without proportional benefit for a batch job that runs every 24h. The self-healing property (WorkItem deferred to next run) is adequate for non-real-time workflows.

### Alternatives considered
- **Single transaction with try-catch around WorkItem creation only:** Prevents domain rollback but still fires notification inside the transaction (phantom risk) and holds DB connection during HTTP call (pool risk)
- **CDI async observer for WorkItem creation:** Decouples but introduces CDI observer ordering concerns and loses the idempotency check (observer can't easily query the domain record's workItemId)
- **Durable retry queue (DurableSponsorNotifier pattern):** Overkill for a 24h batch job — the next scheduled run is the natural retry mechanism
