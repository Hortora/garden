## Symptom

An `@ObservesAsync` observer (e.g. an event logger writing to a database) starts failing — DB connection down, constraint violation, anything that throws. On the `CreateCase` path (fire-and-forget, no `.join()`), nothing visible happens — the observer failure is silently swallowed. On the `NotifyOnly` path (`.toCompletableFuture().join()`), the entire trigger flow fails and resets — the trigger claim is rolled back as if the trigger never happened.

The asymmetry is the gotcha: the same observer, processing the same event type, silently fails on one path and crashes the producer on another.

## Context

`SituationEvaluator.executeDecision()` has two trigger delivery paths:
- **CreateCase:** `changeEvent.fireAsync(...)` — fire and forget, no `.join()`
- **NotifyOnly:** `changeEvent.fireAsync(...).toCompletableFuture().join()` — blocks, exception propagates

When a new `@ObservesAsync` observer is added (e.g. `SituationEventRecorder` for the event log), it receives events from both paths. If it throws, the CreateCase path is unaffected but the NotifyOnly path fails.

## Root cause

CDI 4.0 spec: `Event.fireAsync()` returns a `CompletionStage` that completes exceptionally if any `@ObservesAsync` observer throws. When the producer calls `.join()`, `CompletionException` wraps the observer's exception and propagates to the producer thread. Without `.join()`, the `CompletionStage` is discarded and the exception is lost.

## Fix

Wrap all `@ObservesAsync` observer logic in try-catch when the observer cannot guarantee that no event producer will `.join()` the `CompletionStage`:

```java
@Transactional
void onSituationChange(@ObservesAsync SituationChangeEvent event) {
    try {
        SituationEventEntity entity = project(event);
        em.persist(entity);
    } catch (Exception e) {
        LOG.warning("Failed to record situation event: " + e.getMessage());
    }
}
```

The observer is best-effort — its failure must never propagate to the event producer.

## Why this is non-obvious

The observer has no way to know whether the producer will `.join()`. The CDI spec says nothing about exception delivery semantics being dependent on how the producer consumes the `CompletionStage`. Developers adding a new observer to an existing event type don't naturally check all fireAsync() call sites to determine which consume the result.

### Alternatives considered

- **Remove `.join()` from NotifyOnly path:** breaks the synchronous delivery guarantee that NotifyOnly relies on (trigger claim reset on delivery failure).
- **Separate event types for fire-and-forget vs. joined:** over-engineering; the observer should be self-contained regardless of producer behavior.
