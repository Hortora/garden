### Symptom
Designing a CNN model with `[batch, W, F]` input shape — `InferenceInput.Tensor` appears to support arbitrary tensor input via `Map<String, float[][]>`, but `float[][]` creates rank-2 ONNX tensors only. A 3D input `[batch, W, F]` cannot be represented.

### Context
`InferenceInput.Tensor` was designed for NLP-style models where inputs are rank-2 `[batch, features]`. When building a 1D-CNN for time-series classification (e.g., SC2 strategy classifier with `[batch, time_windows, features_per_window]`), the API constraint surfaces at ONNX export time — the model needs rank-3 input but can only receive rank-2.

### Root cause
`InferenceInput.Tensor` stores `Map<String, float[][]>`. `OnnxInferenceModel.runTensor()` calls `OnnxTensor.createTensor(env, entry.getValue())` which creates a rank-2 tensor from `float[][]`. There is no path to create rank-3+ tensors through the SPI.

### Fix
Accept flattened `[batch, W*F]` (rank-2) as the ONNX model input and reshape internally:

```python
class OnnxWrapper(torch.nn.Module):
    def __init__(self, model, max_windows, f_temporal):
        super().__init__()
        self.model = model
        self.max_windows = max_windows
        self.f_temporal = f_temporal

    def forward(self, temporal_flat, map_feat):
        temporal = temporal_flat.view(-1, self.max_windows, self.f_temporal)
        return self.model(temporal, map_feat)
```

Java caller flattens: `InferenceInput.tensor(Map.of("temporal", new float[1][W*F]))`.
The ONNX Reshape op handles the unflatten cleanly at inference time.

### Why this is non-obvious
The `InferenceInput.Tensor` API looks general-purpose — `Map<String, float[][]>` suggests any tensor input. The rank-2 constraint is not documented and only surfaces when you try to use it for models that aren't NLP-shaped. The fix (flatten + internal reshape) is architecturally clean but requires the ONNX model to embed the reshape, which inverts the normal responsibility (caller provides the right shape, model consumes it).

### Alternatives considered
- Extending `InferenceInput` with a `Tensor3D` variant — rejected as scope expansion for a single use case
- Using `float[1][W*F]` directly without the wrapper — works but pushes reshape logic onto every Java caller
