### Symptom
When extracting factory logic from a Quarkus `@Recorder` into a separate `-core` module, a cyclic Maven dependency appears: core needs runtime for descriptor types, runtime needs core for factories.

### Context
Core extraction pattern: extract framework-neutral POJOs from Quarkus modules so Spring Boot can consume them. The Recorder (e.g. `DesiredStateGraphRecorder`) contains factory methods that create `GoalCompiler` from `GraphDescriptor` records. Both the Recorder and the descriptor records live in the same `annotations/runtime` module.

The natural instinct is to create `annotations/core` with the factory class. But the factory needs `GraphDescriptor` (in runtime), and the slimmed Recorder needs the factory (in core) → cycle.

### What was tried (didn't work)
Created `annotations/core` with `GoalCompilerFactory`, added `annotations/runtime` as a dependency of core (for descriptor types), then added `annotations/core` as a dependency of runtime (for the Recorder to delegate to the factory). Maven rejects the cycle at reactor resolution time.

### Root cause / Fix
Put the factory in the **same module** as the types it consumes — not in a separate module. The factory is framework-neutral (no CDI annotations), but it lives alongside the Recorder in `annotations/runtime`.

```
annotations/runtime/    ← factories + descriptors + Recorder (thin delegate)
annotations/core/       ← DescriptorScanner only (depends on runtime for types)
```

The Recorder delegates to the factory in the same package (no import needed). The Spring auto-config depends on `annotations/runtime` (for factories + types) and `annotations/core` (for the scanner). No cycle.

This follows the platform pattern: Spring modules depend on Quarkus runtime modules as `provided` scope — `quarkus-core` is just annotations (`@Recorder`), not a CDI runtime.

### Why this is non-obvious
The core extraction pattern suggests "framework-neutral code goes in -core". But when the factory's types ARE in the framework-adjacent module, moving only the factory creates a cycle. The resolution is that "framework-neutral" means "no CDI annotations" — it does NOT mean "must be in a separate module". A class without `@ApplicationScoped` can live in a module that has Quarkus dependencies without being coupled to Quarkus.
