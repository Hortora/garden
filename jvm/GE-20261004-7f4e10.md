### Symptom

Generated Java source fails to compile with:

```
cannot find symbol
  symbol:   class Publisher
  location: package java.util.concurrent
```

The generated file contains `import java.util.concurrent.Flow$Publisher;` — the JVM internal class name for the nested `Flow.Publisher` interface.

### Context

When a Java interface method returns `java.util.concurrent.Flow.Publisher<T>` and a Jandex-based code generator (annotation processor, Maven plugin, or build-time tool) produces Java source from bytecode metadata, the generator must convert Jandex `DotName` values to valid Java source import statements.

Triggered when:
- The scanned interface uses `Flow.Publisher<T>` (JDK 9+ Reactive Streams)
- The code generator uses `DotName.toString()` directly for import generation
- The generated source is compiled as part of the same build

### What was tried (didn't work)

Using `java.util.concurrent.Flow.Publisher<T>` as the return type on an `@McpDomain` SPI interface. The annotation processor scanned the interface, generated a JAX-RS resource delegating to it, and emitted `import java.util.concurrent.Flow$Publisher` — producing a compilation failure.

### Root cause

Jandex represents nested/inner classes using the JVM `$` separator internally. `DotName.toString()` for `Flow.Publisher` returns `java.util.concurrent.Flow$Publisher`. Code generators that pass this string directly to an import statement builder produce invalid Java source. The `$` is the JVM bytecode convention for inner classes, not valid Java source syntax.

This affects any nested class, not just `Flow.Publisher` — but `Flow.Publisher` is the most commonly encountered case because it's the standard JDK reactive type that developers use on SPI interfaces.

### Fix

**Option 1 — Fix the generator:** When converting Jandex `DotName` to Java source imports, detect `$` in the class name. Split on `$`, import the outer class (`java.util.concurrent.Flow`), and use the qualified form (`Flow.Publisher<T>`) in method signatures.

**Option 2 — Avoid the trigger:** Don't use `Flow.Publisher` on interfaces scanned by the affected generator. Use a concrete type like Mutiny `Multi<T>` (which implements `Flow.Publisher<T>` in Mutiny 3.x) directly on the interface. The generator handles `Multi<T>` correctly because it's a top-level class, not a nested one.

### Why this is non-obvious

The error message (`cannot find symbol: class Publisher`) points at the generated source, not the generator itself. The developer's first instinct is to check whether `Flow.Publisher` is on the classpath — it is. The issue is in the import statement syntax, not the classpath. The `$` vs `.` distinction is a JVM internals detail that most Java developers don't encounter in source code.
