### Symptom
Compilation error when implementing `PlanRevisionStrategy` in an application module:
```
class is not allowed to extend sealed class: io.casehub.engine.plan.adaptation.AdaptationCause
(as it is not listed in its 'permits' clause)
```

### Context
`RevisionContext` (parameter to `PlanRevisionStrategy.revise()`) requires an `AdaptationCause` to describe why revision was triggered. Natural instinct is to create application-specific cause types (e.g. `ActionFailureCause`, `ReflectionCause`).

### Root cause
`AdaptationCause` is a sealed interface permitting only two subtypes:
- `AdaptationCause.StepFailed(String stepId, String reason)`
- `AdaptationCause.StepCompleted(String stepId, String capabilityName, Map<String, Object> output)`

Both are `final` records — no subclassing.

### Fix
Repurpose the existing permitted subtypes with application-specific semantics:

**For action failures:** Use `StepFailed` — encode action context in `stepId` (e.g. `"MOVE:kitchen"`), failure reason in `reason`.

**For reflection/strategic triggers:** Use `StepCompleted` — set `stepId` to `"reflection"`, `capabilityName` to `""`, encode insights in `output` map (e.g. `Map.of("insights", List.of("HC is suspicious"))`).

The `PlanRevisionStrategy` implementation pattern-matches on these types to build the appropriate LLM prompt.

### Why this is non-obvious
`javap -p` shows `AdaptationCause` as a plain `public interface` — the sealed constraint is only visible in the bytecode `PermittedSubclasses` attribute (or by reading the source). Nothing in the `PlanRevisionStrategy` Javadoc hints that cause types are restricted.

### Alternatives considered
- Requesting the engine team to unseal the interface — rejected as disproportionate change for a pre-release project
- Making revision strategy manor-local (not implementing the SPI) — loses the SPI contract

### Constraints
Applies to any application implementing `PlanRevisionStrategy` outside the `io.casehub.engine.plan.adaptation` package.
