## IntelliJ MCP ide_replace_text_in_file writes to in-memory Document buffer — changes invisible to Maven/javac until ide_sync_files flushes to disk

**Stack:** IntelliJ MCP, Maven 3.x, javac

### Symptom

After using `ide_replace_text_in_file` to patch a Java source file, `mvn clean install` reports BUILD SUCCESS but the compiled bytecode does not contain the changes. The fix appears to be applied (the tool reports "1 replacement made") but has no effect on the build output. Repeated rebuilds, cache clears, and jar replacements all produce the same stale bytecode.

### Context

Patching an annotation processor (`GraphQLResolverProcessor`) via `ide_replace_text_in_file` to add a one-line fix (`kebab.replace('/', '-')`). The tool confirms the replacement. Reading the file back via IntelliJ shows the fix. But `mvn clean install` compiles the old version — the fix never reaches the bytecode.

### What was tried (didn't work)

- Verified the `.m2` jar had the correct MD5 — it matched the target jar
- Disassembled the bytecode with `javap -c` — the fix appeared in the constant pool but was from a DIFFERENT version of the jar
- Deleted and reinstalled the jar multiple times
- Killed Maven daemons, used `-o` offline mode
- Added debug print statements via `ide_replace_text_in_file` — they appeared in IntelliJ's view but not in the compiled output

### Root cause

`ide_replace_text_in_file` uses IntelliJ's Document API to modify the in-memory text buffer. This is visible to IntelliJ (including Read tool which reads through IntelliJ) but is NOT flushed to the filesystem until either:
1. IntelliJ's auto-save fires (configurable delay, typically seconds to minutes)
2. `ide_sync_files` is called explicitly
3. The IDE performs certain internal operations

`mvn compile` / `javac` reads source files directly from the filesystem, not from IntelliJ's buffer. If the Document buffer hasn't been flushed to disk when the build runs, the compiler sees the OLD file content.

### Fix

After any `ide_replace_text_in_file` edit that will be followed by an external build tool (Maven, Gradle, javac), call `ide_sync_files` to flush the Document buffer to disk:

```
ide_replace_text_in_file(file="path/to/File.java", searchText="...", replaceText="...")
ide_sync_files(paths=["path/to/File.java"], project_path="...")
# NOW run mvn compile — disk file matches the edit
```

Alternatively, for cross-project patches where IntelliJ might not flush reliably, use the Edit tool with `replace_all: true` instead — it writes directly to disk.

### Why this is non-obvious

The tool reports success ("1 replacement made") and the Read tool confirms the change is present — because both operate through IntelliJ's in-memory buffer. There is no indication that the disk file differs. The symptom (stale bytecode) points at Maven caching, jar resolution, or annotation processor classpath issues — not at the source file being stale. Multiple diagnostic approaches (bytecode disassembly, MD5 comparison, cache clearing) all appear to confirm the fix is present, leading to extended debugging of the wrong problem.

### Why this fix

`ide_sync_files` is the canonical IntelliJ API for flushing VFS changes to disk. It's the same mechanism IntelliJ uses internally before running external tools. The alternative (using Edit tool) bypasses IntelliJ entirely but loses the benefits of Document-level editing (undo, PSI consistency).

### Alternatives considered

- Using the Edit tool exclusively for cross-project patches — works but bypasses IntelliJ's type awareness and may trigger intellij-first-edit hooks
- Adding explicit delays after `ide_replace_text_in_file` to wait for auto-save — fragile, non-deterministic, and the auto-save interval is configurable
