## CaseHub AgentProvider CDI tiering

### Symptom
Injecting `AgentProvider` gives different implementations depending on which modules are on the classpath. No documentation describes which implementation wins or how to control it.

### Context
`AgentProvider` is the platform SPI for AI agent invocation (single-shot and multi-turn sessions). Multiple implementations exist — the active one is selected by CDI `@Alternative @Priority` tiering based on classpath presence.

### Fix
The tiering (discovered by reading source):

| Tier | Class | Module | Annotation | When active |
|------|-------|--------|------------|-------------|
| 0 | `NoOpAgentProvider` | `casehub-platform` | `@DefaultBean` | Always (fallback) |
| 1 | `ChatModelAgentProvider` | `casehub-platform-agent-langchain4j` | `@Alternative @Priority(1)` | langchain4j adapter on classpath |
| 10 | `ClaudeAgentProvider` | `casehub-platform-agent-claude` | `@Alternative @Priority(10)` | Claude Agent SDK on classpath |

Highest priority wins. `NoOpAgentProvider` logs a WARN and returns empty streams — useful for detecting misconfiguration in dev.

App code always injects `AgentProvider`, never the concrete implementations. To get the Claude provider, add `casehub-platform-agent-claude` as a dependency.

### Why this is non-obvious
The tiering is defined across three separate modules with no central documentation. The `@DefaultBean` / `@Alternative @Priority` mechanism is standard Quarkus CDI, but the specific priority values and which module provides which tier are only discoverable by reading each implementation class. The NoOp fallback silently degrades — the only signal is a WARN log line that's easy to miss.
