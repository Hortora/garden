### Symptom

A `@ConsumeEvent @RunOnVirtualThread` handler for event B queries state that event A's handler should have written, but finds empty/stale results. No error, no warning. The query returns zero results even though event A was published before event B.

### Context

Two Vert.x event-bus events are published sequentially in the same method:

```java
eventBus.publish(ADDRESS_A, eventA);  // handler writes to database
eventBus.publish(ADDRESS_B, eventB);  // handler queries database for A's writes
```

Both handlers are `@ConsumeEvent @RunOnVirtualThread`. They execute on separate virtual threads with no ordering guarantee. Handler B may query the database before handler A has committed its write.

In casehub-engine, this manifests when `WorkflowExecutionCompletedHandler` publishes validation results via an async event AFTER `CONTEXT_CHANGED`. The adaptation evaluator (triggered by `CONTEXT_CHANGED`) queries EventLog for validation entries that haven't been written yet.

### What was tried (didn't work)

1. Publishing the validation event BEFORE `CONTEXT_CHANGED` — still no ordering guarantee between the two virtual threads
2. Using `eventBus.request()` (blocking send-and-reply) — adds latency to the critical path and changes the handler contract

### Root cause

`eventBus.publish()` is fire-and-forget. Each `@ConsumeEvent @RunOnVirtualThread` handler spawns on its own virtual thread. The JVM scheduler makes no ordering promise between virtual threads spawned from the same caller in sequence. Handler A and handler B are genuinely concurrent.

### Fix

Compute the state synchronously inline — do not delegate to an async event handler when a downstream consumer of a later event needs the result. Write the data (e.g., to EventLog metadata) before publishing the event that triggers the consumer.

```java
// Wrong — async handler may not complete before CONTEXT_CHANGED consumer reads it
ExpectationValidationResult result = validator.validate(...);
writeValidationEventLog(result);  // async handler writes this
eventBus.publish(CONTEXT_CHANGED, ...);  // consumer queries validation EventLog

// Right — synchronous inline, data available before downstream consumer runs
ExpectationValidationResult result = validator.validate(...);
enrichMetadataWithValidation(eventLog, result);  // synchronous, same thread
eventLogRepository.append(eventLog);              // committed before next publish
eventBus.publish(CONTEXT_CHANGED, ...);           // consumer sees the data
```

Keep only truly independent observability signals (dashboards, alerting) as async fire-and-forget events.

### Why this is non-obvious

The sequential `publish()` calls look like they establish an ordering — "A happens, then B happens." In synchronous or single-threaded systems this is true. With `@RunOnVirtualThread`, each publish spawns an independent virtual thread. The JVM's virtual thread scheduler provides no FIFO guarantee — a thread spawned later may execute first.

The symptom (empty query results) points to the database or query logic, not to event ordering. Debugging naturally starts in the wrong place because the publish calls look sequential.
