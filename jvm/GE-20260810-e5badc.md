## Symptom

Error handling documentation or design specs say "batch TrustScoreJob catches up on next run" when `LedgerEntryRepository.saveAttestation()` fails. This creates a false sense of safety.

## Context

When an application writes trust attestations (e.g., on case resolution), each `saveAttestation()` call uses `@Transactional(TxType.REQUIRES_NEW)`. If the call fails (DB unavailable, connection pool exhausted), the attestation is never persisted.

## Root cause

`TrustScoreJob` (nightly batch) and `IncrementalTrustUpdateObserver` (per-attestation) both operate exclusively on **existing** `LedgerAttestation` records in the database. They recompute `ActorTrustScore` Bayesian Beta parameters (α, β) from persisted attestations. Neither mechanism can detect or recreate attestations that were never persisted.

The batch job recalculates scores — it does not generate attestation records. A failed `saveAttestation` means the quality signal from that case resolution is permanently lost.

## Fix

Acknowledge the limitation in error handling. Do not claim batch recovery exists. For v1, log the failure and accept the data loss:

```java
try {
    ledgerRepo.saveAttestation(attestation, tenancyId);
} catch (Exception e) {
    LOG.errorf(e, "Failed to save attestation for entryId=%s — attestation permanently lost", entry.id);
}
```

For production systems requiring higher reliability, implement a dead-letter/retry mechanism that re-derives attestations from the source event.

### Alternatives considered

- Wrapping the entire attestation loop in a single transaction — does not help because `saveAttestation` uses `REQUIRES_NEW` internally, so each save is independent regardless.
- Relying on CDI event replay — `@ObservesAsync` may replay events, but this is best-effort and not guaranteed.

## Why this is non-obvious

The name "TrustScoreJob" and the documentation pattern "batch job catches up" strongly imply the batch process is a safety net for transient failures. A developer would reasonably expect it to reconstruct missing data. The actual behavior (score recomputation from existing records only) is correct but the implication of "catching up" is misleading.

### Why this fix

Honest error handling is better than a false safety net. The batch job cannot be made to recreate attestations without knowing the original source event context (analyst outcome, case resolution data). A proper fix requires a separate dead-letter queue with the original event payload — a significantly larger infrastructure change.
