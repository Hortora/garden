### Symptom
When dispatching to CDI beans via reflection, interceptors (`@Transactional`, `@RolesAllowed`, custom interceptors) must fire. Direct `new` construction or field access bypasses the interceptor chain entirely.

### Context
Reflection-based dispatch (e.g., MCP action handler calling GraphQL resolver methods by name) needs the CDI proxy, not the raw bean instance. The proxy IS the interceptor chain — without it, security, transaction, and custom interceptors are silently skipped.

### Fix
Always obtain the bean via `CDI.current().select()`:

```java
// Correct — returns CDI proxy, interceptors fire on invoke
Object resolverBean = CDI.current().select(op.resolverClass()).get();
Method method = op.method();
method.invoke(resolverBean, args);  // interceptors fire

// Wrong — raw instance, no interceptors
Object raw = new MyResolver();
method.invoke(raw, args);  // @Transactional, @RolesAllowed silently skipped
```

### Why this is non-obvious
The reflection API doesn't care about CDI — `Method.invoke()` works on any object. The distinction between proxy and raw instance is invisible at the call site. Code that works correctly in unit tests (where CDI isn't active) silently loses security and transaction guarantees in production if the wrong instance is used.
