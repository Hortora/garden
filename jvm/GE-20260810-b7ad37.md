## Symptom

Filtering `WorkerDecisionEntry` records by capability tag returns zero results despite workers having run for the matching capability.

## Context

CaseHub applications define capabilities in two places with different naming conventions:
1. **Case YAML bindings** — unprefixed names: `ioc-enrichment`, `attck-mapping`, `containment-recommendation`
2. **Eidos agent registration** (`SocCapabilities`, `AgentDescriptor`) — prefixed tags: `soc:host-isolation`, `soc:credential-revocation`

Both are called "capability" in their respective contexts.

## Root cause

`WorkerDecisionEntry.capabilityTag` is populated by the engine from the case YAML binding's capability name — the unprefixed form (e.g., `containment-recommendation`). It does NOT use the eidos agent-registration tags.

If an app defines both `SocCapabilities` (eidos tags) and capability names in the case YAML, filtering `WorkerDecisionEntry.capabilityTag` against `SocCapabilities` constants will silently match nothing.

## Fix

Define separate constants for case-YAML capability names, distinct from eidos agent-registration tags:

```java
// Case-YAML capability names (what WorkerDecisionEntry.capabilityTag carries)
public final class SocCaseCapabilities {
    public static final String IOC_ENRICHMENT = "ioc-enrichment";
    public static final String CONTAINMENT_RECOMMENDATION = "containment-recommendation";
}

// Eidos agent-registration tags (different namespace, different purpose)
public final class SocCapabilities {
    public static final String HOST_ISOLATION = "soc:host-isolation";
    public static final String CREDENTIAL_REVOCATION = "soc:credential-revocation";
}
```

Use `SocCaseCapabilities` constants when filtering `WorkerDecisionEntry` records.

## Why this is non-obvious

Both constant classes are named `*Capabilities`. Both contain capability-related strings. The `soc:` prefix difference is subtle and easy to miss when scanning code. A developer looking for "the containment capability constant" would naturally reach for `SocCapabilities` first, since it already exists and has containment-related entries.
