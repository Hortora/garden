## Jackson @JsonSubTypes sealed interface blocks custom YAML type discriminators

### Symptom

Consumer writes a YAML file referencing a custom type name (e.g. `type: clearance`) in a polymorphic field. Deserialization fails with `InvalidTypeIdException: Could not resolve type id 'clearance' as a subtype of ...` even though a runtime registry exists to handle custom types.

### Context

When a YAML spec uses Jackson `@JsonTypeInfo` with `@JsonSubTypes` on a sealed interface, the set of valid type discriminators is closed at compile time. The runtime registry (e.g. `ObservationFilterRegistry`) that resolves compiled specs to runtime objects operates *after* deserialization — it never gets a chance to run because Jackson rejects the unknown type name during parsing.

### Root cause

Jackson's `@JsonSubTypes` is a static annotation — it defines the closed set of valid type discriminators. Sealed interfaces reinforce this: the compiler enforces that all subtypes are declared. There is no Jackson SPI for dynamically adding new subtypes to a `@JsonSubTypes` set at deserialization time.

### Fix

Custom logic must register under an *existing* type name in the runtime registry, not introduce a new discriminator. The YAML uses a known type (e.g. `type: perception`), and the consumer overrides that type's behavior via the registry:

```java
// Override the built-in perception filter with custom clearance logic
filterRegistry.register("perception", () ->
    (sections, observerTags) -> sections.stream()
        .filter(s -> !(s instanceof AnnotatedSection ann)
                || observerTags.containsAll(ann.requiredTags()))
        .toList());
```

The YAML surface defines structure (what types exist). The registry defines behavior (what those types do). New behavior composes with existing structure — it does not extend the type vocabulary.

### Why this is non-obvious

A developer seeing both `@JsonSubTypes` (closed type set) and a runtime registry (open extension point) would reasonably expect the registry to handle new type names. The architecture looks extensible. But the extension point is at the wrong layer — it's post-deserialization, not during deserialization. The error surfaces at YAML parse time, far from the registry where the custom logic is defined.

### Alternatives considered

- Adding a Jackson `TypeResolverBuilder` to dynamically register subtypes — possible but invasive, requires replacing the annotation-driven resolver
- Using `@JsonTypeInfo(defaultImpl = ...)` to catch unknown types — breaks the sealed interface exhaustiveness guarantee
