### Summary

When two JAX-RS resources share the same path prefix (e.g. `/api/applications/{id}/services/{serviceId}`), add an `/ops` sub-path to the operational resource to avoid ambiguous method routing.

### Context

`ScalingResource` owns `POST /api/applications/{appId}/services/{serviceId}/scale`. `ServiceOperationResource` also needs endpoints under `/services/{serviceId}` — status, scale, upgrade. Having two `@ApplicationScoped` resources with the same `@Path` causes ambiguous routing in Quarkus REST.

### Convention

Give the operational resource a distinguishing sub-path:

```java
// ScalingResource — owns the scaling concern directly
@Path("/api/applications/{appId}/services/{serviceId}")
public class ScalingResource { ... }

// ServiceOperationResource — aggregated ops view
@Path("/api/applications/{id}/services/{serviceId}/ops")
public class ServiceOperationResource { ... }
```

### Alternative

Merge all service-level operations into a single resource class. Rejected because ScalingResource has its own CDI dependency graph (evaluator, cooldown checker) that would bloat the combined class.

### Why this is non-obvious

JAX-RS path conflicts manifest as deployment failures or silent method shadowing — the error messages don't always point to the conflicting resource pair.
