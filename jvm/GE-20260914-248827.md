## Symptom

A Maven plugin code generator scans Jandex indexes for framework-specific annotations (e.g. `io.quarkiverse.mcp.server.Tool`) but pulling the framework as a test dependency adds heavyweight transitive deps, version conflicts, and slow builds.

## Context

Maven plugin generators that use Jandex read annotation metadata from bytecode indexes. The scanner uses `DotName.createSimple("io.quarkiverse.mcp.server.Tool")` to match annotations — it never resolves the annotation class at runtime. This applies to any Jandex-based scanner, not just Maven plugins.

## Root cause

Jandex indexes class names as strings in bytecode. It does not perform runtime class loading or type identity checks. The scanner matches annotations by their fully-qualified name, not by class reference equality.

## Fix

Create minimal annotation stubs in `src/test/java` with the exact FQN of the target annotation. The stub only needs the annotation's retention and target — no implementation:

```java
// src/test/java/io/quarkiverse/mcp/server/Tool.java
package io.quarkiverse.mcp.server;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Tool {
    String value() default "";
}
```

Build the Jandex index in tests using the standard `Indexer`:

```java
var indexer = new Indexer();
indexer.indexClass(SampleToolsFixture.class); // uses the stub @Tool
Index index = indexer.complete();

var scanner = new ToolScanner();
List<ToolDescriptor> tools = scanner.scan(index);
// scanner sees @Tool by DotName — identical to real annotation
```

### Why this is non-obvious

Most developers reflexively add the real framework dependency (`quarkiverse-mcp-server`) as a test dependency. This works but pulls in the full Quarkus MCP runtime with its transitive tree. The insight is that Jandex's string-based matching means the actual annotation class identity is irrelevant — only the FQN in bytecode matters.

### Alternatives considered

- **Real dependency as test scope**: Works but adds 20+ transitive deps, version conflict risk, and slower builds. Rejected for generator modules that should have minimal dependency footprint.
- **Mocking the Jandex Index**: Possible but verbose — you'd need to mock `AnnotationInstance`, `ClassInfo`, `MethodInfo` chains. The stub approach lets you use the real `Indexer` with real bytecode.
