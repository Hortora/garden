### Symptom

Intermittent `NullPointerException` or "definition not found" errors during integration tests.
Failures migrate between unrelated test classes on each run. All tests pass individually.

### Context

A CDI `@ApplicationScoped` registry stores case definitions in a `ConcurrentHashMap`.
On lookup miss, a lazy fallback re-registers all definitions by iterating over CDI beans
and calling `map.put()` for each. Multiple virtual threads call `getCaseDefinition()`
concurrently during worker completion handling.

### What was tried (didn't work)

ConcurrentHashMap — assumed to be "thread-safe" for this use case. Per-entry operations
(get, put, computeIfAbsent) are atomic, but sequential puts across a loop are not batch-atomic.
A concurrent reader observes the map mid-population: after definition A is inserted but before
definition B. Lookup of B returns null.

### Root cause

ConcurrentHashMap provides per-entry atomicity (each put/get is individually thread-safe)
but not batch atomicity. When `registerKnownDefinitions()` inserts entries one at a time
in a for-loop, any concurrent `get()` can observe the map in a partially populated state.
The race window scales with the number of definitions — more definitions means more time
between first and last put.

### Fix

Replace the mutable ConcurrentHashMap with a volatile reference to an immutable Map.
Build the entire registry in a local HashMap, then publish via a single volatile write:

```java
private volatile Map<CaseKey, RegistryEntry> registry = Map.of();

void registerKnownDefinitions() {
    Map<CaseKey, RegistryEntry> snapshot = new HashMap<>();
    for (CaseHub hub : caseHubInstance) {
        registerSingle(hub.getDefinition(), snapshot);
    }
    this.registry = Map.copyOf(snapshot);  // single atomic publish
}
```

Readers see either the old snapshot (empty) or the fully populated new one — never partial
state. No lock contention on the read path. `Map.copyOf()` creates an unmodifiable copy,
guaranteeing immutability.

### Why this is non-obvious

ConcurrentHashMap is the standard recommendation for shared mutable maps. Its javadoc
says retrieval operations "do not entail blocking" and "there is no support for locking
the entire table." Developers read this as "thread-safe map" and assume batch operations
inherit that safety. The per-entry atomicity guarantee is correct but insufficient when
the semantic unit is the entire map contents.

### Why this fix

The volatile snapshot swap avoids ReadWriteLock (which adds contention on every read in
the hot path) and eliminates the lazy re-registration race entirely. `Map.copyOf()`
produces an optimised immutable implementation that performs better than ConcurrentHashMap
for read-heavy workloads.

### Alternatives considered

- **ReadWriteLock** — correct but adds lock contention on every lookup in the hot path.
  Registration is rare; lookups are per-request. The read lock cost is measurable.
- **Eliminate lazy re-registration** — simpler but removes the self-healing behaviour
  for stale CDI bean instances across Quarkus test restarts.

### Caveats

Single-definition registration after startup uses a read-modify-write on the volatile
reference (copy current map, add entry, publish). Two concurrent calls could experience
a lost update. Acceptable when registration is sequential at startup.
