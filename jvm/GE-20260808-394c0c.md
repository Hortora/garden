### Symptom
Intermittent `OptimisticLockException: Unexpected row count (expected 1 but was 0)` when calling `expiryService.checkExpired()` or `expiryService.expireItem()` in a `@QuarkusTest`. The error references a WorkItem that the current test just created. Passes in isolation; fails in full suite.

### Context
Multiple `@QuarkusTest` classes share the same H2 database instance within a single Surefire run. Test classes that create WorkItems with past `expires_at` deadlines don't always clean them up. The Quartz scheduler (`quarkus.scheduler.start-mode=forced`) is active in tests.

### What was tried (didn't work)
- `@AfterEach` cleanup in the failing test class — doesn't help because the leaked items come from *other* test classes that already ran
- Running the test in isolation — passes, confirming cross-class contamination

### Root cause
Two concurrent code paths process the same expired WorkItem:

1. **Cross-class leakage:** Test class A creates a WorkItem with a past deadline. Test class B calls `checkExpired()`, which finds ALL expired items in H2 — including class A's leaked item.

2. **Quartz race:** When a WorkItem is created with a past `expires_at`, the Quartz scheduler immediately schedules a `work-expiry.expiry-{id}` job. If the test also calls `expireItem()` for the same item, both the Quartz job and the test method update the same WorkItem version concurrently → OptimisticLockException.

The symptom (OptimisticLockException) misleads toward a locking or transaction issue. The root cause is test isolation — stale data from other test classes.

### Fix

**For cross-class leakage:** Clean up stale data in `@BeforeEach` before seeding test-specific data:

```java
@BeforeEach
@Transactional
void setup() {
    LifeTaskContext.deleteAll();
    WorkItem.deleteAll();
    // ... seed test-specific data
}
```

For ordered test classes (`@TestMethodOrder`), guard cleanup to avoid deleting data needed by later ordered methods:

```java
@BeforeEach
@Transactional
void setup() {
    if (staticFieldFromOrder1 == null) {
        LifeTaskContext.deleteAll();
        WorkItem.deleteAll();
    }
    LifeTestFixtures.seedStandardTemplates();
}
```

**For Quartz race:** Replace direct `expireItem()` with Awaitility — let the Quartz scheduler handle expiry and poll for the expected outcome:

```java
await().atMost(10, TimeUnit.SECONDS).untilAsserted(() ->
    given()
        .when().get("/life-tasks/" + workItemId)
        .then().statusCode(200)
        .body("candidateGroups", hasItem("household-admin")));
```

### Why this is non-obvious
The OptimisticLockException stack trace points to a specific WorkItem ID that the test just created — nothing suggests the problem is a *different* WorkItem from a *different* test class causing `checkExpired()` to race. The Quartz scheduler runs silently in tests; its interaction with manual `expireItem()` calls is not visible unless you check the Quartz thread pool logs.
