### Symptom
Need multi-tier SLA escalation (tier1 -> tier2 -> tier3 -> manager -> exhausted) but `SlaBreachPolicy` is stateless — no persistence, no breach counter.

### Context
SOC incident response needs priority-differentiated escalation chains. The policy receives `SlaBreachContext` with `BreachedTask.candidateGroups()` but no breach history.

### Technique
The WorkItem's `candidateGroups` IS the state. Each `EscalateTo` execution replaces the groups:

```java
// ExpiryLifecycleService.executeEscalateTo():
item.candidateGroups = String.join(",", escalate.groups());
```

The policy reads the current groups to determine the tier, then returns a flat (non-Chained) decision:

```java
public BreachDecision onBreach(SlaBreachContext context) {
    Set<String> groups = context.task().candidateGroups();
    if (groups.contains(SocGroups.SOC_MANAGER))
        return new BreachDecision.Exhausted("SLA exceeded");
    if (groups.contains(SocGroups.TIER3_ANALYST))
        return BreachDecision.EscalateTo.to(SocGroups.SOC_MANAGER).withDeadline(...);
    if (groups.contains(SocGroups.TIER2_ANALYST))
        return BreachDecision.EscalateTo.to(SocGroups.TIER3_ANALYST).withDeadline(...);
    return BreachDecision.EscalateTo.to(SocGroups.TIER2_ANALYST).withDeadline(...);
}
```

Each breach event independently reads updated groups → returns the next tier → work module updates groups → next breach reads new groups.

### Why this is non-obvious
The natural instinct is to track breach count or use `thenOnBreach()` chains. Both are wrong — breach count requires persistence the SPI doesn't provide, and `Chained` is atomic fallback not cross-breach sequencing (see GE-20260810-793376). The groups-as-state pattern avoids both traps.
