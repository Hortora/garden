### Symptom
`ChannelProjection<S>.apply(S, MessageView)` takes `MessageView`. `MessageObserver.onMessage()` delivers `MessageReceivedEvent`. These are different record types with overlapping but non-identical fields. No conversion utility exists.

### Context
`MessageReceivedEvent` has: messageId, channelName, channelId, tenancyId, messageType, senderId, target, actorType, correlationId, occurredAt, content, topic.

`MessageView` has: id, channelId, sender, type, content, correlationId, inReplyTo, target, topic, artefactRefs, actorType, createdAt, deadline, replyCount.

Four fields are absent from the event: `inReplyTo`, `artefactRefs`, `deadline`, `replyCount`.

### Root cause
The two types serve different purposes — `MessageReceivedEvent` is the observer callback payload, `MessageView` is the read-model for projections and queries. No bridge was needed until `ChannelProjection` consumers needed to fold from observer callbacks rather than from stored messages.

### Fix
Build the MessageView manually with null/empty defaults for missing fields:

```java
private static MessageView toMessageView(MessageReceivedEvent event) {
    return new MessageView(
        event.messageId(), event.channelId(), event.senderId(),
        event.messageType(), event.content(), event.correlationId(),
        null,        // inReplyTo
        event.target(), event.topic(),
        List.of(),   // artefactRefs
        event.actorType(), event.occurredAt(),
        null,        // deadline
        0);          // replyCount
}
```

### Why this is non-obvious
You'd expect either a `MessageReceivedEvent.toMessageView()` method or a utility in qhorus-api. Neither exists. The field mapping requires reading both record definitions to match names (senderId→sender, messageType→type, occurredAt→createdAt) and identify which fields to null out. Existing projections (ConversationProjection) only read sender, type, content, correlationId, and topic — so the null defaults are safe for all current use cases, but a future projection requiring inReplyTo or artefactRefs would silently get wrong data.
