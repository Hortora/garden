### Symptom
Designing a dynamically-created channel observer (not a CDI bean), you assume `ChannelManager` has `addObserver(UUID channelId, MessageObserver observer)` / `removeObserver()` methods. It does not.

### Context
`ChannelManager` is a lifecycle API — `create()`, `delete()`, `pause()`, `resume()`, `setTypeConstraints()`, etc. It manages channel state but has no observer registration.

### Root cause
`MessageObserverDispatcher` (runtime package, not API) discovers all `MessageObserver` instances via CDI `Instance<MessageObserver>` handles. The dispatcher is called from the message dispatch path with `Iterable<? extends Instance.Handle<MessageObserver>>`. Each handle is resolved via `handle.get()`, filtered by `observer.channels()` (channel names, not IDs), and dispatched if matching.

### Fix
Make your observer type implement `MessageObserver` and register it as a CDI bean (`@ApplicationScoped` or `@Produces`). The channels() method returns channel name strings for filtering. For non-CDI environments (testing), call `onMessage(MessageReceivedEvent)` directly.

```java
@Produces @ApplicationScoped
MyObserver observer() {
    return new MyObserver("channel-name");
}
```

### Why this is non-obvious
`ChannelManager` is the obvious place to look for observer registration. Its API has 12 methods for channel lifecycle management but nothing for observer management. The actual registration mechanism is in a runtime-internal class (`MessageObserverDispatcher`) that uses CDI's `Instance<T>` injection — a pattern invisible from the API surface.

### Alternatives considered
- Direct `ChannelManager.addObserver()` — does not exist
- `EventStreamBus` bridge via `ChannelEventAdapter` — carries extracted domain events (type E), not raw MessageView; projection needs MessageView
- Decoupled `Function<Consumer, Cancellation>` subscriber — pushes wiring complexity to consumer
