### Context

Implementing `SituationDefinitionProvider.registrations()` for fsitrading adaptive ops (casehub-ops#25). The RAS API has three sealed interfaces for situation configuration: `ChainMode`, `TriggerAction`, and `TriggerMode`. The actual permitted variants differ from the names a developer would guess.

### The mismatches

| Interface | Intuitive name | Actual variant | Notes |
|---|---|---|---|
| `ChainMode` | `Single(ganglionId)` | `Count(ganglionId, count)` | Use `count: 1` for single-detection semantics |
| `TriggerAction` | `Noop()` | `NotifyOnly()` | Fires situation events without creating a case |
| `TriggerAction` | — | `CreateCase(CaseTriggerConfig)` | Exists as expected |
| `TriggerMode` | `Continuous()` | `Repeating(Duration interval)` | Requires an explicit refresh interval |
| `TriggerMode` | — | `FireOnce()` | Exists as expected |

### Why this is non-obvious

The names are semantically close enough that a developer writes `ChainMode.Single`, `TriggerAction.Noop`, `TriggerMode.Continuous` — all compile-time errors with no suggestion of the correct name. The sealed interface's `permits` clause is only visible in source or bytecode, not in javadoc. The existing reference implementation (`DeploymentTopologySituationDefinitionProvider` in ops#84) uses `ChainMode.Streak` which is a different variant entirely, so it doesn't demonstrate `Count`.

### How to discover the actual variants

```bash
javap -p <jar>!/io/casehub/ras/api/ChainMode.class
javap -p <jar>!/io/casehub/ras/api/TriggerAction.class
javap -p <jar>!/io/casehub/ras/api/TriggerMode.class
```

Or use IntelliJ's type hierarchy on each sealed interface.
