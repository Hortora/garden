# JPA Flyway migrations with GEN_RANDOM_UUID() fail on H2 — PostgreSQL-specific function

## Symptom

`FlywayMigrateException: Failed to execute script V1__create_cbr_case.sql` with `org.h2.jdbc.JdbcSQLSyntaxErrorException: Function "GEN_RANDOM_UUID" not found` when running PostgreSQL-targeted Flyway migrations against H2.

## Context

`casehub-neocortex-memory-cbr-jpa` ships with Flyway migrations at `classpath:db/cbr/migration` that use `GEN_RANDOM_UUID()` — a PostgreSQL-specific function. When the consuming application uses H2 (file-persistent or in-memory) instead of PostgreSQL, these migrations fail at startup.

## Fix

Skip Flyway for the CBR datasource and use Hibernate schema generation instead:

```properties
# Instead of:
quarkus.flyway.migrate-at-start=true
quarkus.flyway.locations=classpath:db/cbr/migration

# Use:
quarkus.hibernate-orm.database.generation=update    # production
quarkus.hibernate-orm.database.generation=drop-and-create  # tests
```

Hibernate generates H2-compatible DDL from the `@Entity` annotations. The `update` strategy creates tables if missing and adds columns if new — safe for pre-release. For production PostgreSQL deployments, use the original Flyway migrations.

## Why this is non-obvious

The JPA module's pom.xml description says "for PostgreSQL with JSONB features" but this is easy to miss. The module's `@Alternative @Priority(3)` annotation and CDI wiring suggest it should work with any JPA-compatible database. The PostgreSQL dependency is marked `<optional>true</optional>`, further suggesting database independence.
