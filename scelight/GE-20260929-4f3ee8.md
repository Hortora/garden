### Symptom
Feature extraction from SC2 replays misses ~66% of rapid-fire commands (e.g., warp-in units). Only the first command in a rapid-fire sequence is captured.

### Context
SC2 records rapid-fire commands (holding a hotkey while clicking multiple locations) as:
1. One `CmdEvent` (game event ID 27) — the initial command with full ability data (abilLink, abilCmdIndex, targetPoint)
2. One or more `SCmdUpdateTargetPointEvent` (game event ID 104) — each subsequent click at a new location

The SC2 protocol `.dat` files define ID 104 as `NNet.Game.SCmdUpdateTargetPointEvent`, but Scelight's `GameEventFactory` has no `case` for ID 104. These events fall through to the base `EventFactory.create()`, which returns a plain `Event` object — no typed subclass.

### Root cause
Any code that dispatches on `raw instanceof CmdEvent` (the standard pattern for processing game events) silently skips all rapid-fire repeat commands. The events exist in the replay data but are invisible to type-based dispatch.

### Fix
Check for event ID 104 alongside `CmdEvent` dispatch. The plain `Event` carries `userId` and `loop` but no ability data — use the abilLink from the most recent `CmdEvent` for the same player:

```java
TrainIntent lastWarpIn = null;

for (Event raw : gameEvents) {
    if (raw instanceof CmdEvent cmd) {
        lastWarpIn = null; // clear on new command
        // ... normal dispatch ...
        if (isWarpIn(cmd)) {
            lastWarpIn = extractTrainIntent(cmd);
        }
    } else if (raw.getId() == 104
               && raw.getUserId() == userId
               && lastWarpIn != null) {
        // Repeat warp-in at new target point
        handleTrain(lastWarpIn, raw.getLoop(), ...);
    }
}
```

### Why this is non-obvious
The symptom (low warp-in coverage) pointed to missing abilLink mappings — the obvious hypothesis. Diagnostic investigation showed abilLink=214 was correct and all CmdEvents were being processed. The actual cause (a completely different event type carrying the repeat commands) required cross-referencing oracle tracker events against raw game event counts to discover. The Scelight library's lack of a typed class for ID 104 made the events invisible to standard dispatch patterns.

### Why this fix
Tracking the last command per player and replaying it on ID 104 is the minimal change. The alternative — adding a full `CmdUpdateTargetPointEvent` class to Scelight — would be more correct but requires modifying the library fork and updating the protocol-aware deserialization. The replay-it approach works because rapid-fire always repeats the same ability.

### Alternatives considered
- **Adding a typed class to Scelight's GameEventFactory:** More architecturally correct, but requires forking deeper into the parser library. The event struct doesn't carry ability data anyway — only the target point changes.
- **Correlating with oracle tracker events:** Would be perfectly accurate but defeats the purpose (stripped replays don't have tracker events).

### Caveats
- ID 104 events after a warp-in may include target adjustments (player re-clicking), not just new warp-ins. This causes ~10% over-emission.
- The event ID (104) is protocol-version-dependent — verify against the `.dat` file for the replay's base build.
